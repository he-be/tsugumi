# 画像デモ (プレフィル進捗・ストリーミング・生成速度)

`sample_imgs/` の画像を選ぶと、その 1 枚がプレフィルに入り、トークンが出て、
速度が動く — その様子をブラウザで見るためのデモ。1 コマンドで
[16K サーバー](../../docs/SERVER_RUNBOOK.md) を起動し、ウォームアップまで済ませ、
終了時にそのサーバーを止める。

```bash
python3 Scripts/demo/serve.py          # http://127.0.0.1:8799/ が開く
```

止めるのは Control-C。**この起動したサーバーだけ**を止めてから終了する。
必要なのは `swift build -c release --product TurboFieldfareServer` と
`scratch/gemma4-qat.gturbo` (vision タワーとドラフターを含むもの) だけで、
Python の追加パッケージは要らない。

| フラグ | 既定 | 意味 |
| --- | --- | --- |
| `--model` | `scratch/gemma4-qat.gturbo` | 使うモデル |
| `--model-port` | 8091 | TurboFieldfareServer 側のポート |
| `--port` | 8799 | このデモ UI のポート |
| `--no-open` | — | ブラウザを自動で開かない |

## 起動の流れ

`プロセス確認 → 起動 → モデルロード → ポート開通 → ウォームアップ → 準備完了`。
この 6 段はブラウザのオーバーレイにそのまま出る (サーバーの stderr 付き)。

- **プロセス確認**: AGENTS.md の `pgrep` 一覧を見る。**既に何か動いていたら自分では
  起動しない**。8091 が答えるならそれに接続し (`owned: false`)、終了時にも**止めない**。
  答えないならエラーで止まる — 他人のプロセスを殺さない。
- **起動**: SERVER_RUNBOOK §1(a) の 16K 構成
  (`--max-context 16384 --expert-cache-slots 80 --verification trusted-install
  --draft-block-size 4`)。
- **ウォームアップ**: テキスト 1 回、画像 1 回。画像側はこの場で作った 96x96 の PNG で、
  vision タワーの初回コスト (M3 Pro 18GB で約 5〜11 秒) を最初の 1 枚に払わせないため。
  これが済むまで「実行」ボタンは押せない。

## 進捗をどこから取っているか

Chat Completions が返すのは生成トークンだけで、プレフィルの途中は何も出ない。
一方サーバーは stderr にリクエストの節目を書く:

```
request chatcmpl-… prepared prompt=304     ← プロンプトのトークン数 (プレフィル開始前)
request chatcmpl-… generating              ← プレフィル開始
request chatcmpl-… completed in 22.9s … accept=1.400
```

`serve.py` はこの stderr を読み、`/api/events` (SSE) に流し直す。ブラウザは
ストリーミングの最初のチャンクで受け取る `chatcmpl-…` の id で突き合わせる。
ログ行の方が先に着くので、id が分かった時点で溜めた行を再生する。

その結果、画面の値は次のようになる:

| 表示 | 出どころ |
| --- | --- |
| プロンプト tok | `prepared prompt=N` (**実測**、プレフィル開始前に分かる) |
| プレフィルのバー | **推定**。`generating` からの経過を推定所要時間で割ったもの |
| プレフィル s / TTFT | **実測**。`generating` から最初のトークンまで |
| 生成速度 tok/s | **実測**。直近 2 秒の窓、完了時は全体の平均に置き換わる |
| 生成トークン | ストリーミング中はデルタ数、完了時は `usage.completion_tokens` |
| MTP 受理長 | `completed … accept=` |

**バーだけが推定である。**画像のプレフィルはトークン数では決まらない — 304 トークン
(画像 1 枚 + テキスト 44) で 13.6 秒かかる一方、テキスト 36 トークンなら 1.6 秒で、
差はタワーの処理時間である。そこで所要時間を

    固定費 0.6 s + 画像枚数 x (1 枚あたりの秒数) + テキスト tok / (tok/s)

と置き、後ろ 2 項を実測から EMA で更新して localStorage に残す (次回以降のバーが
この機体の実測に寄っていく)。テキスト側のレートは 512 トークン以上のプロンプトでしか
更新しない — 短いプロンプトは固定費しか語らないため。

## 送信するもの

ブラウザ内の canvas で長辺 1024 px / JPEG 品質 0.85 に縮めてから
`data:` URI で送る (`sample_imgs/caption.py` と同じ考え方)。タワーはどのみち
リサイズするので、フル解像度を送っても base64 が太るだけである。

サーバー側の制限がそのままデモの制限になる: 画像は 1 リクエスト 4 枚まで、
`data:` URI のみ、**画像リクエストはプロンプトキャッシュを使わない** (毎回フル
プレフィル)、tools とは併用できない。デモは tools を宣言しない。
