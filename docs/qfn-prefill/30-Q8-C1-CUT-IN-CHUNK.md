## 0. 結論

1. **C1 を作った。**チャンクをチェックポイントの位置で切らず、forward の中で切れ目の行の後の GDN 状態・conv 履歴・PLE 履歴を写し、そこからチェックポイントを作る (`Qwen38Runner.cutRows`)。
   GDN は切れ目で区間に分けて回し、区間の終わりで状態を写す。conv と PLE の履歴は、履歴のカーネルを写しに対して T = c で回す。2 機はプロトコル v3 で、M6 が層 0〜45 の切れ目の状態を返す。
2. **単体では、本文 2 の 1 ターンの prefill 合計が 157.019 s (156.068〜157.474) → 141.555 s (141.144〜142.269)、差 15.464 s (導出)。**閾値 3.06 s を超える。
   末尾のチャンク (T < 32) の和 43.49 s (3 run) が 0 になり、大きいチャンクの壁時計は 19.988 → 19.788 s で変わらない。検査 (`--qwen38-resume`) は split と同じ結果。
3. **2 機では inchunk の 3 本中 2 本が 6・7 ラウンド目で `pair link: recv: closed` で止まった。**M6 の Swapouts は run の前後で 50,184・76,954・26,384 ページ (split は 3 本とも 0)。
   M6 の serve が見張りに止められたと見られる (serve のログは最後の run の分しか残らない、27 §2 (c))。切れ目 1 本あたり、M6 の層 0〜45 の写し約 112 MB をフォワードの間持つ (導出)。
   **→ 写しは原因ではなかった。M6 の serve は inchunk だと末尾チャンクが消えてバッチのスクラッチ (約 2.8 GB) を縮めなくなる ([31](31-Q8-C1-PAIR-SCRATCH-SHRINK.md))。**

## 2. 分かったこと / 外れたこと

1. **29 §1.2 の見込み (末尾のチャンクを消すと単体の切片が約 2 s 縮む) は本文 2 で当たった** (8.00 → 5.88 s、導出)。1 ラウンドあたり 1.9〜2.7 s 短い。
2. **2 機では M6 の RAM が足りない。**Q6 の 10 層の構成は wired 最大 13.51〜13.58 GB で余裕が無く ([27 §2](27-Q6-A-BUILT.md) の 2)、C1 の写し (切れ目 1 本 約 112 MB、ラウンド 1 は 2 本) で溢れたと見られる。
   止まったのは文脈が長いラウンド (7.7K・9.6K)。M6 のラウンド後の metal allocated は 13.55〜13.68 GB (r3 の `serve.m6.log`)。
3. **既定には入れていない。**単体は 04 の条件 (検査を通り、交互に取った壁時計が閾値以上縮む) を満たすが、`Q38_CUT_INCHUNK` はエンジンの設定で、2 機 (`Q38_PAIR`) でも同じ経路を通る。今のままでは 2 機で止まる。
4. 単体の Swapouts は inchunk で 36〜76 ページ出た (split は 0〜8)。有効条件ではない (24)。
