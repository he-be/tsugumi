# 05. 罠

[m6-prefill/05](../m6-prefill/05-RISKS.md) の 13 項目 (16 GB のページキャッシュ、単体ベンチの符号反転、主スレッドの I/O、熱、Xcode 無し、機械を混ぜない、既定を動かさない、比で盛る) は
そのまま効く。ここには QFN と 2 機で足すものだけ。

## 1. link-local の IP が変わる

TB の直結は両端とも 169.254.x.x の自動割り当てで、繋ぎ直すと変わる。`~/.ssh/config` の `m6-tb` は 1 日で古くなった ([01 §3](01-ROLES.md))。
**対策**: M6 側のプロセスの bind 先と MBP の接続先は、起動のたびに `ifconfig bridge0` から取る (`cycle.sh` がやる)。証拠の `link.txt` に両端の IP を残す。
Tailscale 側 (`ssh m6`) は常に通るので、link-local が通らないときの起動はそちらで行い、データは流さない。

## 2. 生 TCP の速さは未確認

TWO_MACHINE_DEV §3 の 37.8 Gb/s は証拠ディレクトリが無い。この日の `nc` は失敗した (M6 側で listen が残らない)。
**対策**: E0 で 84 MB 片道と 21 MB 往復 × 48 を取る。B は往復が 48 回あるので、rtt と往復の重なり方がそのまま式に入る。decode は往復の rtt が効く (Q7)。

## 3. 2 機の OS とツールチェーンが違う

MBP は macOS 15 / Swift 6.3.3、M6 は macOS 27 / Swift 6.4。MSL のバージョンも MPS の中身も違う。**2 機の logits は同じにならない** (GPU の丸め順)。
**対策**: Q6 で許容幅を先に置く。fp32 の残差 / 部分和をそのまま渡し、fp16 で送らない。E4-(b) の fp16 tensor ops は相対差を先に測る。greedy の本文は記録するだけで止めない。

## 4. M6 の 16 GB

QFN の dense のビューは全層で 5.4 GB、expert のビューは 32.8 GB ([qwen38/09 §1](../qwen38/09-12K-MEMORY-VERIFY.md))。A では M6 に層 0〜k−1 の dense・KV・GDN 状態・バッチ領域が乗り、B では担当分の expert のビューとバッチ領域だけが乗る。
decode で wired 12〜15 GB に達した単体 ([qwen38/15 §1](../qwen38/15-DECODE-PLAN.md)) に対して M6 は 16 GB。**E1 (M6 で今のコードのまま 4K の 1 チャンク) が乗らなければ A は落ちる** ([04 Q1](04-GATES.md))。
**対策**: 両機の run に `vm_stat` の Swapouts と `Q38_MEM_LOG` を付け、Swapouts が出た run は不合格 (Q1・Q5・Q6)。`iogpu.wired_limit_mb` を上げて逃げない (再起動で戻る上、記録値の条件が変わる)。

## 5. 外付け SSD は手動マウントで、PLE はそこにしか無い

ヘッドレスの M6 は再起動後に `/Volumes/SSD256` が付かない。**PLE BF16 は外付けにしか置いていない**ので、E1 と A の M6 側は起動時に PLE のパスを確かめて、無ければ止まる。B では M6 に PLE が要らない。
**対策**: `cycle.sh` が `diskutil mount disk5s1` を先にやる。外付けの型番は未記載 (m6-prefill/44) なので、劣化や熱で 1.57 GB/s を割っても気付けない。`link.txt` と同様に `run-N.pre.txt` の `iostat` で読む。

## 6. PLE のランダム読みは外付けで遅い

外付けは 3.36 MB のランダム読みで p50 8.5 ms (QD4、[03 §4](03-FACTS.md))。PLE の行は 320 B で、1 チャンク 32,768 本。今の形 (host 1 スレッド、順に触る) では
1 本ごとの遅延が全部足される。**対策**: Q2 を Q1 と並行で先にやる。E1 では PLE の秒 (p_M6) を別に出し、d / r / s の判断に混ぜない。A の式に入る p_M6 は Q2 の後の値も並べる。

## 7. 1 チャンクのラウンドでは重ならない

アプリのラウンドの 8 割は新規が 2048 未満 ([qwen38/33](../qwen38/33-FEWER-ROUNDS-FASTER-PREFILL-PLAN.md))。そこでは A の 2 機の秒は和で、[08 §3](08-CANDIDATES.md) の「定常」の列は当てはまらない。B は 1 チャンクでも両機が同時に働くが、往復 48 回が乗る。
**対策**: A / B の選択も台帳も、本文 2 (記録の再生、ラウンドの分布込み) で判定する。本文 1 (2345〜2499 トークン、2 チャンク) だけで「速くなった」と書かない。

## 8. 先読み・常駐は一度閉じている

[qwen38/13](../qwen38/13-KERNEL-TO-GPU-WAIT.md) と [15 §0-2](../qwen38/15-DECODE-PLAN.md) で、RAM を使う先読み・上位 N・常駐は「RAM を使えば速いというだけ」として閉じた。
Q5 はページキャッシュを使わない固定の置き場で、その判断を上書きする提案ではない。**ユーザーが同じ判断なら Q5 は外す** (README の判断待ち 3)。

## 9. 2 つのモデルプロセス

AGENTS.md の「他のモデルプロセスが動いていたら止める」は 1 機の中の規則。2 機では MBP に 1 つ、M6 に 1 つが正常。
**対策**: `pair_bench.sh` は各機で `pgrep` し、**同じ機械に 2 つ**あるときだけ拒む。M6 側のプロセスは MBP が起動し、MBP が止める (他人のものを止めない)。

## 10. TB を常設しないなら、link が無い日がある

TWO_MACHINE_DEV §3 は「TB4 直結は当てにしない」。運用の形が 2 機なら常設が前提で、その読み替えは README の判断待ち 2。
**対策**: A / B どちらも「M6 が居なければ単体」を既定にする ([08](08-CANDIDATES.md))。2 機の行と単体の行を両方持つ台帳がその形。

## 11. 転送した重みの照合

M6 に置いた本体は `SHA256SUMS` で、PLE BF16 は両機の `shasum` で照合する ([03 §5](03-FACTS.md))。照合済み。

## 12. 単体ベンチの秒を式に入れるときの罠

E1 / E4 で取る d・r・s は単体ベンチと 1 チャンクの値で、本番ループでは順序と重なりが違う (m6-prefill/05 §2)。式の予測と Q6 の実測が 1 割以上ずれることを前提に、
ずれた量を結果文書に書く ([04 Q6](04-GATES.md))。式は分け方を選ぶためだけに使い、進捗や目標にしない。
