## 0. 前提の変更

[16](16-Q1-F4-RESIDENCY.md) はランタイムと同じく page cache に置く形 (他のプロセスに追い出されても動く、Tsugumi の要件) で測った。
**M6 は推論専用なのでこの要件は要らない (ユーザー、2026-09-25)。**ここでは担当分をプロセス自身の MTLBuffer に `F_NOCACHE` の pread で読み、MTLResidencySet で GPU に固定する。
入らない層は、固定の置き場に毎回 `F_NOCACHE` で読む。読んだ範囲はそのたびに `msync(MS_INVALIDATE)` で page cache から落とす (GGUF を mmap しているプロセスでは `F_NOCACHE` の読みもキャッシュに残った、MBP の試走)。

## 1. 結論

1. **自前のバッファに常駐できるのは 11.10 GB まで** (A の形の層 0..<17、作業領域 1 GB、wired limit 14336 MB)。11.71 GB (層 0..<18) では Swapouts が出た。page cache の形 (16) の 12 GB より少ない。
   11.10 GB のとき wired は 13.35〜13.47 GB で、wired limit (15.03 GB) に届く前に RAM が足りなくなった。
2. **超えた分は崖にならない。**常駐 11.10 GB のまま担当分を 14.41 / 16.48 GB にすると、1 回の読みは 0.99〜1.00 / 1.63〜1.64 s で、4 回とも同じ。流した量 3.31 / 5.38 GB を約 3.3 GB/s で読んだ秒 (導出)。
   page cache の形の 14.41 GB は 4 回目に 3.38〜3.92 s (16) だった。
3. B の形 (各層の expert の上側) も同じ向き。常駐 10.88〜10.99 GB で、担当分 14.00 / 16.02 GB の 1 回の読みは 0.91〜0.94 / 1.55〜1.56 s。

## 3. 分かったこと / 外れたこと

- 11.10 と 11.71 GB の間の上限の位置は刻んでいない (層単位で 0.61 GB 刻み)。
- 自前の形の上限が page cache の形 (12.39 GB は残った) より低い理由は確かめていない。
- 作業領域は触った 1 GB の匿名メモリで代えた。F2・F3 で M6 のプロセスが持つ量が 1 GB を超えれば、その分だけ常駐は減る (未確認)。
- wired limit は 14336 MB の 1 条件だけ (ユーザーの指示)。上限は wired limit より先に RAM で決まったので、この条件ではこれを上げても常駐は増えない (導出)。
- route は 1 チャンク分を 4 回。GEMM の秒は F1 ([15](15-Q1-F1-LAYER.md))。

## 4. 次の Gate に渡すもの

- **F2・F3 の M6 側は自前のバッファの形。**常駐は 11.10 GB まで (作業領域 1 GB のとき)。超えた分は 1 回ごとに約 3.3 GB/s の読みの秒を足す (崖ではない)。
- k / σ の格子は常駐の上限で打ち切らなくてよい。常駐 11.10 GB と流す分の秒を式に入れて出す。
- 16 (page cache の形の 12 GB) は、ランタイムと同じ形の値として残す。
