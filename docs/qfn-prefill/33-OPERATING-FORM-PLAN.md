## 0. 結論

1. **運用の形**: MBP がアプリ・サーバー・decode・prompt cache を持つ (P6、[22](22-Q6-P6-DECODE-PLACEMENT.md))。M6 は TB4 直結の先で層 0〜k−1 (k 46) を引き受ける。
   M6 が繋がっていれば 2 機、繋がっていなければ単体。**切り替えはユーザーがボタンで明示する。自動で 2 機に切り替えない。**アプリは M6 に届くときだけボタンを有効にし、途中で link が切れたら単体に落ちて表示もそれに従う。
2. **閉じる判断待ち**: 1 (記録値は MBP の壁時計で単体・2 機の 2 列、台帳 [06](06-LEDGER.md) は既にこの形) と 2 (TB4 は常設でなく「居れば使う」)。判断待ち 3 (Q5 の MBP 側の RAM) は残る (§3)。
3. **残り作業の本体はボタンの実装 (§1)。**Gate で残るのは Q8 の合格判定、Q7 の decode の判別、Q3 で、どれもこの形の判断で変わらない (§3)。

## 1. ボタンのために作るもの (未着手)

コードの現状: 2 機は `Q38_PAIR=<M6 の bridge0 IPv4>[:port]` と `Q38_PAIR_K` を `Qwen38Completion` の初期化で 1 回読むだけ (`Qwen38Pair.configured`)。
link が失敗したラウンドは `pair_off` を記録して単体で回り、次のラウンドで繋ぎ直して層 0〜k−1 の状態を最初から送り直す (`pairRound`)。
M6 側は `TsugumiKernelCheck --qwen38-pair-serve <bridge0 IP> 5310` を `bench/qfn/pair_serve.sh` が ssh で起動する。

| # | 作るもの | 現状と条件 |
| --- | --- | --- |
| 1 | **設定の経路** | アプリの `DecodeRuntimeOptions`・デコードサービスの `Entry`・`TsugumiServer` の引数のどれにも 2 機の項目が無い。「M6 を使う / 使わない」と相手のアドレスを `mtpEnabled` と同じ経路で runtime まで通す |
| 2 | **実行中の切り替え** | `pairConfig` は起動後に書き換えられるが入口が無い。off は次のラウンドの前に link を閉じ、on は新しい接続として状態を送り直す (今の再接続と同じ形)。会話の途中でも壊れない |
| 3 | **M6 の居場所の発見** | bridge0 の IP は link-local で繋ぎ直すたびに変わる ([01 §3](01-ROLES.md))。今は ssh で `ifconfig bridge0` を読む。アプリが bridge0 の上で見つける仕組み (bridge0 限定の Bonjour が候補) が無いとボタンの有効 / 無効を決められない |
| 4 | **M6 の serve の常駐** | 今は ssh で手起動。ボタンで使うなら M6 で常に待ち受ける (launchd の KeepAlive)。条件は 3 つ: (a) serve はラウンドの途中で link が切れると `exit(1)` するので再起動が要り、常駐 10 層 (約 10 GB) の読み直しが毎回入る。(b) serve は起動時の bridge0 のアドレスにしか bind しないので、IP が変わったら bind し直す仕組みが要る (bind は link-local だけ、[01 §3](01-ROLES.md))。(c) SSD256 のマウント (PLE BF16) と `iogpu.wired_limit_mb 14336` は再起動で消えるので、起動時に置く LaunchDaemon が要る |
| 5 | **状態の表示** | ボタンの表示は要求でなく実態。ラウンドログの `pair_k` / `pair_off` を HUD か Inspector に出し、今のラウンドが 2 機だったかが分かるようにする |
| 6 | **M6 のビルドと配備** | M6 は CLT だけで `swift build` 全体は落ちる。serve を `--product` で組む手順は [32](32-Q8-C1-CUT-COPY-LEAK.md) に書いただけで、[01 §2](01-ROLES.md) の `cycle.sh` は未作成。serve を CLI の 1 サブコマンドにするかもここで決める |

順: 4 (M6 の常駐と IP の変動、一番不確か) → 3 (発見) → 1・2 (経路と切り替え) → 5 (表示) → 6。

## 2. 運用上の衝突 (作る前に決める)

- **M6 の常駐と Gemma のベンチ**: serve を常駐させると M6 に約 10.6 GB が常に載る (32 のラウンド後 10.64 GB)。Gemma の m6-prefill のベンチは M6 でモデルプロセスが居れば計測を拒むので、Gemma を測るときは serve を止める運用が要る。
  `pair_serve.sh start` も「M6 にモデルプロセスが居れば止まる」ので、常駐と共存させる直しが要る ([05 §9](05-RISKS.md))。
- **同じ機械に 2 つは無い**の規則はそのまま。MBP に 1 つ、M6 に 1 つが正常。
