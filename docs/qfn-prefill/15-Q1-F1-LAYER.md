## 0. 結論

1. **P1 の経路は腕 M (dense の射影と shared expert は MPS fp16、routed は ds4-metal のタイルの移植)。**4 層とも GPU の合計が最小で、常駐 59.7〜61.3 ms/層 (今のコードの腕 A は 284.5〜292.9 ms)。
   tensor ops のタイル (腕 D) は routed で MPS の約半分 (36.4〜37.4 対 70.7〜87.6 ms) だが、dense では MPS より遅い (proj 18.6〜19.6 対 13.8〜14.7 ms)。
2. **精度は全腕・全テンソルが P1 の上限に入った。**腕 A との差 max |d| / max |A| は C で最大 6.72e-4、D で 5.02e-4、M で 5.24e-4 (上限 2e-3)。モデルでの top-1 と logits の差は未測定 (Q6)。
3. **冷えた条件では SSD の読みが層の壁時計の大半。**層の重み 631〜753 MB の読みが 189〜226 ms で、腕 M の層の壁時計は冷 264.7〜301.4 ms、常駐 76.0〜83.6 ms。
   M6 の 1 層では、GEMM を速くするより担当分を常駐させる方が秒が大きい (P2 と F4 がこれを決める)。

## 2. 分かったこと / 外れたこと

- **11 §1 の予想 (展開をタイルに入れた ds4-metal の形は腕 C より速い) は routed では当たり、dense では外れた。**dense の Q8_0 / F16 は展開が軽く、MPS fp16 の行列積の方が速い。
- **腕 A の routed (per-pair、215.9〜218.2 ms) は本番の routed ではない。**本番は per-pair と展開 + sgemm の混合で、E1 の M6 は 1 層 0.132 s (10 §2、導出)。A は精度の基準として置いた。
- **この表は GEMM だけ。**注意と GDN の中身 (再帰・attention の積)、norm、要素ごとの演算、ルーターの top-10 は入っていない。E1 の pre GPU (4.55 s/チャンク) とは比べられない。
- 冷の読みは 4 スレッドの pread を GPU の前に直列に置いた。読みと GPU の重ね (Q5) は入れていない。
- 計画からのずれ:
  1. 冷えた条件は、最初は Gemma の重み 15 GB を読んで追い出す形 (E3 と同じ) にしたが、層のページが残った (試走、証拠なし)。**`msync(MS_INVALIDATE)` で層の範囲だけを落とし、mincore で確かめる形**に替えた。GPU で使ったビューが残っているとページは落ちないので、空回しの後にビューを捨て、落ちるまで数回繰り返してから作り直す。
  2. 腕 M (C の dense と D の routed) は 12 に無かった。P1 の「C と D の速い方」を群ごとに実測で出すために足した。
  3. ルーター・ssm_alpha / beta・hc の inject・shared expert の gate (群 fp32) は全腕で今の fp32 の経路のまま。tensor ops に載せていない。
  4. ds4-metal からの変更: expert の基底をランタイムの expert ごとのビューから取る、down は 212 B のサイドカーの行 (最後のブロックが 44 B の半ブロック)、mid は half の写しだけ書く、`tiles_per_launch` は min(8, ⌈最大の組数 ÷ 64⌉)。
  5. 入力は乱数で、GEMM ごとに別の x を持つ (群の間に依存が無い)。
