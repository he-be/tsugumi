# 23. decode の置き場を判別する実験 — MTP on (運用点) で、MBP 単体 / 層で分けた 2 機 / M6 が幹の全層 を同じトークン列で測る (2026-09-25)

**状態: 計画。次の手はこれ (Q6 の実装より先)。**22 の P6 は「decode は MBP 単体」と書いたが、根拠は **MTP off** の単体どうしの比較 (MBP 192 ms・M6 207 ms、22 §1) だけで、
運用点は MTP on ([qwen38/17 §0](../qwen38/17-SERVER-APP-WIRING.md) の `--draft-block-size 2`、アプリは MTP 2 固定) なので、その数字ではどの置き場も選ばない。
層を分けた 2 機の decode も測っていない。この文書は、**MTP on を前提に**、置き場の候補を同じトークン列で測って決める手順を固定する。
**MTP で何が変わるかは推測せず、腕に入れて測る。**新しい実測は無い。

言葉: **腕** = 比べる形の 1 つ。**ステップ** = ドラフト 1 回 + 検証 1 回 (MTP on では 1 ステップで 1〜2 トークン出る)。**s/token** = 壁時計 ÷ 出たトークン数。

## 0. 問いと決め方

- **問い**: 運用点 (MTP spec、連鎖 1、instruct、KV Q8_0、チャンク 2048、prompt 8,192) で、**decode の s/token が最も短い置き場はどれか。**
- **物差し**: run ごとに、トークン 100〜399 の窓の s/token。ステップ数ではなくトークン数で窓を切る (腕でステップ数が違いうるため)。
  1 ステップで 2 トークン出ると、トークン 99 と 100 が同じステップに入りうる。**窓は「トークン 100 を出したステップから、トークン 399 を出したステップまで」**とし、
  s/token = そのステップの壁時計の和 ÷ そのステップが出したトークン数 (300 か 301)。トークン 0 は prefill の logits から出るのでステップに入らない。
  腕の値は n = 3 の run の中央値。窓の前 (トークン 1 から、トークン 100 を出したステップの 1 つ前まで) の s/token も並べる (prefill 直後の page cache の入れ替わりを含む区間)。
- **決め方 (測る前に置く)**: 腕ごとに、3 本の run の s/token の max − min をその腕のレンジとする。**S0 以外の腕の中央値の最小が S0 の中央値より、全腕のレンジの最大を超えて短ければ、その腕を decode の置き場にする。**超えなければ MBP 単体 (22 の P6 のまま)。
  22 の MBP (MTP off) は 191〜203 ms でレンジ 12 ms。MTP on のレンジはこの実験で初めて出る。
- **前提 (P 表、測る前に固定。動かしたら結果文書に書く)**

| 項目 | 固定する値 |
| --- | --- |
| M6 の経路 | 今のコード (fp32、重みは page cache、常駐なし)。A の常駐 13 層 + tensor ops の上の decode は測らない (§4) |
| RAM | M6 `iogpu.wired_limit_mb` 14336、MBP 15360 (22 と同じ)。両機 Swapouts 0 が run の有効条件 |
| 無効な run | どちらかの機で Swapouts が 1 ページでも出た run (と、GUARD で止まった run) は判定に使わず、その腕の run を巡回の最後に 1 本足す。1 腕で足すのは 2 本まで。それでも有効が 3 本に届かない腕は、有効な run だけで中央値とレンジを取り、結果文書に本数を書く (22 の M6 は 1 本目に 76 ページ出た) |
| 置き場 | 両機とも GGUF は内蔵 SSD、M6 の PLE BF16 は外付け SSD256 (03 §5)。22 と同じ |
| MTP | spec、連鎖 1 (`Q38_MTP_CHAIN` 既定)、MTP ヘッドと MTP の KV は常に MBP |
| サンプラ | instruct seed 1 は列を作る run だけ。測る run は §2 の固定列で、サンプラは呼ばない |
| 閾値 | 上の決め方 (レンジの最大)。合否を後から動かさない |

## 1. 腕

| 腕 | 幹 (層 0〜47) | head・MTP ヘッド・受理 | 1 ステップの流れ |
| --- | --- | --- | --- |
| S0 | MBP | MBP | link なし。今の `speculativeLoop` と同じ |
| S16・S24・S32 | M6 が層 0〜j−1 (embedding と PLE も)、MBP が層 j〜47 | MBP | MBP ドラフト → M6 へ [y, d] (と前ステップの keep) → M6 の層 (T = 2) → 残差 2 行 (80 KB) → MBP の層 → head → 受理 |
| S48 | M6 が全層 | MBP | 同上。MBP は幹の層を持たず、受けた残差に head を掛ける |

- j は 16・24・32 (24 が中央、16・32 は釣り合いの探り)。S48 は 22 の「M6 に全層を任せる形」の MTP on 版で、MTP off の 207 ms では落とさない。
- MTP off の腕は測らない (S0・S48 の off は 22 にあり、運用点ではない)。連鎖 2 (qwen38/14) も測らない (既定ではない)。

## 2. トークン列の固定 (teacher forcing)

1. **列を作る run (g)**: S0 と同じループ (§3、j = 0・link なし) にサンプラを付けて、instruct seed 1、400 トークン。**この run は比較に入れない。**
   `--q38-out` に出たトークン列 (`ids:`) と、各トークンを出した行の幹の argmax (`top1:`、トークン 0 は prefill の最後の行) を書く。
   **400 トークンより前に EOS が出たら、その列は使わず seed を 1 ずつ上げて g をやり直す** (窓 100〜399 が取れないため。使った seed は結果文書に書く)。
2. **測る run**: 全腕 n = 3、`--q38-force <g の --q38-out>`。各ステップで、ドラフト d は MTP ヘッドの argmax (MBP)、検証 [y, d] は腕の層を通り、
   **受理は「d == 固定列の次のトークン」**で決める。出すトークンは常に固定列のもの。計算は運用点と同じで、サンプラの代わりに固定列を引くだけ。
   測る run は EOS で止めず、固定列の 400 トークンを出し切る (g に EOS は無いので、止まる理由は長さだけ)。
3. 腕でステップ数と受理数が違いうる (M6 の GPU が違うので、ドラフトの argmax が入れ替わりうる)。**run ごとにステップ数・受理数・幹の top-1 が g の記録と一致した数を出す。**
   判定は s/token だけで行う (受理数の違いは s/token に入っている)。受理数が S0 と 5 以上違う腕があれば、どのステップかを結果文書に書く。

## 3. 道具 (作るもの)

`TsugumiKernelCheck --qwen38-split-decode serve|run` を足す。ランタイムの既定は変えない。S0 も同じループ (j = 0、link なし) で回し、腕の間でコードの差を持たない。

1. **ランナーに層の範囲**: `Qwen38Runner.forwardBody` の層のループを `layerRange` で切る口と、残差 (T × hc × D fp32) を外から入れる / 外へ出す口。既定は全範囲。
   M6 側は T = 2 の検証行と `rollback(keep:)` (:1845) も持つ。検証の forward の前に両機とも `snapshotRows = 1` を立てる (立てないと rollback できない)。
   keep は MBP が受理を決めてから次のステップの頭で送る (1 ステップの link は往復 1 回のまま)。
   `snapshotRows` の写しと `rollback` は範囲内の GDN 層だけを触る。次の層の expert の preview (`Q38_PREVIEW`) も範囲の中だけ (範囲の外の層を advise しない)。
2. **prefill は両機とも自分で全層** (今のコード、8,192 トークン)。MBP は MTP ヘッドの prefill も回す (今の `runQwen38Generate` と同じ)。状態の受け渡し (22 §2-2) は作らない。
3. **`--q38-force <g の out>`**: §2 の受理と出力。g の run も測る run も `--qwen38-split-decode run` の同じループ (g は `--q38-force` なしでサンプラを引く)。
   `--qwen38-generate --q38-mtp spec` の `speculativeLoop` は変えない。
4. **出すもの**: ステップごとの壁時計、ドラフト ms、M6 の幹 ms、MBP の幹 ms、link の往復 ms、両機の `kernel>gpu` と `advise` の和、出たトークン数、受理。
   run の終わりに、ステップ数・受理数・top-1 の一致数、トークン 0〜99 と 100〜399 の s/token、両機の Pageins・Swapouts・wired の最大。

## 4. 測り方

- 両機の確認は 22 §4-1 と同じ (他のモデルのプロセスが無い、M6 の wired limit 14336、SSD256 のマウント、bridge0 の rtt)。
- `bench/qfn/split_decode.sh <label> 3 S0 S16 S24 S32 S48` (f23_pair.sh と同じく腕を巡回、1 run 1 プロセス、両機 `guarded.sh`、間 20 秒)。先に g の run を 1 本。
- decode 400 トークン。窓は §0。1 run は prefill (M6 111 s、MBP 83 s、同時) + decode 1〜2 分で、16 本で 1 時間前後。
- 証拠: `bench/qfn/results/2026-MM-DD-pair-split-decode/` (両機のホスト札と link の札、02)。結果文書は 24。
- **測らないもの**: A の M6 (常駐 13 層 + staging、tensor ops) の上の decode。分ける腕か S48 が勝ったら Q7 でその経路の上でもう一度測る (受理率も、04 Q7)。

## 5. 結果の行き先

| 勝った腕 | P6 (22) | 状態の持ち主 | 次 |
| --- | --- | --- | --- |
| S0 | そのまま | 22 §2 (M6 はラウンドごとに受け渡し) | Q6 の k の格子 (44・46・48) |
| S16〜S32 | 書き直す: decode の j と prefill の k が違う | prefill の後に層 j〜k−1 の状態 (KV の行・GDN 状態・conv) を MBP へ。層 0〜j−1 の状態・チェックポイントは M6 (08 §1 の同じ id)。MTP の KV は MBP | Q6 の k の格子は変えない。Q7 で受け渡しの秒と受理率 |
| S48 | 書き直す: 幹は prefill も decode も M6 | 幹の状態・チェックポイントは M6、MTP の KV・prompt cache の場面表は MBP。ラウンド間の受け渡しは無し。M6 が落ちたら MBP 単体で prefill をやり直す (08 §5: M6 の状態は持ち込まない) | 同上 |

- 差がレンジ以内なら S0 (決め方のとおり)。「Mac で測るまで分からない」を残さない: 16 本で決める。
- どの結果でも、Q6 の prefill の k の格子は変えない。
