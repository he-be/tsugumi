# 23. decode を 2 機で分けるか、MBP 単体か — 判別する実験の計画 (2026-09-25)

**状態: 計画。次の手はこれ (Q6 の実装より先)。**22 の P6 は「decode は MBP 単体」と書いたが、根拠は単体どうしの比較 (MBP 192 ms・M6 207 ms、22 §1) だけで、
**層を分けて 2 機で回す decode は測っていない。**この文書は、その 2 つを同じトークン列で測って decode の置き場を決める手順を固定する。数字は 22 の実測からで、新しい実測は無い。

## 0. 問いと決め方

- **問い**: decode 1 ステップの中央値は、MBP 単体 (S0) と、層で分けた 2 機 (Sj: M6 が層 0〜j−1、MBP が層 j〜47 と head) のどちらが短いか。
- **分けて速くなりうる理由**: 今の MBP の decode は GPU を待つ時間が長い (22 の run の各ステップで `kernel>gpu` 39〜74 ms、trunk 173〜273 ms)。
  qwen38/13 では、この待ちは常駐していない MB で決まる。分ければ各機は自分の層の expert だけを page cache に持てばよく、常駐していない MB が減る。
- **遅くなりうる理由**: 1 トークンごとに MBP → M6 → MBP の 2 回の送り (残差 4 × 2560 fp32 = 40 KB、rtt 0.5 ms)。層は直列なので、2 機の GPU は同時には働かない。M6 の 1 層は MBP より遅い (22 §1 の単体の比)。
- **決め方 (測る前に置く)**: 各腕 n = 3 の run ごとの steady 中央値を取り、腕の中央値を比べる。
  **Sj の最小が S0 より、両腕の run 間のレンジ (中央値の max − min) の大きい方を超えて短ければ、decode は分ける (その j)。**超えなければ MBP 単体 (22 の P6 のまま)。
  22 の MBP は 191〜203 ms で、レンジは 12 ms。

## 1. 腕

| 腕 | 形 | 何を見るか |
| --- | --- | --- |
| S0 | MBP 単体 (今のコード) | 基準。22 の再現 |
| S16・S24・S32 | M6 が層 0〜j−1 (embedding と PLE も)、MBP が層 j〜47 + head + サンプラ | j の 3 点。24 が中央、16・32 は M6 の層が遅い分の釣り合いを探す |

- M6 単体 (全 48 層) は 22 で 207 ms と測ってあり、取り直さない。
- MTP は off (MTP の検証は T = 2 で両機を通るので、分けるかが決まってから Q7 で)。サンプリングは公式値のまま、下の §2 でトークン列を固定する。

## 2. 道具 (作るもの)

`TsugumiKernelCheck --qwen38-split-decode serve|run` を足す。ランタイムの既定は変えない。

1. **ランナーに層の範囲**: `Qwen38Runner.forwardBody` の層のループ (`for il in 0..<nTrunk`) を `layerRange` で切る口と、残差 `R` (hc × D fp32) を外から入れる / 外へ出す口を足す。
   既定は全範囲で、今の経路と同じ。`llkvSplit` (qwen38/28) が層の境目で残差を扱う前例になる。
2. **両機とも同じプロンプトを自分で全層 prefill する** (今のコードのまま、8,192 トークン)。各機が全層の状態を持つので、decode の結果は単体と同じ計算になる。
   状態の受け渡し (22 §2-2) はこの実験では作らない。問いは decode の 1 ステップだけだから。
3. **decode**: 1 ステップごとに MBP がトークンを M6 に送り、M6 は embedding・PLE・層 0〜j−1 を回して残差を返し、MBP は層 j〜47・head を回す。
   **入力トークン列は S0 の run 1 の出力 (`generate.out`) に固定する (teacher forcing)。**どの腕も同じトークン列・同じ位置を通るので、expert の選ばれ方が腕で揃う。
   各ステップの logits の top-1 が S0 の記録と一致した数も出す (M6 の層は同じ fp32 のコードだが GPU が違い、ビット一致は前提にしない)。
4. 出すもの: ステップごとの壁時計、M6 の層の秒、MBP の層の秒、送りの往復の秒、両機の `kernel>gpu` と `advise` の和。run の終わりに両機の Pageins・Swapouts・wired。

## 3. 測り方

- 両機の確認は 22 §4-1 と同じ (他のモデルのプロセスが無い、M6 の wired limit 14336、SSD256 のマウント、bridge0)。
- `bench/qfn/split_decode.sh <label> 3 S0 S16 S24 S32` (f23_pair.sh と同じく腕を巡回、1 run 1 プロセス、両機 `guarded.sh`)。
  decode 400 トークン、**steady はステップ 100〜399 の中央値** (prefill の後の page cache から、各機の担当層の分に入れ替わるまでを外す)。前半 100 の中央値も並べる。
- 証拠: `bench/qfn/results/2026-MM-DD-pair-split-decode/`。結果文書は 24。

## 4. 結果の行き先

- **分ける方が速い**: 22 の P6 を書き直す。prefill の k (Q6 の格子、M6 が全層に近い) と decode の j が違うので、prefill の後に層 j〜k−1 の状態 (KV の行と GDN の状態) を MBP に送る。大きさは 22 §0-3 と同じ見積もりで、1 ラウンド 0.03 s 前後 (導出)。
  チェックポイントと prompt cache は、層 0〜j−1 の分を M6 が持つことになる (08 §1 の同じ id の取り決めが要る)。
- **MBP 単体の方が速いか、差がレンジ以内**: 22 の P6 のまま。Q6 に進む。
- どちらでも、Q6 の prefill の k の格子 (44・46・48) は変えない。
- A の M6 の常駐 13 層 (自前のバッファ) の上での decode は、この実験では測らない (今のコードの page cache の経路で測る)。分ける方が勝ったら、Q7 で常駐の上でもう一度測る。
