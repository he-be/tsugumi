## 0. 結論

1. **式では B。**アプリの記録 12 ターン (68 ラウンド、うち 1 チャンクが 55 本) を 08 §3 の式に通すと、prefill 合計は単体 1922 s、A 1890 s (k 15)、**B 1564 s (σ 0.40)**。M6 の写しを使うと A 1842 s (k 16)、**B 1537 s (σ 0.45)** (導出)。A と B の差 (約 300 s) は 07 の決め方 3 の分岐 (差が小さければ B) にかからず、どちらでも B。Q0 の揺れの幅はまだ無いが、この判定には効かない。
2. **M6 は QFN の prefill を今のコードで 4K 通した。**Swapouts は 3 run で 40 / 0 / 0 ページ。A の止める条件 (04 Q1) にはかからなかった。1 チャンクの壁時計は MBP 19.48〜23.08 s、M6 28.92〜30.38 s (両チャンク、3 run)。GPU の秒は両機ほぼ同じで、違いは SSD (advise 4.3〜4.5 s 対 8.1〜8.6 s) と PLE (外付け、毎回 5.9〜6.6 s)。
3. **E4-(b) (fp16 + MPS fp16 行列積) は M6 で 1 層 173〜199 → 74〜87 ms に縮んだが、腕 A との相対差が 4.5〜7.2e-4 で、07 の規則 (qwen38/01 の 1.7e-6 を超えたら使わない) により使わない。**Q8 (tensor ops の Gate) は作らない。

## 2. 式に入れた量と、式に足した項

1 層あたり (導出、E1 の表 ÷ 48): MBP d 0.1035 / r 0.1291 / t 0.0141 / s 0.0929、M6 d 0.0948 / r 0.1325 / t 0.0106 / s 0.1781 (写しあり 0.1286 = E2 の比 0.722 を掛けた値)。
p (冷えた PLE、チャンクあたり) は MBP 3.19、M6 6.24。

- **08 §3 の式には host の残り o を足した。**d + t + s + r だけでは MBP の単体が 1 チャンク 16.4 s になり、E1 の 19.7 s (ple・head を除く) より 17% 短い。
  残り (エンコード・待ち・views) を o = 0.0707 (MBP)、0.0753 (M6) s/層として置いた。A では層と一緒に動き、B では MBP に残す (B に不利な置き方)。
- 1 チャンクのラウンドの A は k を増やすほど遅い (M6 の 1 層 0.44〜0.49 s は MBP の 0.41 s より長く、PLE も M6 で 6.2 s)。A が縮むのは 2 チャンク以上の定常だけで、記録の 68 ラウンドのうち 13 本。
- B の 1 チャンクは 18.62 s (σ 0.40)、写しありで 18.30 s (σ 0.45)。単体の式は 22.89 s (導出)。

## 3. 外れたこと・計画からのずれ

1. **E3 で、M6 の担当分が page cache に残った** (`pair-e3-warm-s{0.35,0.43,0.5}`、追い出し 1 回の後に同じ route を 4 チャンク、n = 1)。
   M6 の読みは σ 0.35 (担当分 9.9 GB) で 3.13 → 0.70〜0.80 s、σ 0.43 (12.3 GB) で 3.83 → 0.64〜0.87 s。σ 0.5 (14.3 GB) は 4.37〜4.40 s のまま。
   MBP の壁時計は σ 0.43 で 9.10 → 8.59〜8.81 s、σ 0.35 は 9.72〜9.83 s で動かない (MBP 側が長い)。
   表 1.5 は、毎 run の前に M6 で Gemma の重み 15 GB を読んで追い出した値。σ 0.43 の 2・3 本目は追い出しが足りず、M6 の未常駐が 12.3 GB 中 11.1 / 8.7 GB だった (MBP の壁時計は 9.06〜9.09 s で変わらない)。
   実際のラウンドで担当分がどれだけ残るかは測っていない。式には入れていない。
2. E3 の GEMM は腕 B (f32 sgemm) で、本番の routed (per-pair との混合、1 層 0.129 s) より遅い。down は本体の 768 詰めを読むので、1 expert 1,489,920 B (本番 1,387,520 B)。E3 は式の形を確かめただけで、秒は B の設計値にしない。
3. 最初の模擬はテンソル全体の no-copy ビューで、σ によらず GEMM の壁時計が 13 s だった (相手の担当分のページまで触る)。expert ごとのビューに直した (09fa82f)。分割の和は `QFN_PROBE_CHECK=1` で全体と 1.45e-7 で一致。
4. E4-(b) は自前の NAX カーネルではなく **MPS の fp16 行列積** (M6 の tensor ops で 18.61 TFLOP/s を出す経路、m6-prefill/03)。展開のカーネルは moe_ggml.metal の f32 版を半精度に書き換えて KernelCheck の中で組んだ。
5. E2 は 1 層の expert 全部 (710 MB) を読む。本番は選ばれた約 400/512 本なので、式の s には E1 の advise を使い、E2 からは写しの比だけを取った。
6. E0〜E2 は道具がまだ commit されていない状態 (9501dc1) で取った。バイナリのソースは同じ。M6 の最初の E2 は `QFN_MODEL` の付け忘れで 2 本が失敗し、消して取り直した。
7. Q0 (基準線) はまだ無い。決め方 3 の閾値に使うが、§0-1 のとおりこの判定には効かない。

## 4. 次の Gate に渡すもの

- **Q6 で作るのは B。**σ は 0.40 (写しなし) / 0.45 (写しあり) から始め、04 Q6 のとおり前後 2 点を測る。
- M6 の PLE BF16 (95 GiB、外付け) は B では要らない (README の判断待ち 4)。
- 開いたまま: M6 の担当分がキャッシュに残る効果 (§3-1) の本番での大きさ。B では M6 に状態が無いので、担当分を残すかどうかは M6 の RAM だけの問題。
- E4-(b) は規則で外れた。fp16 の展開は 1 層で A と 4.5〜7.2e-4 ずれ、1.7e-6 の幅には原理的に入らない。この閾値のままなら M6 の tensor ops は使えない。
