# 19. Q1 の後の手順 — A を作る前に、M6 の読みを MBP の SSD から TB4 で補う腕 (Q4-b) を模擬で測る (2026-09-25)

## 0. 結論 (手順の順)

1. **Q4-b を先に模擬で測る** (§2)。M6 の非常駐層の expert を、MBP が自分の内蔵 SSD から読んで TB4 で送る。読み口が 3.34 GB/s から約 8 GB/s になる見込み (導出)。
   M6 の層の秒が変わると k の釣り合う点が動くので、Q6 の k を 2 度測らないために先に取る。道具は `--qfn-pair-sim` に受け口と送り手を足すだけ。
   その前に M6 の 3 つの TB ポートが対称か (link と外付けが同じバスを分けていないか) を同時転送で確かめる (§2-3-1)。
2. **Q6 で A を作る** (04 Q6)。k は Q4-b の結果 (採用 / 不採用) の方の模擬で最小だった値から始め、前後 2 点を n = 3。**1 チャンクと 2 チャンク以上で釣り合う k が違うので、k はチャンク数で切り替えてよい** (§1-3 の規則、聞かない)。
3. Q7 (decode と会話の機能)。A では M6 が層 0〜k−1 の状態を持つので、チェックポイント・prompt cache の同期がここに入る。
4. Q3 (host の top-10) と Q5 (機内で読みと GPU を重ねる、MBP 側は判断待ち 3) は分け方に依らず、Q6 と並行してよい。

やらないこと: チャンク幅の変更 (§1-2)、B への戻し (18 で決着)、式の修正 (12 §3-4)。

## 1. 問いへの答え (18 §1 の数字から)

### 1-1. 待ちは段の長さが釣り合っていないからで、パイプラインは組んである

2 チャンク以上のラウンドでは、MBP がチャンク c の後半を回す間に M6 が c+1 の前半を回す (08 §1)。k 40 常駐の 2 チャンク (18 §1.2):

```
M6 : [ chunk0 の 40 層 8.1〜8.6 s ][ chunk1 の 40 層 8.1〜8.6 s ]
MBP:                               [ chunk0 の 8 層 2.0 ][ 待ち 6.1 ][ chunk1 の 8 層 2.0 ]      合計 18.5 s
```

- 定常のスループットは長い方の段 (M6) で決まる。チャンクを細かくしても段の長さの比は変わらず、待ちは消えない。消すのは k を下げること。実測でも 2 チャンクの最小は k 32 (17.4 s、待ち 0.6 s)。
- 1 チャンクのラウンド (記録の 68 本中 55 本) は重ねる相手が無く、2 機の秒の和 (M6 8.3 + MBP 2.0 + link)。ここは k が大きいほど短く、k 40 が最小 (10.4 s)。
- 1 ターンの合計で k 40 が勝ったのは、1 チャンクの側の利得 (k 32 比 1.1 s × 55 本) が 2 チャンクの側の損 (1.1 s × 13 本) を上回るから (導出)。

### 1-2. チャンクを小さくすると SSD の読みが増える (08 §5 の根拠)

expert の読みは選ばれた expert の本数に比例し、トークン数にはほぼ依らない。2048 × top-10 = 20,480 回の選択で 256 個はほぼ全部選ばれ、1 チャンクで約 32 GiB 読む (02 §5)。1024 でも 10,240 回でほぼ全部が選ばれる。
GPU の秒はトークン数に比例する。よってチャンクを半分にすると、同じプロンプトで GPU は同じ、読みは 2 倍。

| | 2048 × 1 本 (03 §3) | 1024 × 2 本 (導出) |
| --- | --- | --- |
| MBP 単体: GPU / SSD / 合計 | 11.5〜12.2 / 約 5 / 20〜22 s | 約 12 / 約 10 / 約 26 s |
| M6 (A k 40 常駐): GPU / 読み (非常駐 27 層) / チャンク | 2.4〜2.9 / 4.1〜6.2 / 8.1〜8.6 s | 同じ / 2 倍 / 約 12〜14 s |

今のコードは層ごとに読み → GPU の直列なので足し算になる。重ねる (Q5) と max(読み, GPU) に近づくが、読みの合計は減らない。M6 側は読みが GPU の 2 倍なので隠れない。
チャンク 2048 の上限は attention の作業メモリ (qwen38/03) とアプリのラウンドの新規トークン数 (平均 2,650、8 割が 1 チャンク) で決まっている。

### 1-3. k はチャンク数で切り替えてよい (Q6 の規則)

常駐する 13 層は層 0〜12 で k に依らない (18 §1.1)。よって 1 チャンクのラウンドと 2 チャンク以上のラウンドで別の k を使っても、M6 の常駐は動かない。
**規則**: Q6 の k の格子で t1 (1 チャンク) と t2 (2 チャンク) の最小の k が違い、切り替えた 1 ターンの合計 (12 §3-1 の配分) が 1 つの k の最小より閾値 (3.06 s) 以上短ければ、切り替えを既定にする。閾値未満なら 1 つの k。

## 2. Q4-b — M6 の非常駐層の expert を MBP の内蔵 SSD から TB4 で送る

### 2-1. 形

- 04 の Q4 (M6 の外付けに expert の写し、内蔵と同時に読む) と同じ狙いで、第二の読み口を外付けでなく **MBP の内蔵 SSD + TB4** にする。MBP は本体 GGUF と `down/` の全部を内蔵に持つ。
- M6 が層 L の router を回して選ばれた expert (T × 10 × 8 B = 164 KB) を MBP に送り、MBP が担当分 (帯域比で決める、初期値は M6 内蔵 : TB4 = 3.34 : 4.73) を `pread` して送り返す。M6 は残りを内蔵から読む。往復は rtt 0.5 ms (10 §1.1) で 1 層の読み 0.15〜0.23 s に対して無視できる。
- 受け口は 17 の「入らない層の固定の置き場」そのもの。socket の受信を `MTLBuffer` の contents に直接書く。M6 の RAM は増やさない。常駐 13 層 (10.54 GB) は変えない。
- 1 チャンクのラウンドでは MBP は M6 の段 (8.3 s) の間まるごと暇。2 チャンクの重なりでも MBP の SSD は自分の 8 層分 (0.21〜0.24 s) しか使っていない。

### 2-2. 見込み (導出。読みは直列のまま、帯域比で分かれるとして)

| 読み口 (03 §4、10 §1.1) | GB/s | M6 の非常駐 27 層の読み (k 40) | M6 のチャンク |
| --- | ---: | --- | --- |
| M6 内蔵だけ (18 の実測) | 3.34 | 4.1〜6.2 s | 8.1〜8.6 s |
| 内蔵 + 外付け (Q4 の写し) | 4.83〜4.92 | 2.8〜4.2 s | 約 6.8〜7.2 s |
| **内蔵 + TB4 (Q4-b)** | **約 8.1** (3.34 + 4.73) | **1.7〜2.6 s** | **約 5.7〜6.3 s** |

MBP の内蔵は 6.68 GB/s なので送り側は TB4 で頭打ち。

### 2-3. 確かめないと分からない点

1. **M6 の 3 つの TB ポートが対称か。**外付け SSD256 も TB4 に付いていて、link と外付けがどのポートに刺さっているか、ポートがコントローラ (バス) を共有するかは記録が無い (01 §3、03 §4 とも「TB4」としか書いていない)。
   E0 の 4.73 GB/s と m6-prefill/44 の外付け 1.57 GB/s は別々に測った値で、同時に流したことは無い。
   先に `system_profiler SPThunderboltDataType` を両機で取り、link のケーブルと外付けのバス / ポート番号を `hostinfo.m6.txt` に残す。次に link の 1 GiB 転送 (E0 の `link_probe`) と外付けのランダム読み (`dual_ssd_probe.sh`) を**同時に**流し、
   片方ずつの値 (4.73 / 1.57) からどれだけ落ちるかを、外付けを 3 ポートに刺し替えて 3 通り取る (link は固定)。落ちる組があればその 2 つを同じバスと見なし、link と外付けは別バスの組に固定して `cycle.sh` の確認に入れる。
   3 通りとも落ちなければ対称として扱う。ここで落ちるなら PLE の読み (Q2 の先読み、外付けから) と Q4-b の送りが同じバスで競合するので、§2-4 の run では `iostat` の disk ごとの MB と link の GB/s を同じ run で見る。
2. 4.7 GB/s の受信を M6 の CPU が GPU の合間にさばけるか。E0 は受信だけの測定。M6 側の recv の秒を層ごとに出す。
3. MBP 側の送信のスレッドが MBP の GPU (2 チャンク目の重なり) を邪魔しないか。t2 の MBP の層の和を Q4-b なしと比べる。

### 2-4. 測り方

- 先に §2-3-1 のポートの確認 (link と外付けを同時に流す、3 通り、各 n = 3)。証拠は `bench/qfn/results/2026-MM-DD-pair-tb-ports/`。
- 道具: `--qfn-pair-sim` の M6 側に「非常駐層の担当分を link から受ける」経路、MBP 側に「選択リストを受けて `pread` → send」のスレッドを足す (`--qfn-pair-sim --feed-experts <比>`)。既定は off。
- 条件: A k 40 常駐 (18 と同じ、route `c2048-l<L>.bin`、2 チャンク)。腕は 3 つ: なし (18 の再現) / TB4 の比 0.5 / 帯域比 0.59。各 n = 3。両機 Swapouts 0、wired limit 14336 (P2)。
- 出す量: t1・t2、M6 のチャンクの秒、M6 の層ごとの読み (内蔵 / link)、MBP の待ち、`iostat` (両機、disk ごと)、link の GB/s。
- 証拠: `bench/qfn/results/2026-MM-DD-pair-q4b/`。結果文書は 20。
- 合否 (04 Q4 と同じ): M6 のチャンクの秒が閾値 (3.06 s) 以上縮む、t1・t2 とも縮む向きが揃う、Pageins が増えない、Swapouts 0。通れば Q6 の A に入れる (`Q38_EXPERT_FEED` は候補、既定に入れるのは Q6 で本番の層で縮んだとき)。
- 不合格なら Q4 の外付けの写し (04 Q4) をそのまま測る。両方通れば 3 口 (内蔵 + 外付け + TB4) は Q6 の後に候補として測る。

## 3. 判断待ちの整理

- README の判断待ち 4 (M6 の PLE BF16) は閉じる。PLE BF16 は M6 の外付けにしか置けず、置いてある (03 §5、05 §5)。A では Q2 の先読みが外付けから読む。決めることは無い。
- 判断待ち 1・2 (記録値を取る機械、TB4 の常設) は Q6 の台帳の 2 機の列に要る。Q4-b の道具作りは止めない。
- 判断待ち 3 (MBP 側の Q5 の RAM) はそのまま。
