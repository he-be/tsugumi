**逸脱**
1. **有効条件を測る途中で変えた (ユーザーの判断)。**23 の当初の条件は「両機 Swapouts 0」だったが、MBP は毎 run 0〜53 MB の Swapouts を出した (§1 の表)。「閾値が過剰」として、無効は guarded.sh が止めた run と exit が 0 でない run だけに改めた (23 §0 の P 表を更新)。この条件で 14 本とも有効。スクリプトの画面の `valid 0` は旧条件の判定で、使っていない。
2. **S48 は n = 2。**S32-3 の後、残り 2 本 (S48-3 と足し直しの run) では判定が動かない (§2) ので、S48-3 の途中で止めた (ユーザーの問い「これ以上やる意味あるの」を受けて)。S48-3 の途中のファイルは消した。
3. g の run (比較に入れない) は MBP で Swapouts 6,548 ページ (107 MB)。

**台帳** ([06](06-LEDGER.md)): 計測だけで、ランタイムの既定は変えていない (ランナーに足した `layerRange` 等は既定で全層)。台帳 §1 は動かない。

## 0. 結論

1. **決め方 (23 §0) の答えは S0 (MBP 単体)。22 の P6 (decode の k は 0) はそのまま確定する。**
   窓 (トークン 100〜399) の s/token の中央値は S0 0.1265、S16 0.1421、S24 0.1462、S32 0.1586、S48 0.2191 (n = 2)。
   分けた腕の最小 (S16) は S0 より 0.0156 長く、全腕のレンジの最大 0.0039 (S48) を超えて**遅い**。
2. **j を増やすほど遅い。**1 ステップの中央値は S0 244 ms → S16 276 → S24 281 → S32 307 → S48 433 ms。link の往復は 0.6〜0.7 ms で、差のほとんどは M6 の幹の ms (§1-2)。
3. 受理は腕で 196〜197 (S0 と 1 以内)、幹の top-1 は g と 399〜400 / 400 で一致。

## 2. 判定

- 決め方: 分けた腕の中央値の最小 0.1421 (S16) − S0 の中央値 0.1265 = +0.0156 (S16 が遅い)。「S0 より全腕のレンジの最大 0.0039 を超えて短い」腕は無い。
- S48 の 3 本目と足し直しの run では判定が動かない: 3 本の中央値は 2 本の小さい方 0.2171 を下回らず、S0 より長いまま。
- 23 §5 の表の行 S0: P6 (22) はそのまま。状態の持ち主は 22 §2 (M6 はラウンドごとに受け渡し)。次は Q6 の k の格子 (44・46・48)。

## 3. 読んだこと (n = 3 の範囲で)

- M6 が受け持つ層の ms を層数で割ると、S16 7.0、S24 6.4、S32 6.7、S48 8.1 ms/層。MBP の側は S0 4.6 (219.2 / 48)、S16 4.1、S24 4.0、S32 4.0 ms/層 (head を含む)。検証 1 回の幹は M6 のほうが層あたり長く、直列なので分けた分だけ足される。
- M6 の kernel→GPU と advise は j とともに増え、S48 で 101.8 / 63.0 ms。M6 の wired 最大は S48 で 10.3〜10.4 GB。
- MTP off の単体どうし (22 §1) は MBP 192・M6 207 ms/ステップ (T = 1) だった。今回の S48 の M6 の幹は T = 2 で 391 ms。T の違いとページの読みの違いのどちらが効いたかは、この実験では分けていない。
