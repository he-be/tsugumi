## 0. 10 と 11 で結論が揺れた理由

結論が 2 度動いた (10 で B、11 で取り下げ) のは、M6 の前提を固定しないまま今のコードを測って式に入れたからで、実測が悪いのではない。

1. **M6 の計算経路が前提になっていなかった。**E1 の M6 の秒は fp32 のコードを M6 で動かした値で、M6 の性能ではない。前提が後から「tensor ops 必須」と決まって結論が倒れた。
2. **精度の合否が経路と結びついていなかった。**fp32 の幅 (qwen38/01 の 1.7e-6) を fp16 の腕に当てて落とし、次に規則の方を外した。合否は経路とセットで測る前に置く。
3. **A と B で証拠の重さが違った。**B は E3 の模擬で式を検証したが、A は式だけで、M6 側の層を一度も動かしていない。
4. **式の絶対値が判定の差と同じだけ外れている。**`formula.py --turns` の単体は記録 12 ターンで 1922 s、同じ記録のアプリ実測は 1618 s (導出、`turn-metrics.jsonl`)。
   差 305 s は式の A と B の差 (約 300 s) と同じ大きさで、この式では A / B を選べない。o 項は E1 の 1 チャンクに合わせただけで、記録の再生には合っていない。
5. **順序が逆だった。**07 の決め方 3 の閾値は Q0 の揺れ幅なのに、Q0 は未着手。閾値の無い判定をした。
6. **tensor ops は決め手ではない。**M6 の 1 層は SSD の読み 0.178 s が支配し、routed を tensor ops (腕 C 0.076 s) にしても 1 層 0.49 → 0.43 s (導出、10 §2)。
   動かすのは M6 の担当分がキャッシュに残るかどうかで、E3 の暖かい run では σ 0.35 で M6 の読みが 3.13 → 0.70〜0.80 s (10 §3-1)。式に入っていない最大の項がこれで、
   RAM の使い方はユーザーの判断事項なのに前提として置かれていなかった。
7. **PLE の置き場の都合が A にだけ乗る。**外付けの PLE 6.24 s/チャンク (10 §2) は Q2 で消える量で、Q2 の前後で A の順位が変わる。

- F1 は E4 の腕 D (ds4-metal の移植、`__HAVE_TENSOR__`、M6 だけ) と dense の射影の fp16 を 1 本のベンチにまとめたもの。腕 C と D の速い方を P1 の経路にする。
- F2 の M6 側は attention / GDN の再帰を含まない模擬 (E3 と同じく秒の形を確かめる道具)。M6 で本物の層を回した E1 の秒と、F2 の M6 側の秒の差は結果文書に書く。

- 両機で KernelCheck は同時に 1 本まで。見張りは `Scripts/qwen38/guarded.sh`。層ごとの大きな確保は避ける (10 の最初の E3 の Swapouts、11 §3)。

## 3. 決め方 (計測の前に置く。後から動かさない)

1. F2・F3 の壁時計 (1 チャンクのラウンド、2 チャンク定常) に、記録のラウンド分布 (`formula.py --turns`: 1 チャンク 55 本、2 チャンク 10 本、3 チャンク 3 本) を掛けて **1 ターンの prefill 合計秒**を A と B で出す。式ではなく模擬の実測を配分に掛ける。
2. 小さい方を作る。差が F0 の閾値 (揺れ幅 × 2) 未満なら **B** (M6 に状態が無く、decode と prompt cache に手を入れない方)。
3. 常駐の条件 (P2) は F4 の上限の中で使う。冷えた条件でしか速くならない分け方は選ばない。
4. 模擬の壁時計と式が 1 割以上ずれても判定は模擬の値で行い、ずれた量を結果文書に書く。式は直さない (格子を絞る用途だけ)。
