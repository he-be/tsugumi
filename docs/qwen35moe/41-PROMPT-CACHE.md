# 41. prompt cache — 再帰状態でも「厳密な延長」なら続きから走れる (実測(手元)、2026-08-22)

[26 §4-3](26-PHASE8-SERVER.md) は「**prompt cache は持たない**」と決め、
[34](34-PROMPT-CACHE-ESTIMATE.md) は机上で取り分 (最大 9.2 秒) と危険
(**再レンダの継ぎ目**) を出して終わっていた。[40 §6-1](40-MTP-GRAMMAR.md) が
実測で示したとおり、**エージェント経路で一番効く制約はここ**である — 2,935
トークンのターンで prefill 10.4 秒を、pi は**毎ターン満額**払っていた。

本書はそれを実装して測る。**新しいカーネルは 0 本、Metal は 0 行、
Gemma の経路は 0 行。**

**結論を 1 行で: 当たる。**エージェント形の会話 (tools + thinking + ツール応答の
往復 + ストリーミング) で、**2 ターン目以降は全部ヒット**した。
長文文脈の TTFT は **10.4 → 0.78 秒**、34 の見積もり (9.16 秒) は**当たっていた**。

## 1. 何を作ったか

| 部品 | 中身 |
| --- | --- |
| `QwenPromptCache` (新規、純粋型) | 規則だけ。`match(_:cachePrompt:) -> .hit(cached:) / .miss(divergedAt:)` と `publish(promptIDs:generated:kvPosition:)`。ランナーを知らないので C0 が立つ — `QwenGenerationPlan` と同じ分け方 |
| `QwenGreedyRun` | `cachedPromptTokens` / `kvPosition` を足した。RSP-3 の `cache_n` / `prompt_n` はここから出る |
| `runGreedyCompletion` / `…MTP` | `cachedPromptTokens:` を取る。**接尾だけ**を渡す形になり、文脈上限の precondition が**位置込み**になった ([34 §3-3 ③](34-PROMPT-CACHE-ESTIMATE.md) の abort を潰した) |
| `QwenForwardRunner.reset` | **MTP ヘッドの 1 層キャッシュも落とすようにした** (§3-3) |
| `QwenServerSession` | 無条件 `reset()` を外し、match → 接尾を prefill → `publish`、失敗時は `defer` で捨てる |
| `ServerLog.promptCache` | ミスの診断 1 行 (`miss diverged_at=… held=…`)。**数字だけで、プロンプト本文は 1 バイトも出さない** |

`ServerPromptCache` (Gemma 用) は**使っていない**。あれはトークン列を持ち、
最長共通接頭辞まで K/V を**巻き戻す**器で、この家族には巻き戻しが無いからである
([34 §3-4](34-PROMPT-CACHE-ESTIMATE.md) は流用を勧めていたが、流用すると
「1 エントリ・全部か無か」に対して器が大きすぎる)。

## 2. 規則 — 全部か、無か

```
状態が食ったトークン列 C に対し、
  新しいプロンプト P が |P| > |C| かつ P[0..<|C|] == C  →  ヒット (cache_n = |C|)
  それ以外                                            →  ミス (reset)
```

部分ヒットが無いのは `RecurrentStateManager` の冒頭註のとおり
「途中の 1 トークンを落とす」という操作が再帰に存在しないからで、
[34 §4-1](34-PROMPT-CACHE-ESTIMATE.md) が `maximumSafeRewind = 0` から導いた形と同じである。

**前回とまったく同じプロンプトはミスになる。**状態は「見たもの」より 1 つ短く
(下記)、prefill は logit を作るために最低 1 行を要るからである。Gemma 側が
CACHE-3 の `-1` で踏むのと同じ角を、別の理由で踏む。

### 2-1. 状態は「見たもの」より 1 つ短い — ただし常にではない

ループはトークン *t* を食わせて *t+1* を引くので、**最後に出したトークンは
食われていない**。これが 34 §3-1 の
`KV-backed = promptIDs + produced.dropLast()` である。

**幅 2 の投機ではそうならない場合がある。**受理したパスは 2 行
(`pending` と `draft`) を食っており、その直後に行 0 のトークンで生成が
終わると (停止トークン・`max_tokens` 到達)、**最後に出したトークンの行は
もう食われている**。K/V は巻き戻せても**再帰状態は巻き戻せない**ので、
「1 つ短い」と決め打つと状態と記録が食い違う。

したがって記録するのは**ランナーが言う位置**である:

```swift
cachedTokens = (promptIDs + run.tokens).prefix(run.kvPosition)
```

## 3. 実装で踏んだもの

### 3-1. 34 の見積もりどおりだったもの

- **追加メモリ 0 バイト** — エントリは生きている状態そのもの
- **prefill は position 0 を仮定していない** — `runChunkLayers` は `kv.position`
  から始まる。**継ぎ目に新しい規則は 1 つも要らなかった**
- **`cache_prompt` (CACHE-5) は家族を知らない層で既に読まれていた**
- **tools と thinking の一致は無料で付いてくる** — どちらもトークン接頭辞に出る

### 3-2. 34 の式が外れていたところ (§2-1)

最初の実装は `promptIDs + run.tokens.dropLast()` を記録し、**ランナーの位置と
食い違ったらキャッシュを捨てる**という安全側の分岐を書いていた。
その分岐が**実測で頻発した** — 4 ターンの会話で 1 ターンが丸ごとミスになり、
ログにも出ないまま TTFT が 3.3 秒に戻っていた。原因が上の「受理して終わった
パス」で、`--qwen-resume` の
`幅 2 の位置は prompt+生成 か その 1 つ手前` はこの 2 通りを両方踏む検査である
(実測では `kv=31, prompt+生成=31`、つまり**短くない方**が出る)。

### 3-3. 34 が挙げていなかった穴 — MTP ヘッドのキャッシュ

`QwenForwardRunner.reset()` は `kv` と再帰状態を落とすが、
**`QwenMTPDrafter` の 1 層 K/V は落としていなかった**。CLI は 1 プロセス
1 生成なので誰も踏まないが、サーバーでは**2 本目の要求が 1 本目の行を持ったまま
ドラフトする**。投機は検証されるので**答えは変わらない**が、受理率が黙って
落ちる。`reset()` に足した。

継続のときは**落とさないのが正しい** — その行は同じ会話の、自分が主張する
位置に居るからである。

### 3-4. 失敗経路 ([34 §3-3 ②](34-PROMPT-CACHE-ESTIMATE.md))

無条件 `reset()` が消えた以上、途中で throw した要求の状態を次の要求が拾いうる。
生成を `do` で囲い、`defer` で「完了印が立っていなければ捨てる」ようにした。
**キャンセル (客が切る) もここを通る** — 実測でも、ストリーミングを途中で
切った次の要求が `cache_n=0` で正しく答えた (§7-2)。

## 4. 34 の「一番大きい危険」— 再レンダの継ぎ目 (**実測(手元)**)

[34 §4-3](34-PROMPT-CACHE-ESTIMATE.md) は、テンプレートが assistant ターンを
構造体から描き直すので **`trim` / 思考の往復 / ツール引数の再直列化**の 3 つで
バイトがずれ、**エージェントのツールループが一番ミスしやすい**と書いた。

### 4-1. 実測では、ずれなかった

`reasoning_content` と `tool_calls` を送り返すクライアント (= pi。
`pi-ai/dist/api/openai-completions.js` は思考ブロックの署名が
`reasoning_content` のとき `assistantMsg.reasoning_content` に詰め直す) では、
**3 つとも一致する**:

| 種 | なぜ一致したか |
| --- | --- |
| `trim` | 生成は `<think>\n` + 思考 + `\n</think>\n\n` + 本文。テンプレートは `思考\|trim` を `'\n<think>\n' + … + '\n</think>\n\n'` に挟む。**モデルが書いた改行の数とテンプレートが足す改行の数が同じ**なので、trim して足し直すと元に戻る |
| ツール呼び出し | 本文が空 (`content\|trim` が偽) のとき、テンプレートは `</think>\n\n` の直後に `<tool_call>` を置く。モデルもそう書く。引数は文字列値なのでそのまま (`args_value \| string`) |
| 思考 | このテンプレートは過去の思考を**捨てない**。クライアントが送り返せばそのまま描かれる |

実測 (§5-1) では、**ツール呼び出しのターンも、ツール応答を挟んだ次のターンも、
ストリーミングのターンも全部ヒットした**。

### 4-2. 当たらない形も測ってある

同じ会話で `reasoning_content` を**送り返さない**クライアントを真似ると:

```
keep_reasoning=True  turn2: cache_n=345 prompt_n=24 prompt_ms=644
keep_reasoning=False turn2: cache_n=0   prompt_n=324 prompt_ms=2676
[prompt cache] miss diverged_at=261 held=436
```

`diverged_at=261` は 1 ターン目のプロンプトの**末尾**、つまり
「assistant ターンの描かれ方から違う」を指している。**これは正しい挙動である** —
思考を落とした会話は*違う会話*で、状態を使い回せば客が送っていない文脈に
答えることになる。[34 §4-4](34-PROMPT-CACHE-ESTIMATE.md) の
「文脈を切り詰めるクライアント」「system に時刻が入る」も同じ扱いで、
**どれもミスの診断が 1 行出る**。

## 5. 取り分 (**実測(手元)**)

サーバー、`--ctx-size 32768 --expert-cache-slots 32`、mmap、temp 0 (既定)、
`tools` 1 本 + `enable_thinking: true`。腕は `--draft-block-size 0` と `2`。

### 5-1. エージェント形の 3 ターン (ツール応答の往復を含む)

| 腕 | ターン | `cache_n` | `prompt_n` | `prompt_ms` |
| --- | ---: | ---: | ---: | ---: |
| base | 1 | 0 | 275 | 3,192 |
| base | 2 | 334 | 51 | **1,142** |
| base | 3 | 432 | 22 | **579** |
| mtp | 1 | 0 | 275 | 3,168 |
| mtp | 2 | 334 | 51 | **1,160** |

ストリーミングでも同じ (4 ターン、`cache_n` 0 / 325 / 392 / 480、

**RSP-1 の不変量 `cache_n + prompt_n == usage.prompt_tokens` は全ターンで成立**
(スクリプトが毎回検算している)。

### 5-2. 2,936 トークンの文書を読ませた会話 — 一番大きい数字

| 腕 | ターン | `cache_n` | `prompt_n` | `prompt_ms` | decode tok/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| base | 1 | 0 | 2,936 | 10,333 | 14.04 |
| base | 2 | 3,055 | 37 | **715** | 13.86 |
| mtp | 1 | 0 | 2,936 | 10,399 | 16.76 |
| mtp | 2 | 3,056 | 36 | **781** | 17.49 |

**TTFT −93%。**[34 §1-5](34-PROMPT-CACHE-ESTIMATE.md) の導出は
「10.63 → 1.47 秒 (取り分 9.16 秒)」で、実測は **10.33 → 0.72 秒 (9.6 秒)**。
34 が置いた床 1.30 秒は**保守的すぎた** — 37 トークンの継続は 0.72 秒で済む。
decode の tok/s は腕の中で動いていない (§0 #8)。

## 6. 続きから走った答えは同じか (**実測(手元)**)

| 検体 | 結果 |
| --- | --- |
| **needle** (1 ターン目に「合言葉 PLATYPUS-7734、ポート 60413」、2 ターン目に問う) | 続き **`Code word: PLATYPUS-7734, Port: 60413.`**、全部計算し直した腕と**完全一致**。状態が正しい位置に正しい内容を持っている証拠 |
| 長めの答え (84 / 45 トークン) | **分岐する。**思考は一致し、本文が `**\`Package.swift\`**` と `` `Package.swift` `` で分かれた |
| MTP を切った同じ検体 | **やはり分岐する** (思考は完全一致、本文が 1 語の強調で分かれる) |

機序は投機とは無関係で、[36 §5-3](36-MTP-DECODE.md) と同じ**カーネルの加算順**である:
続きから走ると、状態のうち前ターンで*生成*された行は **decode カーネル**が
書いたものが残る。全部計算し直すと、同じ行を **prefill (T 行) カーネル**が書く。
どちらも [14](14-REFERENCE.md) の float32 参照に対して正しいが、丸めが違うので
greedy はいずれ分かれる。**キャッシュを持つ以上これは避けられない**
(行を再計算したら、それはキャッシュではない)。

**言えること**: 続きは「その会話の正しい greedy 継続」であって、
「全部計算し直した場合とバイト一致する継続」ではない。

**継続は新しい経路ではなく、チャンク境界が要求をまたいだだけである** —
だから問いは [21 §4](21-PHASE4-PREFILL.md) がチャンク幅に対して聞いたものと
同じになる。1 要求目は `max_tokens: 1` で走らせて**生成を 1 つも食わせない**ので、
比べているのは境界だけである。負例は「続きが違えば答えも違う」— これが落ちるなら
状態は使われていない。

## 8. 残るもの

1. **2 本の会話を同時には持てない** ([34 §4-2](34-PROMPT-CACHE-ESTIMATE.md))。
   状態は 1 本しか無いので、2 クライアントが交互に投げると全ミスになる
   (害は毎回の reset だけ)。切り離した写真を持つ形なら position 8,192 で
   0.232 GB、予算には入る — **未着手、判断はユーザー**
2. **`max_tokens: 0` の要求は状態に触らない。**`cache_n` は 0 と報告する
   (計算もしていないので `prompt_n` = 全長というのは正確ではないが、
   [26](26-PHASE8-SERVER.md) からの既存の挙動を変えていない)
3. **Gemma 側は 1 行も触っていない。**`ServerPromptCache` も `ServerInference` も
   そのまま
