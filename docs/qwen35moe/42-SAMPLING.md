# 42. サンプリング — 公式推奨設定を実際に使う (要件と設計)

**要件 + 設計。**2026-08-22 起草。ユーザーが明示した 4 つの要件を仕様として
固定し、`Ornith-1.5-35B-A3B` の decode を greedy 固定から公式推奨サンプリングへ
移すための設計を置く。

---

## 0. 要件 (ユーザー指示、2026-08-22)

**明記しないと謎の仕様が生える**という指摘に対する、この 4 つが上位の制約である。
以下のどれかを壊す実装案は、速度が出ても採らない。

| # | 要件 | 意味 |
| --- | --- | --- |
| **S1** | **公式推奨サンプリングパラメータ以外は使ってはならない** | `temperature=0.6` / `top_p=0.95` / `top_k=20`。サーバーは常にこの 3 つで生成する。クライアントが別の値を送っても**この値で上書きして実行**し、上書きした事実を完了行に記録する。「受理して無視して greedy」は**廃止** |
| **S2** | **MTP は常に有効** | tools / reasoning / 文法 / サンプリングの有無に関係なく `--draft-block-size 2` が効き続ける。**「サンプリング時は MTP を off」は不可** |
| **S3** | **prompt cache は全条件で有効** | tools / reasoning / サンプリング / MTP のどの組み合わせでも `cache_n` が効く。切れるのは要求が `cache_prompt: false` を送ったときだけ (CACHE-5) |
| **S4** | **評価は除く** | 参照一致検査・MTP 受理率・ベンチ採点は `temperature 0` の greedy が要る。**例外は CLI (`TurboFieldfareCLI`) と検査経路のみ**で、サーバー (HTTP) には例外を作らない |

**S1 と S2 は同時に成り立たせる必要がある** — ここが設計の全部である。素直な
投機デコードは「本体の argmax と draft が一致したら受理」なので、サンプリングを
入れると分布が壊れる。壊さない形は §2 の投機サンプリングしかない。

   同じランタイムで片方が断り片方が黙るのが一番悪い → §3

## 2. 設計

### 2-1. logits を書くヘッド — 費用は 0.09%

[32 §4](32-NVMAI-ADOPT.md) は「ヘッドをもう 1 回畳む ≈ 4.0 ms/tok」を上限に置いたが、
**2 回目の走査は要らない**。`qwen_lm_head_greedy_int8_rows_chunk_raw` は今も 1 行
ずつ内積 `z` を計算していて、それを捨てて argmax だけ summaries に残している。
同じパスで `z` を FP16 で書き出すだけでよい:

| | |
| --- | --- |
| 追加で書くバイト | 248,077 × 2 B = **496 KB/行** |
| すでに読んでいるバイト | **540 MB/tok** ([19](19-LM-HEAD-INT8.md)) |
| 比 | **0.09%** |

サンプラは**既にある** — `Sources/TurboFieldfare/Runtime/Generation/Sampler.swift`
(Gemma が使っている GPU の top-k / top-p / 温度、FP16 logits [vocab] を取る)。
logit softcap は Qwen に無いので無条件適用を切る ([03 §178](03-DESIGN.md))。

### 2-2. MTP との両立 — 投機サンプリング (S1 + S2)

現行 ([36](36-MTP-DECODE.md)) の受理規則は **`draft == row0 の argmax`**。
サンプリング下でこれをそのまま使うと、受理された位置だけ greedy になり、
出力は温度 0.6 の分布ではなくなる (= S1 違反)。

正しい形は標準の投機サンプリング (Leviathan et al.)。**draft も本体と同じ
`lm_head` を通る** (`QwenMTPDrafter.swift:14` の `draft = argmax lm_head(...)`)
ので、§2-1 のヘッドを入れれば両方の分布が同じ経路から出る:

| 段 | すること |
| --- | --- |
| 1 | draft は **q から抽出**する (argmax をやめる)。q = 切り詰め + 温度をかけた draft 分布 |
| 2 | 検証パスは今と同じ 2 行 1 パス。row 0 から **p**、row 1 から **p'** を得る |
| 3 | `u ~ U(0,1)` を引き、`u ≤ p(d)/q(d)` なら**受理** → `d` を emit し、続けて **p' から抽出**した 1 個を emit (今の「2 トークン emit」と同じ位置) |
| 4 | 棄却なら **`(p − q)+` を正規化して抽出**した 1 個を emit。row 1 は捨てる (今と同じ `kv.rewind` と shadow の据え置き) |

**出力分布は p と厳密に一致する** (これが投機サンプリングの定理)。受理率は
argmax 一致より下がる (温度 0.6 で確率が割れるぶん) ので、**速度の再測定が要る**。

切り詰め (top-k / top-p) は **p と q の両方に同じ規則で掛けてから**比を取る。
両方とも「ソート順の接頭辞を残す」truncation なので、`top_k=20` を掛けた時点で
台は 20 個以下に収まり、比の計算も残差の再抽出もホストで数十要素を触るだけで済む。

### 2-3. 文法 / tools との両立 (S2)

GEN-7 は今「引いた token を gate に問い、棄却されたらマスクして**再採点**」
(`encodeMaskedRescore`、508 MB の 2 回目の読み) である。logits があれば
マスクは Gemma と同じ「その場で probs を作り直す」経路になり、2 回目の読みは
**棄却が起きたときだけ**に減る。

投機サンプリングと文法を同時に掛けるときは、**p と q に同じマスクを掛けてから**
比を取る。gate は逐次機械なので、位置 t のマスクは「t より前が全部確定した後」に
しか作れない — これは今の実装 ([40 §2](40-MTP-GRAMMAR.md)) が既に守っている順序と
同じで、draft 時点の gate 状態は確定している。

### 2-4. prompt cache (S3)

**影響を受けない。**一致判定はトークン列の接頭辞だけで決まり
([41](41-PROMPT-CACHE.md))、サンプラも MTP も判定に入らない。受理された draft 行が
再帰状態に畳み込まれている件 (`kvPosition` を runner から受け取る) も今のままでよい。

**ただし検査が 1 本増える**: サンプリングは非決定的なので、prompt cache の
「続きから走る」検査は**同じ seed** で走らせるか、トークン列ではなく `cached=` の
数字で判定する。

## 3. サーバーの作法 (S1)

| 項目 | 決定 |
| --- | --- |
| 既定 | 要求が `temperature` / `top_p` / `top_k` を**省略**したら公式値 (0.6 / 0.95 / 20) を入れる |
| 非準拠の明示指定 | **公式値で上書きして実行する** (400 では断らない)。ユーザー決定、2026-08-22 |
| 記録 | 上書きした事実は完了行に出す (`sampling/official-override: temperature=1.0→0.6 …`)。**黙って別のサンプラで走る道を塞ぐ**のが目的で、`greedy-only: … ignored` の置き換えになる |
| SPEC | R3 の「受理して無視」から外し、§12 の DEV エントリを書き換える。`min_p` などの未実装サンプラは DEV-5 のまま |
| 評価 (S4) | CLI は `--temperature 0` を受け付け続ける。サーバーには例外を作らない |

## 3-1. 何が実際に起きたか (**実測(手元)**、2026-08-22)

サーバー (`--draft-block-size 2`、32K、reasoning 既定 on) に 2 ターン投げた:

```
completed in 5.010s prompt=22 cached=0  completion=64 mtp=2 rounds=37 accept=0.703
  approx="sampling/official-override: temperature=1.0→0.6 top_k=none→20 top_p=none→0.95; …"
completed in 3.124s prompt=88 cached=69 completion=51 mtp=2 rounds=28 accept=0.786
```

4 つの要件がこの 2 行に出ている: **S1** 上書きが記録され (公式値どおり送った
要求には `sampling/` の行が 1 つも出ない)、**S2** `mtp=2` が動き、**S3**
`cached=69` が当たり、**S4** CLI と検査は greedy のまま。

### 速度と受理率 (interleaved A/B、192 トークン、3 反復の中央値、クールダウン 20 秒)

| タスク | 腕 | P1 | a | tok/s | decode gpu | decode host |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| a1-agent-edit | greedy | 89.1% | 1.901 | 18.89 | 22.96 ms | 29.99 ms |
| a1-agent-edit | 公式サンプラ | 84.6% | 1.846 | 16.46 | 26.18 ms | 34.58 ms |
| t2-code | greedy | 81.1% | 1.811 | 17.74 | 24.59 ms | 31.79 ms |
| t2-code | 公式サンプラ | 82.9% | 1.829 | **19.34** | 24.80 ms | 26.89 ms |

- **受理率はほとんど動かない。**温度 0.6 / top_p 0.95 の分布は十分に尖っていて
  `p(d)/q(d)` が 1 に近いので、投機サンプリングの受理は argmax 一致と
  ほぼ同じ頻度で通る。**S2 の代償は受理率ではない。**
- **tok/s の符号は 2 本のタスクで逆になった**ので、この n では速度差の向きを
  言えない。2 つの腕は**違うトークンを生成する**ので同じ仕事ではなく
  (エキスパートのヒット率が 49.9% 対 51.7%)、`decode host` の差も
  +4.6 ms と −4.9 ms で符号が割れている。
- ホスト側で払っているのは**語彙 248,077 行の走査**で、1 パスあたり最大 3 回
  (draft の `q`、row 0 の `p`、row 1 の `p'`)。減らす道はある (上位 k の抽出を
  GPU に戻す、粗い閾値で足切りする) が、**まだ測って必要だと分かってはいない**。

## 4. 段取り

全部済んだ (2026-08-22)。`--qwen` は 63 → **80 本**、すべて緑。

1. ✅ **ヘッド**: `qwen_lm_head_logits_int8_rows_chunk_multi` + 検査 7 本。
   書いた logit は既存 `dequant_int8_gemv_simd` と **rel 0.000e+00**
   (FP16 でビット一致)、argmax は融合ヘッドと一致。負例 2 本
2. ✅ **サンプラ**: `QwenSampler` (ホスト) + 検査 9 本。切り詰めは独立に double で
   作った参照と一致 (尖った分布と平坦な分布の**両方の枝**)。softcap を切り忘れる
   負例つき
3. ✅ **投機サンプリング**: `QwenSpeculativeDecode` の受理規則を差し替え。
   受入は合成分布 200,000 回で**全変動距離 0.0008** (許容 6e-3)。
   **負例が本題**: 今までの「argmax 一致で受理」をサンプリング下で使うと
   **全変動距離 0.5** — 半分の質量が別物になる
4. ✅ **文法との同時掛け**: `p` と `q` に同じマスクを掛けてから比を取る。
   マスクは draft の側で 1 回埋めて `p` が使い回す (§2-3)。
   非投機側は「引く → 判定 → 棄却なら覆面分布から引き直す」で、
   **`encodeMaskedRescore` の 508 MB 再読は棄却時だけ**になった
5. ✅ **サーバー**: `QwenGenerationPlan.officialSampling` で上書き + 記録。
   実機の 2 ターンで S1〜S4 を確認 (§3-1)
6. ✅ **再測定**: §3-1 の表

**採点できないと分かったものが 1 つある。**greedy の中立性 (強制棄却の対照と
トークン列が完全一致) は、サンプリングでは**成り立たない性質**である —
受理された腕は draft ストリームから引き、棄却された腕は残差から引くので、
同じ分布でも同じ列ではない。しかも T 行カーネルと decode カーネルは加算順が違う
([36](36-MTP-DECODE.md))。**分布の一致は合成分布で採り、実機で採点できるのは
結線だけ** (種を固定したら再現するか、分布と種からトークンを予言できるか)。

実機の分布そのものも見た (`--qwen-resume` が出す): この fixture では
**公式値の nucleus が 1 本 (p=1.000)**、温度 1.5 でも先頭が 0.986 を持つ。
**「種を変えたら列が変わる」は採点にならない** — モデルが自信を持っている
位置では、温度 0.6 の draw が毎回 argmax を返すのが正しい挙動である。
