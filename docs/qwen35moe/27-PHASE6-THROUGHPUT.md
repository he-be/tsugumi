## 1. 道具 — footer を 3 分割にした

Phase 6 の問いは「速いか」ではなく「**どこで待っているか**」なので、まず
[24 §4](24-PREFILL-MOE-PATH.md) が prefill のマイクロベンチでやった 3 分割
(GPU / 取得 / ホスト) を、**実物を動かす CLI の footer**に持ってきた。

```
[stop=maxNewTokens prefill=498tok new=128tok decode=6.40s tok/s=20.008]
[load=1.26s prefill=3.19s ttft=3.19s … peak=0.49GB]
[expert prefill hit=0.0% 0/7908 | decode hit=73.3% … | io prefill=2.23s decode=2.02s]
[prefill/tok gpu=3.05ms io=4.48ms host=-1.12ms cb=1.4]
[decode/tok gpu=28.50ms io=15.75ms host=5.73ms cb=121.0]
```

- `gpu` は `gpuEndTime - gpuStartTime` の総和 (`QwenForwardRunner.gpuSeconds`)、
  `io` は `ExpertTelemetry` の `fetchNanos`、`host` は**残差**である
- **`host` が負なら、それは異常ではなく重なっている証拠**である。直列だった頃は
  3 つが足し算で壁時計になっていた (§2 の表がそれである)
- `decode=` の意味も変えた。`runGreedyCompletion` が返す RSP-3 の分割を使うので、
  **prefill を含まない**。Gemma 側の footer と同じ意味になり、tok/s が比較できる

ついでに 2 つ直した: `cb=` (1 単位あたりのコマンドバッファ数) を出すようにし、
`prefill=` 秒を `load=` の隣に置いた。

## 2. 直列だったもの — 1 トークンに 81 回の join

decode の 1 層は「norm → 注意/再帰 → 残差 → norm → router」で 1 本、
**router の結果を CPU が読んでエキスパートを取ってから** shared + routed で
もう 1 本。この 2 本を**どちらも `commit` して `waitUntilCompleted`** していた。

| decode (m.json 498 tok / 128 新規、n=3 の中央値) | 直列 | 内訳の意味 |
| --- | ---: | --- |
| GPU | 34.80 ms/tok | 実際に GPU が回っていた時間 |
| 取得 | 16.97 ms/tok | routed expert の読みを**待っていた**時間 |
| ホスト | 16.99 ms/tok | 残り。**81 本の join の往復**がほぼこれ |
| 合計 (= 壁時計) | 68.8 ms/tok | 14.61 tok/s |

ホストの 17 ms は 1 本あたり 0.21 ms である。**GPU がやっている仕事ではない** —
`waitUntilCompleted` から次の `commit` までの往復で、その間 GPU は空いている。

prefill も同じ形で、1 チャンクにコマンドバッファが 700 本 (498 トークンなら
1 トークンあたり 1.4 本) ある。層ごとに pre-router 1 + shared 1 + **タイル 13** +
reduce 1 + 残差 1 で、**タイルは 1 枚ずつ「読む → 待つ → 積む → 待つ」**だった。

## 3. 外した 2 つの直列

### 3-1. 遅延 join — 次の join まで CPU は encode を続ける

キューはコマンドバッファを**コミット順に実行する**ので、層 L の MoE の結果を
層 L+1 の pre-router が読むことは、**join しなくても保証される**。join が要るのは
**ホストが GPU の書いたものを読む所だけ** — それは router の top-8 の読み戻しと、
最後の LM head である。

`commitDeferred` はコミットだけして待たず、次の `wait` が
(a) 順序の保証から**すでに終わっている**バッファを回収し、(b) その GPU 時間を
数え、(c) エラーを見る。1 トークンあたりの join は **81 → 41** になり、
ホスト時間は **16.99 → 5.73 ms/tok** に落ちた。

**危ないのは「ホストが書き換える GPU 可視のバッファ」1 種類だけ**である。
routed の argument buffer (`makeReusedRoutedArgumentBuffer`) は層ごとに
CPU が上書きするが、上書きは**次の層の `wait` の後**に起こるので、飛行中の
バッファが読んでいる間に書き換わることはない。

### 3-2. 読みと GPU を重ねる

**decode**: router の top-8 が読めたら**まず読みを始め** (`startRoutedExpertFetch`
は misses があれば別スレッドに出る)、その handle を待つ前に **shared 分岐を
encode してコミットする**。shared はこの層の MoE のうち**唯一「どのエキスパートか」
に依らない**部分なので、読みの陰に入れられる。

**prefill**: タイル *i* の GPU 仕事の裏で**タイル *i+1* の読みを走らせる**
(深さ 1)。読み先行の計画は**いま GPU が読んでいるタイルのスロットを避けて**
作る (`planRoutedExpertsIfPossible(avoidingSlots:)`) — mmap の腕では追い出し =
residency を落とすことなので、**カーネルの実行中に足元のページを落とさない**ため
である。避けきれない構成 (16 スロットは 1 タイルで埋まる) では**先行を諦める**。
そこは元の直列に落ちるだけで、正しさは動かない。

**先行は mmap の腕だけである。**私有スロットの腕 (`TF_EXPERT_MMAP=0`) では
タイルの blob がスロットそのもので、join していないバッファが読んでいる最中に
次の読みが上書きしうる。あの腕は測定用であって既定ではない (§6-3) ので、
**直列のまま**にした。

### 3-3. 落とし穴 1 つ — 「この層は mmap か」を層に訊いてはいけない

最初の実装は `model.routedExpertResidencySet(layer: L) != nil` で腕を判定した。
層ファイルは**最初の読みで開く**ので、これは**最初のチャンクの全 40 層で nil**を
返す。つまり**一番効かせたいチャンクだけ先行が切れる**。判定は
`model.usesMappedExperts` (プロセスの設定) に直した。**数字は 4.37 → 3.14 秒
(498 トークン) と動いた**ので、これは静かなバグの側だった。

## 4. 実タスク 4 本 (n=3、交互、`tasksab`)

合成の反復ではなく、実際に投げる形の 4 本。t4 だけがこの機械の文書
([01-MODEL.md](01-MODEL.md) の先頭 6,000 字) を読ませる長いプロンプトで、
prefill 側の代表になる。生成は 192 トークン固定、`--thinking off`、
運用点 (32 スロット / lfu / チャンク 2048 / mmap)。

| タスク | prompt | 生成 tok/s 直列 → 重ね | prefill 秒 直列 → 重ね | prefill tok/s |
| --- | ---: | ---: | ---: | ---: |
| t1 日本語の説明 | 56 | 16.31 → **22.33** (+37%) | 2.41 → **1.46** (−39%) | 23 → **38** |
| t2 コード生成 | 60 | 15.32 → **20.00** (+31%) | 2.56 → **1.54** (−40%) | 23 → **39** |
| t3 英語の散文 | 48 | 15.26 → **21.49** (+41%) | 2.76 → **1.52** (−45%) | 17 → **32** |
| t4 2,698 字の要約 | 2,698 | 10.94 → **15.29** (+40%) | 13.62 → **10.19** (−25%) | 198 → **265** |

同じ A/B を m.json (498 トークン) で取ると **14.61 → 20.01 tok/s**、
prefill **4.39 → 3.19 秒**。内訳は:

| m.json / 128 新規 | 直列 | 重ね |
| --- | ---: | ---: |
| decode GPU | 34.80 ms/tok | **28.50** |
| decode 取得 | 16.97 | 15.75 |
| decode ホスト | 16.99 | **5.73** |
| decode 壁時計 | 68.8 | **50.0** |
| prefill GPU / 取得 / ホスト | 3.05 / 4.52 / **+1.25** | 3.05 / 4.48 / **−1.12** |

**GPU 時間そのものも 34.8 → 28.5 ms/tok に減っている。**これは仕事が減った
のではなく、`gpuStartTime`〜`gpuEndTime` が**バッファ 1 本ごとの立ち上がりを
含む**ためで、本数が減れば総和も減る。壁時計の減りのうち何 ms がこれかは
**分けて測っていない** (未確認)。

**出力は 1 トークンも変わらない。**貪欲なので同じプロンプトからは同じ列が出る。
両腕の `new=` と本文が一致していることは 24 回の run すべてで確認した。

## 5. どこが天井か

重ねた後の decode 50.0 ms/tok は **GPU 28.5 + 取得 15.8 + ホスト 5.7** で、
**取得はまだ 1 度も GPU と重なっていない**。重ねられないのは、
**層 L のエキスパートが層 L の router を待つ**からである。
**§9 がこの 15.8 ms を解剖し、層をまたぐ先読みまで測った** — 正体は
デバイスの転送ではなく**ホスト側のページ写像**で、先読みは効くが既定は off。

prefill 側の天井は**読みそのもの**である。1 チャンクで層ごとに約 198/256 の
エキスパートに触るので、498 トークンのプロンプトで 13.4 GB を読む。
これは 6.2 GB/s で、この機械の SSD とページキャッシュの合成値としては
**上限に近い**。重ねの余地は残り 1.3 ms/tok (= 0.65 秒) ある。

**短いプロンプトの TTFT は「トークン数に比例しない」。**56 トークンでも層ごとに
約 150 のエキスパートを読むので 1.46 秒かかる — 1 トークンあたり 26 ms で、
2,698 トークンの 3.8 ms/tok の 7 倍である。チャットの体感を決めるのはこの定数で、
**減らす道は読みのバイトを減らすことしかない** (エキスパート 1 本は行が 3 行しか
使われなくても全部要る)。

### 6-1. スロット数と、机上のヒット率カーブ

`--dump-expert-trace` を 1 回取り、`bench/expert_sim.py` で追い出し規則を
再現した (モデルの再実行は不要)。トレースは m.json / 256 トークン生成。

| スロット | 常駐率 | decode hit (lfu) | decode hit (lru) |
| ---: | ---: | ---: | ---: |
| 16 | 6.2% | 61.9% | 58.4% |
| 24 | 9.4% | 69.7% | 66.0% |
| **32 (運用点)** | 12.5% | **74.9%** | 71.3% |
| 48 | 18.8% | 82.1% | 79.6% |
| 64 | 25.0% | 86.7% | 84.6% |

**シミュレータは実機と厳密に一致する** — 32/lfu の 74.9% は footer の
`decode hit=74.9% 61113/81600` とヒット数まで同じである。したがってこの表は
**実測 1 点からの導出ではなく、規則の再現**である。

- **lfu が lru に 3〜3.5 ポイント勝つ**のは全スロット数で同じ。既定は lfu のまま
- **prefill のヒット率は構造的に 0% である。**1 チャンクの中で各エキスパートは
  ちょうど 1 回しか要求されない (タイルは互いに素) ので、当たりようがない
- [05 §1-1](05-RISKS.md) の心配 (被覆率が 25% → 12.5% に半減する) は
  **ヒット率には出ていない**: Gemma の 32 スロットが 71.0% のところ、
  Ornith の 32 スロットは 74.9% である。母集団が 2.67 倍でも**ルーティングの
  偏りがそれを吸収している**

### 6-2. ヒット率は壁時計の代理にならない (mmap の腕では)

スロット数を振ると**ヒット率は大きく動くのに、時間はほとんど動かない**
(n=3、m.json / 128 新規):

| スロット | decode hit | 取得 ms/tok | tok/s | prefill 秒 |
| ---: | ---: | ---: | ---: | ---: |
| 16 | 60.6% | 16.85 | 19.25 | 3.21 |
| 24 | 68.2% | 16.12 | 20.00 | 3.23 |
| **32** | **73.3%** | **15.76** | **20.17** | **3.22** |

**ヒット率が 12.7 ポイント動いて tok/s は 4.8% しか動かない。**mmap の腕では
「ミス」はスロットの入れ替えであって、**バイトがディスクから来るとは限らない** —
ページキャッシュに残っていれば residency の付け替えだけで済む。
[05 §1-1](05-RISKS.md) が「32 スロットが覆うのは 1 層の 12.5%」と心配したのは
私有スロットの世界の話で、**既定の腕ではスロットは被覆率の指標であって
転送量の指標ではない。**

だから **48 スロットの提案は弱い**: 机上のヒット率は 74.9% → 82.1% に上がるが、
上の傾き (ヒット率 1 ポイントあたり 0.38%) をそのまま伸ばすと **tok/s は +2〜3%**
にしかならない (導出)。footprint は mmap の腕では動かない (peak 0.5 GB のまま)
ので害も無い。**候補追加の可否はユーザー判断**である
([04-PHASES.md](04-PHASES.md) 次の一手)。

prefill はスロット数に**まったく動かない** (3.21 / 3.23 / 3.22 秒)。§3-2 の
読み先行は 16 スロットでは「飛行中のタイルを避ける計画」が作れず諦めるが、
prefill の重なりの大半は**shared 分岐と第 1 タイルの読み**の方から来ているので、
そこは残る。

## 9. 残った取得を追い詰めた — 正体はページ写像だった

§5 は「取得 15.8 ms/tok は GPU と重なっていない」で終わっていた。**その 15.8 ms が
何なのか**を先に決めないと、隠す道具 (先読み) の値段が決まらない。

### 9-1. 「io」の 85% は residency set の更新で、その 94% は `commit()`

mmap の腕の「取得」は**バイトの転送ではない** — `MmapExpertMapping.syncResidency`
が `removeAllocation` / `addAllocation` / `commit()` / `requestResidency()` を
呼ぶ時間である。計器を足して割った (t1 / 192 トークン):

| | ms/tok |
| --- | ---: |
| expert io 全体 (prefill + decode) | 17.1 |
| うち residency の更新 | **14.6 (85%)** |
| └ 足し引き | 0.02 |
| └ **`commit()`** | **13.6 (94%)** |
| └ `requestResidency()` | 0.8 |

`commit()` は **1 回 0.4 ms** で、層ごと・トークンごとに呼ぶので 40 回/トークン。
set の大きさへの依存は弱い (16 / 32 / 64 本で 388 / 414 / 476 µs) ので、
**ほぼ固定費 × 回数**である。

`iostat` を同時に取ると、**decode 中の disk0 は 0.6〜0.85 GB/s** しか動いていない
(prefill 中は 2.4〜2.7 GB/s、冷たい device の天井は 6.0〜6.5 GB/s
[docs/mtp/33](../mtp/33-M8-IO-FLOOR.md) §0-2)。**バイトはページキャッシュに在る。**

### 9-2. 非投機的な手は 3 つとも引き分けだった (**実測**)

| 腕 | io ms/tok | host ms/tok | gpu ms/tok | tok/s |
| --- | ---: | ---: | ---: | ---: |
| 既定 (層ごとに commit) | 11.9 | 5.5 | 27.1 | 22.49 |
| ① 落とさない `TF_EXPERT_MMAP_RESIDENT=64` | 11.8 | 5.6 | 27.4 | 22.57 |
| ① 同 `=128` | — | — | — | **GPU OOM** |
| ② set を使わない `TF_EXPERT_MMAP_RESIDENCY=0` | 1.9 | 15.7 | 26.8 | 22.0 |
| ③ `TF_EXPERT_MMAP_COMMIT_EVERY=4 / 16 / 64` | 4.5 / 2.5 / 2.1 | 12.7 / 14.7 / 15.3 | 27.0 | 22.74 / 22.66 / 22.51 |

**どれも壁時計を動かさない。**`commit()` を消すと同じ時間が**カーネル内の
フォールト** (host の残差) に移るだけである。GPU 時間は全腕で 27.0〜27.4 ms と
1 度も動かない。

① が 128 で落ちるのは `iogpu.wired_limit_mb` が 8192 だからで
(128 × 1.69 MiB × 40 層 = 8.6 GB)、**set を大きくして写像を減らす道は
wired limit で閉じている**。

### 9-3. 正体 — 1 トークンに 9,200 ページ

ヒット率 72.4% なので **1 トークンに 85 本のエキスパートが常駐状態を変える**。
1 本 1.77 MB = **16 KiB ページ 108 枚**なので、**約 9,200 ページ/トークン**。
`commit()` で払っても、カーネル内のフォールトで払っても、**誰かが払う**。
これが decode 44.5 ms/tok の内訳「計算 27 + 写像 17」の後半である。

16 → 32 スロットの実測 (§6-2) から**限界費用は 1 ミスあたり約 0.06 ms**
(41 ミス減で 2.4 ms) と読める。32 → 48 スロットは −28 ミス/tok ≈ **+3.5%** の
見込み (**導出**)。

### 9-4. 層をまたぐ先読みの的中率 (256-way、**実測**)

層 L の pre-router コマンドバッファに**層 L+1 の router を相乗り**させ
(層 L の `normed` に当てる)、**層 L の join で一緒に読み戻す** — 追加の
往復はゼロである (`TF_QWEN_ROUTER_PREVIEW=1`、方策は何も変えない計器)。

| | 値 |
| --- | ---: |
| 比較した (層, トークン) | 7,449 |
| 予測 top-8 と実際の top-8 の重なり | **78.2%** |
| **実際に取得が要った 15,937 本のうち予測が名指していた割合** | **64.5%** (10,286) |
| rank ごとの的中 (使われた) | 98.6 / 96.6 / 93.4 / 87.7 / 79.7 / 68.1 / 57.2 / 44.0% |
| rank ごとの「取得が要った」 | 13.2 / 16.3 / 17.4 / 19.1 / 20.4 / 19.2 / 17.4 / 15.2% |

**Gemma の 128-way が 70% だったのに対し、256-way でも 64.5% が名指せる。**
rank ごとに見ると 1 位はほぼ必ず使われ (98.6%)、8 位でも 44% は使われる。
外れても**常駐していれば費用はゼロ** (プランがヒットとして見る) で、
**費用が出るのは「非常駐かつ使われない」ぶんだけ**である。

### 9-5. 実際に投げた A/B (n=3、交互、`TF_QWEN_EXPERT_PREFETCH=8`)

投げ方は Gemma の設計 ([docs/mtp/30](../mtp/30-M8-B-PREFETCH.md) §1) をそのまま:
`planSpeculativeRoutedExperts` は**使用回数を上げず、直近のプランが触った
スロットは犠牲にしない** (置けなければ諦める)。待つのは**その層のプランを作る
直前**、残りはトークンの終わりで畳む。

| プロンプト | off | top-8 先読み | 差 | decode hit |
| --- | ---: | ---: | ---: | --- |
| t1 日本語の説明 (56 tok) | 22.41 | **22.83** | +1.9% | 72.4 → 80.6% |
| m.json (498 tok) | 20.07 | **21.60** | **+7.6%** | 73.3 → 81.3% |
| t4 要約 (2,698 tok) | 15.83 | **17.92** | **+13.2%** | 65.0 → 75.2% |

**出力は 1 バイトも動かない** (md5 一致、`--qwen-decode` は 55 本全一致、
mmap と私有スロットの両腕で)。効きはミスの多さに比例する — t4 が一番効き、
GPU 律速に近い t1 が一番効かない。

費用も見えている: 予測の router GEMV が **GPU を +1.2〜1.8 ms/tok** 押し上げる
(40 層ぶんの追加ディスパッチ)。t1 で効きが薄いのはこれが利得と釣り合うため。

### 9-6. なぜ Gemma では負けて、ここでは勝つのか

同じ機構が [docs/mtp/30](../mtp/30-M8-B-PREFETCH.md) では **−3.5% / −1.5%** だった。
違いは的中率ではない (あちらも 70% で当たっていた)。**待ちの正体が違う**:

| | Gemma (2026-08-19、私有スロット) | Ornith (本書) |
| --- | --- | --- |
| 待ちの正体 | **デバイス帯域** (深さ 4.72 で 5.91 GB/s ≒ 天井 6.0-6.5) | **ホスト側のページ写像** (デバイスは天井の 1 割) |
| 外れの費用 | 読むバイトが **+11%**。床に当たっているのでそのまま時間 | 写像 1 本 ≈ **0.06 ms**、常駐していればゼロ |
| 32 / 48 スロットの床 | 32 は I/O 床、48 は **GPU 床** ([33](../mtp/33-M8-IO-FLOOR.md) §0-5) | 計算 27 ms と写像 17 ms が**直列に並んでいる** |

つまり **Gemma には隠す先が無かった** (どちらかが必ず床) のに対し、Ornith では
**GPU が 27 ms 回っている間にホスト側の写像を進められる**。

### 9-7. 既定は off のまま

`TF_QWEN_EXPERT_PREFETCH=<N>` で入る (0 = 既定 = off)。既定を変えるかは
**ユーザー判断**である ([04-PHASES.md](04-PHASES.md) 次の一手 #29)。判断材料:

- **利得は +1.9〜13.2%**、プロンプトが長い (= ミスが多い) ほど効く
- **出力は動かない。**メモリも動かない (peak 0.5 GB のまま)
- 対価は **GPU +1.2〜1.8 ms/tok** の予測 GEMV。短いプロンプトではこれが利得の
  大半を食う
- 触るのは `QwenForwardRunner` だけで、**Gemma の経路は 1 行も変わらない**
