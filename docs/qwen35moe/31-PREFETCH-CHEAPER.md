## 1. 計器 — 何を待っていたのか

方策を変えずに 3 つ足した (`ExpertPrefetchStats`、footer の `[prefetch …]` 行):
発行数 / 棄却数 / 自分の推測を待った時間。運用点 (32 スロット、n8) で:

| プロンプト | issued | declined | reads | waits (>100 µs) | wait 合計 |
| --- | --- | --- | --- | --- | --- |
| m (498 tok) | 4,953 | **0** | 10,805 | 4,953 (323 = 6.5%) | 141.8 ms = **1.11 ms/tok** |
| t4 (2,698 tok) | 4,953 | **0** | 13,592 | 4,953 (414 = 8.4%) | 183.8 ms = **1.44 ms/tok** |

- **`declined = 0`** — 投機プランの all-or-nothing な棄却
  (`PreadExpertStreamer.swift:341`) は N=8 では 1 度も起きない。
  [28 §3-2](28-PREFETCH-IDEAS.md) の半減リトライも partial プランも**要らない**。
  N=12/16 でも 0 のままだった (§2-2 の表)。
- **wait の平均は 29〜37 µs**、93% は 100 µs 未満。リードタイム (層 L の MoE の
  GPU 時間) は**足りている**ので、[28 §3-3](28-PREFETCH-IDEAS.md) の d=2 は
  「的中を落とすだけの手」の側に落ちた。**やらない。**
- 1 プランが実際に動かすのは **2.18 本** (10,805/4,953)。残りは既に常駐で、
  [28 §1-1](28-PREFETCH-IDEAS.md) の「常駐ならゼロ」がそのまま出ている。

## 2. N を振る — 予測は当たる、写像が増える

### 2-1. 机上 (先読み off、preview だけ 16 ランク)

select カーネルは k=8 固定なので、9 位以降は GEMV の 256 logit を**ホストが
並べて**取る (§3-1 の経路)。先読みを止めて名指しだけ数えると:

| | miss/ペア | ランク 1〜8 が名指す | 1〜16 が名指す | 9〜16 の上積み |
| --- | --- | --- | --- | --- |
| m (498 tok) | 2.068 | 65.9% | **88.8%** | +22.9 ポイント |
| t4 (2,698 tok) | 2.674 | 61.6% | **84.6%** | +23.0 ポイント |

[28 §3-1](28-PREFETCH-IDEAS.md) の見込み (「裾は厚い」) は正しかった。

### 2-2. 実機 (n=3、中央値、`bench/qwen35.sh prefetchn`)

| 腕 | m: tok/s | GPU | io | 実プランの miss | reads/層 | wait |
| --- | --- | --- | --- | --- | --- | --- |
| off | 19.772 | 28.71 | 15.56 | 10,244 | — | — |
| n8 | 21.573 | 29.63 | 23.41 | 3,650 | 2.18 | 1.11 ms/tok |
| n8w | 21.582 | 28.28 | 24.72 | 3,650 | 2.18 | 1.20 |
| n12 | 21.799 | 28.30 | 29.47 | 1,973 | 4.05 | 4.26 |
| n16 | 19.847 | 29.41 | 38.00 | **1,316** | 6.17 | **8.50** |

t4 (n=3) も同じ形: n8w 18.076 / n12 17.339 / n16 16.045。

> tok/s・GPU・io は中央値だが、**右の 3 列 (miss / reads / wait) は run 間で
> 完全に一致する** — 貪欲で出力が同じなら経路も plan も同じで、計器は同じ数を
> 出す (`reads=10,805` は 3 回の n8 run すべてで一致した)。

**名指しは効いている** (miss 3,650 → 1,316) のに壁時計は落ちる。理由は
[28 §1-1](28-PREFETCH-IDEAS.md) の通貨で読める — **先読みは写像を消す機構では
なく、陰に移す機構**である。N を上げると移す量が増え (reads 2.18 → 6.17)、
陰 (層あたり GPU ≈0.7 ms) に入りきらなくなって wait に出る (1.11 → 8.50 ms/tok)。
io も 15.6 → 38.0 ms/tok に膨らむ。**N の限界費用が GPU 側でゼロなのは
[28 §0-2](28-PREFETCH-IDEAS.md) の言う通りだった** が、律速はそこではなかった。

> **`declined` は N=16 でも 0**。棄却は N を上げても起きない
> (投機プランは直近プランのスロットを避けるだけで、32 スロットに 8+16 は入る)。

## 3. 固定費 — ディスパッチの本数を削る

### 3-1. preview の select を出さない (n8w)

GEMV は元から 256 logit 全部を書いている。top-8 に切っていたのは後段の select
カーネルだけなので、**preview では select を encode せず、ホストが並べる**
(`MoE.encodeRouterLogitsBF16` + `QwenForwardRunner.rankLogits`)。
ホスト側は 256 要素の挿入 1 パスで、読み戻す join は元からある。

**同値であることを実測で確かめた** — `TF_QWEN_PREVIEW_WIDE=1` で N=8 のまま
広い経路を通すと、preview の列 (overlap 79.0%、rankUsed 98.6/…/45.2)、
reads=10,805、hit=81.3%、出力の sha256 まで k=8 経路と**完全に一致**する。
tie の割り方まで `router_topk_select_k8_body` に合わせてある。

削れるのは **40 ディスパッチ/tok**。GPU 時間は **−1.4〜1.6 ms/tok** で、
[27 §4](27-PHASE6-THROUGHPUT.md) の「本数が減ると gpu 総和が減る」の encoder 版。
1 本あたり **≈35〜40 µs** (導出)。

### 3-2. 2 層ぶんの router を 1 ディスパッチに融合 (n8f)

[28 §3-4 (b)](28-PREFETCH-IDEAS.md) をカーネル 1 本で実装した
(`router_gemv_gemma4_bf16_pair_r4`: 行 2×256、低い半分が自層、高い半分が
preview。各行は自分の simdgroup を持つので**還元順は変わらない**)。
検査は通り (`--qwen-decode` 55 本一致)、GPU はさらに **0.3〜0.6 ms/tok** 下がる
(m: 28.35 → 27.78、t4: 32.37 → 32.13)。**が、壁時計には出ない** —
m は +0.9% (4/5 ペア)、t4 は −1.0% (2/5 ペア)。**引き分けとして記録**し、
既定は off (`TF_QWEN_PREVIEW_FUSE=1` で入る)。
GEMV は launch だけでなく実仕事を持つので、select ほど純粋な overhead では
なかった、と読める (**導出**)。

## 7. 適応スキップは成立しない — 層分布に崖が無い (**導出**、2026-08-22)

[28 §3-4 (c)](28-PREFETCH-IDEAS.md) の在庫 (「層別の miss 分布から preview を
張らない層を選ぶ」) を、§6 の予告どおり**トレース 1 本だけ**で引いた
(`bench/qwen35_preview_skip.py`、`scratch/qwen35/preview-skip.txt`)。
**モデルの再実行はしていない。**

### 7-1. 先に機構の訂正 — preview は 40 本ではなく 39 本/tok

`QwenForwardRunner.swift:862` の条件は `L + 1 < cfg.numLayers` なので、
preview を張るのは**層 0〜38 の 39 本**である (層 39 の次は無い)。
§1 の計器 `issued = 4,953` は **127 tok × 39** で、これが裏付ける。
§3-1 の「削れるのは 40 ディスパッチ/tok」は **39 ディスパッチ/tok** が正しい
(§3-1 の GPU −1.4〜1.6 ms/tok は実測なので動かない。1 本あたりの導出値が
35〜41 µs になるだけ)。**層 0 の miss (4.38/tok) は誰も先読みできない。**

### 7-2. 検算 — このトレースは §2-2 の off 腕そのものである

`bench/expert_sim.py` と同じ追い出し規則を当てると、
**10,712 行すべてでトレース自身の `hits` / `misses` 列と一致した**。

| 量 | §2-2 の実測 (m、off 腕) | 本トレース (**導出**) |
| --- | ---: | ---: |
| plan の miss /tok | 80.66 (10,244 / 127) | **80.34** (20,487 / 255) |

2 桁目まで一致するので、以降はこのトレースを off 腕の代理として使える。

### 7-3. 層別の miss 分布 — 崖が無い (255 ステップ × 40 層)

| | 値 |
| --- | ---: |
| 全体 | **80.34 miss/tok** |
| 一様なら | 2.009 miss/step/層 |
| 最大 | L2 **4.435** (L0 4.376 / L1 4.404 が並ぶ) |
| 最小 | L36 **0.890** (L39 1.020 / L35 1.141 / L34 1.165) |

| miss の多い上位層 | 累積比 | 一様なら |
| ---: | ---: | ---: |
| 4 層 | 20.1% | 10% |
| 10 層 | 38.7% | 25% |
| 20 層 | 63.9% | 50% |
| 30 層 | 84.4% | 75% |

**最大と最小で 5 倍しか違わず、上位 10 層でも 38.7% にしかならない。**
形は「前 3 層が高く、深いほど緩やかに下がる」勾配で、**崖は無い**。
「miss がほとんど無い層」は 1 つも存在しない — 一番静かな L36 でも
0.890 miss/step で、miss = 0 のステップ比は最大の L39 でも 50.2%。

### 7-4. 層別の名指し率は**未確認**

28 §3-4 (c) の仮説のもう半分「予測が当たらない層」は**引けなかった**。
preview の予測は層 L+1 の router GEMV が出す 256 logit の順位だが、
**トレースには実際に使われた top-8 しか列が無く、予測の列が存在しない。**
全体値 64.5% は [27 §9-4](27-PHASE6-THROUGHPUT.md) の実測があるが、層別の
内訳はどこにも記録されていない。取るには層別の計器を足して実機を 1 本回す必要がある。

**副産物が 1 つ出た (構造の事実):「前トークンの top-8」を予測子にしたときの
名指し率は、40 層すべてで厳密に 0.0% である。**32 スロットの層は 1 トークンに
1 回しか要求を受けないので、前トークンの 8 本は追い出される機会が無く必ず常駐している。
つまり **miss とは定義上「最近使っていない本」**であり、履歴だけの安い予測子
(過去 16 トークンまで広げても層帯ごとに 11〜43%) は router GEMV の代わりにならない。
§2-1 で N を 16 まで広げたのと同じ結論を別の側から言っている。

### 7-5. 判定 — どこを切っても負

陰に入りうる miss は層 1〜39 の 75.96/tok (層 0 の 4.38 は元から入らない)。
miss の少ない層から順に preview を切ると:

| 打つ GEMV | 切る層 | 失う miss/tok | 陰の miss 比 | 名指し失 (×0.645) | 差 (µs/tok) |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 39 | 0 | 0.000 | 0.0% | 0.000 | 0 |
| 36 | 3 | 3.051 | 4.0% | 1.968 | **−52** |
| 30 | 9 | 11.020 | 14.5% | 7.108 | **−228** |
| 20 | 19 | 27.216 | 35.8% | 17.554 | **−635** |
| 10 | 29 | 46.992 | 61.9% | 30.310 | — |

換算 (すべて**導出**):

- **GEMV 1 本 = 15〜22 µs。**§3-2 の融合が 39 本ぶんの launch を半分にして
  GPU −0.3〜0.6 ms/tok なので launch は 8〜15 µs/本、router 重み 1 MiB/層の
  読みが ≈7 µs。§3-1 の select 1 本 (≈35〜41 µs) より**安い**。
- **陰から出た miss 1 件 = 60 µs** ([27 §9-3](27-PHASE6-THROUGHPUT.md) の
  写像の限界費用)。別ルート (§2-2 と §4 から、m の利得 4.48 ms/tok ÷
  陰に移した 51.92 miss/tok) では **86 µs/件**。

**損益分岐は 0.388〜0.568 miss/step。これを下回る層は 0 層である**
(一番静かな L36 で 0.890)。86 µs 側で引くと分岐点は 0.27〜0.40 とさらに下がる。
逆に解くと、**L36 一本を切るだけでも preview GEMV が 34 µs 以上でなければ
分岐しない** — それは select 1 本と同格ということで、§3-2 の融合実験が否定している。

**28 §3-4 (c) は閉じる。**理由は仮説 (a)「miss がほとんど無い層」が実在しないこと。
仮説 (b) の側は §7-4 のとおり未確認だが、閉じたとしても浮く上限は
39 本 × 22 µs = 858 µs/tok = 46.2 ms/tok の **1.9%** で、その全部を取るには
全層スキップ (= 先読みそのものの停止、−2,082 µs/tok) が要る。
**部分集合で符号が反転する余地は無い。**
