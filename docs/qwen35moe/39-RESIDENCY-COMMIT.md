# 39. residency の commit を呼び出しスレッドから外した — 検証パスの io を 38.2 → 7.2 ms/パスに (実測(手元)、2026-08-22)

[38 §7](38-MTP-VERIFY-PATH.md) は次の一手を 2 つ挙げて終わった:
**1. `io` (エキスパート取得) が検証パスの最大の項になった**、
**2. `draft` が 6.0 ms/パスで計器がまだ無い**。本書はその 2 つを測り、
そこから出た手を 2 本試して 1 本を採った。

**結論を 1 行で: 取得の待ちは「読み」ではなく `MTLResidencySet.commit()` で、
それを呼び出しスレッドから外すだけで素の decode も MTP も速くなる。**
`commit()` を捨てる腕 ([27 §9-2](27-PHASE6-THROUGHPUT.md) ②) は引き分けだったので、
**払う仕事が無駄だったのではなく、払うスレッドが間違っていた。**

## 1. `draft` に計器を入れた — [38 §7-2](38-MTP-VERIFY-PATH.md) を閉じる

ドラフタは runner のコマンドバッファを使わず自前で `commit`/`waitUntilCompleted`
するので、[38](38-MTP-VERIFY-PATH.md) の段プロファイルでは `draft` だけ
**GPU 時間が 0** と出ていた。`QwenMTPDrafter.DraftProfile` を足し、
ヘッド自身の構造で 3 つに切った (`[mtp/draft …]` 行、**実測(手元)**):

| 区間 | 中身 | wall ms/パス | GPU ms/パス |
| --- | --- | ---: | ---: |
| `catchup` | 受理された前パスが飛ばした位置に `(k, v)` だけ書く行 | 0.40 | 0.26 |
| `preRouter` | 最終行の 1 本目 — embed / fc / norm / QKV / attention / router / 共有エキスパート。router をホストが読むので join される | 1.03 | 0.77 |
| `tail` | 2 本目 — routed エキスパート 8 本 + residual + final norm + **508 MB の `lm_head`** | 4.70 | 4.48 |
| **計** | (t2 コード、`rows=1.72`、`cb=2.72`) | **6.15** | **5.51** |

**89.6% が GPU である。**ホスト側の取り分は 0.64 ms/パスしかない —
つまり「router の読み戻しのために 2 本に割っている」代償は
**1 パス 0.64 ms = 0.7%** で、GPU で routing を回して 1 本に融合しても
それ以上は取れない。[38 §7-2](38-MTP-VERIFY-PATH.md) が「勝ち幅 15〜20% と
同じ桁」と書いた 6.0 ms は、**削れる無駄ではなく実際の計算**だった。

中身は `tail` の 4.48 ms に集中していて、その大半は 508 MB の `lm_head` 1 行ぶん
である (同じパスで本体の `head` は 2 行で 5.77 ms)。**1 パスにつき 508 MB を
2 度読んでいる** — ドラフタが 1 行、検証が 2 行。これが §7 の動機になり、
§7 でそのまま潰れた。

## 2. 層またぎの先読みを検証パスに入れた — 負け (**実測(手元)**)

[27 §9-5](27-PHASE6-THROUGHPUT.md) の先読み (層 L の `normed` に層 L+1 の router を
当て、予測の強い順に前倒しで取得) は **decode ループにしか無い**。検証パスは
`runChunkLayers` を通るので、1 層 1 タイル・重ねる相手が共有エキスパートだけ、
という一番痩せた形で走っていた。そこに同じ機構を入れた
(`TF_QWEN_MTP_PREFETCH=<N>`、2 行の予測 top-N の**和集合**を rank で交互に並べる)。

同一セッション、t2 コード、64 トークン:

| 腕 | tok/s | `io` ms/パス | `preRouter` GPU | syncs | commit ms/tok |
| --- | ---: | ---: | ---: | ---: | ---: |
| `width2` | **18.277** | 38.22 | 25.52 | 1,681 | 18.39 |
| `width2pf` (N=4) | 17.786 (**×0.973**) | 33.38 | **33.79** | **2,687** | **26.92** |
| `width2async` (§3) | **19.533** | **7.23** | 25.40 | 1,531 | 17.03 |

予測そのものは**よく当たっている** — rank ごとの的中は
98.7 / 98.3 / 96.6 / 93.9 / 87.9 / 66.7 / 35.8 / 12.3%、`declined=0`。
それでも負けるのは 2 つの理由が重なるからで、どちらも
[27 §9-5](27-PHASE6-THROUGHPUT.md) の decode の数字からは読めない:

1. **予測 router の GPU が +8.3 ms/パス。**decode の +1.2〜1.8 ms/tok に対して
   2 行ぶんで 3 倍近い。T 行のブロック router をもう 1 本回す形が、
   幅 2 では割に合わない。
2. **commit の通貨は「回数」である。**先読みが層 L+1 の**ミス集合を丸ごと**
   覆わない限り、その層は自分の取得でもう一度 `syncResidency` を呼ぶ —
   1 本でも足りなければ 0.6 ms の commit が丸ごと出る。
   [27 §9-4](27-PHASE6-THROUGHPUT.md) の実測は「取得が要った本のうち予測が
   名指せるのは 64.5%」なので、**覆えることはまず無い**。実測でも
   syncs は 1,681 → 2,687 と**増え**、commit は +8.5 ms/tok 増えた。

`io` が 4.8 ms 減ったのは先読みぶんの commit が背景に逃げたからで、
差し引き +2.4 ms/パスの負けである。**既定は off のまま残す** — 機構は
正しく動いており (的中・refusal・待ちのどれも健全)、負けているのは
この土俵の費用構造のほうだからである。

### 2-1. 負けた実験が次の手を決めた

この腕で一番効いたのは tok/s ではなく `[prefetch …]` の 1 行だった:

```
prefetch issued=1404 declined=0 reads=2346 waits=1404 slow=0 max=0.05ms wait=0.1ms (0.002ms/tok)
```

**1,404 回の先読みが 1 度も待たされていない。**先読みの commit は
「層 L のミス待ち + MoE の encode + 層 L+1 の pre-router」= 実測 2 ms 強の
リードタイムの裏で完全に終わっている。つまり **commit は背景スレッドに
置けば critical path から消える**。あとは「層自身の commit も背景に置けるか」
だけで、それは正しさの問題である。

## 3. 採った手 — `commit()` を専用の直列キューに投げる

**mmap の腕の `executeExpertCachePlan` はバイトを 1 つも読まない。**返すのは
`expertCachePlanBuffers` — マッピングを切った `MTLBuffer` そのもので、
residency の状態とは無関係である。常駐の**保証**は `useResource` が出しており、
[49 §2](../mtp/49-D-P5-RESIDENCY-SET.md) はそれを外していない。
`MTLResidencySet` が買っているのは「フォールトをカーネルの外に出すこと」だけで、
**待つ理由は 1 つも無い。**

```
TF_EXPERT_MMAP_RESIDENCY_ASYNC=1
```

- **帳簿は同期のまま。**`slotExpert` / `expertResidency` の更新はプランが
  予約したスロットの確定で、次のプランがそれを読む。ここを遅らせたら
  二重書きになる。
- **set の編集 + `commit()` + `requestResidency()` だけ**を層ごとの直列キューへ。
  直列なのは `syncResidency` の中の `lock` と同じ理由 (スナップショットを撮る順と
  set に当てる順が入れ替わってはいけない) と、層ごとにスレッドを増やさないため。
- スナップショットは**適用時**に撮る (`cacheLock` の下で `slotExpert` を読む)。
  だから遅れた sync ほど新しい状態を映し、**間に挟まった sync が
  「足すものが無い」で丸ごと消える** — §6 の `added` 半減はこれである。

新しいカーネルは 0 本、Metal の 1 行も触っていない。

## 5. 「commit は要らなかった」ではない — 三者比較 (**実測(手元)**)

[27 §9-2](27-PHASE6-THROUGHPUT.md) ② の「set を使わない」腕
(`TF_EXPERT_MMAP_RESIDENCY=0`) は引き分けだった。**同じ腕を同じセッションに
並べると、非同期との差が機序を名指す**:

| タスク | `base` | `basenores` (set 無し) | `baseasync` |
| --- | ---: | ---: | ---: |
| a1 エージェントのコード修正 | 13.557 | 13.213 (**×0.975**) | 15.671 (**×1.156**) |
| t2 コード生成 | 20.752 | 20.468 (**×0.986**) | 21.210 (×1.022) |

**set を捨てると引き分け以下** — 27 の結論の再現である。**非同期だけが勝つ。**
つまり `commit()` が買っている「フォールトの先回り」は**実際に効いていて**、
27 が測ったのは「先回りの価値」ではなく「**先回りを呼び出しスレッドで
やることの代償**」だった。両者は同じ大きさなので、同期の腕では相殺して
引き分けに見える。分けて初めて差が出る。

> a1 の `baseasync` は反復間の振れが大きい (16.405 / 14.937)。中央値は取るが、
> **この 1 セルに「×1.156」以上の解釈は載せない。**言えるのは
> 「set 無し < 同期 < 非同期」の並びまでである。

読み方は 2 つある:

1. **`io` はほぼ消える** (t2 の検証パスで 36.5 → 8.3、t4 で 48.8 → 9.3)。
   しかし**減ったぶんの大半は次の層の join に現れる** (`preRouter` の host)。
   背景スレッドの commit とメインスレッドの `commit`/`waitUntilCompleted` は
   ドライバの中でぶつかっており、**完全な並列にはならない**。

ここで動かしているのは計算ではなくページ写像だけである。

## 7. 潰した案 — ドラフタの語彙を切り詰める

§1 の「1 パスに 508 MB を 2 度読む」から、**ドラフタ側だけ語彙の先頭 N 行に
切る**案が出る。投機なので**正しさは動かない** — 外れたら検証が捨てるだけで、
費用は受理率の低下として現れる。幅 2 の算術では
`d(tok/s)/tok/s = dP1/(1+P1) − dC/C` なので、P1 = 75% では
**受理率 5.6 ポイントまでなら 3.2% の費用削減と釣り合う**。

実装する前に、既存の A/B の `--dump-tokens` で**生成トークンの id 分布**を
測った (**実測(手元)**、`bench/qwen35/mtp38-ab/*.mtp.1.json`):

| タスク | id < 16,384 | < 32,768 | < 65,536 | < 131,072 |
| --- | ---: | ---: | ---: | ---: |
| a1 エージェントのコード修正 | 80.2% | 82.8% | 86.5% | 93.2% |
| a2 エージェントのツール JSON | 87.9% | 93.9% | 98.5% | 98.5% |
| t2 コード生成 | 78.6% | 79.7% | 82.8% | 93.2% |
| t3 英語の散文 | 89.6% | 94.8% | **99.0%** | 99.5% |
| t4 2,698 tok の要約 | 67.7% | 73.4% | 75.0% | 90.6% |

**248,077 行の語彙は頻度順ではない。**半分に切っても t2 / t4 は
7〜9 ポイント、4 分の 1 に切れば 17〜25 ポイント落ちる — 上の許容幅
5.6 ポイントの 3〜4 倍である。**先頭 N 行の切り詰めは筋が悪い。**

残る形は「頻度順の索引を作って gather する `lm_head`」だが、
それは新しいカーネル 1 本と語彙索引という成果物 1 つを要求し、
天井は 4.5 ms/パス (4.5%) である。**先に §3 を採った理由がこれで、
着手するとしても順番は後**になる。

## 8. 検算

### 8-1. Phase 4 の検査 (`TF_EXPERT_MMAP_RESIDENCY_ASYNC=1`)

```
PASS  41 tokens, every one equal to the float32 reference
PASS  chunk 8 (3 chunks) — the same 41 tokens
PASS  routed experts on the per-pair path, chunk 512 (1 chunks) — the same 41 tokens
PASS  routed experts on the per-pair path, chunk 8 (3 chunks) — the same 41 tokens
  negative controls — each must disagree within 16 tokens:  5/5 PASS
```

### 8-2. 投機の中立性と、38 との一致

- `TF_QWEN_MTP_FORCE_REJECT=1` と本番の腕が **96/96 一致** (非同期 on、t2、96 トークン)。
  [38 §4](38-MTP-VERIFY-PATH.md) が守った性質は保たれている。
- 非同期の腕の出力が [38](38-MTP-VERIFY-PATH.md) の同期の腕と **96/96 一致**。
- 素の decode は `base` と `baseasync` で **192/192 × 3 タスク一致** (§4)。

### 8-3. `swift test`

1,350 テスト / 206 スイート。**失敗 22 件はすべて `remote HTTP 404: https://hf.test/…`**
で、[36 §6-2](36-MTP-DECODE.md) / [38 §6-3](38-MTP-VERIFY-PATH.md) と同じ

## 9. 残る未確認と、次の一手

1. **`preRouter` の host が新しい最大項になった** (t2 の検証パスで 41.4 ms/パス、
   素の decode で 27.2 ms/tok)。背景の commit とメインスレッドがドライバの中で
   ぶつかっているぶんで、**そこに計器がまだ無い**。次に測るならここ。
2. **既定を変えるかはユーザー判断。**`MmapExpertMapping` は Gemma 側も通る
   共有経路で、A/B は Ornith の 3 タスクしか見ていない
   ([27 §9-7](27-PHASE6-THROUGHPUT.md) と同じ扱い)。
3. **先読みは既定 off のまま残した** (§2)。予測 router の GPU が幅 2 で 3 倍
   高いことが主因なので、融合 router (`encodeRouterGemma4BF16Paired` の T 行版)
   があれば結論は変わりうる。**未実装・未測定**。
