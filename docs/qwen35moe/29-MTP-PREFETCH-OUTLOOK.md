verify ブロックの世界でどう化けるか、そして MTP でしか出てこない手を、
同じ作法 (実装の形と判定基準つき) で在庫にする。**

## 0. 結論を先に

| # | 論点 | 結論 |
| --- | --- | --- |
| 1 | MTP は何を割るか | **写像の主部は commit の固定費 × 回数であり、MTP はその回数を割る。**io 15.8 ms/tok の 94% は `commit()` 0.4 ms × 40 回/tok で、**set の大きさへの依存は弱い** (16/32/64 本で 388/414/476 µs、[27 §9-1](27-PHASE6-THROUGHPUT.md))。verify ブロックでは residency の更新が層ごと・**ブロックごと**になるから、この 13.6 ms/tok が **13.6/a ms/tok** になる — union が膨らんでも固定費の側はほぼ増えない (**導出**、§1-1) |
| 2 | 28 の在庫は死ぬか | **死なない。ブロック版に化ける。**preview は k 行で張り (k 行 router は Gemma M5.6 のカーネルが前例)、union の top-N を host が選ぶ — 本ブランチの `rankLogits` は行を回すだけ (§2)。しかも 28 §3-4 の固定費 (予測 GEMV +1.2〜1.8 ms/tok) も **a で割れる**ので、**MTP 自体が §3-4 の一番大きい手**である (§1-3) |
| 3 | 判定が反転しうる手 | **スロット数。**verify の 1 層は 8k 本 (k=4 で最大 32) を同時に要求し、32 スロットでは実プランだけで席が埋まりうる。Gemma は MTP 下で 32→48 スロットが **23.6 → 28.9 t/s** だった ([mtp/27 §2](../mtp/27-M7-RESULTS.md))。28 §2 の「弱い」はトークン単位の勘定で、**ブロック単位では #28 (48 候補) の判断材料が変わる**。union の実分布は既存トレースから机上で出る (§5-1) |
| 4 | 昇格する手 | **all-or-nothing の棄却外し (28 §3-2)。**union + 投機 N がスロット数を超える世界では `declined` はゼロでは済まない。partial プラン (置けるぶんだけ置く) が「計器を見てから」から「Phase 7 の設計要件」に昇格する見込み (§2) |
| 5 | MTP でしか出ない手 | **ドラフトの陰。**ドラフト側は 256 エキスパート全常駐 (453 MB、[03 §6-2](03-DESIGN.md)) で **I/O がゼロ** — その GPU 時間 (mtp 層 + lm_head) の間、ホストと SSD は完全に暇である。ここが**トークン境界をまたぐ写像の最初の隠し場所**になる: 次ブロック先頭層の先行 commit、状態書き出しの回収、棄却プランの再試行 (§3-2)。token id 条件の事前分布も offline gate つきで在庫に入れる (§3-3) |
| 6 | 28 §3-6 の訂正 | **「エージェント経路では MTP は効かない」は旧情報。**Gemma 側は 2026-08-22 に文法込みの投機 (位置ごとに文法込みで引き、採用のみ前進、巻き戻し無し) が緑になった ([CONFORMANCE](../serving/CONFORMANCE.md) GEN-14)。Qwen も部品は揃っている — マスクつき再畳み込み ([25](25-CLI-TOOLS.md)) が「文法込みで引く」そのもの (§4-1)。**ただし Phase 6 の手が不要になるわけではない**: 受理長はタスクで 2 倍動き (1.058〜2.346、[mtp/26 §2](../mtp/26-M6-RESULTS.md))、**a≈1 のタスクでは先読みだけが残る** (§4-2) |
| 7 | 一番大きい未知 | **受理長 a。Ornith では 1 つも測っていない。**カーネルを 1 本も書かずに測れる: float32 参照器 ([14](14-REFERENCE.md)) に `mtp.*` を足し、実生成のトレース上で draft top-1 と本体 top-1 の一致率を CPU で取る (§3-4)。**Phase 7 の着手前に a の桁が出る** — a が 1.0 に張り付くなら Phase 7 の期待値そのものが消える。**→ 測る前に向きが出た ([30](30-MTP-HEAD-GRAFT.md))**: 同梱ヘッドは乱数初期化なので出荷版のままなら a ≈ 1。**その差し替えは済んだ** ([30 §6](30-MTP-HEAD-GRAFT.md))。**§3-4 の測定も済んだ** ([33](33-MTP-ACCEPTANCE.md)): **P1 = 78.70% / a = 2.344 (平均)** で中止線は上回る。ただし**取り分は「a 倍」ではない** — 検証費用が和集合で伸びるので運用幅は k=2、机上 +8.5〜11.5% ([33 §3](33-MTP-ACCEPTANCE.md)) |

## 1. MTP が費用構造をどう変えるか

### 1-1. 写像の勘定 — 「トークンごと」が「ブロックごと」になる

[27 §9-1](27-PHASE6-THROUGHPUT.md) の分解をブロックに引き直す。
decode 50.0 ms/tok = GPU 28.5 + 写像 15.8 + ホスト 5.7。写像 15.8 の内訳は:

| 項 | いま (1 tok = 1 プラン/層) | verify (1 ブロック = 1 プラン/層) |
| --- | --- | --- |
| `commit()` 固定費 13.6 ms/tok (0.4 ms × 40 回) | トークンごと | **回数がブロックごと → 13.6/a ms/tok** (**導出**)。set の大きさへの依存は弱いので、union が 8 本 → 8k 本になっても 1 回の値段はほぼ動かない |
| miss の限界費用 (0.06 ms/本、[27 §9-3](27-PHASE6-THROUGHPUT.md)) | 85 本/tok が常駐状態を変える | **union の重複しだい。**隣接トークンが同じエキスパートを引くぶんだけ miss/採用トークンは減る (重複率は**未確認** — §5-1 でトレースから出る) |
| `requestResidency()` 等 0.8 ms/tok | トークンごと | 同じく /a (**導出**) |

つまり **28 §1 の「通貨」は変わらない** (待ちはホストのページ写像のまま、
バイトはページキャッシュに在る) が、**支払い回数の分母がトークンから
ブロックに変わる**。28 の言葉で言えば: 先読みは写像を「陰に移す」手、
MTP は写像を「割る」手で、**割った残りを移す**のだから両者は競合ではなく
直列に合成できる (§3-1)。

Gemma の M7 が同じことの対照実験になっている: あちらは通貨がデバイスの
バイトで、verify ブロック 1 回が 32 スロットで **469 MB 読んでいた**
([mtp/27 §5](../mtp/27-M7-RESULTS.md))。Ornith の verify は 469 MB の読みではなく
「miss × 108 ページの写像」を払う — **Gemma で verify を救ったのが 48 スロット
(469 → 216 MB) だったという事実は、通貨を写像に読み替えてもそのまま効く**
(miss が減る = 写像が減る)。これが §2 のスロット再判定の根拠である。

### 1-2. GPU の勘定 — k 行は k 倍にならない

verify は k 行を 40 層に通すが、GPU は k 倍にならない:

- MoE の重み読みは**行ではなく union に比例する** (同じエキスパートを引く行は
  重みを共有する)。[24 §3](24-PREFILL-MOE-PATH.md) のタイル版が prefill で
  示した現象の k 行版。
- lm_head (INT8、4.0 ms / 134 GB/s = **重み帯域律速**、[19](19-LM-HEAD-INT8.md))
  は k 行まとめて畳めばほぼ 1 回分 (**導出**)。
- dispatch の固定費 ([27 §4](27-PHASE6-THROUGHPUT.md) で「バッファ本数が減ると
  gpu 総和が減る」) はブロック化そのもので減る。

Gemma の実測がアンカーになる: ブロックは **decode の約 2 倍の GPU 仕事で
k=4 行を処理した** (ブロックの GPU busy 50 ms は [mtp/25 §1](../mtp/25-M5.6-RESULTS.md)、
decode の busy 25.7 ms は [mtp/24](../mtp/24-M5.5-RESULTS.md) の `GPUQueueOccupancy`)。
Ornith は 30/40 層が線形注意で、verify の k 行は再帰を逐次に進めるが
1 行あたりの仕事は小さい ([15](15-PHASE2-GDN.md) の decode 系列)。
**Ornith の係数は未確認** — だが構造は同じ方向を向いている。

### 1-3. ドラフトの費用と、机上の天井 (**導出**)

ドラフト 1 トークン = mtp 層 1 層 (≈ 本体 1 層並み ≈ 0.7 ms) + **lm_head 4.0 ms**。
**主費用は共有 lm_head の側**である。k=4 のドラフトで ≈ 19 ms/ブロック —
これは verify と違って行をまとめられない (逐次に引くから)。§3-5 が攻め手。

28 §1-3 の天井 (名指し 100% + 固定費 0 で 34 ms/tok ≈ 29 tok/s) を
MTP で書き直すと:

```
ms/tok ≈ [ verify_gpu(k) + draft(k) + 写像固定費 13.6〜14.4 + miss写像 + 状態書き出し 1.25 ] / a
```

a への依存がすべてで、仮に Gemma の係数 (verify_gpu ≈ 2×28.5、draft ≈ 19) を
借りると a=2 で ≈ **48 ms/tok**、a=2.5 で ≈ 38、a=3 で ≈ 32 (**導出** —
係数も a も Ornith では未確認なので、これは「a がいくつなら元が取れるか」の
逆算にだけ使う: **損益分岐は a ≈ 1.9 あたり**)。thinking の長い生成は
コード寄りの分布 (Gemma で a=2.346) に出る可能性があるが、それこそ §3-4 で
先に測る。

## 3. MTP でしか出ない手

### 3-1. ブロック版の層またぎ先読み (28 §3-1 との合流点)

**機序。**verify の層 L で k 行の `normed` があるから、L+1 の preview も
k 行で張れる (256 logit × k 行、GEMV は 1 dispatch)。host は k 行それぞれの
top-N を取って union を作り、L+1 の実プラン union との差 (= 名指せた miss) を
先読みする。**行あたりの的中 64.5% ([27 §9-4](27-PHASE6-THROUGHPUT.md)) が
union では上がる方向**に働く (どれか 1 行が名指せば足りるから — 効果量は
**未確認**、§5-1 のトレースで出る)。

**実装の形。**本ブランチの `encodeRouterLogitsBF16` を k 行版にする
(`maxRouterRows` のスクラッチは既にある — [28 §6](28-PREFETCH-IDEAS.md))。
Gemma M7 の 3 点セット (union を 1 プラン / 常駐タイルを先頭に / k 行 router
1 dispatch、[mtp/27](../mtp/27-M7-RESULTS.md)) は Qwen 側にそのまま輸入する。

### 3-2. ドラフトの陰 — トークン境界をまたぐ最初の隠し場所

28 §3-6 は「先読みはトークン境界を越えられない」で終わっていた。MTP は
越える機構そのものだが、**副産物としてもう 1 つの陰をくれる**: ドラフト中の
ホストと SSD は完全に暇である (エキスパート 256 本が全常駐 = I/O ゼロ、
[03 §6-2](03-DESIGN.md))。k=4 なら **≈19 ms/ブロックの純粋な GPU 時間**
(§1-3) が、いまの decode には存在しない「写像だけを流し込める窓」になる。

入れる候補、価値の順に:

1. **次ブロック先頭層の先行 commit。**直前 verify ブロックの層別 union は
   確定済みで、隣接ブロックのエキスパート重複が高ければ (LFU ヒット 72.4% は
   それを示唆する — ブロック粒度の値は**未確認**)、次ブロックの層 0〜数層ぶんの
   residency をドラフトの陰で先に払える。予測器が要らないのが強み。
2. **状態書き出しの回収。**行ごとの再帰状態書き出し (k=4 で 188 MiB/ブロック、
   [03 §6-3](03-DESIGN.md)) の転送・整理をここに置く。
3. **棄却プランの再試行。**§2 で `declined` が実在する世界になったら、
   ドラフトの陰は再試行の無料枠になる。

### 3-3. token id 条件の事前分布 (offline gate つき)

ドラフトはトークン **id** を verify より先に確定させる。すると
「P(層 ℓ のエキスパート集合 | token id)」という、いままで原理的に使えなかった
条件付けが使える — verify ブロック**先頭の数層** (preview がまだ届かない場所)
だけでも、§3-2-1 の無差別な再 commit より的中の高い先読みになりうる。

**gate が先。**既存トレース ([27 §6-1](27-PHASE6-THROUGHPUT.md) の TSV) には
(layer, token, top-8) が落ちているので、token id からエキスパート集合が
どれだけ予測できるか (相互情報量なり、単純に「同じ id の前回の top-8 の再現率」
なり) は**モデルを再実行せずに**出る。弱ければ表を持つ費用 (語彙 248,077 ×
40 層は素直には持てない — 頻出 id だけの LRU 表になる) を払わずに捨てる。

### 3-4. 受理長 a の CPU 先行測定 — Phase 7 の M0

§1-3 のとおり、**期待値のすべてが a に握られている**のに Ornith の a は
1 つも測っていない。カーネルゼロで測れる:

- float32 参照器 ([14](14-REFERENCE.md)) に `mtp.*` の forward を足す
  (1 層 + fc + norm 2 本 — 構造は [03 §6-4](03-DESIGN.md))。
- 実タスク 4 本 ([27 §2](27-PHASE6-THROUGHPUT.md)) の生成列に沿って、各位置で
  draft top-1 と本体 top-1 の一致率 (= greedy の受理率) を取る。位置 t の
  hidden は本体 forward の副産物なので、追加費用はドラフト側だけ。
- Gemma で受理長がタスクで 2 倍動いた (1.058 / 1.885 / 2.346、
  [mtp/26 §2](../mtp/26-M6-RESULTS.md)) 以上、**タスク別に**出す。
  thinking の中と外も分ける (分布がまったく違うはず)。

これが Gemma の M0 ([mtp/10](../mtp/10-M0-RESULTS.md)) に当たる。
**a < 1.5 なら Phase 7 の形を考え直す** (§1-3 の損益分岐)。

**→ 測った ([33](33-MTP-ACCEPTANCE.md))。**a = 2.180〜2.534 (深さ 3、平均 2.344)、
P1 = 69.31〜87.83% (平均 78.70%)。中止線は上回ったが、**§1-3 の天井の式は
和集合の項が抜けていて過大**だった ([33 §3-2](33-MTP-ACCEPTANCE.md) が置き換える)。
thinking の中と外の分割は**未実施** (4 本とも `--thinking off`)。

### 3-5. ドラフト lm_head の固定費

ドラフトの主費用は共有 lm_head 4.0 ms/tok (§1-3)。verify と違って行を
まとめられないので、k=4 で 16 ms がそのまま残る。攻め手はあるが
(語彙を頻出側に絞った draft 専用ヘッド、greedy チェーンの途中打ち切り)、
**どれも品質と引き換えなので §3-4 の数字より先には動かない**。在庫として
記録するだけ。

## 4. 訂正と、変わらないもの

### 4-1. 訂正: エージェント経路と MTP (28 §3-6)

28 §3-6 の「ツール宣言のあるエージェント経路では MTP は効かない (文法 →
投機オフ)」は **2026-08-21 までの Gemma の状態**で、翌日に直っている
([CONFORMANCE](../serving/CONFORMANCE.md) GEN-14、2026-08-22 緑): 投機ループが
位置ごとに**文法込みで**引き (GEN-7 の棄却サンプリング)、採用したトークンだけ
文法状態を進めるので**巻き戻しが要らない**。参照実装 (llama.cpp) も文法と投機を
併用している。

Qwen 側は現状「投機は起動時に断る」([26 §4](26-PHASE8-SERVER.md)) だが、
**同じ形を組む部品は揃っている**: マスクつき再畳み込み
(`qwen_lm_head_greedy_int8_rows_chunk_masked`、[25](25-CLI-TOOLS.md)) が
「文法込みで引く」に相当し、拒まれたトークン 1 個につきヘッド 1 回という
費用構造も同じ。Phase 7 の受入条件に「tools 宣言つきでも投機が通る」を
足すかは**ユーザー判断** (Gemma はこれを後追いで直す羽目になった —
[CONFORMANCE](../serving/CONFORMANCE.md) の教訓はここで先取りできる)。

### 4-2. 変わらないもの

- **受理長はタスクで 2 倍動く** ([mtp/26 §2](../mtp/26-M6-RESULTS.md))。
  a≈1 の世界 (Gemma では日本語散文) では MTP は 1.0 倍で、**そこでは 28 の
  先読み在庫が唯一の機構のまま**である。Phase 6 の手は Phase 7 が入っても
  陳腐化しない — 両者は客層 (タスク) を分け合う。
- **CLI の非投機経路と prefill** も従来のまま 28 の世界。
- **死んだ手は死んだまま** (§2 の下 3 行)。
- **既定は変えない。**verify の設計判断 (k、スロット、partial プラン) は

## 5. 机上で先に引けるもの (実験手順)

順序は 28 §5 と同じ思想: **計器 → 机上 → CPU → 実装 → 実機**。
Phase 7 のコードを書く前に、1〜3 は全部出る。

1. **トレース 1 本からブロックの世界を再現する** (モデル再実行不要)。
   既存の (layer, token, top-8) トレースを k 個ずつ束ね、`expert_sim.py` の
   流儀で: 層別 union サイズの分布 (k=2..5)、隣接ブロックの重複率 (§3-2-1)、
   32/48 スロットでの miss/ブロック と declined 率の予測 (§2)、
   ブロック版 preview の的中 (§3-1 — preview top-16 のトレースは
   [28 §5-2](28-PREFETCH-IDEAS.md) が同じものを要求している。**1 回のトレース
   取得で両方に効く**)。
2. **28 §5-1 の計器の A/B** (本ブランチで実装済み・未計測)。wait と
   `declined` は Phase 6 の判断 (#29) と Phase 7 の設計の両方の入力になる。
3. **受理長 a の CPU 測定** (§3-4)。タスク別・thinking 内外別。
   **a < 1.5 なら Phase 7 の形を考え直す。**
4. **Phase 7 の設計判断**を 1〜3 の数字で立てる: k、スロット (#28 と合流)、
   partial プラン (§2)、preview のブロック化 (§3-1)、ドラフトの陰に何を
   入れるか (§3-2)。
5. **検査のゲート**は [04](04-PHASES.md) Phase 7 の出口 (非投機と greedy で
   バイト一致 — ただし prefill がタイル版になった今、この前提を先に 1 回
   確かめる) + [28 §5-4](28-PREFETCH-IDEAS.md) と同じ全一致・`swift test`。
   Gemma の経路に触れないこと。
