## 1. 分岐は 1 か所 — `prefillRoutedPath`

[21 §3-2](21-PHASE4-PREFILL.md) は per-pair GEMV
(`prefill_grouped_routed_moe_batched_*`) を選んだ。整列の前提もバッチの計画も
要らないので、**router と答えの間で動く部品が一番少ない**形から始めたためである。
タイル版 (`prefill_moe_gemm_int4`) はその対極で、64×64 のタイルを 1 エキスパートの
行ブロックに当てる。

`QwenForwardRunner.prefillRoutedPath` はそのどちらを使うかだけを持つ。
**タイルの取得も、sorted pair も、`routePartials` の書き方も共通**で、
どちらの経路も**ペア 1 本につき 1 行をちょうど 1 回**書く。だから下流の
token-major な総和も、上流のエキスパート取得も、どちらが走ったかを知らない。

```swift
switch prefillRoutedPath {
case .perPair: … encodeStreamedBatched(…)
case .tiled:   … encodeStreamedTiled(…, groups: groups, maxRowsPerBatch: s.gemmBatchRows)
}
```

`.tiled` を頼まれて出せないときは**黙って per-pair に落ちない**。落ちる実装だと
「タイル版の壁時計」として記録した数字が per-pair のものになり得る — 測定のための
分岐が測定を嘘にする。`TF_PREFILL_MOE=scalar` (Gemma 側の既存のノブ) は
タイル版の PSO を作らないので、その場合はここで例外が上がる。

### 1-1. 足したのは 3 つだけ

| どこ | 何を |
| --- | --- |
| `QwenForwardRunner` | `prefillRoutedPath` (既定 `.tiled` — §3-2) と `supportsTiledRoutedPrefill`、`gpuSeconds` / `gpuCommandBuffers` |
| `QwenPrefillContext` | `gemmBatchRows` と、それに合わせた `gateUpAct` の幅 |
| `QwenPrefill` | 上の `switch` |

**`PrefillGroupedRoutedMoE` は無改造。**`encodeStreamedTiled` も
`usesExpertGEMMPath` も `PrefillRoutedGEMMPlanner` も Gemma のために書かれた
ものがそのまま当たる。当たる理由は形の側にある: `D=2048` と `F=512` は
どちらも**タイルの K 段 (32) と affine group (64) の両方の倍数**で、
routed expert は 3 本とも 4-bit だからである ([01 §3-2](01-MODEL.md) の
1,769,472 B = 3 × 2048 × 512 × 0.5625 がそれを言っている)。

`gateUpAct` は**両方の経路のぶんを常に確保する。**per-pair は
`3 × 32 × F`、タイル版は `3 × gemmBatchRows × F` を要り、`gemmBatchRows` は
チャンクが作り得るペア数 (`width × topK`) で 2048 まで頭打ちにした。
スクラッチは幅でキャッシュされるのに `prefillRoutedPath` は実行の合間に
変えられるので、**確保した時点の経路に合わせて張ると、A/B が切り替わった
最初の 1 回が古いスクラッチを踏む。**チャンク 2048 で 6.3 MB。

## 2. 検査 — 同じ 55 トークン

`--qwen-prefill` に腕が増えた。上の 2 本は**既定の経路** (いまは tiled) で走り、
その下が**もう一方の経路を全チャンク幅で**通したものである:

```
PASS  55 tokens, every one equal to the float32 reference     ← チャンク 512
PASS  chunk 8 (3 chunks) — the same 55 tokens
PASS  routed experts on the per-pair path, chunk 512 (1 chunks) — the same 55 tokens
PASS  routed experts on the per-pair path, chunk 8 (3 chunks) — the same 55 tokens
```

2 つの経路は同じ sorted pair を読んで同じ `routePartials` に書くので、
**ここが食い違ったらどちらかがバグ**であって、プロンプトの性質ではない。

**幅を全部通すのが要点である。**最初は `prefillChunks.first` だけを通していて、
**幅 8 をタイル版が一度も通っていなかった** — そこはエキスパート 1 本に
64 行ブロックの 1〜2 行しか入らない、バッチ計画が一番痩せる形である。
広げても緑だった。

`TF_PREFILL_MOE=scalar` を立てるとタイル版のパイプラインが作られないので、
**既定が `.perPair` に戻り、腕も足されない** (§3-2)。

### 2-1. 取得エキスパート数がわずかに違う

同じ合成プロンプトを流しても、取るエキスパートの本数がちょうどは揃わない:

| トークン / チャンク | per-pair | tiled |
| --- | ---: | ---: |
| 2048 / 2048 | 8,560 | 8,559 |
| 2048 / 1024 | 15,983 | 15,990 |
| 2048 / 512 | 29,054 | 29,067 |
| 512 / 512 | 7,359 | 7,363 |

**router が非決定的なのではない** (実測 = ソース: タイル版は逆量子化した重みを
FP16 で staging する — 重み 1 本につき丸め 1 回、`PrefillInt4QMM` と同じ規約 —
のに対し per-pair は FP32 のまま積む)。その差が MoE の出力の下位ビットに出て
**次の層の router の top-8 の境目が入れ替わる**、というのが**導出**の説明である。

差はどれも **0.05% 未満**で、**トークンは 55 本とも一致している** (§2) ので
argmax を動かす大きさではない。ただし**取得本数と取得時間は 2 つの経路の間で
厳密には同じ仕事ではない** — §3 で経路の比較を **GPU 列**で書いているのは
そのためである。

## 3. #20 — どちらが速いか

`--qwen-prefill-bench`、合成プロンプト (語彙に散らした ID)、スロット 32、n=3、
**クールダウン 4 秒** ([04](04-PHASES.md) Phase 6 の作法。空けないと数字が
別物になる — §4)。**運用値ではない** — この経路は直列で、タイルごとに GPU を
止める ([21 §5](21-PHASE4-PREFILL.md) と同じ断り)。**3 回目の行**を並べる
(1 回目はシェーダのコンパイルを含む)。

| トークン | チャンク | 経路 | 総 (ms) | GPU | 取得 | ホスト | 1 トークン (ms) |
| ---: | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 512 | 512 | per-pair | 4,360 | 1,970 | 2,022 | 368 | 8.52 |
| 512 | 512 | **tiled** | **3,857** | **1,526** | 1,999 | 332 | **7.53** |
| 2048 | 512 | per-pair | 19,318 | 8,422 | 8,958 | 1,938 | 9.43 |
| 2048 | 512 | **tiled** | **16,383** | **6,594** | 8,365 | 1,424 | **8.00** |
| 2048 | 1024 | per-pair | 13,892 | 8,281 | 4,617 | 994 | 6.78 |
| 2048 | 1024 | **tiled** | **11,401** | **5,498** | 4,830 | 1,073 | **5.57** |
| 2048 | 2048 | per-pair | 11,179 | 8,324 | 2,327 | 527 | 5.46 |
| 2048 | 2048 | **tiled** | **8,042** | **5,036** | 2,467 | 539 | **3.93** |

**タイル版が 4 通りとも速い。**経路が変えるのは GPU 時間だけなので、そこで見ると
**−22% / −22% / −34% / −40%**。既定のチャンク幅 2048 で 1 トークン
**5.46 → 3.93 ms** になる。

### 3-1. [05 §1-2](05-RISKS.md) への答え

あの節の心配は「Ornith はチャンク 2048 でもエキスパート 1 本あたり平均 64 行 =
**64 行ブロックがちょうど 1 個**にしかならないので、半端ブロックが Gemma より
増える」だった。**形の話としては正しいまま**である。しかし
**per-pair GEMV に留まる理由にはならなかった。**

その心配が数字として見えるのは、per-pair ではなく**タイル版の側の GPU 列**である:

| チャンク | per-pair の GPU | tiled の GPU | エキスパート 1 本あたり平均行数 ([05 §1-2](05-RISKS.md)) |
| ---: | ---: | ---: | ---: |
| 512 | 8,422 ms | 6,594 ms | 16 |
| 1024 | 8,281 ms | 5,498 ms | 32 |
| 2048 | 8,324 ms | 5,036 ms | 64 |

**per-pair は 3 通りとも同じ (8.3 秒)** — ペアごとの GEMV なので、同じ 2048
トークンをどう割ろうと仕事量が変わらない。**タイル版だけがチャンク幅で動く**
(6.6 → 5.0 秒) のは、まさに埋まらないブロックの費用である。占有率の話は
**実在した**が、それでも一番埋まらないチャンク 512 でタイル版が 22% 速い。

### 3-2. 既定をタイル版にした (2026-08-22 ユーザー確定)

[04](04-PHASES.md) の運用ルールどおり、この表はまず**候補として**出した。
**ユーザーの判断で既定を `.tiled` に切り替えた** — 効くのが既定のチャンク幅
(2048 で GPU −40%) で、隠れ得るのは既定でない幅の方だからである (§3-3)。

| ノブ | 効き |
| --- | --- |
| 既定 | `.tiled` |
| `TF_QWEN_PREFILL_MOE=per-pair` (または `scalar`) | この family だけ GEMV に戻す |
| `TF_PREFILL_MOE=scalar` (Gemma 側の既存のノブ) | **タイル版の PSO を作らない**ので、既定も自動的に `.perPair` になる |
| `--qwen-prefill-bench-moe per-pair\|tiled` | 測定の 1 回だけ選ぶ |

**`TF_PREFILL_MOE=scalar` を既定の側が知っている**のが要点である。あれは
好みの表明ではなく `PrefillGroupedRoutedMoE` が**タイル版のパイプラインを
そもそも作らない**ノブなので、それを見ずに `.tiled` を既定にすると
**「既定が例外を投げる」**ことになる。`--qwen-prefill` も
`supportsTiledRoutedPrefill` を先に訊いてから腕を足す — **作れない経路の腕を
落とすのと、腕を足さないのは別のこと**である。

明示的に `.tiled` を頼まれて出せないときは、いまも例外を投げる (§1)。

## 4. #21 — 逆転は GPU 時間だった

[21 §5](21-PHASE4-PREFILL.md) が「説明が付いていない」と置いた行:
2048 トークン / チャンク 512 だけ、**1 回目より 2・3 回目が遅い。**
今回も同じ形で再現した (26,324 → 34,808 → 35,761 ms、per-pair)。

### 4-1. 3 つに割った

総時間だけを見ていると、GPU が遅いのか I/O が遅いのかが分からない。
`--qwen-prefill-bench` に列を足した:

- **GPU** — `QwenForwardRunner.wait` が、待ち終えたコマンドバッファの
  `gpuEndTime - gpuStartTime` を足していく。この経路は**厳密に直列**
  (commit → wait → 次を積む) なので区間は重ならず、**和が持続時間になる**
- **取得** — `ExpertTelemetry` の `fetchNanos` (pread と view 作りを含む)
- **ホスト** — 残り (総時間 − GPU − 取得)

`--qwen-prefill-bench-cooldown` も足した。[04](04-PHASES.md) Phase 6 の作法の
クールダウンを**プロセスの中で**取る (既定 4 秒)。

### 4-2. 逆転は GPU 時間で、間隔を空けると消える

2048 トークン / チャンク 512、per-pair、n=3:

| クールダウン | | 1 回目 | 2 回目 | 3 回目 |
| ---: | --- | ---: | ---: | ---: |
| **0 秒** | 総 (ms) | 24,220 | 30,089 | **33,119** |
| | GPU | 8,610 | 19,877 | **22,671** |
| | 取得 | 6,686 | 8,691 | 8,856 |
| | ホスト | 8,924 | 1,521 | 1,592 |
| **4 秒** | 総 (ms) | 24,956 | 19,171 | **19,318** |
| | GPU | 8,678 | 8,427 | **8,422** |
| | 取得 | 7,095 | 8,858 | 8,958 |
| | ホスト | 9,183 | 1,887 | 1,938 |
| **20 秒** | 総 (ms) | 24,999 | 19,008 | **18,960** |
| | GPU | 8,693 | 8,433 | **8,436** |
| | 取得 | 6,995 | 8,709 | 8,671 |
| | ホスト | 9,311 | 1,866 | 1,853 |

**増えているのは GPU 時間だけで、8.6 秒が 22.7 秒になる (2.6 倍)。**
取得もホストも 3 通りでほぼ同じ値を出している。そして**4 秒空けるだけで
増加は消える** — 20 秒にしても 4 秒と変わらない。

機械の中で何が起きているかは**導出**である (この文書は GPU のクロックも
温度も読んでいない): 連続で回すと 1 回のイテレーションが 24 秒の GPU 負荷 +
49 GB の読み出しになり、**持続負荷でクロックが落ちる**という形が数字に合う。
チャンク 2048 の行 (§4-3) が同じ条件で落ちないことも、これと向きが合う —
そちらは同じ 2048 トークンを**読み出し 14 GB** で通す。

**逆転の正体は、この増加が 1 回目の一度きりの費用より大きいことである。**
1 回目のホスト時間 9 秒はシェーダのコンパイルなどの一度きりの費用で、
2 回目以降は 1.5〜1.9 秒に落ちる。**間隔が空いていればその 7 秒ぶん
1 回目の方が遅く**なり ([21 §5](21-PHASE4-PREFILL.md) の他の 3 行がそれ)、
間隔が無いと GPU の 14 秒増がそれを上回って符号が変わる。

### 4-3. [21 §5](21-PHASE4-PREFILL.md) の表を訂正する

あの表は**クールダウン無しで取ったもの**だった。作法どおり 4 秒空けると、
2048 トークン / チャンク 512 は:

| | [21 §5](21-PHASE4-PREFILL.md) (連続) | クールダウン 4 秒 |
| --- | ---: | ---: |
| 3 回目 | 36,456 ms | **19,318 ms** |
| 1 トークン | 17.80 ms | **9.43 ms** |

**チャンク 512 はチャンク 2048 の 3.2 倍遅いのではなく、1.7 倍遅い。**
チャンク 2048 の側は連続でも 4 秒でも同じ (11,191 / 11,179 ms、5.46 ms) なので、
**あの表で訂正が要るのはこの 1 行だけである。**

### 4-4. 取得が 1 回目だけ安いのは別の話

3 通りとも、**取得は 1 回目が 2・3 回目より 2 秒ほど速い** (6.7 → 8.9 秒)。
チャンク 2048 ではもっと極端で **0.3 → 2.3 秒**になる。ヒット率は
どの回も 0.0% で、取るエキスパートの数も同じである。

**エキスパートキャッシュの話ではなく、OS のページキャッシュの話である**
(導出): 1 回目が読む頃には直前のプロセスが読んだページがまだ残っていて、
1 回のイテレーションが 14〜49 GB を流す間にそれが自分で追い出される。
18 GB の機械で 20.49 GB のファイルを繰り返し流すのだから、**2 回目以降が
定常**であって 1 回目が特別なのだ、と読むのが順当である。

**これは逆転の説明にはならない** (2 秒しか動かない)。§4-2 の 14 秒が答えである。
