# 43. 集めるモードの 1 ラウンドを Mac のアプリの経路で測る (42 の S0・S1)

書いた日: 2026-09-19。表記は 01 と同じ (実測 / 導出 / 未確認)。計画は 42。K0 は環境を作ったところまで (§6)。

> **決定 (2026-09-19、ユーザー)**: KVA はやらない。理由は §7。K0 の残りと K1〜K4 は行わない。

この文書で使う言葉 (42 と同じ)。

- **集めるモード**: 40 の進め方。1 ターンは「調査」(R1) と「回答」(R2) の 2 ラウンド。
- **KVA**: LLKVApprox (28〜30)。新規トークンのうち末尾を除いた行について、後半 24 層を通さず、その層の KV と GDN の入力を近似で埋める。ここでは埋め方は `hcmix` だけ (学習したヘッドは無い)。
- **末尾**: KVA でも 48 層すべてを通す、プロンプトの最後のトークン数 (`Q38_LLKV_SUFFIX`)。
- **前半・後半**: 層 0〜23 と層 24〜47。

## 0. 結論

**R2 の prefill は、近似なしの 37.3 s が、末尾 256 で 28.9 s (−8.4 s)、末尾 1,024 で 34.3 s (−3.0 s) になった** (実測、Mac、5 問 × 2 回の平均)。

| | R2 の prefill | R1 の prefill | 1 ターンの壁時計 |
| --- | ---: | ---: | ---: |
| 近似なし (S0) | 37.3 s (34.7〜38.5) | 13.2 s (13.0〜13.5) | 83.9 s (79〜88) |
| KVA 末尾 256 (S1) | 28.9 s (27.4〜29.7) | 12.3 s (12.1〜12.6) | 81.1 s (67〜122) |
| KVA 末尾 1,024 (S1) | 34.3 s (32.8〜35.3) | 13.2 s (13.0〜13.5) | 83.7 s (75〜107) |

- 1 ターン 83.9 s の中で、KVA が縮めたのは R2 の prefill の 8.4 s (末尾 256) か 3.0 s (末尾 1,024) と、末尾 256 のときの R1 の prefill の 0.9 s。
- 壁時計の列は回答の長さで動く。`hcmix` を立てると回答が変わり、生成トークン数の平均は 136 → 184 (末尾 256)・159 (末尾 1,024) になった。壁時計の差は KVA の速さを表していない。回答の中身は読んでいない (42 §3-1)。
- 学習したヘッドの GEMM (約 385 MB、F16) の秒数は入っていない。K3 で足したときに測り直す (42 §3-3)。
- KVA はやらないことにした (§7)。

## 1. 測り方

- 入口: `TsugumiToolLoopCheck --gather DIR` を `--endpoint` なしで流す。モデルはアプリと同じ `RealInferenceClient` の Qwen3.8 セッション (`Qwen38ServerSession`) で、この Mac のプロセスの中で動く。プロンプトキャッシュ、チェックポイント (18)、MTP、チャンク 2,048、32K、KV Q8_0 は、アプリの既定のまま。
- 文法: 集めるモードの文法は、`ValidatedChatRequest.grammar` (プロセスの中でだけ設定できる。HTTP の本文からは設定できない) で渡す。
- R1 の固定: `--gather-force scratch/qwen38/plan42/force-G3a.json` で、R1 は G3a の 1 回目 (PC の Q4_K_XL) が書いた文字列そのものを書く。その 1 本の文字列だけを許す文法で、同じサンプラと decode のループ (MTP 込み) を通す。検索語が同じなので、アプリが渡す段落 (`question,articles=12`) も 3 構成で同じになる。
- R2 はアプリと同じ文法 (「回答」か「調査」) で、公式サンプラで書かせた。10 本すべてが「回答」を書いた。
- 5 問 (N1〜N5、1 ターン目) × 2 回、構成ごとに別プロセス。問の間は 20 秒。見張りは `guarded.sh`、`caffeinate -i`。走行は `scratch/qwen38/plan42/run.sh`、集計は `analyze.py`。
- 計器 (この作業で足した):
  - `Q38_ROUND_LOG=FILE`: prefill のチャンクごとに、前半・後半に分けた `StepProfile`、pread で求めたバイト数、MTP の KV を作る秒、チェックポイントを取る秒、プロセスの `ri_diskio_bytesread` の累計。チェックポイントの復元と、decode 中の取得も 1 行ずつ。
  - `rounds.jsonl` にラウンドごとの `disk_read_bytes` (プロセスの `ri_diskio_bytesread`)、`system_disk_read_bytes` (全 `IOBlockStorageDriver` の `Bytes (Read)`。`iostat` が読むカウンタ)、`swapouts`。
  - pipeline では、層 23 の routed の待ちは層 24 の pre-router の待ちに入る。前半・後半の境目は 1 層ずれる。
- 見張り: 止まった走行は無い。Swapouts は S0 で 5,416 ページ、末尾 256 で 20、末尾 1,024 で 3,380。ほとんどが R1 の最中。wired の最大は 14.6 GB。

## 2. 近似なしの内訳 (S0)

- GPU の時間: 前半は pre-router 3.13 s・routed 4.94 s、後半は 3.08 s・5.17 s。pipeline なので routed の GPU は pre-router の wall の中に入る。
- pread で求めたバイト数: 前半 26.5 GB・後半 24.6 GB。prefill 全体の実読み (`ri_diskio`) は 70.7 GB (69.5〜71.4)。42 §1 の読みの下限 (6.5 GB/s) で割ると 10.9 s (導出)。
- **KVA で消える部分の上限**: 末尾 256 を含まないチャンクの後半 (pre-router + route + routed) は 8.71 s (8.52〜8.97)。S1 の末尾 256 は 8.4 s 縮めた (§3)。
- R2 はどれも、R1 の直後の状態 (位置 = R1 のプロンプト + 生成) から続かず、R1 のプロンプトの最後のチェックポイント (465〜472) から復元して流し直した。R1 の出力は改行で終わり、テンプレートがその改行を落とすため、R1 の生成の最後で一致が切れる (ログの `diverged at=534 live=535`)。その分、R1 の出力 (54〜84 トークン) が R2 の新規に入っている。PC の記録 (G3a) でも R2 の cached は R1 のプロンプトより 4 少ない。

### 2-2. R1 (新規 466〜473 トークン、キャッシュなし)

- prefill 13.2 s (13.0〜13.5)。チャンクは 457〜464 (10.3〜10.7 s)、8 (2.5〜2.7 s)、1 (0.2 s)。
- 前半は pre-router 3.62 s・route 1.93 s、後半は 3.58 s・1.96 s。PLE 0.94 s、MTP の KV 0.76 s、head 0.28 s。
- 実読み 33.4 GB (32.9〜34.0)。pread で求めたバイト数は 20.5 GB。

### 2-3. 1 ラウンドの固定分 (33 §1-1、42 §1) について分かったこと

- R1・R2 とも、チェックポイントの位置で切れた 8 トークンのチャンクが 2.5〜2.7 s かかっている (10 本 × 2 ラウンド × 3 構成、すべて)。そのうち pre-router が 2.1〜2.4 s (60 本)。8 トークンは pread の閾値 (`Q38_PREAD_MIN_T` 32) より小さいので、expert は advise と page fault で読まれる。
- 1 トークンのチャンク (P − 1) は 0.2 s。
- チャンクが切れなかった場合の秒数は測っていない (未確認)。この差が P1 の取り分の候補になる。42 §4 のとおり、P1 にはここでは手を付けていない。

### 2-4. 読み込み量の計器

- ラウンド全体で、プロセスの `ri_diskio_bytesread` と全ディスクの `Bytes (Read)` はほぼ一致した (R2 で 99.5 GB と 100.2 GB、R1 で 46.7 GB と 47.0 GB。60 ラウンド全部で差は 2% 以内)。**42 §1-1 の未確認 (`prefillDiskReadBytes` が実際のディスク I/O か) は、実際のディスク I/O だと言える。**
- prefill の実読みは、pread で求めたバイト数より大きい (R2 で 70.7 GB と 51.1 GB)。差は、小さなチャンクの page fault と、PLE・密な重みの読み直し (導出。内訳は取っていない)。

## 3. KVA を立てたとき (S1)

`Q38_LLKV_SPLIT=24 Q38_LLKV_FILL=hcmix`、末尾 256 と 1,024。

| R2 の項目 (平均) | 近似なし | 末尾 256 | 末尾 1,024 |

| 残りのチャンク | 10.5〜14.2 s | 9.9〜12.1 s | 10.7〜14.1 s |

| 埋め (`hcmix`) | 0 | 2.16 s | 1.34 s |

- 末尾 256 では、後半の 10.8 s が消え、埋めに 2.2 s かかり、差し引き 8.4 s 縮んだ。42 §1-3 の見込みのとおり、末尾を含むチャンクの後半の読みは残る (後半の pread 9.1 GB)。
- 末尾 1,024 では、2,048 のチャンクの一部と、残りのチャンクの全部が 48 層を通る。縮んだのは 3.0 s。
- R1 は新規 466〜473 トークン。末尾 256 では、そのうち約 210 トークン (システムプロンプト側) が近似され、13.2 → 12.3 s。末尾 1,024 では近似がかからない。

### 3-2. 配管の確認 (42 §5 の 4 つ目)

- `Q38_LLKV_SPLIT` をアプリの経路で立てても、チェックポイントの取得・復元、MTP、プロンプトキャッシュの続きは止まらずに回った (30 ラウンド × 2 構成、エラーなし)。値が正しく続いているかは見ていない (未確認)。
- **直したこと**: 直す前の `Qwen38Completion` は、プロンプトの最後のチャンクにだけ末尾を渡していた。チェックポイント (U − m) でプロンプトが切れると、最後のチャンクは 8 + 1 トークンしかない。そのため、末尾 256 のつもりでも、48 層を通るのは最後の 9 トークンだけになっていた。今は、どのチャンクでも、プロンプトの終わりから `llkvSuffix` 以内の行を正確に流す。最後のチャンクが末尾より長い場合 (29 の測定) は、前と同じ。

## 7. KVA をやらない理由 (2026-09-19)

ユーザーの判断。根拠は、目的の指標 (1 ターンの待ち時間) で見た §0〜§4 の数字。

- **KVA が触れるのは、1 ターン 83.9 s のうち約 9 s だけ。** 近似なしの内訳 (§4、§2-1) で、KVA で減らない部分を先に数える。
  - R1 の 22.2 s (prefill 13.2 s + decode 9.0 s)。末尾 256 でも prefill が 0.9 s 減るだけ。
  - 段落の集め (埋め込み) の 6.2 s。
  - R2 の decode (回答) の 18.1 s。
  - R2 の prefill の前半 24 層 (15.5 s) と、PLE・MTP の KV・head など (約 6 s)。
  - R2 の prefill の後半 24 層 (15.3 s) のうち、末尾を含むチャンクの分。そのチャンクは末尾の行のために後半の層を通るので、後半の expert の読みも残る (末尾 256 でも 9.1 GB)。
  - 残る 8.7 s (末尾 256 を含まないチャンクの後半) が、近似が完全でも消せる上限。
- **上限からさらに引かれる。** `hcmix` の埋めに 2.2 s かかり、実際に縮んだのは 8.4 s (末尾 256) と 3.0 s (末尾 1,024)。学習したヘッドを足すと、その GEMM の秒数がさらに乗る (未測定)。
- **壁時計では打ち消された。** `hcmix` で回答が変わり、R2 の decode が 18.1 → 24.7 s に伸びて、1 ターンは 83.9 → 81.1 s。
- **学習で近似を良くしても、上限は 1 ターン約 10% のまま。** 42 §0 で「R2 の新しいトークン (約 29 s) に当たるのは K だけ」と書いたが、当たるのは後半の層の、末尾を含まないチャンクの分だけだった。1 ターンの約 3/4 (R1、段落の集め、R2 の前半の層、decode) には届かない。

残すもの: コード (`Q38_LLKV_*`、既定は無効) と、この文書で足した計器 (`--gather` のローカル経路、`--gather-force`、`Q38_ROUND_LOG`、`RoundMeter`)。計器は KVA 以外の測定にも使える。PC の venv (`C:\LLM\llkv\.venv`) はそのまま置いてある。
