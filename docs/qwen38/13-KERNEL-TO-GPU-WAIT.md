# 13. routed の kernel→GPU 開始の待ちは何か: ほぼページインで、ビューの常駐費用ではない

実測: 2026-09-14、M3 Pro 18 GB、macOS 15。GGUF・プロンプトは [12](12-PIPELINE-PREVIEW.md) と同じ。
表記は 01 と同じ (実測 / 導出 / 未確認)。

## 0. 結論

1. **12K の prev10 は途中で止めた** (§4)。パス 1 の投機で wired 15.0 GB・file-backed 1.1 GB まで行き、ユーザーの判断で打ち切った
   (「実用にならない。RAM を使えば速いというだけ」)。上位 N の掃引と、予測した expert を前もって常駐させる腕 (12 §4 の 2・3) も同じ軸なので回していない。
2. **使用済みの no-copy の expert ビューは、ページがキャッシュにあれば kernel→GPU 開始が床と同じ 0.05 ms** (§1、3 起動)。
   本数 (3〜300) にもバイト (15〜154 MB) にも比例しない。
3. 費用が出るのは次の 2 つ (§1):
   - **ビューの初回**: 0.35〜0.44 ms/15 MB、2.8〜3.2 ms/154 MB。本数ではなくバイトに比例する (3 本 15 MB = 30 本 15 MB)。
   - **キャッシュに無いページ**: 7.0〜7.2 ms/15.4 MB。kernel→GPU 開始の中で同期して読まれる。
4. **使ったビューは、MTLBuffer が生きている間 wired のまま** (§2)。1,393 MB 分を持つと wired が +1,456〜1,458 MB、解放すると戻る (3 起動中 2 起動。1 起動目は増えなかった)。
5. **ランナーの decode では、待ちは route 時点の未常駐バイトでほぼ決まる** (§3)。code・late・素の 3 本で、
   kernel→GPU (ms) = 6.5〜7.7 + 0.080〜0.084 × 未常駐 MB (R² 0.84〜0.91、1 本あたり 198 ステップ)。新規ビューの MB はほぼ効かない。
6. **定数のうちキュー待ちは 0** (§5)。ビューを毎ステップ作り直すと、定数は 18.1〜21.3 ms (保持すると 6.7〜7.4 ms) になり、プローブの初回単価で計算した値と合う。
   導出では、保持していても 1 ステップ約 200 MB のビューを対応付け直している。これを減らすのは RAM 軸なので、ここで止めた。
7. **ドライバの中のページインは、コマンドキューをまたいでデバイス全体で直列** (§6)。別のキューのキャッシュ済みのバッファも待たされ、cold 2 本は並べても 14 ms。

## 5. 定数 (§3 の 6.5〜7.7 ms) の分解

どちらも code・late・素・`Q38_COUNT_MISS=1`、seed 1〜3。トークン列は §3 の走行と一致。

- **shared の後ろでのキュー待ちは 0**: routed の kernel 開始の時点で、直前に commit した shared のバッファは GPU で終わっている
  (`behind shared` が 3 本とも全ステップの中央値 0.0 ms、shared の GPU は 1 ステップ 2.8 ms)。
- **ビューを毎回作り直す腕** (`Q38_FRESH_VIEWS=1`、検査用): 1 ステップの新規ビューが 739 MB (保持する腕は中央値 31〜33 MB)。

| 腕 | seed | steady tok/s | kernel→GPU 中央値 ms | 未常駐 中央値 MB | 定数 + 未常駐 (ms) | R² | ビュー作成の host 中央値 ms |
| --- | ---: | ---: | ---: | ---: | --- | ---: | ---: |
| 保持 | 1 | 7.37 | 20.1 | 157 | 6.7 + 0.092 m | 0.66 | 0.7 |
| 保持 | 2 | 7.30 | 21.5 | 182 | 7.3 + 0.080 m | 0.89 | 0.8 |
| 保持 | 3 | 7.21 | 22.0 | 185 | 7.4 + 0.077 m | 0.94 | 0.7 |
| 作り直し | 1 | 6.83 | 28.6 | 200 | 19.4 + 0.049 m | 0.91 | 5.0 |
| 作り直し | 2 | 6.73 | 29.6 | 213 | 18.1 + 0.058 m | 0.75 | 4.9 |
| 作り直し | 3 | 6.58 | 32.8 | 216 | 21.3 + 0.055 m | 0.88 | 5.0 |

導出 (§1 の単価を当てる): 作り直しは、床 48 × 0.05 + 739 MB × 0.023 ≈ 19.4 ms で、定数 18.1〜21.3 ms と合う。
同じ式で保持する腕の定数 7 ms を読むと、約 200 MB/ステップのビューを対応付け直している計算になる。
どのビューが外れているかは測っていない。いずれにしても、外さないように持つ手は wired を増やす RAM 軸になる。

## 6. ページインはキューをまたいで直列 (`--qwen38-residency-probe --q38-queues`、3 起動 × 30 ラウンド)

1 ラウンドにつき 5 腕。cold は、開始時点で 1 ページもキャッシュに無い 10 expert の新しいビュー 30 本 (層 30〜47、1 組を 1 回だけ使う)。
warm は、層 8 の 10 expert をキャッシュ済みにして使い回すビュー 30 本。2 本のバッファは続けて commit する。

| 腕 | 先の kernel→GPU p50 (ms、起動 1 / 2 / 3) | 後の kernel→GPU p50 | 両方が終わるまで p50 |
| --- | --- | --- | --- |
| warm (1 本) | 0.212 / 0.214 / 0.211 | — | 0.421 / 0.417 / 0.446 |
| cold (キュー A) → warm (A) | 7.227 / 7.162 / 7.523 | 0.213 / 0.202 / 0.194 | 7.566 / 7.494 / 7.902 |
| cold (A) → warm (**B**) | 7.147 / 7.255 / 7.286 | **7.294 / 7.395 / 7.437** | 7.524 / 7.580 / 7.644 |
| cold (A) → cold (B) | 7.185 / 7.162 / 7.332 | **14.072 / 14.074 / 14.588** | 14.298 / 14.329 / 14.867 |
| cold 2 組を 1 本 (A) | 13.926 / 14.018 / 14.410 | — | 14.271 / 14.380 / 14.794 |

- **別のキューのキャッシュ済みのバッファも、A のページインが終わるまで GPU で始まらない。**cold 2 本を別々のキューに出しても、1 本にまとめた場合と同じ 14 ms。
- 同じキューの後ろに並んだ warm は、自分の kernel 開始が cold の後になるので、自分の kernel→GPU は 0.2 ms に見える。
- warm 1 本の 0.21 ms は §1 の v30same (0.05 ms) より大きい。このプローブではキューが 2 本ある点が違うが、差の原因は分けていない。

### 6-1. 12 §4 の「行 y を先行させる」形への含意 (導出、材料はすべて既存の実測)

- ドライバの中のページインはデバイス全体で直列なので、行の順序やキューを変えても、Metal に読ませる限り隠れない。
  隠せるのは、commit より前に host 側 (advise / pread) で読み終えた分だけ。
  行 y を先行させた場合に先回りできるのは y の expert (routing は正確) で、d の expert は鎖の中に残る。
- ずらすと、T=2 の 1 本のバッチが T=1 の 2 本になる。12 §2-1 の prev10 の行 (code、パス 1) では:
  - 素 (T=1): pre GPU 50 + routed GPU 8.5 ≈ 58.5 ms
  - 検証 (T=2): 53 + 15.3 ≈ 68 ms
  
  T=1 を 2 本にすると GPU は約 117 ms で、+49 ms になる。
- 先回りで消せる上限は、y の分の kernel→GPU の待ちと advise。素の T=1 では、それぞれ 25〜34 ms と 7〜21 ms (12 §2-1)。
- **結論はまだ出していない。**GPU の増分 (約 +49 ms) と、消せる待ちの上限 (約 32〜55 ms) が同じ程度なので、損得は作ってみないと決まらない。

### 9-3. 順番 (測れる最小の段から)

1. **影モードで連鎖の受理率を測る** (実装が小さく、損得の前提になる)。
   - `--q38-mtp shadow` のループで、d1 = argmax mtpForward([y], pos, h) の直後に、d2 = argmax mtpForward([d1], pos+1, hidden: mtpHidden(row: 0)) を足す (`Q38_MTP_CHAIN=2` など)。
   - logits は幹と共有のバッファなので、d1 の時点で配列にコピーする (10 §7)。
   - 位置 pos+1 の MTP の KV は、次のステップの mtpForward([y'], pos+1) が上書きするので、巻き戻しは要らない。そうなっていることを greedy で確かめる: 連鎖あり/なしで d1 列が一致すること。
   - 記録: 位置別の受理 (d1 == t1、d1 と d2 がともに一致)、d2 のドラフト ms。
   - プロンプト: code / tool / explain + long / long2 / long3、instruct、seed 1〜2。12K は memlog 越し。
2. **検証の幅の費用をいまの形で測り直す**: `Q38_BENCH_WIDTHS=1,2,3 Q38_BENCH_REPS=12 $B --qwen38-prefill-bench ...` を短文脈 (256) と 12K で。
   - T=3 で pre GPU が倍に跳ねる件 (09 §3-1) が残っていれば、先にその経路を見る (T の閾値で遅いカーネルに落ちていないか、`Q38_SPLIT_PRE=1`)。
3. **ループと巻き戻しを n_max 2 に広げる** (`speculativeLoop`)。
   - 検証は [y, d1, d2] (T=3)。受理数 a = 0 / 1 / 2 で、出すトークンは a + 1 本。
   - 巻き戻しは「行 a の後」へ戻す一般形にする: GDN 状態の退避を行 0 と行 1 の 2 本、conv 履歴に入る行を 2 行分、PLE 履歴も 2 行分。
   - `snapshotFirst` の precondition (T < `gdnMinTokens`) はそのまま使える。
   - MTP の追いつき (`mtpTokens` / `mtpRows`) は、受理した行の token と、その 1 つ前の位置の幹の h (verify の `hidden(row:)`) の組にする。
   - 中立性の検査: greedy で off == 全部棄却 == 2 本目だけ棄却 (新しい強制モード) == spec のトークン列。`spec10.sh` に腕を足す。
4. **端から端**: n_max 1 と n_max 2 を腕を交互に (ABBA)、短文脈 3 本 + 12K 3 本、instruct、seed 1〜2、200 トークン。
   - steady tok/s・受理・1 ステップの内訳 (`routeDetail`)。12K は memlog で wired / file-backed / Swapouts を見る。

### 9-4. 落とし穴

- 12K の n_max 1 の投機で、すでに wired 14.0〜14.7 GB・file-backed 1.1〜2.1 GB (10 §5、§4)。T=3 は expert の和集合がさらに増える (12K で 1,222 本、09 §3-1)。**見張り (`guarded.sh` / `memlog.sh`) を外さない。**
  止まったら、次を流す前に `pgrep -x TsugumiKernelCheck` が空であることを見る。
- 反復が 3 未満のセルには数字だけを書く。仮の値を掛けた損益表で進退を決めない (10 §8、09 §0-5)。
- zsh は `${=VAR:-a b c}`。集計では、MTP の prefill をチャンク行と合計行で二重に数えない (10 §7)。
- `Q38_COUNT_MISS` (mincore) は速度に影響しうる (§3)。速度を比べる走行では切る。
