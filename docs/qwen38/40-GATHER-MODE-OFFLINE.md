# 40. Wikipedia はアプリが読み、モデルは「回答」か「調査」だけを書く (PC、Offline)

書いた日: 2026-09-18。表記は 01 と同じ (実測 / 導出 / 未確認)。測定環境・変更案・揺れの幅の意味は 37 と同じ。測定環境は 37 §2 (PC の `qwen3.8-flash-next-q4kxl-32k-instruct-bf16ple`)。

この文書で使う言葉。

- **集めるモード**: この文書で試した進め方 (§1)。モデルに Wikipedia の道具を渡さず、検索と読み取りはアプリが行う。
- **調査**: モデルの出力の形の 1 つ。「調査」の行と、「- 」で始まる検索語の行 (1〜4 行) だけからなる。
- **回答**: モデルの出力の形の 1 つ。「回答」の行と、その後の最終回答からなる。
- **段落**: 記事の節を 300 字以内に切った塊 (§1-1)。アプリが質問との近さで選び、モデルに渡す単位。

## 0. 何を確かめたか

- 目的は 37 と同じ。1 問の待ち時間を、往復の数を減らして縮める。
- 39 の R1-d は、道具を渡したまま検索結果に節を添え、モデルが往復しないことを期待する形だった。往復の数はモデルの選択に任されたままだった。今回は、往復の種類そのものをモデルの選択肢から外す。
  - モデルは Wikipedia を読まない。ページを開く・目次を見る・節を選ぶ、という往復は起こりえない。
  - モデルの出力は、文法 (GBNF) で「調査」か「回答」のどちらかの形に縛る。
- 判定は 39 §4 と同じ式による 1 ターンの Mac の時間で、測る前に決めた。「なし」(39 の W1a、W1b) より揺れの幅を超えて短くなるか。正答も 39 と同じ基準で見る。

## 1. 実装

### 1-1. 集める側 (`WikipediaGatherer`、`Sources/TsugumiApp/Core/LocalWikipedia/WikipediaGatherer.swift`)

- 検索語をすべて今の索引で検索し、各語の 1 位、各語の 2 位… の順に、重複なしで記事を 8 件まで取る (設定の `maxSearchResults`、39 と同じ 8)。
- 記事を `PageOutline` で節に分け、節の中の行を順に 300 字まで詰めて段落にする。300 字を超える行は「。」の後で切り、それでも長い文は 300 字で切る。
- 段落を Ruri v3 (38 の 2,048 版、Neural Engine) で埋め込む。記事ごとのベクトルはターン中はキャッシュする。
- 段落の点数は、質問と各検索語とのコサインのうち最大のもの。大きい順に、合計 3,000 字まで渡す (最初の 1 段落は必ず)。3,000 字は、なしの検索結果 1 本の字数の中央値 (W1a の 3,032 字、実測) に合わせた。同じターンで一度渡した段落は再び渡さない。
- 渡す形:

  ```
  Wikipedia (2026年8月30日 時点の複製) を「…」「…」で検索し、見つかった記事から質問と検索語に近い段落を選びました (近い順):

  [高市早苗 · 節 1/40] (節のラベル)
  (段落)
  …
  見つかった記事: 高市早苗 / 石破茂 / …
  ```

- テスト (`LocalWikipediaTests.swift` の `WikipediaGathererTests`): 段落の切り方、記事の取り方、近い順と字数の上限、同じ段落を再び渡さないこと、何も見つからないとき。

### 1-2. 回す側 (`TsugumiToolLoopCheck --gather DIR`、`Sources/TsugumiToolLoopCheck/GatherLoop.swift`)

- アプリの `AppModel` のツールループは使わない。サンプリングの値と thinking の設定は `AppModel.makeRequest()` から取る (temperature 0.7、top_k 20、top_p 0.8、thinking off。公式値のまま)。
- 1 ターンの流れ:
  1. ラウンド 1: 出力は「調査」の形だけ (文法で縛る)。
  2. アプリが検索語で集め、段落を user のメッセージとして会話に足す。
  3. ラウンド 2 以降: 出力は「回答」か「調査」のどちらか (文法)。「調査」ならアプリが 2 に戻る。
  4. `--max-rounds` (6) のラウンドは「回答」だけ。
- 文法は `/apply-template` で組んだプロンプトを `/v1/completions` の `grammar` に渡してかける。PC の llama-server は `tool_choice` の強制を無視するが (`RemoteInferenceClient.swift` の冒頭)、`grammar` は効く (実測、`probe.py` で資料なし・資料ありの 2 通りを確認)。
- 検索語の 1 行は文法で 40 字までに縛り、プロンプトでも 40 字以内と知らせる。最初の 2 セットではこの上限がなく、1 行が止まらずに伸びた (§3-5)。
- システムプロンプトは、今のもの (`web-search-system-prompt.txt`) の日付と回答の節をそのまま使い、道具の説明をこの進め方の説明に替えた (`GatherPrompt.system`)。

## 2. 測り方

- 39 §2 と同じ。`--network offline --max-rounds 6 --thinking off --context 32768 --repeats 5`、`questions-v2-stage2.json` の N1〜N5。1 セット = 5 問 × 5 回 = 25 ターン。
- 集めるモードを 2 セット (G2a、G2b) 流し、間を 20 秒あけた。なしは 39 の W1a と W1b をそのまま使う。
- 埋め込みは Mac (Neural Engine)、推論は PC。全部 `guarded.sh` と `caffeinate -i` の下で流した。Swapouts はどのセットでも増えていない。無効な回 (error、空の回答) は 0。
- 1 ターンの Mac の時間 (導出) = ラウンド × 6.3 s + 新しいトークン ÷ 95 + 生成 ÷ 8 + 埋め込みの秒数。6.3 s と 95 tok/s は 33 §1、8 tok/s は 39 §4 と同じ。埋め込みの秒数は Mac で実測した値をそのまま足す。
- 正答の基準は 39 §2 と同じ (`answer-notes-v2.md` の「良い答えの条件 1」の核が、回答の結論にあるか)。100 回答すべてを読んで確かめた。

## 4. 結論

- **待ち時間は縮む (導出)。** 事前に決めた式で、1 ターンの Mac の時間は 137.2 / 140.2 s から 86.0 / 85.1 s になった。揺れの幅 (3.0 s) を大きく超えている。ラウンドは 4.20 から 2.08 に、新しいトークンは 1 ターンあたり 5,437〜5,763 から 3,411〜3,453 に、生成は 424〜428 から 265 に減った。埋め込みの 2.9〜3.5 s を足しても縮む。
- **正答は落ちた。** 集めるモードは 100 ターン中 4 回外れた。なしは 50 ターン中 0 回。4 回とも、答えの入っていない段落を渡されたのに「回答」を選んでいる (§3-3)。原因は、正しい記事を取れなかったこと (3 回) と、段落が質問に答えていなくてもモデルが「回答」を選ぶこと (§6)。これを採る前に扱いを決める必要がある。
- 時間は PC で測ったトークン数と、Mac で別に測った定数からの導出。Mac で集めるモードを流して測ったものではない (38 §2-9 で、埋め込みを QFN と同居させても prefill が 2〜6% 長くなるだけ、decode に差はないことは確かめてある)。
- 実装は `--gather` (測定器) と `WikipediaGatherer` (アプリの Core、アプリからはまだ使っていない) にある。アプリに入れるかどうかはユーザーが決める。

## 6. 外れた 4 ターンの原因 (実測)

2 つに分けて調べた。(1) 渡した段落に今の事実が入らなかったのはなぜか。(2) それでも「回答」を選んだのはなぜか。

### 6-1. 段落に今の事実が入らなかった理由

`--gather-probe` (モデルを使わず、同じ検索語で検索と段落の順位を出す) で、外れたターンの検索語をそのまま流した。今の事実を書いた文は測る前に決めた (N1「現職は衆議院議員の高市早苗」、N2「日本最東端の駅である」(根室駅)、N3「2025年12月31日に暫定税率は廃止された」(ガソリン税))。記録は `probe-cases.json` と `probe-failures.txt`。

| ターン | 正しい記事は取った 8 件にあったか | 取っていたら、その文の段落の順位 (枠は上位 12〜13) |
| --- | --- | --- |
| G2b の N1 の 3 回目 | なし。4 つの検索語 (「日本国閣僚一覧」「第103代内閣総理大臣」「2026年9月時点の首相」、40 字で切れた文) の上位は、イタリアの首相・石破佳子・空港・サウジアラビアの首相一覧など | 1 位 (内閣総理大臣の一覧) |
| G1a の N3 の 3 回目 | なし (ガソリン税) | 12 位 |
| G1b の N3 の 1 回目 | なし (ガソリン税) | 10 位 |
| G1a の N2 の 5 回目 | なし (根室駅、東根室駅)。どちらも検索語 1 の 6 位と 8 位で、各語の上位 2 件ずつ取る規則で落ちた | 8 位 (根室駅の冒頭) |

- N3 で「ガソリン税」が出なかったのは、索引の検索が語ごとの連続一致だから。検索語「ガソリン税 暫定税率廃止」の「暫定税率廃止」は、記事「ガソリン税」には連続では現れない (「暫定税率を廃止」3 回、「暫定税率は廃止」1 回)。この語に連続で一致する記事が 6 件あったので、緩い一致には移らなかった (`LocalWikipediaIndex.search`)。
- N2 では、取った記事の中で上位 12 段落のうち 9 つが、検索語「知床斜里駅」に最も近い段落だった。段落の点数は「質問と各検索語とのコサインの最大」なので、記事名そのものの検索語がその記事の段落を上位に並べる。取った中の「日本の都道府県の東西南北端の駅の一覧」の段落 (10 位) は、複製の時点でも東根室駅を最東端と書いている。
- 3 ターンは、正しい記事さえ取れていれば、その文の段落は 3,000 字の枠に入っていた。

### 6-2. 「回答」を選んだ理由

判断のラウンドの最初の 1 トークンで、「回答」と「調査」の確率を PC のサーバで測った (`branch.py`、`n_probs`、文法なし)。プロンプトは `GatherPrompt` の文面で組み直し、G2 の 50 ターンでは記録のプロンプトのトークン数と全部一致した。G1 の 3 ターンは文面が 1 か所違う (「40 字以内で、」の有無) ので、8 トークンずれる。記録は `branch-actual.txt` と `branch-empty.txt`。

| 場合 | P(回答) |
| --- | --- |
| G2 の 50 ターン、2 ラウンドで終わったもの (46) | 0.90〜0.997 (44 ターンが 0.95 以上) |
| G2 の 50 ターン、3 ラウンドになったもの (4) | 0.42〜0.76 |
| 外れた 4 ターン、渡した段落のまま | 0.77 (G1b N3)、0.90 (G2b N1、G1a N3)、0.995 (G1a N2) |
| 外れた 4 ターン、段落を「(新しい段落はありません)」に替える | 0.02〜0.31 |
| G2a の各問の 1 回目、段落を同じく替える | 0.11〜0.61 |

- 段落が無ければ「調査」に傾く。関係のない段落 (G2b N1 のサウジアラビアの首相一覧など) でも、あると P(回答) は 0.90 になる。モデルの判断は段落があるかには反応するが、段落が質問に答えているかには弱くしか反応しない。
- 段落が無いときも、N1 と N2 では P(回答) が 0.57 と 0.61 残る。
- G1a の N2 は、渡した段落に「東根室駅が日本最東端」という (古い) 記述があり、P(回答) は 0.995 だった。

## 7. 判断の分かれ目を測る物差しと、2 つの形 (実測)

### 7-1. 物差し

- 好ましい判断を次のように決めた (測る前に)。渡した段落に今の事実 (answer-notes-v2 の条件 1 の核) を書いた段落があれば「回答」、無ければ「調査」。
- 事例は判断のラウンド (各ターンの 1 回目) のプロンプトから作った (`decide_set.py`)。
