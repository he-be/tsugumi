# 18. prompt cache のチェックポイント (15 §2 G-0 / G-2) — Gemma の場面表どおりの位置で取り、SSD に置く

書いた日: 2026-09-14。対象は [17](17-SERVER-APP-WIRING.md) の結線 (`Qwen38ServerSession` → `Qwen38Engine` → `Qwen38Runner`)。表記は 01 と同じ (実測 / 導出 / 未確認)。
要件は [15 §2 G](15-DECODE-PLAN.md) の要件表 (基準は Gemma の server 経路、Ornith の現状は要件にしない)。

## 0. 結論

1. 15 の要件表の場面を 12K (`long`、11,679 トークン、MTP on、公式サンプラ) で踏み、**prompt_n は全場面で Gemma 以下** (§3)。
   再生成 1・指示つき再生成 16・指示を外した再生成 9・次のターン 21・止めた後の再生成 1 (Gemma は止めた後だけ全部 12,437)。ツールの往復は 4K で応答 55・その再生成 1 (Gemma も 55 / 1)。
   15 G-2 の止める条件 (Qwen3.8 の prompt_n が Gemma より大きい場面) には当たらなかった。
2. チェックポイントは 1 本 112.6 MiB (GDN 状態・conv 履歴・PLE 履歴、文脈長に依らない)。取るのは P−1、最後の user 本文の末尾 U−m、decode 中の `<tool_call>` の直前。
   残すのは「その要求で取った分 + 戻った点 + その要求が欲しい位置で既に持っている分」で、12K の場面では常に 2〜3 本。
3. **置き場は SSD (既定)。**RAM に 4 本 (450 MB) 持った 4K の走行は 5 本中 2 本で Swapouts が見張りを越えた (+7,288 / +8,936 ページ)。
   SSD (F_NOCACHE、作ってすぐ unlink) では 4K・12K とも見張り内。取得は 1 本 52〜115 ms (4K の検査)、12K の場面で 1 要求あたり 44〜156 ms (1〜2 本)、復元は 34〜37 ms (12K)。
4. `--qwen38-resume` (greedy) で、区切って取った答え・P−1 から・分岐点 L から別プロンプト・`<tool_call>` の直前からの続きが、通しで計算した答えとトークン列で一致 (MTP off / spec、tool と code)。
5. INV-1 (描き直し == 生成) は手を入れていない。今回のツールの往復 (文字列引数だけ) は描き直しが生成と一致して生きている状態から延長できた。一致しない場合は `<tool_call>` の直前のチェックポイントに戻る (§1-3、実機の場面では未踏)。

## 1. 形

### 1-1. 状態と戻し方 (G-0)

| 状態 | チェックポイントに入れるか | 戻し方 |
| --- | --- | --- |
| GDN 36 層の状態・conv 履歴、PLE 履歴 | 入れる (`Qwen38Runner.forEachRecurrentRegion`、117.6 MiB = 112.6 MiB + PLE) | 現在のバッファへコピー (`rollback` がバッファを差し替えるので同一性に頼らない) |
| `plePrev` | 入れる | 代入 (保留中の rollback も捨てる) |
| エンジンの `pendingH`・MTP の未消化行 (`mtpTokens` / `mtpRows`) | 入れる | 代入 |
| full attention の KV・インデクサ鍵・MTP KV | 入れない | 位置を戻すだけ。インデクサのブロック鍵は、4 個目のトークンを含むバッチが書き直す (`firstBlock = (max(pos0−3,0)+3)/4`、コードから) |

### 1-2. 取る位置

| 位置 | いつ | 使う場面 |
| --- | --- | --- |
| P−1 | prefill を P−1 で区切った直後 (MTP ヘッドも同じ行を食べた後) | 同じプロンプトの再生成 (1 ターン目を含む)、止めた後の再生成、ツール応答の再生成 |
| U−m | 最後のメッセージが user のとき。U = その `<|im_end|>` の位置、m = 本文の末尾 16 トークンを文字列に戻し `\n` / `\n\n` / `\n\n(` を足して符号化したときに変わる末尾のトークン数 | 指示つき再生成 (アプリの U5 は `\n\n` + 指示 1 行)、指示を外した再生成 |
| `<tool_call>` の直前 | decode でそのトークンを食わせる前。投機ループはこのトークンをドラフトとして受理しない (必ず次に食わせるトークンになる) | 描き直しがツール呼び出しの中でずれたとき |

m は最初「文字を直接つなげる」接尾辞 (`x` など) も入れていて、`.x` が 1 つの pretoken になるため m = 1 と出た (U5 では 0 で足りる)。行の追加だけに絞った。

### 1-3. 判定と捨て方 (`Qwen38PromptCache`、セッション)

- 分岐点 `agreed` = 持っている列と新しいプロンプトの LCP。候補は「名前のある生きている状態」と「位置 ≤ agreed かつ < P のチェックポイント」で、新しい方 (同位置なら生きている状態)。無ければ位置 0。
- `agreed` より後のチェックポイントは捨てる (別の列の途中)。
- 成功した要求の後は `取った分 ∪ 戻った点 ∪ この要求の P−1 / U−m の位置` だけを残す。
- 例外・取り消しの後は生きている状態を名無しにし (`publishInterrupted`)、プロンプトの中のチェックポイントは残す。これが「止めた後の再生成 1 トークン」。
  サーバの取り消し (ストリームを閉じる) は `shouldStop` のきれいな停止になり、延長も残る。
- `cache_prompt: false` はチェックポイントを取らない。

## 2. 検査 (`--qwen38-resume`、greedy、4K、`scratch/qwen38/resume/`)

B は A の最後の user 本文に `\n\n(Keep the answer short.)` を足したもの。L = LCP(A, B) は code 71 / tool 459 (どちらも `<|im_end|>` の位置 = m 0)。

| 項目 | tool off | tool spec | code off | code spec |
| --- | --- | --- | --- | --- |
| 区切って取った答え == 通し | 一致 | 一致 | 一致 | 一致 |
| P−1 から (prompt_n 1) == 通し | 一致 | 一致 | 一致 | 一致 |
| 負例 (P−1 から別のトークン) | 違う | 違う | 違う | 違う |
| L から B (prompt_n 16) == B を通し | 一致 | 一致 | 一致 | 一致 |
| `<tool_call>` の直前から == 通しの残り | 一致 | 一致 | (呼び出し無し) | (呼び出し無し) |

tool spec の 1 本目は、L→B の途中で Swapouts +7,288 ページとなり見張りが止めた (RAM 置き、4 本)。同じ条件の再走行は一致・+504 ページ、SSD 置きでは一致・0 ページ。

## 3. 場面ごとの prompt_n (server、`scratch/qwen38/cache18/scenes.py`、各 n = 1)

### 3-1. 12K (`long`)

Qwen3.8: `-c 12288 --draft-block-size 2`、SSD 置き。Gemma: `scratch/gemma4-qat-sym.gturbo`、`-c 16384 --draft-block-size 4` (同じメッセージ、Gemma のトークンで 12,353)。

| 場面 | 要件 (15) | Qwen3.8 cache_n / prompt_n | prefill | Gemma cache_n / prompt_n | prefill |

| 同じプロンプトの再生成 | 1 | 11,678 / 1 | 0.33 s | 12,352 / 1 | 0.17 s |

### 3-2. ツールの往復 (短い `tool`、ツール 2 本)

| 場面 | Qwen3.8 (4K、SSD) | Gemma (8K) |

## 4. 残り
