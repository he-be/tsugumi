### R1. ツールの形の候補

## 4. P: 1 ラウンドの prefill

### P0. 固定分を分ける

- `TsugumiToolLoopCheck --replay RUN_DIR` (32 §3) で記録済みの会話をローカルの Qwen3.8 で再生し、ラウンドごとに次を記録する。新規 56・883・1,455 トークン級のラウンドを含む会話を選ぶ。
  - チェックポイントの復元と保存 (18 の値は 1 本 34〜156 ms)
  - 描画とトークン化
  - `forward` の中: 層ごとの route・読み (バイト数と秒)・GPU・PLE (既存の `Q38_*` の計器)
  - MTP の KV を作る時間 (23 の MTP prefill は 12K で 11 s 台)
  - `prefillDiskReadBytes` と、同じ区間の `fs_usage` または `iostat` のディスク読み込み
- 同じラウンドを、直前に decode をしたあと (実運用と同じ) と、prefill を続けたあとで比べ、ページキャッシュの冷え方で読み込み量が変わるかを見る。
- 見張り (`Scripts/qwen38/guarded.sh`、memlog) をつけ、各ラウンド 2 回以上流す。

### P1. 小さな T の経路

P0 で大きかった項目から手を入れる。次の 3 つは、今の閾値が 2,048 / 4,096 のチャンクで決めたものなので、候補に挙げる。

- **P1-a routed の GEMM の閾値 (`Q38_GEMM_MIN_T` = 1,024)。** 06 と同じ 1 層ベンチを、T = 64・128・256・512・1,024 と、実際のラウンドの選択で取る。08 の混成 (組が 24 未満の expert は per-pair) は T が小さいときも効くはず。これも同じベンチで確かめる。
- **P1-b `pread` の閾値 (`Q38_PREAD_MIN_T` = 32) と読み方。** P0 で読みが大きければ、T が 32〜1,024 のときの読みの並列度とまとめ方を、05 の `readbench` で測る。ページキャッシュを増やす方向の案は入れない。
- **P1-c MTP の KV を作る時間。** P0 で固定分に占める割合が大きければ、見直す。

どれも出力がビット一致するか、参照 (France / Fuji) で PASS するかを確かめてから速度を測る。1 層ベンチを書く前に効果を見積もって止めることはしない (05 §6-3 の見積もりは外れた)。

## 5. K: LLKVApprox を再開する

### 近似がかかる場所

- ラウンドの新規トークンは、「モデルが書いた呼び出し (decode 済み) + ツール結果 + 次の手番の頭」。近似されるのは、ほぼ**ツール結果**になる (末尾 256 を除く)。
- 近似した KV はプロンプトキャッシュに残り、後のラウンドと回答の decode がそれを読む。**誤差はラウンドをまたいで積み重なる。** 29 の検査は 1 回の prefill の直後だけで、この積み重なりは見ていない。
- 小さなラウンド (1-1 の 17 本) には効かない。

### 分担

- **学習は 5080 PC (CUDA) で行う。** 5080 は 16 GB、RAM は 126 GB、E: の HDD は 18.6 TB (空き 17.3 TB)。C: の SSD は空き 420 GB (2026-09-18 に確認)。
- **環境は Windows のネイティブで組む。WSL は使わない。** Python (python.org 版か `uv`) と、PyTorch の CUDA 12.8 以降のビルド (5080 は Blackwell) を入れる。
  Triton (`torch.compile`) と flash-attn は使わない。LoRA と MLP の行列積だけなので、無くても困らない。
- 正解データは、**Mac のランナーと同じ値**でなければならない。30 で、HF の投影器がうちの値に合わなかった理由の候補に、重みと経路の違いが入っている。
  PC で作るなら、その値が Mac のランナーと合うことを先に確かめる (K0)。
- 組み込みと品質の関門 (K3・K4) は、ランナーが Metal なので Mac で行う。

### K0. PC の準備と、正解データの作り方を決める

- 環境: Python、PyTorch (CUDA)、`gguf-py` (純粋な Python)、`tokenizers`。GGUF 本体 (`Qwen3.8-Flash-Next-IQ2XXSImatrix-Q2KDownPad768-MTP.gguf`) と、アプリが使う PLE 表 (今の既定は BF16、31) を PC に置く。
- **正解データの作成器を PC に作る**: `Scripts/qwen38/reference_forward.py` (CPU の float32 参照器。Mac のランナーはこれと一致させてある) を、PyTorch の CUDA で T トークンまとめて流す形に移す。
  - 必要なのは層 0..47 の正確な forward と、途中の値の書き出しだけ (境界の残差、層 24.. の `attn_qkv` / `ssm_beta` / `ssm_alpha`、`attn_k` / `attn_v` / `indexer.k_proj`)。
  - 重みは RAM (126 GB) に置き、層ごとに GPU へ送る。routed expert は選ばれた分だけ逆量子化する。QSA の選択 (予算 2,048) も写す。
  - `hcmix` の土台は、境界の残差と各層の `hc_attn` から PC で計算する。Mac のダンプのように 3 回流す必要はない。
- **合うかの確認**: 30 の Mac のダンプ (`scratch/qwen38/llkv28/dump512`、prompt-code の先頭 512 トークン、1.2 GB) と同じトークンを PC で流し、目標ごとにコサインと相対誤差を出す。
  実装の差は、ヘッドが詰める差 (`hcmix` 0.835 → 1) より十分小さくなければならない。**全目標でコサイン 0.999 以上**を合格にする。
  届かなければ、ずれ始める層を探して報告する。
- 合わない、または作成が遅すぎる場合の代わり: Mac のランナーの `--qwen38-llkv-dump` で作り、LAN で PC に送る。

### K1. 正解データ (最初は 10 万トークン)

- 入力の分布は、アプリの実際のプロンプトに合わせる。`--replay` の `prompts/` (アプリと同じ描画) と、日本語 Wikipedia の記事をツール結果として描いた会話を使う。
  学習用と評価用は会話単位で分ける。K4 で使う会話 (k6、32 の branch33) は学習に入れない。
- 1 トークン約 330 KB (bf16、30 §5) なので、10 万トークンで約 33 GB。置き場は E: (HDD)。
  学習中に読むぶんは、RAM (126 GB) のページキャッシュか C: の SSD に載る量に収まる。
- 2,048 トークンを 1 ファイルにする。ファイルには境界の残差、`hcmix` の土台、正確な値、トークン列と出所を入れる。
- 最初の段は 10 万トークンで止める (30 §5 の最小の段)。量を増やすかどうかは、K4 の 1〜2 の結果を見てユーザーが決める。
  HDD には、PixelML や jun76 の量 (500 万トークンで約 1.6 TB) も入る。量を増やすときの律速は、PC での作成速度と HDD の読み (シーケンシャル) になる。どちらも K0・K1 で実測する。

### K2. 学習

- `Scripts/qwen38/llkv_train.py` (PyTorch、CUDA)。
- 形は PixelML と同じにする。GDN 18 層に LoRA (r128、qkv / b / a)、FA 6 層に MLP (隠れ 512、k / v / ik)。出力層は zero-init。
- **土台は `hcmix` にする。** 30 で一番近かったのが `hcmix` で、自前で学習するなら土台は自由に選べる。学習するのは「正確な値 − `hcmix`」を、境界の残差から当てるヘッド。
  学習中にモデルの重みは要らない (30 §5)。
- 損失は、目標ごとの MSE とコサイン。評価用のデータで、目標ごとの平均コサインを `hcmix` の 0.835 と並べる。
- メモリは 6〜8 GB の見込み (導出、30 §5)。5080 の 16 GB に収まる。
- 出力は F16 の safetensors。Mac に送って K3 で読む。

### K3. 組み込み

- `Q38_LLKV_HEADS=<path>`: ヘッドを F16 で読み、`linear(recurrentOnly:)` と `attentionFill` (29 §1) の射影の後に足す。GEMM は既存の sgemm。
- ヘッドの重みが全部 0 なら、今の `hcmix` とビット一致することを検査にする。
- メモリ: ヘッドは約 385 MB (F16)。32K spec の wired 最大 14.08 GB (23) に足して入るかを、32K の prefill と decode で確かめる。

### K4. 品質の関門 (安い順、どれも近似なしの実行と比べる)

1. 評価用ダンプのコサイン。`hcmix` を上回らなければ、ここで止めて報告する。
