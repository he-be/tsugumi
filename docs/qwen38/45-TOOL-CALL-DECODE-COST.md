# 45. QFN がツール呼び出しを書く時間 — 枠と URL の書き写し (記録の数え直しと机上の検討)

書いた日: 2026-09-19。表記は 01 と同じ (実測 / 導出 / 未確認)。**モデルは動かしていない。** 実測は、24 §3 の記録 (`scratch/qwen38/outline24/{qwen32k-b,qwen32k}/rounds.jsonl`) と 43 の S0 の記録を数え直したものと、QFN のトークナイザ (`~/LLM/Qwen3.8-Flash-Next-tokenizer`) で数えたトークン数。

この文書で使う言葉。

- **QFN**: Qwen3.8-Flash-Next。
- **枠**: ツール呼び出しのうち、引数の値でない部分。`<tool_call>`、`<function=名前>`、`<parameter=名前>`、それぞれの閉じ、終端のトークン。
- **値**: 引数の中身 (`url` の URL、`query` の検索語、`sections` の節番号)。
- **強制ラウンド**: アプリが呼ぶ道具を指定するラウンド (`tool_choice` が `function:名前`)。Online の最初の `web_search` と `fetch_page`。
- 1 ラウンドの中の秒数の分け方: そのラウンドの decode の秒数を、生成トークン数で均等に割って、枠と値に配った (導出)。

## 0. 結論

1. **QFN は、ツール呼び出しを 1 回書くのに中央値 5.7〜6.3 s を使っている** (実測、約 7.8 tok/s)。Online の検査 (`qwen32k-b`、15 ターン) では 68 回で 431 s、壁時計 3,382 s の 13%。
2. **その 431 s の 56% (241 s) は枠で、モデルが選ぶ余地がほとんど無いトークン。** URL の書き写しは 25% (109 s)、検索語は 14% (59 s)、節番号は 5% (21 s)。
3. **URL は検索結果に載っている文字列の書き写し。** 検索結果には既に `[1]`、`[2]` の番号が付いている (`WebSearchToolExecutor.render`)。URL 1 本は 8〜63 トークン (1〜8 s)、番号なら 1 トークン。同じページの節を読むときも URL を丸ごと書き直していて、15 回で 33 s。
4. **文法で 1 本に決まっている文字列でも、decode の速さは変わらない。** 43 の S0 の R1 は、1 本の文字列だけを許す文法で書かせたが、54〜84 トークンに 6.4〜10.5 s かかった (実測、約 7.6 tok/s)。今のランナーには、決まっているトークンを decode せずに済ませる経路が無い。
5. 減らし方の候補は §3。**枠のうち、強制ラウンドの値の前と、最後の引数のあとの閉じは prompt の側に移せて (枠 241 s のうち約 110 s 以下、導出)、モデルの出力の形は変わらない。残りの枠は、決まっているトークンを MTP の検証パスに入れる形 (§3-2) が届く。URL を番号にするのは道具の定義の変更で、モデルの挙動が変わりうるので 37 のやり方 (PC、2 セット) で確かめる対象。** どちらも未着手で、効果は測っていない。
6. 集めるモード (40〜43) のモデルの出力は検索語だけで、URL も節番号も書かない。残っているのは R1 の 9.0 s (検索語 54〜84 トークン) で、枠に当たるのは「調査」と行頭の `- ` だけ。

### 2-3. 決まっている文字列を書かせたときの速さ (実測、43 の S0)

43 の R1 は `--gather-force` で、1 本の文字列だけを許す文法を掛けて書かせた。サンプラが選べるトークンは毎回 1 つ。

| | 10 本 |
| --- | --- |
| 生成トークン数 | 54〜84 |
| decode の秒 | 6.4〜10.5 s |
| MTP の下書き (受理 / 提案) | 18/35〜33/49 |

文法で決まっていても、トークンごとに forward を 1 回通すので、秒数は普通の decode と同じになる。コードを検索した範囲 (`Sources/Tsugumi/Runtime/Qwen38/`、`Qwen38ServerSession.swift`) に、決まっているトークンをまとめて流す経路は無い。

## 3. 減らし方の候補 (机上。どれも未着手、効果は未測定)

### 3-1. 枠を prompt の側に移す (モデルの出力の形は変わらない)

- **値の後の枠 (10 トークン + 終端) のうち、決まっている部分。** 文字列の値は「`\n</parameter>` を含まない任意の文字列」(`QwenToolCallGrammar`) なので、値の終わりはモデルが `\n</parameter>` (4 トークン) を書いて決める。そのあとは 2 通り。
  - 宣言された引数が残っていなければ、`\n</function>\n</tool_call>` + 終端の 7 トークン (約 0.9 s) は決まっている。ここで生成を止め、残りはアプリが足す。足した分は、次のラウンドでツールの結果と一緒に prefill される (同じチャンクに入るので、チャンクの固定分は増えない)。
  - 引数が残っていれば (`fetch_page` の `url` のあとの `sections`)、次の引数を書くか `</function>` で閉じるかをモデルが選ぶ。決まっているのは `</function>` を書いたあとの `\n</tool_call>` + 終端の 3 トークンだけ。
- **強制ラウンドの値の前の枠 (14 トークン、1 回あたり約 1.8 s)。** 道具の名前も引数の名前もアプリが決めているので、`<tool_call>` から `<parameter=url>` までを prompt の末尾に置き、モデルには値から書かせる。そのラウンドの prefill のチャンクに 14 トークンが加わるだけになる。28 ラウンドに掛かる。
- auto のラウンドの値の前の枠は、モデルが道具を選ぶ部分 (`<tool_call>` と関数名) を含むので、この形では動かせない。
- 確かめること (未確認):
  - 描き直し == 生成 (INV-1、15 §2 G)。アプリが足した枠のトークン列が、テンプレートの描き直しと一致するか。値の最後の文字と次の改行がトークンの境目でつながらないか。
  - チェックポイントの位置 (18 の「`<tool_call>` の直前」) が、prompt の末尾に枠を置いたときにどこになるか。
  - 文法の状態から「この先は 1 通りしかない」を判定する口。今の `GrammarTokenConstraint` にあるかは見ていない。
- 導出の上限: `qwen32k-b` で、値の後の枠が 68 × 0.9 s 以下 = 約 60 s 以下、強制ラウンドの値の前の枠が 28 × 約 1.8 s = 約 50 s。合わせて 15 ターンで約 110 s 以下、1 ターンあたり約 7 s 以下 (壁時計の中央値 203 s の約 4%)。prefill に加わる分 (1 回 14〜25 トークン、68 tok/s で 0.2〜0.4 s) は引いていない。

### 3-2. 決まっているトークンを MTP の下書きの代わりに入れる

- 文法で次のトークンが 1 つに決まっている間は、MTP の下書きの代わりにそのトークンを検証パスに入れる。検証は必ず通るので、1 パスで n_max + 1 トークン進む。§2-3 の受理は 18/35〜33/49 で、決まっている文字列でも下書きの半分近くが外れている。
- 小さいまとまりを prefill の経路で流す形にはしない。43 §2-3 で、8 トークンのチャンクは 2.5〜2.7 s かかっていて (pread の閾値 32 より小さい)、同じ 8 トークンの decode (約 1.0 s) より遅い。
- 確かめること (未確認): 検証パスに外から下書きを入れたとき、MTP の KV (29 §1) と GDN の状態が正しく続くか。n_max 2 の 1 パスの秒数は 14 にある。
- 3-1 で動かせない auto のラウンドの枠と、集めるモードの強制した R1 に届く。

### 3-3. URL を番号で指す (道具の定義の変更。モデルの挙動が変わりうる)

- `fetch_page` に、検索結果の番号で指す引数を足す。検索結果の文面は既に `[番号] タイトル / URL / 抜粋` の形。URL 1 本 8〜63 トークンが 1 トークンになる。
- 同じページの節を読むときは、開いたページを番号か直前のページとして指す。ページはターンの間 `WebPageCache` にある (24)。
- 導出の上限: `qwen32k-b` で `url` の値 873 トークン、109 s。15 ターンで 1 ターンあたり約 7 s。
- 注意:
  - 記録には、検索結果に無い URL をモデルが書いた呼び出しがある (`https://swift.org/blog/all/`、`feed.xml`、24 §3 の en-url の 404 が 3 回)。番号だけにするとこれは書けなくなる。`url` を残して両方受けるかは未設計。
  - 引数の順は宣言順 (24 §3-2)。番号の引数を `sections` より前に宣言する。
  - 道具の定義を変えるとシステムプロンプトが変わり、開くページや往復の数が変わりうる。37 のやり方 (PC の Q4_K_XL、2 セット、揺れの幅を超えたものだけ) で確かめる対象。

### 3-4. 集めるモードの R1 (検索語)

- R1 の出力は 54〜84 トークン、9.0 s (43 §4)。枠に当たるのは「調査」と行頭の `- ` で小さい。残りは検索語そのもの。
- 検索語の行数と長さは文法の上限 (1〜4 行、1 行 40 字、40 §3-5) で決まっている。上限を変えると集まる段落が変わるので、41 の物差し (段落に事実が入ったか) で見る対象。ここでは案にしない。

## 4. 44 との関係

- 44 の形では、QFN の出力はツール呼び出しと選択肢回答だけになる。回答の decode が Gemma に移ったあと、QFN の decode で残るのはこの文書の部分。
- Gemma に替えてもここは変わらない (Gemma にツールは持たせない、44 §0)。
