# 25. 残り回数・文脈の行 (案 2・3) を分岐点の次トークンで確かめる

書いた日: 2026-09-15。表記は 01 と同じ (実測 / 導出 / 未確認)。
走行の記録は `scratch/qwen38/budget25/` (長い会話、途中で止めた) と `scratch/qwen38/branch25/m6/` (分岐点) (git 管理外)。

## 0. 結論

1. **発端:** アプリ (16K、Online、62128b8 の直後のビルド) の「m6 mac miniのSSD速度は？」で、ツール 6 回の上限のあと `tool_choice: none` のラウンドが `<tool_call><function=fetch_page>…` を 61 トークン書いて終わり、それが回答として表示された (21 A-4 の形)。上限の行 (21 §8 の 4) は最後のツール結果の末尾に付いていた。最後の prompt は 8,164 / 16,384 で、文脈は逼迫していなかった。
2. ユーザーの選択で案 2 (毎ラウンド残り回数を伝える) と案 3 (文脈の残りも伝える) を入れ、実験した。`AppModel.toolBudgetNotes` (`limit` 既定 = 今の挙動 / `rounds` / `context`)、検査は `TsugumiToolLoopCheck --budget-notes`。
3. 9 会話 × 3 腕を最後まで流す実験は 1 本目の途中で止めた (ユーザー: 数千トークンの生成・prefill は要らない、原理を確かめればよい)。
4. 代わりに **分岐点の次トークン** を測る `--qwen38-branch-probe` を作った: アプリの会話を描き直し、最後のツール結果の末尾に足す行だけを変え、次の 1 トークンが `<tool_call>` になる確率を出す。共通部分の prefill は 1 回、各案はチェックポイントから数十トークン。M6 の 12 案で約 5 分。
5. **検査に誤りがあった (直した):** チェックポイントは再帰状態だけを持ち、KV は持たない (設計どおり、`Qwen38Checkpoint` のコメント)。低い位置から続けた案が KV を書いた後に高い位置のチェックポイントを戻していて、その案の数字が壊れていた (0.27 と 0.88 のような食い違いに見えた)。高い位置から順に処理する。
6. **経路の確認 (§2):** 同じ経路の再実行・容量 8K / 16K・restore (すぐ戻す / 先へ進めてから / デコード後) はどれも logits がビット一致。**チャンクの切り方だけで logits が動く** (語彙全体の max |Δ| 2.07〜3.50、上位 20 で 0.82〜1.60、KL ≤ 0.020、P(`<tool_call>`) 0.86〜0.91)。5e-2 の許容を超える。正常な範囲かは未確認。
7. **結果 (§3、M6 の 1 会話の 3 分岐点):**
   - 行が無ければ、どの分岐点も P(`<tool_call>`) ≈ 1。
   - 残り回数の行 (案 2): 残り 4 回で 1.000、残り 1 回で 0.95 / 0.88 (2 経路)。ほとんど下がらない。
   - 文脈の行 (案 3) を実際の値 (7,212 使用 / 16,384) で足すと 0.87 / 0.65。残りを 484 と書くと 5 回の後で 0.0001 / 0.0003、2 回の後では 1.000。
   - 上限の行: 5 回の後に置けば 0.0004 / 0.0003、**実際の上限のラウンド (6 回の後) では 0.30**。公式サンプラ (温度 0.7・top-k 20・top-p 0.8) の候補に `##` (0.66) と入るので、GUI で `<tool_call>` を書いたのは約 3 回に 1 回の事象として再現する。
8. `toolBudgetNotes` の既定は `limit` のまま (アプリの挙動は変えていない)。上限のラウンドで `<tool_call>` を書く件 (A-4) は残る。

## 1. 行の形 (`AppModel`)

上限前のラウンドの最後のツール結果の末尾に、そのラウンドの呼び出しの後、初めて描かれる前に足す (21 §8 の 4 と同じ置き方なので以後の描き直しも同じ文字列、INV-1)。

| `toolBudgetNotes` | 上限前のラウンド | 上限のラウンド |
| --- | --- | --- |
| `limit` (既定) | なし | `(ツール呼び出しは合計 6 回までで、上限に達しました。…)` |
| `rounds` | `(ツール呼び出し: 6 回中 2 回使用、残り 4 回。)` | 同上 |
| `context` | `(ツール呼び出し: 6 回中 2 回使用、残り 4 回。文脈: 16,384 トークン中、この結果の前までで 8,225 使用、残り 8,159。)` | 同上 |

- 回数はラウンドの数 (上限の行と同じ数え方)。1 ラウンドに呼び出しが複数あれば最後の結果にだけ付く。
- 文脈の「使用」は直前のラウンドの prompt + 生成トークン (正確)。足す結果そのものは数えない (アプリはトークナイザを持たない)。
- テスト: `AppModelToolLoopTests.budgetNotesGoOnEachRoundsLastResult` (`rounds` / `context`、2 呼び出しのラウンド、上限の行、描き直しの接頭辞)、`budgetNotesGroupDigitsAndStopAtZero`。

## 2. 分岐点の検査と経路

### 2-1. 道具

- `Scripts/qwen38/budget_branches.py OUT --chat N --points 2,5,6`: chats.json の 1 会話の `outputContinuationTurns` を、`Tests/.../qwen38-tool-loop/spec.json` の宣言とシステムプロンプトで上流の `chat_template.jinja` に描き、分岐点 k (モデルの呼び出し k 回目の結果を読んだ直後) ごとに案のトークン列と manifest を書く。M6 の長さはアプリの記録 4,276 / 7,213 / 8,164 に対して 4,276 / 7,212 / 8,163 (記録の日付は 9/15、spec は 9/14。1 トークンの差の出所は未確認)。
- `TsugumiKernelCheck --qwen38-branch-probe manifest.json`: trunk を 1 回 prefill し各案の分岐位置でチェックポイント、高い位置から順に restore → 末尾を `runner.forward` → 最後の logits。P(`<tool_call>`) は温度 0.7 の softmax (top-k / top-p の前)、上位 5 と、公式サンプラで `samples` 回 × `sampleTokens` の引き。manifest に `capacity` と `cuts` (追加のチャンク境界)。
- `--qwen38-path-check <tokens> --q38-cuts … --q38-resume-at N`: 1 本のプロンプトの最後の logits を 6 経路で比べる。
- `--qwen38-restore-check <tokens> <trunk> <position>`: live / すぐ restore / trunk を先まで流してから restore / デコード 12 トークン (greedy・サンプル) の後の restore。
