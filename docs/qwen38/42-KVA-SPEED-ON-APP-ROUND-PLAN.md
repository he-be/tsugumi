この文書で使う言葉。

- **集めるモード**: 40 の進め方。1 ターンは「調査」(1 ラウンド目、R1) と「回答」(2 ラウンド目、R2) の 2 ラウンド。
- **固定分**: 33 §1-1 の言葉。1 ラウンドの prefill の秒数のうち、新規トークンの数に比例しない部分。
- **KVA**: LLKVApprox (28〜30)。新規トークンのうち末尾を除いた行について、後半 24 層を通さず、その層の KV と GDN の入力を近似で埋める。
- **読みの下限**: あるラウンドが SSD から読んだバイト数を、`pread` の上限 6.5 GB/s (05 §1) で割った秒数。読む量を変えない限り、これより短くはならない。

## 0. なぜこの順か

- 往復を減らす側は 41 で終わった。集めるモードはどのターンも 2 ラウンドで終わり、集め方で縮められる時間は残っていない (41 §7-4)。
- 1 ターン約 85 s の内訳 (41 §7-1、導出) は、R2 の新しいトークン 約 29 s、回答の生成 23〜26 s、R1 約 19.5 s、R2 の固定分 6.3 s、埋め込み 3〜5 s。
- 33・37 の計画に残っているのは P (1 ラウンドの prefill の固定分) と K (KVA) の 2 本。一番大きい項目 (R2 の新しいトークン) に当たるのは K だけ。
- ただし K は K0〜K4 で 8〜10 日かかり、品質の関門 (K4) で止まる可能性がある。**学習に入る前に、K がアプリの 1 ラウンドで何秒縮めるかを実測する。** KVA の配管は 29 でランナーに入っていて (§2)、速度は学習したヘッドが無くても測れる。
- P の候補 (33 §4 P1) は、取り分があるかどうかを確かめずに書いてあった (§1-1)。同じ測定 (§3 S0) で、P1 に手を付けるかどうかも決められる。

## 1. 33 §4 (P) に書いてあることの根拠

### 1-1. 測ってあるもの・確かめていないもの

| 33 に書いてあること | 根拠 |
| --- | --- |
| 1 ラウンドに約 6〜10 s の固定分がある | **実測からの導出。** 83 ラウンドで回帰し直すと、prefill 秒 = 6.20 + 新規 ÷ 89.6 tok/s (R² 0.968)。33 は 95 tok/s (23 のベンチ) を引いて出していたが、回帰でも同じ大きさになる |
| `prefillDiskReadBytes` が実際のディスク I/O かは未確認 | **コードで確認した。** `AppDiskReadSampler` は `proc_pid_rusage` の `ri_diskio_bytesread` の差分を取っている。ページキャッシュに当たった分は入らない。`fs_usage` や `iostat` との突き合わせはしていない (未確認) |
| 小さな追加に合わせて閾値を詰めたことはない | **本当。** 03〜08 のランナーの測定はどれも 2,048 / 4,096 のチャンク。小さな T を測ったのは 07 §2 の GDN 1 層 (T = 16〜128) だけ |

### 1-3. KVA について、記録から言えること

- KVA でも末尾 256 トークンは後半 24 層を通す。1-2 のとおり三十数トークンで expert の大半を読むので、**最後のチャンクでは、後半の層の読みは KVA でも減らない見込み** (導出)。減るのは、末尾を含まないチャンクの後半の読みと、後半の層の計算。
- 29 §2 の速度は 8K で 1.44〜1.50 倍、3,072 トークン (2 チャンク) で 34.8 → 22.8 s (1.53 倍、n=1)。どちらも `--qwen38-llkv-check` で位置 0 から流した値で、プロンプトキャッシュの続き・直前の decode・MTP の KV は入っていない。**アプリのラウンドの形では測っていない。**
- 集めるモードの R2 の新規は 1 回 2,716〜2,765 トークン (41 §7-1)。チャンク 2,048 なら 2 本で、末尾 256 を除く約 9 割が近似の対象になる (導出)。
- 集めるモードで近似されるのは、回答が読む Wikipedia の段落そのもの。29 の検査は prefill 直後の次トークンと教師強制 32 トークンだけで、「近似した本文を読んで回答を書く」ところは見ていない。`hcmix` は k6 の P(`<tool_call>`) を動かした (30)。

### 3-1. 入力を固定する

- G3a の 5 問 (N1〜N5) の 1 回目のターンから、R1 と R2 のプロンプトのトークン列を作る。描画はアプリと同じもの (`GatherLoop.swift`)、検索語は記録の R1 の出力、段落は `--gather-search "question,articles=12"` の集め。41 §1 で、モデルなしの書き出しが記録の本文と一致することは確かめてある。
- S0 と S1 は同じトークン列を使う。`hcmix` を立てるとモデルの出力が変わりうるので (30)、S1 ではモデルに R1 を書かせず、記録の R1 の出力を教師強制で流す。S1 の回答の中身は読まない。見るのは秒数だけ。

### 3-2. S0: 近似なしの内訳

- 流す形は実運用と同じにする。R1 の prefill → R1 の出力 (約 65 トークン) の decode → R2 の prefill。プロンプトキャッシュは持ったまま、32K、KV Q8_0、MTP on、チェックポイント on、チャンク 2,048。
- R1 と R2 のそれぞれで取る数字。
  - prefill の秒、チャンクごとの秒
  - 前半 24 層と後半 24 層に分けた、route (うち読みの秒とバイト数)・routed (wall / GPU)・pre-router (wall / GPU)・PLE
  - MTP の KV を作る秒、チェックポイントの復元と保存の秒
  - `ri_diskio_bytesread` の差分と、同じ区間の `iostat` の読み込み量 (§1-1 の残りの未確認を埋める)
  - wired の最大、Swapouts
- 5 問 × 2 回以上。見張りは `guarded.sh` と `caffeinate -i`、間は 20 秒。
- ここで分かること: R2 の約 29 s と固定分 6.3 s が、どの層のどの項目か。KVA で消える部分 (末尾を含まないチャンクの後半 24 層) の上限。P1 の候補に取り分があるか。

### 3-3. S1: KVA を立てたときの秒数

- S0 と同じ流し方で `Q38_LLKV_SPLIT=24 Q38_LLKV_FILL=hcmix`。末尾は 256 と 1,024 の 2 通り。
- 取る数字は S0 と同じ項目と、埋めの秒。5 問 × 2 回以上。
- 学習したヘッド (約 385 MB、F16) の GEMM はまだ無いので、その分の秒数は入らない。K3 で足したときに測り直す (未測定のまま見積もらない)。
- 近似した KV を持ったまま回答を decode したときの tok/s と MTP の受理率 (`draftAccepted / draftProposed`) も記録する。`hcmix` の値なので、学習後の値の代わりにはしない。数字だけ書く。
- **出す結論は 1 つ**: 集めるモードの 1 ターンで、R2 の prefill が何秒から何秒になったか (実測、Mac)。1 ターン 85 s の中で何秒かを並べて書き、K1 以降に進むかはユーザーが決める。

### 3-4. K1〜K4 に足すこと (33 §5 への追加)

- **K1 の入力の分布に、集めるモードの描画を入れる。** 33 §5 K1 は Web・Wikipedia のツール結果の会話を想定していた。今の運用の形は集めるモードなので、R2 のプロンプト (質問 + 段落 12 個前後 + 見つかった記事) を学習用に入れる。評価用の 5 問 (N1〜N5) と同じ記事は学習に入れない。
- **K4 の 4 (回答の読み取り) を、集めるモードの R2 で行う。** G3a・G3b の記録した回答 (近似なし、PC の Q4_K_XL) ではなく、Mac のランナーで近似なしに書かせた回答を教師にして、近似ありでトークンごとの KL と top-1 一致を出す。比べる相手は同じランナーの近似なしに限る。
- K4 の 2 (k6 の分岐点) と 3 (記録した会話の全ラウンド) は 33 のまま。集めるモードはツールを呼ばないので、P(`<tool_call>`) の代わりに、R1 の「調査」と「回答」の分かれ目の次トークンの確率を見る (25 と同じ測り方)。
