# 44. QFN が文脈を集め、Gemma が最終回答を書く案 (机上の検討)

書いた日: 2026-09-19。表記は 01 と同じ (実測 / 導出 / 未確認)。**この文書のための新しい測定は無い。** 実測と書いた数字は、どれも過去の記録 (43 の S0、24 §3・§4 の走行) を数え直したもの。

> **決定 (2026-09-19、ユーザー)**: この案はやらない。根拠は 46。thinking off の Gemma は同じ 50 個の段落で核が結論にある回答が 39 / 50・37 / 50 (QFN 47 / 50)、thinking on は 46〜47 / 50 まで戻るが生成が約 10 倍になり、受け渡しで縮めたかった時間が消える (46 §5-3)。H-Mac と Online の受け渡しは行わない。45 (QFN のツール呼び出しの decode) は別の項目で、この決定の対象ではない。

この文書で使う言葉。

- **QFN**: Qwen3.8-Flash-Next。Mac のランナーは `Qwen38Runner`。
- **Gemma**: Mac のアプリに入っている `gemma4-qat-sym.gturbo` (26B-A4B、MTP あり)。
- **集めるモード・R1・R2**: 40、43 と同じ。1 ターンは「調査」(R1、検索語を書く) と「回答」(R2、渡された段落を読んで「回答」か「調査」を選び、回答を書く) の 2 ラウンド。
- **受け渡し**: QFN が集め終えた時点で QFN を降ろし、Gemma を載せて、集まった文脈を渡すこと。
- **入れ替え**: モデルを降ろして別のモデルを載せること。受け渡しで 1 回、次のターンのために QFN に戻すのでもう 1 回。

## 0. 前提 (2026-09-19、ユーザー) と結論

前提。

- **Gemma にツールを持たせても、ろくな結果が出ないことは分かっている。** 記録では 24 §4・§5 (目次を受け取っても 15 回中 1 回しか節を読まない、呼び出しを書かずに 25,184 トークン生成して上限、出典の形が揃わない)。したがって「R1 も Gemma にする」形は検討しない。
- 役割: **QFN はツール呼び出しと選択肢回答に徹して、文脈を集める。Gemma は、その文脈から (必要なら事前に絞り込んだ上で) 最終回答だけを書く。**

結論。

1. **同じ Mac、同じアプリの経路で、Gemma は QFN に比べて prefill が約 3.8 倍、回答の decode が約 4.5 倍速い** (実測、24 の同じ 7 会話。§1)。
2. **QFN の回答の decode は、1 ターンの大きな部分を占めている。** Online の検査 (24 §3) では 15 ターンの壁時計 3,382 s のうち 1,297 s (38%)、集めるモード (43 S0) では 83.9 s のうち 18.1 s (22%)。受け渡しで消えるのはこの部分。
3. **受け渡しで新しく払うものは 3 つ。** Gemma が文脈を読む prefill、入れ替え 2 回、次のターンで QFN が Gemma の回答を読む prefill。2 つのモデルは 18 GB に同時に載らない (§2)。入れ替えの秒数と、入れ替え直後の速さは測っていない (未確認)。
4. **集めるモードでは、R2 の「回答」か「調査」かの選択を QFN に残すと、時間は縮まない (導出、§3-1)。** QFN が選ぶには R2 の段落 (新規 2,650 トークン、prefill 37.3 s) を読む必要があり、消えるのは回答の decode 18.1 s だけで、Gemma の prefill (約 12 s) と回答 (約 4 s) と入れ替えが乗る。縮むのは、QFN の R2 をなくして R1 のあと直接 Gemma に渡す形で、約 44 s + 入れ替え (導出)。41 §6 の G3a・G3b (50 ターン) と 43 の S0 (10 ターン) では、R2 はすべて「回答」を選んでいる。
5. **Online では、QFN の選択を残しても縮む見込み (導出、§3-2)。** QFN は最後のツールの結果を読んで「もう呼ばない」と決めるところまでで、そこで受け渡す。回答 1 本あたり、消えるのは decode の中央値 78.6 s、乗るのは Gemma の prefill と回答で約 30〜55 s + 入れ替え。幅は渡す文脈の長さ (絞り込むかどうか) で決まる。
6. **机上で決まらないのは Gemma の回答の側** (§4)。渡された文脈だけから日本語で正しく答えるか、回答の長さ、Gemma のトークナイザでのトークン数。
7. QFN の側の decode を短くする話 (URL の書き写し、呼び出しの枠) は別の項目にした (45)。

## 2. 2 つのモデルを同時に載せられるか (導出)

- QFN は 43 の走行で wired 最大 14.6 GB、Gemma は 32K のロードで約 10 GB を wired で持ち (MAC_APP §4e)、ツールのループ中は最大 15.95 GB。足すと 18 GB を超えるので、同時には載らない。
- 1 ターンに入れ替えが 2 回入る。
  - ready までの秒数は Gemma 2.3 s (MAC_APP §6)、QFN 0.9 s (17)。どちらも重みは mmap で、実際の読みは最初の要求のときに起きる。入れ替え直後のラウンドの秒数は測っていない (未確認)。
  - アプリの `RealInferenceClient` は backend を 1 つだけ持つ (`unload()` → ロード)。1 ターンの途中で入れ替える経路は無い。
- 入れ替えで消えるもの。
  - Gemma の prompt cache (`ServerPromptCache`、RAM)。Gemma は毎ターン、渡された文脈と会話の履歴の全部を新規として読む。
  - QFN の RAM の状態 (KV、GDN)。チェックポイントは SSD にある (18) ので残り、次のターンはそこから復元する。
- 次のターンで QFN が新しく読むもの: Gemma が書いた回答。QFN の KV には入っていないので、次のターンの prefill の新規に入る (621 トークンなら約 10〜17 s、§1 の束から)。今も QFN は自分の R1 の出力を R2 で読み直している (43 §2-1) ので、読み直しそのものは新しい種類の費用ではない。

## 4. 机上では決まらないことと、最小の段

決まらないこと (どれも未確認)。

1. **Gemma が、渡された文脈だけから正しく答えるか。** 集めるモードなら N1〜N5 の正答 (39、40 と同じ基準) で、QFN の記録 (41 §6 の G3a 24/25、G3b 23/25) と並べられる。
2. **Gemma の回答の長さ**と、Gemma のトークナイザでの文脈のトークン数。
3. **文脈の渡し方。** Gemma にはツールを宣言しないので、ツールの結果は本文として渡す。事前の絞り込みは、集めるモードでは既にある (質問に近い段落を kohagi の埋め込みで選ぶ、38・40)。Online のページの本文に同じ絞り込みを掛けるかは未設計。
4. **thinking。** アプリの Gemma の既定は off。§1 の Gemma の走行は on。on にすると decode が思考の分だけ伸びる。
5. 入れ替えの秒数、入れ替え直後のラウンドの速さ。

最小の段 (提案。**H-PC は 2026-09-19 に流した。結果は 46**: 同じ 50 個の段落で、核が結論にある回答は QFN 47 / 50、Gemma 39 / 50 と 37 / 50。差はほぼ N5。H-Mac と Online は未着手)。

- **H-PC (Mac のモデルは使わない)**: G3a・G3b の 50 ターンの検索語は記録にあり、段落の集めはモデルを使わずに再現できる見込み (41 の `make_cases.py`)。その段落と質問を、PC の llama-swap の `gemma4-26b-a4b` に、ツールの宣言なし・文法なし・公式サンプラで渡し、回答を 2 セット取る。出るもの: 正答の数 (QFN の 24/25・23/25 と同じ基準)、回答の長さ、Gemma のトークナイザでのトークン数。
  - 先に確かめること: PC の `gemma4-26b-a4b` の量子化。
- **H-Mac**: H-PC で回答が使えると分かったときだけ。Mac で QFN の R1 → 入れ替え → Gemma の回答 → 入れ替え、を 43 と同じ 5 問 × 2 回で流し、§3-1 の右の列と入れ替えの秒数を実測にする。1 ターンの途中で backend を入れ替える経路を `TsugumiToolLoopCheck` に足す必要がある。
- Online の受け渡し (§3-2) は、H-PC の結果を見てから。
