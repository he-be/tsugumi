# 21. ツールループの不具合の整理 — 何が壊れていて、何が壊れていないか

書いた日: 2026-09-15。対象は [20](20-WEB-TOOLS-WIRING.md) の実モデル検査 (`TsugumiToolLoopCheck`) と、その後の修正・再走行。表記は 01 と同じ (実測 / 導出 / 未確認)。各セル n = 1。

20 の後、症状 (文脈超過・cache 外れ・Swapouts) を 1 つずつ潰そうとして、直すたびに別の症状が出た。
この文書は手を止めて、記録した会話の中身から原因を層ごとに分け、残りの作業の順を決めるためのもの。

## 0. 結論

1. **壊れているのは主にアプリのツールの作り** (Gemma と共有の経路)。モデルでも、パース・描画でもない。
   - A-1 `fetch_page` が本文を打ち切っても続きを読む手段が無く、同じ URL を同じ引数でもう一度呼ぶと同じ本文がもう一度積まれる。
   - A-2 前のターンのツール結果が履歴に全部残る。
   - A-3 1 ターンで読むページの合計に上限が無い (ページ 1 枚の字数上限だけ)。
   - A-4 ラウンド上限に達したことをモデルに伝えていない。
2. **server の不具合は 1 つ** (S-1: `tool_choice: none` で宣言をプロンプトから消していた)。直したが未コミットで、直した結果 A-4 が表に出た (§3)。
3. **パースと描画は壊れていない。**並列 2 呼び出しを含めて呼び出しは全部正しく読めた。描画は HF と一致 (20 §2)。ラウンドとターンをまたいで cache は続いている。
4. **実験の足場が 2 つ足りない。**Web を毎回引くので同じ場面を再現できない (E-1)。見張りが 100 MB 前後の一時的な書き出しでも止める (E-2)。
5. サンプリングは公式推奨値から変えない (ユーザー指示)。中国語の語が混ざるのは避け難いものとして扱う。

## 2. 層ごとの原因

### A. アプリのツールの作り (Gemma と共有)

**A-1 `fetch_page` の打ち切りに続きが無い。**
`WebSearchToolExecutor` は打ち切ると末尾に `…(本文はここで打ち切り)` とだけ書く (`WebSearchToolExecutor.swift:221`)。
`WikipediaToolExecutor` は `…(本文はここで打ち切り。全 N 文字。続きは wikipedia_page の from=M で読めます)` と書き、`from` 引数がある。
記録では、同じ本文の再取得 5 回はどれも、その URL の打ち切られた本文を受け取った後だった (ja-howto の hrstsh.com 3 回、en-url 2 の swift.org 3 回、en-swift 2 の CHANGELOG 2 回)。
打ち切られた本文を受け取って再取得しなかった場合もある (打ち切りは合計 23 回)。
ja-howto の超過 14,640 には同じ本文 12,178 字が 2 回分入っている。

**A-2 履歴にツール結果が全部残る。**
ja-news 2 ターン目は再取得なしで、1 ラウンド目が 11,470 (full1) / 9,282 (p2000b)。1 ターン目に読んだページがそのまま載っている。
en-swift 3 ターン目 (full1) も 1 ラウンド目で超えた。ページを 2,000 字にしても ja-news 2 ターン目は超えた (p2000b)。

**A-3 1 ターンで読む合計に上限が無い。**
ja-price 1 ターン目は再取得なしで、ページ 3 枚 (5,360 / 6,087 / 6,074 字) + 取得失敗 1 + 検索 + Wikipedia で 12,369 になった。
システムプロンプトは「一度に開くのは多くても 2〜3 ページ」と書くが、ラウンドをまたいだ合計の制限は無い。

**A-4 上限をモデルに伝えていない。**
上限 (既定 6) に達したラウンドでアプリは `tool_choice: none` を送るが、プロンプトには何も足さない。
S-1 の修正前は宣言が消えていたのでモデルは呼べなかった。修正後は宣言が見えたままなので、モデルは呼び出しを書いた (§3)。

### S. server

**S-1 `tool_choice: none` で宣言を描かなかった (修正済み・未コミット)。**
`ChatRequestParser` が `none` のとき `tools` を空にしていた。llama.cpp (`common/chat.cpp` の `common_chat_templates_apply_jinja`) は `tool_choice` によらず `tools` をテンプレートに渡し、`none` では文法を載せず、呼び出しも解読しない。
あわせてアプリも上限のラウンドで `tools: []` を送っていた。宣言はプロンプトの先頭にあるので、どちらもそこから cache が外れる (full1 en-swift の cached 0 / 4,767、0 / 11,229)。

### P. パース・描画・cache (壊れていない)

- 描画: アプリの要求組み立てで 6 要求が HF jinja と文字列一致 (20 §2)。`none` の要求も同じ描画 (§3 のテスト)。
- 呼び出しの解読: 記録のすべての呼び出し (同じラウンドの `fetch_page` 2 本を含む) が引数つきで読めた。
- cache: 完了したラウンド間の不足は、S-1 の場合を除いて 0 (20 §3、p2000b も同じ)。

### M. モデルの挙動 (記録だけ)

- en-swift は 2 走行とも 1 ターン目に上限まで検索と取得を続けた。
- 検索語に中国語の語 (`内存構成`)。避け難いものとして扱う。

## 4. 実験の足場

**E-1 再現できない。**毎回 Serper と実ページを引くので、検索結果・ページの中身・長さが走行ごとに変わる。A の修正の前後比較もページ上限の比較も同じ入力で行えない。
A-1 を直すと呼び出し方が変わるので、記録した呼び出しをそのまま読み戻す形では使えない。

**E-2 見張りが一時的な書き出しで止める。**

| 走行 | 止まった場所 | Swapouts | wired 最大 / file-backed 最小 | 備考 |
| --- | --- | ---: | --- | --- |
| 20 smoke | 2 ターン目 5 ラウンド目の prefill (prompt 10,690) | +7,276 (114 MiB) | 14.63 / 1.02 GB | |
| p2000 | ja-news 1 ラウンド目の prefill (prompt 1,652)、開始 28 s | +8,392 (131 MiB) | 14.33 / 0.94 GB | Chrome が開いていた。モデル読み込み前から圧縮メモリ 0.66 → 2.1 GB |
| p2000b | ja-howto 1 ターン目 5 ラウンド目 (prompt 5,868) | +5,512 (86 MiB) | 14.99 / 1.11 GB | Chrome を閉じた後。書き出しは 2 サンプル (4 s) で起きた |
| 20 full1 | (止まらず、845 サンプル) | +96 | 14.66 / 1.17 GB | |

見張り (`guarded.sh`) のしきい値は 4,096 ページ (64 MiB)。
p2000b の記録では、wired がラウンドごとに 8 GB 前後 ↔ 14 GB で上下し、file-backed が 6 GB ↔ 1.5 GB で逆に動いた。書き出しは wired が 14 GB に上がったサンプルで出た。
09 の記録 (prefill 中 7〜8.5 GB、decode で 11.5〜14 GB) と同じ形。長い prefill の後に decode を 1 回やるだけの server の走行 (17: 0、18: +28) より、切り替わりの回数がずっと多い。Swapins は記録していない。

## 6. 判断が要ること

- 2 の見張りの具体値 (たとえば「1 分あたり +4,096 ページが 2 分続く」か「合計 +65,536 ページ」)。以前の基準を緩めることになる。
- 7 の A-2 / A-3 の直し方 (履歴のツール結果を短くするか、1 ターンの読む量を制限するか)。6 の結果を見てから。

## 7. この間の進め方の誤り (記録)

- 会話の中身を読まずに、トークン数と Swapouts だけで打ち手を選んだ。20 §3-4 で「記録だけ」にした同じ URL の再取得が、超過の最大の件 (ja-howto) の中身だった。
- ページを 2,000 字にしたのは、原因を確かめる前の当て推量だった。
- 検査の `answer` 判定が「非空」だけで、ツール呼び出しの XML が回答になっていても合格にした。3 と一緒に「回答に `<tool_call>` / `<function=` を含まない」を判定に足す。
