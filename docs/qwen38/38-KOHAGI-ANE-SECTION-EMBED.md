# 38. 節の埋め込みを ANE で (kohagi + Ruri v3) — 使えるかの確認 (途中)

書いた日: 2026-09-18。表記は 01 と同じ (実測 / 導出 / 未確認)。§2 は QFN なし、§2-5 は再起動後に QFN と同居させた測定。§2-6〜2-8 は同じ日の続き (QFN なし)、§2-9 は 2,048 版を QFN と同居させた測定。

## 0. なぜこれを確かめるか

- 目的は 37 と同じ。QFN の 1 問の待ち時間を、往復の数を減らして縮める。
- 変更案の候補 (37 §3-2 に未追加): **アプリが質問に合う節を選び、検索結果に本文ごと添える。** 今はモデルが「開く → 目次を見る → 節を読む」に往復を使っている (24、34)。その判断をアプリが LLM を使わずに行う。
- 節の選び方に文埋め込みモデルを使う。この文書で確かめるのは、**使えるかどうかだけ** (日本語で動く、RAM、秒数)。他の選び方との優劣は比べない (目的の数字が動くと分かってからの話)。
- 道具はユーザーの指定で [kohagi](https://github.com/takahashim/kohagi) (Ruri v3 を Core ML に変換して ANE で動かす CLI)。ANE で動くので、QFN が使う GPU を取り合わない。

言葉:

- **埋め込み**: 文章を固定長のベクトル (Ruri v3 130m は 512 次元) にしたもの。質問と節のベクトルのコサインで、質問に近い節を選ぶ。
- **Ruri v3**: `cl-nagoya/ruri-v3-*`、日本語の文埋め込みモデル。検索文書には `検索文書: `、質問には `検索クエリ: ` を前に付ける。

### 2-6. プロセスを常駐させたときの 1 ページ (Swift から Core ML を直接)

kohagi v0.6.0 の CLI は stdin を最後まで読んでから埋め込む (1 行ずつ 4 秒おきに送っても、stdin を閉じるまで何も出ない。`--batch-size 1` でも、stdout を pty にしても同じ)。常駐の代わりにはならないので、同じ `.mlmodelc` を Swift から読む測定器を作った。

- `Scripts/qwen38/ruri_embed/main.swift`。`MLModelConfiguration.functionName` で bucket (`seq_64` など) ごとに 1 つずつ読み、`.cpuAndNeuralEngine`。トークナイザは `tokenizer.json` の Unigram を自前で (Viterbi、byte fallback、Metaspace は先頭に ▁ を足さない、`<s> … </s>`)。mean pooling と L2 正規化は kohagi と同じ。
- 照合: 890 節 (§1 の Web 401 + §2-7 の Wikipedia 489) で、トークン ID が HF `tokenizers` 0.23.2 と **890/890 一致**。埋め込みは kohagi の出力とのコサインが最小 0.9999996 (Web 401 節)。
- 一致させるまでに直した 3 点 (アプリに組み込むときも同じ所で間違える):
  1. Swift の `Character` (書記素) で区切ると、結合文字や U+FE0F が前の字とまとまる。Unicode スカラーで区切る。
  2. `JSONSerialization` は文字列の先頭の U+FEFF を落とす。語彙の `"\ufeff"` が空文字になり、`"\ufeff\ufeff"` と衝突していた。`JSONDecoder` で読む。語彙を `String` のキーで引くと正準等価な別の語が同じキーになる (15 組) ので、UTF-8 のバイト列かスカラーで引く。
  3. スコアの和を Float で取ると、同点の分け方 (全角空白 4+8 と 8+4) で HF (f64) と違う方を選ぶ。Double で取る。
- 読み込み: 0.43〜0.45 s (トークナイザ 0.06〜0.09 s を含む)。この測定器の最初の 1 回だけ 13.6 s (ANE 向けのコンパイル、n=1)。
- footprint 33〜47 MB (kohagi は 142 MB)。Swapouts は増えていない。

### 2-8. 2,048 トークンまで切らずに埋め込む

### 2-9. 2,048 版を QFN と同居させる

条件は §2-5 と同じ (Offline 5 問、`--max-rounds 6 --thinking off --context 32768 --repeats 1`、MTP 既定 on、`iogpu.wired_limit_mb=14336`、A1 → B1 → A2 → B2、間 20 s、`Scripts/qwen38/guarded.sh` (`GUARD_LOG`) と `caffeinate -i` の下)。違いは B で流すもの: §2-8 の `ruri_embed` (2,048 版) で Wikipedia 489 節を埋めるのを 2 秒おきに繰り返す (毎回プロセスを起こし直す。1 回の単独は 44.1 s)。

全体:

| セット | 埋め込み | ラウンド | 5 問の合計 | wired の最大 | Swapouts | 埋め込みの回数 | footprint 最大 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A1 | なし | 21 | 664 s | 13.20 GB | +52 | - | - |
| B1 | あり | 19 | 774 s | 14.27 GB | +252 | 16 | 215.5 MB |
| A2 | なし | 19 | 671 s | 13.47 GB | +156 | - | - |
| B2 | あり | 22 | 871 s | 14.41 GB | +132 | 18 | 217.3 MB |

- 見張りは一度も止めていない。
- B2 の N3 だけ QFN の検査が落ちた: `live [round 2 cached 1226 of live 1311]`。ラウンド 1 でモデルが `wikipedia_search` を 2 つ同時に呼んだ回 (このラウンドは shortfall 85)。A1・B1・A2 と §2-5 の 4 セットには出ていない。原因は調べていない。
- ラウンド数と合計時間は §2-5 と同じ理由で、埋め込みの効果として読まない。
