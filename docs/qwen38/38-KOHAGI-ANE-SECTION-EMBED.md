# 38. 節の埋め込みを ANE で (kohagi + Ruri v3) — 使えるかの確認 (途中)

書いた日: 2026-09-18。表記は 01 と同じ (実測 / 導出 / 未確認)。§2 は QFN なし、§2-5 は再起動後に QFN と同居させた測定。

## 0. なぜこれを確かめるか

- 目的は 37 と同じ。QFN の 1 問の待ち時間を、往復の数を減らして縮める。
- 変更案の候補 (37 §3-2 に未追加): **アプリが質問に合う節を選び、検索結果に本文ごと添える。** 今はモデルが「開く → 目次を見る → 節を読む」に往復を使っている (24、34)。その判断をアプリが LLM を使わずに行う。
- 節の選び方に文埋め込みモデルを使う。この文書で確かめるのは、**使えるかどうかだけ** (日本語で動く、RAM、秒数)。他の選び方との優劣は比べない (目的の数字が動くと分かってからの話)。
- 道具はユーザーの指定で [kohagi](https://github.com/takahashim/kohagi) (Ruri v3 を Core ML に変換して ANE で動かす CLI)。ANE で動くので、QFN が使う GPU を取り合わない。

言葉:

- **埋め込み**: 文章を固定長のベクトル (Ruri v3 130m は 512 次元) にしたもの。質問と節のベクトルのコサインで、質問に近い節を選ぶ。
- **Ruri v3**: `cl-nagoya/ruri-v3-*`、日本語の文埋め込みモデル。検索文書には `検索文書: `、質問には `検索クエリ: ` を前に付ける。

## 2. 結果 (実測、M3 Pro 18 GB。2-1〜2-4 は QFN なし)

### 2-1. 動くか

- 動いた。`瑠璃も玻璃も照らせば光る` のベクトルの先頭は `0.00702, -0.03196, …`。README の CPU 出力 `0.006987, -0.032139, …` と近い (全次元の照合はしていない)。

### 2-2. 401 節をまとめて 1 回 (3 回)

| 回 | 実時間 | peak memory footprint | maximum RSS |
| ---: | ---: | ---: | ---: |
| 1 | 6.51 s | 141.8 MB | 376.7 MB |
| 2 | 6.74 s | 143.3 MB | 362.2 MB |
| 3 | 6.75 s | 142.1 MB | 380.9 MB |

- 実時間はプロセスの起動と読み込みを含む。
- 節のトークン数: 中央値 305、最大 512。**512 で切り詰められた節が 98 / 401** (節の最大は 2,795 字)。

### 2-3. 起動と読み込みだけ (質問 1 文、`検索クエリ: `)

1.25 s / 0.72 s / 0.72 s (1 回目は読み込みのキャッシュが冷えていた)。

### 2-4. 1 ページずつ別のプロセスで (36 ページ、各 1 回、間 2 s)

- 実時間の中央値 **0.89 s**、最大 1.62 s (起動と読み込みを含む)。
- 節の数ごと: 1〜6 節 0.77〜0.89 s、8〜19 節 0.86〜1.03 s、24〜25 節 1.25〜1.26 s、37 節 1.40 s、40 節 1.58〜1.62 s。
- 導出: 起動と読み込みの約 0.72 s を引くと、40 節のページで 0.9 s 前後。プロセスを常駐させれば、ページごとの読み込みは払わない (常駐時の実測は未)。

### 2-5. QFN と同居させる (再起動後)

条件:

- QFN: `TsugumiToolLoopCheck` を `--endpoint` なしで (Mac のランナー)、Offline 5 問 (`questions-v2-stage2.json`)、`--max-rounds 6 --thinking off --context 32768 --repeats 1`。MTP は既定のまま on。`iogpu.wired_limit_mb=14336`。
- 同居 (B): QFN の開始と同時に、kohagi で 401 節を流すのを 2 秒おきに繰り返し、QFN が終わったら止める。kohagi は毎回プロセスを起こし直す (§2-2 と同じ 1 回)。
- 単独 (A) と同居 (B) を A1 → B1 → A2 → B2 の順に各 2 セット、間に 20 秒。全部 `guarded.sh` と `caffeinate -i` の下。
- kohagi の各回を、`rounds.jsonl` の started / prefill_s / ended と時刻で突き合わせ、prefill 中・decode 中・またがり に分けた (90% 以上が片方に入れば その側)。
- 再起動後の kohagi 単独: 7.79 s (冷えた状態) / 6.53 / 6.54 / 6.54 s。§2-2 と同じ。

前提の修正: 再起動後の最初の実行で、QFN のランナーが読み込みの直後に Metal の検証で落ちた (`q38_gdn_norm_gate cannot be used to build a pipeline state`)。27B のランナーの追加 (ab8ccf3) でこのカーネルに関数定数 1 (SiLU) が足されたが、`Qwen38Runner` は定数なしでパイプラインを作っていた。`psoKV` (定数付き、1 は未設定 = sigmoid) で作るように直し、`TsugumiKernelCheck` の France decode・France prefill (chunk 4)・Fuji prefill (予算 16、chunk 53) の 3 本が PASS (最悪 8.27e-04 / 8.27e-04 / 1.09e-02、23 の記録と同じ範囲)。

全体:

| セット | kohagi | ラウンド | 5 問の合計 | wired の最大 | Swapouts | kohagi の回数 | kohagi の footprint 最大 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A1 | なし | 18 | 652 s | 13.34 GB | +32 | - | - |
| B1 | あり | 20 | 676 s | 13.60 GB | +184 | 75 | 158.3 MB |
| A2 | なし | 23 | 736 s | 13.09 GB | +144 | - | - |

- Swapouts は 4 セットとも数百ページ (数 MB)。見張りは一度も止めていない。

kohagi の 1 回 (401 節、起動と読み込みを含む):

| セット | QFN の prefill 中 | QFN の decode 中 | またがり |
| --- | --- | --- | --- |
| B1 | 6.85 s (6.74〜7.84、31 回) | 6.99 s (6.82〜7.71、17 回) | 7.11 s (6.73〜8.62、27 回) |

言えること (この 4 セットの範囲で):

- kohagi を QFN と同時に動かしても、スワップは増えず、wired の最大も 13.9 GB までで収まった。
- QFN の prefill は、kohagi が絶え間なく動いている条件で 2〜6% 長くなった。ラウンド 1 の 1,220 トークンで 0.9 s 前後。
- decode の 1 ステップの時間には、単独 2 セットの差を超える違いは出なかった。
- 実際の使い方 (開いたページの節だけを 1 回) では kohagi が動くのは数秒なので、この条件 (絶え間なく流す) より QFN への影響は小さいはず (導出、未測定)。
