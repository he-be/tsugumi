# 24. ページを目次と節で読む (fetch_page / wikipedia_page) と、Qwen3.8 の prefill 進捗

書いた日: 2026-09-15。表記は 01 と同じ (実測 / 導出 / 未確認)。各セル n = 1。
走行の記録は `scratch/qwen38/outline24/` (git 管理外)。

## 0. 結論

1. **Qwen3.8 の prefill 進捗が、終わる寸前にしか出なかった。** `Qwen38Completion` は 2,048 トークンのチャンクが終わるたびにしか `onPrefill` を呼ばず、始める前の報告も無かった。Qwen3.8 の prefill は約 95 tok/s なので 1 チャンク 20 秒強、ツールのラウンドの追加分は 2,048 未満が多く、報告は終わりの 1 回だけになる。Gemma (`CompletionPrefill`) は始める前に `cached / total` を出す。
2. 直した: 始める前に `(cached, total)`、チャンクの中はトランクの層ごと (`Qwen38Runner.forward(onLayer:)`)、数え方は Gemma と同じ絶対位置。チャンク幅は変えていない。
3. **ページを読むツールが、モデルの読み方に合っていなかった** (ユーザー指摘)。`fetch_page` / `wikipedia_page` は先頭から 6,000 字ずつ `from` で送るだけで、見出しは抽出で捨てていた。iPhone 18 の会話 (アプリ、16K) は 15,923 字のページの 11,899 字目まで 2 ラウンドで読み (約 7,100 トークン、prefill 64 秒)、回答に使ったのは 1 回目の先頭にほぼ揃っていた。`from` のたびにページを取り直してもいた。
4. 作り直した (ユーザーの選択: 目次 + 節、Gemma と Qwen3.8 の両方): 短いページは全文、長いページは **目次 (番号・名前・字数) と冒頭の節**、`sections` に番号を渡すとその節を返す。取得したページはターンの間アプリが持つ (`WebPageCache`)。
5. `sections` は文字列 ("2,3")。整数の配列だと Qwen3.8 の描き直し (`[2,3]`、GEN-8) が HF の `tojson` (`[2, 3]`) と 1 文字ずれた (§2-3)。
6. **それでも Qwen3.8 は `sections` を書けなかった。** Qwen の呼び出し文法が引数をキーの昇順に固定していて、`url` の後に `sections` を足す道が無かった (§3-1)。21・23 の「from を使わない同じ URL の再取得」もこの形。文法を宣言順 (必須が先) にし、描き直しを書かれた順にした (SPEC §12 DEV-15 を更新)。
7. 宣言順にした後の 14 ターン (23 §5 と同じ会話、各 n = 1): 同じ本文の再取得 8 回 → 0 回、`sections` つきの取得 14 回、読んだページの字数 172,169 → 99,183 字、ラウンド 66 → 77 (§3-3)。

## 1. prefill 進捗

| | 前 | 後 |
| --- | --- | --- |
| 最初の報告 | 1 チャンク目の終わり | `runCompletion` の prefill の前 (`done = cached`) |
| チャンクの中 | なし | トランク 48 層の各層のあと (`onLayer`、チャンク末尾の 1 つ手前で止める: `done == total` はアプリが decode 開始とみなす) |
| 数え方 | 今回の追加分の中の位置 / 追加分の長さ | プロンプト全体の位置 / 全体の長さ (`CompletionPrefill` と同じ) |

`TsugumiToolLoopCheck` に `progress` 判定を足した: prefill が 5 秒を超えたラウンドは、開始 1 秒以内に cached の位置から報告が始まり、報告の間が 5 秒を超えず、最後が `done == total`。

## 2. 目次と節

### 2-1. 形

- 抽出 (`HTMLTextExtractor`) は `<h1>`〜`<h6>` を行として残し、行番号を `headingLines` に持つ。`text/markdown` は `#` 行。Jina Reader (`X-Return-Format: text`) と Wikipedia の索引 (cirrus の平文、見出しなし) は見出しを持たない。
- `PageOutline`: 見出しで節を切る。本文の無い見出しは次の節の名前に連ねる。150 字未満の節は次の節に合流。長い節 (部分の大きさの 4/3 超) は行末 → 文末 → 空白で部分に切る (部分は 1,500 字、ページが長ければ 全体 / 40 まで、上限は 1 回の上限の 3/4)。40 節を超えたら隣り合う小さい組から合流。見出しの無い部分は書き出し 30 字、切った部分は「見出し (i/n) 「書き出し 24 字」」を名前にする。
- 全文を返す条件: 全体が min(3,000, 1 回の上限) 字以下、または 1 節。
- 1 回目: 「本文は全 N 文字、K 節。目次と節 1〜m の本文です。他の節は … sections に番号を渡すと読めます (1 回 L 文字まで)。」→ 目次 → 冒頭の節 (合計 1,500 字まで、少なくとも 1 節) → 次の節。
- `sections`: 番号順に、1 回の上限に収まるだけ返す。出さなかった節・無い番号・次の節を 1 行ずつ書く。無い番号だけならエラーとして目次を返す。
- システムプロンプト (`search-tool-prompts.json`) の読み方の説明と、URL の事前取得の説明を合わせた。

### 2-3. 配列の引数と上流の描画

`sections` を `{"type":"array","items":{"type":"integer"}}` で宣言すると、Qwen38ToolLoopPromptTests の HF 描画一致が t2r2・t3r1 で落ちた: 過去の呼び出しの値を Swift は `[2,3]`、HF の `tojson` (`json.dumps`) は `[2, 3]` と描く。Qwen3.8 の文法も空白なしを強いる (GEN-8)。宣言と 1 要素の配列は一致する。**文字列にして避けた**。非文字列の引数を持つツールで同じずれが出る (Ornith の tojson の件と同根、未修正)。

## 3. 実モデル (Qwen3.8 32K、Online)

23 §5 と同じ 6 会話 + iPhone 18 の 1 問 (`scratch/qwen38/outline24/conversations.json`)、32K、q8_0、MTP on、ページ上限 6,000、公式サンプラ、`--web-store` (23 の記録の写しから再生、足りない分は記録)、各 n = 1。

### 3-1. 辞書順の文法のまま (`qwen32k`、途中で止めた)

ja-news 3 ターン + en-swift 1 ターンで `sections` は 0 回。en-swift 1 ターン目は同じ URL を `sections` なしで 2 回続けて呼び、同じ目次と節 1 を 2 回受け取った (2 ページとも)。

原因: `QwenToolCallGrammar` は引数をキーの昇順でしか書かせない (Gemma の `dictsort` の決まりを当てていた、SPEC §12 DEV-15)。`sections` も `from` も `url` より昇順で前なので、`url` から書いたモデルにはその後に足す道が無く、`url` だけの呼び出し = 同じページの取り直しになる。Qwen のテンプレートは `arguments|items` (呼び出しの順) で描く。21・23 の「from を使わない同じ URL の再取得」(A-1) も同じ形 (23 の記録の `from` つき 5 回は、どれも昇順どおり `from` を先に書いていた)。

### 3-2. 直した (ユーザーの選択: 宣言順)

- 文法: 必須を先、次に省略可、それぞれ宣言の原文 (`parametersSource`) の順、原文が無ければ昇順 (`QwenToolDeclaration.parameterOrder`、llama.cpp の json-schema-to-grammar と同じ規則)。
- 解読器: `argumentsJSON` をモデルが書いた順で出す。
- 描き直し: `HistoricalToolCall.argumentsSource` (アプリは `argumentsJSON`、OpenAI 経路はクライアントの `arguments` の文字列) の順で、swift-jinja に順序つきの `Jinja.Value.object` を渡す。原文が無ければ文法の順。
- Package.swift に swift-jinja / swift-collections を直接の依存として足した (版は swift-transformers 経由ですでに解決済みのもの)。
- テスト: `QwenChatGrammarBuilderTests` (必須が先・宣言の原文の順)、`QwenToolCallParserTests` (書かれた順の JSON と描き直しの順)、`Qwen38ToolLoopPromptTests` (`{"title":…,"sections":"2,3"}` の呼び出しを含む 6 要求が HF 描画と一致、INV-1)。全 1,591 件緑。

## 5. 残り

- **Gemma は目次を受け取ってもほとんど節を読まずに答える** (§4、15 回中 1 回)。前の作りの 6,000 字と比べて根拠が減っているかは未測定。
- 上限のラウンド (`tool_choice: none`) で Qwen3.8 が `<tool_call>` を本文に書く (A-4)。
- 要約だけのターンにも Online の強制検索が掛かる。
- 全文で返した短いページに `sections` を付けた呼び出しに、全文であることを言わない。
- 履歴のツール結果 (A-2)。
- OpenAI 経路の宣言は原文を持たないので、Qwen の引数の順は「必須が先・昇順」になる。
- 非文字列の引数の描き直しが HF の `tojson` と空白で違う (§2-3)。
- Jina Reader は見出しを渡していない (`X-Return-Format: text`)。Wikipedia の索引も見出しを持たない。
- `Scripts/app/smoke_decode.py` の近似ツールは `from` のまま。
