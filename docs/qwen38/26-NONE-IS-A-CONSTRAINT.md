# 26. 対症療法をやめる: `tool_choice: none` はサンプラの拘束、ツールループの残件を原因側で直す

書いた日: 2026-09-15。表記は 01 と同じ (実測 / 導出 / 未確認)。
これは方針書で、実装はまだ無い。実施の記録は 27 以降に書く。

## 0. 結論

1. **A-4 (上限後の `none` のラウンドで `<tool_call>` が回答として表示される) は直っていない。** 21 §8 の上限の行、25 の `toolBudgetNotes` (残り回数・文脈の行) はどちらもプロンプトに文を足して確率を下げる対症療法で、実際の上限のラウンドでは行があっても P(`<tool_call>`) = 0.30 (25 §3、実測)。公式サンプラなら約 3 回に 1 回再現する。
2. **原因は `none` の定義にある。** 今のコードは `none` = 「文法なし」(SPEC GEN-4、`QwenChatGrammarBuilder` / `ChatGrammarBuilder` の `.none` は `nil` を返す)。宣言はプロンプトに残す設計 (21 S-1、cache のため) なので、モデルはツールを見ながら何にも拘束されていない。これは Qwen 固有ではなく Gemma も同じ経路で、同じ穴がある (コードから導出、Gemma で発現した記録は無い)。
3. **あるべき状態: `none` は「呼ばないでほしい」というお願いではなく、「呼べない」という保証。** サンプラがツール呼び出しの開始トークンを禁止する。これ以後、プロンプトの文言や設定の分岐で確率を下げる案は出さない。
4. 修正は 3 つ。順に (1) `none` の拘束 (§2)、(2) `toolBudgetNotes` の rounds / context の撤去 (§3、判断待ち)、(3) 本文の後の `<tool_call>` の描き直しで cache が外れる INV-1 の穴 (§4)。S-2 は報告の分類だけ (§5)。
5. 触らないもの (§6): チャンク境界で logits が動く件、描き直しと記録の 1 トークン差、n = 1 の数字。アプリの不具合ではなく、上の判断も変えない。

## 1. 何が対症療法だったか

| 段 | やったこと | 結果 |
| --- | --- | --- |
| 21 S-1 | `none` でも宣言をプロンプトに残す (cache が先頭から外れるため) | 正しい。ただしモデルがツールを見たまま拘束なしになり A-4 が表に出た |
| 21 §8 の 4 (A-4) | 上限のラウンドの最後の結果に「上限に達した」の 1 行 | 上限の 1 ラウンド前に置けば 0.0004、実際の上限のラウンドでは 0.30 (25 §3、実測) |
| 25 案 2 (`rounds`) | 毎ラウンド残り回数を伝える | 残り 1 回でも 0.88〜0.95。効かない (実測) |
| 25 案 3 (`context`) | 加えて文脈の残りを伝える | 実際の値で 0.65〜0.87。効いたのは「残り 484」と嘘を書いた場合だけ (実測) |

共通するのは、サンプラに拘束が無いことを、モデルに読ませる文で埋めようとしたこと。行はモデルへの事実の通知としては残してよい (上限の 1 行) が、保証にはならない。

## 2. 修正 1: `none` をサンプラで拘束する

### 2-1. 規則

- `tool_choice: none` のとき、ツール呼び出しの**開始トークン**を候補から落とす。Qwen は `<tool_call>` (`QwenToolCallMarkers.toolCallStartTokenID`)、Gemma は `<|tool_call>` (`ChatGrammarMarkers.toolCallStartTokenID`)。両方とも文法・復号器がすでにトークン id で扱っている (DEV-22)。
- それ以外は無拘束。終了は常に可 (`mayEndHere = true`)。閉じトークンは禁止しない (開きが無ければ復号器は閉じを見ない。閉じだけを書いた場合の復号器の扱いは未確認、§2-3 の検査に含める)。
- 宣言はこれまでどおりプロンプトに残す (S-1 の判断は変えない)。
- 綴りの列 (`<`, `tool`, `_`, `call`, `>`) は禁止しない。復号器は id でしか呼び出しを認識しないので、綴られても本文の文字として表示されるだけで、呼び出しにはならない (DEV-22 と同じ理由)。表示の問題として残るかは §2-3 の実測で見る。
- `response_format` があるときは今までどおり response format の文法が勝つ (GEN-12)。`none` の拘束はツール文法の枠 (`toolConstraint`) の中の話。

### 2-2. 変更点

| 場所 | 変更 |
| --- | --- |
| `Sources/Tsugumi/Runtime/Generation/` | `GenerationConstraint` の実装を 1 つ足す (禁止する id の集合を持ち、`allows` はその id 以外を真、`fillAllowedMask` は全部真にして id だけ偽、`accept` は何もしない、`mayEndHere` は真) |
| `QwenChatGrammarBuilder.toolConstraint` / `ChatGrammarBuilder.toolConstraint` | `.none` で `nil` ではなく上の拘束を返す。`ChatGrammarConstraint` は `grammar: String` が必須で文法テキスト前提なので、文法かトークン禁止かのどちらかを持てる形に広げる (plan 側で `ConstraintGate` に渡す対象を選ぶ)。`selected.isEmpty` の `guard` は `none` より後なので影響しない |
| `QwenGenerationPlan` / `ServerGenerationPlan` | 拘束を `ConstraintGate` に渡す経路は既存 (`Qwen38Completion` 202 行、`SpeculativeCompletion`、`QwenSpeculativeDecode`、`RawCompletion`)。MTP の投機経路も同じ gate を通るので、ドラフトの検証にもそのまま効く (導出、§2-3 で確認) |
| `docs/serving/SPEC.md` GEN-4 | 「`none` は文法なし」を「`none` は開始トークンの禁止」に改める。R4 (黙って自由生成に落とさない) と整合する |
| `AppModel.startNextRound` のコメント | 「`none` is what stops a call」は拘束が入って初めて真になる。上限の 1 行は通知として残す |

### 2-3. 検査 (長い会話を流さない)

1. 単体: `QwenChatGrammarBuilderTests.none_has_no_grammar` / `ChatGrammarBuilderTests.GEN_4_none_has_no_grammar` を書き換える。`none` の拘束が開始 id だけを落とし、他の全 id と終了を許すこと。宣言が空の `none` でも同じ。
2. 分岐点 (25 §2 の道具): M6 の k6 「上限の行 (アプリの実際)」を禁止つきで測る。合格は P(`<tool_call>`) = 0 と、公式サンプラの引き 2 回が本文 (`## M6 …`) で始まること。`--qwen38-branch-probe` に拘束を渡す口が要る (manifest か引数)。
3. 投機: 同じ分岐点を MTP on で引き、`<tool_call>` が出ないこと。
4. `TsugumiToolLoopCheck` の answer 判定 (`<tool_call>` / `<function=` を含まない) は既にある。25 の発端の会話 (ja-m6ssd、16K、`--web-store`) を 1 本だけ流し、上限の後の `none` のラウンドが回答で終わること。ここは再現率 0.3 の事象なので n = 1 の合格は補助で、判定は 2 と 3。
5. Gemma: 同じ単体テストと、Gemma のツールループ検査 1 本 (`none` のラウンドが起きる会話) で回答で終わること。

## 3. 修正 2: `toolBudgetNotes` の rounds / context を撤去する (判断待ち)

- 25 の実測で rounds は効かず、context は実際の値では弱い。§2 が入れば両方とも役を失う。
- 3 モードの設定として残すと、根拠の無い分岐が製品に生える。UI には出ていない (`AppModel.toolBudgetNotes` と `TsugumiToolLoopCheck --budget-notes` だけ) が、`AppModel` の公開プロパティなのでいずれ設定に出る形をしている。
- 残すのは上限の 1 行 (`roundBudgetReachedNote`) だけ。これはモデルへの事実の通知で、§2 の拘束と役が違う。
- ユーザーの選択で入れたものなので、撤去は判断を仰ぐ。撤去する場合は `AppToolBudgetNotes`、`roundBudgetNote`、テスト `budgetNotesGoOnEachRoundsLastResult` / `budgetNotesGroupDigitsAndStopAtZero`、`--budget-notes` を消し、25 §1 に撤去の旨を追記する。

## 4. 修正 3: 本文の後の `<tool_call>` の描き直し (INV-1 の穴)

### 4-1. 事実 (21 §9、実測 n = 1)

en-swift 2 ターン目 2 ラウンド目で、1 ラウンド目の生成は本文 `…再取得します。` の後に改行 1 つで `<tool_call>` を書いたが、描き直しは改行 2 つを置く。server は `diverged at=10582` で分岐し、チェックポイント 10,006 から 1,233 トークンを prefill し直した。

原因は上流テンプレートの規則: assistant の `content` が空でなければ `'\n\n<tool_call>\n<function='` を置く (`chat_template.jinja` 127〜128 行)。モデルは改行 1 つで書く。復号器が本文の末尾の改行をどう持つかは未確認 (`QwenToolCallParser` は呼び出しの本体だけを trim する)。

### 4-2. あるべき状態

INV-1 は「次のラウンドのプロンプトは、前のラウンドのプロンプト + 生成の厳密な延長」。テンプレートの正規形とモデルの書き方が違う場面では、**同じターンの中でアプリ自身が生成した assistant の手番は、生成した文字列 (またはトークン列) そのものを置く**のが原因側の直し方。引数の順序を `argumentsSource` で通したのと同じ考え (24、DEV-15)。テンプレートの正規形に寄せる (改行を足して描く) のは、モデルが次にどう書くかに依存するので対症療法になる。

### 4-3. 判断点

- 生成した文字列を置く範囲: ターンの中の continuation (`outputContinuationTurns`) だけか、履歴 (`chats.json`、文字列で保存) にも及ぼすか。履歴はターンをまたいで描き直されるので、チェックポイント (18) の位置との関係を見て決める。
- OpenAI 経路 (クライアントが `content` と `tool_calls` を送り返す) は生成物を持たないので、テンプレートの正規形しか描けない。ここは llama.cpp と同じ挙動で、直さない。
- 検査は分岐点の道具でよい: 21 の en-swift の記録から、1 ラウンド目の生成の末尾と 2 ラウンド目のプロンプトの該当位置が一致することを、実モデルなしで (トークン列の比較で) 見る。

## 5. S-2: 文脈の末尾で切れた呼び出しの報告

prompt + 生成 = 文脈になった場合、パーサが malformed と報告する (21 §9、12K の記録)。32K では発生していない。直すなら、生成が文脈の上限で止まった事実を `qwen_structured_output_failure` より先に見て「文脈超過」として報告する。報告の分類だけで、挙動は変えない。§2〜§4 の後。

## 8. これ以後の決まり

- **拘束はサンプラ、通知はプロンプト。** 「呼べない」「止まる」「形式を守る」はサンプラ (文法・トークン禁止) で保証する。プロンプトの文は事実の通知に限り、確率を下げるための文を足さない。
- **設定の分岐を足して逃げない。** 効くか分からない案は `TsugumiKernelCheck` の分岐点で測り、効かなければ製品に入れない。
- **Qwen と Gemma は同じ規則。** 片方だけ直さない。Gemma が基準で、Ornith の実装を根拠にしない。
- **過去の文書は経緯であって正ではない。** 21・25 の「残り」は本書で整理し直した。番号だけを引き継がない。
