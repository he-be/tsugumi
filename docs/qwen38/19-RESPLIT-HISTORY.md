# 19. 長い回答の次のターンで cache が P−1 まで落ちる — 生成の分け方と描き直しの分け方のずれ

書いた日: 2026-09-14。対象は [18](18-PROMPT-CACHE-CHECKPOINTS.md) の `Qwen38PromptCache`。表記は 01 と同じ (実測 / 導出 / 未確認)。

## 0. 結論

1. アプリで、1,640 / 3,700 トークンの回答の次のターンが前のプロンプトの P−1 まで戻り、回答を全部 prefill し直した (`turn-metrics.jsonl`、チャット 35 の 2・4 ターン目、cached 69 / 3,751)。
   18 の場面検査は `max_tokens 64` の短い回答だけで、この形を踏んでいなかった。
2. **原因は、モデルが出したトークンの分け方を描き直しが正準形に戻すこと。**文字列は同じでもトークン列が違い、LCP が回答の途中で切れる。
   server で再現した 2 件はどちらもこれ: `、前回答えた` を生成は `前回`+`答` (247988 96517)、描き直しは `前`+`回答` (95990 97913)。`各項` を生成は `各`+`項` (96139 98547)、描き直しは `各項` (119783)。
   Gemma は KV を分岐点まで戻せるので分岐点から先を払うだけ。Qwen3.8 は GDN の状態を戻せず、分岐点より前の最新のチェックポイント (P−1) まで落ちる。
3. **直し方: 新しいプロンプトが持っている列と「同じバイトを別の分け方で切っただけ」の区間は、持っている列の分け方に置き換える** (`Qwen38PromptCache.aligned`)。
   モデルに入るのはモデル自身が出したトークン列。バイトが違う区間・追加トークン (`<|im_end|>` など) は置き換えない。
4. 修正後、3 会話 × 4 ターン (公式サンプラ、thinking off、`max_tokens 2048`、各 n = 1) で次のターン 9 回すべてが前の回答の続きから (prompt_n 19〜39)。置き換え 6 回、分岐 0 回。修正前の同じ会話 (math-ja) は 3 回中 2 回が P−1 (prompt_n 1,535 / 1,855)。
5. アプリの DecodeService の stderr は `/dev/null` だったので、`~/Library/Application Support/Tsugumi/decode-service.log` に出す (起動ごとに空にする)。

## 1. 形

### 1-1. 置き換え (`Qwen38PromptCache.aligned`)

- 持っている列 `tokens` と描いたプロンプトを先頭から並べ、ID が違う位置で、少ない方のバイト数の側に 1 トークンずつ足していく。
  バイト列 (byte-level のトークン文字列) が途中で食い違ったら、そこで打ち切る。両側のバイト数が揃ったら、その区間を `tokens` の分け方にして先へ進む。
- 片側 32 トークンまで。追加トークン (`isAddedToken`) は区間に入れない。
- 最初の置き換えられない食い違いより後は描いたまま。その前までの置き換えは残る (チェックポイントの判定は置き換えた列で行う)。
- `cache_prompt: false` では何もしない。
- 置き換えた要求は `prompt cache qwen38 resplit spans=N rendered=R prompt=P` をログに出す。生きている状態を見送った要求は `diverged at=… held=[…] prompt=[…]` で分岐点の前後 6 トークンを出す。

### 1-2. 何が変わるか

- 置き換えた後のプロンプトは、テンプレートを描いて符号化した列とトークン単位で違う (バイトは同じ)。モデルが見るのは、自分が前のターンで出した列そのもの。
- 置き換えた後の列で、生きている状態から延長する経路は 18 と同じで、エンジン側の変更は無い。

## 2. 検査

### 2-1. モデル無し (`Tests/TsugumiServer/Qwen38PromptCacheTests.swift`)

追加 3 件。§0-2 の実際の ID と byte-level 文字列を fixture にしている。

| テスト | 見ること |
| --- | --- |
| 分け方の違う描き直しでも生きている状態から | 置き換え前は `restore(5)`、置き換え後は `live(13)` |
| バイトが違うなら描いたまま | 違うバイトは置き換えない。その手前の置き換えは残り、`restore(5)` |
| 追加トークンは置き換えない | `<|im_end|>` の位置で打ち切る |

`Scripts/test.sh --filter "Qwen38|PromptCache|DecodeService"`: 48 件緑。

### 2-2. server (`Scripts/qwen38/cache_turns.py`、`scratch/qwen38/cache19/`)

`TsugumiServer --model ~/LLM/Qwen3.8-Flash-Next-DS4-IQ2 -c 12288 --draft-block-size 2`。persona の 1 行を system に置き、user 発話 4 つを、その場で出た回答を履歴に戻しながら流す。
判定は各ターンで `cache_n > 前のターンのプロンプト長`。

| 会話 | ターン | 修正前 cache_n / prompt_n | 修正後 cache_n / prompt_n | 前の回答 (修正後) |
| --- | ---: | ---: | ---: | ---: |
| math-ja | 2 | 1,815 / 21 | 1,481 / 21 | 1,412 |
| math-ja | 3 | **1,835 / 1,535** | 2,806 / 19 | 1,305 |
| math-ja | 4 | **3,369 / 1,855** | 4,872 / 34 | 2,048 (length) |
| code-en | 2 / 3 / 4 | — | 1,603 / 30、3,680 / 29、5,313 / 29 | 1,517 / 2,048 / 1,605 |
| explain-ja | 2 / 3 / 4 | — | 2,075 / 39、3,689 / 28、5,489 / 31 | 2,018 / 1,576 / 1,773 |

置き換えは math-ja で 3 要求 (区間 1 / 2 / 2)、explain-ja で 3 要求 (各 1)、code-en は 0。修正後の走行の Swapouts は +80 ページ。
回答は毎回サンプリングなので、修正前と修正後で回答の中身も長さも違う (同じ回答での前後比較ではない)。

## 3. 残り

- Ornith の `QwenPromptCache` も「生きている状態の厳密な延長だけ」なので、同じ落ち方をするはず (未確認)。
- 描き直しが文字列ごと変わる場合 (`content|trim` で端の空白が消える、非文字列引数の `tojson`、17 §3-1) は置き換えの対象外で、今までどおり P−1 または `<tool_call>` の直前に戻る。
- 再生成・止めた後の再生成を、長い回答の後で踏む場面は `cache_turns.py` にまだ無い (18 §4)。
- 置き換えた列からの続きが「置き換えた列を通しで計算した答え」と一致するかの greedy 検査はしていない。延長の経路は 18 §2 と同じ。
- アプリの `decode-service.log` は、組み直した .app で実際に書かれることをまだ見ていない。
