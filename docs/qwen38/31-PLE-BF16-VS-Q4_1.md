# 31. PLE 表の量子化: Q4_1 サイドカーと元の BF16 の比較

実測: 2026-09-17、M3 Pro 18 GB、macOS 15。本体 GGUF・両サイドカー (down / bf16) は既定のまま、KV は Q8_0 (既定)。
比べたのは PLE 表 (`ple.weight`、160 × 320,001,536 行、510 億値) だけ。**各セルは 1 プロンプト 1 回の走行**で、解釈は書かない。
経路は決定的 (同じ腕の 2 回目は max|Δ| 0.000)。

## 0. 結論

1. ds4 の新しい `qwen38-q2` (`antirez/qwen3.8-flash-next-gguf` の `Qwen3.8-Flash-Next-Q2.gguf`、147,207,127,040 B) は、うちの本体 GGUF と同じテンソル 1,255 本 (型・形・相対オフセット) の後ろに、
   `per_layer_token_embd.weight` (BF16、[160, 320001536]、95.37 GiB) を 1 本足したもの。データの開始位置は 256 B 後ろ。
   本体の 4 か所 × 1 MiB の sha256 はうちの GGUF と一致した (全体の照合はしていない)。
2. 最初は 95 GiB を取らず、プロンプトが引く行だけを HTTP の複数レンジで取った (1 本の接続、1 リクエスト 256 レンジ、318,494 行・約 102 MB、約 4 分)。
3. 0 段: Q4_1 の行の相対誤差 ‖q−b‖/‖b‖ は、9 プロンプトとも中央値 0.078、最大 0.094〜0.105、コサインの最小 0.995。
4. 1 段: 下の表。PLE を抜いた腕を物差しとして並べた。
5. 表を全部取った (§4)。2 段 (`--qwen38-branch-probe`、公式サンプラ 16 回): k6-none は両方 16/16 が `<tool_call>`。
   k6-limit は Q4_1 が P 0.6747・7/16、BF16 が P 0.1387・0/16 (§5)。
6. 3 段 (greedy 200 トークン): tool は 85 トークンまで一致。code は 3、explain は 79、long は 47 トークン目で分かれた (§6)。

## 7. 既定の表を BF16 に切り替え (ユーザー判断、2026-09-17)

- サーバーでの確認 (`TsugumiServer --model … -c 4096`、`Q38_SERVER_GREEDY=1`、200 トークン):

| | code と `gen/code-bf16.out` | explain と `gen/explain-bf16.out` |
