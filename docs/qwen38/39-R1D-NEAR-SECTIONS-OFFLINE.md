# 39. R1-d: Wikipedia の検索結果に、質問に近い節を本文ごと添える (PC、Offline)

書いた日: 2026-09-18。表記は 01 と同じ (実測 / 導出 / 未確認)。測定環境は 37 §2 (PC の `qwen3.8-flash-next-q4kxl-32k-instruct-bf16ple`)。

**今の状態 (2026-09-18 追記):** R1-d の前提は「往復は答えのある場所を探すため」だった。40 §8-4 で数え直すと、なし (W1a / W1b) のツールラウンド 80 本のうち 40〜42 本は、今の事実を読んだ後に回っていた。R1-d は事実を読むまでの往復を減らしたが、読んだ後の往復 (19〜24 本) は残った。§4 の「やめる」は変えない。

## 0. 何を確かめたか

- 目的は 37 と同じ。1 問の待ち時間を、往復の数を減らして縮める。
- 変更案 **R1-d**: `wikipedia_search` の結果に、見つかった記事の節のうち **ユーザーの質問に近いもの** を、アプリが選んで本文ごと添える。今はモデルが「記事を開く → 目次を見る → 節を読む」に往復を使っている。その選択をアプリが LLM を使わずに行う。節の選び方は文埋め込み (Ruri v3、Neural Engine)。使えることは 38 で確かめた。
- この文書で見るのは、**往復の数が揺れの幅を超えて減るか**。「なし」の 2 セットは 37 §3-1 W1 の Offline を兼ねる。

## 1. 実装

- `RuriSectionEmbedder` (`Sources/TsugumiApp/Core/LocalWikipedia/SectionEmbedder.swift`)。38 §2-6 の測定器をアプリに移したもの。Core ML の `.mlmodelc` (kohagi が変換した 64〜2,048 の bucket 版、38 §2-8) と `tokenizer.json` を読み、`.cpuAndNeuralEngine` で動かす。プロセスで 1 回だけ読み込む。
- `WikipediaToolExecutor`:
  - ターンの始めの `lookups(prompt:)` で、ユーザーの質問文を保持する (事前の検索は増やさない)。
  - `wikipedia_search` の結果に、検索で見つかった全記事 (設定の 8 件まで) を `PageOutline(text:pageLimit:)` で節に切り、質問 (`検索クエリ: ` 付き) とのコサインが大きい順に、1 回の読みの上限 (6,000 字) に収まるだけ添える (最初の 1 節は必ず、長ければ打ち切り)。同点は検索順・ページ順。記事ごとのベクトルはターン中はキャッシュする。
  - 添えるときは、今の「題名一致なら 1 件目の記事の目次と冒頭を添える」(go) は出さない。
  - 形:

    ```
    質問に近い節 (検索結果の記事から、アプリが質問との近さで選んだもの。近い順):

    [ガソリン税 · 節 3/3] 道路特定財源としては他に自動車取得税、軽油引取税、自動車重量…
    (節の本文)

    [道路特定財源制度 · 節 9/13] …
    (節の本文)

    同じ記事の他の節は、wikipedia_page に題名と sections (節の番号) を渡すと読めます。
    ```
- 設定: `web-search.json` の `sectionEmbeddingPath` (空なら off、既定は空)。`TsugumiToolLoopCheck --section-embed DIR` でその実行だけ on にする。モデルの置き場は `~/LLM/ruri-v3-130m-ane-2048/` (`.mlmodelc` 294 MB と `tokenizer.json`)。
- テスト: トークナイザが 38 §2-6 で直した 3 点 (先頭の U+FEFF、結合文字を 1 文字として扱う、正準等価の畳み込みをしない)、節の並び順と 6,000 字の上限、ターンごとの質問の入れ替え。モデルの置き場があるときだけ、kohagi と同じ値が出ることも確かめる (`SectionEmbedderTests.swift`、`LocalWikipediaTests.swift`)。
  - `TsugumiAppCoreTests` を全部流すと、`AppModelTests.cancelDuringPrefillKeepsPromptSnapshotUntilClear` が落ちる。変更前の HEAD でも全体を流すと毎回落ち、単独では通る (この変更とは関係ない、原因は未調査)。

## 4. 結論: 今の形の R1-d は目的に効かない。やめる

往復の数は減ったが、目的は待ち時間で、それは縮んでいない。

- **実測した時間では長くなった。** PC 上の 1 セットの実時間は、なし 641 / 602 s、あり 712 / 653 s (+8〜11%)。埋め込みの時間 (79.0 / 81.5 s) を除いても 633 / 572 s で、なしとの差は 1〜5% しかない。
- **Mac でも縮まない (導出)。** 1 ターンあたり、33 §1 の Mac の実測値 (1 ラウンドの固定分 中央値 6.3 s、新規トークンは 95 tok/s) とこの測定のトークン数から計算した。

  | 項目 | 1 ターンあたりの差 | Mac の時間 |
  | --- | ---: | ---: |
  | ラウンド | −1.04〜−1.24 本 | −6.6〜−7.8 s |
  | 新しいトークン | +1,027〜+1,996 | +10.8〜+21.0 s |
  | 生成トークン | −25〜−46 | −3〜−6 s (約 8 tok/s) |
  | 埋め込み | | +3.2 s |
  | 合計 | | **+0.5〜+14.5 s** |

- 原因は添え方。検索のたびに 8 記事から最大 6,000 字を足すので、検索結果 1 本が中央値 1,837〜2,002 トークンから 4,738 トークンになった。減った往復で読まずに済んだ分より、足した分が多い。N2 (もともと検索 → 回答の 2 ラウンド) は増えただけ (新しいトークン 3,605 → 9,640)。
- 正答が 25 / 25 で変わらなかったことは、採る理由にならない (なしも 25 / 25)。
- この結論を出した時点で、初稿は「待ち時間が縮むかは Mac で測るまで分からない」として M に進む提案をしていた。上の計算に要る数字は手元にそろっていたので、これは結論の先送りだった。

実装 (`sectionEmbeddingPath`、既定は空で off) はコードに残してある。消すかどうかはユーザーが決める。
