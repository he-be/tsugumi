# 27. M7 の結果 — 32 スロット (16GB Mac) の verify

測定: 2026-08-19、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3。
対象モデル `scratch/gemma4-qat.gturbo` (drafter 同梱)。触ったファイルは §8。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

M6 までの数字は全部 **80 スロット**で取っている。本書の運用点は
`Scripts/demo/serve.py` が使う **32 スロット / 8192 context** — 16GB の Mac に
載せるための設定である。ここでは M6 までの結論がそのまま成り立たない:
**32 スロットのブロックは GPU ではなく SSD で律速している**。

目標は「画像キャプションで 30 t/s」。**32 スロットでは届かなかった (23.6 t/s)。
48 スロットなら 28.9〜29.9 t/s で、peak は 6.83 GB (16GB 機に収まる)。**
§7 に、どこが壁でなぜ 32 では越えられないかを測った値で置く。

---

## 0. 結論 — 5 つ

1. **32 スロットで 20.8 → 23.6 t/s (+13.4%)** (§2)。同一セッションの交互 A/B
   3 往復、中央値。ブロック 1 回は **99 → 82 ms**、GPU idle は **47 → 33 ms**。
   **出力は 1 バイトも変わらない** (§8)。
2. **48 スロットでは 24.7 → 28.9 t/s (+17%)** (§2)。M6 までの改修が効いていた
   80 スロットと同じ形の運用点で、こちらのほうが改善幅が大きい。
   **採点基準 v1 は 32 スロットで 1.394** (80 スロットの 1.336 より高い、§2c) —
   スロットが少ないほど投機が効く。off 側も I/O 律速で、ブロックは
   k トークンの和集合 1 件で読むぶん**産出あたりの読み出しが少ない**からである。
3. 効いた 3 つは全部**ブロックの verify の中**である (§3〜§5):
   層の expert union を**タイルごとでなく 1 プランで置く**、
   **常駐エキスパートのタイルを先頭に切る**、
   **router の k 行を 1 dispatch に畳む**。
4. **`moe` の 11 ms は「重み帯域の不足」ではなかった** (§6)。
   `moe` の時間は**エキスパート数ではなく (token, expert) ペア数に比例する**
   (bs=2/4/6 で 0.027 / 0.029 / 0.031 ms/ペア、**実測**)。
   ロード幅・活性化の再ロード・int4 展開の巻き上げを 3 つとも試したが
   **GPU busy は 1 ms も動かなかった** — 25-M5.6 §5 が置いた床 (16 ms) の
   導出そのものが違っている。
5. **32 スロットの壁は expert I/O である** (§7)。ブロック 1 回が SSD から
   **469 MB** 読む (48 スロットでは 216 MB)。この 469 MB は、層の依存関係が
   許す範囲でしか GPU 仕事と重ならない。**ホスト往復 (idle) の残り 33 ms は
   ほぼ全部この読み出しの露出分**で、`moe` を速くしても減らない。

## 1. 測り方 (**実測**)

条件は 25-M5.6 §2 と同じゴールタスク (`bench/mtp_goal_prompt.json` /
IMG_2112 / Reasoning ON / temp 0 / 200 tok / bs=4) で、**スロットだけ 32**、
context は demo と同じ 8192。3 つの改修はすべて env で個別に落とせるので
(M4.5 系の規約どおり)、**同一セッション・同一バイナリの交互 A/B** で取る
(プロセスは実行ごとに分かれる。切り替えはプロセス起動時の env):

```
TF_MTP_ROWS_LAYER_PLAN=0 TF_MTP_ROWS_RESIDENT_FIRST=0 TF_MTP_ROWS_ROUTER_FOLD=0
```

ブロック 1 回の内訳は `TF_PREFILL_HOST_PROFILE=1 TF_PREFILL_GPU_PROFILE=1` の
per-block 行の中央値 (温まっていない先頭 10 ブロックを捨てる)。

> **セッションを跨いだ比較はしていない。**同じコマンドの t/s が日をまたがず
> 20.3〜21.3 の幅で動く (ページキャッシュの温まり方)。判定はすべて交互 A/B。

## 3. 層の union を 1 プランで置く (**実測**、コード)

18-M4.6 が入れた lookahead は、層のタイル (エキスパート 8 個ずつ) を
**タイルごとに** `planRoutedExpertsIfPossible` に通していた。タイル 1 のプランは
**タイル 2 が要求するエキスパートを知らない**ので、LFU の追い出し候補として
それを選べてしまう。層は同じラウンドの中でそれを読み直す。

トレース再生で先に見積もった (**導出**、`bench/expert_sim.py` の追い出し規則を
そのまま使った机上計算):

| k | 1 プラン | タイル 8 個ずつ | 比 |
| --- | ---: | ---: | ---: |
| 2 | 39.63 ミス/産出tok | 41.31 | 1.042 |
| 4 | **39.78** | **46.47** | **1.168** |
| 6 | 40.45 | 51.81 | 1.281 |

実機では **hit 74.2% → 76.4%** (ミス 10,904 → 9,984、**−8.4%**)。
`RoutedExpertFetchPlan.slice` を足して、**プランは層で 1 回、fetch はタイルごと**に
した (タイル別に投げるのは、常駐だけのタイルを先に GPU に渡すため — §4)。

> **ミスが 8% 減っても壁時計はほとんど動かない** (**実測**、単独 A/B で +0.2〜1.7%、
> ノイズと同程度)。§7 のとおり読み出しは**帯域より待ち時間**で決まっているので、
> バイト数を数 % 削っても露出時間は比例して減らない。この改修の価値は
> **§4 と組んだときに「常駐」の側が厚くなること**にある。

## 4. 常駐エキスパートのタイルを先頭に切る (**実測**、コード) — 効いた本体

タイルは `groupTokenExpertPairs` が**物理オフセット順**に 8 個ずつ切っていた。
32 スロットの層は 19 エキスパート中 5 個くらいがミスなので、
**どのタイルにもミスが 1〜2 個混じる**。タイルは自分の fetch を待ってから
encode されるので、**層の最初の読み出しが返るまで GPU に渡す仕事が 1 つもない**。

やったこと: ブロック経路では、グルーピングの**ソートキーの最上位に「常駐か」**を
足し (`nonResidentSortBit`)、常駐の個数のところで**タイルの切れ目を強制する**
(`tileBreakAfterGroup`)。結果、層のタイルは

```
[常駐 8][常駐 6]        … 読み出し無し。fetch を待たずに encode して commit
[ミス 5]               … ここで初めて待つ
```

となり、**層の routed 仕事の 3/4 が読み出しと重なる**。
`tileOrder` は元から「ミスの少ないタイル順」なので、並べ替えはそのまま効く。

| (32 スロット、単独 A/B) | off | **on** |
| --- | ---: | ---: |
| decode t/s | 20.7 | **22.8** |
| ブロック 1 回 | 100 ms | **89 ms** |
| GPU idle | 46 ms | **35 ms** |
| `wait.front` | 39 ms | **26 ms** |

**重ねられる上限はここで使い切っている** (**導出**): `moe` は 28 ms / 558 エキスパート
= 0.05 ms/エキスパート、層あたり常駐 14 個で **0.7 ms**。同じ層の fetch は
32 スロットで **1.5 ms** (46 ms / 30 層)。**GPU 側に 0.7 ms しか無いので、
残り 0.8 ms は原理的に露出する。**層をまたいで先に読むことはできない
(層 L+1 のルーティングは層 L の出力が要る)。

## 5. router の k 行を 1 dispatch に畳む (**実測**、コード)

ブロックの router は **decode のカーネルを行ごとに k 回**呼んでいた
(16-M4.5-PLAN §4: 「ブロックのエキスパート選択を decode の選択と同じにする」ため)。
k=4 で層あたり 8 encoder、ブロック 1 回で **240 dispatch**。
router の重みは 720 KB しかないので、**これは重みの帯域ではなく dispatch の値段**。

`router_gemv_gemma4_bf16_rows` / `router_topk_select_k8_rows` を足した。
**行はグリッドの y に置くだけ**で、1 行が使う threadgroup とレーンの配置は
以前と同じ — つまり**行ごとの総和の順序が動かない**ので、
16-M4.5-PLAN §4 が守りたかった性質 (競り合ったときのエキスパート選択が
decode と同じ) はそのまま残る。dispatch は **240 → 60**。

| | off | **on** |
| --- | ---: | ---: |
| 48 スロット t/s | 26.9 | **29.7** |
| 32 スロット t/s | 23.9 | **24.9** |
| GPU busy (48) | 51 ms | **47 ms** |
| `attn` 段 (内訳、`post` を含む) | 15 ms | **12 ms** |

## 6. 効かなかったもの — `moe` の 11 ms (**実測**)

25-M5.6 §5 は残りの 1 番目に **`moe` 27 ms 対 床 16 ms** を置いた。
床は「607 エキスパート × 3.72 MB = 2.26 GB / 135 GB/s」という**重み帯域の**計算である。
**この床の立て方が違っていた。**

**`moe` はエキスパート数ではなくペア数に比例する** (**実測**、48 スロット、
同一プロンプト):

| bs | エキスパート/ブロック | ペア/ブロック | `moe` | ms/エキスパート | **ms/ペア** |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | 371 | 480 | 13 ms | 0.035 | **0.027** |
| 4 | 558 | 960 | 28 ms | 0.050 | **0.029** |
| 6 | 721 | 1440 | 44 ms | 0.061 | **0.031** |

重み帯域で律速しているなら ms/エキスパートが一定になるはずで、そうなっていない。
**行あたりの仕事で律速している。**そこで rows カーネルの行側を 3 通り削ったが、
**GPU busy はどれも 1 ms も動かなかった** (**実測**、48 スロット、busy 47〜48 ms):

| 試したこと | 期待 | 結果 |
| --- | --- | --- |
| 重みを 2 回の 16bit ロード → **1 回の 32bit ロード** (`.gturbo` の sub-tensor は実際には 16B 整列、§9) | ロード命令が半分 | **不変** |
| **1 simdgroup が出力 2 行**を持つ (活性化のロードが半分。k=4 では活性化 8 ロード対重み 1 ロード) | ロード量 −40% | **不変** |
| int4 の展開を**行ループの外に巻き上げ** (k=4 で展開 64 回 → 16 回) | 命令数 −30% | **不変** (コンパイラが既にやっていた) |

3 つとも**戻した** (コードは元のまま)。
**未確認**: 何で律速しているか。命令数からの見積もり (**導出**) は
ブロック 1 回で約 6 ms、DRAM からの見積もりは約 15 ms、実測は 28 ms。
どちらの見積もりにも合わないので、次に見るなら Instruments の GPU カウンタで
occupancy と stall 理由を取るところから (ここでは取っていない)。

## 7. 32 スロットの壁 — SSD (**実測** + **導出**)

改修後のブロック 1 回 (32 スロット) は **call 82 ms = busy 49 + idle 33**。
idle 33 ms はほぼ全部 expert の読み出しの露出分である。

**読む量** (**実測**): ブロック 1 回で 126 ミス × 3.72 MB = **469 MB**。
産出は 2.703 トークンなので **174 MB/トークン**。

**読める速さ** (**実測**、`packed_experts/layer_*.bin` を直接 pread するプローブ。
1 層ぶんのミスをまとめて読む形):

| 同時に読むエキスパート数 | 中央値 | 実効帯域 |
| ---: | ---: | ---: |
| 2 | 1.50 ms | 4.94 GB/s |
| 4 | 2.29 ms | 6.49 GB/s |
| 8 | 3.34 ms | 8.90 GB/s |
| 4 (各 4 分割 = 深さ 16) | 2.15 ms | 6.91 GB/s |

**分割してキューを深くしてもほとんど増えない** (6.49 → 6.91 GB/s)。
32 スロットの層は平均 **4.2 ミス** (126 / 30 層) で、プローブの「4 ミス = 2.29 ms」に対し
**実機の fetch は層あたり 1.5 ms** (46 ms / 30 層) — つまり**実機のほうが速い**
(ミスの一部がページキャッシュに当たっている)。**読み出し側に大きな余地は無い。**
実際、`bench/expert_sim.py` の追い出し規則を最適置換 (Belady) に置き換えても
ミスは 39.8 → 30.5 / 産出tok にしか下がらない (**導出**) ので、
ポリシーを詰めても 2 割強である。

**予測はできない** (**実測**、トレース再生): あるラウンドのミスのうち、
**直前のラウンドで要求されていたものは 0.0%**、5 ラウンド以内で 26%、
10 ラウンド以内で 47%。ミスとは定義上「最近使われていないもの」なので、
直近の履歴からの先読み (RDADVISE) は当たらない。

**スロットを増やすと消える** (**実測**):

| スロット | decode hit | ミス/ブロック | 読む量/ブロック | t/s (after) | peak |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 32 | 76.4% | 126 | 469 MB | **23.6** | 5.09 GB |
| 48 | 87.9% | 58 | 216 MB | **28.9〜29.9** | 6.83 GB |
| 64 | 93.7% | 36 | 135 MB | 28.5 (改修前) | 8.67 GB |

**48 → 64 で速くならない** — 48 スロットで I/O の壁は消えていて、
そこから先は §5/§6 の GPU 側 (busy 47 ms) が決めている。

> **結論 (導出)**: 「32 スロットで 30 t/s」は、この機械では verify 経路の改修では
> 届かない。30 t/s = 33 ms/トークンに対し、32 スロットは**トークンあたり 174 MB を
> SSD から読む**。層の依存関係 (ルーティングは前層の出力が要る) が許す重なりは
> §4 で使い切っていて、残り 33 ms/ブロックは露出したままである。
> **16GB 機で 30 t/s を狙うなら 48 スロット** (peak 6.83 GB) が運用点で、
> 32 スロットのままなら 23.6 t/s が現状の値である。
> demo の既定 (`Scripts/demo/serve.py` の `EXPERT_CACHE_SLOTS`) は**変えていない**
> — メモリ予算の判断なので、変えるかどうかは使う側の選択にする。
> 試すための口だけ足した: `python3 Scripts/demo/serve.py --expert-cache-slots 48`
> (既定は 32 のまま)。

## 8. 正しさ (**実測**)

**ゲート 1 (出力一致) — 3 つの改修は 1 バイトも変えない。**
同じプロンプト (120 tok、32 スロット、bs=4) を 4 通りで回して md5 が一致:

| LAYER_PLAN / RESIDENT_FIRST / ROUTER_FOLD | md5 |
| --- | --- |
| 0 / 0 / 0 | `f7fa102a…` |
| 1 / 0 / 0 | `f7fa102a…` |
| 1 / 1 / 0 | `f7fa102a…` |
| 1 / 1 / 1 | `f7fa102a…` |

理由 (**導出**): 層のプランは**どのスロットに置くか**を変えるだけ、
タイルの切り方は**どの dispatch がどのペアを持つか**を変えるだけ
(ペアごとの算術と `routePartials` の書き込み先は同じ)、
router の畳み込みは**行ごとの threadgroup とレーン配置を保つ**。

**`--verify-block` は 25-M5.6 と 1 桁も変わらない** (**実測**、k=4 / 8 ラウンド):
**12 中 9 PASS / 3 FAIL**、落ちる 3 本も落ち方も同じ
(`argmax k=4` と `greedy` が **pos 25 で block=2897 / scalar=11442、margin 1.0e-3**、
`wide-vs-width1` が 3.170 対 tol 3.0)。`logits k=4` の worst も **1.932e-02** で
25-M5.6 の 1.9e-2 と同じ。**新規失敗ゼロ、数値の移動もゼロ** — 本書の 3 つは
ブロックの算術を 1 つも触っていない、という §8 の主張の裏取りである。
(25-M5.6 §4 のとおり、この 3 本は**通ったことにしない**。)

| ゲート | 結果 |
| --- | --- |
| 1. 出力一致 | **合格** (上の md5、4 通りで一致) |
| 3. テキスト回帰 (MTP 無効) | **構造的に不変** (**導出**)。3 つとも `speculativeBlock` の中だけ。router の畳み込みは `speculativeBlock && t <= maxTokens` の枝、残り 2 つは `blockPipeline` の枝 |
| 4. メモリ | peak **5.09 GB** (32 スロット / 8192 context)。新規確保は router logits の 8 KB 化のみ |
| 8. 巻き戻しの検出力 | **合格** (`rewind/*` 4 本とも PASS) |
| 10. 退行なし | 下記 |
