# 32. M8 果実 A の実装 — `down` を崖で 2 分割したら GPU は −7%、壁時計は動かない

測定: 2026-08-19、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3 / Xcode 26.6。
対象モデル `scratch/gemma4-qat.gturbo` (drafter 同梱)、**48 スロット** (32 も §3)、8192 context。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

31-M8-A-ROWS-BENCH §7 の引き継ぎ (「`encodeStreamedRows` の `down` のエンコードを、
行数で 2 つに分けて 2 回呼ぶ」) を実装した。**入った。出力は 1 バイトも動かない。**
`moe` は **30.11 → 27.99 ms/ブロック (−7.0%)** で、これは 8 回の交互 A/B で
分布が重ならない。**それでも t/s は動かない** (−0.2%、ノイズ)。

## 0. 結論 — 5 つ

1. **入った。ゲート 1 は通る** (**実測**、§2)。48 / 32 スロットで回した 34 回すべてで
   出力 md5 が `3eefadf60a5aa49540a4086706d6e5e4`。ビット一致はカーネル単体でも
   固定した (新テスト 1 本、§6)。
2. **`moe` −7.0%、GPU 全体 −4.1%** (**実測**、§3)。順序を入れ替えた ABBA ×4 で
   off 29.71〜30.73 ms 対 on 27.41〜28.76 ms と**分布が重ならない**。
3. **31 §6 が置いた −17% は出ない。−7.0% である** (**実測**)。ただし
   **外したのは計器ではなく積み方**で、production の実形状を測り直すと
   計器は **−2.07 ms/ブロック**を予言し、実測は **−2.12 ms** だった (§4)。
4. **外れた理由は 3 つとも「タイルの実形状」である** (**実測**、§4)。
   - production のタイルは **16 エキスパートではなく 5.68**
   - **タイルの 43% は最大行数が 2 以下**で、そもそも分割が発火しない
   - **ディスパッチを 1 本増やす費用が +2.3%** ある (対照で分離、§3)
5. **壁時計は動かない** (**実測**、§5)。48 スロットのブロックは
   call 94.4 ms のうち fetch 55.0 ms + `wait.front` 30.3 ms で、
   30 §5 が 32 スロットで見た「I/O が床」が **48 スロットでも成り立っている**。
   GPU を 2.1 ms 削っても出る先が無い。

既定は**オン**のまま入れる。出力不変・GPU 単調改善・壁時計中立で、
I/O が床でなくなったときに初めて表に出る種類の改善だからである。
切り分け用に `TF_MTP_ROWS_DOWN_SPLIT` (閾値、`0` で分割しない) を残した。

## 1. 何を入れたか (**実測**)

`PrefillGroupedRoutedMoE.encodeStreamedRows` の `down` のエンコードを、
ブロックの行数で 2 つに割って 2 回呼ぶ。31 §7 の指示そのままである。

- `rowCount <= 2` のブロックはそのバケットの最大行数の PSO、`>= 3` は
  `widestBlock` の PSO。片方が空なら 1 本に戻る (現状と同じ)
- **`local_row` / `pair_start` は触っていない。**ブロックごとに確定済みで、
  2 つのディスパッチが書く `act` の行と `route_partials` の位置は互いに素
- **`gate/up` は 1 本のまま** (31 §4 のとおり崖が無い)
- 閾値は `PrefillGroupedRoutedMoE.rowsDownSplitRowCount` (既定 2)。
  `TF_MTP_ROWS_DOWN_SPLIT=0` は分割前の形そのもので、A/B の off 側はこれである

## 2. ゲート 1 (**実測**)

```bash
TF_MTP_ROWS_DOWN_SPLIT=0 .build/release/TurboFieldfareCLI \
  --model scratch/gemma4-qat.gturbo --messages-file bench/mtp_goal_prompt.json \
  --image sample_imgs/IMG_2112.JPG --image-tokens 280 --thinking on --temperature 0 \
  --max-new 120 --max-context 8192 --expert-cache-slots 48 \
  --verification trusted-install --draft-block-size 4
```

**本書の測定で回した 34 プロセス (48 / 32 スロット、off / on / §3 の対照 nocap、
プロファイル有無を問わず) すべてで md5 `3eefadf60a5aa49540a4086706d6e5e4`。**
`cap` はレジスタ配列の大きさとループ上限を決めるだけなので、31 §6 の
「ゲート 1 は自明に通る」は実測でも成り立つ。

## 3. 速度 (**実測**、`TF_PREFILL_GPU_PROFILE=1`、49 verify ブロック/回の平均)

順序で熱が片側に乗るのを避けるため **off,on,on,off,off,on,on,off の ABBA ×2**
で回した (30 §3 の交互 A/B を順序均衡にしたもの):

| | `moe` | GPU 合計 | t/s |
| --- | ---: | ---: | ---: |
| off (分割しない) | **30.11 ms** | 51.45 ms | 23.60 |
| on (`down` 2 分割) | **27.99 ms** | 49.33 ms | 23.57 |
| | **−7.0%** | **−4.1%** | −0.2% |

`moe` は 8 回の**分布が重ならない** (off 29.71 / 29.71 / 30.24 / 30.73、
on 27.41 / 27.47 / 28.35 / 28.76)。GPU 合計も同じく重ならない
(off 50.86〜52.31、on 48.14〜50.55)。t/s は run 間 ±5% の中で、
off 22.59〜24.56 / on 22.59〜24.33 と**完全に混ざる**。

**32 スロットも同じ形である** (**実測**、ABBA ×1):

| | `moe` | GPU 合計 | t/s |
| --- | ---: | ---: | ---: |
| off | 30.68 ms | 51.53 ms | 20.81 |
| on | **28.88 ms** | 50.03 ms | 20.77 |
| | **−5.9%** | −2.9% | −0.2% |

30 §5 のとおり 32 スロットは I/O がさらに厚いので、GPU の削りは 48 スロット以上に
壁時計から遠い。**48 スロットを先に見るという 31 §6 の順序付けは正しかった**が、
その 48 スロットでも出なかった、というのが本書の結論である。

**ディスパッチ 1 本の費用の分離** (**実測**、off → nocap → on を 3 周):
`nocap` は**分割はするが両方に `widestBlock` の PSO を渡す** = 追加ディスパッチの
費用だけを払って cap の利益を取らない対照である。

| | `moe` | off 比 |
| --- | ---: | ---: |
| off | 30.57 ms | — |
| **nocap (ディスパッチだけ +1)** | **31.29 ms** | **+2.3%** |
| on | 28.46 ms | −6.9% |

**追加ディスパッチは +0.72 ms/ブロック。**ブロックあたり増える encoder は
57 本 (§4) なので **12.6 µs/本**である。cap の利益は総額 −9.2%、
そこからこれを引いた残りが表に出ている −6.9〜7.0% である。

## 4. 31 §6 の −17% が外れた理由 — 3 つとも「タイルの実形状」(**実測**)

`encodeStreamedRows` に計器を 1 本足した
(`TF_MTP_ROWS_DOWN_SPLIT_DEBUG=1`、タイルごとに行数ヒストグラムを stderr へ)。
48 スロット・bs=4 の 1 回分で **1144 タイル / 6560 ブロック**:

| | 実測 | 31 §5 が置いていた値 |
| --- | ---: | ---: |
| タイルあたりエキスパート | **5.68** | 16 |
| エキスパートあたり行数 (平均) | 1.65 | 1.75 |
| 行数の分布 | 1:4036 2:1257 3:818 4:449 | 1:8 2:5 3:2 4:1 |
| タイルの最大行数 | 1:256 2:209 3:341 4:338 | (常に 4 とみなしていた) |
| **分割が発火するタイル** | **57.3%** | (100% とみなしていた) |

5.68 は host profile 側とも独立に一致する (`tiles=100 experts=569`/ブロック、§5)。

**計器を production の形で測り直す** (**実測**、`--moe-rows-bench` を拡張):
タイル幅を振れるようにし、行数の混合を上のヒストグラムの比率で置いた。
µs / 1 タイル (括弧内は µs/エキスパート):

| 幅 | 混合 | 現状 (1 本) | **`down` 2 分割** | 完全バケット化 |
| ---: | --- | ---: | ---: | ---: |
| 4 | 1123 | 188.9 (47.2) | **164.9 (41.2)** | 179.0 (44.8) |
| **6** | 111123 | **261.2 (43.5)** | **225.1 (37.5)** | 244.3 (40.7) |
| 8 | 11112234 | 408.9 (51.1) | **354.2 (44.3)** | 390.8 (48.9) |
| 16 | 1111111111222334 | 737.4 (46.1) | **618.6 (38.7)** | 652.4 (40.8) |

2 つ出てくる:

1. **崖はタイル幅に依らない。**幅 6 でも −13.8% で、31 §4 の崖は 16 エキスパートの
   人工物ではない。**31 §6 のカーネル側の主張はそのまま正しい。**
2. **完全バケット化は 2 分割より遅い** (幅 16 で 652.4 対 618.6)。31 §6 は
   (cap, r) のグリッドを足し算して 597.3 を**導出**していたが、
   グリッドにディスパッチの費用が入っていなかった。**31 §6 の「完全バケット化との
   差は −3%」は符号が逆で、実際は 2 分割のほうが 5% 速い。**

**積み直し** (**導出**、上の実測から):

```
100 タイル/ブロック × 57.3% (発火する割合) × 36.1 µs/タイル (幅 6 の差) = 2.07 ms/ブロック
```

**実測は 30.11 − 27.99 = 2.12 ms/ブロック。**3% 差で合う。
**計器は production を正しく予言している** — 外れていたのは 31 §5 が置いた
タイルの形 (16 エキスパート・常に最大 4 行) のほうである。

## 5. 壁時計に出ない理由 (**実測**、`TF_PREFILL_HOST_PROFILE=1`)

49 verify ブロックの平均、off 側:

| call | fetch | wait.front | enc.moe | tiles | experts | miss |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 94.4 ms | **55.0** | 30.3 | 1.14 | 100 | 569 | 61 |

**fetch が call の 58%** である。30 §5 は「32 スロットは I/O が床、48 スロットでは
fetch が本当に縮む」と書いたが、**この prompt では 48 スロットでも fetch が床**で、
GPU を 2.1 ms 削った先に受け皿が無い。`wait.front` (30.3 ms) は GPU を待つ時間だが、
その裏で fetch が走っているので、GPU が早く終わっても call は縮まない。

> host profile 側の off/on 差 (call −2.8%) は**採らない**。同じ差分で fetch も
> −2.7% 動いており、分割が fetch を速くすることはありえない。2 回ずつでは
> I/O の run 間ばらつきに埋もれる。§3 の GPU profile (8 回・順序均衡) のほうを採る。

## 6. テスト

**分割あり/なしがビット一致することを固定する 1 本を足した** — 31 §6 の
「ゲート 1 は自明に通る」を、パイプライン全体ではなくカーネル単体で番人にする。

`PrefillGroupedRoutedMoETests.rowsSplitDownMatchesSingleDispatch`:
エキスパートが 2, 3, 3, 4, 4 行を持つ**両側が空でないタイル**を作り、
`downSplitRowCount: 0` (分割前の形) と既定の 2 で 1 回ずつ走らせて
`route_partials` を**ビットパターンで**比較する。`downSplitRowCount` は
そのためだけに開けた引数で、production の呼び出しは既定値を使う。

`Scripts/test.sh` は **872 テスト / 146 スイートで全通過** (31 の 871 に本節の 1 本)。

## 7. 引き継ぎ

**28 §2 の本題は開いたままである。**31 §6 が書いたとおり、崖を消しても
`down` の行あたり 15.1 µs は残る。31 §3 が挙げた**未確認**の容疑者
(`down` の F=704 スカラー末尾 — ループ反復の 75% がデータの 27% を
半分のレーンで処理する) には手を入れていない。次はそこである。
ただし末尾を組み替えると `simd_sum` の総和順序が動くので、
`PrefillRoutedMoERowsVsDecodeTests` のビット一致とは正面から衝突する。

**そして 30 §5 と本書 §5 が 2 度同じことを言っている。**48 スロットでも
fetch が call の 58% で、GPU 側の改善は壁時計に出ない。
**`moe` をこれ以上削る前に、I/O を床から外す仕事のほうが先である。**
