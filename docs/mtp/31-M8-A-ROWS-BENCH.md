# 31. M8 果実 A の計器 — `moe` を verify ブロックの時間軸から外して測る

測定: 2026-08-19、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3 / Xcode 26.6。
モデル不要 (合成重み)。表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

30-M8-B-PREFETCH §7 の最終行が置いた引き継ぎ (「A (`moe` 28 ms) は依然未測定。
次はこちらを先に測るのが筋である」) に着手した。**実装はまだ入れていない** —
本書は計器を作って測っただけである。実装の引き継ぎは §7 にある。

## 0. 結論 — 4 つ

1. **27 §6 の 3 つの「不変」は、カーネルではなく測り方の限界だった可能性が高い**
   (**導出**、§1)。3 つとも 48 スロットの verify ブロックの GPU busy (47〜48 ms) で
   読んでおり、1 ms 未満は分解できない。新しい計器はその 1/1000 を読む。
2. **`down` が `gate/up` の 2 倍高い。読むバイトは半分なのに** (**実測**、§3)。
   行あたり 15.1 µs 対 7.4 µs、バイトは 1.24 MB 対 2.48 MB/エキスパート。
   **バイトあたり 4 倍**である。
3. **`cap` と実行時行数のミスマッチに崖がある** (**実測**、§4)。1 行しか持たない
   エキスパートは、同じタイルに 3 行のエキスパートが 1 個いるだけで
   `down` が **167 → 284 µs (+70%)** になる。8 行なら 2.09 倍。
   **28 §2 が挙げた「発行/占有率律速」説を支持する初めての直接の実測**である。
4. **`encodeStreamedRows` はタイルの最大行数で PSO を 1 本選ぶ**ので、production は
   この罰則を毎回払っている (**実測**、§5)。**`down` のディスパッチを崖で 2 分割する**
   だけで `moe` −17%、28 → 23.2 ms の**導出**が立つ (§6)。出力はビット不変。

## 1. なぜ計器から作ったか (**導出**)

28 §2 は 27 §6 の 3 点を割り算し直して「行 1 本の限界費用 37 µs が、エキスパート 1 個の
重み全読み 27.5 µs を上回る」を出し、原因の候補を 2 つ (発行/占有率律速、活性化の再読)
挙げた。だが 27 §6 は既にその両方を狙った実験を 3 本やって、全部「不変」で戻している:

| 27 §6 が試したこと | 結果 |
| --- | --- |
| 重みを 2×16bit → 1×32bit ロード | 不変 |
| 1 simdgroup が出力 2 行 (活性化ロード半減) | 不変 |
| int4 展開を行ループの外へ巻き上げ | 不変 (コンパイラが既にやっていた) |

**3 つとも「48 スロット・busy 47〜48 ms」で読んでいる。**しかも 30 §5 が測ったとおり
その時間軸には expert I/O が同居していて、32 スロットでは I/O のほうが床である。
**「カーネルが変わらない」のか「測れていない」のかが分かれていない。**
だから最初にやるのは、この 2 つのカーネルを**ブロックの時間軸から外すこと**である。

## 2. 計器 (**実測**、`--moe-rows-bench`)

`Sources/TsugumiKernelCheck/MoERowsBench.swift` (新規)。既にある
`--rows-bench` (dense 側の `dequant_int4_gemv_rows_simd`) と同じ作りで、対象を
routed の 2 本にしたもの。

- 合成重み・**モデル無し・expert キャッシュ無し・I/O 無し**、16 エキスパート 1 タイル
- production 形状: **D=2816、F=704、affine group 32** (`ArchConfig.gemma4_26B_A4B`)
- **`gate/up` と `down` を別々に**時間を取る (ブロックプロファイルは和しか出さない)
- 1 コマンドバッファに `iterations` 回エンコードして `gpuEndTime - gpuStartTime`
- `FC_MOE_ROWS_CAP` (function constant 16) を自由に指定できる

```bash
swift build -c release --product TsugumiKernelCheck
.build/release/TsugumiKernelCheck --moe-rows-bench --group-size 32 \
  --moe-rows-bench-iterations 200
```

**再現性はパス間 1% 未満** (**実測**、200 反復 ×2 パス)。500 µs のディスパッチを
1 µs で読む。表の最初の 1 セルだけウォームアップが乗るので捨てること。

**外部校正** (**実測** + **導出**): §5 の混合を cap=4 で積むと **46.7 µs/エキスパート**
になり、27 §6 がパイプラインで測った bs=4 の **50.2 µs/エキスパート**と **7% 差**で
一致する。計器と、§5 が置いた行数の混合の**両方**がこれで裏を取れている。

## 3. `down` が `gate/up` の 2 倍高い (**実測**)

cap = r (production が選ぶ形)、µs / 16 エキスパート 1 ディスパッチ:

| 段 | r=1 | r=2 | r=3 | r=4 | r=6 | r=8 | µs/行/エキスパート |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `gate/up` | 296.4 | 296.2 | 404.4 | 528.1 | 815.3 | 1121.3 | **7.37** |
| `down` | 168.9 | 217.0 | 600.0 | 793.3 | 1278.7 | 1857.6 | **15.08** |

読むバイトは逆である (**導出**、group 32):

| 段 | 詰め重み | affine | 合計/エキスパート |
| --- | ---: | ---: | ---: |
| `gate/up` | 1.98 MB | 0.50 MB | **2.48 MB** |
| `down` | 0.99 MB | 0.25 MB | **1.24 MB** |

**バイトあたり 4 倍**。帯域では説明できない。

**未確認だが疑わしいのは `down` のスカラー末尾である。**`gate/up` は D=2816 を
reduce するので 88 グループ = 11 ベクトル化ブロック**丁度**で末尾が無い。`down` は
F=704 を reduce するので 22 グループ = **2 ブロック + 6 グループの末尾**で、その末尾は
`lane >= kPrefillRowsTailLanes` (= 16) で抜ける **半分のレーンしか動かない**スカラー
ループである (`prefill.metal:1184-1198`)。**ループ反復数の 75% が、データの 27% を
半分の占有率で処理している。**27 §6 の 3 本はどれもベクトル化ループ側を触っていて、
この末尾に手を入れていない。

> 末尾を組み替えるとレーン → 要素の割り当てが変わり、`simd_sum` の総和順序が動く。
> 16-M4.5 §4 の「ブロックは decode の一般化」(`PrefillRoutedMoERowsVsDecodeTests` が
> ビット一致で固定している) と正面から衝突するので、**§7 の打ち手より後**である。

`FC_MOE_ROWS_CAP` を固定して実行時行数 r を振った。µs / 1 ディスパッチ:

**崖は cap=2 と cap=3 のちょうど間にある。**r=1 で +51%、r=2 で +102%。
cap=3 以降は緩やかにしか増えない。レジスタ配列 (`x_row[cap]` / `dst[cap]` /
`acc[cap]`) が cap=3 で占有率の段を 1 つ落としている形と整合する (**未確認**、

## 5. production は毎回この罰則を払っている (**実測** + **導出**)

`PrefillGroupedRoutedMoE.encodeStreamedRows` は、タイルの**最大**行数
(`widestBlock`) で PSO を 1 本選び、16 ブロック全部をそれで走らせる
(`PrefillGroupedRoutedMoE.swift:764-767`)。

bs=4 では 1 エキスパートの行数は 1〜4 (エキスパートはトークンあたり高々 1 行)、
平均 1.72 (27 §6)。**16 個の最大はほぼ確実に 4** なので、production は事実上いつも
cap=4 で走っている — つまり **1 行のブロックが §4 の +76% を払っている**。

混合を (1 行×8、2 行×5、3 行×2、4 行×1 = 平均 1.75) と置くと (**導出**、
§2 の外部校正がこの置き方を支持する)、µs / タイル:

| | `gate/up` | `down` | 計 | µs/エキスパート |
| --- | ---: | ---: | ---: | ---: |
| 現状 (全部 cap=4) | 330.5 | 416.1 | **746.6** | 46.7 |
| `down` だけ 2 分割 | 330.5 | **289.1** | **619.6** | 38.7 |
| 完全バケット化 | 321.3 | 276.0 | 597.3 | 37.3 |

## 6. 打ち手 — `down` のディスパッチを崖で 2 分割 (**導出**)

行数 ≤2 のブロックと ≥3 のブロックを**別のディスパッチ**にし、それぞれ自分の cap の
PSO で走らせる。

- **`down` −30.5%**、`moe` 全体 **−17%**。28 ms なら **28 → 23.2 ms、−4.8 ms/ブロック**
- **追加ディスパッチはタイルあたり 1 本だけ。**27 §5 が 60/ブロックまで畳んだ経緯が
  あるので、完全バケット化 (最大 8 本) との差 −3% はこの 1 本ぶんの価値より小さい
- **`gate/up` は分割しない** — §4 のとおり −2.8% しか出ないのにディスパッチが増える
- **ゲート 1 は自明に通る。**cap はレジスタ配列の大きさとループ上限を決めるだけで、
  1 行あたりの演算列も総和順序も変わらない。既存の
  `PrefillRoutedMoERowsVsDecodeTests` (decode とビット一致) がそのまま番人になる

**期待値の位置づけ**: 28 §7 は A に「28 → 16 ms」を置いていた。これはその半分弱で、
**A を閉じるものではない**。§4 の崖を消しても `down` の行あたり 15.1 µs は残る
(cap=1 → cap=2 の増分が 48 µs/16 = 3.0 µs/行に対し、cap=3 以降は 12〜13 µs/行)。
**28 §2 の本題 (行 1 本 37 µs 対 重み全読み 27.5 µs) はまだ開いている。**

**壁時計に出る場所** (**導出**): 30 §5 のとおり 32 スロットは fetch が 60.7/94.2 ms で
I/O が床なので、GPU を削っても出にくい。**48 スロット側が先**に見えるはずである。

## 7. 実装の引き継ぎ

やることは 1 つ。`encodeStreamedRows` の `down` のエンコードを、行数で 2 つに
分けて 2 回呼ぶ形にする。

- **場所**: `Sources/Tsugumi/Kernels/Prefill/MoE/PrefillGroupedRoutedMoE.swift`
  の `encodeStreamedRows` (`:690-770`)。今は `blocks` を 1 本作って
  `encode(rowsDownCappedPSO[widestBlock] ?? rowsDownPSO, ...)` を 1 回呼んでいる
- **分け方**: `blocks` を `rowCount <= 2` と `rowCount >= 3` の 2 つに割り、
  前者は `rowsDownCappedPSO[そのバケットの最大行数]`、後者は
  `rowsDownCappedPSO[widestBlock]` で 1 回ずつエンコードする。
  片方が空ならそのディスパッチは出さない (現状と同じ 1 本に戻る)
- **`local_row` / `pair_start` は触らない。**ブロックごとに既に確定している値で、
  2 つのディスパッチが書く `act` の行と `route_partials` の位置は互いに素である
- **`gate/up` は 1 本のまま**
- **閾値 2 は §4 の崖の位置**であって、`kPrefillMoERowsMax` のような構造的な定数では
  ない。カーネルを触ったら §4 の表を取り直すこと

**判定**:

1. `--moe-rows-bench` の §5 の混合が §6 の表どおり動くか (数分)
2. ゲート 1 — 30 §2 と同じ 1 本で出力 md5 が `3eefadf60a5aa49540a4086706d6e5e4` のまま
3. `Scripts/test.sh --filter PrefillRoutedMoERowsVsDecode|PrefillGroupedRoutedMoE`
   (フルは 11 分かかるので節目だけ)
4. 48 スロットの交互 A/B ×3 (30 §3 と同じ回し方)。**32 スロットは後**
