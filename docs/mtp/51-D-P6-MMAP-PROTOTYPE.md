# 51. D の P-6 — 実装して測った。運用点で **tok/s +18.0% / 占有 −3.21 GB**、代わりに **ttft +52%**

実測: 2026-08-20、M3 Pro 18 GiB / macOS 15.7.5、`iogpu.wired_limit_mb` = 14336。
[49 §10](49-D-P5-RESIDENCY-SET.md) が置いた P-6 を、プローブではなく
**推論経路に実装して**測った (ユーザー決定: [50 §7](50-D-PRIZE-NOCACHE.md) の
「占有の札として進める」。**速度は「負けない」を確認するだけのはずだった**)。

計器は `TF_EXPERT_MMAP=1` の 1 個。既定は今の `pread` のままである。
一次ログは `bench/mtp51/`。ドライバは `bench/mtp51_mmap_ab.py`
(**ABBA 3 ラウンド = 片側 n=6**、毎 run ミス数と生成文 sha256 を検定する)。

**結論から:**

- **速度は「負けない」どころか勝った。**運用点 (`math` / 256 tok / 32 スロット /
  temp 0 / MTP off) で **tok/s 25.63 → 30.26 (+18.0%)**、`io` **14.28 → 7.26 ms/tok
  (半分)**。**12 run の生値に腕の重なりが 1 つも無い** (§2)
- **50 §4 の「D が消せるのは 0.62〜1.08 ms/tok = 壁時計の約 2%」は外れていた。**
  実測は **7.02 ms/tok**。50 §4 の 2 つの入力 (`f` と `C`) を両方成り立たせる
  読み方は無く、**外れているのは `f` のほう** — 運用点はあの推定よりずっと暖かい (§4)
- **占有は予告どおり出た。**peak **4.53 → 1.31 GB** (−3.21 GB)、rss 3.30 → 0.37 GB。
  48 §8 の「私有スロット 3.22 GB が消える」がそのまま (§3)
- **払っているのは ttft である。**prompt prefill **1.19 → 1.81 s (×1.52)**。
  差は丸ごと expert io で、**冷たい一気読みでは今の 8 並列 `pread` に負ける** (§5)。
  47 §0 の「冷たい側で負けない」は **decode では満たすが prefill では満たさない**
- **出力はバイト一致。**両条件 × 12 run すべてで生成文の sha256 が同一、
  ミス数も同一 (9145/61200 と 3829/61200) ⇒ 48 §9 の受け入れを満たす
- **MTP (bs=4) でも同じ向き** — tok/s **+8.6%**、受理長・ラウンド数・受理
  ヒストグラムは 12 run すべて同一 (§6a。**別インストールなので絶対値は
  §2 と並べない**)
- 製品側の差分は **86 行**、新規ファイル 1 本 (194 行)。`MoE.swift` は無改変
  (`useResource` は残したまま。49 §2 の腕 B\* のとおり set は上乗せである)

## 0. 何を実装したか — 49 §9 の作りをそのまま

| | |
| --- | --- |
| 張り方 | 層ファイルを **`MAP_SHARED` + `PROT_READ`** で 1 本、**プロセス寿命ぶん張りっぱなし** |
| バッファ | エキスパート単位に **128 本**の `bytesNoCopy` (`expertStride` 3,358,720 B = 205 ページで境界に乗る) |
| residency | **層ごとに `MTLResidencySet` 1 個**。中身は**その層のスロット表の写し**で、fetch の側 (I/O キュー) で `commit()` + `requestResidency()` |
| 掛け方 | エキスパートを読むコマンドバッファに `useResidencySet(_:)` 1 行 (decode の `routedCB` / `phase1HitCB`、prefill の `tileCB`) |
| `useResource` | **外していない** (49 §2 の B\*) |
| CPU 事前タッチ | **入れていない** (49 §5) |
| `F_RDADVISE` | 既存経路がそのまま出す。**両腕で同一**なので比較の外にある |
| スロット | **1 個も確保しない。**`posix_memalign` のループが 0 周になる |

**プランと LFU の帳簿は 1 行も変えていない。**ミス/ヒットの判定も、
`--expert-cache-slots 32` の意味も、タイルの切り方も今のままである。
変わったのは**ミスが何をするか**だけ — 3.36 MB を私有スロットへ `pread` する代わりに、
residency set にそのエキスパートを足す。**だから両腕でミス数が完全に一致する**
(§1)。`--expert-cache-slots` は D では「同時に residency を張っておく本数」に
意味が変わる (48 §8 が「製品の決定」と呼んだもの) が、**この測定では
両腕で同じ 32 に固定してある。**

## 1. 受け入れ — バイト一致 (実測、両条件 × 12 run)

| 条件 | ミス/要求 | 生成文 sha256 (先頭 12) |
| --- | ---: | --- |
| `math` / 256 tok | **9145 / 61200** (両腕・12 run とも同一) | **`40f67036aa88`** (両腕・12 run とも同一) |
| `story` / 256 tok | **3829 / 61200** (同上) | **`99b3239bcf26`** (同上) |

⇒ **同じバイトを読んで同じ 256 トークンを出している。**48 §9 が置いた受け入れ
(temp 0 / 256 tok でバイト一致) を満たす。比べているのは純粋に費用だけである。

## 2. **運用点 — tok/s +18.0%、`io` は半分** (実測、片側 n=6)

`math` / 256 tok / 32 スロット / temp 0 / MTP off / `trusted-install`。
ABBA (pread mmap mmap pread) × 3 ラウンド。中央値:

| 腕 | n | `io` ms/tok | GB/s | **tok/s** | prefill s | peak GB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **pread** (今) | 6 | 14.28 | 8.44 | **25.63** | 1.19 | 4.53 |
| **mmap** (D) | 6 | **7.26** | 16.61 | **30.26** | 1.81 | **1.31** |
| | | **×0.51** | | **×1.180** | ×1.52 | ×0.29 |

**生値に重なりが無い** (12 run、ABBA の位置効果込み):

| | pread | mmap |
| --- | --- | --- |
| tok/s | 25.20 / 25.41 / 25.59 / 25.68 / 25.72 / 25.89 | 30.06 / 30.09 / 30.14 / 30.37 / 30.55 / 30.99 |
| `io` ms/tok | 13.99〜14.63 | 6.77〜7.73 |

**ラウンド内の 2 本目のほうが速い**のは両腕に同じ向きで出ている
(pread 25.20→25.41、mmap 30.14→30.55)。48 §5a の位置効果で、ABBA が両側から
食わせているぶん、順位は動いていない。

### 2a. 2 つ目の条件 — `story` でも同じ向き (実測、片側 n=6)

同じ設定で `bench/story.json` (ミス 3829 = **50.4 MB/tok**。運用点の 120.4 の軽い側)。

| 腕 | n | `io` ms/tok | GB/s | **tok/s** | prefill s | peak GB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| pread | 6 | 7.35 | 6.87 | **29.89** | 1.28 | 4.52 |
| mmap | 6 | **3.39** | 14.94 | **33.76** | 1.85 | **1.31** |
| | | ×0.46 | | **×1.129** | ×1.44 | ×0.29 |

**バイトが 2.4 分の 1 になると取り分も減る** (+18.0% → +12.9%)。向きは同じで、
やはり 12 run に重なりが無い。**バイトに比例する費用を消している**ことと整合する。

## 3. **占有 — 3.21 GB が消えた** (実測)

| | pread | mmap | 差 |
| --- | ---: | ---: | ---: |
| peak phys footprint | 4.53 GB | **1.31 GB** | **−3.21** |
| peak rss | 3.30 GB | **0.37 GB** | −2.92 |
| マップした量 | — | 12.90 GB (30 層) | — |

48 §8 が予告した「私有スロット **3.22 GB** が消える」が、**そのままの数字で出た**
(32 スロット × 30 層 × 3.36 MB = 3.22 GB)。残るのは clean file-backed なので
**重みは swap に落ちない**し、**`iogpu.wired_limit_mb` を 14336 に上げてある前提も
外れる** (48 §7 の見積もりでは D 後に wire するのは約 2.5 GiB で、再起動後の
既定 8192 MB に収まる。**本測定は 14336 のまま走っているので、8192 で回る確認は
していない** — §7)。

## 4. **50 §4 の賞金の見積もりが外れた理由** (**導出**)

50 §4 はこう置いた:

```
io_cached = f * C + (1-f) * D      f = キャッシュ由来の割合 = 17〜19%
D が消せる量 = f * C = 0.62〜1.08 ms/tok      C = 3.76〜5.66 ms/tok (21.3〜32.0 GB/s)
```

**実測の差は 7.02 ms/tok** (14.28 − 7.26) で、**7〜11 倍**である。
しかも mmap 側の 7.26 ms/tok は 0 ではない (マッピングと residency の費用が
残っている) ので、**pread 側のコピーはそれより更に大きい。**

`f` と `C` を両方成り立たせる読み方は無い:

| 前提 | 帰結 | 判定 |
| --- | --- | --- |
| `f` = 17〜19% を保つ | 7.02 ms を出すには `C` ≥ 37〜41 ms/tok = **コピーが 3 GB/s** | **無い。**48 §3 の暖かい `pread` は 21〜32 GB/s、本測定の pread 全体でも 8.4 GB/s |
| `C` = 3.76〜5.66 ms を保つ | `f` > 1 が要る | **無い** |
| **`f` が 17〜19% より大きい** | `C` が 7〜14 ms/tok (9〜17 GB/s) 程度なら 7.02 が出る | **これだけが残る** |

**独立な裏づけ**: mmap 側は同じ 120.4 MB/tok を **16.6 GB/s** で通している。
**この機械の SSD は `F_NOCACHE` で 9.36 GB/s が上限**である (50 §3)。
⇒ **mmap 側のバイトの大半は SSD から来ていない。**運用点は 50 §4 の推定より
ずっと暖かく、**今の `io` の大半はディスクではなくコピーだった。**

**では 50 §2 の `F_NOCACHE` 実測 (運用点で `io` 15.51 → 17.84 ms/tok) と
どう両立するのか** — `F_NOCACHE` を立てても `io` が 15% しか増えないのは、
「キャッシュ由来が 17〜19% しかない」でなくても説明が付く。**この 2 つを
分ける軸は振っていない** (§7)。**本書が測ったのは差の総量であって、
その内訳ではない。**

### 4a. 何が効いているかは分けていない (**未確認**)

D は 2 つのことを同時にやる。**本書はどちらの取り分かを分離していない。**

1. **コピーが消える** — ページキャッシュに居るページは、写さずにそのまま GPU が読む
2. **ページキャッシュが 3.2 GB 広くなる** — 私有スロットが消えたぶん、
   同じ 18 GiB でファイルバックが余計に居られる ⇒ **ヒット率そのものが上がる**

2 は 50 §4 のモデルの外にある (あのモデルは `D` = ディスクの取り分を D の前後で
不変としている)。**分けるには、mmap 側に 3.2 GB の anonymous バラストを
持たせて同じ圧力にする腕が要る** (§7 の次の 1 手)。

## 5. **払っている側 — prompt prefill が ×1.52 遅い** (実測)

| | pread | mmap |
| --- | ---: | ---: |
| prefill (= ttft) | 1.19 s | **1.81 s** |
| うち expert io | 0.77〜0.83 s | **1.33〜1.49 s** |
| prefill の要求 | 1963 エキスパート / **ヒット 0.0%** | 同じ |

**差は丸ごと expert io である。**prefill は 1963 エキスパート (6.6 GB) を
ヒット 0% で一気に読む — 46 §5a の「生成の頭ほど遅い」区間そのもので、
**D がいちばん弱いと 48 §5 が言っていた冷たい側**である。

**帰属していない**が、形から素直な候補は**並列度**である:
`pread` の腕はミスを `concurrentPerform` で 8 本同時に投げる
(`executeExpertCachePlan`) のに対し、D の腕は `requestResidency()` を
**タイルごとに 1 本ずつ**出している。

**ただし「set 更新の直列化が犯人」は落ちた** (実測)。本枝は途中で
「set の更新を層ごとの 1 個のロックで直列化する」修正を入れている
(スナップショットの順と適用の順が入れ替わると、新しい sync が足した
エキスパートを古い sync が落としうるため)。**その前後で prefill は動かない**:

| ビルド | pread | mmap |
| --- | ---: | ---: |
| ロック無し (`mmap_ab_256_math.log`) | 1.211 s | **1.798 s** |
| ロック有り (`mmap_ab_256_math_v2.log`) | 1.187 | **1.805** |

prefill はタイルの fetch を**同時に**投げる (`tileLookahead`) ので、
ロック無しの版では set の更新が重なりうる。**重ねても速くならない**
⇒ **残る候補は「`requestResidency()` そのものが直列に効く」か
「冷たいページのフォールトが本当に高い」かで、分けていない** (§7)。

**運用上の意味**: 32 スロット / 256 tok の 1 リクエストで見ると、
ttft が +0.62 s、decode が −1.7 s (255 tok を 10.0 → 8.4 s) で、
**e2e の壁時計では取り返している**が、**短い応答ほど不利になる。**
`serve.py` の運用点は 32 スロットで、**ここは製品の判断が要る。**

## 6. MTP (bs=4) — **別条件**

`--draft-block-size 4` は `scratch/gemma4-qat-sym.moepack` に drafter が入って
いないので、**45 以前の affine インストール** (`scratch/gemma4-qat.moepack`、
expertStride 3,719,168 = 227 ページ) で回した。
**§2/§2a の表と絶対値で並べてはいけない** (40 §4-11) — 重みの形式も、
モデルも、経路 (ブロック) も違う。腕の内部比較としてだけ読む。

### 6a. 結果 — **同じ向き。tok/s +8.6%** (実測、片側 n=6)

`math` / 256 tok / 32 スロット / temp 0 / **bs=4** / affine インストール。

| 腕 | n | `io` ms/tok | **tok/s** | prefill s | peak GB | 受理長 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| pread | 6 | 18.70 | **31.92** | 1.37 | 4.87 | 1.713 / 94 rounds |
| mmap | 6 | **13.95** | **34.66** | 2.15 | **1.32** | **同一** |
| | | ×0.75 | **×1.086** | ×1.57 | ×0.27 | |

- **投機の中身は 1 ミリも動いていない** — 受理長 1.713、ラウンド 94、
  受理ヒストグラム `28,12,13,41` が **12 run すべてで同一**である。
  ⇒ D が動かしたのは費用だけで、**投機の帳簿には触れていない。**
- **取り分は小さくなる (+18.0% → +8.6%)。**ブロックは 1 ラウンドで
  2.72 トークン出すので、トークンあたりの expert バイトが減る =
  消せる分も減る。**向きは同じ。**
- **占有は 3.55 GB 消えた** (affine は expertStride 3,719,168 なので
  32 × 30 × 3.72 MB = 3.57 GB。予告どおり)。
- **prefill の負けは MTP でも同じ** (×1.57)。


## 7. このプローブが答えていないこと (**未確認**)

- **§4a の内訳。**「コピーが消えた」と「キャッシュが 3.2 GB 広くなった」を
  分けていない。**次の 1 手はこれ** — mmap の腕に 3.2 GB の anonymous バラストを
  持たせて同じ圧力に揃える。取り分が残れば 1、消えれば 2 である。
- **prefill の負け (§5) は帰属していない。**「set 更新の直列化」は §5 で落ちた。
  残る手前の手は 3 つ — タイルごとでなく**層ごとに 1 回**にまとめる、
  **`requestResidency()` を待たずに投げる** (`useResource` が残っているので
  正しさは崩れない。フォールトがコマンドバッファの中に戻るだけ)、
  **prefill だけ `pread` に戻す** (両方持つのは差分が増えるが、
  冷たい一気読みと暖かい 1.2 ミス/層は別の仕事である)。
- **`iogpu.wired_limit_mb` を既定 (8192) に戻して回していない。**48 §7 の
  「D は wired_limit 依存を外す」は**導出のままである。**
- **`requestResidency()` が何を確保しているかは見ていない** (49 §8 から持ち越し)。
- **マッピングの寿命は「張りっぱなし」でしか測っていない。**キャッシュから
  落ちたページを再び触る費用は、この構成では `io` の中に紛れている。
- **48 スロット / 16 スロットで振っていない。**D では `--expert-cache-slots` の
  意味が「同時に residency を張る本数」に変わるので、**最適値が動く可能性がある。**
- **サーバー経路 (`Scripts/demo/serve.py`) では回していない。**CLI だけである。
- **プロセス終了時に `munmap` していない** (試作の意図的な手抜き。まだ
  `MTLBuffer` を持っている側が消えたページを指すのを避けるため)。
- **温度は temp 0 である。**40 §4-4 のとおり運用の既定は temp 1.0 で、
  そこでは出力が腕をまたいで一致しないので ABBA の検定が効かない。
  **本書の比は temp 0 の比である。**
