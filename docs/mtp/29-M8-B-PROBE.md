# 29. M8 果実 B の前提検定 — router の先行適用は当たるか

測定: 2026-08-19、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3。
対象モデル `scratch/gemma4-qat.gturbo` (drafter 同梱)、32 スロット / 8192 context。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

28-M8-PROPOSAL §7 が置いた「着手前に潰す計測 4 本」のうち **2 本目 (B の的中率)**
だけを実行した。提案書は「まずオフラインで的中率を測る」と書いたが、
**トレースをダンプせず実機の計器で測った** — 既存の `encodeRouterGemma4BF16Rows`
に層 L+d の重みを渡すだけで済み、hidden をファイルに出す配管が要らないからである。

**A (`moe` の GPU counters) はまだ測っていない。**

## 0. 結論 — 4 つ

1. **当たる。**層 L の router 入力に層 L+1 の router 重みを当てると、
   層 L+1 が実際に読むことになるエキスパート (= ミス) の **66.0%** に
   先に名前が付く (**実測**、層 2,146 件)。27-M7 §7 の「予測はできない」は
   **履歴ベース限定の話だった**という提案書 §3 の読みが裏付けられた。
2. **番号の再利用では代わりにならない** (**実測**、`./bench/mtp_router_xlayer.py
   scratch/mtp-traces/math-t0.tsv`)。層 L が選んだ集合が層 L+1 を当てる率は
   **5.9%** で、ランダム (8/128 = 6.2%) と区別がつかない (同じ層の直前ステップ
   なら 32.9% なので、計り方の問題ではない)。router を当てる以外に道は無い。
3. **予測を全部先読みすると損する。**予測のうち非常駐は層あたり 6.04 本で、
   的中は 47.9% — ブロックが読むバイトが **1.72 倍** (469 → 806 MB) になる。
   32 スロットの I/O 余裕はそれを吸えない (§3)。
4. **router の予測重みで上から N 本に絞ると割に合う。**N=1 なら的中 70%、
   バイトは **1.07 倍**で済む。**導出**でブロック 82 → 63〜66 ms、
   **23.6 → 約 30 t/s**。提案書 §7 が p=0.7 で見積もった水準に、実測の p で着く。

## 1. 測り方 (**実測**)

`RouterPreviewProbe` (新規) は、**層 L の router を encode した直後の同じ
command buffer に、層 L+d の router をもう 1 本積む**。入力は層 L の
`scratch.routerX` (post-attention 正規化後の hidden) のまま、重みだけ
`layerViews[L + d]` のものに差し替える。compute encoder は直列なので
`routerLogits` の共用は安全である。

読み戻しは層 L の routing 読み戻しと同じ場所 (`.route` 段) で行い、

- **`compare`**: この層について d 層前に控えておいた予測を、いま実際に要求した
  集合・その時点の常駐状況 (`routedExpertResidency`) と突き合わせる。
- **`record`**: 続けて層 L+d 用の予測を控える。予測の強さは
  **ブロックの全行が付けた router 重みの和** (複数の行が選ぶほど確か、という順)。

**先読みは 1 本も発行していない。**予測は数えるだけで routing にも fetch にも
渡らないので、この計器は**測るだけで何も速くしない**。

```bash
TF_MTP_ROUTER_PREVIEW=1 .build/release/TurboFieldfareCLI \
  --model scratch/gemma4-qat.gturbo --messages-file bench/mtp_goal_prompt.json \
  --image sample_imgs/IMG_2112.JPG --image-tokens 280 --thinking on --temperature 0 \
  --max-new 200 --max-context 8192 --expert-cache-slots 32 \
  --verification trusted-install --draft-block-size 4
```

**ゲート 1 (出力一致)**: 計器 on/off で md5 一致 (`3eefadf6…`、120 tok)。
計器自身の費用は 23.6 → 22.0 t/s (余分な router GEMV と residency 問い合わせ)
で、**測定時だけ**の負担である。

## 2. 当たるか (**実測**、200 tok、層 2,146 / 2,072 件)

| d | top-8 の重なり | **実ミスの被覆** | 予測のうち非常駐 | その的中率 | 読むバイト |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 75.7% | **66.0%** (6,217/9,424) | 6.04/層 | 47.9% | **1.72×** |
| 2 | 67.6% | 56.9% (5,009/8,800) | 6.65/層 | 36.4% | 2.00× |

「実ミスの被覆」が本題である: 層 L+d が SSD から読むことになるエキスパートの
うち、層 L の時点で名前が付いていた割合。d=1 で **2 本に 1 本以上**当たる。

> 予測集合の大きさは実際の要求とほぼ同じ (pred/act = 1.02) で、**上振れした
> 予測をしているのではない** — 同じくらいの大きさの集合が 3/4 重なっている。

## 3. 全部読むと損する (**導出**)

d=1 の「非常駐の予測 6.04 本」を全部読むと、層あたりの読み出しは
実ミス 4.39 本 + 外れ 3.15 本 = **1.72 倍**になる。ブロック 1 回は
469 → 806 MB。27-M7 §7 のプローブ (深さ 4 で 6.5 GB/s、深さ 8 で 8.9 GB/s) で
割ると **I/O だけで 100 ms 近く**になり、GPU busy 49 ms を大きく超える。
**今の 82 ms より遅い。**

先読みは「発行時刻」を前倒しにするだけで「読める速さ」は増やさないので、
**バイトを増やす先読みは 32 スロットでは自滅する。**

## 4. 順位で絞る (**実測**)

そこで予測重みの強い順に並べ、「上から N 本だけ先読みする」を積み上げで測った
(d=1、cov = 実ミスの被覆、read = ブロックが読むバイトの倍率):

| N | 的中率 | ミス被覆 | 読むバイト |
| ---: | ---: | ---: | ---: |
| **1** | **70%** | 16% | **1.07×** |
| 2 | 59% | 28% | 1.15× |
| 3 | 53% | 38% | 1.24× |
| 4 | 48% | 46% | 1.33× |
| 6 | 36% | 56% | 1.48× |
| 8 | 31% | 61% | 1.58× |

d=2 は全体に 10 ポイント低い (1 位で 59%)。**順位は効いているが緩やか** —
1 位でも 70% で、100% には遠い。

## 5. 導出した効き (**導出**)

32 スロットの層あたりの数字 (27-M7 §4/§7 から): GPU busy 1.63 ms、
ミス 4.2 本、読み 0.357 ms/本 (= 45 ms / 126 本)、
現状ミスを隠せるのは常駐タイルの 0.7 ms だけ。

先読みが当たった分は**前の層の GPU 仕事 1.63 ms の陰**に入る (今は 0.7 ms しか
無い)。外れた分と当たらなかったミスは今と同じで、層あたり I/O が GPU を
超えたところからは I/O が床になる:

| N | 層あたり I/O | 層あたり露出 | ブロック | ms/tok | t/s |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 現状 | 1.50 ms | 0.80 ms | 82 ms | 42.4 | 23.6 |
| 1 | 1.61 | 0.56 | 約 66 | 約 34 | 約 29 |
| 2 | 1.72 | 0.38 | 約 63 | 約 33 | 約 30 |
| 3 | 1.86 | 0.23 | 約 63 | 約 33 | 約 30 |
| 4 | 2.00 | 0.11 | 約 63 | 約 33 | 約 30 |

**N=2〜4 は横ばい** — 露出が減るぶんバイトが増えて相殺する。
**N=1 を推す**: バイトが 7% しか増えず、層あたり 1 スロットしか動かさないので、
提案書 §3 が警告した「32 スロットの追い出し合戦」のリスクが最小である。
実装後に N を振って測り直す (フラグにする)。

**decode (MTP off) 側にも同じだけ効くはず** (**未確認**) — 32 スロットは off 側も
I/O 律速なので (27 §2c)、採点基準 v1 の比は下がりうる。目標は絶対 t/s なので
それは正しい方向である。

## 6. 実装の設計 — 次の作業への引き継ぎ (**未確認**)

計器は入っている。**まだ入っていないのは「予測を実際に fetch に渡す」経路**である。

**置き場所**: `RealForwardRunner.executePrefillChunk` の層ループ。
予測の読み戻しは既に `.route` 段にある (`routerPreviewProbe.record` の隣)。
そこで `nonResident` の先頭 N 本を層 L+d の streamer に投げる。

**必要な新 API** (`PreadExpertStreamer` / `ModelExpertIO`):

1. **投機用のプラン** `planSpeculativeExperts(experts:)`。既存の
   `makeExpertCachePlan` と 2 点だけ違う:
   - **`expertUseCount` を増やさない。**今のプランは要求した全エキスパートの
     使用回数を上げる (`PreadExpertStreamer.swift:270`)。外れた先読みで
     使用回数が上がると、**役に立たないエキスパートが LFU で守られる**。
   - **追い出してよい相手を絞る。**犠牲の `slotLastUse` が「この層の前回の
     プランの clock」より新しいものは選ばない = **直近のラウンドで使った
     エキスパートは追い出さない**。置けなければ `nil` を返して先読みを諦める。
     32 スロット / 層 19 エキスパートなら 13 スロットが候補になるので、
     N=1 では十分足りる (**導出**)。

2. **層 L+1 に入る前に先読みハンドルを待つ。**`executeExpertCachePlan` は
   **読み終わってから** `expertResidency` を上げる (`PreadExpertStreamer.swift:318`)
   ので、完了した先読みは層 L+1 のプランに**ただのヒットとして見える** —
   ここは何も足さなくてよい。危ないのは**飛行中**で、そのときスロットは
   まだ空きに見えるため、層 L+1 のプランが**同じスロットを犠牲に選んで
   二重書きしうる**。層 L+1 の `.route` 段の頭でハンドルを `wait()` すること。
   今その位置で miss を待っていたのと同じ場所なので、**前倒しの利益は残る**。

**正しさ**: 先読みはヒントで、実行は正規の routing のまま。読むバイトの中身も
同じ。**ゲート 1 は構造的に通る** — 27-M7 §8 と同じ論法 (どのスロットに置くかが
変わるだけ) が使える。env-gate (`TF_MTP_EXPERT_PREFETCH`、既定オフ) を付け、
**同一セッションの交互 A/B** と md5 で判定する。

**測り方**は 27-M7 §9 の 1 行そのまま + `TF_PREFILL_HOST_PROFILE=1
TF_PREFILL_GPU_PROFILE=1`。見るのは `GPU idle` と `wait.front`、
そして telemetry のミス数 (先読みの分だけ増えるはず)。
