# 49. D のプローブ — P-5。フォールトはコマンドバッファの外に出る。出すのは `MTLResidencySet` 1 個

実測: 2026-08-20、M3 Pro 18 GiB / macOS 15.7.5、`iogpu.wired_limit_mb` = 14336。
[48 §13](48-D-P1-P4-MMAP-RESIDENCY.md) が置いた P-5 を実行した。
**推論経路 (`Sources/TurboFieldfare/`) は無改変。**計器は
`TurboFieldfareKernelCheck --mmap-p5-probe` の新規フラグ 1 つ
(`Sources/TurboFieldfareKernelCheck/MmapP5FaultProbe.swift`)。

一次ログは `bench/mtp48/p5_*.log`。本測定は**独立な 4 invocation × 片側 n=20 = n=80**
(交互順を 2 種類)。統計は `bench/mtp48_p5_stats.py` が一次ログから出し直す
(**導出**のみ、新しい測定はしない)。

**結論から:**

- **フォールトはコマンドバッファの外に出る。**`MTLResidencySet` を 1 個作って
  エンコード前に `requestResidency()` するだけで、初回タッチの上乗せは
  **0.61 → 0.09 ms (6.8 倍)** になり、**同じマッピングを 2 回目に走らせた床から
  0.09 ms しか離れていない**。**もう中に残っていない**
- **48 §11/§12 の「2.44 µs/ページ」という立て方が間違っていた** (§4)。
  ページ数を **410 → 3,280 (8 倍)** 振ると、residency set 側の上乗せは
  **0.06〜0.12 ms で平ら**である。これは**ページ単価ではなくコマンドバッファ
  あたりの固定費**で、**48 §12 の表 (ページ/tok × 単価) は arm B には当たらない**
- **CPU 事前タッチ (腕 C) は効かない** — 何もしないより**遅い** (1.88 対 1.79 ms) 上に
  準備側で 0.90 ms 食う。CPU のフォールトは GPU の residency を満たさない (§5)
- **48 §13 の PASS 条件「in-band 1.0 ms 以下」は満たせない。ただしこの閾値は
  ハーネスの床より下にあった** (§6) — 冷たいページが 1 枚も無い同じコマンド
  バッファが **1.16〜1.21 ms** (うち GPU 0.68 ms) 掛かる。**フォールト費用が
  ちょうど 0 の腕でも通らない閾値**である。**48 §13 が実際に問うたこと
  (外に出せるか) は通った**
- **48 §11 の対照 4.25 ms は再現するが、P-5 の対照 (腕 A) は 1.79 ms で、
  2.5 倍合わない** (§7)。**3 つの候補を潰したが帰属できていない。**
  **P-5 の判定はこの差に依存しない** — 腕 A は同じハーネス・同じ分・
  同じプロトコルの内部対照である (40 §4-11)

## 0. 何を測ったか — 「in-band」と「premium」

48 §11 は「1,640 ページを全部ページキャッシュに載せてから走らせても
コマンドバッファは 4.25 ms 掛かる」を測り、カーネル 0.25 ms を引いた
**4.00 ms をフォールト/マッピングの費用**とした。この引き算には穴がある —
0.25 ms は 48 §3 が**1 本のコマンドバッファに 1,200 パス積んで償却した**値で、
**コマンドバッファ 1 本ぶんの固定費が入っていない。**

そこで P-5 は**同じ試行の中で 2 回目を走らせる**。マッピングもバッファも同じ、
違うのは「もうどのページも冷たくない」だけである。

| | 定義 |
| --- | --- |
| **in-band (1st)** | `makeCommandBuffer` + エンコード 2 本 + commit + 完了待ち。48 §11 の `run` と同じ区間 |
| **warm** | **同じ試行の中で**、同じフィクスチャでもう 1 本走らせた値。冷たいページが無いときの床 |
| **premium** | 1st − warm。**初回タッチが実際に掛けた費用**。48 §13 が外に出せと言っているのはこれ |
| **prep** | 腕ごとの準備の壁時計。前の層の GPU 仕事の陰に隠す必要がある側 |

先読み (`F_RDADVISE` を出して `mincore` が 1,640/1,640 になるまで待つ) は
どの腕にも共通で、**どの腕にも計上していない**。その値は中央値 **2.95 ms** で、
48 §11 の 2.70 ms と同じ桁である (**ハーネスが移っていないことの検定**)。

## 1. 腕 — 4 つ + 交絡分離の 1 つ

| 腕 | 何をするか |
| --- | --- |
| **A** | 今の形。`useResource` を 8 バッファに掛けるだけ。**内部対照** |
| **B** | `MTLResidencySet` に 8 バッファを入れて `commit()` + `requestResidency()` を**別スレッドで**、エンコードの前に。**`useResource` は外す** (この API はその代替である) |
| **B\*** | **B に `useResource` を残したもの。**「set が効いた」と「毎エンコードの `useResource` ループを外したのが効いた」を分ける |
| **C** | CPU 側でページごとに 1 バイト読む (`concurrentPerform` で 8 並列) |
| **D** | B + C。**両方を同時に投げて両方を待つ** (production の形) |

`BpwProbe.encode` は渡された `blobs` にしか `useResource` を掛けないので、
**`blobs` を空にするだけで腕を切り替えられる** — 43/44 の計器に手を入れていない。

**出力は全 400 試行で腕 A とビット一致した。**residency set に任せて
`useResource` を外した腕も、同じ重みを読んでいる。

## 2. 結果 — **`MTLResidencySet` が premium を 6.8 倍落とす** (実測、n=80)

独立な 4 invocation (交互順 palindrome 2 本 + rotate 2 本) を pool した中央値。
CI はブートストラップ 20,000 回 (**導出**)。

| 腕 | n | 1st | warm (床) | **premium** | premium 95% CI | prep |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **A** useResource のみ | 80 | 1.79 ms | 1.20 | **+0.61** | 0.51〜0.73 | 0.00 |
| **B** residency set | 80 | **1.26** | 1.19 | **+0.09** | 0.05〜0.10 | 0.59 |
| **B\*** set + useResource | 80 | **1.26** | 1.19 | **+0.07** | 0.06〜0.10 | 0.56 |
| **C** CPU 事前タッチ | 80 | 1.88 | 1.18 | **+0.71** | 0.68〜0.80 | 0.90 |
| **D** B + C | 80 | **1.23** | 1.16 | **+0.07** | 0.04〜0.10 | 1.06 |

**CI は重ならない。**GPU 時間はどの腕でも **0.68 ms で同じ**なので、
動いているのはドライバ側だけである。

**順位は 4 invocation すべてで同じで、交互順を変えても崩れない** (実測):

| | A | B | B\* | C | D |
| --- | ---: | ---: | ---: | ---: | ---: |
| palindrome run1 / run2 | 1.71 / 2.00 | 1.28 / 1.25 | 1.27 / 1.24 | 1.87 / 1.82 | 1.26 / 1.20 |
| rotate run1 / run2 | 1.71 / 2.01 | 1.27 / 1.26 | 1.26 / 1.22 | 1.92 / 1.85 | 1.25 / 1.23 |

`rotate` は毎ラウンド 1 つずつ回すので、**5 ラウンドでどの腕もどの腕の直後に来る。**
48 §5a が見つけた位置効果 (0.58〜1.03 ms、測ろうとしている差と同じ大きさ) は、
**P-5 では順位を動かしていない。**

**B と B\* は差が無い。**⇒ **効いているのは residency set であって、
`useResource` を外したことではない。**実装上これは重要で、
`MoE.swift:392/434/473` の `useResource` ループは**残したままでよい**。

### 2a. 副産物 — residency set が P-1 を独立に裏づける (実測)

`MTLResidencySet.allocatedSize` は commit 後に **26.9 MB** を返す
(8 × 3.36 MB)。層ファイルは 429.9 MB である。
⇒ **48 §1 の「粒度はバッファであってマッピングではない」を、
まったく別の計器が同じ数字で言っている。**

## 3. 準備側 — **0.59 ms。1 層先行に収まる** (実測、n=80)

| 腕 | prep 合計 | うち set | うち CPU タッチ | 128 バッファの作成 |
| --- | ---: | ---: | ---: | ---: |
| A | 0.00 ms | — | — | 0.60 ms |
| **B** | **0.59** | 0.43 | — | 0.57 |
| B\* | 0.56 | 0.45 | — | 0.59 |
| C | 0.90 | — | 0.87 | 0.61 |
| D | 1.06 | 0.53 | 0.98 | 0.60 |

48 §13 が置いた「準備側が並列で 1.5 ms 以下」は **B で 0.59 ms、通る。**

**47 §8 の 3 番目の未確認 (「エンコード時に 3,840 個の `MTLBuffer` を触る費用」)
にも数字が付いた** — 128 本の `bytesNoCopy` バッファを作るのは **0.60 ms/層**。
ただし**これは production の形ではない** (P-5 は試行ごとに作り直す。
production は張りっぱなしなので 1 回きりの起動費用になる) ⇒ **上限として読む。**

## 4. **48 §11/§12 の立て方が壊れる — premium はページ数で動かない** (実測)

48 §11 も §12 も、コマンドバッファ 1 本の費用をページ数で割って
「2.44 µs/ページ」と呼び、**それを production のページ/tok に掛けている。**
**線形は測られていない。仮定である。**エキスパート数を振ると:

| エキスパート | ページ | A | B | B\* | C | D |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | 410 | 1.58 ms | **0.06** | 0.36 | 0.44 | 0.11 |
| 4 | 820 | 2.08 | **0.12** | 0.24 | 0.41 | 0.12 |
| 8 | 1,640 | 0.67 | **0.11** | 0.06 | 0.72 | 0.18 |
| 16 | 3,280 | 0.89 | **0.11** | 0.10 | 1.44 | 0.12 |

(片側 n=16。値は premium の中央値。)

- **B と D は平ら。**ページを 8 倍にしても 0.06〜0.12 ms から動かない
  ⇒ **これはコマンドバッファあたりの固定費であって、ページ単価ではない。**
- **A と C は動くが単調ではない** (A: 1.58 → 2.08 → 0.67 → 0.89)。
  **ページ数では説明できない**。**帰属していない** (**未確認**)。

⇒ **48 §12 の表の立て方 (「ページ/tok × µs/ページ」) は、少なくとも
residency set を使う形には当たらない。**固定費として積むなら
**30 層 × 0.11 ms = 3.22 ms/tok** で、今の `io` 14.21 ms/tok の **0.23 倍**である。

参考までに、48 §12 の表を P-5 のページ単価で引き直すと (**導出**、
上のとおり arm B には当たらない立て方だが、48 §12 と同じ土俵で並べるため):

| 前提 | ページ/tok | 48 §12 (2.44 µs/pg) | arm A | **arm B** |
| --- | ---: | ---: | ---: | ---: |
| 初回タッチだけ (46 の trace、n=1) | 4,490 | 10.95 ms | 1.68 | **0.23** |
| 今のミスと同数 (45 §4) | 7,882 | 19.23 | 2.96 | **0.41** |
| 全要求 (マッピングが 1 歩も生き残らない) | 49,200 | 120.0 | 18.45 | **2.55** |
| **対照: 今の `io`** (45 §4) | — | **14.21** | | |

**どの前提でも arm B は今の `io` より 1 桁小さい。**
**48 §12 の「どの前提を置いてもフォールト費用は `io` と同じ桁」は、
residency set を使う形では成り立たない。**

## 5. **腕 C は効かない — CPU のフォールトは GPU の residency ではない** (実測)

CPU 側でページを触っても premium は **0.71 ms** で、**何もしない腕 A (0.61) より
悪い**。しかも準備側で 0.90 ms 掛かる。ページ数を振ると C の premium は
**0.44 → 1.44 ms** と増える (§4) — **払っているのに買えていない。**
D ≒ B なので、**B の上に C を足しても何も足されない。**

⇒ 48 §13 が「33 §1 の深さ 8 以上と同じ発想」で置いた腕は**落ちた**。
ページをこのタスクの PTE に入れることと、GPU がそれを読めるようにすることは
**別の帳簿**である (48 §11 が「どちらの取り分か未確認」と書いた 2 つのうち、
**GPU 側だった**、と読める。ただし直接は測っていない — **導出**)。

## 6. **48 §13 の PASS 閾値は床より下にあった** (実測)

48 §13 は「in-band が 8 エキスパートあたり **1.0 ms 以下**」を PASS に置いた。
最良の腕 D は **1.23 ms** で、**通らない。**

しかし**冷たいページが 1 枚も無い同じコマンドバッファ (warm) が 1.16〜1.21 ms**
掛かる。うち GPU が 0.68 ms である。⇒ **フォールト費用がちょうど 0 の腕でも
1.0 ms は割れない。**閾値は 48 §3 の「カーネル 0.25 ms」に乗っているが、
あれは**1,200 パスを 1 本に積んで償却した値**で、コマンドバッファ 1 本ぶんの
固定費 (約 0.5 ms) が入っていない。**閾値の置き方の誤りであって、腕の失敗ではない。**

**48 §13 が実際に問うたこと (§13 の見出しは「フォールトをコマンドバッファの
外に出せるか」である) で判定し直すと:**

| | 値 |
| --- | ---: |
| 出す前 (腕 A) | 0.61 ms |
| 出した後 (腕 B) | **0.09 ms** |
| 残っている割合 | **15%** |
| 自分自身の床までの距離 | **0.09 ms** |

**⇒ 出た。**そして**外に出した先 (prep 0.59 ms) は、1 層先行に収まる。**

## 7. **48 §11 の 4.25 ms と 2.5 倍合わない。3 つ潰したが帰属できていない** (実測)

腕 A は 48 §11 の対照と**同じプロトコル**である (冷たく落とす → `MAP_SHARED` で張る →
128 バッファ → advise → 常駐を待つ → コマンドバッファ 1 本)。
値は **1.79 ms** で、48 §11 は **4.25 ms** と書いている。

**48 §11 は今日も再現する** (`bench/mtp48/p5_control_recheck_full.log`、
同じ `--mmap-residency-probe` を今日走らせて **4.9〜5.4 ms**)。
**機械が変わったのではない。**潰した候補:

| 候補 | 検定 | 結果 |
| --- | --- | ---: |
| **residency set がプロセス全体のドライバ状態を暖める** (腕 A が同居しているせい) | 腕 A だけを別プロセスで (`--mmap-p5-only A`) | **2.02 ms** — 変わらない ⇒ **落ちた** |
| **anonymous メモリの汚染** (48 §5 の犯人。`MAP_PRIVATE` の腕が 430 MB/試行を汚す) | 先に 20 試行ぶん = **8.6 GB** を汚してから測る (`--mmap-p5-pollute 20`) | **2.15 ms** (+0.36) — **向きは合うが 5 分の 1 しか動かない** |
| **引数バッファを advise の前に組む** (48 §11 の P-4 ループはそうしている。GPU アドレスを冷たいページに対して書く) | `--mmap-p5-fixture-early` | **2.18 ms** (+0.16) — **足りない** |

⇒ **残るのは「全景を走らせたプロセスの履歴」の別の何か** (30 試行 ×
1,200 反復のコマンドバッファ、3,840 本以上のバッファの生成と解放)。
**未確認のまま置く。**

**P-5 の判定はこの差に依存しない。**腕 A は同じハーネス・同じ分・同じ
プロトコルで並べた内部対照で、40 §4-11 が「条件が違う絶対値は並べない」と
決めたのはまさにこの形を守るためである。**依存するのは 48 §12 のページ単価のほうで、
そちらは §4 のとおり立て方ごと当たらない。**

## 8. このプローブが答えていないこと (**未確認**)

- **end-to-end は依然として未測定。**1 層・8 エキスパート・コマンドバッファ 1 本の
  値である。30 層 × 先読み 1 層先行の噛み合いは P-6 (§10)。
- **マッピングの寿命は測っていない** (48 §7 から持ち越し)。P-5 も試行ごとに
  張り直す。**「一度フォールトしたページを、キャッシュから落ちたあと再び触る費用」は
  未測定**。§4 の「固定費」がそこでも固定費かは分からない。
- **prep 0.59 ms が本当に前の層の GPU 仕事と重なるかは測っていない。**
  測ったのは壁時計と、それが別スレッドで走ることだけである。
- **`requestResidency()` が何を確保しているかは見ていない。**wire したのか、
  GPU ページテーブルを張っただけなのかは区別していない
  (48 §1a のとおり `wire_count` はこの問いに使えない)。
- **腕 A / C の premium がページ数で単調でない理由** (§4)。
- **48 §11 との 2.5 倍** (§7)。
- **48 §7 の残りはそのまま残る** — `ExpertPrefetch` との相互作用、
  `--expert-cache-slots` の意味、47 §4 の取り分の再測。
- **数字は計器ハーネスのものであって production ではない** (40 §4-11)。

## 9. 実装する場合の作り (48 §9 に足すもの)

- **`MTLResidencySet` を層ごとに 1 個持ち、その層の 8 バッファを入れて
  `commit()` + `requestResidency()` を `ExpertPrefetch` の位置 (1 層先行、
  別スレッド) で呼ぶ。**コマンドバッファ側は `useResidencySet(_:)` 1 行。
- **`useResource` は外さなくてよい** (§2 の B\*)。`MoE.swift:392/434/473` は
  そのままでよい ⇒ **差分がさらに小さくなる。**
- **CPU 事前タッチは入れない** (§5)。
- 48 §9 の残り (`MAP_SHARED` + `PROT_READ`、層ごとに 1 マップ + 128 バッファ、
  `F_RDADVISE` 必須、受け入れは temp 0 / 256 tok × 3 プロンプトでバイト一致) は
  **そのまま。**

## 10. 次の 1 手 — P-6 (48 §13 が「P-5 が PASS したときだけ」と置いたもの)

**30 層 × 8 エキスパート、マッピングは張りっぱなし、先読みは 1 層先行、
residency set は層ごと。**比ではなく **1 歩の壁時計**を今の
`PreadExpertStreamer` と並べる。ここで初めて測れるもの:

1. **マッピングが生き残る率** (48 §12 の 2 番目。P-5 は使い捨てなので測れない)
2. **prep 0.59 ms が本当に隠れるか** (§8)
3. **§4 の「固定費」が 30 層でも固定費か** — 30 × 0.11 = 3.22 ms/tok の検定
4. **47 §4 の取り分の測り直し**

**⇒ `F_NOCACHE` は実行した → [50](50-D-PRIZE-NOCACHE.md)。**
賞金は **`io` の 17〜19% = 0.62〜1.08 ms/tok (壁時計の約 2%)** で、
**47 §4 の 36〜40 t/s は立たない。**しかも**上の §4 が置いた費用の上限
(3.22 ms/tok) のほうが大きい。⇒ D の根拠は速度から占有 (私有スロット 3.22 GB) に
移る。**P-6 を回すかどうかは、その前提で決める話になった (50 §7)。
**48 §13 のもう 1 本 (`--dump-expert-trace` を運用長で) は未着手のまま**だが、
§4 が掛け算そのものを取り下げたので優先度は下がっている。
