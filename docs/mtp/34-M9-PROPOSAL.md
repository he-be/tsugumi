## 0. 結論

1. **3 連敗の共通形は 1 つ**: ブロックの壁時計は近似的に
   **Σ_blocks max(I/O 露出, GPU busy)** であり、単独レバーはいつも
   「もう片方の床」に食われた (§1-L1)。**単独 A/B で負けたレバー
   (64 スロット、先読み) は捨てられない** — `moe` が削れた後に再評価するまで
   保留である。
2. **User 側の見落としが 6 件ある** (§2)。28 が自分で挙げて誰も実行していない
   計測 3 本 (GPU counters / llama-bench 校正 / mmap プローブ)、
   参照実装を与えたのに未使用のもの 1 件 (`mul_mm_id`)、
   誰も名前を挙げていない参照 2 件 (**MTLIOCommandQueue** と
   **`--draft-p-min` の的中前提を無料で測れる `outLogits`**)。
3. **推す本命は「適応ドラフト打ち切り」(P3) である。**在庫のレバーで唯一、
   **GPU (moe はペア比例、27 §6) と I/O (union のバイト) の両方の床を同時に削る**。
   受理規則は変えないのでゲート 1 は構造的に通り、前提検定は
   **既存の `outLogits` 口だけで半日**でできる (§3)。
4. **28 §7 のような t/s 合算表は本書には置かない。**平均で積んだ期待値は
   2 回続けて外れた (29 §5、31 §6)。期待値は P1 の台帳 (ブロックごとの
   (io, busy) 結合分布) の上で立て直してから言う (§1-L2)。

## 1. 負例から抜く規則 — 6 つ

**L1. 壁時計は Σ max(io, gpu) で読む。片側だけの改善は出ない。**
30 (I/O 側に足して GPU 側が空いていない)、32 (GPU を 2.1 ms 削って fetch が床)、
33 (io を 0.45 s 削って busy が 1 ms も動かない) — 3 回とも同じ負け方である。
33 §4 が初めてブロックを大きさ別に並べて、48 スロットの中央値は GPU 律速・
最大ブロックだけ I/O 律速と**分布が割れている**ことを示した。
⇒ **レバーを引く前に、そのレバーが削る資源が「どのブロックで」束縛かを
台帳で確認する** (P1)。単独で負けたレバーの再評価は、相方の床が動いた後。

**L2. 平均で割った導出は分布に負ける。**
29 §5 の「層あたり I/O 1.50 ms」は割り算の平均で、実測は 2.0 ms (30 §5)。
32 §5 の「fetch が call の 58%」は**最大ブロックの姿**で、分布の中央では
すでに GPU 律速だった (33 §4)。⇒ 期待値は分布 (ブロック別・層別) の上で積む。
スカラー 1 個の「層あたり」「ブロックあたり」から t/s を導出しない。

**L3. 合成ベンチは production の形状ヒストグラムを先に測ってから。**
31 §5 は「タイル = 16 エキスパート・最大行数は常に 4」と置いて −17% を導出した。
実形状 (5.68 エキスパート、43% は分割が発火しない) を入れ直すと計器は
−2.07 ms を予言し、実測 −2.12 ms と 3% で合った (32 §4)。
**計器は正しかった。置いた形状が間違っていた。**⇒ 合成ベンチに渡す形状は
仮定せず、production に 1 行の計器 (ヒストグラム) を足して取る。

**L4. 固定費を台帳に入れる。**予測の router 1 本/層で −1.0〜1.2% (30 §3)、
追加ディスパッチ 1 本で +2.3% = 12.6 µs/本 (32 §3)。どちらも 29/31 の導出には
入っていなかった。⇒ ヒント・分割・計器の類は「本体の利得 − 固定費」で出す。
固定費は対照 (N=0 / nocap) で先に単離する — この単離のやり方自体は
30 §3 と 32 §3 が確立したので、以後は必ず使う。

**L5. 機構の成功指標で壁時計を語らない。**先読みの的中率は予測どおり 70% 出て、
それでも遅くなった (30)。hit 率は先読みで必ず悪化するから判定に使えない
(29 §7)。⇒ 判定は常に交互 (順序均衡 ABBA) の壁時計。機構指標は
「機構が壊れていないこと」の確認にだけ使う。

**L6. 測定の衛生が 2 回、系列を切った。**27 §7 の 8.90 GB/s は
ページキャッシュ込みで、冷たい天井は 6.0〜6.5 GB/s (33 §1) — この幻の帯域が
29 §5 の楽観の一部である。プローブは未コミットで書き直しになり (33 §1)、
ベンチ資産 `IMG_2112.JPG` がワークツリーから消えて md5 系列が切れた (33 冒頭)。
⇒ プローブとベンチ資産は git に入れる。冷温はプロトコルで固定する (P6)。

## 3. 本命 — P3: 適応ドラフト打ち切り (28 §4-2 の昇格)

**なぜ今これか。**L1 で見ると、在庫のレバーはほぼ全部が片側しか削らない
(`moe` 系 = GPU、スロット/先読み/mmap = I/O)。**ドラフトのペアを減らすことだけが
両側を同時に削る**: `moe` の時間はペア数に比例し (27 §6、32 §4)、ブロックが
読む union のバイトは行数に単調である。しかも受理長は IMG_2113 基準で
**1.644** に下がっており (33 冒頭)、bs=4 の 3 ペア中、平均 1.4 ペアは
**受理されない位置への支出**である。story 系 (a=0.937、26 §2) では 3 ペア中
約 2.9 ペアが捨てられている。

- 27 §3 の「ミス/産出tok は k=2〜6 で平坦」は**一様な k** の話である。適応打ち切りは
  「受理されそうにない位置だけ」を削るので、産出を保ったままペアを減らす —
  平坦線の**下**に出られる可能性がある (**未確認**、これが検定対象)。
- **正しさ**: 受理規則 (D5) は変えない。受理されるのは target 自身の draw に
  一致した接頭辞だけなので、**ドラフトを何本出そうが出力列は target の greedy 列
  そのもの** — ゲート 1 は構造的に通る (`TF_MTP_DRAFTS=0` でも同文、23 §2 が実測済み)。
  変わるのはラウンド数と受理列だけである。
- **参照実装**: llama.cpp `--draft-p-min` (`common/speculative.cpp:335`)。

**段取り** (L3 の規則どおり、前提検定 → 形状実測 → 実装):

1. **前提検定 (半日、カーネル変更なし)**: `DraftForward` の `outLogits` を有効に
   した probe run で、各ドラフト位置の (top-1 margin, 実際に受理されたか) を
   ダンプし、ROC を引く。margin で受理/棄却が分離しないならここで捨てる。
   分離するなら閾値 τ ごとに「残るペア数 / 失う受理」の表を出す。
2. **バイト側の見積もり (半日)**: 既存の expert トレース + `mtp_expert_sim.py` で、
   打ち切った行を union から抜いたときのミス/産出tok を再生する。
   27 §3 の平坦線の下に出るかはここで決まる。
3. **実装 (1〜2 日)**: production の drafter は logits を読まないので、argmax
   カーネルに margin (top1 − top2) の出力を 1 語足し、margin < τ で round を
   打ち切る。τ は env (`TF_MTP_DRAFT_PMIN` 相当)、既定は A/B で決める。
   判定は L5 のとおり ABBA の壁時計のみ。**可変長ブロックになるので、
   受理列・ラウンド数は off と一致しなくなる** — md5 一致だけをゲートにする。

## 5. 期待値について — あえて合算表を置かない

28 §7 は「A で 26、B で 30、C-4 で 33 t/s」と積み、A と B の実測は ±0 と −3.5%
だった。原因は §1 の L1〜L4 に分解済みで、同じ積み方をもう一度やる理由は無い。

代わりに**判定条件だけ**置く:

- P3 は、検定 1 (margin の ROC) で「受理の 9 割を保ったままペアを 3 割落とす τ」が
  存在しなければ実装しない。
- P2 は、counters が発行/占有率律速を示さなければ (= 実 DRAM トラフィックが
  帯域床に近ければ)、`moe` はこの形状の相場と判定し、P7 の校正値と突き合わせて
  **A を閉じる** — そのときの残レバーは P3 と P5 だけになる。
- P4 の行列で「32 スロット 30 t/s」(28 の目標) に届く組が出なければ、
  30 t/s の運用点は 48 スロットと確定し、28 §4-3 の動的スロット
  (メモリ圧力で 48 → 32) を製品判断として上に戻す。

**数字を言うのは P1 の台帳が出てからである。**
