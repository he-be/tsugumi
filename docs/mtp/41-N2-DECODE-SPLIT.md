# 41. N2 — decode の壁時計を GPU busy と待ちに割る: 残り 25 ms は GPU busy だった

測定: 2026-08-20 07:52〜08:23、M3 Pro 18GB / macOS 15.7.5 / commit `7732643`。
**46 run すべて rc=0、`Sources/` は 1 行も変えていない。**
一次資料は `bench/mtp40/` (bs=0)、`bench/mtp40b/` (bs=2,3)、`bench/mtp40d/` (bs=4)、
`bench/mtp40c/` (細分、帰属専用)。`sudo sysctl iogpu.wired_limit_mb=14336` 済み。

[37](37-M9-B-PROPOSAL.md) §3 の **N2**。37 §1a は既存ログ 9 本から
「`decode/tok` の 4 項の外に 21〜25 ms/tok が残る」を出し、
**それが GPU busy なのかホスト往復の待ちなのかは footer では分解されない**と
明示的に開けていた。分解した。使ったのは既に在る環境変数 2 つだけである
(`TF_PREFILL_HOST_PROFILE=1` が decode 側の busy/idle 記録を開き、
`TF_PREFILL_GPU_PROFILE=1` がその内訳を段に割る。`RealForwardRunner.swift:2696-2716`)。

軸は 2 本 — **register** (`2^H` の代理ラベル。38 §3) と **スロット数**。
運用点 (温度・top-k・top-p は CLI 既定) / 3 反復 / 20 秒クールダウン / 暖機 1 本、
画像は 39 (N1) の画像 A (`NO_FUSION_0401_001.png`)。

`残差 = wall − io − cb1 − cb2 − head` (37 §1a の「4 項の外」) を同じ run で計算し、
同じ run の GPU busy と並べる:

## 3. 運用点は投機オンである — ブロック経路の同じ分解 (**実測**)

37 §1a の 2 つ目の穴 (「bs>0 では 4 項が全部 0.00 になる」) は、
**計器が無いのではなく別の計器が持っていた**。`TF_PREFILL_HOST_PROFILE=1` は
ブロック 1 個ごとに `[prefill host …]` と `[prefill gpuq busy/idle/span]` を吐き、
`TF_PREFILL_GPU_PROFILE=1` を足すと `[prefill gpu attn/shared/moe/tail/head]` が付く
(36 §14 はこの前半だけで 32 スロットの台帳を作った)。48 スロット・運用点で取り直した。
ブロックとプロンプト prefill の分離は `experts > 0` (36 §16 の訂正版)。

ms / **産出**トークン (ブロックだけを合算。ドラフトは含まない):

`step(bs) = F + c·bs` をブロック 1 個の GPU 秒で、隣接ペアの傾きから解く

⇒ **検証位置 1 つの限界費用 `c` の 89〜94% は routed MoE である。**
`attn` (+0.07〜+0.67)、`head` (−0.03〜+0.09)、`tail` (0.00) は **bs に依らない** —
層の前半と lm head はブロック 1 回ぶんしか払わない。
**36/39 が壁時計だけで測ってきた `c` に、初めて GPU の段の名前が付いた。**

壁時計の `c` は **8.59 / 8.95 ms** (bs 2→3) で、その **81〜84% が GPU busy** である。
base を §1 の同条件 bs=0 に取ると `c = 8.59/42.26 = 0.203` (ja_prose) /
`8.95/49.27 = 0.182` (en_bullets) base/位置で、**36 §4a の本番帯 (temp 1.0 で
0.128〜0.187) の上端に載る。39 §1 の costProbe 値 (48 スロットで 0.287) ではない。**
**N5 の食い違いは計器側にある**という 36 §4e の読みを支持する (**導出**)。

**F の壁時計 27.25 / 38.19 ms のうち GPU busy は 15.31 / 18.19 ms** で、
残り **11.9 / 20.0 ms がブロック 1 回あたりの待ち**である。22 §7 が
「30 層ぶんのホスト往復 ≈ 20 ms」と**導出**した枠はここに在るが、
**register だけで 1.7 倍動く**ので純粋な往復レイテンシではない (**実測**)。

## 5. `attn` バケットの中身 — 7 割は dense 射影で、attention 本体ではない (**実測**)

`TF_PREFILL_GPU_PROFILE=2` で層の前半を 9 つに切った 6 run。
**細分はグループごとにコマンドバッファを切るので壁時計が膨らむ。
比率だけが読める値である** (`PrefillGPUProfile.swift` の doc comment)。
バケット内の比 (Σ秒 / Σtotal、%):

| セル | qkv | oproj | post | attn.swa | rope | attn.full | embed/norm/kvcopy |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| ja_prose | **38.1**±0.3 | 19.2±0.1 | 19.1±0.2 | 9.6±0.1 | 8.4±0.2 | 0.1 | 0.0 |
| en_bullets | **38.5**±0.4 | 19.3±0.3 | 19.7±0.2 | 9.6±0.1 | 8.7±0.4 | 0.1 | 0.0 |

⇒ **F の最大項 `attn` 11.0 ms/ブロックのうち、attention 本体は 9.6% (約 1.1 ms) しかない。**
**Q/K/V 射影 38% + 出力射影 19% = 57% が dense 射影**で、
post (post-attention の norm と router) の 19% を足すと **76%** になる。
(細分 run の Σtotal は 10.5 ms/ブロックで細分なしの 11.1 の 95%。上の絶対値は
比を 11.0 に当てたものである。)
22 §3 の感度表は「F が唯一の大きなレバー」と言ってきたが、**その F の中身は
24-M5.5 / 25-M5.6 が 2 度削った attention ではない。**

## 6. 判定 — 34 の P2 は**進む**。ただし理由が入れ替わる

37 §4 が置いた N2 の判定条件は「残り約 25 ms/tok の**半分以上が GPU busy** なら
P2 (counters) に進む / **待ちが主なら P2 を閉じる**」だった。

- **残差 24.8〜28.3 ms/tok に対し busy 25.4〜26.4 ms/tok** (§2)。**進む。**
- **ただし 34 が置いた問い (「`moe` に 2 倍眠っているか」) は的が小さい。**
  `moe` は scalar decode の busy の **30〜35%**、運用点 (bs=2) の busy の **37〜42%**
  であって、全部ではない。
- **入れ替わる理由はこちらである: `c` を動かせるのは `moe` だけである** (§4)。
  39 §2 が「48 スロットでも最適 bs は 2」と出し、36 §0-(7) が
  「広い幅が負ける理由は費用側だけ」と書いた、その費用側の正体が
  **1 位置 6.4〜6.9 ms の routed MoE** だと分かった。**bs を伸ばしたいなら
  触るのは `moe` 以外に無い。**
- **F を狙うなら的は attention ではない** (§5)。**次の提案 (N7 相当) はここに置く。**

**N2 の 2 つ目 (投機オン経路で 4 項を出す) は、コードを変えずに閉じる** (§3)。
scalar decode の 4 項カウンタをブロック経路に配線する必要は無い —
**ブロック経路には既により良い計器 (段別ホスト台帳 + マージした gpuq) がある。**
37 §5 が「設計判断」と書いた口は、**開けない**を選ぶ。

## 7. 限界 (**未確認**)

1. **計器が測定対象を 1.9〜2.3% 遅くする** (同一 seed・同一セルの env 有無で
   23.420 対 23.856 / 20.416 対 20.881 t/s)。**busy の絶対値は計器付きの run のものである。**
   36 §14a の +0.09% より大きいのは、decode 側の窓が 32 歩ごとに記録を開くためと見られる。
2. **48 スロットが 32 スロットより遅く出た** (ja_prose、wall 42.26 対 41.00)。
   ただし **32 の 7 run は 48 の 10 run の後に回している**うえ、この日の熱ドリフトは
   **速くなる側に +0.85%** である。差 1.26 ms のうち約 0.36 ms はドリフトで説明が付く。
   **符号を主張するには ABBA が要る。**(39 §6-3 が画像 B で見た符号の不一致と同じ場所である)
3. **`busy` が register でわずかに動く** (+0.48〜+0.91 ms/tok)。
   動くのは `shared` と `moe` だけで、`attn` と `head` は動かない。
   **候補は 2 つ**: 並行する pread とのメモリ競合、タイル数の増加。
   **どちらかを決める測定は取っていない。**
4. **`c` は bs 2〜4 の内側でも完全な直線ではない** (ja_prose の moe で
   +6.76 対 +5.55、18% 差)。36 §4d が bs≥6 で見た破れの弱い版である。
5. **細分 (§5) はブロック 1 個では読めない** — ログが 1 ms 刻みで、細目は
   0.000〜0.005s だからである。100 個以上を合算してはじめて意味を持つ (36 §14a と同じ)。
6. **scalar decode 側に細分の口は無い** (`Detail` はチャンク経路だけ)。
   §5 の 9 分割はブロック経路の `attn` の話であって、§1 の 11.1 ms/tok のものではない。
7. **画像 1 枚・register 2 本・スロット 2 点。**`2^H` の連続量としては 2 点しかない。
8. **計器の名前が衝突する。**`[prefill gpu]` と `[prefill host]` は `tail` と `head` を
   両方持つ (意味は別物)。集計で先に読んだほうが上書きされる —
   `bench/mtp40b_analyze.py` は GPU 側に `g_` を付けて避けている。
