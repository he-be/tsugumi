# 18. M4.6 の結果 — verify のボトルネックは演算でも dispatch でもなく expert I/O だった

測定: 2026-08-18、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3。
対象モデル `scratch/gemma4-qat.gturbo`。

表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

---

## 0. 結論 — math が損益分岐を超えた。ゲートにはまだ届かない

17-M4.5 §4 は「GPU が動いていない 38 ms の正体は層ごとのホスト往復と dispatch 数」と
書いた。**これは外れていた。**新しいホスト側プロファイル (§1) で 1 ブロックの壁時計を
段ごとに割ると、k=4 では **40 ms が expert の読み出しでブロックしていた** (§2)。
往復も dispatch も合計で 3 ms に満たない。

読み出す**バイトは 1 バイトも減らしていない**まま、それを GPU の仕事の裏に隠した (§3)。
費用 (**実測**、warm、decode ステップ換算):

| | k=1 | k=2 | k=4 | k=8 |
| --- | ---: | ---: | ---: | ---: |
| M4 の借り物カーネル (15-M4) | 3.48 | 4.65 | 6.02 | 8.53 |
| M4.5 (17-M4.5) | 1.67 | 2.12 | 2.74 | 4.89 |
| M4.5 を同じビルドで測り直し (`LOOKAHEAD=0`) | 1.65 | 2.02 | 2.68 | 4.79 |
| **M4.6** | **1.60** | **1.77** | **2.34** | **4.33** |
| 16-M4.5 §3 の予測 (バイトのみ) | 1.00 | 1.23 | 1.55 | 1.99 |

1 ラウンドの費用 = `verify(k) + (k−1) × 0.098` (10-M0 §2) に 14-M3.5 §4 の実測受理長を
入れると (**導出**):

| プロンプト | a (bs=4) | 産出 | 費用 (steps) | M4.5 | **M4.6** |
| --- | ---: | ---: | ---: | ---: | ---: |
| math (temp 0) | 1.947 | 2.947 | 2.63 | 0.97 | **1.12** |
| m (temp 0) | 1.562 | 2.562 | 2.63 | 0.85 | **0.97** |
| story (temp 0) | 0.937 | 1.937 | 2.63 | 0.64 | **0.74** |

**math で初めて 1 を超えた。**ただし 16-M4.5 §6 の停止条件 (`verify(1) ≤ 1.15`、
`verify(4) ≤ 1.9`) には**まだ届いていない** (1.60 / 2.34)。

正しさは M4.5 と**同一**である: 12 cases PASS、logits の中央値・最悪値・argmax は
17-M4.5 §5 の表と 1 桁目まで同じ (§5)。今回入れたのは**読み出しをいつ始めるか**と
**タイルをどの順で encode するか**だけで、カーネルにも数値にも触っていない。

## 1. まず測る道具を足した — ホスト側プロファイル (**実測**)

`PrefillGPUProfile` はコマンドバッファの GPU スパンしか見えないので、
「GPU が動いていない時間」の中身が原理的に分からない。同じ形で**呼び出しの壁時計を
段ごとに割る** `PrefillHostProfile` を足した (`TF_PREFILL_HOST_PROFILE=1`、
stderr に 1 ブロック 1 行)。段は enc.front / wait.front / drain / route /
wait.shared / meta / fetch / enc.moe / wait.tile / tail / head と、
どの段も取らなかった残り (other)。expert の要求数・ミス数・読み出し秒も同じ行に出す。

`total` が壁時計に一致するように取ってあるので、**取りこぼしは other に落ちる**。
実測では other は 1 ms 未満で、内訳は網羅されている。
`PrefillGPUProfile` の桁も `%.2fs` → `%.3fs` に上げた (0.02s 表示では
1 ブロック 30〜120 ms の内訳が読めなかった)。

## 2. 分かったこと — verify ブロックは expert I/O で律速していた (**実測**)

M4.5 の実装 (`LOOKAHEAD=0`) を 1 ブロックぶん割ると:

| k=4、1 ブロックの中央値 | ms |
| --- | ---: |
| wait.front (層前半のコマンドバッファ待ち = 前層 MoE の残り + 自層 attention) | 47 |
| **fetch (expert をスロットに読み込む待ち)** | **40.5** |
| head | 7 |
| wait.shared | 5 |
| enc.front / drain / enc.moe / route / meta / other | 計 5 |
| = 壁時計 | 106 |
| (うち GPU スパン合計) | 68 |

`fetch` の中身は**実際の読み出し**である: k=4 で 1 ブロックあたり expert 要求 572 回、
**ミス 58 回 = 0.20 GB を 5.0 GB/s で読んでいる** (**実測**)。往復や dispatch ではない。

これは MTP に不利な事実ではない。**同じ 4 トークンを decode で回せば 4 × 0.096 GB
= 0.38 GB** 読むので、ブロックが expert 和集合を畳む利益は**すでに出ている** (**導出**)。
問題は畳んだ後の 0.20 GB が **GPU の仕事とまったく重なっていなかった**ことで、
1 ブロック = GPU 68 ms + 読み出し 40 ms がほぼそのまま直列に並んでいた。

### 2-1. 外した案 — 層の和集合を先に 1 回で読む (**実測**)

タイルごとに読むのをやめ、層の expert 和集合を 1 プランで読んでから encode に入る、
という形を試した。`executeExpertCachePlan` はミスを `concurrentPerform` で並列に
読むので、「4 波 × 4 read」が「1 波 × 16 read」になる。

**遅くなった** (k=4 で 105.5 → 116 ms)。読み出しは**帯域律速で、並列度を上げても
合計時間が縮まない**。しかも待ちが全部 encode の前に来るので、それまで多少は
重なっていたぶんまで露出する。この案は捨てた。

## 3. 入れたもの — 読み出しを GPU の裏に回す

| # | 内容 |
| --- | --- |
| **a** | `Model.startRoutedExpertFetch(plan:)` — 読み出しを**始めて戻る**。返り値の `RoutedExpertFetchHandle.wait()` で結果を受け取る。ミス 0 のプランは呼び出しスレッドでそのまま実行する (キューへのホップのほうが高い) |
| **b** | 層のルーティングが grouping まで済んだ時点で、**その層の全タイルの読み出しを一度に発行する**。プランは順に作り、割り当てたスロットを積んで次のプランに `avoidingSlots` で渡すので、飛んでいる read が別の read の書き込み先に着地することはない |
| **c** | **常駐タイルを先に encode する。**タイルは互いに独立 (`routePartials` の別々の範囲に書き、reduce は全タイルの後) なので、encode 順は自由に選べる。ミス数の昇順に並べ替えると、まだ読んでいるタイルが GPU の仕事の裏に入る |
| **d** | shared expert の完了待ちを層末尾の drain まで遅らせる。層 tail は `h1` を **GPU 上で**読むし、同じキューで後ろに並んでいるので、ホストが途中で止まる理由がない |

b と c は**セットでないと効かない**。b だけ (全タイルを発行、encode 順はそのまま) では
k=4 で 105 → 100.5 ms にしかならなかった: 層のミスはタイルに均等には散らばらず、
「重い read を持つタイル」が先頭に来ると GPU は結局その read を待つ。
c を足すと 100.5 → 96.5 ms になる (**実測**、同一ビルドの 3 回の測定)。

`TF_MTP_ROWS_LOOKAHEAD=0` で a〜d を丸ごと元に戻せる。
**prompt prefill と decode 経路は無変更**で、この経路は `blockPipeline`
(= `verifyBlock` 由来かつ k ≤ 8) かつ**層の expert 和集合がキャッシュに収まる**ときだけ
通る。収まらない層 (k=8 で頻発) は M4.5 の per-tile 経路のままである — そこは
タイルが途中でスロットを返すので、飛んでいる read の着地先が保証できない。

## 4. 効き — 段ごとの実測 (**実測**)

同じビルド・同じ run 内で `TF_MTP_ROWS_LOOKAHEAD` を 0/1 した 2 回 (a-off / d-on)。
機械が run ごとに drift する (17-M4.5 §3) ので ms と比の両方を出す:

| k=4、1 ブロックの中央値 | M4.5 (`=0`) | **M4.6 (`=1`)** |
| --- | ---: | ---: |
| 壁時計 | 106 ms | **93.5 ms** |
| GPU スパン合計 | 68 ms | 70 ms |
| GPU が動いていない時間 | 38 ms | **23.5 ms** |
| fetch でブロックした時間 | 40.5 ms | **32 ms** |
| 読み出しの合計時間 (重なりを含む) | 40 ms | **52 ms** |
| 読み出したバイト | 0.20 GB | **0.20 GB** |

読み出しの合計 (バックグラウンドのスレッドで測った各 read の和) が 40 → 52 ms に
**伸びている**のに壁時計が縮んでいるのが、重なりが起きた証拠である。
バイトは同じなので、**これは I/O を減らした結果ではなくスケジュールの結果**である。

ブロック時間 (ms/block、2 回ずつ):

| | k=1 | k=2 | k=4 | k=8 |
| --- | ---: | ---: | ---: | ---: |
| `LOOKAHEAD=0` | 68 / 68 | 83 / 83 | 110 / 110 | 197 / 195 |
| **`LOOKAHEAD=1`** | **62 / 65** | **68 / 72** | **94 / 95** | **172 / 176** |

- **k=1 は d しか効かない** (層あたりタイルが 1 本なので隠す相手がいない)。
  それでも 68 → 63.5 ms 相当で、shared expert の待ち 3 ms がまるまる消えている。
- **k=8 でも効く** (197 → 174)。和集合がキャッシュに収まらない層は旧経路に落ちるが、
  収まる層のぶんだけ縮む。読み出しの合計は k=8 で 99 → 190 ms まで伸びていて、
  ここが最も重なっている。

## 5. 正しさ — M4.5 と同一 (**実測**)

```
.build/release/TurboFieldfareKernelCheck --verify-block scratch/gemma4-qat.gturbo
PASS  12 cases (verify block)
```

`verify/baseline/prefill-vs-decode` は 1.762e-03 (M4/M4.5 と同値)、
k=1 の中央値 1.2e-03 / 最悪 9.8e-03、k=4 の中央値 1.4/1.3/1.1/1.3e-03 /
最悪 2.4e-02、argmax は logits ヘッド 128/128・fused greedy ヘッド 48/48 一致 —
**17-M4.5 §5 の表と同一の数字**である。カーネルにも、どのカーネルが呼ばれるかにも
触っていないので、これは期待どおりの結果で、そのことの確認になっている。

`Scripts/test.sh` は **842 テスト / 143 スイート / 11 issue** で、
issue の内訳は M4.5 と同じ既知の陳腐化 4 スイートのみ (`AppModelInstallTests` /
`AppRuntimeOptionsTests` / `AppContextLengthOptionTests` /
`RuntimeConfigurationTests`)。**新規失敗ゼロ、テスト数も M4.5 と同じ**である
(今回はカーネルを足していないので新しいユニットテストもない)。

タイルの encode 順を変えたことが数値を動かさないのは、タイルが
`routePartials` の互いに素な範囲に書き、reduce がその全部の後に走るからである
(§3 c)。順序が入れ替われば数字が動く実装なら、この 12 本のどれかが落ちる。

## 6. 残っているもの

k=4 で GPU が動いていない時間は 38 → 23.5 ms まで減ったが、まだ 23.5 ms ある。
そのほとんどは依然 `fetch` (32 ms のうち隠しきれなかったぶん) である。
層の中で読み出しに重ねられる GPU の仕事は routed MoE の 35 ms が上限で、
読み出しは 52 ms あるので、**層の中だけでは原理的に隠しきれない** (**導出**)。

続けるなら次に測る価値があるのは、順に:

1. **キャッシュのスロット数**。いまは層あたり 48 (= 5.0 GB)。
   `RuntimeConfiguration.allowedExpertCacheSlots` は 112 まで許す。
   ミスが減れば読むバイトが減り、これは重なりの話ではなく総量の話になる。
   メモリ (18 GB 機で 64 スロット = 6.6 GB) との釣り合いを実測で見る (**未確認**)。
2. **層をまたいだ先読み。**層 L の expert は層 L の attention が終わるまで分からないが、
   **1 つ前のブロックの同じ層の選択**は予測子として使える。当たれば読み出しが
   前の層の GPU 時間に重なる。外すと帯域を無駄にするので、**予測精度の実測が先**
   (**未確認**)。
3. **層前半 (17-M4.5 §7 が挙げていた次の 1 段)**。GPU 内訳は attn 30% で、
   その中は qkv 36% / oproj 20% / post 26% / attention 本体 13% (**実測**、
   `TF_PREFILL_GPU_PROFILE=2`)。qkv と oproj は M4.5 で既に k 行 GEMV に
   なっていて帯域床に近く、**ここを触っても GPU 時間はほとんど減らない**。
   17-M4.5 §7 が次の 1 段に挙げた根拠 (「dispatch 数とホスト往復」) は §2 で
   否定されたので、**この項目の優先度は下がった**。
4. ゴール条件 (vision + Reasoning ON) はまだ一度も測っていない (16-M4.5 §5-3)。
   ブロックが SSD ミスを和集合に畳む利益は §2 で初めて数字になった
   (k=4 で 0.20 GB 対 decode 4 歩の 0.38 GB) ので、**そこが最も効く条件**である。

`.build/release/TurboFieldfareKernelCheck --verify-block scratch/gemma4-qat.gturbo`
(正しさ 12 cases + warm の cost 行)。
`--verify-cost-only` に `TF_PREFILL_HOST_PROFILE=1` を足すと §2/§4 の内訳、
`TF_PREFILL_GPU_PROFILE=1` (または層前半を割る `=2`) を足すと GPU 側。
A/B は `TF_MTP_ROWS_LOOKAHEAD=0`。
