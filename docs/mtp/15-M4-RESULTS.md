# 15. M4 の結果 — verify パスと KV 巻き戻し

測定: 2026-08-18、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3。
対象モデル `scratch/gemma4-qat.gturbo`。

表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

> **[2026-08-18 追記] §4 の実測値は有効。§4-1 の当てはめ (`2.6 + 0.86k`) と
> §5 / §5-1 の含意は [16-M4.5-PLAN.md](16-M4.5-PLAN.md) が差し替えた。**
> 3.8 倍の乖離は費用の構造ではなく**借りたカーネルの性能**で、
> 4 点全部が「64 行タイルの FLOPs ÷ 2.9 TFLOPS + head を k 回読むバイト」で
> 残差 4% 以内に説明できる。したがって §5 が無効化した 14-M3.5 §5 の速度比は
> **有効なまま**であり、無効なのは §5 の方である。

## 0. 結論 — 正しさは全部通った。費用が想定の 3.8 倍だった

04-PHASES M4 の出口条件は 3 つとも成立した (**実測**、§1〜§3):

| # | 出口条件 | 結果 |
| --- | --- | --- |
| 1 | 全位置 logits が 1 トークンずつの `produce` と一致 | **成立。**argmax は 128/128 一致 (logits ヘッド) + 128/128 一致 (fused greedy ヘッド)。数値差は §2 |
| 2 | 巻き戻し後の続きが「巻き戻さなかった世界」と一致 | **成立。**16/16 トークン一致 |
| 3 | わざと壊して FAIL する | **成立。**短い/長い/巻き戻さないの 3 通りとも 0/16 (k=8 では 1/16) |

`TurboFieldfareKernelCheck --verify-block` が **12 cases PASS / exit 0**。

**しかし M4 で初めて測った verify の費用が、10-M0 §2 の費用モデルと合わない** (§4):

| k | 10-M0 §2 の `cost(k)` (**導出**) | M4 の実測 |
| ---: | ---: | ---: |
| 1 | 1.00 | **3.7** |
| 2 | 1.32 | **4.8** |
| 4 | 1.85 | **7.0** |
| 8 | 2.68 | **9.4** |

(単位はどちらも「decode 1 トークンぶん」。実測は decode 38.2〜38.5 ms/tok に対する比。
2 run で再現性 2% 以内、§4-1)

M0 の式は「forward が読む重みのバイト数」だけで費用を書いており、
**チャンク経路のカーネルが 4 トークンに対してどれだけ無駄な演算をするかが入っていない**。
GPU の内訳を取ると verify 1 ブロックの 60〜69% が routed MoE で、そこは
64 行タイルを 1 行のために回している (§4-2)。実測は直線に乗る:
**`verify(k) ≈ 2.6 + 0.86k` decode ステップ** — 固定費 2.6、
そしてブロックに 1 トークン足す限界費用が **decode 1 回とほとんど変わらない**。

この費用のままだと、14-M3.5 §5 の受理率を入れても **MTP は 2.5〜3.7 倍の減速**
になる (§5)。**M5 (ループ統合) に進む前に verify の費用を潰す段 (M4.5) が要る。**
ただし §5-1 のとおり、**固定費を全部消しても黒字にならない**: 限界費用を
10-M0 §2 の帯域下限まで下げて初めて 1.59 倍で、余裕はほとんどない。

## 2. 全位置 logits — argmax は完全一致、数値差はチャンク経路のもの

384 tok ぶんではなく **128 位置** (k=4 × 32 ラウンド) で、各ラウンドごとに

1. `produce` を k 回回して参照行を取る (この時点でカーネルは decode 経路)
2. `rewind(to:)` でカーソルを戻す
3. `verifyBlock` で同じ k トークンを 1 回で流す
4. 行ごとに突合

という形で測った。**参照行は巻き戻しの前に確保しているので、巻き戻しが壊れていても
偽の PASS にはならない** (壊れていれば 4 で外れる)。

| | median | worst | 絶対値 median | 絶対値 worst | argmax 一致 |
| --- | ---: | ---: | ---: | ---: | ---: |
| **k=1** (投機なしのチャンク経路) | 1.045e-3 | 3.545e-2 | 0.039 | 1.625 | **128/128** |
| **k=4** | 1.061e-3 | 3.786e-2 | 0.047 | 1.625 | **128/128** |
| fused greedy ヘッド k=4 | — | — | — | — | **128/128** |
| k=8 (64 位置) | 1.250e-3 | 2.387e-2 | — | — | **64/64** |

相対値は行ごとの `max|verify − produce| / max|produce|`。

**差はブロックが作っていない** (**実測**)。決め手は 3 つ:

1. **k=1 と k=4 の分布がほぼ同じ** (worst 比 1.068)。k=1 の `verifyBlock` は
   投機の要素がゼロ (1 トークンをチャンク経路で流すだけ) なので、
   ここで出る差はブロック幅の関数ではない。
2. **worst の行が k=1 と k=4 で同じ** (pos=129、abs=1.625)。
3. **ブロック内の深さに傾向がない。**k=8 の i=0..7 の median は
   1.0e-3〜1.8e-3 で平ら。行 i はブロックが書いた i 行に attend するので、
   KV に系統差があればここが右上がりになるはずで、なっていない。

つまりこれは **「チャンク経路 対 スカラー decode 経路」の既存の差**である。
その差は MTP 以前から製品に入っている: プロンプト最終位置の 1 行は必ず
チャンク経路が出しており、最初の生成トークンはそこから引かれる
(`RawCompletion.swift` の `PrefillSeed`)。同じ位置を両経路で出して比べると
**rel 1.762e-3 / abs 0.037** (**実測**) で、上の median と同じ水準。

原因は 30 層 × 2816 の積み上げを別カーネル (タイル化 `simdgroup_matrix` QMM 対
行ごとの GEMV) で回すことによる累積順序の違い (**導出**)。

### 2-1. 04-PHASES §4 の中止条件について

「verify の全位置 logits が 1 トークン decode と一致しない、かつ近似でしか通らない
→ 通さずに報告」に該当する。**報告する。**判断材料は次のとおり:

- **一致しない。**bit 一致ではない。worst で 0.04 相対 / 1.6 logit。
- ただし**その差は verify が作ったものではない** (§2 の 1〜3)。同じ差は
  今の製品が毎ラウンド 1 回踏んでいる。
- **トークンの選択は 256/256 一致** (logits ヘッド 128 + greedy ヘッド 128)。
- 危険度の指標として、参照行の top-1 / top-2 差がその行の数値差より小さい
  「競り合った行」を数えた: **128 行中 3 行** (k=1 では 1 行)。この 3 行でも
  実際の argmax は一致した。競り合った行の定義は語彙全体の最大差を使う保守的な
  もので、真の入れ替わり確率はこれよりずっと低い (**導出**)。

**M5 のゲート 1 (「MTP あり/なしの出力が完全一致」) は、この差の上に立っている。**
競り合った行が 2.3% ある以上、長い生成で 1 回も入れ替わらない保証はない
(**未確認**)。M5 では「完全一致するか」ではなく**「何トークン目で分岐したか」を
測る**形に変えるべきである。分岐が起きた場合でも、MTP あり側は
「チャンク経路が定義するモデル」を決定的に実行しており、壊れているわけではない。

## 3. KV 巻き戻し — 一致 16/16、検出力 3/3

プロンプトを prefill したあと `verifyBlock` で k トークン書き、
`rewind(to: p + a)` で a=k/2 だけ受理したことにし、そこから 16 トークンを
`produce` で素直に伸ばして、**一度も投機しなかった世界**の続きと突き合わせた。

| 巻き戻し先 | 一致 (k=4) | 一致 (k=8) |
| --- | ---: | ---: |
| `p + a` (正しい) | **16/16** | **16/16** |
| `p + a − 1` | 0/16 | 1/16 |
| `p + a + 1` | 0/16 | 1/16 |
| 巻き戻さない (`p + k`) | 0/16 | 1/16 |

**1 位置ずれただけで最初のトークンから外れる。**検出力としては十分で、
「巻き戻しが効いていないのに通ってしまう検査」ではないことが言える。

ユニットテストも足した (`KVCacheManagerTests`): カーソルだけが動くこと、
リングが巻いた領域でもスロット写像が変わらないこと、
`maxSpeculativeBlockTokens` が容量を増やさない (= 事前条件であって要求ではない) こと。

## 4. verify の費用 — 想定の 3〜4 倍 (**実測**)

### 4-1. 測り方と数字

費用プローブは次を回す:

1. 同じプロンプトから 144 トークンを `produce` で生成し、その系列を記録する
2. **同じ系列・同じ位置**を、k = 1 / 2 / 4 / 8 のブロックで `verifyBlock` に流す
3. decode を**もう一度**測る (前後で挟んで drift を見えるようにする)

いずれも fused greedy ヘッド。512 KiB の logits をホストに読み戻すと
ハーネスを測ることになるため。

正しさの検査を回したあと (= expert キャッシュがヒット率 91.5% まで温まった状態) の
2 連続 run。**再現性は 2% 以内** (**実測**):

| | decode | k=1 | k=2 | k=4 | k=8 |
| --- | ---: | ---: | ---: | ---: | ---: |
| run 1 (ms) | 38.2 /tok | 140 | 182 | 265 | 359 |
| run 2 (ms) | 38.5 /tok | 141 | 185 | 269 | 366 |
| decode ステップ換算 | 1.00 | **3.7** | **4.8** | **7.0** | **9.4** |
| 10-M0 §2 の `cost(k)` (**導出**) | 1.00 | 1.00 | 1.32 | 1.85 | 2.68 |

decode 38.2〜38.5 ms/tok は 13-M3 §7 の 26.87 t/s (= 37.2 ms/tok) と一致するので、
**この条件のプローブは信用できる**。

直線に乗る (**実測**): `ms/block ≈ 100 + 33k`。decode 1 ステップ換算では

```
verify(k) ≈ 2.6 + 0.86k   [decode ステップ]
```

- **固定費 2.6 ステップ。**ブロックを 1 回張るだけで decode 2.6 回ぶん。
- **限界費用 0.86 ステップ/トークン。**ブロックに 1 トークン足すのは、
  そのトークンを普通に decode するのと**ほとんど変わらない**。
  投機デコードが前提にしている「k トークンぶんの重みを 1 回で読む」節約が、
  ここではほぼ効いていない。

> `--verify-cost-only` (プローブだけを 1 プロセスで回す) だと数字が変わる:
> decode 45.8〜60.3 ms/tok、verify は k=2〜8 で 255〜390 ms とほぼ平ら。
> こちらはキャッシュが温まりきる前 (ヒット率 89.1%) の値で、decode 側も
> ベースラインから 20〜60% 遅い。**温まった上の表を採る。**

### 4-2. どこに行っているか

`TF_PREFILL_GPU_PROFILE=1` で verify 1 ブロックの GPU 内訳を取った (k=4、**実測**):

```
[prefill gpu attn=0.05s(20%) shared=0.02s(8%) moe=0.14s(60%) tail=0.00s(0%) head=0.03s(11%) total=0.24s]
```

- **routed MoE が 60〜69%。**この計測時の壁時計 (325 ms) と GPU 合計 (240〜360 ms) が
  ほぼ一致するので、ホスト側の往復ではなく **GPU で本当に時間を使っている**。
- タイル化された routed GEMM は expert ごとに **64 行のブロック**を計算する。
  プロンプトのチャンク (128〜2048 トークン) はそれを埋めるが、
  4 トークンの verify ブロックは 1 expert あたり 1 行前後しか入らない。
  30 層 × 約 32 expert × 64 行 の GEMM を、有効行 4 のために回している (**導出**)。
  §4-1 の固定費 2.6 ステップの主犯はここだと見ている (**未確認** — 直接は切り分けていない)。
- expert I/O は限界費用の側に効く。routed expert は k トークンの和集合として増え
  (10-M0 §2 の実測: 1 forward あたり 240 → 596.9 個 / k=1 → 4)、
  キャッシュの尻尾を引きずり出す。ただし GPU 内訳が moe に寄っている以上、
  **今の実装では I/O より演算の無駄が主**である (**導出**)。

M0 の式が外したのはここである。あの式は「forward が読むバイト数」だけを見ており、
**同じバイト数を読むのにチャンク経路が何倍の演算をするか**を勘定していない。

### 4-3. 当たり — 狭いチャンクでタイル経路を使わない

`PrefillGroupedRoutedMoE` には行数の少ない場合向けの経路
(`encodeStreamedBatched`) が既にある。タイル経路の選択に
「チャンク幅 >= しきい値」を足して A/B した (`TF_PREFILL_MOE_GEMM_MIN_TOKENS=16`、**実測**):

| ms (`--verify-cost-only`、冷えた条件) | decode | k=1 | k=2 | k=4 | k=8 |
| --- | ---: | ---: | ---: | ---: | ---: |
| タイル経路 (既定) | 57.9 | 224 | 387 | 325 | 335 |
| 狭いチャンクは batched | 45.8 | **118** | **262** | **258** | **255** |

絶対値では 20〜47% 速い。ただし **decode 側も同時に下がっており** (この 2 run は
機械の状態が違う)、比の改善は主張できない (§4-4)。方向としては当たっているが、
**これだけでは足りない**ことも同時に見えている: 一番効いた k=1 でも
118 ms = decode 2.6 ステップ相当で、§5-1 が要求する水準には遠い。

`--verify-block` の 12 cases はこの経路でも全部 PASS するので、
**数値は同じで速度だけ違う**ことは確認済み。

しきい値の既定は **0 (従来どおり)** のままにしてある。prefill 本体の速度を変える
変更であり、`bench.sh pp` での A/B が要るため、この段では入れない。

**残りの当たり (未着手):**

- head が 11%。k 行ぶんの lm_head を k 回の GEMV で回している。
  1 回の GEMM にまとめられる。
- attn が 20%。30 層ぶんのコマンドバッファ往復が 4 トークンに対して重い。
- 本命は「decode 経路の routed MoE カーネルを k 行に一般化する」こと。
  expert の重みを 1 回読んで、その expert に routing された k 行のうち
  該当分だけに当てる。チャンク経路を借りずに済むので §2 の数値差も消える。

### 4-4. この測定の限界 (**未確認**)

- キャッシュの温度で数字が変わる (§4-1 の注)。上の表は正しさの検査 (256 位置ぶんの
  decode + verify) を回したあとの状態で、decode がベースラインと一致する条件を選んでいる。
  **冷えた状態では verify が k に対して平らになる**ので、その領域の挙動は別物である。
- プロンプトは 25 tok 1 本のみ。長いプロンプト (= 長い KV) での attention 側の
  伸びは測っていない。ゴール条件は Vision + Reasoning ON の長いコンテキストなので、
  そこでの `verify(k)` は測り直しが要る。
- `TF_PREFILL_MOE_GEMM_MIN_TOKENS` の A/B (§4-3) は 2 つの run にまたがっており、
  decode 側も同時に動いている。**絶対値の改善は言えるが、比の改善は言えない。**

## 5. 速度への含意 (**導出**) — ⚠ 16-M4.5 が差し替えた

> **この節は無効。**§4-1 の実測費用を「設計の費用」として使っているが、
> それは prefill カーネルを借りた実装の費用である (16-M4.5 §0/§2)。
> k 行カーネルでの予測は verify(4) ≈ 1.55 decode ステップで、
> 有効な速度比は 14-M3.5 §5 の表 (math 1.60 / m 1.39 / story 1.05) のままである。
> 以下は「借りたカーネルではこうなる」という記録として残す。

14-M3.5 §4 の実測受理長 (temp 0) と §4-1 の実測費用を合わせる。
ドラフター 1 ステップは decode の 9.8% (10-M0 §2)。

```
1 ラウンドの費用 = verify(k) + (k−1) × 0.098   [decode ステップ]
1 ラウンドの産出 = a + 1 トークン
速度比 = (a + 1) / 1 ラウンドの費用
```

| プロンプト | a (k=4) | 産出 | 費用 (7.0+0.3) | 速度比 | 14-M3.5 §5 の予想 |
| --- | ---: | ---: | ---: | ---: | ---: |
| math | 1.947 | 2.95 | 7.3 | **0.40** | 1.59 |
| m | 1.562 | 2.56 | 7.3 | **0.35** | 1.39 |
| story | 0.937 | 1.94 | 7.3 | **0.27** | 1.05 |

**2.5〜3.7 倍の減速。**14-M3.5 §5 の速度比は M0 の費用モデルをそのまま使った値なので
**無効**である。k=2 でも改善しない (math で 1.79 / 4.9 = 0.37)。

### 5-1. 実装を直したらどこまで行くか — 上限も厳しい

`verify(k) ≈ 2.6 + 0.86k` の 2 項をそれぞれ潰した場合 (**導出**):

| 仮定 | verify(4) | math の速度比 |
| --- | ---: | ---: |
| 現状 | 7.0 | 0.40 |
| 固定費をゼロにする (限界費用はそのまま) | 3.4 | 0.79 |
| 10-M0 §2 の帯域下限まで落とす (`1.55`) | 1.55 | **1.59** |
| 下限の 2 倍で止まる | 3.1 | 0.87 |

**固定費だけ潰しても黒字にならない。**限界費用 0.86 ステップ/トークンを
M0 の帯域下限 0.62 まで下げることが必要条件になる。

その 0.62 という下限自体が、この構成の本質的な弱点である (**導出**):
1 トークンの重み 2.4055 GB のうち dense は 1.5129 GB (63%) だけで、
残り 37% の routed expert は k トークンの和集合として**ほぼ k に比例して増える**
(10-M0 §2 の実測: k=4 で 1 トークンあたり 0.622 倍)。
投機デコードが稼ぐ「dense 重みを 1 回で済ませる」節約は、
**MoE では 63% ぶんにしか効かない**。

参照実装 (llama.cpp、V100 + RTX 3090) が同系モデルで 1.26〜1.28 倍を出している
(14-M3.5 §3) のと矛盾しない: あちらは expert が全部 VRAM に載っており、
そもそも「読むバイト数」が律速ではない。
**18 GB 機で expert を SSD からストリームする構成では、verify の費用構造が違う。**
これは受理率の問題ではなく、**ターゲット側の実行効率の問題**である。
(16-M4.5 §2 の再解釈では、この「構成の本質的な弱点」も成り立たない —
参照実装との差はカーネルの置き場所であって、expert をストリームすること自体ではない。)
