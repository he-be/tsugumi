# 25. M5.6 の結果 — ブロックの attention を k 行 1 回に畳んだ

測定: 2026-08-18、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3。
対象モデル `scratch/gemma4-qat.moepack` (drafter 同梱)。触ったファイルは §7。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

24-M5.5 §7 は残りを 4 つ並べ、1 番目に **attention の行共有**を置いた
(「いまは decode のカーネルを k 回呼んでいるので KV を k 回読む。
k 行を 1 回の split-KV で通すカーネルを書けば約 3 ms、−7 ms」)。
本書はそれだけをやった。予測より下に出た。

---

## 0. 結論 — 4 つ

1. **ブロックの attention は k 行 1 回になった** (§1)。
   `attention_rows_partial` は 1 threadgroup = (q head, chunk)、
   **1 simdgroup = 1 行**で、行ごとの可視範囲 `[kv_start_r, start+r+1)` を
   カーネルの中で切る。KV の走査はブロック 1 回につき 1 周で、
   dispatch は層あたり **2k → 2 本**になる。
2. **`attn.swa` は 21 → 10 → 約 1.5 ms** (§2、k=4 / ゴール条件)。
   24-M5.5 §7 の予測 (約 3 ms) より下で、**KV 帯域の床のすぐ上**である。
   ついでに床の値を訂正する: 24 §2 の 229 MB は KV head を 16 と数えていたが
   SWA の KV head は **8** なので、正しくは **115 MB ≒ 0.85 ms** (**導出**)。
3. **層前半 (`attn`) は 24 → 15 ms、ブロックの GPU busy は 59 → 50 ms** (§2)。
   同一プロンプト・同一ラウンド数 (74 ラウンド、受理列まで一致) の同条件 2 プロセスで
   **verify の合計は 8.90 → 7.00 s (−21%)**。
4. **スコア (採点基準 v1) は 1.136 → 1.336 倍** (§3)。
   **22 §5 が凍結した目標 1.33 に届いた。**受理長 (1.885) もドラフターも
   1 行も動かしていないので、動いたのは費用側だけである。
   正しさは §4 — ゲート 1 (`bench/m.json`) は **215/215 全一致**のままだが、
   `--verify-block` は **12 中 9 PASS / 3 FAIL** で、24-M5.5 の 11/1 から
   **2 本増えた**。増えた 2 本は同じ 1 箇所 (top-1 マージン 1.0e-3 の競り合った位置)
   の argmax 反転である。**通ったことにはしない。**

## 1. 書いたもの — 1 simdgroup = 1 行 (**実測**、コード)

24-M5.5 が入れた経路は「decode の split-KV カーネルを行ごとに呼ぶ」だった。
正しい形だったが、**KV を k 回読む**のと**層あたり 2k 本の encoder** が残った。

`attention_rows_partial` (`Sources/Tsugumi/Metal/Attention/attention.metal`) は
その 2 つを畳む:

```
threadgroup = (q head, chunk)   … grid = num_q_heads * num_chunks
threads     = rows * 32          … 1 simdgroup = 1 行、行の中は 32 レーンで head_dim を割る
```

- **行ごとの可視範囲はカーネルの中で切る。**chunk は行の**和集合**
  `[kv_start_0, start + rows)` の上で切り、各行は自分の範囲
  `[kv_start_r, start + r + 1)` に `p_begin`/`p_end` をクランプする。
  SWA は窓の下端も行ごとに動くので、その両方が行の中で決まる。
- **threadgroup メモリもバリアも無い。**1 行 = 1 simdgroup なので、
  内積の集約は `simd_sum` 1 本で足りる。Q はレジスタに載ったまま
  (レーンあたり `head_dim/32` 要素) で、位置ループの中で読み直さない。
- **pass 2 は decode の `attention_decode_combine` をそのまま使う。**
  partial の並びを `[行][q head][chunk]` にしたので、grid 幅を
  `rows * num_q_heads` にするだけで既存のカーネルが merge できる。
- **1 行のブロックは decode の呼び出しのままにした** (`t > 1` のときだけ新経路)。
  `TF_MTP_DRAFTS=0` の 1 行ブロックが decode と同じカーネル・同じ数値で走る、という
  24-M5.5 の性質を落とさないため。

切り替えは M4.5 系の規約どおり 2 段:

| 環境変数 | 経路 |
| --- | --- |
| (既定) | **本書**。k 行を 1 回の split-KV で通す |
| `TF_MTP_ROWS_ATTENTION_SHARED=0` | 24-M5.5。decode のカーネルを行ごとに k 回 |
| `TF_MTP_ROWS_ATTENTION=0` | M5.5 以前。prefill の query-block カーネル |

## 2. 測ったこと (**実測**)

条件は 24-M5.5 §2 と同じ (`bench/mtp_goal_prompt.json` / IMG_2112 / Reasoning ON /
temp 0 / 200 tok / 80 スロット)。温まった 25 ブロックの中央値:

| | 24-M5.5 (`SHARED=0`) | **本書** | 差 |
| --- | ---: | ---: | --- |
| GPU busy | 59 ms | **50 ms** | −9 |
| GPU idle | 15 ms | 14 ms | |
| span (ブロック 1 回) | 75 ms | **65 ms** | −10 |
| `attn` (層前半 30 本) | 24 ms | **15 ms** | **−9** |
| `moe` / `shared` / `head` | 27 / 4 / 3 | 27 / 4 / 3 | 不変 |
| `wait.front` | 56 ms | 47 ms | |
| verify 合計 (200 tok の 74 ラウンド) | 8.90 s | **7.00 s** | **−21%** |

**ラウンド数も受理列も 1 つ違わない** (どちらも `rounds=74 accept=1.689/3
tok/round=2.703 accepted=18,18,7,31`) ので、この 2 プロセスは
**同じ仕事を違う速さでやっている**。壁時計の判定は §3 の交互 A/B に任せる。

層前半の内訳 (`TF_PREFILL_GPU_PROFILE=2`、k=4、温まった 25 ブロックの中央値):

| | qkv | rope | **attn.swa** | attn.full | oproj | post | 計 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| M5.5 以前 (query-block) | 5 | 1 | **21** | 2 | 3 | 5 | 35 |
| 24-M5.5 (行ごとに k 回) | 4 | 1 | **約 10** | 1 | 2 | 5 | 24 |
| **本書** | 4 | 1 | **約 1.5** | 0.3 | 2 | 5 | 15 |

> **床の訂正 (導出)**: 24-M5.5 §2 は SWA の KV を
> 「25 層 × 16 head × 560 tok × 256 × 2 B × 2」= 229 MB と書いたが、
> SWA の **KV head は 8** (Q head が 16)。正しくは **115 MB ≒ 0.85 ms**。
> いま測っている約 1.5 ms はその **1.8 倍**で、
> q head 2 本が同じ KV head を共有する (= 同じ行を 2 つの threadgroup が読む) 分と
> ちょうど同じ桁である (**未確認**、GQA を畳む形はまだ試していない)。

dispatch も減った (**導出**): 層あたり `2k → 2` 本、k=4 のブロック 1 回で
**240 → 60 本**。24-M5.5 §4 が「同じ scratch を使うので Metal のハザード追跡で
直列化される」と書いた行が、そもそも 1 本になった。

## 4. 正しさ (**実測**)

**ゲート 1 は変わっていない** (`bench/m.json` / thinking off / temp 0 / 96 tok /
80 スロット、24-M5.5 §5 と同一条件、出力の共通接頭辞):

| 比較 | 結果 |
| --- | --- |
| MTP off × MTP on (bs=4) | **215 / 215 全一致** |
| bs=4 × bs=2 | 全一致 |
| bs=4 × 投機ゼロ (`TF_MTP_DRAFTS=0`) | 全一致 |
| bs=4 (本書) × bs=4 (`SHARED=0`) | 全一致 |

`TsugumiKernelCheck --verify-block` (k=4、8 ラウンド) は
**12 中 9 PASS / 3 FAIL**。24-M5.5 は 11/1 だったので **2 本増えた**:

| ケース | 24-M5.5 | **本書** |
| --- | --- | --- |
| `verify/rows/logits k=4` (tol 8e-2) | 4.0e-2 PASS | **1.9e-2 PASS** (worst は縮んだ) |
| `verify/rows/wide-vs-width1` (k=4 worst / k=1 worst ≤ 3) | 6.5 FAIL | **3.2 FAIL** (縮んだが依然 tol 超え) |
| `verify/rows/argmax k=4` | PASS | **FAIL** — pos 25 で block=2897 / scalar=11442 |
| `verify/rows/greedy` | PASS | **FAIL** — 同じ pos 25 |
| `verify/rows/logits k=1` / `argmax k=1` | PASS | **PASS** (1 行のブロックは decode の呼び出しのまま) |
| `rewind/*` 4 本 | PASS | **PASS** |

- **反転は 1 箇所で、そこは検査自身が「競り合っている」と印を付けている位置である**:
  pos 25 の top-1 マージンは **1.0e-3**。k=4 の logits 誤差 (median 1.5e-3 /
  worst 1.9e-2、15-M4 §2 の既知の帯 3.8e-2 の内側) はこのマージンより大きいので、
  **どちらに倒れるかは丸めが決める**。24-M5.5 が全位置一致だったのは、
  同じ帯の中で偶々 decode と同じ側に倒れていたということである (**導出**)。
- **誤差そのものは縮んでいる** (worst 4.0e-2 → 1.9e-2、`wide-vs-width1` 6.5 → 3.2)。
  それでもガードの意図 (「幅を広げたことで増える誤差を検出する」) は
  まだ満たしていない。**3 FAIL のまま記録する。**
- **未確認**: chunk の切り方を行ごとに (decode と同じ範囲で) 揃えれば
  この位置が戻るかどうか。いまは和集合の上で切っている。

その他のゲート (**実測**、04-PHASES §3):

| ゲート | 結果 |
| --- | --- |
| 3. テキスト回帰 (MTP 無効) | **構造的に不変** (**導出**)。新経路は `speculativeBlock` かつ `t > 1` の中だけで、decode も prompt prefill も 1 命令も変わらない |

| ホスト往復 (idle) | 14 ms | — | — |

> **感度表の入力は未再測定である** (**未確認**)。`bench/mtp_budget.py` の
> F=1.33 / M=0.31 は 23-M5 §5 のもので、M5.5 と本書の 2 回ぶん古い。
> 次の改修を感度表に通す前に (22 §6 のルール 3)、ループ実測で引き直すこと。

**順番が入れ替わった。**24-M5.5 §7 は 1 番目が attention、2 番目が `moe` だったが、
attention は床のすぐ上に来たので、**残っているのは `moe` の 11 ms と
ホスト往復の 14 ms** である。`post` の 4 ms (router の行ループ、30 層 × k dispatch) は
本書と同じ手 — k 行を 1 本の dispatch に畳む — がそのまま効くはずの場所である
(**未確認**)。
