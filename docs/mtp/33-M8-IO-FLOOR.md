# 33. M8 — I/O は 48 スロットですでに床ではない。§7 の順序は逆である

測定: 2026-08-19、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3 / Xcode 26.6。
対象モデル `scratch/gemma4-qat.gturbo` (drafter 同梱)、32 / 48 / 64 スロット、8192 context。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

32-M8-A-ROWS-SPLIT §7 の 2 本目 (「**`moe` をこれ以上削る前に、I/O を床から外す
仕事のほうが先である**」) に着手した。**本番のコードは 1 行も変えていない** —
本書はプローブ 1 本と、既存のフラグ (`--expert-cache-slots`) の測り直しである。

**結論は §7 の指示と逆になった。**I/O を 17〜22% 外しても壁時計は動かない。
48 スロットの verify ブロックは**中央値ではすでに GPU 律速**で、
床は `moe` のほうにある。**§7 の 1 本目 (果実 A) が先である。**

> **本書の絶対値は 31 / 32 と比較できない。**`sample_imgs/IMG_2112.JPG` が
> ワークツリーから消えていたので `IMG_2113.JPG` に差し替えた。プロンプトが
> 変わったので受理長は 1.885 → **1.644**、出力 md5 は `3eefadf6…` →
> **`1b72732ecc7da80cb8b9cd1ae2f6d51a`** になる。本書の中の A/B はすべて
> この新しい基準で、同一条件どうしの比較である。

## 0. 結論 — 5 つ

1. **分割はどの深さでも効かない** (**実測**、§1)。1 本を 2/4 分割しても帯域は
   平ら、8 分割以降は単調に悪い。31 §7 が想定した「キューを深くする」は
   **1 本のエキスパートを割っても作れない**。
2. **27 §7 の「8 本 = 8.90 GB/s」はページキャッシュ込みの数字だった** (**実測**、§1)。
   `F_NOCACHE` を立てた冷たい device の天井は **6.0〜6.5 GB/s** である。
   同じプローブを production の fd フラグ (キャッシュあり) で回すと、
   深さ 8 以上で 9〜12 GB/s まで伸びて 27 §7 の表を再現する。
3. **本番の発行深さは層のミス数そのもの** (**実測**、§2)。
   `executeExpertCachePlan` は `concurrentPerform(iterations: plan.misses.count)`
   なので、**キャッシュを良くするほどキューが浅くなり帯域が落ちる**。
   32 / 48 / 64 スロットで 4.72 / 2.67 / 1.52 ミス/層 → **5.91 / 4.90 / 3.36 GB/s**。
4. **48 → 64 スロットは io を −17% 減らして t/s を動かさない** (**実測**、§3、
   冷たい ABBA)。ミスは −43% (3600 → 2055)、io は 2.73 → 2.28s、
   **t/s は 26.39 → 25.58 (−3%)**。ピークメモリは 6.83 → 8.6 GB。
   32 → 48 は io −32% で **t/s +14%** なので、**膝は 48 と 64 の間にある**。
5. **出ない理由は GPU 床である** (**実測**、§4)。同じ大きさのブロックを並べると
   `fetch` が減ったぶん `wait.front` が増え、`gpuq busy` は 43〜46 ms で
   **1 ms も動かない**。48 スロットでも `experts=537/527/482` のブロックは
   call が 63/54/43 ms、busy が 44/43/37 ms で**すでに GPU 律速**。
   64 スロットで表に出るのは一番大きいブロック (call 83 → 64 ms) だけである。

## 1. プローブ — 分割は効かない。27 §7 の天井はキャッシュだった (**実測**)

`bench/io_depth_probe.c` (新規)。27 §7 のプローブは**コミットされておらず**、
書き直す羽目になったので今回は残す。実 `packed_experts/layer_*.bin`
(30 層 × 128 エキスパート × 3.72 MB) からランダムな (層, エキスパート) を読み、
**同時に読むエキスパート数 × 1 本あたりの分割数**を振る。
`F_NOCACHE` / `F_RDAHEAD` を切り替えられる。中央値、先頭 4 回は捨てる。

```bash
clang -O2 -o /tmp/io_depth_probe bench/io_depth_probe.c -lpthread
/tmp/io_depth_probe scratch/gemma4-qat.gturbo/packed_experts 30 128
```

**分割は効かない** (**実測**、`NOCACHE=1 RDAHEAD=0`、GB/s):

| 同時エキスパート | split=1 | split=2 | split=4 | split=8 | split=16 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 4.03 | 4.28 | 4.40 | 3.55 | 3.17 |
| **2** | **5.14** | 5.07 | 5.02 | 4.26 | 3.93 |
| 4 | 5.50 | 5.41 | 5.48 | 4.89 | 4.38 |
| 8 | 5.85 | 5.85 | 5.81 | 5.24 | 4.63 |
| 16 | 6.04 | 6.00 | 5.96 | 5.40 | 4.67 |

**同じバイトを細かく割ってもリクエスト数が増えるだけで帯域は増えない。**
27 §7 が唯一測った分割の行 (4 本 × 4 分割で 6.49 → 6.91) は
**キャッシュありで測った +6% で、冷たい device では出ない** (5.50 → 5.48)。

**天井はキャッシュの有無で二重になる** (**実測**、split=1):

| 同時エキスパート | `F_NOCACHE=1` (device) | `F_NOCACHE=0 F_RDAHEAD=1` (production の fd) |
| ---: | ---: | ---: |
| 1 | 4.25 | 4.25 |
| 2 | 5.14 | 5.03 |
| 3 | 5.40 | 5.52 |
| 4 | 5.61 | 6.89 |
| 8 | 5.98 | **9.01** |
| 12 | 6.49 | **11.15** |
| 16 | 6.33 | **12.11** |

**深さ 1〜3 では両者が一致し、深さ 4 以上でだけ割れる。**割れているのは
スイープ中に温まったページキャッシュのヒットで、**27 §7 の 8.90 GB/s の正体は
これ**である。本番が住んでいるのは深さ 1〜3 の行 (§2) なので、
**`F_NOCACHE` を立てる打ち手は無い** — 立てても本番の深さでは同じ数字になる。

> 副産物: これで 28 §1 の判定表の「SSD 実効帯域 6.5〜8.9 GB/s = **限界**」は
> 上限が **6.0〜6.5 GB/s** に下がる。判定 (限界) は変わらない。

## 2. 本番の発行深さは層のミス数そのもの (**実測**)

`PreadExpertStreamer.executeExpertCachePlan` (`:345`) は

```swift
DispatchQueue.concurrentPerform(iterations: plan.misses.count) { ... }
```

で、**キューの深さがそのままミス数**である。層の全タイルのミスは
`startLayerFetches` (`RealForwardRunner.swift:2092`) が**まとめて 1 回で発行**して
いるので、層の中でこれ以上前倒しできる余地は無い (27 §3 が既に畳んでいる)。
層をまたぐには前層の出力が要るので、深さを増やす道は投機的先読みしかなく、
それは 30 が実装して負けている。

**結果として、キャッシュを良くするほど帯域が落ちる** (**実測**、§3 の run から):

| スロット | ミス/ブロック | ミス/層 | 読むバイト | io (wall) | 実効帯域 | §1 の同深さ |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 32 | 6374 | **4.72** | 23.7 GB | 4.01s | **5.91 GB/s** | 5.6〜5.8 |
| 48 | 3600 | **2.67** | 13.4 GB | 2.73s | **4.90 GB/s** | 5.1〜5.4 |
| 64 | 2055 | **1.52** | 7.64 GB | 2.28s | **3.36 GB/s** | 4.3〜4.6 |

(ミス/層は 45 ラウンド × 30 層 = 1350 層訪問で割った。バイトは
`expertStride` 3,719,168 B × ミス数。io は `TF_PREFILL_HOST_PROFILE` の
`decode ... io=` で、§4 のとおり `fetch` 段の wall とほぼ一致する。)

**本番はプローブの曲線の上に乗っている**が、浅い側で少し下回る —
ミスが 0 本の層と 1 本の層が混ざるので、平均深さより実効はさらに浅くなる。

## 3. スロットスイープ (**実測**、冷たい ABBA)

毎回**別モデルの 12 GB (`scratch/gemma4.gturbo/packed_experts`) を読んで
ページキャッシュを流してから**回した。`--max-new 120`、bs=4、8192 context。

| スロット | hit | io | t/s | ピーク |
| ---: | ---: | ---: | ---: | ---: |
| 32 | 74.6% | 4.01s | 23.16 | 5.1 GB |
| **48** | 85.6% | 2.73s | **26.39** | 6.83 GB |
| 64 | 91.8% | **2.28s** | 25.58 | 8.6 GB |

- **32 → 48**: io **−32%**、t/s **+14%**。I/O が床である。
- **48 → 64**: io **−17%**、t/s **−3%**。**I/O はもう床ではない。**

個別の値 (t/s): 32 が 22.50 / 23.83、48 が 26.27 / 26.51、64 が
25.43 / 26.27 / 25.21 / 25.41。48 と 64 は**分布が重なる**ので
「64 のほうが遅い」は主張しない。主張するのは**「io が 0.45s 減っても
t/s に出ない」**のほうで、これは 4 回すべてで成り立っている。

**メモリの値段は本物である**: 64 スロットは peak 8.6 GB で、18 GB 機の
運用点としては 48 スロット (6.83 GB) から 1.8 GB 増える。**得るものが無い。**

## 4. なぜ出ないか — GPU 床 (**実測**、`TF_PREFILL_HOST_PROFILE=1`)

同じ run の verify ブロックを `experts=` の数で突き合わせた
(ブロック 1 個ぶん、ms):

| experts | | fetch | wait.front | call | **gpuq busy** |
| ---: | --- | ---: | ---: | ---: | ---: |
| 597 | 48 | 50 | 25 | 83 | 46 |
| | **64** | **26** | 29 | **64** | **45** |
| 537 | 48 | 32 | 23 | 63 | 44 |
| | **64** | **18** | 35 | **61** | **44** |
| 527 | 48 | 19 | 28 | 54 | 43 |
| | **64** | **15** | 32 | **55** | **43** |
| 482 | 48 | 10 | 26 | 43 | 37 |
| | **64** | **8** | 28 | **44** | **36** |
| 335 | 48 | 23 | 22 | 52 | 30 |
| | **64** | **5** | 30 | **43** | **30** |

3 つ出てくる:

1. **`gpuq busy` は 1 ms も動かない** (46/44/43/37/30 対 45/44/43/36/30)。
   当然である — スロット数は GPU の仕事を変えない。**これが床である。**
2. **`fetch` が減ったぶん `wait.front` が増える。**537 のブロックで
   fetch −14 ms に対し wait.front **+12 ms**、call は **−2 ms** しか動かない。
   ホストが I/O を待つのをやめると、そのぶん GPU を待つ。
3. **48 スロットでも中央の 3 ブロックはすでに GPU 律速**である
   (call 63/54/43 に対し busy 44/43/37 = **70〜86%**)。
   64 スロットが本当に効くのは一番大きい `experts=597` のブロック
   (83 → 64 ms) だけで、それはブロックの少数派である。

**32 §5 が「48 スロットでも fetch が call の 58%」と書いたのは
一番大きいブロックの姿**であって、ブロック分布の中央ではない。
本書の §3 が測ったのは分布全体で、そちらでは 48 スロットの時点で
**I/O はもう床から外れている**。

## 5. ゲート 1 (**実測**)

スロット数は出力を変えない。32 / 48 / 64 の 3 通りで

(冒頭のとおり、この md5 は画像が `IMG_2113.JPG` の基準で、

足したのは `bench/io_depth_probe.c` (ビルド対象外の単体 C) だけである。

## 6. 引き継ぎ — **32 §7 の順序は逆である**

32 §7 は「`moe` をこれ以上削る前に、I/O を床から外す仕事のほうが先」と書いた。
**本書の実測はその逆を言う**:

- I/O を **−17%** 外しても (64 スロット)、壁時計は動かない (§3)。
- 動かない理由は GPU 床で (§4)、その GPU 床の**中身の 60% が `moe`**
  (32 §3: GPU 合計 49.3 ms のうち `moe` 28.0 ms)。
- **`moe` を削らない限り、I/O 側の改善は受け皿が無い。**逆に `moe` を削れば、
  48 → 64 スロットの io −0.45s が初めて表に出る余地ができる (**導出**)。

**したがって次は 32 §7 の 1 本目である** — `down` の F=704 スカラー末尾
(31 §3、`prefill.metal:1184-1198`。ループ反復の 75% がデータの 27% を
半分のレーンで処理する)。計器 `--moe-rows-bench` は既にあり、
`MoERowsBench.swift:33-34` の `moeRowsD` / `moeRowsF` を可変にするだけで、
**カーネルを触らず・ビット一致テストを壊さずに**末尾仮説を潰せる。
黒なら、そこで初めて `simd_sum` の総和順序と
`PrefillRoutedMoERowsVsDecodeTests` の衝突を払う判断をすればよい。

**I/O 側で本書が閉じたもの** (これ以上やらなくてよい):

| | 結果 |
| --- | --- |
| 読みを分割してキューを深くする | **閉**。どの深さでも効かない (§1) |
| `F_NOCACHE` を立てる | **閉**。本番の深さ 1〜3 では素の device と同値 (§1) |
| スロットを 64 に増やす | **閉**。io −17%、t/s ±0、メモリ +1.8 GB (§3) |

**I/O 側で開いたまま残るもの** (どれも `moe` の後):

| | |
| --- | --- |
| 深さを層またぎで作る | 30 の投機的先読みが唯一の道で、符号が負のまま。30 §7 の「予測を安くする」が前提 |
| バイトそのものを減らす | 1 エキスパート 3.72 MB のうち **20% (743 KB) が affine (group 32 の bf16 scale/bias)**。group 64 なら −10% だが再量子化と数値の移動を伴う (**未確認**、本書では測っていない) |
| 追い出しポリシー | Belady 床は 27 §7 の **−23%** のまま。§3 のとおり**バイトを減らしてもキューが浅くなって半分しか効かない**ので、実効は −10% 程度と読むべき (**導出**) |
