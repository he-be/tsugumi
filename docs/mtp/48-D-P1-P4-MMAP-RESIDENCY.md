# 48. D のプローブ — P-1〜P-4 の実測。粒度は通り、冷たい側は先読みでだけ通る

実測: 2026-08-20、M3 Pro 18 GiB / macOS 15.7.5、`iogpu.wired_limit_mb` = 14336。
[47](47-D-MMAP-RESIDENCY-PROPOSAL.md) が置いた P-1〜P-4 を実行した。
**推論経路 (`Sources/Tsugumi/`) は無改変。**計器は
`TsugumiKernelCheck --mmap-residency-probe` の新規フラグ 1 つ
(`Sources/TsugumiKernelCheck/MmapResidencyProbe.swift`)。

一次ログは `bench/mtp48/`。P-1〜P-3 は**反復 5 × 独立な 4 run = 片側 n=20**、
ゲート (P-4) は ABBA を 5 invocation × 片側 n=50。統計は
`bench/mtp48_gate_stats.py` が一次ログから出し直す (**導出**のみ、新しい測定はしない)。

**結論から:**

- **P-1 PASS / P-2 PASS** — どちらも決定的。粒度はバッファ単位で、暖かい側のコピーは 0 になる
- **P-3 FAIL** — 先読み無しの冷たい側は今の並列 `pread` に **2.5 倍**負ける
- **P-4 は「ゲートの上」** — `F_RDADVISE` で **1.16 倍** (統計の取り方で 1.12〜1.20 倍) まで
  戻るが、ゲートは 1.20 倍で**余白が 0.04 しかない**。**きれいな PASS とは言えない**。
  ブートストラップの 95% CI は **1.098〜1.280** で、**ゲートは測定の分解能の内側にある** (§5b)
- **冷たい費用の正体はディスクではない** (§11)。`F_RDADVISE` で 1,640 ページを
  **全部ページキャッシュに載せてから**走らせても、コマンドバッファは **4.25 ms** かかる
  (n=20)。カーネル 0.25 を引いて **2.44 µs/ページ**。**残っているのはフォールトと
  マッピングの費用**で、これが 47 §5(b) の言う「深さ」の正体である
- **⇒ 単発の 1.16 倍では決まらない** (§12)。production の費用は
  「**マッピングが生き残る率**」で決まり、どの前提を置いてもフォールト費用は
  今の `io` 14.21 ms/tok と同じ桁になる。**次に測るものは §13**

> **[49](49-D-P5-RESIDENCY-SET.md) が §11〜§13 を上書きしている (2026-08-20、同日)。**
> P-5 は通った — **`MTLResidencySet` でフォールトはコマンドバッファの外に出る**
> (初回タッチの上乗せ 0.61 → **0.09 ms**、準備 0.59 ms)。そして
> **§11/§12 の「2.44 µs/ページ」という立て方が壊れている** — ページ数を 8 倍
> 振っても residency set 側の上乗せは **0.06〜0.12 ms で平ら**で、
> **ページ単価ではなくコマンドバッファあたりの固定費**だった。
> ⇒ **§12 の表 (ページ/tok × 単価) と、そこから出る「フォールト費用は `io` と
> 同じ桁」は成り立たない** (49 §4)。**§1〜§10 (P-1〜P-4) はそのまま生きている。**

47 §7 の判定表はこの行を「実装する (先読みを併せて)」と「保留 = ユーザーの決定」の
境目に置いている。**どちらに倒すかは §8 の材料を見てユーザーが決める** —
ただし §11/§12 を足した今、**「決める前に §13 の P-5 を 1 本測る」が第 3 の選択肢**である。
なお **47 §3 の前提が 1 つ壊れている** — `MAP_SHARED` を明示しないと
メモリの議論が逆向きになる (§2)。

## 0. カーネルは production のバイトをそのまま読んでいる

`BpwLayout(.sym)` (44 の計器) が**出荷済みチェックポイントのエキスパート blob の
オフセットを完全に再現する** — gate 0 / gate_scales 991,232 / up 1,115,136 /
up_scales 2,106,368 / down 2,230,272 / down_scales 3,221,504。
なのでプローブは合成フィクスチャを作らず
`packed_experts/layer_00.bin` に直接カーネルを向けている。
形状・群サイズは 43/44 と同じ (D=2816 F=704 group 32)、振っているのは
**バッファの出どころだけ**である。

## 1. P-1 — **PASS。粒度はバッファであってマッピングではない** (実測、5/5 × 4 run = n=20)

冷たい状態から、**8 エキスパートを名指すコマンドバッファ 1 本**を走らせ、
マッピングのうち何ページが常駐になったかを数えた。

| マッピング | バッファの切り方 | 常駐になったページ | = | 冷たい壁時計 |
| --- | --- | ---: | ---: | ---: |
| `MAP_PRIVATE/r` | **エキスパート単位 (128 本)** | **1,640 / 26,240** | **26.9 MB** | 15.6〜19.3 ms |
| `MAP_PRIVATE/r` | 層単位 (1 本) | 26,240 / 26,240 | 429.9 MB | 209〜220 ms |
| `MAP_PRIVATE/rw` | **エキスパート単位** | **1,640** | **26.9 MB** | 15.2〜19.1 ms |
| `MAP_PRIVATE/rw` | 層単位 | 26,240 | 429.9 MB | 211〜214 ms |
| `MAP_SHARED/r` | **エキスパート単位** | **1,640** | **26.9 MB** | 12.4〜14.1 ms |
| `MAP_SHARED/r` | 層単位 | 26,240 | 429.9 MB | 163〜165 ms |

1,640 = 8 × 205 ページ**ちょうど**で、47 §7 が置いた PASS の値
(8 × 3.36 = 約 27 MB) と FAIL の値 (層ファイル 420 MB) が**そのまま出た**。
外れ値なし、3 つのマッピング様式すべてで同じ。

⇒ **47 §5(a) の未確認は閉じた。**エキスパート単位のバッファで 806 MB/ステップに
収まる。**代替案として置いてあった「blob ごとに `mmap` を 1 本ずつ張る」
(3,840 マップ) は要らない** — マップは層ごとに 1 本、バッファが 128 本で足りる。

### 1a. 計器の注記 — **`wire_count` はこの問いに使えなかった** (実測)

47 §7 は「wired ページの増分」で判定するよう書いていたが、
**system 全体の `wire_count` (`host_statistics64`) はどの腕でもほとんど動かない**
(**120 セル中 102 で 0**)。しかも**雑音床が invocation ごとに 6 / 3,878 / 7,554 /
13,233 ページ (0.1〜216.8 MB) と動く** — PASS の信号 (26.9 MB) の **8 倍**である。
**この計器では P-1 は原理的に判定できない。**
リージョンの `user_wired_count` は全セルで 0。

動いた 18 セルには 1 つだけ読める構造がある (**実測**、6 ログ全部):

| 腕 | 非ゼロだったセル (ページ) |
| --- | --- |
| **エキスパート単位** | 54 / 111 (×5) / 172 / 434 / 4,503 / 4,660 / 4,667 / 5,518 — **上端 90 MB** |
| **層単位** | 1,759 / 9,280 / 16,317 / 20,072 / 24,429 / 24,466 / 24,635 / 27,625 / 47,033 |

**152 MB (9,280 ページ) 以上の跳ねは 9 回あって、9 回とも層単位の腕である。
エキスパート単位の腕は 1 度も 5,518 ページを超えなかった。**
9 回のうち 8 回は雑音床の上端 (13,233) より上にある。
⇒ **弱い裏付けにはなる**が、雑音床が信号の 8 倍ある以上これは主証拠にできない。
**そこで P-1 は「冷たい状態からの常駐ページ数」で測った。**これは
マッピング単位なので system 雑音を持たず、上表のとおり分離は完全である。
**「Metal は wire しない」とは主張しない** — 動かなかったのはカウンタである。

## 2. **47 §3 の前提が 1 つ壊れている — `MAP_PRIVATE` は copy-on-write を割る** (実測、5/5 × 4 run = n=20)

47 §3 は「D 後はほぼ全部が clean file-backed になり、page-out もせず swap にも
行かず、捨てて読み直すだけになる」と書いた。**これは `MAP_SHARED` でだけ成り立つ。**

| マッピング | 腕 | anonymous になったページ | dirty |
| --- | --- | ---: | ---: |
| `MAP_PRIVATE/r` (**書き込み権限なし**) | エキスパート単位 | **1,640** | 1,640 |
| `MAP_PRIVATE/r` | 層単位 | **26,240 (429.9 MB)** | 26,240 |
| `MAP_PRIVATE/rw` | エキスパート単位 | 1,640 | 1,640 |
| `MAP_PRIVATE/rw` | 層単位 | 26,240 | 26,240 |
| **`MAP_SHARED/r`** | エキスパート単位 | **0** | **0** |
| **`MAP_SHARED/r`** | 層単位 | **0** | **0** |

`PROT_READ` だけで張ってもプロセスは書けないのに、**GPU が読んだページは
例外なく anonymous + dirty になる**。anonymous は回収に圧縮か swap が要るので、
`MAP_PRIVATE` で実装すると **47 §3 の「degradation の質が上がる」は逆になり、
私有バイトは今の 3.22 GB から減らない。**

⇒ **D は `MAP_SHARED` + `PROT_READ` で実装する。**47 は様式を指定していなかった。

## 3. P-2 — **PASS。暖かいときのコピーは消える** (実測)

| | 8 エキスパートを GPU の前に置く費用 | 1 エキスパートあたり |
| --- | ---: | ---: |
| 今の経路 (並列 `pread` → 私有スロット、暖かい) | **0.84〜1.26 ms** (21〜32 GB/s、n=20) | 0.105〜0.140 ms |
| `mmap` + `bytesNoCopy` (暖かい) | **0** | **0** |

`mmap` 側はカーネルがマッピングを**その場で読む**ので、転送という段が存在しない。
カーネル自体は 0.241〜0.265 ms/パス (8 エキスパートで 105〜111 GB/s) で、
これは 43 §2 の床の上に乗っている。
47 §7 の閾値は「今の `pread` の 3 分の 1 以下」で、**測ったのは 0** である。

## 4. P-3 — **FAIL。冷たいときは今の並列 `pread` に 2.5 倍負ける** (実測)

先読み無し、冷たい状態から 8 エキスパート (26.87 MB):

| | 壁時計 | 実効帯域 |
| --- | ---: | ---: |
| 今の並列 `pread` (`concurrentPerform`) | **4.8〜5.7 ms** (中央値 4.95、n=20) | 4.75〜5.61 GB/s |
| `mmap` `MAP_SHARED` エキスパート単位 | **11.7〜19.3 ms** (中央値 13.1、n=20) | 約 2.0 GB/s |

比は中央値で **2.5 倍**、47 §7 のゲート (1.2 倍以内) を大きく割る。
(上端の 19.3 ms は run 4 の 1 本目、次の 14.6 は run 3 の 1 本目。**4 run とも
「その run の 1 本目が最も遅い」**で、残り 16 本は 11.7〜13.6 に収まる。
この 1 本目効果は §5a と同じ向きである。)
**これは 47 §5(b) が名指しした失敗そのもの** — residency 起点のページインが
1 本のコマンドバッファの中で直列化する。
なお `pread` 側の 4.99〜5.51 GB/s は 33 §1 の「深さ 8 以上で 6.0〜6.5」と
同じ桁で、**別条件の値を持ち込まずに同じハーネスで対照が取れている** (40 §4-11)。

## 5. P-4 — **ゲートの上。`F_RDADVISE` で 1.16 倍まで戻るが余白は 0.04** (実測、ABBA、n=50)

`RDAdvice.swift:34` と同じ `fcntl(F_RDADVISE)` を 8 本の範囲に発行してから
コマンドバッファを出す。

**先に計器の交絡を 1 つ潰してある。**最初に取った 5 run では比が
**1.16 → 1.17 → 1.19 → 1.21 → 1.31 と単調に悪化**し、`pread` 側は動かなかった。
犯人は**このプローブ自身**である — ゲート測定の前に走る `MAP_PRIVATE` の腕が
1 trial ごとに 430 MB を anonymous にし (§2)、run をまたいで圧縮と swap が
溜まっていく。`--mmap-probe-gate-only` を足してゲートだけを別プロセスで取ると
**ドリフトは消える** (5 invocation で 1.21 / 1.12 / 1.17 / 1.16 / 1.18、傾向なし)。
以下は**その clean な測定**である (invocation 5 本 × ABBA、片側 n=50)。

| | n | 中央値 | IQR | 実効帯域 |
| --- | ---: | ---: | ---: | ---: |
| `pread`、並列、私有スロットへ | 50 | **5.36 ms** | 4.99〜5.58 | 5.01 GB/s |
| `mmap` + `F_RDADVISE`、`bytesNoCopy` | 50 | **6.22 ms** | 5.79〜6.82 | 4.32 GB/s |

**比は統計の取り方で動き、ゲート (1.20 倍) をまたぐ:**

| 取り方 | 比 | 対 1.20 |
| --- | ---: | --- |
| 中央値どうし (pooled) | **1.161** | 通る |
| ABBA の round 内で比を取り、その中央値 (n=25、1.06〜1.28) | **1.204** | **ちょうど線の上** |
| `mmap` 側からカーネル実行 0.25 ms を引く (対照には含まれていない) | **1.115** | 通る |

**⇒ 通ってはいるが余白は 0.04 で、round 単位で見ると半分は 1.20 を超える。**
「冷たい側で今の並列 `pread` に負けない」(47 §0) は**辛うじて成り立つ**、
という以上のことは言えない。

先読みの内訳 (別計測、n=5): 発行してすぐ走らせると合計 5.2〜7.4 ms、
常駐を待ってから走らせると待ち 2.2〜3.2 ms + 実行 4.0〜5.0 ms。
**`F_RDADVISE` はページを速く運ぶのではなく、フォールト列に重なることで効いている。**

### 5a. ABBA の中に位置効果がある — **直前が `mmap` の試行だと両腕とも遅い** (実測、n=25 ずつ)

ゲートの生値は 1 本おきに上下する。ABBA の 1 ラウンドは
`pread(1) → mmap(2) → mmap(3) → pread(4)` なので、各腕の 1 本目は
**直前が `pread`**、2 本目は**直前が `mmap`** である。

| | 直前が `pread` | 直前が `mmap` | 差 |
| --- | ---: | ---: | ---: |
| `pread` | 4.990 ms | 5.570 ms | **+0.580** |
| `mmap` + advise | 5.790 ms | 6.820 ms | **+1.030** |

**位置効果 (0.58〜1.03 ms) は、測ろうとしている差 (0.865 ms) と同じ大きさである。**
しかも**両腕で同じ大きさではない**ので、ABBA は打ち消しきれていない:

| 位置を揃えた比 | 値 |
| --- | ---: |
| 直前が `pread` どうし | **1.160** |
| 直前が `mmap` どうし | **1.224** |

⇒ **「1.16 か 1.20 か」の揺れの少なくとも一部は、プローブ自身の後片付け
(直前の `mmap` 試行が残す状態) である。**機構の差ではない可能性がある。
犯人の候補は 128 バッファの解放とドライバの参照 (§6 の制約 2 と同じもの) だが、
**帰属していない** (**未確認**)。

### 5b. ゲートは測定の分解能の内側にある (**導出**、ブートストラップ 20,000 回)

| | 値 |
| --- | ---: |
| 比の点推定 (中央値どうし) | 1.161 |
| **95% CI** | **1.098 〜 1.280** |
| **P(比 > 1.20)** | **0.30** |

**片側 n=50 では 1.20 の上か下かを決められない。**§5 の「余白 0.04」は
正確には「**ゲートが信頼区間の中にある**」である。
**これを n で殴って決めにいくのは筋が悪い** — §5a のとおり系統誤差が
効果と同じ桁にあり、しかも §11 が「単発の比は production の費用を代表しない」を示す。

## 6. 副産物 — **sudo 無しでページキャッシュを落とせる** (実測)

47 §6 は「`purge` は sudo が要るので冷たい条件は `madvise` 側を第一手にする」と
書いたが、**`madvise(MADV_DONTNEED)` はこのタスクの PTE を落とすだけ**で、
張り直すとページは全部キャッシュにある。**`msync(..., MS_INVALIDATE)` は落ちる**:

```
pass1 incore after touch : 26240
pass2 incore on fresh map: 0            <- 別マッピングでも 0
pass2 cold serial touch  : 0.587 s -> 0.73 GB/s
pass2 warm serial touch  : 0.000 s -> 1719 GB/s
```

**制約が 2 つある** (両方とも実際に踏んだ):

1. **同じファイルに他のマッピングが開いていると、`msync` は 0 を返して落とさない。**
   落とすのは測る側のマッピングを張る**前**にすること。
2. **`MAP_SHARED` の腕の直後は、`MTLBuffer` を解放してもしばらく落ちない。**
   ドライバの参照が残る。**落ちたことを `mincore` で確認して retry する**
   (計器は 25 ms 間隔で最大 40 回)。

## 7. このプローブが答えていないこと (**未確認**)

- **47 §8 のうち 2 つは残る** — end-to-end の噛み合い (`ExpertPrefetch` との相互作用、
  層をまたぐ発行の重なり、エンコード時に 3,840 個の `MTLBuffer` を触る費用) と、
  `--expert-cache-slots` の意味。
- **`iogpu.wired_limit_mb` は逆で、47 §8 の 3 番目は落とせる** (**導出**、P-1 + §2)。
  D が wire するのは 1 ステップぶん 26.9 MB × 30 層 = **806 MB** と、常駐コア 1.27 GiB +
  KV 約 0.18 + drafter 0.22 で **約 2.5 GiB**。パイプラインが 3 枚重なっても 2.4 GiB 増。
  **再起動後の既定 8192 MB (8.0 GiB) に収まる。**しかも消えるのは anonymous な私有
  3.22 GB のほうである。47 §8 の「常駐前提にすると起動時の必須条件に格上げされる」は
  **47 §3 が「全部 wire する版は採らない」と決めた設計と矛盾している** —
  あの警告は却下された「全部常駐」版に対してだけ正しい。**D は wired_limit 依存を外す。**
- **冷たい側の数字は 1 層・8 エキスパート・コマンドバッファ 1 本である。**
  production は 1 ステップで 30 層を、先読みを 1 層先行させて発行する。
  **1.17 倍は単発の比であって end-to-end の比ではない。**
- **順序効果は半分だけ帰属した。**ゲート側は §5a で「直前が `mmap` の試行だと
  両腕とも遅い」ところまで分離したが、**何がその状態を残しているかは未確認**。
  P-4 の 5 trial が 1 run の中で単調に上がるほう (5.2 → 7.4 ms) も未説明のままである。
- **§1a の `wire_count` の 5 つの跳ね (+4,660〜+20,072 ページ) は帰属できていない。**
- **47 §4 の取り分 36〜40 t/s は再測していない。**あれは 46 §5b の
  「`io` 14.21 ms/tok の 4 分の 3 はコピー」に乗っている。
  **本書はそれを測っていないが、§12 で見積もりの立て方のほうに 2 つ穴を指摘する。**
- **マッピングの寿命は測っていない。**プローブは trial ごとに `mmap` を張り直す
  (§10 の設計)。production はプロセス寿命ぶん張りっぱなしなので、
  **「一度フォールトしたページを、キャッシュから落ちたあと再び触る費用」は未測定**である。
  §12 のとおり、D の勝ち負けはここで決まる。
- **数字は計器ハーネスのものであって production ではない** (40 §4-11)。

## 8. 判断の材料 — 進むか、保留か

**47 §7 の判定表はこの行 (`PASS PASS FAIL PASS`) を「実装する」に置いているが、
P-4 の余白は 0.04 しかない (§5)。**倒す先はユーザーが決める。両側の材料:
**§11〜§13 を足した今、第 3 の選択肢 (決める前に P-5 を 1 本測る) が加わっている。**

**進む側**

- **運用点は暖かい regime である** (40 §3、ユーザー確定)。そこでは P-2 が決定的に
  通っており、**8 エキスパートあたり 0.84〜1.26 ms のコピーが丸ごと 0 になる。**
- 冷たい側の負けは **8 エキスパートで 0.86 ms** (6.22 対 5.36)。**冷たいのは
  生成の頭だけ**である (46 §5a)。
- **`iogpu.wired_limit_mb` への依存が外れる** (§7)。D 後に wire するのは約 2.5 GiB で、

## 11. **冷たい費用の行き先はディスクではない — フォールト経路である** (実測、n=20)

> **§11〜§13 は [49](49-D-P5-RESIDENCY-SET.md) を併せて読むこと。**
> 「フォールト経路である」は正しい。**壊れているのは 2 つ** — (1) 4.00 ms を
> ページ数で割って µs/ページと呼ぶ立て方 (49 §4: 振ると平ら = 固定費)、
> (2) カーネル 0.25 ms の引き算 (49 §6: あれは 1,200 パスを 1 本に積んで
> 償却した値で、コマンドバッファ 1 本ぶんの固定費が入っていない)。
> なお **4.25 ms 自体は今日も再現する**が、同じプロトコルを単独プロセスで
> 走らせると 1.79 ms で、**2.5 倍の差は帰属できていない** (49 §7)。

§5 の内訳 (「advise → 常駐を待つ → 走らせる」) を 4 run ぶん揃えると、
**P-3/P-4 の解釈が変わる。**

| | n | 中央値 | 26.87 MB 換算 |
| --- | ---: | ---: | ---: |
| 先読みを出して常駐を待つ (`mincore` が 1,640/1,640 になるまで) | 20 | **2.70 ms** | 9.95 GB/s |
| **その後**にコマンドバッファを走らせる | 20 | **4.25 ms** | **6.32 GB/s** |
| うちカーネル本体 (§3 で別に測ってある) | — | 0.25 ms | 111 GB/s |
| **残り = フォールト/マッピング** | — | **4.00 ms** | **2.44 µs/ページ** |

**1,640 ページが全部ページキャッシュに載っていることを確認してから走らせても、
コマンドバッファは 4.25 ms 掛かる。**ディスクは 1 バイトも読んでいない。
カーネルは 0.25 ms なので、**残る 4.00 ms はページをこのタスク/GPU に
マップする費用**である (**導出**。`mincore` は VM オブジェクトの常駐を答えるので、
残っているのは PTE と Metal の residency 側の帳簿である。
どちらの取り分かは**未確認**)。

これで 3 つの数字が 1 本につながる (**導出**):

| | 内訳 |
| --- | --- |
| P-3 (先読み無し、13.1 ms) | フォールトが**ディスク待ちを直列に含む** |
| P-4 (先読みあり、6.2〜6.8 ms) | ディスクを先読みに逃がした残り = **フォールト 4.0 + α** |
| P-2 (暖かい、0) | **同じマッピングを 2 回目に触るのでフォールトが無い** |

⇒ **`F_RDADVISE` が効いていたのは「ページを速く運ぶから」ではなく
「ディスク待ちをフォールト列から外に出すから」である** (§5 の最終段落の観察と一致)。
**そして外に出しきれていないのは 4.00 ms のほうである。**

## 12. 取り分の再評価 — 47 §4 の立て方に穴が 2 つある (**導出**)

> **穴 2 の表は [49 §4](49-D-P5-RESIDENCY-SET.md) が取り下げている。**
> 「ページ/tok × µs/ページ」の掛け算そのものが当たらない。
> **穴 1 (「2 つの独立な見積もり」は同語反復) はそのまま生きている。**

**穴 1: 「2 つの独立な見積もり」は独立ではない。**
47 §4 はコピー側 28.3 ms/tok と GPU 側 25.2 ms/tok の一致を裏付けにしているが、
45 §4 の会計は `wall ≈ busy + io` であって、38.76 − 14.21 = **24.55** と
GPU 側 25.2 は**同じ量を 2 度書いたもの**である。差 3.1 ms は「消えずに残る
`io` の 1/4」(3.55) にほぼ等しい。**根拠は 1 本である。**
加えて 41 §1 は scalar decode の別 run、45 §4 は `sym` の別 run で、
**40 §4-11 が自分で決めた「条件が違う絶対値は並べない」に触れている。**

**穴 2: フォールト費用が計上されていない。**§11 の 2.44 µs/ページを
production の触り方に当てると、**どの前提を置いても今の `io` と同じ桁になる**:

| 前提 (1 歩でフォールトするページ) | ページ/tok | 直列なら ms/tok |
| --- | ---: | ---: |
| **初回タッチだけ** (`bench/mtp46/trace_boundary.tsv` の decode 21.9 エキスパート/歩) | 4,490 | **10.95** |
| 今のミスと同数 (45 §4、38.45/tok) | 7,882 | **19.23** |
| 全要求 (240/tok、マッピングが 1 歩も生き残らない場合) | 49,200 | 120.0 |
| **対照: 今の `io`** (45 §4) | — | **14.21** |

**1 行目の 21.9 エキスパート/歩は 24 tok のトレース 1 本 (n=1) から数えた値で、
運用長での追試が要る** (→ §13)。ただし**結論は 1 行目に依存しない** —
帯の下端 10.95 でも今の `io` の 0.77 倍で、**「`io` の 3/4 が消えて 10.5 ms 取れる」
という 47 §4 の前提は、そのままでは成り立たない。**

⇒ **D の取り分を決めるのは 2 つだけ**:

1. **フォールトをコマンドバッファの外に出せるか** (§13 の P-5)。出せれば §11 の
   4.00 ms は前の層の GPU 仕事の陰に隠せる。出せなければ上表がそのまま費用になる。
2. **マッピングが生き残る率**。P-2 の「0」は 2 回目に触ったページの値である。
   production で 1 歩あたり何ページが「既にマップ済み」かは**未測定**であり、
   ページプール 12.011 GiB に対しこの機械で使える上限は約 10 GiB しかない
   (46 §5b の起動前の内訳から**導出**)。
