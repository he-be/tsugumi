# 26. M6 の結果 — Server に載せた

測定: 2026-08-18、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3。
対象モデル `scratch/gemma4-qat.gturbo` (drafter 同梱)。触ったファイルは §6。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

M5.6 まではループを回すのが CLI だけで、`TurboFieldfareServer` は
`--draft-block-size` を知らなかった。04-PHASES の M6 (CLI / Server / 受入) の
残りはそこ 1 点である。本書はサーバーに同じ 1 本の口を足し、
**pi (コーディングエージェント) が実際に投げる形** — tools 宣言つき・streaming・
プロンプトキャッシュ有効 — で A/B を取った。

---

## 0. 結論 — 4 つ

1. **サーバーに `--draft-block-size` が入った** (§1)。既定は 0 (オフ) で、
   0 のときは MTP 以前と 1 命令も変わらない。ドラフター無しのモデルに
   `> 0` を渡した起動は**ポートを開く前に落ちる**。
2. **pi 形のコーディング要求で 1.386 倍** (§2、3 回の中央値 25.3 → 18.3 s)。
   同じ要求の出力は **2,213 文字が 1 バイト違わない**。受理長は 2.346。
3. **日本語の散文では 1.0 倍** (§2)。受理長が **1.058** しかなく、
   13-M3 が測った「日本語長文 0.91〜1.12 倍」の帯にそのまま乗る。
   **タスク依存は二次だと書いた 22 §3 の読みは、この 2 タスクの間では成り立たない**
   — 感度表は受理長 a を固定して費用側を振る道具なので、a 自体がタスクで
   2 倍動く区間には答えを持っていない。
4. **ゲート 9 (プロンプトキャッシュ) は合格** (§3)。2 ターン目の
   `cached_tokens` は MTP on/off とも **209** で、続きの本文も一致する。
   ゲート 1 は**サーバーでも分岐する**が、分岐は投機ではない:
   `TF_MTP_DRAFTS=0` (提案ゼロ) でも同じ日本語の生成が 90 文字目で分かれる。

## 1. 書いたもの (**実測**、コード)

CLI と同じ名前・同じ値・同じ検証の 1 フラグ:

| | |
| --- | --- |
| フラグ | `--draft-block-size <0 or 2...8>` (既定 0) |
| 起動時に落とす | `--prefill off` との併用 / ドラフター section の無いモデル |
| リクエスト単位で退避 | `repetition_penalty != 1.0` は素の decode 経路で答える |
| ログ | 完了行に `mtp=4 rounds=179 accept=2.346` を足す |

- **`SpeculativeScratch` はプロセスに 1 本、起動時に確保する。**0 のときは
  確保しないので、MTP 以前のメモリプロファイルがそのまま残る (ゲート 4)。
- **退避を「拒否」にしなかった理由**: D5 の受理規則は「ターゲット自身が引く
  はずだった 1 手」と比べる規則で、その 1 手が (位置, seed, 確定済み履歴) だけから
  再現できることに依存する。repetition penalty はまだ確定していない履歴に
  依存させるので検証できない。**答えられる要求を 400 で断る理由はない**ので、
  その要求だけ素の経路に落とす。
- ストリーミング・tools・プロンプトキャッシュの各経路は**触っていない**。
  `runRawCompletion` を呼んでいた 1 か所が分岐しただけで、進捗コールバックは
  両経路で同じものを渡している。

## 2. 速度 (**実測**、同一プロセス内 3 回の中央値)

条件: `--expert-cache-slots 80 --verification trusted-install --max-context 16384`、
temp 0、on と off は**別プロセス**(サーバーの設定はプロセス固定)。
どちらも 1 回捨ててから 3 回測っている (expert キャッシュを温める)。

**(a) pi 形のコーディング要求** — tools 4 本 (`read`/`bash`/`edit`/`write`) 宣言、
`stream: true`、`max_tokens 600` (両条件とも `finish=length` で打ち切り):

| | off | on (bs=4) | 比 |
| --- | ---: | ---: | ---: |
| 壁時計 (中央値) | 25.329 s | **18.280 s** | **1.386** |
| 壁時計 (3 回) | 28.672 / 25.329 / 25.203 | 20.276 / 17.959 / 18.280 | |
| 出力 | 2,213 文字 | 2,213 文字 | **1 バイト差なし** |
| 受理長 / ラウンド | — | 2.346 / 179 | |

**(b) 2 ターンの対話** (tools 無し、非ストリーミング、`max_tokens 400`)。
2 ターン目はプロンプトキャッシュがヒットする:

| ターン | off 壁時計 | on 壁時計 | 比 | `cached_tokens` |
| --- | ---: | ---: | ---: | ---: |
| 1 (cold prefix) | 8.257 s | **5.453 s** | **1.514** | 0 / 0 |
| 2 (cache hit) | 7.351 s | **5.004 s** | **1.469** | 209 / 209 |

出力は両ターンとも on/off で一致 (164 / 161 トークン)。

**(c) 日本語の散文** (600 字程度の説明を求める、非ストリーミング):

| | off | on (bs=4) | 比 |
| --- | ---: | ---: | ---: |
| 壁時計 (中央値) | 11.214 s | 11.136 s | 1.007 |
| decode t/s (中央値) | 26.2 | 28.6 | 1.093 |
| 生成トークン | 294 | 319 | (本文が分岐している) |
| 受理長 | — | **1.058** | |

> **受理長がタスクで 2 倍動く。**vis 1.885 (25-M5.6)、code 2.346、日本語散文 1.058。
> 費用側は同じなので、**同じバイナリで 1.39 倍のタスクと 1.0 倍のタスクがある**。
> 22 §3 の感度表は a を入力に取る道具なので、この差は感度表の外側にある
> (「タスク依存は二次」は**費用側を振ったときの**話だった)。

## 3. 正しさ (**実測**)

**ゲート 9 (Server / プロンプトキャッシュ) — 合格。**
`cached_tokens` は on/off とも 0 → 209 で一致し、キャッシュがヒットした
2 ターン目の本文も一致する。投機した位置が publish されないのは
コード側でも見えている: `promptCache.publish` が読むのは巻き戻し後の
`kvBackedTokenIDs` / `kvPosition` で、これは D6 のループが
「投機しなかった世界」と同じ値にしてから返すもの (15-M4 のゲート)。

**ゲート 1 (出力一致) — 分岐する。位置を記録する。**

| 比較 | 結果 |
| --- | --- |
| code (tools + streaming、600 tok) | **2,213 文字が全一致** |
| 2 ターン対話 (164 + 161 tok) | **全一致** |
| 日本語散文 (294〜319 tok) | **247 文字目で分岐** |
| 日本語散文、`TF_MTP_DRAFTS=0` (提案ゼロ) | **90 文字目で分岐** |

- **投機を切っても分岐する**ので、原因は投機ではなく、15-M4 §2 が特定した
  「ブロック経路 対 スカラー decode 経路」の既存差である。競り合った位置
  (top-1 マージンが logits 誤差の帯 3.8e-2 より小さい位置) がどちらに倒れるかを
  丸めが決める、という 25-M5.6 §4 と同じ話が、長い日本語生成では
  **数百トークンに 1 回起きる**ということ (**実測**)。
- 24-M5.5 / 25-M5.6 が `bench/m.json` で 215/215 全一致だったのは
  **96 トークン・英語・thinking off** の条件だったから、と読むのが正しい
  (**導出**)。分岐しない条件を選んで測っていた。
- **どちらの側が「正しい」かは、この検査では決まらない。**両方ともターゲットの
  argmax であって、差は FP16 の丸めである。
- 各条件の生成は**プロセスを跨いで決定的**である (同条件 2〜3 回で 1 バイト差なし)。

**その他** (**実測**): tool call は on/off で同一
(`read_file{"path":"/etc/hosts"}`、`finish_reason=tool_calls`)。
`repetition_penalty: 1.1` の要求は 200 で答える (素の経路に退避)。
`Scripts/test.sh` は §6 の新規 2 本を含めて **860 テスト / 145 スイート**、
25-M5.6 と**同じ 11 issues・同じ 4 スイート** (App のピン留め監査 / 既定値の陳腐化)。
**新規失敗ゼロ**、テストは 858 → 860。

## 4. 残っているもの (**実測** + **導出**)

25-M5.6 §5 の残り (`moe` の 11 ms、ホスト往復の 14 ms) はそのままである。
本書が足したのは 2 つ:

1. **受理長の低いタスクでは投機が効かない** (§2c)。費用側をどれだけ削っても
   日本語散文は 1.0 倍前後にとどまる。効かせるならドラフター側 (M3.5 以来
   1 行も触っていない) の話になる。
2. **サーバーは常に logits ヘッド経路で走る** (`forceLogitsHead: true`)。
   CLI の採点 (25-M5.6 §3) は temp 0 = 融合 greedy ヘッドで測ったので、
   サーバーの数字はそれより不利な側で測られている (**導出**、A/B は取っていない)。
   ヘッド経路をリクエストの温度で切り替えるにはロード時の分岐を動かす必要がある。

## 5. 測り直しの 1 行

```bash
.build/release/TurboFieldfareServer --model scratch/gemma4-qat.gturbo \
  --port 8091 --expert-cache-slots 80 --verification trusted-install \
  --draft-block-size 4
```

`accept` はサーバーの完了ログに出る。off 側は `--draft-block-size` を外して
同じ要求を投げ、**壁時計と本文の両方**を比べる (t/s だけを比べると、
本文が分岐したときに長さの違いを速度と読み違える — §2c がその例)。
