# MTP (Multi-Token Prediction) — 計画

QAT ウェイト対応・Vision 対応に続く 3 つ目の大改修。
`google/gemma-4-26B-A4B-it-qat-…-assistant` ドラフターを使った
propose-and-verify (投機デコード) を本ランタイムに入れる。

**現在地: M4 完了 ([15-M4-RESULTS.md](15-M4-RESULTS.md))。正しさは全部通った。
費用が想定の 3〜4 倍で、次は M5 ではなく M4.5 (verify の費用)。**

verify パス (`verifyBlock`) と KV 巻き戻し (`rewind`) が入り、M4 の出口条件 3 つは
成立した: 全位置の argmax が 1 トークンずつの `produce` と **256/256 一致**、
巻き戻し後の続きが「巻き戻さなかった世界」と **16/16 一致**、わざと壊した
巻き戻し 3 通りは全部 FAIL する。数値は bit 一致ではない (最大 3.8e-2 相対) が、
**その差は verify が作っていない** — 投機要素ゼロの k=1 ブロックが同じ値を出すので、
正体はチャンク経路とスカラー decode 経路の既存差である (15-M4 §2)。

**一方、M4 で初めて測った verify の費用は `2.6 + 0.86k` decode ステップ** —
k=4 で **7.0 ステップ**で、10-M0 §2 が導出した 1.85 の 3.8 倍だった (15-M4 §4)。
GPU 内訳の 60〜69% が routed MoE で、64 行タイルを 4 行のために回している。
この費用のままでは 14-M3.5 の受理率を入れても **2.5〜3.7 倍の減速**になるので、
14-M3.5 §5 の速度比 (math 1.59 など) は**無効**である。

受理率側は参照実装と並んでいる (14-M3.5)。残っているのは**ターゲット側の実行効率**だけで、
そこも余裕は薄い: 固定費を全部消しても k=4 は 3.4 ステップ (math 0.79 倍) で、
限界費用を M0 の帯域下限まで下げてようやく 1.59 倍 (15-M4 §5-1)。
decode 経路 (`produce`) は今も無変更で、`verifyBlock` を呼ばない実行のコストはゼロ。

## ゴール (2026-08-17 に確定)

QAT ウェイト・Vision・MTP の 3 改修が揃った状態として、**Server** で
**単発の Vision タスクを Reasoning ON で** `pp ≥ 200 t/s` / `tg ≥ 30 t/s` で回す。
GUI は対象外。**主眼は wall time で、t/s は目安**。
受理率はタスク依存なので、**cpp / haiku / math / story / vis の 5 本**で測り、
先読み長 k のトレードオフを併せて記録する。
現在地とゴールの距離は M0 §4。`pp 200` は tower 固定費のため構造的に未達 (M0 §0-5)。
`tg 30` (= 1.48 倍) の見通しは **M4 で後退した**。14-M3.5 §5 の速度比
(math 1.59〜1.73 / m 1.36〜1.39) は M0 の費用モデルで引いた値だが、
M4 が verify を実測して 3 倍の乖離を見つけた (15-M4 §4) ため無効。
**受理率は参照実装と同水準まで戻っている**ので、残る変数はターゲット側の実行効率
1 つに絞られた。M4.5 で k=4 の verify を 2.5 decode ステップ以下にできるかが分岐点で、
できなければこの構成での MTP は成立しない (15-M4 §5)。
**MTP が負うのは素直な高速化まで**で、残りは decode 経路の別の仕事になる。

表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

## この計画の運用ルール

`PLAN_VISION.md` が 1,728 行になり、途中から誰も通読できなくなった反省で分けている。

- **1 文書 = 1 論点。**目安 200 行以内。超えたら分ける。
- **進捗は文書を増やして書く。**既存文書の先頭に `0-A` `0-B` … と積んでいく形は取らない。
  M0 の結果は `10-M0-RESULTS.md`、M1 は `11-M1-RESULTS.md` というように
  **段ごとに新しいファイル**を作り、この索引に 1 行足す。
- **設計文書 (01〜05) は書き換える。**結果が出て前提が変わったら追記ではなく本文を直す。
  「読むべき最新の設計」が常に 1 か所にあるようにする。訂正の履歴は git log が持つ。
- 受入結果は最後に `RESULTS_MTP.md` (リポジトリ直下、PLAN §6 準拠) にまとめる。
  `RESULTS_QAT.md` / `RESULTS_VISION.md` と同じ場所・同じ体裁にする。
