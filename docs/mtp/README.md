# MTP (Multi-Token Prediction) — 計画

QAT ウェイト対応・Vision 対応に続く 3 つ目の大改修。
`google/gemma-4-26B-A4B-it-qat-…-assistant` ドラフターを使った
propose-and-verify (投機デコード) を本ランタイムに入れる。

**現在地: M5 (ループ統合) 完了 ([23-M5-RESULTS.md](23-M5-RESULTS.md))。**
22-GOAL-RESET §7 の指示どおり M4.x の最適化を止めてループを先に作り、
**採点基準 v1 (ゴールタスク 8 枚の end-to-end 壁時計比の中央値) を初めて実行した**。
スコアは **1.05 倍** (bs=4)。目標 1.33 に未達、22 §5 の中止ライン 1.10 も下回る。
ゲート 1 の分岐は投機ではなくチャンク経路とスカラー decode 経路の数値差で、
**bs=2 / bs=4 / 投機ゼロの出力は 1 バイト違わない**。
ループ実測はマイクロベンチと 2 点で食い違い、`verify(4)` は 1.78 → **2.63**
decode ステップ、受理長は a(4) 1.60 → **1.90**。感度表の入力を
**F=1.33 / M=0.31 / draft=0.079** に差し替えると予測が実測を再現する
(`bench/mtp_budget.py` 更新済み)。次の 1 段は温まったブロック 89 ms の
**76% を占める `wait.front`** (30 層ぶんのホスト往復) で、
F 半減 → e2e 1.30、F と M 両方半減 → 1.70。

M4.8 まで:
19-M4.7 §7 の「次の 1 段」だけをやった: k 行カーネルは**重みを 1 回しか読んでいなかったが、
活性化は k 回読んでいた**。affine バイアス項の活性化和 (重み行に依存しないのに lm head の
262144 行が全部計算し直していた)、活性化のロードと変換、そして実行時値のままだった
ブロック幅 — この 3 つを外すと、head と Q/K/V 射影は **k=4 が k=1 と同じ時間**になる
(461 MB を 3.41 ms = 135 GB/s、帯域床)。routed MoE には別口で「常に 8 行ぶんに展開」が
あり、これも k で固定した。ブロックの GPU スパンは k=4 で **68 → 52 ms**、
費用は **2.02 → 1.78** decode ステップ (同一セッションの A/B) で、
**`verify(4)` が 16-M4.5 §6 のゲート 1.9 を初めて下回った** (ただし M5 のループ実測は
2.63 で、この水準はマイクロベンチのものだった — 23-M5 §4)。

M4.7 まで:
expert cache のスロットを 48 → **80** に広げると、18-M4.6 が「隠す」対象にしていた
読み出しが**消える**: k=4 の `fetch` は 27 → 9 ms、ブロックは壁時計 76.5 ms に対し
GPU スパン 72.5 ms で**ほぼ GPU 律速**になった。費用は k=4 で **2.38 → 2.16**、
k=8 で 4.25 → 3.57 decode ステップ。同時に 2 つの前提が崩れた: (a) ブロックが expert
和集合を畳む利益は**産出トークンで割ると 12%** しかない (18-M4.6 §2 は検証トークンで
割っていた)、(b) 費用の k に対する伸びが M0 のモデルより急なので、
**`bs=4` 固定 (14-M3.5 §5) は最良ではない** — ただし M4.8 で費用の伸びが緩み、
m は bs=4 が上に戻った (20-M4.8 §5)。

M4.6 まで:
17-M4.5 §4 が「層ごとのホスト往復と dispatch 数」と読んだ残差は、ホスト側の
新しいプロファイルで割ると **expert の読み出し待ち**だった (k=4 で 1 ブロック 106 ms の
うち 40 ms、ミス 58 回 = 0.20 GB)。読むバイトは変えずに、層の全タイルの読み出しを
grouping の直後にまとめて発行し、**常駐タイルを先に encode して**その裏に隠した。
費用は k=1 で 1.60、k=4 で **2.74 → 2.34** decode ステップ。
14-M3.5 の受理長で引くと **math が初めて黒字 (0.97 → 1.12 倍)**。
**16-M4.5 §6 のゲート (1.15 / 1.9) にはまだ未達。**
M4.5 (17-M4.5) で入った k 行カーネル (routed MoE・射影・shared expert・ヘッド・router、
カーネル単位で decode と bit 一致) はそのまま効いている。

M4 では verify パス (`verifyBlock`) と KV 巻き戻し (`rewind`) が入り、出口条件 3 つが
成立した ([15-M4-RESULTS.md](15-M4-RESULTS.md)): 全位置の argmax が 1 トークンずつの
`produce` と **256/256 一致**、巻き戻し後の続きが「巻き戻さなかった世界」と
**16/16 一致**、わざと壊した巻き戻し 3 通りは全部 FAIL する。数値は bit 一致ではないが、
**その差は verify が作っていない** — 投機要素ゼロの k=1 ブロックが同じ値を出すので、
正体はチャンク経路とスカラー decode 経路の既存差である (15-M4 §2)。この差は M4.5 でも
残っている (17-M4.5 §5) — 消すには層の前半も decode に寄せる必要がある。

M4 が測った「費用が想定の 3.8 倍」の正体は 16-M4.5 が言うとおり
**借りたカーネルの性能**だった。verify は prefill チャンク経路を借りており、
そこは 1 スレッドグループが 64 行の出力タイルを持つ。4 行のために 64 行ぶん計算するので
**演算強度が稜線を 5 倍超え、帯域律速だった decode が演算律速に変わる**。
M4.5 でこれを k 行カーネルに直した結果、**k 行に増やした演算は実際にタダだった**
(17-M4.5 §4 の GPU 実測)。残ったのはホスト側の往復と dispatch 数である。

受理率側は参照実装と並んでいる (14-M3.5)。残っているのは**ターゲット側の実行効率**
1 つで、M4.5 はその置き場所の訂正だった — 半分は直り、半分 (層の前半) が残っている。
decode 経路 (`produce`) は今も無変更で、`verifyBlock` を呼ばない実行のコストはゼロ。

## ゴール (2026-08-17 に確定)

QAT ウェイト・Vision・MTP の 3 改修が揃った状態として、**Server** で
**単発の Vision タスクを Reasoning ON で** `pp ≥ 200 t/s` / `tg ≥ 30 t/s` で回す。
GUI は対象外。**主眼は wall time で、t/s は目安**。
受理率はタスク依存なので、**cpp / haiku / math / story / vis の 5 本**で測り、
先読み長 k のトレードオフを併せて記録する。
**採点基準は [22-GOAL-RESET.md](22-GOAL-RESET.md) に凍結した (v1)。**
`pp 200` は tower 固定費のため構造的に未達 (M0 §0-5)。`tg 30` は単位を固定して

| | v1 |
| --- | ---: |
| **目標** | ゴールタスク 8 枚 (`sample_imgs/`、Reasoning ON、temp 0、80 スロット、生成長の上限なし) の **end-to-end 壁時計比の中央値 1.33 倍** |
| **中止** | **1.10 倍**を切る → 報告して停止 |

と読む。比は必ず**同一セッションの MTP on/off 交互 A/B** で取り、絶対 t/s は載せない。

**採点は M5 のループ実測だけで行う。**M4.x に点数は付けない — 15-M4 から 21 までの
速度比はすべて `verify(k) × a` の**導出**で、別条件で測った 2 つの proxy の積を
成績表に載せたために 6 本が互いを差し替え続けた (22 §1)。**倒れたのは水準だけで、
同一セッション A/B で取った差分は 1 件も倒れていない** (22 §2)。

改修候補は着手前に**感度表**に通す (`./bench/mtp_budget.py`、22 §3): 現状
**F (ブロック 1 回の固定費) が唯一の大きなレバー** (半減で e2e 1.29、床付近で 1.58)、
**受理長 a はもう効かない** (vis を math 並みにしても 1.08)、
**タスク依存は二次** (4 タスクの幅 0.16〜0.20 に対しレバーは 0.6)。
現在地は **e2e 1.00 前後** (21 §6 の導出。M5 未実装のため実測はまだ無い)。

表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

## この計画の運用ルール

`PLAN_VISION.md` が 1,728 行になり、途中から誰も通読できなくなった反省で分けている。

- **1 文書 = 1 論点。**目安 200 行以内。超えたら分ける。
- **進捗は文書を増やして書く。**既存文書の先頭に `0-A` `0-B` … と積んでいく形は取らない。
  M0 の結果は `10-M0-RESULTS.md`、M1 は `11-M1-RESULTS.md` というように
  **段ごとに新しいファイル**を作り、この索引に 1 行足す。
- **設計文書 (01〜05) は書き換える。**結果が出て前提が変わったら追記ではなく本文を直す。
  「読むべき最新の設計」が常に 1 か所にあるようにする。訂正の履歴は git log が持つ。
- 受入結果は最後に `RESULTS_MTP.md` (リポジトリ直下、PLAN §6 準拠) にまとめる。
  `RESULTS_QAT.md` / `RESULTS_VISION.md` と同じ場所・同じ体裁にする。
