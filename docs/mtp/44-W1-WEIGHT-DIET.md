# 44. W1 — QAT ウェイトの `bias` は情報ゼロ。`scale` は詰めると負ける

測定: 2026-08-20、M3 Pro 18GB / macOS 15.7.5 / commit `4311ad5`。
一次資料は `bench/mtp44/`。**推論経路 (`Sources/Tsugumi/`) は無改変** —
足したのは計器の 1 ファイル (`BpwProbe.swift`) と `main.swift` のフラグ 1 つ、
それと `bench/check_bias_identity.py` である。

[43](43-P2-MOE-ROWS-TAIL.md) §2 が `gate/up` を **133〜137 GB/s の帯域床**と読んだ。
床にいるなら**時間はバイトである**。ならば「バイトを減らせば減った分だけ速くなる」が
検定できる。減らせるバイトが実在するかを先に確かめ (§1、§2)、あるならカーネルで
測る (§4、§5)。34 の P リストには無い枝なので **W1** と呼ぶ。

## 0. 結論 — 4 つ

1. **`bias` は情報を持っていない** (**実測**、§1)。`bias == -8 * scale` が bf16 の
   ビットパターンとして `scratch/gemma4-qat.moepack` の **7 億 8817 万群すべて**で
   成り立つ。**格子整合の QAT チェックポイント固有**で、通常の affine 量子化
   (ベースライン) は 34〜38% が外れる。落とせるのは **1.468 GiB / 14.71 GiB = 9.98%**。
2. **落とすと床の上でバイト比どおりに速くなる** (**実測**、§4)。`gate/up` は
   293.1 → 264.7 µs (**−9.7%**、バイト比 −10.0%) で、**GB/s は 135.3 → 134.8 と動かない**。
   43 §2 の「床」の読みは正しかった。運用のタイル (幅 5.7、行数混合) で **−6.5%**。
3. **`scale` を詰めるのは 2 つの別々の理由で負ける** (**実測**、§5)。
   8 ビット符号は `gate/up` を **−14.6%** にするが、**出力の相対 RMS 誤差 0.70%** を
   持ち込む (仮数 1 ビットぶん)。9 ビット符号は**ビット一致で可逆**なのに、
   展開費用が `down` の末尾に丸ごと乗って **+15.5%**。
   **運用のタイルではどちらも `sym` 単独に負ける** (−1.5% / +2.5% 対 −6.5%)。
4. **⇒ 採るのは `bias` 落としだけ。**形式は 5.000 → **4.500 bpw**、
   expertStride は 3,719,168 → **3,358,720 = group-64 ベースラインと同一**になる。

## 1. `bias` は `scale` から完全に導出できる (**実測**)

`-8` は 2 の冪なので `-8 * s` は bf16 で丸め無しに表現できる。だから恒等式は
**値ではなくビットパターンとして**検定できる (`bench/check_bias_identity.py`)。

| 対象 | 群数 | 不一致 | bias が占めるバイト |
| --- | ---: | ---: | ---: |
| resident (`model_weights.bin`) | 74,488,832 | **0** | 9.85% |
| packed experts (30 層すべて) | 713,687,040 | **0** | 10.00% |
| draft (gs=64、別リポジトリ由来) | 6,557,696 | 1,924,670 (29.35%) | 5.55% |
| **対照**: ベースライン resident | 37,413,376 | 14,202,207 (**37.96%**) | 5.53% |
| **対照**: ベースライン experts | 356,843,520 | 123,669,478 (**34.66%**) | 5.56% |

**対照群が要る。**恒等式は「affine 量子化なら成り立つ」ものではない。成り立つのは
**格子に整合させて復元したチェックポイントだけ**で、min/max から scale を再導出した
ベースラインは 3 分の 1 が外れる。draft も外れるので**対象外**である。

落ちるバイト: experts **1.329 GiB** + resident **142.1 MiB** = **1.468 GiB**、
インストール済みウェイト 14.71 GiB の **9.98%**。

## 2. `scale` 側には 16 ビット中 9 ビットしか入っていない (**実測**)

同じスクリプトが 2 つ目を測る。**符号ビットは全群で 0**、そして行内の bf16 指数の幅は:

| span | 0 | 1 | 2 | 3 | 4 以上 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 行の割合 (17,389,056 行) | 5.77% | 90.40% | 3.45% | 0.32% | **0.062%** |

⇒ 行ごとに指数アンカーを 1 バイト置けば、**2 ビットの指数差 + bf16 の仮数 7 ビット
= 9 ビットで 99.94% の行がビット一致**する。仮数のエントロピーは 6.838/7 ビットなので
**そこは縮まない**。つまり 4.500 bpw の残りに手を入れる余地は「16 ビット → 9 ビット」
しかなく、上限は **4.287 bpw** である。§5 はこれを実際に作って測る。

## 3. 計器 — 形状ではなく**形式**だけを振る (**実測**)

`TsugumiKernelCheck --bpw-probe`。43 の `--moe-rows-shape-sweep` が還元次元を
振ったのに対し、こちらは**形状を production に固定して重みの形式だけを振る**。

`BpwProbe.swift` は `prefill_moe_rows_gate_up_act` / `prefill_moe_rows_down` の
自己完結な写しを**独自の MTLLibrary** にコンパイルする。ランタイムのシェーダは
1 行も変わらない。形式は関数定数 (index 17) で特殊化する:

| 形式 | 群あたりの scale メタデータ | B/行 (gate/up, down) | bpw |
| --- | --- | ---: | ---: |
| `affine` (production) | bf16 scale + bf16 bias | 1760, 440 | 5.000 |
| `sym` | bf16 scale、`w = s*(q-8)` | 1584, 396 | 4.500 |
| `sym8` | 8 bit 符号 (指数 2 + 仮数 6) + 行アンカー | 1497, 375 | 4.253 |
| `sym9` | 9 bit 符号 (指数 2 + 仮数 7) + 行アンカー | 1509, 381 | 4.287 |

**演算は 3 形式で同一に保ってある。**`affine` は `fma(s,dot,acc); fma(b,sum,acc)`、
対称形は `fma(s, fma(-8,sum,dot), acc)` で、**どちらも 2 FMA**。活性化の 8 要素和も
ロードも同じ。**動くのは重み側のバイトだけ**である。

**写しの検定 (これを先に置く)。**`affine` を production の形状で測ると
**gate/up 293.1 µs / down 216.4 µs** で、43 §2 の **297.8 / 222.4** と 1.6〜2.7% で
一致する。以下の数字はこの写しの上で読んでよい。

## 4. `bias` を落とすと、床の上でバイト比どおりに速くなる (**実測**)

16 エキスパート 1 タイル、r=2 (運用点)、50 反復、3 回の中央値。GB/s は重みトラフィック
で、床は 20-M4.8 §3 の 135 GB/s。

| `gate/up` (D=2816、88 群、末尾なし) | µs | **GB/s** | 対 affine |
| --- | ---: | ---: | ---: |
| affine | 293.1 | **135.3** | . |
| **sym** | **264.7** | **134.8** | **−9.7%** |
| sym8 | 250.2 | 134.8 | −14.6% |
| sym9 | 251.9 | 135.0 | −14.0% |

| `down` (F=704、22 群、6 群の末尾) | µs | **GB/s** | 対 affine |
| --- | ---: | ---: | ---: |
| affine | 216.4 | 91.6 | . |
| **sym** | **201.5** | **88.5** | **−6.9%** |
| sym8 | 218.0 | 77.5 | +0.7% |
| sym9 | 249.9 | 68.7 | +15.5% |

⇒ **`gate/up` の GB/s は 3 形式で 134.8〜135.3 と動かない。**バイトが 10.0% 減れば
時間が 9.7% 減る。**43 §2 の「床」は床だった。**
⇒ **`down` は GB/s が落ちる** (91.6 → 88.5 → 77.5 → 68.7)。バイトを減らしても
時間がその比では減らない ＝ **バイトで払っていない**。43 §2 と同じ結論に、
今度は形式側から到達している。

再現性: 3 run で `gate/up` affine は 293.5/293.1/292.2 (0.4%)、`sym` の対 affine は
−10.2/−9.7/−7.5%。`down` の `sym` は −7.3/−7.3/−6.1%。

**数値の一致 (**実測**)**: `sym` 対 `affine` は `act` / `route_partials` とも
**最大 0.0000% / 0.0003%** (half 1 ulp)。**同じ答えである。**

## 5. `scale` を詰める枝は閉じる — 理由は 2 つあって別々である (**実測**)

**(a) `sym8` は答えを変える。**仮数を 7 → 6 ビットにすると、scale 符号そのものの
誤差が **最大 0.775% / RMS 0.410%**、ビット一致するのは **50.0%** の群だけになる。
そしてこの誤差は**出力で薄まらない** — カーネルの出力で測ると
**gate/up の RMS 0.70%、down の RMS 0.42%**。群のスケール誤差は群の寄与に
コヒーレントに乗るので、群数の平方根では割れない。**この大きさを是とするかは
KL の対照群を置かないと言えない**ので、ここでは採らない。

**(b) `sym9` は答えを変えないが、展開費用が `down` の末尾に落ちる。**
9 ビット符号はフィクスチャで **100% ビット一致**、出力も `sym` と完全一致する。
それでも `down` は **+15.5%**。理由は 43 §3 が特定した場所と同じで、
`down` の 22 群は **2 ブロック + 6 群の末尾**であり、**末尾は 1 群ずつ 16 レーンで
回る**。ブロック経路では 1 群の展開を 4 レーンが並列に負担するが、
**末尾では償却先が無い。**`gate/up` (88 群 = 11 ブロック、末尾なし) では
逆に `sym` より 4.8% 速い。

**(c) 運用のタイルではどちらも `sym` 単独に負ける。**32 §5 の行数混合
(1:4036 2:1257 3:818 4:449) と実タイル幅で測ると:

| タイル幅 | affine | **sym** | sym8 | sym9 |
| ---: | ---: | ---: | ---: | ---: |
| 6 (production は 5.7) | 259.8 µs | **242.8 (−6.5%)** | 256.0 (−1.5%) | 266.2 (+2.5%) |
| 16 | 715.8 µs | **682.3 (−4.7%)** | 715.6 (−0.0%) | 756.1 (+5.6%) |

⇒ **均一 r で読める −14% は運用点に残らない。**43 が「31 §6 の −17% が 32 で −7% に
なった」と書いたのと同じ落ち方をする。`gate/up` だけを `sym9` にする混成も、
幅 6 では `gate/up` が 108.2 → 114.3 µs と**負ける**ので救えない。

**⇒ scale フィールドはこの 2 本のカーネルでは詰められない。**§2 が示した
「16 ビット中 9 ビット」は事実だが、**残り 7 ビットを取り出す費用のほうが高い。**

## 6. 判定 — `bias` 落としだけを進める

形式は **`sym` (4.500 bpw)**。QAT チェックポイント限定で、repack 時に群ごとに
恒等式を検定し、破れたら**落とさずに拒否する**のが正しいガードである
(ベースラインを黙って壊さないため)。

持ち帰るもの (**導出**、実測はカーネル単体まで):

| | 現行 | `sym` |
| --- | ---: | ---: |
| expertStride | 3,719,168 | **3,358,720** (= group-64 ベースラインと同一) |
| インストール | 14.71 GiB | 13.28 GiB |
| resident | 1512.9 MB | ~1364 MB |
| expert キャッシュ (48 スロット) | 4.99 GiB | **4.50 GiB** (同予算なら **53 スロット**) |
| io | ミス数 × stride | **−9.69%** |

`io` はミス数 × `expertStride` に厳密比例する (`ModelExpertIO.swift:100`) ので
バイト比がそのまま乗り、41 §3 で `idle ≈ io` なので壁時計に出る見込みが立つ。
`head` も 20-M4.8 §3 の床測定 (461 MB を 3.41 ms) そのものなので同率で効くはずだが、
**これは未測定である** (§7)。

## 7. 限界 (**未確認**)

- **測ったのは routed MoE の rows カーネル 2 本だけ**である。`head` /
  dense 射影 / shared expert は同じ affine gs=32 だが、**このプローブは触っていない**。
  §5(b) の結論 (「末尾のあるカーネルでは展開費用が償却できない」) は、
  末尾の無い `head` には**そのまま持ち越せない**。
- **合成重み・常駐・I/O 無しの単体計測**である。GPU 秒 → 壁時計の変換は
  33 §5 / 41 §3 の枠が要る。**t/s は測っていない。**
- **repacker も形式も実装していない。**上の表の stride とキャッシュは
  バイト勘定の**導出**であって、リパックして測った値ではない。
- §2 の span 分布には resident と draft が混ざっている。routed expert だけに
  絞ると 2 ビットで足りない行は 1622 万行中 **1 行**である。

## 8. 再現手順

```bash
# §1 / §2 — 格子の検定 (7 秒、scale/bias のページしか触らない)
cd scratch && python3 ../bench/check_bias_identity.py gemma4-qat.moepack
python3 ../bench/check_bias_identity.py gemma4.moepack   # 対照群

# §3-§5 — 形式スイープ (1 回 4 分。3 回、間に 20 秒のクールダウン)
swift build -c release --product TsugumiKernelCheck
./.build/release/TsugumiKernelCheck --bpw-probe --group-size 32 \
    --moe-rows-bench-iterations 50
```

`bench/check_bias_identity.py` は numpy が要る (`/Users/mh/LLM/venv`)。
