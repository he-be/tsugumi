## 1. 測り方 — decode 経路は無変更のまま

04-PHASES §2 のとおり、verify パスも KV 巻き戻しもループ改修もなしで測った。

- `TF_DRAFT_PROBE=<path>` が立っているときだけ、decode の各ステップで
  ドラフターを `drafts` 回まわし、提案列を記録する。**KV には 1 バイトも書かない。**
- 提案は、その後ターゲットが実際に出したトークンと突き合わせる。一致した接頭辞の
  長さがそのラウンドの受理長 (**導出**: D5 の same-seed 規則から、提案が受理される
  条件は「ターゲットが引いた 1 個と等しい」ことだけ)。
- `drafts=3` の 1 回の走行で **bs=2/3/4 が同時に出る** (**導出**: ドラフターは
  greedy で bs に依存しないので、bs のラウンドはこの提案列の先頭 bs−1 個)。
- 記録は全位置で取るが (dense)、集計は **ラウンドを鎖でつないで**行う
  (受理 a のあと次のラウンドは a+1 先から始まる)。10-M0 §3 の上限表と同じ数え方で、
  直接比較できる。dense 平均との差は 0.05 以内 (**実測**)。

計装は `Sources/TurboFieldfare/MTP/DraftAcceptanceProbe.swift` と、
`RealForwardRunner.produceToken` の 2 か所の呼び出しだけ。オフのときのコストは
`draftProbeSettings != nil` の判定 1 個。

## 2. 受理長と速度比 (**実測**)

384 tok 生成、Reasoning ON、64 スロット、prefill on/chunk 128、seed 1。
`a` は鎖で数えた平均受理長、括弧内は M0 の上限に対する達成率。

| プロンプト | temp | a (bs=2) | a (bs=3) | a (bs=4) |
| --- | --- | ---: | ---: | ---: |
| math | 0 | 0.597 (65%) | 1.016 (55%) | 1.309 (51%) |
| math | 1.0 | 0.677 (74%) | 1.117 (61%) | 1.639 (63%) |
| story | 0 | 0.477 (59%) | 0.649 (42%) | 0.693 (35%) |
| story | 1.0 | 0.460 (57%) | 0.614 (40%) | 0.686 (34%) |
| m (技術説明) | 0 | 0.592 | 1.071 | 1.262 |
| m | 1.0 | 0.588 | 0.974 | 1.254 |
| haiku | 0 / 1.0 | 0.800 (87%) | 1.571 (91%) | 2.000 (80%) |

- **haiku は参考値にとどまる**: 22 tok で `endOfTurn` に達し、鎖のラウンドが
  6〜10 本しかない (**実測**)。temp 0 と 1.0 で完全に同じ列を引いており、
  この長さでは温度の差が出ていない。
- **達成率は 34〜91%。**10-M0 §4 が「ゴールには上限の 83% が要る」と書いた水準に
  届いているのは haiku だけで、story は 34〜59% にとどまる。
- **temp 1.0 は受理率を壊さない** (**実測**)。math は temp 1.0 のほうが高く、
  story はほぼ同じ。10-M0 §3 の「切り落としのおかげで抽選分布が尖っている」という
  説明と整合する。
- **bs を上げると story は損に転じる。**受理長が 0.65 → 0.69 とほとんど伸びない
  一方、`cost(k)` は 1.60 → 1.85 と増えるため (**導出**)。

## 3. ドラフターの実費用 (**実測**)

| プロンプト | ドラフター 1 ステップ |
| --- | ---: |
| story / math (プロンプト 43〜96 tok) | 2.73〜3.59 ms |
| m (プロンプト 518 tok) | 4.66〜5.17 ms |

10-M0 §2 は「ドラフター 1 ステップ = 0.236 GB = decode の 9.8%」と**バイト数から**
見積もっていた。decode 実測 31 ms/tok (`RESULTS_VISION.md` §3) に対して 2.7 ms は
8.7% で、**バイトベースの見積もりが妥当だったことを壁時計で裏づけた** (**実測**)。

ただしこの値は診断の測り方 (embed 1 回 + ドラフター 1 回、それぞれ commit + wait) を
含むので、**上振れ側の値**。M4 以降で 1 本のコマンドバッファにまとめれば下がる
(**導出**)。プロンプトが長いほど伸びるのは共有 KV への attention が伸びるため。

## 4. ドラフターの入力規約 — 実測で決着 (**実測**)

M2 の fixture は「同じ入力を与えたとき参照と一致するか」しか見ていないので、
**ラウンドで何を入力に選ぶか**は M3 で初めて問題になった。上流の 2 実装は
この点で読みが割れている:

- HF `SinglePositionMultiTokenCandidateGenerator`:
  `last_hidden_state[:, n_last_matches]` と `input_ids[:, -1:]` — hidden は
  bonus トークンの**1 つ前**の位置、`position_ids = input_ids.shape[1] - 1`。
- mlx-vlm `set_shared_kv`: `position` の既定値が `kv_offset` そのもの
  (キャッシュの**次**のスロット)。

3 通りを同じプロンプトで測って決めた (192 tok、temp 0、bs=4 の平均受理長):

| mode | 内容 | math | story |
| --- | --- | ---: | ---: |
| `prev-last` | hidden は 1 つ前、RoPE 位置は**最後にキャッシュされた位置** | **1.30** | **0.553** |
| `prev-bonus` | hidden は 1 つ前、RoPE 位置は bonus トークン自身 | 1.07 | 0.532 |
| `same` | hidden は同じ位置、KV に自分の行を含む | 1.65 | 1.03 |

- **`prev-last` を採用した** (`TF_DRAFT_PROBE_MODE` の既定)。実装可能な 2 通りの
  うち両プロンプトで一貫して高い。
- **`same` は採用できない** (**導出**)。この構成はドラフターに「ターゲットが
  その hidden からすでに引いたトークン」を予測させており、実ラウンドでは bonus
  トークンはタダで手に入る。しかも bonus トークンは定義上まだターゲットに
  食わせていないので、その KV 行は存在しない。数字が高いのは、**受理を 1 個
  水増ししているから**であって速くなるからではない。
- DeepSeek 系 MTP の定式 (`h_i` と `emb(t_{i+1})` から `t_{i+2}` を予測) とも
  `prev-*` が一致する。

`DraftForward.encode` に `kvLength` を足して、この 3 通りを表現できるようにした
(既定は `position + 1` = M2 の fixture 規約なので、M2 の突合は無変更で通る)。

## 6. 実装上の発見 — 量子化 group サイズが 1 プロセスに 2 つある

`MetalContext` は affine group サイズを**シェーダライブラリに焼き込む**
(「1 プロセス 1 モデル、モデルの group サイズは一様」という前提)。ところが
MTP 付きの `.gturbo` は**1 ファイルの中でこの前提を破る** (**実測**):

- ターゲット (26B): `manifest.quant.*.groupSize` = **32**
- ドラフター: `manifest.draft.quant.groupSize` = **64**

M2 の `KernelCheck --draft` は既定の group 64 のコンテキストで走っていたので
表に出なかった。decode ランタイムに載せた最初の瞬間に、ドラフターの int4 GEMV が
全部でたらめになり (提案がすべてトークン 0)、それで発覚した。

対処として `MetalContext(sharingDeviceWith:)` を足した — 同じ `MTLDevice`、
別のキュー、別のライブラリ。バッファはデバイス単位なので 2 つのコンテキストで
共有でき、キュー間の順序は呼び出し側 (プローブは各ステップで待つ) が持つ。

**M4/M5 に進む場合はここが設計判断になる** (**導出**): (a) 2 コンテキストを
本番でも持つ (ライブラリのコンパイルが 1 回増える)、(b) ドラフターを group 32 で
repack する (M1 の取得経路と M2 の bit-exact 確認をやり直す)、(c) group サイズを
関数定数に落とす (シェーダ全体に波及)。

## 9. 判断を引き継ぐ人へ

- **止める場合**: 入れたものは診断だけで、decode 経路は probe オフで無変更。
  そのまま置いておいても害はない (§5)。
- **続ける場合の最短路**: bs=2 固定 + §6 の group サイズ問題を (b) で解いてから
  M4 (verify パス) に進む。ただしゴール (1.48 倍) には届かないことを承知の上で。
- **測り直したくなったら**: `TF_DRAFT_PROBE=/tmp/probe.tsv .build/release/TurboFieldfareCLI
  --model scratch/gemma4-qat.gturbo --messages-file bench/story.json ...` の 1 行。
  TSV には位置ごとの提案・実際・受理長が残るので、bs や鎖の数え方は後から変えられる。
