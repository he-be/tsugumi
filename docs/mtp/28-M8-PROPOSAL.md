# 28. 提案 — M7 の先: 物理限界か、まだ果実が残っているか

書いた日: 2026-08-19。実測は取っていない — 本書は 27-M7 までの実測の**再読**と、
`~/LLM/llama.cpp` (v0.1.0, 34af94cd9, 2026-08-17) の調査から成る提案書である。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

問いは 3 つ: (1) 物理限界に達したと言えるか、(2) low hanging fruit が残っていないか、
(3) 試していない発想の転換は無いか。llama.cpp から取り込めるものは各節に混ぜ、
§6 に一覧を置く。

## 0. 結論

**物理限界には達していない。**限界と言えるのは「SSD の実効帯域」と
「dense 部の DRAM 帯域」の 2 つだけで、**大きな定量ギャップが 2 つ残っている**:

1. **`moe` の 28 ms は帯域床 15.4 ms の 1.8 倍で、行の追加が丸ごと 1 エキスパート
   読み分の値段になっている** (§2、27 §6 の 3 点の再読)。M4.8 が dense 側で取った
   「k 行はタダ」が routed 側では実現していない。
2. **32 スロットの idle 33 ms は「読むバイト数」ではなく「読み出しを発行できる
   時刻」の問題**で、発行時刻は物理ではない (§3)。27 §7 の「予測はできない」は
   **履歴ベース**の話であり、**隠れ状態ベースの投機的先読みは未試行**。

2 つとも当たれば 32 スロットで 30 t/s が射程に入る (**導出**、§7)。
どちらも「まず半日〜1 日の計測で仮説を潰せる」形にしてある。

## 2. 果実 A — `moe` の 28 ms: 行の追加がタダになっていない (**導出**)

27 §6 の表を割り算し直すと、3 点が 1 本の線に乗る:

| bs | ペア/エキスパート (= 平均行数 r) | µs/エキスパート | µs/ペア |
| ---: | ---: | ---: | ---: |
| 2 | 1.29 | 35.0 | 27.1 |
| 4 | 1.72 | 50.2 | 29.2 |
| 6 | 2.00 | 61.0 | 30.6 |

`µs/エキスパート = a + b·r` に当てると **a ≈ −12, b ≈ 37** — 切片がほぼゼロ
(負値はノイズ) で、**行 1 本の限界費用 37 µs が、エキスパート 1 個の重み全読み
27.5 µs (3.72 MB / 135 GB/s) を上回っている**。つまり
`prefill_moe_rows_gate_up_act` は重みロードを行間で共有している
(コード上は 1 回しか読まない) のに、**共有の利益が実効ゼロ**である。
dense 側の rows カーネルは「k=4 が k=1 と同じ時間」(20-M4.8 §3) だったから、
これは routed 固有の現象で、27 §6 の「ロード幅を変えても不変」とも整合する —
**律速はロードのバイト数ではない**。

候補は 2 つ (**未確認**、どちらも counters で区別できる):

- **発行/占有率律速**: 行ループが `g_acc[cap]`/`u_acc[cap]`/`x_row[cap]` を
  レジスタに持ち、simdgroup あたりの命令数が r に比例する。occupancy が
  レジスタで頭打ちならロード改善が効かないことも説明できる。
- **活性化の再読が L2 に乗っていない**: 1 行あたり各 simdgroup が x (5.6 KB) を
  全周読む。キャッシュに乗らなければ活性化トラフィックはペア × 約 4 MB で、
  これも実測 (≈ ペア × 27.5 µs) を再現する。ただし 27 §6 の「2 行/simdgroup で
  不変」はこの説に不利。

**打ち手** (この順で):
1. Instruments の GPU counters で occupancy / stall 理由 / 実 DRAM トラフィックを
   取る (27 §6 自身が挙げた次の一歩)。**半日**。どちらの説かはここで決まる。
2. 発行律速なら: 出力 2 行 (f, f+1) を 1 simdgroup に持たせる形を「活性化削減」
   でなく「r ループの命令を重み側と共有する」設計で再訪。または
   **simdgroup_matrix 化** — llama.cpp の `kernel_mul_mm_id`
   (`ggml/src/ggml-metal/ggml-metal.metal:10598`、simdgroup 行列で expert 別
   タイル GEMM) が同形状の先行実装。**ただし総和順序が変わる**ので
   「ブロックは decode の一般化」(16-M4.5 §4) と衝突する — env-gate で入れ、
   ゲート 1 (出力 md5) で判定する。26 §のとおり margin 1e-3 の反転が増える
   リスクは明記しておく。
3. 活性化説なら: x を threadgroup memory に載せる (1 tg = 8 f行 × 全 r 行で共有)。

**期待値** (**導出**): moe 28 → 16 ms なら 48 スロットで busy 47 → 35 ms、
ブロック 67 → 約 55 ms、**約 33 t/s**。32 スロットでは −4〜5 ms/tok。

## 3. 果実 B — 隠れ状態ベースの投機的エキスパート先読み (発想の転換)

27 §7 は「直前ラウンドのミスの 0.0% しか再要求されない」から「予測はできない」
と結んだ。だがこれは**履歴からの予測**の話で、ミスは定義上「最近使われていない
もの」だから当たらないのは当然である。**未試行なのは計算そのものからの予測**:

**層 L の hidden に層 L+1 の router を先行適用し、L+1 の union fetch を層 L の
処理と同時に発行する。**residual stream は隣接層で似ているので top-8 の重なりは
高いことが知られている (Mixtral offloading / Pre-gated MoE 系の文献の中心手法)。
router 重みは全層で 22 MB (720 KB × 30、27 §5) で常駐でき、GEMV は µs オーダー。

- **正しさは不変**: 先読みはヒントに過ぎず、実行は正規の routing で行う。
  外れたら今と同じ (待つ)。出力バイトは 1 つも動かない — ゲート 1 は自明に通る。
- **注意 2 つ**: (a) 外れた先読みは SSD 帯域とスロットを浪費する。まず
  「空きスロット/最下位 LFU にしか置かない」制約付きで入れる。
  (b) 32 スロットでは**追い出し合戦**になりうる — 的中率次第。
- **まずオフラインで的中率を測る** (**未確認**): hidden をダンプし、
  L+1〜L+3 の router を先行適用して実 routing との top-8 重なりと
  「実ミスのうち先読みが当てた率」を出す。トレース基盤
  (`--dump-expert-trace`) と `bench/mtp_expert_sim.py` に乗る。**1 日**。

**期待値** (**導出**): 的中率 p でミス露出はほぼ (1−p) 倍。p=0.7 なら
idle 33 → 約 13 ms、32 スロットのブロック 82 → 約 62 ms。
**decode 側 (MTP off) にも同じだけ効く**ことに注意 — 32 スロットは off 側も
I/O 律速 (27 §2c) なので、絶対 t/s は両側で上がり、スコア比は下がりうる。
目標が「32 スロットで 30 t/s」(絶対値) なら、これは正しい方向である。

## 4. 果実 C — 小さいもの (実装済みの口で測れる)

1. **bs スイープを 32 スロットで取り直す**。sim ではミス/産出tok が k=2〜6 で
   平坦 (39.6〜40.5、27 §3) — I/O 費用は k に中立なので、受理/round が伸びる分
   bs=6 が 32 スロットで勝つ可能性がある。ただし moe はペア比例 (§2) なので
   **A の前に測ると結論が変わる**。フラグは既存。**半日**。
2. **適応ドラフト長**: llama.cpp の `--draft-p-min` (`common/speculative.cpp:335`
   — ドラフターの top-1 確率が閾値を切ったら打ち切る)。moe がペア比例である限り、
   受理されない位置のペアは GPU 時間の純損失で、story 系 (a=0.937) で効く。
   受理規則は変えないので出力は不変。
3. **48 スロットの既定化 or メモリ圧力での動的スロット**: 30 t/s は 48 スロット
   (peak 6.83 GB) で既に射程 (27 §7)。「16GB 機に 6.83 GB は許されるか」は
   性能でなく製品判断なので、`DISPATCH_SOURCE_TYPE_MEMORYPRESSURE` で
   48 → 32 に落とす動的化を提案する (逆方向の昇格は再読が要るので保守的に)。
4. **ドラフターを verify の idle に重ねる**: 全受理 (次ブロックの接頭辞が確定)
   を仮定した先行ドラフト。32 スロットではブロック中 GPU が 33 ms 遊んでいる。
   当たれば round あたりドラフト 3 ステップ (約 3 ms/tok) が消える。外れたら
   捨てるだけで、正しさは不変。中規模の配管 (ドラフター KV の巻き戻し)。

## 5. 発想の転換 — 検討して**却下**したもの (理由付き)

| 案 | 却下理由 |
| --- | --- |
| 全エキスパートを低 bit で RAM 常駐 (miss 時のフォールバック) | int4 で 14.3 GB (128 experts × 30 層 × 3.72 MB)。int2 でも 7.2 GB で他と合わず 16GB に入らない。そもそも hit/miss で数値が変わり、出力がキャッシュ状態依存になる — ゲート 1 と決定性の原則に反する |
| ツリー投機 / 多候補ドラフト | ペア数と union の両方が増える。moe はペア比例 (§2)、32 スロットは I/O 律速 — 両方の壁に正面から当たる。受理長は完全勝利でも 1.08 (22 §3) |
| より良いドラフター (EAGLE3 / DFlash / DSpark、`common/common.h:171`) | 同上 — a はレバーでない。ドラフト費用 0.079 も既に小さい |
| n-gram 自己投機 (`NGRAM_*`、同上) | 同上。コード系タスク限定で受理は伸びるが感度表の外 |
| ディスク上のエキスパート再配置 (共起ペアの隣接化で pread 融合) | 読み出しは既に並列発行でプローブの帯域上限近く (27 §7)。回数を減らしても帯域は増えない |
| KV キャッシュ量子化 (llama.cpp の `-ctk`) | `attn.swa` は 1.5 ms (25-M5.6) — もう的が小さい |
| エキスパートの zstd/LZ4 圧縮 | int4 QAT 重みは高エントロピーで 1 割も縮まない見込み。帯域限界なので伸びしろ自体が小さい |

**却下しなかった転換が 1 つ**: **スロットキャッシュを捨てて mmap +
`makeBuffer(bytesNoCopy:)` にする** — llama.cpp の中心設計。エキスパートの
常駐管理を OS のページキャッシュに委ねると、キャッシュ容量が「固定 N スロット」
でなく「空き RAM 全部」になり、**32/48 のジレンマそのものが消える**
(clean page は圧力で自動的に落ちる)。決定性も保たれる (同じバイトを読む)。
**未確認**が 2 つ: GPU アクセス起点のページインのレイテンシが pread より
悪くないか、`useResource` が働く粒度。1〜2 日のプローブで判定できる。
当たれば PreadExpertStreamer の置き換えという大工事なので、A/B の後に。

## 7. 期待値の合算と推奨順序 (**導出**)

32 スロット、現状 23.6 t/s (42.4 ms/tok = ブロック 82 ms / 2.703 tok + 口幅 12 ms):

| 積む | ブロック | ms/tok | t/s |
| --- | ---: | ---: | ---: |
| 現状 | 82 | 42.4 | 23.6 |
| + A (moe 28→16) | 約 74 (busy −12、露出増を差し引き) | 約 38 | 約 26 |
| + B (p=0.7) | 約 60 | 約 33 | 約 30 |
| + C-4 (先行ドラフト) | — | 約 30 | 約 33 |

48 スロットは A だけで約 33 t/s。**数字はすべて導出であり、A は counters の
半日、B はオフライン的中率の 1 日で、実装前に潰せる。**

順序: **(1) A の counters (半日) → (2) B の的中率 (1 日) → (3) C-1 の bs
スイープ (半日) → (4) 外部校正 (半日) → 実装は A → B → C の当たった順**。
(1)(2) が両方外れたら、そのときはじめて「32 スロットは物理限界、運用点は
48 スロット」と言ってよい — 現時点でそう言うのは早い。
