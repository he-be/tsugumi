## 0. 結論 — 6 つ

1. **`moe` はこの HW の相場である。A は閉じてよい** (§6、**導出**)。同じアーキ
   (30 層・128 エキスパート・topK 8) を全常駐で回す llama.cpp の decode は
   **26.9 ms/tok**。エキスパートのバイト数で割ると **20.3 GB/s**。
   turbo の off 側 40.5 ms/tok (27 §2、48 スロット) は **22.0 GB/s** で、
   **参照実装より 8% 速い**。28 §6 の「2 倍悪いのか」への答えは
   **相場どおり、むしろ僅かに上**である。M3 Pro の実効帯域 150 GB/s に対して
   両者とも 14% しか出ていない — これは MoE decode が
   「240 個の小行列を毎トークン集める」形だからで、実装の問題ではない。
2. **参照実装でも受理長は k で単調に伸び、壁時計は k で単調に悪化した** (§3、**実測**)。
   L5 (機構指標で壁時計を語らない) が**独立実装で再現**した。
   `sample_llamacpp_cmd.txt` の `--spec-draft-n-max 4` はこの機械では
   **base 比 0.61〜0.64 倍**、つまり投機を切ったほうが 1.6 倍速い設定である。
3. **損益分岐受理長は測れる。しかも 2 種類の数だけで決まる** (§4、**実測**)。
   ブロックの壁時計は `step(k) = base + Σc_i + d·k` に乗る
   (c = verify 位置 1 つの限界費用、d = ドラフト 1 本の費用)。
   llama.cpp は **c = 0.27 → 0.53 → 0.69 base (位置が奥に行くほど高い)、
   d = 0.15〜0.23 base** で、分岐点は k=1 で 1.49、k=2 で 2.15、k=4 で 3.8。実受理長 (1.6 / 2.0 / 2.4) と
   突き合わせると **k=1 だけが勝つ**。34-M9 §5 が「P1 の台帳が出るまで数字を
   言わない」と書いた台帳は、**この形 (c, d の 2 値) で書けば十分**である。
4. **turbo の c は llama.cpp の 1/3 である** (§6、**導出**)。27 §2 の実測
   (48 スロット、off 24.7 → on 28.9 t/s、受理長 1.885) を同じ式に入れると
   **c + d ≈ 0.20 base**。llama.cpp は 0.70 base。**これが turbo の構造的な強み**
   で、ブロックが union を 1 回読むぶん verify 位置が安い。
   **k を減らす方向の P3 は、この安さのぶんだけ取り分も小さい。**
5. **P3 の前提 (confidence で受理/棄却が分離する) は参照実装で成立する** (§5、**実測**)。
   `p_min = 0.90` はドラフトを **−65%** 落として受理を **−19%** しか落とさない
   (story: 315→111 本、受理 111→90)。34-M9 §3 が要求した「受理の 9 割を保って
   ペアを 3 割落とす τ」は、**受理 81% 保持でペア 65% 削減**という形で存在する。
6. **ただし p_min は「一番良い固定 k」に勝てなかった** (§5、**実測**)。
   最良の適応設定 (n8/p0.90) は base 比 0.91〜1.00、固定 k=1 は 1.08〜1.14。
   理由は 2 つ: (a) **ゲートは払った後にしか効かない** — 打ち切り 1 回につき
   ドラフト前進 1 本が丸ごと無駄になる (§5c)、(b) k=1 の 1 本目は条件付き受理率が
   60〜71% もあり、そもそも削る余地が無い (§3c)。
   ⇒ **P3 は「現行 bs=4 との比較」ではなく「最良の固定 bs (bs=2 を含む) との比較」で
   採点しなければならない。P4 の行列に bs=2 (ドラフト 1 本) が入っていないのは穴である。**

| 増分 (ms) | — | +7.3 | +14.2 | +18.6 | +17.0 | (+4.5)* | +20.1/本 |

| image | 4 | 103.6 | 85.0 | 18.5 | 4.6 | 3.85 | 2.341 | 負け |

**ドラフト 1 本 = 4.1〜6.1 ms が 3 つの k で一定**である。別々の 2 つの計器
(サーバの壁時計と batched-bench) が同じ内訳に収束したので、この分解は信用できる。

⇒ **台帳は (c, d) の 2 値でいい。**`step(k)/base = 1 + (c+d)·k` と

llama.cpp の c は平坦ではない — 2 本目 +7.3 ms (0.27 base)、3 本目 +14.2 (0.53)、
4 本目 +18.6 (0.69)、5 本目 +17.0 (0.63) と**奥ほど高い**。d は 4.1〜6.1 ms
(0.15〜0.23 base) で**深さによらず一定**。
34-M9 の P1 が作ろうとしている「ブロック別 (io, busy) 結合分布」は、
**この 2 値を測るための道具**と位置づければ半日で終わる。

## 5. P3 の参照実装 — `--spec-draft-p-min` を振る (**実測**)

`common/speculative.cpp:1632` の MTP ドラフトループは
`cur_p->data[0].p < params.p_min` で打ち切る。34-M9 §3 が置いた案そのものである
(ただし margin ではなく **top-1 確率**。しかも `top_k = 10` で切ったあとの
再正規化確率である — `speculative.cpp:1211` のサンプラ構成)。

| task | 設定 | t/s (base 比) | ドラフト総数 | 受理総数 | ドラフト/ラウンド | 受理長 | step |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| story | n4 p0 | 23.27 (0.628) | 315 | 111 | 3.89 | 2.370 | 101.3 |
| story | n4 p.75 | 34.86 (0.941) | 142 | 98 | 1.51 | 2.043 | 58.3 |
| story | **n4 p.90** | **37.14 (1.002)** | 111 | 90 | 1.09 | 1.882 | 50.4 |
| story | n8 p.90 | 36.69 (0.990) | 103 | 86 | 0.97 | 1.811 | 49.1 |
| math | n4 p0 | 23.80 (0.641) | 312 | 113 | 3.95 | 2.430 | 101.6 |
| math | n4 p.90 | 36.31 (0.978) | 124 | 94 | 1.27 | 1.959 | 53.7 |
| math | **n8 p.90** | **37.22 (1.002)** | 155 | 111 | 1.91 | 2.370 | 63.4 |
| image | n4 p0 | 22.49 (0.608) | 322 | 110 | 3.93 | 2.341 | 103.6 |
| image | **n4 p.90** | **34.23 (0.926)** | 120 | 86 | 1.13 | 1.811 | 52.6 |
| image | n8 p.90 | 33.49 (0.906) | 116 | 81 | 1.05 | 1.730 | 51.4 |

**(a) 前提は成立する。**ドラフトの精度 (受理/ドラフト) は
p0 の 34〜36% から p.90 で 70〜81% に上がる。**confidence は受理/棄却を分離する。**
34-M9 §3 の検定 1 (margin の ROC) は、**やる前から答えが半分見えている** —
少なくとも同型のドラフタでは分離する。

**(b) それでも固定 k=1 に負ける。**最良の適応設定は 0.91〜1.00 base、
固定 k=1 は 1.08〜1.14 base。**適応は「大きすぎる k」を救うが、
「正しい k」には勝たない。**

**(c) なぜ負けるか — ゲートは払ってからしか効かない** (**導出**)。
story の n4 p.90 は ドラフト/ラウンドが 1.09 本で k=1 とほぼ同じなのに、
ステップは 50.4 ms と k=1 の 40.0 ms より 10.4 ms 重い。ループは
「decode してから confidence を見て捨てる」ので、**打ち切り 1 回につき
ドラフト前進 1 本 (4〜5 ms) が丸損**になる。加えて時々 2 本目が通るので
verify も少し大きい。**この 1 本の無駄が、削ったペアの利得をほぼ食う。**

⇒ turbo で P3 を実装するときの設計上の帰結:
**「今引いた札の confidence で次を止める」形にすると、止めるたびに 1 本払う。**
turbo の d (ドラフト費用) は 27/32 の台帳では単離されていない。
**P3 の検定 1 の前に d を単離しないと、P3 の期待値は立たない** (L4)。

## 6. turbo に翻訳する (**導出**)

**(a) 帯域の相場。**エキスパートの実バイト数で割る。
アーキは両者同じ (30 層 × topK 8 = 240 エキスパート/tok)。

| | エキスパート 1 個 | /tok のバイト | step | 実効帯域 |
| --- | ---: | ---: | ---: | ---: |
| llama.cpp IQ3_XXS | 2.277 MB (3.06 bpw) | 546 MB | 26.9 ms | **20.3 GB/s** |
| turbo QAT int4 | 3.719 MB (`expertStride`) | 892 MB | 40.5 ms (24.7 t/s、27 §2) | **22.0 GB/s** |

**turbo のほうが 8% 速い。**28 §6 と 34-M9 §5 が「A を閉じる」条件に挙げた
外部校正は、**A を閉じる側に出た**。P2 の counters は「なぜ 20 GB/s しか
出ないか」を知るためには意味があるが、**`moe` にまだ 2 倍が眠っている、
という説はこれで消える**。M3 Pro の 150 GB/s に対して両実装とも 14% しか
使えていないのは、MoE decode が小行列 240 本の gather だからである。

**(b) c の比較 — turbo の構造的な強み。**27 §2 の実測 (48 スロット、
off 24.7 → on 28.9 t/s、受理長 1.885) を §4 の式に入れると
`step/base = 1.885/1.170 = 1.611`、bs=4 (ドラフト 3 本) なので
**c + d ≈ 0.204 base/位置**。llama.cpp を同じ本数 (3 本、k=3) で揃えると
`step/base = 3.00`、**0.67 base/位置**。**turbo の verify 位置は 3.3 倍安い** — union を 1 回読む構造がそのまま出ている。
27 §2 の「スロットが少ないほど投機が効く」も同じ式で読める
(I/O が重いほど c が相対的に小さくなる)。

**(c) だから優先順が変わる。**
- **turbo で k を増やす価値は llama.cpp より大きく、減らす価値は小さい。**
  c+d = 0.204 なら、位置を 1 本削って得られるのは 0.204 base、
  失うのは受理 1 本 = 1.0 base。**打ち切ってよいのは受理確率が 20% を切る位置だけ**である。
- **その 20% 未満が実在する場所が 1 つある**: 26 §2(c) の日本語散文、
  **受理長 1.058** (= a1 ≈ 0.058)。ここは 3 本すべてが 20% を大きく下回る。
  この形では `step/base = 1.611` を払って 1.058 しか産んでいないので、
  **ドラフトを止めるだけで 1.52 倍**になる (**導出**)。
  §5 の実測 (story で n4 → n8/p.90 が 0.628 → 0.990 = 1.58 倍) はこれの実例である。
- ⇒ **P3 の正味の価値は「散文でドラフトを止めること」に集約される。**
  「受理されそうにない位置を削って産出を保つ」(34-M9 §3 の期待) ではなく、
  **タスクごとに投機を on/off する門番**として評価するのが正しい。
  ROC の検定は残す価値があるが、**τ の候補は 0.2 付近**であって、
  llama.cpp の 0.9 のような高い閾値ではない (c が 3.4 倍違うため)。

**(d) P4 の行列に穴がある。**34-M9 §4 の P4 は bs {3,4,6} を回す予定だが、
参照実装では **k=1 (bs=2) が全タスクで唯一の勝ち**だった。
turbo の c は小さいので最適 k はもっと大きいはずだが、**それは測っていない**。
**bs=2 を行列に入れる。**また 26 §2 のとおり受理長はタスクで 2 倍動くので、
**行列はタスク軸 (vis / code / prose) と直積で回さないと最適 k は決まらない。**

## 7. 参照実装から拾った細かい事実 (**実測**、コード読み)

1. **投機パラメータは per-request で変えられない** (`server-schema.cpp:195` が
   `#if 0`)。A/B は必ずプロセス再起動。turbo が env で切り替えられるのは利点。
2. **gemma4 の MTP ドラフタは target の KV を共有する** (`speculative.cpp:1373`
   `is_mem_shared`)。しかも**全ドラフト位置が同じ position を使う**
   (`speculative.cpp:1665` のコメント、HF の gemma4_assistant の仕様)。
   turbo の DraftForward が position をどう置いているかの照合先になる。
3. **ドラフタのサンプラは `top_k = 10` 固定**で、p_min はその**再正規化後の
   top-1 確率**と比較される (`speculative.cpp:1211`)。
   turbo が margin (top1−top2) を使うなら**閾値の意味が変わる** — 移植するときは
   同じ量に揃えるか、τ を独自に取り直すこと。
4. `--spec-draft-n-min` は「これ未満なら draft を丸ごと捨てる」で、
   打ち切りとは別の口 (`speculative.cpp:1270`)。
5. サーバは decode グラフを再利用している (`graphs reused = 110/192 tok`)。
   グラフ構築費が毎ステップ乗らない設計で、turbo の可変長ブロック
   (34-M9 §3 の「可変長ブロックになる」) を作るときの対照になる
   — **可変長にするとグラフ/パイプラインの再利用が壊れないか**は
   turbo 側で確認が要る (**未確認**)。
6. モデルロードは `--no-mmap` で 11.4 GB を **3.2 s (≈3.5 GB/s)**
   (ページキャッシュ温、**実測**)。33 §1 の冷たい天井 6.0〜6.5 GB/s と整合する。

## 9. 限界 (**未確認**)

- 量子化が違う (IQ3_XXS 3.06 bpw vs QAT int4 5.0 bpw/エキスパート)。

  −0.8% だったので系統誤差はその程度と見ている。
