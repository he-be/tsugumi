対象モデル `scratch/gemma4-qat.gturbo` (drafter 同梱)、**32 スロット**。
測ったのは **verify ブロックの費用曲線 c** (幅 k を 1,2,3,4,6,8 で振る) と、

34-M9-PROPOSAL §4 の **P1 (台帳)** と **P4 (行列)** に当たる作業で、
35-LLAMACPP-CALIBRATION §6(d) が「turbo 側で d を単離しないと次の判断が立たない」

## 0. 結論 — 15 つ

1. **32 スロットの c は 0.38〜0.54 base/位置である** (§2、**実測**)。
   幅 k のブロック 1 回は base の **0.99 / 1.38 / 1.83 / 2.36 / 3.59 / 4.79 倍**
   (k = 1/2/3/4/6/8)。平均 c = (step/base − 1)/(k−1) は
   **0.380 / 0.415 / 0.453 / 0.518 / 0.541** で、**奥ほど高い**。

2. **35 §6(b) の導出には 2 つの読み違えがある** (§3、**実測**、コード読み)。
   (i) footer の `accept` は**受理長ではなく「ラウンドあたり受理ドラフト本数」**
   である (`SpeculativeCompletion.swift:66-70` / `Run.swift:312-314`)。受理長
   (tok/round) はこれに **+1**。35 は 1.885 を分子に置いたが、正しくは 2.885。
   (ii) 27 §2(b) の「24.7 → 28.9 t/s」は **M7 の 3 改修の before/after** であって
   off/on ではない。**両方とも MTP on** である。
   ⇒ **0.204 という数字は使えない。48 スロットの c+d は本書でも未測定。**
3. **本番 footer から 32 スロットの (c, d) 台帳が今日すぐ取れた** (§3、**実測**)。

   `rounds / accept / draft / verify / decode` が全行に入っている。8 枚の画像で
   **step(4)/base = 1.735〜1.935 (c = 0.245〜0.312)、d = 3.10〜3.31 ms/本

4. **turbo の bs=4 は 32 スロットで構造的に負けてはいない** (§3c、**導出**)。

   **2.849〜2.949**。llama.cpp と同じ量 (総ラウンド費用を位置数で割る) で揃えると

   のであって 3.3 倍ではない。**35 §6(d) の「bs=2 だけが勝つ」は参照実装の性質で、
   turbo にそのまま移るとは言えない。**それでも bs=2 を行列に入れる理由は残る (§4)。
5. **ブロックが広いほどキャッシュ hit 率は落ちるが、位置あたりのミスは落ち続ける**
   (§2b、**実測**)。hit は 73.5% → 67.6% → 60.2% (decode/k=4/k=8) と落ちるが、
   これは union の重複除去で**要求そのものが 240 → 114 件/位置に減る**からで、
   ミスは **63.6 → 45.4 件/位置 (−29%)** と単調に減っている。
   **union の再利用は効いている。頭打ちになるのはバイトの側ではなく費用の側である。**
   33 §3〜§4 の「48 スロットでは I/O はもう床ではない」を verify 幅の側から
   見た同じ絵である (**導出**)。

## 1. 測り方 (**実測**)

計器は `Sources/TurboFieldfareKernelCheck/VerifyBlockCheck.swift` の
`costProbe` (`--verify-cost-only`、`:651-779`)。設計はこうである:

- **同じトークン列・同じ位置**を、1 トークンずつの `produce` と 幅 k の
  `verifyBlock` の両方で歩く。列は最初の decode パスが記録した greedy 列で、
  どの幅も**同じ 144 位置**を歩く (`blocks = total / k`、`:744`)。
  幅ごとにブロック数を固定すると、広い幅ほど深い KV で測ることになるので、
  そうしていない (`:692-696` のコメント)。
- **decode 基準は幅ごとに測り直す** (`:729`、`:760-761`)。この機械は 1 run の
  中でドリフトするので、各幅は**前後 2 本の decode 基準の平均**で割られる。
- warm cache (既定)。各フェーズの先頭 2 ブロックぶんは計時から捨てる (`:745`)。
- 144 位置 = (16 timed + 2 warmup) × 8 (`CostProbePlan`、`:610-620`)。

コマンド:

```
TF_EXPERT_CACHE_SLOTS=32 TF_VERIFY_COST_WIDTHS=1,2,3,4,6,8 \
  .build/release/TurboFieldfareKernelCheck --verify-block scratch/gemma4-qat.gturbo \
  --verify-cost-only --verify-block-size 4 \
  --verify-image sample_imgs/IMG_2113.JPG --verify-thinking
```

### 5b. 温度は受理だけでなく**費用構造ごと**切り替える

`isPureGreedy = (temperature == 0 && repetitionPenalty == 1)`
(`Sources/TurboFieldfare/Runtime/Generation/RawCompletion.swift:69-71`)、
`forceLogitsHead: !config.isPureGreedy` (`Sources/TurboFieldfareCLI/Run.swift:158`)、
`guard !fusedGreedy || config.isPureGreedy`
(`Sources/TurboFieldfare/Runtime/Generation/CompletionPrefill.swift:41-42`)。
**temp 0 は融合 greedy ヘッド、temp 1.0 は logits ヘッド**で、
経路が分岐する。実測された差は 4b のとおり
**ラウンド外費用 0.06〜0.83 ms/round (temp 0) 対 1.277 ms/引いた行 (temp 1.0)**。

⇒ **温度を変えると「受理長」と「ラウンド外費用」の両方が動く。**
`step(k) = base + Σc_i + d·k` の 3 つの入力のうち 2 つが温度に依存する。
**温度をまたいで台帳の数字を流用してはいけない。**

### 5c. 論点 — **採点基準 v1 は temp 0 で凍結されているが、運用点は temp 1.0 である**

22 §4 の採点基準 v1 は **「8 枚 × 固定プロンプト / Reasoning ON / temp 0 /
80 スロット / 生成長の上限なし」**である。凍結された基準なので、
これを動かすのは製品判断であって本書の判断ではない。

一方、**実際の運用点は temp 1.0 である** — temp 0 は同一文の反復に落ちるので、
出荷する設定にはならない。ここに正面からの矛盾がある:

- **採点は temp 0 でやる**。ならば最適 bs は temp 0 で決めるべきである
  (受理長 2.885 なら bs=4 は §2 の分岐点 2.36 を悠々と超える)。
- **ユーザは temp 1.0 で使う**。ならば最適 bs は §4f のとおり **2〜3** で、
  bs=4 は 8〜14% 損している。

**最適 bs は温度で変わる。**したがって
**「どちらの温度で採点するか」は、性能の問題ではなく製品の問題である。**
本書はこれを決めない — **上に戻す**。
決めるまでは、**bs の既定値を 4 から動かす判断もできない** (**未確認**)。

対照実験 (同じスイープを temp 0 で回す) は本書の執筆時点で測定中であり、
**本書では結論を出さない**。

**→ その後、対照は 3 本とも完走した** (`bench/logs/36_cd_sweep_temp0.tsv`、
`36_cd_thinkon.tsv`、`36_cd_thinkon_bs.tsv`)。**結果は §10 にある。**
本節が「決めない」と書いた製品判断 (どちらの温度で採点するか) は
**依然として上に戻したまま**だが、**「最適 bs は温度で変わる」は §10e で
5 条件 9 通りに広げて裏取りされた** — そして**どの条件でも bs=4 は最適でない**。

1. **§2 は画像 1 プロンプト 1 本・warm cache・各幅 1 回測り・thinking on。**

2. **decode 基準が 8.6% ドリフトしている** (54.3 → 50.0 ms/tok)。
   計器は前後ブラケットの平均で割るので比への影響は小さいはずだが、
   幅ごとに 1 回しか測っていないので**分散と区別できていない**。
3. **48 スロットの対照が無い。**§3d のとおり、35 §6(b) との食い違いを
   「スロット数の違い」で説明する仮説は**まったく検証していない**。
4. **`io=` 列は壁時計ではない。**§1 の (b) のとおりフェッチ呼び出しの総和で、
   幅が広いほど同時に飛ぶタイルが増えるので過大に出る。
   **実効帯域をこの列から出してはいけない。**
   (`VerifyBlockCheck.swift:630-632` のコメントは「verifyBlock は prefill バケットに
   計上する」と書いているが、実装は `RealForwardRunner.swift:723` で
   `beginPhase(.decode)` している。`ExpertIODelta` は両バケットの差を足すので
   §2b の数字には影響しないが、コメントは古い。)
5. **costProbe は融合 greedy ヘッドで測っている — temp 1.0 の運用点で毎行払う
   費用が入っていない。**これが §2/§3b に対する最大の留保である。裏を取った経路:
   - `costProbe` は runner を **`forceLogitsHead: false`** で作る
     (`VerifyBlockCheck.swift:673`)。つまり融合 greedy ヘッドで、
     logits バッファは書かれない。
   - 本番 CLI は `forceLogitsHead: !config.isPureGreedy`
     (`Sources/TurboFieldfareCLI/Run.swift:158`)、
     `isPureGreedy = (temperature == 0 && repetitionPenalty == 1)`
     (`Sources/TurboFieldfare/Runtime/Generation/RawCompletion.swift:69-71`)。
     **temp 1.0 は必ず logits ヘッドに落ちる。**そうしないと
     `Sources/TurboFieldfare/Runtime/Generation/CompletionPrefill.swift:41-42` の
     `guard !fusedGreedy || config.isPureGreedy` が
     `unsupportedPrefillSeed` を投げて止まる。
   - logits ヘッドになると `SpeculativeCompletion.swift:196-217` の
     `targetToken` が blit 経路に入る: **引いた行 1 本につき 512 KiB の
     blit + 専用コマンドバッファ + `waitUntilCompleted` + `sampleOnce`**。
     引く行数は **受理数 + 1** なので、bs=4 なら **ラウンドあたり約 2.9 本**。
   - この費用は **`verifySeconds` にも `draftSeconds` にも入らない**
     (`SpeculativeCompletion.swift:341-342`、`RealForwardRunner.swift:726-731`)。
     落ちるのは `decode − draft − verify` の残差 = §4 の `outside_s` である。
   ⇒ **§2 の c 曲線と §3b の台帳 (どちらも temp 0 / 融合 greedy) は、
   temp 1.0 の運用点の費用を下に見積もっている。**
   **§4b がこの経路を実測で裏取りした** (1.277 ms/引いた行) が、
   §2/§3b の数字がそのぶん低いという評価は変わらない。

   **両者の (c, d) を直接並べてはいけない。**§5 のとおり温度は

### 8a. 費用曲線を 3 つのスロット数で並べる (**実測**)

各セルは `costProbe` が前後 2 本の decode 基準の平均で割った `step(k)/base` を
ログからそのまま写した値である (§1 の暖機の扱いは 3 本とも同じ)。

| k | 16 スロット | 24 スロット | 32 スロット |
| ---: | ---: | ---: | ---: |
| decode base (ms/tok) | **57.1** | **53.1** | **51.2** |
| 1 | 1.01 | 1.00 | 0.99 |
| 2 | 1.65 | 1.51 | 1.38 |
| 3 | 2.30 | 2.03 | 1.83 |
| 4 | **3.02** | **2.67** | **2.36** |
| 6 | 4.20 | 4.05 | 3.59 |
| 8 | 5.22 | 5.32 | 4.79 |

平均 c = `(step(k)/base − 1)/(k−1)` に直す (**導出**、四則のみ):

| k | 16 スロット | 24 スロット | 32 スロット |
| ---: | ---: | ---: | ---: |
| 2 | 0.650 | 0.510 | 0.380 |
| 3 | 0.650 | 0.515 | 0.415 |
| **4** | **0.673** | **0.557** | **0.453** |
| 6 | 0.640 | 0.610 | 0.518 |
| 8 | 0.603 | 0.617 | 0.541 |

**bs=4 の平均 c は 0.673 / 0.557 / 0.453 と単調である** (16 → 24 → 32)。
k=2〜4 のどの幅で切っても順序は同じで、**3 点 × 3 幅の 9 通りすべてで
「スロットが少ないほど c が高い」**が成り立つ。

3 つ読める:

1. **スロットは base よりブロックのほうを大きく動かす。**16 → 32 で
   decode base は 57.1 → 51.2 ms/tok (**−10.3%**) しか下がらないのに、
   k=4 のブロックは 169 → 118 ms (**−30.2%**) 下がる。
   スロットを増やして得ているものの大半は **verify 幅の限界費用**の側にある。
   これは 33 §3 の「32 → 48 で t/s +14%」を、
   **どの経路が安くなったのかの側から**見た絵である (**導出**)。
2. **「奥ほど c が高い」は 32 スロットの性質であって、普遍則ではない**
   (**未確認**)。§0-1 と §2 が 32 スロットで見た単調増加
   (0.380 → 0.541) は 24 スロットにも出る (0.510 → 0.617) が、
   **16 スロットでは出ない** — 0.650 / 0.650 / 0.673 / 0.640 / 0.603 と
   ほぼ平坦で、k=4 を頂点に**むしろ下がる**。各幅 1 回測りなので
   6% 程度の凸凹は分散と区別できない (§7-2)。言えるのは
   **「16 スロットでは c の深さ依存が見えなくなる」**までで、
   §0-1 の本文 (32 スロットの話) はそのままでよい。
3. **位置あたりの費用 (`step/base ÷ k`) の底が動く。**
   32 スロットは k=4 で 0.590 の底を打って戻る (§2c)。24 スロットは
   k=4 の 0.667 でほぼ平ら。**16 スロットは k=8 の 0.652 まで下がり続けて
   底を打たない。**スロットが少ないほど「1 位置あたりを安くする」という
   意味では広い幅が効き続ける — にもかかわらず**運用点で広い幅が勝たない**
   のは、位置あたりの費用ではなく `step/base` 対 `tok/round` の勝負だからである
   (§8d)。

### 8b. 機構 — union は 3 つのスロット数で同じだけ効いている。動くのはミスだけ (**実測** + **導出**)

§2b と同じ換算 (144 位置で割る、要求件数 = `miss / (1 − hit)`) を 3 本のログに当てる。

| フェーズ | 要求/位置 (**導出**) | 16 スロット hit / ミス/位置 | 24 スロット | 32 スロット |
| --- | ---: | ---: | ---: | ---: |
| decode | **240** | 55.9% / **105.8** | 65.8% / **82.1** | 73.5% / **63.6** |
| k=4 | **152** | 40.4% / **90.1** | 55.9% / **66.7** | 67.6% / **49.1** |
| k=8 | **114** | 30.6% / **79.2** | 47.3% / **60.1** | 60.2% / **45.4** |

ミス総数 (decode → k=8) は **16 スロット 15234 → 11406、24 スロット
11819 → 8657、32 スロット 9164 → 6535** である。

**(a) 復元した要求件数は 3 つのスロット数で同一である。**decode 240、k=4 152、
k=8 114 — 小数第 1 位まで揃う (実際の計算値は 239.9/240.0/240.1、
151.2/151.3/151.5、114.1/114.1/114.0)。当然といえば当然で、
**union の重複除去はリクエスト列の性質であってキャッシュの性質ではない**。
decode の 240 = 30 層 × topK 8 が 3 本とも出ることが、§2b と同じ検算になっている。

**(b) したがって §0-5 と何も矛盾しない。**§0-5 は
「union の再利用は効いている。頭打ちになるのはバイトの側ではなく費用の側である」と
書いた。**16 スロットで hit が 30.6% まで落ちるのは、union が効かなくなったからではない。**
union は 3 つのスロット数で**まったく同じだけ** (240 → 114、−52.5%) 効いている。
スロット数が決めているのは**畳んだ後の要求 1 件が当たるかどうか**のほうで、
その結果が「位置あたりのミス」である:

| decode → k=8 のミス/位置 | 16 | 24 | 32 |
| --- | ---: | ---: | ---: |
| decode | 105.8 | 82.1 | 63.6 |
| k=8 | 79.2 | 60.1 | 45.4 |
| union による減り | **−25.1%** | **−26.8%** | **−28.7%** |

1.75 倍運んでおり、**8a の c の比 (0.603 / 0.541 = 1.11) より
ずっと大きい**。バイトが 1.75 倍でも費用が 1.11 倍にしかならないのは、

(**導出**、本節は帯域を主張しない — `io=` 列は壁時計ではない、§7-4)。

### 8d. 帰結 — 最適 bs はスロット数の関数である (**実測**)

| slots | prose 最速 bs | image 最速 bs | bs=4 の取りこぼし (prose / image) |
| ---: | --- | --- | ---: |
| 16 | **2** (1.303)、bs=3 は 1.293 | **2** (1.355)、bs=3 は 1.325 | **+24.7% / +17.3%** |
| 32 (§4f) | **3** (1.339)、bs=2 は 1.278 | **2** (1.395)、bs=3 は 1.393 | +14.2% / +9.8% |

**どちらのタスクでも、スロットを減らすと最適 bs は下がるか同じで、上がることはない。**
image は 16 スロットで bs=2 が bs=3 を **2.2%** 上回り (熱ドリフト +0.07% より
十分大きい)、32 スロットでは 0.14% 差で**同値**だった。prose は 32 スロットで
bs=3 が bs=2 を **4.8%** 上回った (ドリフト −0.35%) のに、16 スロットでは
**0.8% 差で同値**に落ちる (§7-11 のとおり、この差はドリフトより小さい)。
**両タスクとも「bs=3 の優位が 16 スロットで消える」という同じ向きに動いている。**

機構は 8a と 8c で閉じている。速くなる条件は `tok/round > step(bs)/base` であり、
**`tok/round` はスロット数で動かない** (受理はモデルと温度とプロンプトで決まる、
§5a の外部傍証)。実測でも 16 スロットの tok/round は bs=2 で 1.613 / 1.684、
bs=3 で 2.043 / 2.123 で、**32 スロットの 1.613 / 1.684、2.043 / 2.123
(§4a の prose・image) と 3 桁一致する。**分子が固定で分母だけが c で膨らむので、
**c が上がるほど損益分岐は手前に来て、最適 bs は縮む。**

⇒ **c が下がるほど最適 bs は伸びる。**この向きを 48 スロットに当てると
**bs=3〜4 が最適になる可能性がある**が、**測っていない** (**未確認**、§8f)。
33 §3 が「48 → 64 でスロットの効きは頭打ち」と示している以上、
**3 点の外挿で 48 の c を出してはいけない** (§7-10)。

**bs の既定値についての含意** (**導出**)。§4f と §5c は
「32 スロット・temp 1.0 で bs=4 は 8〜14% 損しているが、採点温度が決まるまで
既定は動かせない」と書いた。本節はそこに 1 行足す —
**既定 bs を 1 つの定数にする限り、スロット数を変えたときに必ずどこかで損をする。**
16 スロットでの取りこぼしは **17〜25%** で、32 スロットの 8〜14% より大きい。
`(slots, temperature)` から bs を引く表にするか、既定を 2〜3 に寄せるかは
**§5c と同じく上に戻す判断**である。

### 11e. 帰結 — 製品判断に戻す

1. **ベンチマークは register を固定しないと、実装を比較したことにならない** (**実測**)。
   26 §2 は「**受理長**はタスクで 2 倍動く」と言った。本節はそこに
   **「**decode 速度**も register で 1.28 倍動く」**を足す (25.30 / 19.75 = 1.281)。
   **2 つの実装を別々の register で測った比較は、実装ではなく register を測っている。**
   34-M9 §1 の **L3「合成ベンチは production の形状ヒストグラムを先に測ってから」**の、
   **出力側の版**である。
   **そして採点基準 v1 (22 §4) は日本語散文キャプション 1 種類で凍結されている** —
   これは **4 つの register のうち最も速い側**、つまり**楽観側**である (**実測**)。
   §9f が「8 枚が揃えば決着する」と書いたが、
   **8 枚が全部同じ register なら、決着するのは「その register での順位」だけ**である。
2. **スロット数の選択は register 依存である** (**実測**)。
   33 §3 (32 / 48 / 64 のスイープ) と 28 §4-3 (動的スロット) の議論は、
   すべて**画像・日本語散文 1 種類**の上で立っている。
   コードでは同じスロット数で hit が 11.9〜18.5 pt 低いので、
   「48 で頭打ち」「64 は得るものが無い」という判定が
   **そのまま移るとは言えない** (**未確認** — コードで 48/64 は測っていない)。
   ⇒ **どの register で運用するかを決めてからでないと、スロット数の数字は立たない。**
3. **未確認: なぜ英語・箇条書きがエキスパートを散らすのか。**
   本節が測ったのは **hit と t/s という結果だけ**で、
   **ルーティングの分布そのものは 1 度も見ていない。**
   仮説は複数立つ (トークン語彙が違えばルータの入力分布が違う /
   markdown の記号トークンが専用のエキスパートを引く /
   英語トークンのほうが 1 トークンあたりの情報が少なく列が長くなる) が、
   **どれも測っていない。**
   `bench/mtp_router_xlayer.py` や expert トレースで
   **層ごとの top-K 分布を register 別に取れば直接答えが出る。**
   これは本書が残す**いちばん筋の良い次の 1 手**である。
4. **既定 bs の判断に対しては、本節は「急がなくてよい」と言っている** (**導出**)。
   §9f のとおり採点条件で bs=3 と bs=4 は引き分けで、
   §11c のとおり register を変えれば最適 bs はまた 4 になる。
   **register を固定していない今、既定 bs を動かす根拠は無い。**
   §5c と §10e が上に戻した問い (どの温度で採点するか) に、
   **「どの register で採点するか」が加わる。**

`--messages-file` だけ (`ja_prose` と `en_bullets` は同じ画像つき、

画像経路の有無が交絡していることに注意)。

### 12a. トレースの schema と検証 (**実測**)

**ここを最初に置くのは、§12 の残り全部がこの 3 本のファイルに乗っているからである。**
台帳が信用できる範囲は、この節で確かめた範囲を超えない。

ヘッダ (3 本とも同一):

```
# turbo-fieldfare expert trace v1
# experts=128 / layers=30 / slots=32 / topK=8 / policy=lfu
# prefill=chunked / prefillChunkTokens=2048
# model=mlx-community/gemma-4-26B-A4B-it-qat-q4_0-mlx-aligned
phase	step	layer	hits	misses	experts
```

**1 行 = 1 層 1 回のルーティング要求**である。`experts` はその要求が引いた
エキスパート番号の列で、`hits + misses` はその長さに等しい。行数の算術で確かめる:

| | `ja_prose` | `en_bullets` | `code` |
| --- | ---: | ---: | ---: |
| 全行 | 6,091 | 6,123 | 5,998 |
| うち decode 行 | **5,730** | **5,730** | **5,730** |
| うち prefill 行 | 361 | 393 | 268 |
| decode の異なり step 数 | **191** | 191 | 191 |
| decode の異なり layer 数 | **30** | 30 | 30 |
| step あたりの decode 行数 (min/max) | 30 / 30 | 30 / 30 | 30 / 30 |
| `hits+misses != 8` または `len(experts) != 8` の行 | **0** | **0** | **0** |

**5,730 = 191 × 30** で、しかも step ごとにきっかり 30 行 —
**欠けている (step, layer) の組は 1 つも無い**。要求されたエキスパートの総数は
**5,730 × 8 = 45,840** である (**自分で検算した**: `191*30 = 5730`、`5730*8 = 45840`)。
192 tok 生成に対して decode 位置が 191 なのは、
**最初の 1 トークンが prefill の最終位置から出るから**である。

decode の hits/misses の合計は **3 本とも footer と完全に一致する**:

| register | TSV 合計 hits/総数 | footer の `decode hit` | 一致 |
| --- | ---: | --- | :-: |
| `ja_prose` | 42,709 / 45,840 = **93.17%** | `hit=93.2% 42709/45840` | ✓ |
| `en_bullets` | 37,136 / 45,840 = **81.01%** | `hit=81.0% 37136/45840` | ✓ |
| `code` | 37,268 / 45,840 = **81.30%** | `hit=81.3% 37268/45840` | ✓ |

prefill は 3 本とも `hit=0.0%` で、TSV 側も hits が全行 0 である
(2,785 / 2,996 / 2,028 ミス。footer と一致)。**冷たいキャッシュから始まっている。**

**再生器の検証。**`bench/expert_sim.py` の `LayerCache` は
`PreadExpertStreamer.makeExpertCachePlan` の追い出し規則を写したものである
(`PreadExpertStreamer.swift:53`、`236-311`、`467-501`):
**層ごとに独立した 32 スロット**、追い出し順は
**空き → 使用回数の少ない順 → 最終使用の古い順** (`shouldEvictSlot:506-511`)、
**使用回数は減衰しない**。この再生器にトレースを流し込むと:

| register / スロット | 再生器の decode hits | 実機 footer の decode hits | 差 |
| --- | ---: | ---: | ---: |
| `ja_prose` / 32 | 42,709 | 42,709 (`36_trace/ja_prose.err`) | **0** |
| `ja_prose` / 24 | 41,331 | 41,331 (`36_register/ja_prose_s24_bs0.err`) | **0** |
| `ja_prose` / 16 | 38,815 | 38,815 (`36_register/ja_prose_s16_bs0.err`) | **0** |
| `en_bullets` / 32 | 37,136 | 37,136 | **0** |
| `code` / 32 | 37,268 | 37,268 | **0** |
| `code` / 24 | 34,597 | 34,597 (`36_register/code_s24_bs0.err`) | **0** |
| `code` / 16 | 30,334 | 30,334 (`36_register/code_s16_bs0.err`) | **0** |

**7 点すべてで hit 数が 1 件も違わない。**しかも 16 / 24 スロットの 4 点は
**別プロセスの別 run** (§11d の測定) であって、32 スロットのトレースを
再生しただけでその 4 本を当てている — **同じ register なら要求列は
スロット数によらず同一**で (temp 0 / seed 固定なので生成列が決まる)、
**再生器はその上で追い出しを正しく再現している**、ということである。

⇒ **以降の反実仮想 (スロット数・政策・Belady・層ごと再配分) は、
この再生器による導出である。**一致を確認した範囲は
**8〜32 スロット・LFU だけ**なので、40 スロット以上と LRU は
外挿であることを忘れないこと (§7-23)。

### 12b. 分布 — 実効エキスパート数が 32 スロットをまたぐ (**実測**)

decode 191 位置 × topK 8 なので、**どの層も要求は 1,528 件**である
(191 × 8 = 1,528、3 本とも一致)。その 1,528 件が 128 個のエキスパートに
どう散るかを見る。

**(1) 層あたりの異なりエキスパート数** (128 個中、30 層の平均と範囲):

| register | 平均 | 最小 | 最大 |
| --- | ---: | ---: | ---: |
| 日本語散文 | **54.9** | 23 | 103 |
| 英語箇条書き | **82.8** | 56 | 107 |
| コード | **88.8** | 71 | 115 |

**(2) 集中度** — 各層で最も多く引かれた上位 8 個 / 上位 32 個が
その層の 1,528 件に占める割合 (30 層平均):

| register | 上位 8 | 上位 32 | **実測 hit (32 スロット)** | 差 |
| --- | ---: | ---: | ---: | ---: |
| 日本語散文 | 66.4% | **94.8%** | 93.17% | **−1.59 pp** |
| 英語箇条書き | 45.9% | **83.1%** | 81.01% | **−2.07 pp** |
| コード | 45.8% | **82.4%** | 81.30% | **−1.14 pp** |

**これが本節でいちばん強い結果である。「各層の最頻 32 個を固定する」だけの
静的オラクルが、稼働中の 32 スロット LFU キャッシュの hit 率を
3 本とも 1.1〜2.1 pp 以内で言い当てている。**

**なぜそうなるか** (**導出**、コード読み)。LFU の使用回数
`expertUseCount` は**要求のたびに増えるだけで、減衰も窓もリセットも無い**
(`PreadExpertStreamer.swift:236-311`)。生成が進むほど「今までいちばん多く
引かれた 32 個」の使用回数が他を引き離すので、**キャッシュの中身は
その層の最頻 32 個に収束して、以後ほとんど動かなくなる**。
つまり **32 スロット LFU は、実質的に静的オラクルとして振る舞っている**。
実測がオラクルより 1〜2 pp 低いのは、収束するまでの立ち上がりぶんである
(§12d の「先頭を捨てると hit が上がる」がこれに対応する)。

**この収束は片刃である。**最頻 32 個が要求の 95% を覆う register (日本語散文) では
LFU は最良に近い。覆いが 83% しかない register では、**LFU は
「覆えない 17%」をキャッシュに載せる機会そのものを潰している** —
使用回数で負け続けるエキスパートは、何度来ても居座れない。
これが §12e の Belady 余地 (英語 +6.8 pp) の正体である。

**(3) エントロピーで見た実効エキスパート数** (層ごとに要求分布の
シャノンエントロピー `H` を取り `2^H`、30 層平均):

| register | 全 30 層 | 層 0-9 | 層 10-19 | 層 20-29 |
| --- | ---: | ---: | ---: | ---: |
| 日本語散文 | **23.5** | 31.0 | 25.2 | **14.1** |
| 英語箇条書き | **41.8** | 48.6 | 36.8 | 39.9 |
| コード | **43.8** | 50.7 | 35.3 | 45.4 |

**32 という数はこの 3 つの間に落ちている。**日本語散文は 23.5 で
**32 スロットの内側**、英語箇条書き (41.8) とコード (43.8) は
**外側**である。§11 が測った 12 pt の hit 差は、これで説明が付く。

**層の深さの効き方が register で違う。**日本語散文は奥ほど鋭くなる
(31.0 → 25.2 → **14.1**、最後の 10 層は実効 14 個で 32 スロットの半分以下) が、
**英語箇条書きとコードは奥で鋭くならない** (39.9 / 45.4)。
§12a の層別 hit でも同じ形が出る — 日本語散文は層 20-29 が 95〜99% なのに、
英語箇条書きは層 28/29 が 65% / 71%、コードは 69% / 63% まで落ちる。
**「奥の層は狭い」は register の性質であって、モデルの性質ではない。**

### 12c. 再利用距離 — 分布の上側がスロット数の壁を越える (**実測**)

(2) は「どれだけ散るか」を測った。次は「いつ戻ってくるか」である。
各層について、あるエキスパートが引かれたとき **前回その層で引かれてから
今回までに、その層で引かれた異なりエキスパート数**を数える
(LRU のスタック距離。**スロット数 S のキャッシュは、この距離が S 未満の
再利用だけを取れる**)。

| register | 初出 (この層で初めて) | 位置ギャップ 中央値 / p75 / p90 | スタック距離 中央値 / p75 / p90 | 距離 < 32 の割合 |
| --- | ---: | --- | --- | ---: |
| 日本語散文 | 1,648 | **1** / 2 / 9 | **0** / 8 / **21** | **91.6%** |
| 英語箇条書き | 2,485 | 2 / 5 / 18 | **8** / 20 / **41** | **80.0%** |
| コード | 2,664 | 2 / 6 / 17 | 8 / 20 / **42** | 79.3% |

(「距離 < 32 の割合」は 45,840 要求ぜんぶを分母に取り、**初出は距離 ∞ 扱い**にした
値である。これが **32 スロットの LRU が原理的に届く上限**にあたる。
再利用だけを分母に取ると 95.0 / 84.6 / 84.2% になる。)

**日本語散文のスタック距離は中央値 0 である。**半分以上の再利用が
「直前の位置で同じ層が同じエキスパートを引いている」もので、
その間に他のエキスパートが 1 つも挟まらない。
**対して英語箇条書きは p90 が 41** — 上位 1 割の再利用は
**32 スロットでは原理的に取れない**。
**壁を越えているのは分布の上側であって、平均ではない** (34 §1 の L2 と同じ形)。

窓 W 位置のあいだに各層が引く異なりエキスパート数 (ワーキングセット):

| register | W=2 | W=8 | W=16 | **W=32** | W=64 | W=191 (全体) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 日本語散文 | 10.7 | 19.5 | 26.6 | **34.5** | 42.7 | 54.9 |
| 英語箇条書き | 12.5 | 27.9 | 39.7 | **52.5** | 65.2 | 82.8 |
| コード | 12.5 | 27.7 | 40.2 | **54.3** | 69.4 | 88.8 |

**W=32 で日本語散文は 34.5、英語箇条書きは 52.5 — 32 スロットの 1.6 倍**である。

**(4) 連続位置の重なり** (topK 8 のうち、30 層 × 位置の平均):

| register | lag 1 | lag 2 | lag 4 | lag 8 | union k=4 | union k=8 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 日本語散文 | **5.28** | 4.93 | 4.68 | 4.44 | **14.43** | **19.55** |
| 英語箇条書き | 3.47 | 3.11 | 3.00 | 2.66 | 19.09 | 27.87 |
| コード | 3.48 | 3.38 | 2.81 | 2.69 | 18.71 | 27.73 |

**日本語散文は隣の位置と 8 個中 5.3 個を共有する。英語箇条書きは 3.5 個である。**
そして lag 8 まで行っても日本語は 4.44 で下げ止まる —
**この register には「この層はこの 4〜5 個」という定常の芯がある**。

**この表は §2b / §8b の union の話と同じ量である。**幅 k のブロックが
1 位置あたり何件のミスを出すかは union のサイズで決まり、
それが **k=8 で 19.55 対 27.87 と 1.43 倍違う**。
§11c が「コードは hit 最悪なのに投機の base 比が最良」と書いた理由の半分がここにある
— コードは union が大きいぶん base が I/O 律速で、
広いブロックの重複除去が効く余地が大きい。

### 12d. バーストではない — 仮説を立てて棄却した (**実測**)

**立てた仮説**: 英語箇条書きの hit が低いのは、markdown の行頭
(`\n`, `-`, `**`) のような**特定の位置でだけ**ルータが飛ぶからで、
ミスは少数のバースト位置に固まっているのではないか。
そうなら**先読みや行頭専用の扱い**という機構が効く。

**棄却である。**位置あたりのミス数 (最大 240 = 30 層 × 8) を見ると:

| register | 平均 | 標準偏差 | 最小 | 最大 | **最悪 10% の位置が占めるミスの割合** | 平均の 2 倍超の位置 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 日本語散文 | 16.39 | 13.44 | 4 | 154 | **26.3%** | **11 個** |
| 英語箇条書き | 45.57 | 19.21 | 13 | 170 | **18.5%** | **2 個** |
| コード | 44.88 | 21.76 | 6 | 137 | 19.9% | 5 個 |

**向きが仮説と逆である。**最悪 10% の位置にミスが集中しているのは
**日本語散文のほう** (26.3% 対 18.5%) で、平均の 2 倍を超える位置も
日本語 11 個に対し英語 2 個。**英語箇条書きのミスはむしろ均一に降っている。**
(191 位置に均等なら最悪 10% の share は 10% になる。日本語の 26.3% は
「たまに大きく外す」で、英語の 18.5% は「いつも外し続けている」である。)

**自己相関にも行頭の周期は出ない。**lag 1〜12 の自己相関は
日本語 +0.34 → +0.04、英語 +0.31 → +0.22、コード +0.37 → +0.08 と
**単調に減るだけで、特定の lag にピークが無い**。
markdown の行が 8〜15 トークン程度であることを考えると、
行頭が原因なら lag 8〜15 にピークが立つはずだが、立っていない。

**立ち上がり (cold start) でもない。**先頭から何位置か捨てて hit を測り直すと:

| 捨てる位置 | 日本語散文 | 英語箇条書き | 差 |
| ---: | ---: | ---: | ---: |
| 0 (全部) | 93.17% | 81.01% | **12.16 pp** |
| 8 | 93.75% | 81.55% | 12.20 pp |
| 32 | 93.78% | 82.43% | 11.35 pp |
| 96 (半分) | 94.14% | 83.89% | **10.25 pp** |

**先頭 96 位置 — 生成の半分 — を捨てても、12.16 pp の差は 10.25 pp にしか縮まない。**
縮んだ 1.91 pp が §12b で言った「静的オラクルへの収束の立ち上がりぶん」である。
**残り 10 pp は定常状態の性質**であって、暖機で消えるものではない。
(コードだけは逆に、位置 96 以降で hit が **80.38%** と**下がる** — 生成が進むほど
散る。コードの分布は日本語散文と違って、奥へ行っても英語箇条書きより落ち着かない。)

⇒ **機構で狙える「悪い位置」は存在しない。分布そのものが広い。**
34 §1 の L5 (機構の成功指標で壁時計を語らない) と同じ理由で、
この棄却は記録に残す価値がある — **バースト前提の先読みを設計していたら、
的中率は出ても hit は動かなかった**はずである。

### 12e. 何が効くか — 4 つの反実仮想 (**導出**)

すべて §12a の再生器による**導出**で、**実機では 1 回も走らせていない** (§7-23)。

**(i) 政策 — LFU 対 LRU (32 スロット、decode hit)**:

| register | **LFU (現行)** | LRU | 差 |
| --- | ---: | ---: | ---: |
| 日本語散文 | **93.17%** | 91.86% | **−1.31 pp** |
| 英語箇条書き | **81.01%** | 79.77% | **−1.25 pp** |
| コード | **81.30%** | 79.23% | **−2.07 pp** |

**LFU が 3 本とも勝つ。`PreadExpertStreamer.cachePolicyDefault = .lfu` は
既に正しく、LRU にしてはいけない。**
理由は §12b で見たとおり — この作業負荷では最頻 32 個を握り続けるほうが強く、
LRU は §12c の p90 の長い再利用に振り回される。

**(ii) 上界 — Belady 最適 (層ごと、decode のみ、32 スロット)**:

| register | LFU 実測 | **Belady 最適** | **政策で埋められる余地** |
| --- | ---: | ---: | ---: |
| 日本語散文 | 93.17% | **94.57%** | **+1.40 pp** |
| 英語箇条書き | 81.01% | **87.80%** | **+6.79 pp** |
| コード | 81.30% | **87.37%** | **+6.07 pp** |

**日本語散文には政策の余地が無い** (+1.4 pp で、しかも Belady は未来を
知っている上界なので実装できない)。**余地があるのは英語箇条書きとコードのほう
(+6〜7 pp) である。**§12b の言い方に戻すと、LFU が静的オラクルに退化するのが
効かなくなる register でだけ、賢い政策に取り分がある。
ただし **Belady まで届く実装は存在しない**ので、これは
「+6.8 pp は原理的な天井」という読み方しかできない。

**(iii) 層ごとのスロット再配分** (総量 30 × 32 = 960 を固定し、
層ごとに 8〜96 の範囲で貪欲に再配分):

| register | 一様 32 | 再配分後 | 利得 |
| --- | ---: | ---: | ---: |
| 日本語散文 | 93.17% | 94.68% | **+1.51 pp** |
| 英語箇条書き | 81.01% | 81.64% | **+0.62 pp** |
| コード | 81.30% | 81.95% | **+0.65 pp** |

**効くのは日本語散文だけで、英語箇条書きには効かない。**
日本語散文の配分は極端に偏る (**層 1 に 80、層 23 に 14**) —
§12b の層別 hit で層 1 だけが 67% と落ち込んでいたのを埋めているだけである。
英語箇条書きは 30 層がどこも同じくらい広いので、動かす先が無い。
⇒ **層ごと再配分は「日本語散文の層 1 が外れ値」という 1 点の話であって、
register 問題の答えではない。**しかも現行の `PreadExpertStreamer` は
層ごとに同じスロット数を前提にしているので、試すには実装変更が要る。

**(iv) スロット数** (32 スロット LFU からの反実仮想):

| スロット | 日本語散文 | 英語箇条書き | コード | メモリ増 (**導出**) |
| ---: | ---: | ---: | ---: | ---: |
| 16 | 84.67% | 64.69% | 66.17% | −1.79 GB |
| 24 | 90.16% | 74.56% | 75.47% | −0.89 GB |
| **32 (現行)** | **93.17%** | **81.01%** | **81.30%** | — |
| 40 | 95.04% | **85.93%** | 85.50% | **+0.89 GB** |
| 48 | 96.22% | 89.66% | 88.81% | +1.79 GB |
| 60 | 97.38% | **93.53%** | 92.49% | **+3.12 GB** |
| 64 | 97.68% | 94.42% | 93.47% | +3.57 GB |
| 96 | 99.40% | 98.47% | 97.44% | +7.14 GB |

(メモリ増は **30 層 × スロット差 × `expertStride` 3.719 MB**。§11d-1 と同じ換算。)

2 つ読める:

1. **32 → 40 が折り返し点である。**+8 スロット (**+0.89 GB**) で
   **英語箇条書き +4.92 pp / コード +4.20 pp** に対し、
   **日本語散文は +1.87 pp** で、そこから先は逓減する (40 → 48 で +1.18 pp)。
   **スロットを積む価値は register で 2.6 倍違う。**
2. **英語箇条書きを日本語散文の 93.17% に並ばせるには約 60 スロット要る**
   (60 スロットで 93.53%、58 スロットでは 92.97% で届かない)。
   **+28 スロット = +3.12 GB** である。
   ⇒ **register の差をスロットで買うのは高い。**§11d が壁時計で
   「スロットを増やしても register の差は埋まらない」と言ったのと同じことを、
   hit の側から言っている。

**4 つを並べた結論**:

- **(i) LFU は既に正しい。LRU にしてはいけない。**
- **(ii) 政策の余地は日本語散文には無く (+1.4 pp)、英語箇条書きにある (+6.8 pp)** —
  ただし到達手段は無い (Belady は上界)。
- **(iii) 層ごと再配分は英語箇条書きには効かない (+0.62 pp)。**
  日本語散文の +1.51 pp も外れ値 1 層の話で、実装変更に見合わない。
- **(iv) スロットで解くなら 32 → 40 が折り返し点** (+0.89 GB で英語 +4.9 pp)。
  並ばせるところまで行くと +3.12 GB。

**残っている手はスロット数だけである。**そしてそれは
「どの register で運用するか」を決めないと引けない (§12f)。

### 12f. 帰結 — 32 スロットという運用点の性格

**本節の要点はここである。**

**この機体の 32 スロットは、日本語散文のワーキングセットがたまたま収まる数である。**
日本語散文の実効エキスパート数は層あたり **23.5**、W=32 の窓で見た
ワーキングセットは **34.5** — どちらも 32 の目と鼻の先にある。
一方、英語箇条書きは **41.8 / 52.5**、コードは **43.8 / 54.3** で、
**32 スロットから 1.6 倍あふれる**。

**そして採点基準 v1 (22 §4) は日本語散文キャプション 1 種類で凍結されている。**
§11e-1 は「日本語散文は 4 つの register のうち最も速い = 楽観側である」と書いた。
本節はそれを機構まで下ろす:

> **32 スロットは、楽観側の register に合わせて選ばれた数である。**

これは誰かの判断ミスではない — 33 §3 のスロットスイープも、
28 §4-3 の動的スロットの議論も、**すべて画像・日本語散文 1 種類の上で立っている**
(§11e-2)。その register では 32 で 93.2%、40 で 95.0%、48 で 96.2% と
すぐ逓減するので、「48 で頭打ち」「64 は得るものが無い」は**その register では正しい**。
**英語箇条書きでは 32 → 40 → 48 が +4.9 / +3.7 pp とまだ立っている。**
同じスイープを別の register で回せば、別の答えが出る。

**帰結として、以下は順序が入れ替わる**:

1. **33 §3 / 28 §4-3 の動的スロットの議論は、register を決めてからでないと立たない。**
   「48 で頭打ち」という判定は日本語散文の性質であって、実装の性質ではない。
   動的スロットの利得を見積もるなら、**どの register の分布の上で見積もるのか**を
   先に固定すること。
2. **34 P5 (mmap + `bytesNoCopy`) の優先度も同じ条件に掛かっている。**
   P5 の狙いは「48/64 のジレンマ (メモリ 1.8 GB の空振り、33 §3) を構造ごと消す」
   ことだった。**日本語散文ではそのジレンマは本物である** (48 → 64 で +1.46 pp)。
   **英語箇条書きでは、そもそも 48 も 64 もまだ空振りではない**
   (48 → 64 で +4.77 pp)。P5 が解こうとしている問題の大きさが register で違う。
   ⇒ **P5 の判定点 (GPU アクセス起点ページインのレイテンシ) を測る前に、
   どの register で運用するかを上に確認すること。**
3. **§11e-4 の「既定 bs を動かす根拠は無い」に、
   「既定スロット数を動かす根拠も無い」が加わる。**どちらも register 依存で、
   register が凍結されていない。

**未確認 — なぜ日本語散文がルータを狭くするのか。**
本節が答えたのは「**どう**散るか」であって、「**なぜ**散るか」ではない。
候補は 3 つあり、**どれも決まっていない**:

- **トークナイザの粒度。**日本語のほうが 1 トークンあたりの文字数が少なく、
  同じ内容に多くのトークンを使う。同じ語が繰り返し同じトークン列に割れるなら、
  ルータの入力分布は狭くなる。
- **言語専門エキスパート。**128 個のうち一部が言語別に特化していて、
  日本語では常に同じ部分集合が引かれている。
- **語彙的反復。**キャプションという課題自体が同じ語を使い回すので、
  register ではなく**タスク**の効果である。

**分けられない理由ははっきりしている: トレースにトークン ID の列が無い。**
`ExpertTraceWriter.append` が書くのは
`phase step layer hits misses experts` だけで
(`ExpertTelemetry.swift:186-198`)、**どのトークンがどのエキスパートを引いたかを
突き合わせられない**。**`append` に token id を 1 列足せば測れる** —
そうすれば「同じトークンは同じエキスパートを引くか」(ルータの決定性)、
「日本語のトークン集合はエキスパート空間のどこに写るか」、
「markdown の記号トークンが専用のエキスパートを引くか」が
**すべて同じ 1 本のトレースから出る**。これが §11e-3 が
「いちばん筋の良い次の 1 手」と呼んだものの、**その次の 1 手**である。

**もう 1 つ測っていないこと**: §11a の 2×2 のうち
`ja_bullets` と `en_prose` のトレースを取っていないので、
**言語と書式のどちらが分布を広げるのかを §12 は分けられていない** (§7-22)。
§11a は壁時計で「両方効き、交互作用 −3.9 pt」と分解したが、
**分布の側の同じ分解は、あと 2 本トレースを取るだけで出る。**

### 14a. 計器と分離の手続き (**実測**)

**計器が何を言っているか**を先に固定する

`GPUQueueOccupancy.swift` の doc comment):

| 列 | 意味 | 落とし穴 |
| --- | --- | --- |
| `call` | **そのチャンク呼び出しの壁時計**。全ステージ + `other` がこの中に落ちる | — |
| `wait.front` | 層の前半バッファで**ホストがブロックされた**時間 | **「GPU が遊んでいた」ではない。**front バッファは前層の MoE と shared expert の後ろに同じキューで並ぶので、この待ちの大半は**どのみち起きる GPU 仕事の裏**であり、**床であって無駄ではない** (doc comment に明記されている) |

4. **ステージ集合。**prompt 行だけが `wait.shared` と `wait.tile` を持つ

### 14c. Σ max(io, busy) の検定 — **34 §1-L1 の算術形は破れる** (**実測**)

ブロックごとに `max(io, busy)` を取って合計し、footer の `verify=` と比べる:

| モデル | `ja_prose` (実測 4.728 s) | `en_bullets` (6.242 s) | `code` (5.555 s) |
| --- | ---: | ---: | ---: |
| **Σ max(io, busy)** — 34 §1-L1 | 3.770 s (**−20.3%**) | 4.702 s (**−24.7%**) | 3.955 s (**−28.8%**) |
| Σ max(fetch, busy) | 3.677 s (−22.2%) | 4.198 s (−32.7%) | 3.578 s (−35.6%) |
| Σ (busy + io) — 完全に直列 | 5.356 s (+13.3%) | 7.650 s (+22.6%) | 6.794 s (+22.3%) |
| Σ span = Σ (busy + idle) | 4.686 s (−0.9%) | 6.207 s (−0.6%) | 5.522 s (−0.6%) |
| **Σ (busy + 0.66·io)** | **4.695 s (−0.7%)** | **6.168 s (−1.2%)** | **5.516 s (−0.7%)** |

**Σ max は 20〜29% 足りない。**ブロック単位でも同じで、
`call / max(io, busy)` の中央値は **1.228 / 1.429 / 1.439**、
**240 ブロックのうち比が 1.00 に近い (< 1.05) ものは 1 つも無い**
(最小でも `ja_prose` の p10 で 1.108)。

**なぜ足りないか。**`max` は「I/O が GPU の裏に**完全に**隠れる」を仮定している。
実測の隠れ率は **1/3 しかない**。しかも
**GPU 律速側のブロック (busy ≥ io) だけを取り出しても同じである**:

| | GPU 律速ブロック数 | その平均 `busy` | その平均 `io` | その平均 `idle` | **io のうち漏れた割合** |
| --- | ---: | ---: | ---: | ---: | ---: |
| `ja_prose` | 83 / 90 | 37.6 ms | 15.6 ms | 8.8 ms | **56.1%** |
| `en_bullets` | 30 / 77 | 41.1 ms | 29.7 ms | 15.3 ms | **51.4%** |
| `code` | 24 / 73 | 39.8 ms | 31.6 ms | 17.5 ms | **55.2%** |

**「GPU のほうが大きいブロック」でさえ、I/O の半分は壁時計に漏れている。**
`max` が正しいなら漏れは 0 のはずである。

**正しい形。**恒等式として `call ≈ span = busy + idle` (Σ で −0.6〜0.9%)。
そして **`idle` はブロックごとに `io` のほぼ線形関数**である (最小二乗、切片つき):

| register | 回帰 | 相関 r |
| --- | --- | ---: |
| `ja_prose` | `idle = −5.0 ms + 0.889·io` | **0.995** |
| `en_bullets` | `idle = −5.1 ms + 0.761·io` | **0.991** |
| `code` | `idle = −8.1 ms + 0.818·io` | **0.952** |

そして **Σ idle / Σ io は 3 本とも 0.657 / 0.670 / 0.662** —
**register が io を 2.2 倍動かしても、隠れる割合は動かない。**
だから `Σ (busy + 0.66·io)` が 3 本とも 1.2% 以内で当たる
(**Σ max より 30 倍良い**)。

**帰結 — 34 §1-L1 をどう書き換えるか** (**実測** + **導出**):

- **「壁時計は Σ max(io, gpu)」は下限であって壁時計ではない。**
  この運用点 (32 スロット / bs=3) では **20〜29% 下に外す**。
  35 §4 の `step(k) = base + Σc_i + d·k` のような**台帳の側は無傷**である
  (§3c で 8 枚とも 3 桁一致している)。壊れたのは
  **「ブロックの中を (io, busy) の max で読む」という 1 行だけ**である。
- **「片側だけの改善は出ない」は、この式の上では成り立たない。**
  実測の形は加法的で、**∂wall/∂io ≈ 0.66** (3 本とも)。
  GPU 側の係数も 1 に近い (`en_bullets` の多変量回帰で
  `call = −6 ms + 0.760·io + 1.028·busy`)。
  ⇒ **どちらの側を削っても壁時計に出る。ただし I/O 側は 2/3 の効率で出る。**
- **未確認 (重要)**: ∂wall/∂busy ≈ 1 は**因果ではない**。
  この 3 本では `busy` のばらつきが p10-p90 で 8〜12% しかなく、
  しかも `busy` は `io` と正の相関を持つ (大きいブロックは両方大きい) ので、
  回帰係数は交絡している。**`busy` を実際に動かす A/B (34 の P2) でしか確かめられない。**
- **30 / 32 / 33 の 3 つの負けを本節は覆さない。**あれらは別の条件
  (33 は 48 スロット、32 は合成ベンチ、30 は先読み) で起きており、
  本節は 32 スロット / bs=3 / temp 0 の 3 本しか見ていない。
  ⇒ **L1 を「レバーを引く前に、そのレバーが削る資源がどのブロックで束縛かを
  台帳で確認する」という運用規則として使うのは今も正しい。
  破れたのは Σ max という算術だけである。**そしてその確認は、
  本節が示したとおり **register ごとにやり直さないといけない** (§14d)。

### 14d. register が束縛を入れ替える — どちらの果実を摘むかは register が決める (**実測**)

**ブロック単位の判定** (中央値だけでなく分布で):

| | `ja_prose` | `en_bullets` | `code` |
| --- | ---: | ---: | ---: |
| **`busy` > `io` のブロック** | **83 / 90 = 92.2%** | 30 / 77 = **39.0%** | 24 / 73 = **32.9%** |
| `busy` > `fetch` のブロック | 83 / 90 = 92.2% | 37 / 77 = 48.1% | 29 / 73 = 39.7% |
| `busy`/`span` の中央値 | **0.815** | 0.597 | 0.577 |
| `idle`/`span` の p10 / 中央値 / p90 | 0.093 / **0.187** / 0.335 | 0.214 / **0.403** / 0.588 | 0.278 / **0.420** / 0.556 |
| Σ `idle` / Σ `call` | **27.1%** | **46.9%** | **44.9%** |
| Σ `busy` / Σ `call` | **72.4%** | 52.8% | 54.8% |
| Σ `busy` | 3.412 s | 3.291 s | 3.036 s |
| Σ `io` | **1.944 s** | **4.359 s** | **3.758 s** |
| 1 ラウンドあたり `busy` / `io` / `call` | 37.9 / 21.6 / **52.4** ms | 42.7 / 56.6 / **80.9** ms | 41.6 / 51.5 / **75.9** ms |

**言える。**中央値でも分布でも同じ向きが出る:

- **`ja_prose` (最速、35.9 t/s) は GPU 律速である。**ブロックの **92.2%** で
  `busy` が `io` を上回り、verify の壁時計の **72.4%** が GPU busy、
  `idle` は 27.1% しか無い。
- **`en_bullets` / `code` は I/O 露出律速である。**`busy` が勝つブロックは
  **39.0% / 32.9%** しかなく、`idle` が verify の **46.9% / 44.9%** を占める。

そして **Σ `busy` は 3.41 / 3.29 / 3.04 s と ±6% しか動かないのに、
Σ `io` は 1.94 → 4.36 s と 2.2 倍動く**。
**verify 総額の差 (4.73 / 6.24 / 5.56 s) は、ほぼ全部 I/O 側の差である。**

> **帰結。**有利な register では、verify の壁時計の **72% が GPU busy** である。
> そこに残っているのは **カーネル側 = 34 の果実 A / P2** (down 分割、行あたり費用) である。
> 苦手な register では `idle` が **45〜47%** を占める。
> そこに残っているのは **I/O 側 = 果実 C / P5** (mmap + `bytesNoCopy`、スロット) である。
> **「どちらの果実を摘むか」は実装の性質ではなく、register が決める。**

これは §12f が hit 率の側から言ったこと
(「32 スロットは楽観側の register に合わせて選ばれた数である」) を、
**壁時計の側から言い直したもの**である。
そして **34 §4 が P2 と P5 に付けた優先順位は、
どの register で運用するかを決めない限り決まらない** — §12f-2 が
「P5 の判定点を測る前に、どの register で運用するかを上に確認すること」と書いたのと同じ結論に、
別の計器から独立に着いた。

**注意 2 つ** (どちらも「苦手 register」を 1 本の軸で語らないため):

1. **`en_bullets` と `code` は verify ブロックの中身ではほとんど同じ**
   (`idle`/`call` が 46.9% 対 44.9%、`busy`/`span` の中央値が 0.597 対 0.577) のに、
   **t/s は 28.26 対 31.75 と 12% 違う**。差はブロックの中ではなく
   **受理の側** (tok/round 2.494 対 2.630) と**ブロック数** (77 対 73) にある。
   §11c の「キャッシュの最悪ケースが投機の最良ケース」がここでも効いている。
2. **`ja_prose` はブロックあたりの `experts` 中央値が 372 (他は 480 / 485) で、
   `busy` も 38 ms 対 41〜42 ms と低い。**
   ⇒ **union が小さい register は I/O だけでなく GPU も安い。**
   §12c の重なりの表 (lag 1 で 5.28 対 3.47) と同じ量を、ブロックの側から見ている。
   つまり register の効果は「I/O だけ」ではなく、**I/O に 2.2 倍・GPU に 1.1 倍**である。

近い量が 2 つあり、**どちらとも桁は合うが一致はしない**:

- **(a) §11a / §11b の bs=0 対比較から出る限界費用。**`ja_prose` と `en_bullets` の

  (この 2 つの比 2.394 / 2.24 = **106.9%** が §11 冒頭の「減速の 106%」の正体である)。
  ⇒ **本節の 3 本まとめの d`call`/d`miss` = 451 µs は、(a) の 402 µs と 12% 差**で合う。
- **(b) `expertStride` 3,719,168 B を 9.14 GB/s (= 8.51 GiB/s) で読んだときの時間**が
  ちょうど 407 µs である。⇒ **verify の実効帯域はそこに届いていない**
  (6.45 / 7.29 / 8.24 GiB/s)。近いのは `code` だけで、
  `ja_prose` は 537 µs/件 = **6.45 GiB/s** と 32% 遅い。
  ミスの少ないブロックほど 1 件あたりが高い、という向きである
  (行ごとの `GB/s` 列でも、末尾の軽いブロックが 9〜10 GiB/s、
  冒頭の重いブロックが 3〜5 GiB/s で、**同じ向き**)。

**そして register ごとの傾きは 302〜847 µs と 2.8 倍ばらついている。**
⇒ **「ミス 1 件あたり N µs」というスカラー 1 個は、ブロック粒度では成り立たない。**
34 §1 の **L2「平均で割った導出は分布に負ける」がここでもそのまま出る** —
まとめの 451 µs で 1 本だけ予測すると、`code` を 2.8 倍外す。

**未確認**: `code` の傾きだけ 232 µs と低い理由は決めていない。
`code` は `miss` 100–200 に点が集中していて (73 個中 46 個)、
その帯では `idle` が 35.9 → 37.3 ms と 1.4 ms しか動かない — 飽和側で傾きを取っている
可能性があるが、確かめていない。

### 14f. 本節の未確認

1. **各 register 1 run ずつ**である。分散を取っていない (§7-17 と同じ穴)。
   ただし `code` については profile 無しの run と footer が一致しており (§14a)、
   **生成列は temp 0 で決定的**なので、動く余地があるのは時間の列だけである。
2. **bs=3 だけ**である。幅を広げると union が広がって
   `busy` と `io` の比は動くはずだが (§2b / §8b)、bs=4/6 では測っていない。
   **§14d の「果実 A か C か」の判定は bs=3 の判定である。**
3. **`wait.front` は床と無駄を分けない。**本節は無駄を `gpuq idle` で数えたが、
   **その `idle` がどのステージで起きたかは分からない** —
   `PrefillHostProfile` と `GPUQueueOccupancy` は同じ `call` を別の軸で切っており、
   突き合わせる列が無い。「`wait.front` のうち何 ms が `idle` だったか」を出すには
   計器を足す必要がある (**未実装**)。
4. **分離が正しいことの根拠は §14a の 5 つの手がかりと 5 本の検算**である。
   手がかりのうち 4 つ (`ahead` / `experts` / `buffers` / ステージ集合) は
   **行の位置と独立**なので、順序を仮定していない。
   ただし **「1 回の verify ラウンドがちょうど 1 回のチャンク呼び出しを出す」ことは
   コードで確かめていない** — `rounds` と行数が 3 本とも一致し、
   Σ`call` が footer の `verify=` に 0.3% で合ったことからの**導出**である。
5. **`io` は壁時計ではない** (§7-4)。preads が並行なら合計は壁時計を超え得る。
   **Σ`idle`/Σ`io` = 0.66 という比はこの定義の上での比**であって、
   「I/O の 66% が露出している」と読むのは `io` が直列であることを仮定している。
6. **§14c の ∂wall/∂busy ≈ 1 は因果ではない** (§14c 末尾に書いたとおり)。
   本節が実測として言えるのは **Σ max が 20〜29% 足りない**ことと、
   **`idle` が `io` のほぼ線形関数である**ことまでである。
7. **`code` は画像経路を通っていない** (§7-20)。
   `ja_prose` / `en_bullets` との比較には prefill の形状差が交絡している。
   ただし本節が使っているのは **decode の verify ブロックだけ**で、
   プロンプト prefill の 1 行は分離して捨てている。

## 15. 果実 B (先読み) を苦手な register で測り直す — 追い出しで死んでいた (**実測**)

§14 が「expert I/O の 3 分の 2 は隠れていない」「苦手な register では idle が
Σcall の 45〜47%」を示したので、**30-M8-B-PREFETCH で負けた先読みを、
条件を変えて測り直す**根拠ができた。30 の敗因は「I/O 側に足したが GPU 側が
空いていない」と読まれていたが、苦手な register では GPU は実際に空いている。

条件は全部 **32 スロット / temp 0 / thinking off / seed 1234 / 192 tok / bs=3**、
`TF_MTP_EXPERT_PREFETCH=1` (既定 N=1、d=1)。生ログ `bench/mtp36/36_pf_*.err`。

### 15a. 3 つの register で全敗する (**実測**)

| register | off | on | 差 | decode hit off → on |
| --- | ---: | ---: | ---: | --- |
| 日本語散文 (画像) | 36.052 t/s | 34.889 | **−3.2%** | 89.4% → **86.5%** |
| 英語箇条書き (画像) | 28.015 | 27.232 | **−2.8%** | 75.5% → **74.3%** |
| コード (テキスト) | 32.672 | 31.060 | **−4.9%** | 74.5% → **73.7%** |

**idle が 45% あっても負ける。**しかも**先読みを入れると hit 率が下がる**。

### 15b. 予測費用と追い出しを分ける (**実測**)

`TF_MTP_EXPERT_PREFETCH_N=0` は「予測はするが 1 本も投げない」設定である
(`ExpertPrefetch.swift:22-24`)。コード register で N を振ると:

| 設定 | t/s | off 比 | decode hit |
| --- | ---: | ---: | ---: |
| off | 32.672 | — | 74.5% |
| **N=0 (予測のみ)** | 31.842 | **−2.5%** | **74.5%** (不変) |
| N=1 (既定) | 31.060 | −4.9% | 73.7% |
| N=2 | 30.321 | −7.2% | 72.5% |

**分解できた** (**導出**): 予測そのもの (層 L+d の router を GPU でもう 1 本回す)
が **−2.5%** で、hit は 1 ポイントも動かない。**投げた先読みは 1 本増えるごとに
hit を下げ** (74.5 → 73.7 → 72.5)、そのぶん t/s も落ちる。
30 §3 が対照 (N=0) で単離した固定費 −1.0〜1.2% と同じ量がここでは −2.5% で、
**残りは追い出しである**。

### 15c. 帰結 — 先読みは「空きスロット」を前提にしている

`ExpertPrefetch.swift:20-21` のコメントは既定 N=1 の理由を
「32 スロットの追い出し合戦のリスクが最小」と書いている。**今夜の実測はその
リスクが現実であることを示した** — 先読みは**同じ 32 スロットを本体と奪い合う**。
§12e の反実仮想 (32 スロットの Belady 最適は苦手な register で +6.8pp) が
言っていた「政策の余地」は、**先読みという形では取れない**。取るなら
(a) スロットを増やす、(b) 先読み専用の小さな控えを別に持って LFU の常駐を
追い出さない、のどちらかである (**未確認**、どちらも未実装)。

⇒ **34 の果実 B は、32 スロットでは register を変えても復活しない。**
30 の結論は正しかったが、理由は「GPU が空いていない」ではなく
**「キャッシュに空きがない」**だった。
