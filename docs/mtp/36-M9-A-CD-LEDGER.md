## 0. 結論 — 11 つ

1. **32 スロットの c は 0.38〜0.54 base/位置である** (§2、**実測**)。
   幅 k のブロック 1 回は base の **0.99 / 1.38 / 1.83 / 2.36 / 3.59 / 4.79 倍**
   (k = 1/2/3/4/6/8)。平均 c = (step/base − 1)/(k−1) は

2. **35 §6(b) の導出には 2 つの読み違えがある** (§3、**実測**、コード読み)。
   (i) footer の `accept` は**受理長ではなく「ラウンドあたり受理ドラフト本数」**
   である (`SpeculativeCompletion.swift:66-70` / `Run.swift:312-314`)。受理長
   (tok/round) はこれに **+1**。35 は 1.885 を分子に置いたが、正しくは 2.885。
   (ii) 27 §2(b) の「24.7 → 28.9 t/s」は **M7 の 3 改修の before/after** であって
   off/on ではない。**両方とも MTP on** である。
   ⇒ **0.204 という数字は使えない。48 スロットの c+d は本書でも未測定。**
3. **本番 footer から 32 スロットの (c, d) 台帳が今日すぐ取れた** (§3、**実測**)。
   `bench/logs/mtp_goal_ab_slots32.tsv` は **27 §2(c) の生データそのもの**で、
   `rounds / accept / draft / verify / decode` が全行に入っている。8 枚の画像で
   **step(4)/base = 1.735〜1.935 (c = 0.245〜0.312)、d = 3.10〜3.31 ms/本

   (§3c)。**35 §4 の `step(k) = base + Σc_i + d·k` は turbo でもそのまま成り立つ。**
4. **turbo の bs=4 は 32 スロットで構造的に負けてはいない** (§3c、**導出**)。
   損益分岐 (d 抜きの下限) は bs=4 で 2.36 tok/round、実測 tok/round は
   **2.849〜2.949**。llama.cpp と同じ量 (総ラウンド費用を位置数で割る) で揃えると

   のであって 3.3 倍ではない。**35 §6(d) の「bs=2 だけが勝つ」は参照実装の性質で、
   turbo にそのまま移るとは言えない。**それでも bs=2 を行列に入れる理由は残る (§4)。
5. **ブロックが広いほどキャッシュ hit 率は落ちるが、位置あたりのミスは落ち続ける**
   (§2b、**実測**)。hit は 73.5% → 67.6% → 60.2% (decode/k=4/k=8) と落ちるが、
   これは union の重複除去で**要求そのものが 240 → 114 件/位置に減る**からで、
   ミスは **63.6 → 45.4 件/位置 (−29%)** と単調に減っている。
   **union の再利用は効いている。頭打ちになるのはバイトの側ではなく費用の側である。**
   33 §3〜§4 の「48 スロットでは I/O はもう床ではない」を verify 幅の側から
   見た同じ絵である (**導出**)。
6. **2 つの計器が 32 スロットの c で 1.7 倍食い違う** (§3d、**未確認**)。

   対照実験は測定中で、本書は結論を出さない。

## 1. 測り方 (**実測**)

計器は `Sources/TurboFieldfareKernelCheck/VerifyBlockCheck.swift` の
`costProbe` (`--verify-cost-only`、`:651-779`)。設計はこうである:

- **同じトークン列・同じ位置**を、1 トークンずつの `produce` と 幅 k の
  `verifyBlock` の両方で歩く。列は最初の decode パスが記録した greedy 列で、
  どの幅も**同じ 144 位置**を歩く (`blocks = total / k`、`:744`)。
  幅ごとにブロック数を固定すると、広い幅ほど深い KV で測ることになるので、
  そうしていない (`:692-696` のコメント)。
- **decode 基準は幅ごとに測り直す** (`:729`、`:760-761`)。この機械は 1 run の
  中でドリフトするので、各幅は**前後 2 本の decode 基準の平均**で割られる。
- warm cache (既定)。各フェーズの先頭 2 ブロックぶんは計時から捨てる (`:745`)。
- 144 位置 = (16 timed + 2 warmup) × 8 (`CostProbePlan`、`:610-620`)。

コマンド:

```
TF_EXPERT_CACHE_SLOTS=32 TF_VERIFY_COST_WIDTHS=1,2,3,4,6,8 \
  .build/release/TurboFieldfareKernelCheck --verify-block scratch/gemma4-qat.gturbo \
  --verify-cost-only --verify-block-size 4 \
  --verify-image sample_imgs/IMG_2113.JPG --verify-thinking
```

生ログ: `bench/logs/36-cost-32slots-image.log` (exit 0)。
プロンプトは **308 tok (画像 1 枚 / 266 soft)、thinking on**。

**暖機の扱い** (**実測**)。decode 基準の系列は時系列で
**54.3 → 52.6 → 50.9 → 50.2 → 50.0 → 50.2 → 50.6 ms/tok**。
最大/最小 = **1.086 (8.6%)** で、先頭が最も高く単調に下がるので**暖機**である。
各幅は前後の平均で割られているので、この単調な下りは幅ごとの比には
ほとんど乗らない (計器の設計どおり) — ただし 8.6% の幅があること自体は
§6 の限界に残す。

**限界 2 つ**を先に置く。(a) 各幅 1 回測りで分散を取っていない。
(b) 各幅の `io=` は**フェッチ呼び出しの所要時間の総和**であって壁時計ではない
(`ModelExpertIO.swift:211-249` の `startRoutedExpertFetch` はグローバルキューに
投げるので、同じ層のタイル同士が重なりうる)。**この列から実効帯域を読んではいけない。**

## 2. c 曲線 (**実測**)

### 2a. 費用

`base` は同じ log の `decode=51.2 ms/tok`。`step/base` は計器が前後 2 本の
decode 基準の平均で割った値をそのまま載せた。

| k | ms/block | step/base | 隣接差 (base/位置) | 平均 c = (step/base − 1)/(k−1) | 前後の decode 基準 (ms/tok) |
| ---: | ---: | ---: | ---: | ---: | --- |
| decode | 51.2 /tok | 1.000 | — | — | — |
| 1 | 53 | **0.99** | — | — | 54.3 / 52.6 |
| 2 | 71 | **1.38** | +0.39 | **0.380** | 52.6 / 50.9 |
| 3 | 93 | **1.83** | +0.45 | **0.415** | 50.9 / 50.2 |
| 4 | 118 | **2.36** | +0.53 | **0.453** | 50.2 / 50.0 |
| 6 | 180 | **3.59** | +0.615/本 | **0.518** | 50.0 / 50.2 |
| 8 | 242 | **4.79** | +0.60/本 | **0.541** | 50.2 / 50.6 |

3 つ読める:

1. **k=1 のブロックは decode と同値である (0.99)。**ブロック経路そのものには
   固定費が乗っていない — 費用は全部**位置に比例する側**にある。
   `costProbe` のコメント (`:606-609`) が「k=1 と k=4 で同じ費用なら call を
   払っている、k で伸びるならトークンを払っている」と書いた二択は、
   **トークン側**に出た。
2. **c は平坦ではなく、奥ほど高い** (0.39 → 0.45 → 0.53 → 0.615)。
   llama.cpp も同じ形だった (35 §4: 0.27 → 0.53 → 0.69)。
3. **6 本目以降で伸びが止まる** (0.615 → 0.60)。ここだけ単調でない。
   1 回測りなので**未確認**として扱う。

### 2b. なぜ伸びるか — hit 率とミスの分解 (**実測** + **導出**)

log の I/O 行をそのまま置き、位置あたりに直す。144 位置で割った
(`ExpertIODelta.describe`、`:642-648`。`miss = experts − hits` なので
要求件数 = `miss / (1 − hit)` が復元できる)。

| フェーズ | hit | miss | ミス/位置 | 要求/位置 (**導出**) | バイト/位置 (**導出**) | io ms/pos |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| decode | 73.5% | 9164 | 63.6 | **240** | 237 MB | 30.65 |
| k=1 | 77.1% | 7899 | 54.9 | **240** | 204 MB | 26.19 |
| k=2 | 73.3% | 7456 | 51.8 | **194** | 193 MB | 22.10 |
| k=3 | 70.8% | 7253 | 50.4 | **172** | 187 MB | 23.17 |
| k=4 | 67.6% | 7068 | 49.1 | **152** | 183 MB | 27.52 |
| k=6 | 64.1% | 6824 | 47.4 | **132** | 176 MB | 32.84 |
| k=8 | 60.2% | 6535 | 45.4 | **114** | 169 MB | 32.32 |

(バイトは `expertStride` 3,719,168 B ×ミス数、33 §2 と同じ換算。
decode と k=1 の要求 240 件/位置は **30 層 × topK 8 = 240** と一致する —
この復元が正しいことの検算になっている。)

**(a) union の重複除去は効いている。**幅 8 のブロックは 1 位置あたり
240 件ではなく **114 件**しか問い合わせない (8 トークンぶんの 1920 件が
912 件に畳まれている)。バイトも **237 → 169 MB/位置 (−29%)** と単調に減る。

**(b) hit 率が落ちるのは、その重複除去の裏返しである。**分母が
「畳まれた後の distinct な要求」になるので、1 件あたりの当たりやすさは下がる。
**hit 率の低下だけを見て「union の再利用が効かない」とは言えない。**

**(c) 効かないのは費用の側である。**バイトは −29% しか減らないのに、
位置あたりの費用は `step/base / k` で見ると
1.00 → 0.69 → 0.61 → 0.59 → 0.60 → 0.60 と **k=4 で底を打って戻る**。
バイトの節約は k=2 でほぼ取り切っていて、そこから先に払う c が勝つ。
これは 33 §3〜§4 が 48 スロットで見た形 (「io を −17% 削っても壁時計が動かない、
床は GPU 側にある」) と**同じ絵を verify 幅の側から見たもの**である (**導出**)。

## 3. 35 §6(b) との突き合わせ

### 3a. 35 が何をどう導いたか

35 §6(b) はこう書いている:

> 27 §2 の実測 (48 スロット、off 24.7 → on 28.9 t/s、受理長 1.885) を §4 の式に
> 入れると `step/base = 1.885/1.170 = 1.611`、bs=4 (ドラフト 3 本) なので
> **c + d ≈ 0.204 base/位置**。

ここに 2 つの読み違えがある (**実測**、コードと元表の突き合わせ)。

**(i) 分子が受理長ではない。**footer の `accept` は
`meanAcceptedLength = accepted / rounds` で、コメントが明記するとおり
**"Mean accepted draft length per round"** = **ラウンドあたり受理ドラフト本数**
である (`Sources/TurboFieldfare/Runtime/Generation/SpeculativeCompletion.swift:66-70`)。
1 ラウンドが産む token は **受理ドラフト + bonus 1 本**なので、
式の分子に置くべき「受理長」は **accept + 1**。
`Sources/TurboFieldfareCLI/Run.swift:312-314` は現に `accept=` と
`tok/round=` を**別々に**印字しており、27 §2 自身の引用
`rounds=74 accept=1.689/3 tok/round=2.703` がその裏取りである。
⇒ 1.885 ではなく **2.885** を置かねばならない。

**(ii) 分母の 1.170 が off/on 比ではない。**27 §2(b) の表の 2 列は
`before` / `after` で、**M7 の 3 改修 (LAYER_PLAN / RESIDENT_FIRST / ROUTER_FOLD)
の A/B** である (27 §1 のコマンドと env を見れば分かる)。
**24.67 も 28.90 も MTP on 側の数字**であって、投機の on/off ではない。
⇒ この比を `step/base` の式に入れることはできない。

**(iii) 積。**(i) だけを直しても `2.885/1.170 = 2.466` → c+d = **0.489**、
つまり 35 の 0.204 の 2.4 倍になる。(ii) を直すと元の 2 数からは何も出ない。
**0.204 という数は、どの直し方でも復元されない。**48 スロットの c+d は
本書でも**未測定**である。

### 3b. 32 スロットの本番台帳 (**実測**)

`bench/logs/mtp_goal_ab_slots32.tsv` は **27 §2(c) の生データそのもの**である
(`ratio` 列 1.2351 / 1.4006 / 1.3871 / 1.4208 / 1.3305 / 1.2824 / 1.4154 / 1.4608 が
27 §2(c) の表と 1 桁まで一致する)。`bench/mtp_goal_ab.py` の条件は
**32 スロット / bs=4 / temp 0 / thinking on / 画像 280 tok / max-context 4096**。
footer の `rounds / accept / draft / verify / decode` がそのまま列にあるので、
**35 §4 の分解が今日すぐできる**:

- `base` = off 側の decode 秒 / 産出トークン
- `step(4)` = `verify` 秒 / `rounds`
- `d` = `draft` 秒 / (`rounds` × 3)
- ラウンド外 = (`decode` − `draft` − `verify`) 秒 / `rounds`
- `tok/round` = on 側の産出トークン / `rounds` (= `accept` + 1)

| 画像 | base ms/tok | tok/round | step(4) ms | step/base | c 平均 | d ms/本 | d /base | ラウンド外 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |

**一部の点で当てた c と d で、測っていない点を予言する**しかない。

prose bs=6 は「1.104 倍で勝つ」と予言して**実測は 0.980 で負けた** —

**台帳は「測った範囲の内挿には使えるが、外挿には使えない」**というのが正しい強さである。

破れの向きは §2 と同じ (**奥ほど c が高い**)。隣接差で見ると:

| task | c(2→3) | c(3→4) | c(4→6) | c(6→8) |
| --- | ---: | ---: | ---: | ---: |
| prose | 0.176 | 0.124 | **0.287** | 0.177 |
| math | 0.121 | 0.186 | **0.320** | 0.174 |
| image | 0.228 | 0.090 | **0.257** | 0.189 |

3 タスクとも **4→6 で跳ねる**。1 回測りなので位置 5 と 6 のどちらで跳ねたかは
分けられない (**未確認**) が、**3 タスクで同じ場所に出る**ので偶然ではなさそうである。

### 4e. c の 3 つ目の値 — 計器の食い違いは §3d より大きい (**実測**)

同じ 32 スロット bs=4 の平均 c が、これで 3 通りになった:

| **§4a 本番スイープ** | 3 タスク / **temp 1.0** / thinking off / 192 tok | **1.383〜1.560** | **0.128〜0.187** |

**§2 の c 曲線で今夜の運用点を予言すると、3 タスク × 5 幅の 15 点すべてで負ける
と出る。**実際には bs=2/3/4 は 12 点中 12 点で勝っている:

| | prose 予測/実測 | math | image |
| --- | --- | --- | --- |
| bs=2 | 1.061 / **1.278** | 1.132 / **1.237** | 1.105 / **1.395** |
| bs=3 | 0.993 / **1.339** | 0.954 / **1.231** | 1.029 / **1.393** |

決まっていない」と書いた問いに、**運用点の側から答えが出た** —
costProbe (0.453) も §3b (0.264) も高すぎて、**今夜の bs=4 の勝ちを説明できない**。

**base 側の交絡を疑って引き算しても閉じない** (**導出**)。temp 1.0 では base
(bs=0) の 1 トークンも 4b の 1.277 ms を払っているので、`step/base` は分母だけが
膨らんで小さく出る。base からこれを引いた「純 decode」で割り直すと
c は prose 0.156 / math 0.202 / image 0.143 (bs=4) — **0.264 にも 0.453 にも届かない**。
残る候補は §3d の表と同じ (thinking on/off、生成長 192 対 1000 前後、
画像の有無、キャッシュ状態) で、**どれが効いているかは相変わらず測っていない**。

### 4f. 最適 bs は 2〜3 で、**既定の bs=4 は 3 タスクとも最適でない** (**実測**)

| task | 最適 bs | その t/s | bs=4 の t/s | **伸びしろ** |
| --- | ---: | ---: | ---: | ---: |
| prose | **3** | 34.014 (1.339) | 29.776 (1.172) | **+14.2%** |
| math | **2** | 28.578 (1.237) | 26.486 (1.146) | **+7.9%** |
| image | **2** | 34.552 (1.395) | 31.462 (1.270) | **+9.8%** |

**現行既定の bs=4 は、32 スロット / temp 1.0 の運用点で 8〜14% を取りこぼしている。**
ただし math (bs=2 対 bs=3 で 0.5% 差) と image (0.14% 差) は**1 回測りでは
区別できない**。**強く言えるのは「最適は 2〜3 であって 4 ではない」まで**である。

**bs=6 と bs=8 では受理が飽和している** (**実測**)。prose は両方 `accept=1.358`
`rounds=81`、image は両方 `accept=1.274` `rounds=84` — **完全に同値**である。
幅を 6 から 8 に広げて得たトークンはゼロで、払った費用は
step +18%/+20%、draft +38%/+35% だけ増えた。

ただし**「同じ受理列を歩いた」わけではない**。ヒストグラムは別物である
(prose: `32,24,9,5,2,9` 対 `39,21,5,5,2,2,3,4`)。
一致しているのは `rounds` だけで、`accept` はそこから機械的に従う —
192 tok 固定なら `accept = (new − 1)/rounds − 1` だからである (4a の検算)。
**「accept も rounds も一致」は 2 つの事実ではなく 1 つである。**
なお math では飽和せず、bs=6 の accept 1.768 が bs=8 の 1.387 を**上回る**
(単調でない)。**受理の飽和は 3 タスクの一般則ではない** (**未確認**)。

§4 旧稿が置いた「§2 の分岐点と実 tok/round の突き合わせ」も答えが出た。
§2 の下限 (bs=2 で 1.38 / 3 で 1.83 / 4 で 2.36 / 6 で 3.59 / 8 で 4.79) に対し
実測 tok/round は **bs=2 で 1.61〜1.71 (超える)、bs=3 で 1.94〜2.12 (超える)、
bs=4 で 2.00〜2.13 (下回る)、bs=6/8 は大きく下回る**。
**bs=4 は §2 の分岐点を下回るのに実測では勝っている** — これも 4e と同じ結論
(§2 の c は運用点より高い) を指している。

### 4g. 位置別受理率 a_i — **深さで落ちない** (**実測**)

1 run の中のヒストグラムから直接出した (35 §3c は k をまたいだ別 run の差分で
しか出せなかった)。bs=8 の 3 行を全長で並べる:

| task | a1 | a2 | a3 | a4 | a5 | a6 | a7 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| prose | 0.519 | 0.500 | 0.762 | 0.688 | 0.818 | 0.778 | 0.571 |
| math | 0.450 | 0.722 | 0.692 | 0.667 | 0.667 | 0.875 | 0.571 |
| image | 0.631 | 0.453 | 0.667 | 0.438 | 0.571 | 0.500 | 0.500 |

**a1 は 15 run 全体で 0.450〜0.728 (中央 ≈ 0.63)、a2 以降も 0.42〜0.88 で、
深さに対する下り坂が無い。**むしろ prose と math では a3 以降のほうが a1 より高い。
**35 §3c の llama.cpp (story で a1 = 0.60、a2 ≈ 0.67、深さで落ちない) と
同じ形・同じ高さである。**

分母は急速に痩せる (prose bs=8 で 81 → 42 → 21 → 16 → 11 → 9 → 7 ラウンド)。
**a4 以降は 2 項分布の標準誤差だけで ±0.12〜0.19 あるので、
上の凸凹を読んではいけない。**言えるのは
**「a1 から a7 まで一貫して 0.4〜0.9 の帯にあり、単調な減衰が無い」**までである。

**a1 が bs で動く**のは説明がついていない (prose 0.638 → 0.519、
math 0.705 → 0.450、いずれも bs=3 → bs=8)。分母 80〜119 に対し 2〜3σ の動きで、
**ドラフタは bs によらず 1 本目を同じに出すはずなので、これは
「生成文が run ごとに違うこと」で説明するしかない** (**未確認**)。

**35 §6(c) の τ (打ち切り閾値) への含意** (**導出**)。
「受理確率が 20% を切る位置だけ打ち切ってよい」という判定基準は、
今夜の a_i にはどの位置でも当たらない — **受理側から幅を絞る理由は無い**。
bs=6/8 が負けるのは 4d の c (4→6 で 0.26〜0.32 base/位置) のせいであって、
受理が落ちるからではない。**35 §3c の「大きい k が負けるのは費用側だけの
問題である」は、turbo でもそのまま成り立つ** (**実測**)。

> **【後日追記】本節の疑いは §10 で 1 因子ずつ分解された。**
> 本節の本文は当時の推論の記録としてそのまま残す。読むときは §10 と併せること。
> とくに **§5a の「外部の傍証は温度説に有利である」は image に限った話**で、
> **prose では temp 0 が受理を 17〜33% 下げる** (§10a)。
> また 1.7 倍の差のうち **温度は ×1.236 ぶんでしかなく、thinking が ×1.165、

### 5a. 受理が 1.7 倍動いて見える

| 出典 | 条件 | bs | accept (受理ドラフト本数/round) | tok/round |
| --- | --- | ---: | ---: | ---: |
| 27 §2(c) = §3b | 32 スロット / **temp 0** / thinking on / 画像 8 枚 | 4 | **1.852〜1.952** (中央 1.876) | 2.85〜2.95 |
| §4a (今夜) | 32 スロット / **temp 1.0** / thinking off / 3 タスク | 4 | **0.990 / 1.076 / 1.122** | 2.00〜2.13 |
| §4a (今夜) | 同上 | 2〜8 | **0.605〜1.768** | 1.61〜2.78 |

**同じ 32 スロット・同じ bs=4 で、accept が 1.876 対 1.06 — 1.7 倍違う。**
いちばん条件の近い比較 (どちらも `mtp_goal_prompt.json` + `IMG_2113.JPG`) でも
**1.855 対 1.122 = 1.65 倍**である。

**ただし温度以外も 3 つ違う** (正直に書く): thinking on/off、
生成長 (1043 tok 対 192 tok)、画像トークン数の扱い。
**この 3 点と温度を分離できていないので、「温度で 1.7 倍」とは言えない。**

**外部の傍証は温度説に有利である** (**導出**)。35 §3 の llama.cpp スイープは
**temp 1.0 / 192 tok / 同じ 3 タスク**で、受理長 (= tok/round) が
k=1 (turbo の bs=2 に対応) で **1.600 / 1.714 / 1.699** だった。
今夜の turbo bs=2 は **1.613 / 1.714 / 1.684** — **math は 3 桁完全一致、
他も 1% 以内**である。実装がまったく違う 2 つのランタイムが、
**同じモデル・同じ温度・同じプロンプトで同じ受理長を出す**。
受理は実装ではなく**モデルと温度とプロンプトで決まる量**らしい、という読みになる。
そうであれば temp 0 の 2.885 tok/round との差は温度が主因である公算が高い。
**それでも交絡を潰した対照は要る。**

### 5b. 温度は受理だけでなく**費用構造ごと**切り替える

`isPureGreedy = (temperature == 0 && repetitionPenalty == 1)`
(`Sources/TurboFieldfare/Runtime/Generation/RawCompletion.swift:69-71`)、
`forceLogitsHead: !config.isPureGreedy` (`Sources/TurboFieldfareCLI/Run.swift:158`)、
`guard !fusedGreedy || config.isPureGreedy`
(`Sources/TurboFieldfare/Runtime/Generation/CompletionPrefill.swift:41-42`)。
**temp 0 は融合 greedy ヘッド、temp 1.0 は logits ヘッド**で、
経路が分岐する。実測された差は 4b のとおり
**ラウンド外費用 0.06〜0.83 ms/round (temp 0) 対 1.277 ms/引いた行 (temp 1.0)**。

⇒ **温度を変えると「受理長」と「ラウンド外費用」の両方が動く。**
`step(k) = base + Σc_i + d·k` の 3 つの入力のうち 2 つが温度に依存する。
**温度をまたいで台帳の数字を流用してはいけない。**

### 5c. 論点 — **採点基準 v1 は temp 0 で凍結されているが、運用点は temp 1.0 である**

22 §4 の採点基準 v1 は **「8 枚 × 固定プロンプト / Reasoning ON / temp 0 /
80 スロット / 生成長の上限なし」**である。凍結された基準なので、
これを動かすのは製品判断であって本書の判断ではない。

一方、**実際の運用点は temp 1.0 である** — temp 0 は同一文の反復に落ちるので、
出荷する設定にはならない。ここに正面からの矛盾がある:

- **採点は temp 0 でやる**。ならば最適 bs は temp 0 で決めるべきである
  (受理長 2.885 なら bs=4 は §2 の分岐点 2.36 を悠々と超える)。
- **ユーザは temp 1.0 で使う**。ならば最適 bs は §4f のとおり **2〜3** で、
  bs=4 は 8〜14% 損している。

**最適 bs は温度で変わる。**したがって
**「どちらの温度で採点するか」は、性能の問題ではなく製品の問題である。**
本書はこれを決めない — **上に戻す**。
決めるまでは、**bs の既定値を 4 から動かす判断もできない** (**未確認**)。

対照実験 (同じスイープを temp 0 で回す) は本書の執筆時点で測定中であり、
**本書では結論を出さない**。

**→ その後、対照は 3 本とも完走した** (`bench/logs/36_cd_sweep_temp0.tsv`、
`36_cd_thinkon.tsv`、`36_cd_thinkon_bs.tsv`)。**結果は §10 にある。**
本節が「決めない」と書いた製品判断 (どちらの温度で採点するか) は
**依然として上に戻したまま**だが、**「最適 bs は温度で変わる」は §10e で
5 条件 9 通りに広げて裏取りされた** — そして**どの条件でも bs=4 は最適でない**。

### 8a. 費用曲線を 3 つのスロット数で並べる (**実測**)

各セルは `costProbe` が前後 2 本の decode 基準の平均で割った `step(k)/base` を

| 1 | 1.01 | 1.00 | 0.99 |
| 2 | 1.65 | 1.51 | 1.38 |
| 3 | 2.30 | 2.03 | 1.83 |
| 4 | **3.02** | **2.67** | **2.36** |
| 6 | 4.20 | 4.05 | 3.59 |

3 つ読める:

1. **スロットは base よりブロックのほうを大きく動かす。**16 → 32 で
   decode base は 57.1 → 51.2 ms/tok (**−10.3%**) しか下がらないのに、
   k=4 のブロックは 169 → 118 ms (**−30.2%**) 下がる。
   スロットを増やして得ているものの大半は **verify 幅の限界費用**の側にある。
   これは 33 §3 の「32 → 48 で t/s +14%」を、
   **どの経路が安くなったのかの側から**見た絵である (**導出**)。
2. **「奥ほど c が高い」は 32 スロットの性質であって、普遍則ではない**
   (**未確認**)。§0-1 と §2 が 32 スロットで見た単調増加
   (0.380 → 0.541) は 24 スロットにも出る (0.510 → 0.617) が、
   **16 スロットでは出ない** — 0.650 / 0.650 / 0.673 / 0.640 / 0.603 と
   ほぼ平坦で、k=4 を頂点に**むしろ下がる**。各幅 1 回測りなので
   6% 程度の凸凹は分散と区別できない (§7-2)。言えるのは
   **「16 スロットでは c の深さ依存が見えなくなる」**までで、
   §0-1 の本文 (32 スロットの話) はそのままでよい。
3. **位置あたりの費用 (`step/base ÷ k`) の底が動く。**

   のは、位置あたりの費用ではなく `step/base` 対 `tok/round` の勝負だからである

### 8b. 機構 — union は 3 つのスロット数で同じだけ効いている。動くのはミスだけ (**実測** + **導出**)

§2b と同じ換算 (144 位置で割る、要求件数 = `miss / (1 − hit)`) を 3 本のログに当てる。

| フェーズ | 要求/位置 (**導出**) | 16 スロット hit / ミス/位置 | 24 スロット | 32 スロット |
| --- | ---: | ---: | ---: | ---: |
| decode | **240** | 55.9% / **105.8** | 65.8% / **82.1** | 73.5% / **63.6** |
| k=4 | **152** | 40.4% / **90.1** | 55.9% / **66.7** | 67.6% / **49.1** |
| k=8 | **114** | 30.6% / **79.2** | 47.3% / **60.1** | 60.2% / **45.4** |

ミス総数 (decode → k=8) は **16 スロット 15234 → 11406、24 スロット
11819 → 8657、32 スロット 9164 → 6535** である。

**(a) 復元した要求件数は 3 つのスロット数で同一である。**decode 240、k=4 152、
k=8 114 — 小数第 1 位まで揃う (実際の計算値は 239.9/240.0/240.1、
151.2/151.3/151.5、114.1/114.1/114.0)。当然といえば当然で、
**union の重複除去はリクエスト列の性質であってキャッシュの性質ではない**。
decode の 240 = 30 層 × topK 8 が 3 本とも出ることが、§2b と同じ検算になっている。

**(b) したがって §0-5 と何も矛盾しない。**§0-5 は

書いた。**16 スロットで hit が 30.6% まで落ちるのは、union が効かなくなったからではない。**
union は 3 つのスロット数で**まったく同じだけ** (240 → 114、−52.5%) 効いている。
スロット数が決めているのは**畳んだ後の要求 1 件が当たるかどうか**のほうで、

| decode → k=8 のミス/位置 | 16 | 24 | 32 |
| --- | ---: | ---: | ---: |
| decode | 105.8 | 82.1 | 63.6 |

一方、**同じ k で横に見たときのミスはスロット数でほぼ倍動く** (k=8 で
79.2 対 45.4、**1.75 倍**)。**hit 率の高低ではなく、位置あたりのミス数が
c を決めている** — これが 8a の単調性の機構である (**導出**)。

バイトに直すと (`expertStride` 3,719,168 B、33 §2 と同じ換算) k=8 で
**295 / 224 / 169 MB/位置**。32 スロットの 169 MB に対し 16 スロットは
1.75 倍運んでおり、**8a の c の比 (0.603 / 0.541 = 1.11) より
ずっと大きい**。バイトが 1.75 倍でも費用が 1.11 倍にしかならないのは、
33 §4 の「床は GPU 側にある」と同じことを別の軸から見たものである
(**導出**、本節は帯域を主張しない — `io=` 列は壁時計ではない、§7-4)。

| prose | **0.218** | 0.140 | **1.56** |
| image | **0.189** | 0.128 | **1.48** |
| (参考) costProbe §8a | **0.673** | 0.453 | **1.49** |

スロット比では 1.5 倍で一致する。**水準が合わない交絡 (thinking on/off、
生成長、キャッシュ状態) は**スロット軸に対してはほぼ効いていない**という読みになる。
§3d/§4e が「どちらが運用点の値か決まっていない」と保留した問いは
本節でも解けていない — **解けたのは「どちらの計器でも c(slots) の傾きは同じ」まで**である
(**実測**)。

**(b) 動くのは c だけである** (**実測**)。同じ表を d とラウンド外で見ると:

| | 16 スロット (bs=4) | 32 スロット (§4a、bs=4) |
| --- | ---: | ---: |
| `d_ms` prose / image | 2.82 / 3.07 | 2.89 / 3.09 |
| 外 ÷ tok/round (6 run の範囲) | 1.261〜1.287 | 1.250〜1.313 (15 run) |

2% 以内)。ドラフタは resident 側にあり routed expert をほとんど引かないので、
スロット数で動かないのは筋が通る (**導出**)。

(6 run すべてが 1.261〜1.287)。これは logits の blit 経路 (§7-5) であって
expert キャッシュとは無関係だから、**スロットで動かないことが §4b の機構説明の
追加の裏取りになっている** (**実測**)。

⇒ **台帳の 3 入力 `(c, d, 外)` のうち、スロット数が動かすのは c だけである。**

**(c) 絶対値ではスロットが多いほうが依然として速い。**16 スロットの最速は
prose 30.881 / image 31.721 t/s、32 スロットの最速は 34.014 / 34.552 t/s (§4f)。

「スロットを減らすなら bs も一緒に動かさないと二重に損をする」である。

### 8d. 帰結 — 最適 bs はスロット数の関数である (**実測**)

| slots | prose 最速 bs | image 最速 bs | bs=4 の取りこぼし (prose / image) |
| ---: | --- | --- | ---: |
| 16 | **2** (1.303)、bs=3 は 1.293 | **2** (1.355)、bs=3 は 1.325 | **+24.7% / +17.3%** |
| 32 (§4f) | **3** (1.339)、bs=2 は 1.278 | **2** (1.395)、bs=3 は 1.393 | +14.2% / +9.8% |

**どちらのタスクでも、スロットを減らすと最適 bs は下がるか同じで、上がることはない。**
image は 16 スロットで bs=2 が bs=3 を **2.2%** 上回り (熱ドリフト +0.07% より
十分大きい)、32 スロットでは 0.14% 差で**同値**だった。prose は 32 スロットで
bs=3 が bs=2 を **4.8%** 上回った (ドリフト −0.35%) のに、16 スロットでは
**0.8% 差で同値**に落ちる (§7-11 のとおり、この差はドリフトより小さい)。
**両タスクとも「bs=3 の優位が 16 スロットで消える」という同じ向きに動いている。**

機構は 8a と 8c で閉じている。速くなる条件は `tok/round > step(bs)/base` であり、
**`tok/round` はスロット数で動かない** (受理はモデルと温度とプロンプトで決まる、
§5a の外部傍証)。実測でも 16 スロットの tok/round は bs=2 で 1.613 / 1.684、
bs=3 で 2.043 / 2.123 で、**32 スロットの 1.613 / 1.684、2.043 / 2.123
(§4a の prose・image) と 3 桁一致する。**分子が固定で分母だけが c で膨らむので、
**c が上がるほど損益分岐は手前に来て、最適 bs は縮む。**

⇒ **c が下がるほど最適 bs は伸びる。**この向きを 48 スロットに当てると
**bs=3〜4 が最適になる可能性がある**が、**測っていない** (**未確認**、§8f)。
33 §3 が「48 → 64 でスロットの効きは頭打ち」と示している以上、
**3 点の外挿で 48 の c を出してはいけない** (§7-10)。

**bs の既定値についての含意** (**導出**)。§4f と §5c は
「32 スロット・temp 1.0 で bs=4 は 8〜14% 損しているが、採点温度が決まるまで
既定は動かせない」と書いた。本節はそこに 1 行足す —
**既定 bs を 1 つの定数にする限り、スロット数を変えたときに必ずどこかで損をする。**
16 スロットでの取りこぼしは **17〜25%** で、32 スロットの 8〜14% より大きい。
`(slots, temperature)` から bs を引く表にするか、既定を 2〜3 に寄せるかは
**§5c と同じく上に戻す判断**である。

### 8e. 35 §6(b) の再訪 — 大きさは違うが、向きは残っているかもしれない (**未確認**)

書いた**高いほう**は、今夜そのまま再現された。低いほう (1.06) が
なぜ低かったのかは §10 で 1 因子ずつ分解する。

全 15 run が `stop=endOfTurn/endOfTurn` で、生成長比 (on/off) の中央値は
**bs=2 で 0.995、bs=3 で 1.000、bs=4 で 0.988** である。
**bs=4 だけが off より 1.2% 短い文を出している**ので、
壁時計比は bs=4 をわずかに有利に見せている (短い文は早く終わる)。
9b の decode t/s 比のほうが bs=3 に有利に出る (+4.2% 対 +3.5%) のは
この分である (**導出**)。

### 9f. 結論 — 言える線 (**実測**) と言えない線 (**未確認**)

**言える:**

1. **採点条件でも bs=3 が頂点である。**中央値で bs2 1.419 < bs4 1.449 < bs3 1.500。
2. **bs=3 は測定した全条件で bs=4 と同等以上である。**
   §4f (temp 1.0 / 192 tok) で prose 最速・math と image で bs=2 に次ぐ 2 位、
   §10 (temp 0 / thinking on / 192 tok) で最速、本節 (採点条件) で最速。
   **bs=4 が単独最速になった条件は、本書が測ったどこにも無い** (§10e)。

**言えない:**

3. **「既定を 3 にすれば採点が +3.5% 上がる」とは 3 枚では言えない。**
   画像ごとの符号が割れ (2 勝 1 敗)、画像間のばらつき (2.9〜4.2%) が
   効果と同じ桁で、1 回測りの雑音 (最大 3.3%) も同じ桁である。
   中央値と平均で答えが 3 倍違う (+3.48% 対 +1.07%) こと自体が、
   **3 枚では統計が立っていない**ことを示している。
4. **§4f の「bs=4 は 8〜14% 取りこぼしている」はここには移らない。**
   あれは temp 1.0 / thinking off / 192 tok の合成条件の数字である。
   採点条件での差は **1〜3.5%** で、1 桁小さい。
   **§5c の「最適 bs は温度で変わる」は、大きさの側でも効いている。**

⇒ **8 枚が揃えば決着する。**必要なのは 5 枚の復元と、
本節と同じ手続き (bs3/bs4 を 2 回ずつ、順序入れ替え) を 8 枚で回すことだけである。
コードの変更は要らない。

## 10. 条件が受理を動かす — 1 因子ずつ (**実測**)

今夜、**1 因子ずつ動かした対照が取れた**。本節はその結果である。

条件は全部 **image / 32 スロット / 192 tok / temp 0 / seed 1234 /
`bench/mtp_goal_prompt.json` + `IMG_2113.JPG`** で、動かしたのは thinking だけである。

### 10a. 思考チャネルを開けるだけで受理が +16% 上がる (**実測**)

同じ bs=4 で **accept 1.387 → 1.616、+16.5%** (tok/round 2.400 → 2.630)。
**動かしたのは `--thinking` だけ**である。

**§5 への訂正** (**実測**)。§5 は accept の 1.7 倍差を「温度説」として立て、
「thinking on/off・生成長・画像トークン数も違う」と交絡を正直に並べた上で
**外部傍証 (35 §3 の llama.cpp) から温度説に有利**と書いた。
今夜の 1 因子対照は、**その疑いの少なくとも一部が thinking 側だった**ことを示す。
image / bs=4 の accept を 1 段ずつ登ると (**実測**、最後の段だけ **未確認**):

| 段 | 条件 | accept | 前段比 |
| --- | --- | ---: | ---: |
| 0 | temp 1.0 / thinking off / 192 tok (§4a) | 1.122 | — |
| 1 | **temp 0** / thinking off / 192 tok | 1.387 | **×1.236** |
| 2 | temp 0 / **thinking on** / 192 tok (本節) | 1.616 | **×1.165** |
| 3 | temp 0 / thinking on / **1043 tok** (§9、採点条件) | 1.855 | ×1.148 (**未確認**) |

**3 つの因子が掛け算で 1.122 → 1.855 (×1.653) を作る。**
§5a が「1.7 倍」と呼んだ差は、**温度単独ではなく 3 因子の積**である。

**ただし段 1 (温度) はタスクで符号が変わる** (**実測**、これが本節の重要な但し書き)。

| --- | ---: | ---: | ---: |

⇒ **「温度を下げれば受理が上がる」は成り立たない。**
§5a が外部傍証から「温度が主因」と読んだ部分は、**image に限った話**である。
**§5 の本文はそのまま残すが、§5a の読みは本節で上のように限定される。**

段 2 (thinking) は **image / bs=4 の 1 点でしか測っていない**。
prose や math で同じ +16% が出るかは**未確認**である。

`--image-tokens 280` 対 `mtp_goal_ab.py` の生成長無制限) ので、
**生成長だけの効果ではない** — §5a と同じ意味で**未確認**である。

### 10b. thinking on は base を 20% 遅くする (**実測**、理由は **未確認**)

同じ image / temp 0 / 192 tok で、**bs=0 の base が 25.298 → 20.286 t/s**
(**−19.8%**、39.53 → 49.30 ms/tok、**+9.8 ms/tok**)。

**受理が +16% 上がったのに比が下がるのはこのためである** (1.403 → 1.288)。
分子 (tok/round) は伸びたが、分母の `step/base` がそれ以上に伸びた (§10d)。
**「受理が上がる条件は速い条件だ」とは限らない。**

**なぜ thinking on の decode が 20% 遅いのかは本書では調べていない** (**未確認**)。
`decode_hit` は 82.0% (on) 対 93.2% (off) で **11 ポイント落ちている**ので、
思考チャネルのトークン分布がルーティングを散らしてキャッシュミスを増やす、
という読みは立つ (`decode_experts` は 45840 で両者同一 = 192 tok × 240 件)。

### 10c. 受理が上がっても最適 bs は動かない (**実測**)

**thinking on の最適も bs=3 である** (1.342 対 bs=2 1.297 / bs=4 1.288 / bs=6 1.110)。
thinking off (temp 0) の image も **bs=3 が最適** (1.454 対 bs=2 1.401 / bs=4 1.403)。

**accept が 1.387 → 1.616 (+16.5%) 上がっても、最適 bs は 3 のまま動かない。**
「受理が高いほど最適 bs は伸びる」という素朴な予想は、**この範囲では出ていない。**

理由は台帳で説明がつく (**導出**)。速くなる条件は `tok/round > step(bs)/base` で、
thinking on は**分子と分母を同時に上げる**:

| | tok/round (分子) | step(4)/base (分母) |
| --- | ---: | ---: |
| thinking off | 2.400 | 1.466 |
| thinking on | 2.630 (**+9.6%**) | 1.848 (**+26.1%**) |

**分母のほうが速く伸びるので、最適点は伸びない。**むしろ bs=6 は
thinking off なら測っていないが、thinking on では **1.110 まで落ちている**。
§4g・§8d と同じ結論 — **幅の勝負を決めているのは受理側ではなく費用側である。**

### 10d. c も 1 因子で動く — §3d / §4e の食い違いの大半は thinking だった (**実測**)

これが本節でいちばん効く結果である。§3d と §4e は
**同じ 32 スロット bs=4 の平均 c が 3 通り (0.453 / 0.264 / 0.128〜0.187) に割れる**
ことを挙げ、候補 (thinking on/off、生成長、画像、キャッシュ状態、温度) を並べて
**「どれが効いているかは測っていない」**で止めた。今夜、そのうち 2 つが分離できた。

image / bs=4 / 32 スロットの平均 c を 1 段ずつ登る (`c = (step(4)/base − 1)/3`):

| 段 | 条件 | step(4)/base | 平均 c | 前段比 |
| --- | --- | ---: | ---: | ---: |
| 0 | temp 1.0 / thinking off / 192 tok (§4a) | 1.383 | **0.128** | — |
| 1 | **temp 0** / thinking off / 192 tok | 1.466 | **0.155** | ×1.21 |
| 2 | temp 0 / **thinking on** / 192 tok (本節) | 1.848 | **0.283** | **×1.82** |
| 3 | temp 0 / thinking on / **863〜1383 tok** (§3b 中央値) | 1.793 | **0.264** | ×0.93 |

**段 2 で c が 1.82 倍に跳ぶ。**そして段 3 (生成長) はほとんど動かない (−7%)。

**§3d が挙げた食い違いのうち、thinking で説明できる部分は今夜消えたが、
costProbe と本番の 1.7 倍は消えていない。**残る候補は §3d の表のうち
**プロンプト長 (308 tok 対 4096 context)・検証対象の列 (記録済み greedy 列 対
実ドラフト)・キャッシュ状態・1 回測り**である。**§3d の保留はそのまま残る。**

**おまけ 1 — thinking on では台帳が外挿にも耐える** (**実測**)。
§4d は「c を定数と置く外挿は bs=6 以上で 10〜15% 破れる」と書いた
(temp 1.0 / thinking off、image は bs=3 −5.3% / bs=6 −10.4%)。
同じ手続き (bs=2 と bs=4 で `step(k)` に直線を当て、bs=3 と bs=6 を予言) を

| E | 32 | 0 | on | **上限なし** (採点条件、863〜1056 tok) | — | — | **3** | §9 |

**bs=4 が最適になった条件は 1 つも無い。**測った 9 つの (条件 × タスク) のうち
**bs=2 が 5 つ、bs=3 が 4 つ**で、**4 はゼロ**である。

3 つ読める:

1. **温度は最適 bs を動かすが、向きはタスクで違う。**A → B で
   image は 2 → **3 に伸び**、prose は 3 → **2 に縮む**。

2. **thinking は最適 bs を動かさない** (B → C、image とも 3)。
   生成長も動かさない (C → E、とも 3)。
3. **スロット数は動かす** (A → D、prose 3 → 2、§8d)。

⇒ **既定 bs を 1 つの定数で持つ限り、`(slots, temperature, task)` の
どこかで必ず損をする。**そして**現行の既定 4 は、測った全条件で最適でない。**
**bs=2 と bs=3 のどちらに寄せるかは条件で割れる**ので、
本書は**「4 から動かすべきである」までを実測として置き、
どこへ動かすかは §5c と同じく上に戻す。**
