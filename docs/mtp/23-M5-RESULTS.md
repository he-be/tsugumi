## 0. 結論 — 5 つ

1. **M5 は存在する。**`verifyBlock` を呼ぶのが測定ハーネスだけだった状態を終わらせ、
   prefill → ドラフト → verify → 受理 → 巻き戻しのループが `--draft-block-size`
   1 本で回る (§1)。**採点基準 v1 が初めて実行できる**ようになった。
2. **スコアは 1.05 倍** (ゴールタスク 8 枚の end-to-end 壁時計比の中央値、bs=4)。
   目標 1.33 に対して未達で、**22 §5 の中止ライン 1.10 も下回る** (§3)。
   目標も中止ラインも書き直さない。数字をそのまま残す。
3. **ゲート 1 の分岐は投機が作っていない** (§2)。MTP on の出力は
   **bs=2 でも bs=4 でも投機ゼロでも 1 バイト違わず同じ**で、素の decode とだけ
   分かれる。原因は 15-M4 §2 が測っていたチャンク経路とスカラー decode 経路の
   数値差である。**ドラフターの提案は出力に影響しない** (D5 の設計どおり)。
4. **マイクロベンチはブロックの費用を 26〜48% 低く言っていた** (§4)。
   ループ実測の `verify(4)` は **2.63** decode ステップ (マイクロは 1.78 / 2.09)。
   一方で**受理長は想定より良い** (a(4) 1.60 → **1.90**)。
   感度表の入力を直すと **F=1.33 / M=0.31** で、
   直した表の予測 (k=2: 0.91、k=4: 1.03) は実測 (0.92 / 1.05) を再現する (§5)。
   **モデルではなく入力が違っていた** — 22 §6 のルール 4 のとおり機械的に引き直した
   (`bench/mtp_budget.py` 更新済み)。
5. **次の 1 段の場所が名指しできた** (§7)。温まったブロック 89 ms のうち
   **`wait.front` が 68 ms (76%)** — 30 層ぶんのホスト往復である。
   感度表を引くと **F 半減で e2e 1.33 (最良 k=3)** — 目標にちょうど届く —
   F と M を両方半減で **1.70**。

## 1. 何を作ったか (**実測**、コード)

15-M4 以降「`verifyBlock` を呼ぶのは `KernelCheck` の測定ハーネスだけ」だった
(22 §0-4) 状態を終わらせた。入ったのは 4 つ:

| 追加 | 場所 | 中身 |
| --- | --- | --- |
| 本番ドラフター | `Sources/TurboFieldfare/MTP/SpeculativeDrafter.swift` | M3 の probe の `draftRound` から記録・ダンプを外したもの。入力規約は 14-M3.5 §6 の `prev-bonus` (hidden は 1 つ前の行、RoPE は bonus トークン自身の位置、KV は `[0, p)`、ラウンド中は位置固定) |
| hidden の取り出し | `RealForwardRunner` の head 経路 | head は最終 RMSNorm を自分のカーネル内で当てるので post-norm hidden はどこにも無い (02 §N3)。**speculative ループがバッファを bind している間だけ** head 行ぶんの norm を 1 回足して書き出す |
| ループ | `Sources/TurboFieldfare/Runtime/Generation/SpeculativeCompletion.swift` | D6 の 1 ラウンド。prefill までの前段は `CompletionPrefill.swift` に括り出して `runRawCompletion` と共有する (D6 の指示どおり、while に分岐を足していない) |
| CLI | `--draft-block-size <0\|2..8>` | 既定 **0** (D7)。0 のときドラフター 236 MB は開かない (D1 の遅延ロード) |

ラウンドの中身 (D6 のまま):

```
bonus t (前ラウンドの受理末尾 / prefill の seed。KV 行はまだ無い)
  ドラフト  : bs-1 個 (t, t を産んだ行の hidden, KV[0,p))
  verify    : [t, d1..d_{bs-1}] を verifyBlock で 1 回
  受理      : 行 j の出力 == d_{j+1} である最長の接頭辞 a
  巻き戻し  : rewind(p + a + 1)  ← 次の bonus はターゲット自身が引いた行 a の出力
  産出      : a + 1 トークン
```

## 2. ゲート 1 — 分岐は投機ではなく経路が作っている (**実測**)

04-PHASES §3 ゲート 1 は「分岐したなら何トークン目かを記録する。
早い位置で頻繁に分岐するなら実装が間違っている」である。記録する。

`bench/m.json` / thinking off / temp 0 / 96 tok / 80 スロット、出力の共通接頭辞 (文字):

| 比較 | 共通接頭辞 | 読み |
| --- | ---: | --- |
| MTP off × 2 回 | **215 / 215 (全一致)** | 決定的 |
| MTP on (bs=4) × 2 回 | **210 / 210 (全一致)** | 決定的 |
| bs=4 × bs=2 | **210 (全一致)** | **ブロック幅を変えても同じ文** |
| bs=4 × bs=4 かつドラフト 0 本 (`TF_MTP_DRAFTS=0`) | **210 (全一致)** | **投機を全部止めても同じ文** |
| MTP off × MTP on | **87** (約 40 トークン) | ここで分岐 |

**分岐は投機が作っていない。**ドラフトを 1 本も出さない (`TF_MTP_DRAFTS=0`、
毎ラウンドが 1 トークンのブロック) 設定でも、bs=2 でも bs=4 でも、
**出力は 3 通りとも 1 バイト違わず**、同じ位置で MTP off と分かれる。
残るのは 15-M4 §2 が既に測っていた差 —
**チャンク経路とスカラー decode 経路の logits は bit 一致しない** (最大 3.8e-2 相対) —
だけである。verify はチャンク経路を通り、素の decode はスカラー経路を通るので、
競り合った行が 1 つ倒れた時点で以後の文が変わる。

つまり **MTP の出力はドラフターの提案に依存しない** (D5 の受理規則がそう作られている)。
依存するのは「ターゲットをどちらの経路で回したか」だけである。
`TF_MTP_DRAFTS` はこの切り分けのために足した診断ノブで、既定では読まれない。

**ゲート 1 の判定**: 分岐位置は 1 箇所、原因は M4 で既知の経路差、
ブロック幅と提案内容に**不変**。「早い位置で頻繁に分岐する」には当たらない。

## 4. 診断 — どこに時間があるか (**実測**、達成/未達には使わない)

同じ 8 枚から、1 ラウンドの内訳を素の decode 1 ステップ (off 側の
`decode / new`、40〜46 ms) で割ったもの:

| 量 | ループ実測 (中央値) | 直近のマイクロ実測 | 差 |
| --- | ---: | ---: | --- |
| `verify(4)` | **2.63** decode ステップ | 1.78 (20-M4.8 §0) / 2.09 (21 §3) | **+48% / +26%** |
| ドラフター 1 ステップ | **0.079** | 0.098 (21 §6) | −19% |
| 1 ラウンド計 (k=4) | **2.89** | — | |
| 産出 `a+1` | **2.89 トークン** (a = 1.90) | a=1.596 と仮定していた (22 §3 の vis) | **受理は想定より良い** |
| a(2) / a(3) | **0.817 / 1.449** | 0.739 / 1.243 | +11% / +17% |
| decode 倍率 | **1.04** | — | |
| decode が wall に占める割合 | **0.880** | 0.888 (22 §4) | 一致 |

- **受理側は想定より良い** (a 1.60 → **1.90**)。ドラフターへの追加投資が
  要らないという 22 §3 の結論はさらに強くなった。
- **費用側が想定より悪い。**`verify(4)` はマイクロベンチの **1.4〜1.5 倍**かかる。
  これがスコアが 1.0 前後に張り付く理由で、**M5 を先に作った目的そのもの**である
  (マイクロの水準を閾値と比べても現実が出てこない、という 22 §1-b の実例が
  もう 1 つ増えた)。
- 差の出どころは expert の読み出しである (**実測**、`bench/m.json` 64 tok の同条件):
  MTP on の decode は **要求 10,895 / hit 93.3% / io 1.95 s**、
  off は **要求 15,120 / hit 95.4% / io 1.04 s**。
  **ブロックは要求数を 28% 減らすのに、I/O 秒は 1.9 倍**になる。
  18-M4.6 §2 の「和集合の利益は産出で割ると 12%」に、
  **和集合はミス率を上げる**という逆向きの項が付く。

導出のチェック (**導出**): 産出 2.89 / ラウンド 2.89 ステップ = decode 倍率 1.04、
share 0.880 を入れると e2e **1.036** — 実測の壁時計中央値 1.050 と一致する
(残差は load と ttft の振れ)。**モデルは壊れていない。入力が違っていた。**

## 6. 単体で確かめたこと (**実測**、`swift test`)

`Tests/.../SpeculativeCompletionLoopTests.swift` — カーネルを使わない
6 本。ターゲットはスクリプト化したオートマトン、ドラフターも差し替え可能で、
`verifyBlock` の契約 (`startPosition == カーソル`、ブロック幅の上限、
巻き戻し範囲) をテスト側の偽ランナーが実行時に検査する。

| テスト | 見ているもの |
| --- | --- |
| 全提案が当たるドラフター | 出力トークン列・テキスト・停止理由・`kvPosition`・履歴が `runRawCompletion` と一致。受理数 == 提案数 |
| 全提案が外れるドラフター | 同上一致。受理 0、1 ラウンド 1 トークン |
| 1 本目だけ当たるドラフター | 同上一致。2 本以上受理したラウンドが 0 |
| ラウンドが停止トークンを追い越した場合 | `endOfTurn` で止まり、**KV が本文の終わりで終わる** (投機で先に進んだ行は commit されない)、未確定トークンが停止トークン 1 個 |
| `--max-new` 1/2/3/5/7 | 産出がぴったり、KV カーソルが `kvPosition` と一致 |
| repetition penalty | D5 が検証できないので**拒否**する (黙って別物を出さない) |

**ゲート 1 の縮小版がこの 1 本目〜3 本目である**: ドラフターが何を出しても、
出るトークン列は素の decode のそれと同じでなければならない。

## 7. 次 — F の内訳は測れた。`wait.front` が 76%

22 §7 が「M5 のあと、感度表が指す唯一の経路は F の内訳」と書いた先を、
ループの中で測った (**実測**、`TF_PREFILL_HOST_PROFILE=1`、
IMG_2112 / Reasoning ON / 200 tok / 80 スロット / bs=4、75 ブロック。
値は 1 ms 分解能):

| | 冷えている 25 ブロック | **温まった 25 ブロック** |
| --- | ---: | ---: |
| ブロック 1 回 | 151 ms | **89 ms** |
| `wait.front` (層前半のコマンドバッファ待ち) | 71 ms (47%) | **68 ms (76%)** |
| `fetch` (expert の読み出し、うち io) | 60 ms (40%) | 9 ms (10%) |
| `head` | 4 ms | 4 ms |
| ミス数 | 25 | 7 |
| その他 (enc / drain / route / tail) | 5 ms | 5 ms |

**温まったブロックの 4 分の 3 が `wait.front` である。**30 層ぶんで 68 ms、
1 層あたり 2.3 ms。19-M4.7 §5 は k=1 のとき GPU スパンが 11 ms と測っており、
差はホスト往復のレイテンシである (**導出**)。F = 1.33 decode ステップ
= 約 55 ms のほぼ全部がここにある。

**冷えているうちは別の話が乗る**: ブロックあたりミス 25 回 = 89 MB、
`fetch` が 60 ms。§4 の「要求は 28% 減るのに I/O は 1.9 倍」はこの区間のことで、
**ブロックのミスはまとめて来るので decode ほど隠せていない**。
ゴールタスクは 1 本 1000 トークン級なので温まった区間が支配的だが、
単発タスクを並べる実運用では冷えた区間の比率が上がる。

したがって次の 1 段は 2 つ、順に:

1. **`wait.front` を削る** — 層前半を 30 回ホストで待つのをやめる
   (層をまたいで submit をつなぐ / 待ちを 1 回にまとめる)。
   感度表で **F 半減 → e2e 1.33 (k=3)**、F 1/4 → 1.62 (k=2)。
   **単独で目標に届く改修はこれだけである** (22 §6 のルール 1)。
2. **ブロックのミスを隠す** — 冷えた区間の `fetch` 60 ms。
   18-M4.6 の読み出し先行発行はブロック内では効いていない。
