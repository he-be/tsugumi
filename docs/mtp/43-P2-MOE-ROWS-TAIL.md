# 43. P2 — `moe` は帯域床ではない。外れているのは `down` の 6 群の末尾 1 か所だけ

測定: 2026-08-20、M3 Pro 18GB / macOS 15.7.5 / commit `657425b`。
一次資料は `bench/mtp43/`。**推論経路 (`Sources/TurboFieldfare/`) は無改変** —
足したのは計器バイナリの 1 フラグだけである
(`TurboFieldfareKernelCheck --moe-rows-shape-sweep`)。

[34](34-M9-PROPOSAL.md) の **P2**。41 §6 が「`c` を動かせるのは `moe` だけ」と
出したので、その `moe` が**帯域床にいるのか、発行/占有率で律速しているのか**を決める。
34 §5 は判定条件を先に置いていた — **帯域床に近ければ `moe` はこの形状の相場と判定して
果実 A を閉じる**、そうでなければ 34 §2b-1 の二択 (`down` の末尾繕い 対
`mul_mm_id` 型 simdgroup_matrix 化) を 1 つ選ぶ。**選べた。counters は要らなかった。**

## 1. 計器 — 還元次元だけを振る (**実測**)

`prefill.metal` の rows カーネル 2 本は、還元次元を
`kPrefillRowsGroupsPerBlock` = 8 群 (32 レーン × 8 要素、128 バイト) ずつ舐め、
**余った群を 1 つずつ `kPrefillRowsTailLanes` = 16 レーンで**処理する。
production の形状 (affine 群 32) では:

| | 還元次元 | 群 | 全ブロック + 末尾 | 内側ループの周回 |
| --- | ---: | ---: | --- | ---: |
| `gate/up` | D = 2816 | 88 | **11 + 0** | 11 |
| `down` | F = 704 | 22 | **2 + 6** | 8 |

**`down` だけが 6 群の末尾を持つ。**31 §5 が「`down` は `gate/up` の 2 倍高いのに
バイトは半分」と測った非対称は、ここが疑われていた (34 §2b-1)。

`--moe-rows-shape-sweep` は**還元次元だけを振る** — `down` の F を振っても
出力行数 (D) とディスパッチ格子は動かないので、変数は 1 つである。
これで 2 つの費用モデルが分かれる:

- **バイトで払っている** → 時間は `群` に比例し、形状に対して単調
- **周回で払っている** → 時間は `ブロック + 末尾` に従い、**バイトの多い形状のほうが
  速くなりうる** (F=768 は 24 群を 3 周、F=704 は 22 群を 8 周)

**鋸歯を出せるのは後者だけである。**

## 2. 帯域で読むと 1 行で終わる (**実測**)

r=2 (bs=2 の運用点。production は平均 1.72 行/エキスパート)、16 エキスパート 1 タイル、
合成重み・常駐・I/O 無し、50 反復。GB/s は重みトラフィックで、
**床は 20-M4.8 §3 の 135 GB/s** (461 MB を 3.41 ms)。

| `gate/up` (D を振る、出力は F=704 行) | 群 | 末尾 | µs | **GB/s** |
| --- | ---: | ---: | ---: | ---: |
| D=2560 | 80 | 0 | 264.0 | **136.5** |
| D=2624 | 82 | 2 | 274.8 | **134.5** |
| D=2688 | 84 | 4 | 281.4 | **134.5** |
| D=2752 | 86 | 6 | 290.6 | **133.3** |
| **D=2816 (production)** | 88 | **0** | 297.8 | **133.1** |
| D=2880 | 90 | 2 | 296.9 | **136.6** |

| `down` (F を振る、出力は D=2816 行) | 群 | 末尾 | µs | **GB/s** |
| --- | ---: | ---: | ---: | ---: |
| F=512 | 16 | **0** | 115.1 | **125.2** |
| F=576 | 18 | 2 | 148.1 | 109.5 |
| F=640 | 20 | 4 | 185.4 | 97.2 |
| **F=704 (production)** | 22 | **6** | 222.4 | **89.2** |
| F=768 | 24 | **0** | **165.5** | **130.7** |
| F=832 | 26 | 2 | 204.5 | 114.6 |

⇒ **`gate/up` は末尾があってもなくても 133〜137 GB/s で、床に貼り付いている。**
⇒ **`down` は末尾の無い形状 (F=512 / 768) だけが 125〜131 GB/s で床にいる。**
**production の F=704 は 89.2 GB/s = 床の 66%。**

**F=768 は F=704 より 25.6% 速い。バイトは 9% 多い。**
**帯域律速ではこれは起こらない。**19-M4.7 §5 の「`moe` は 81 GB/s しか出ていない」に
名前が付いた — 出ていないのは `down` の末尾 1 か所である。

再現性: F=704 を 2 回取って 222.4 / 221.2 µs (0.5%)。他の点も 3% 以内。

## 3. 末尾は「バイトあたり」ではなく「**行あたり**」の費用である (**実測**)

同じ形状を r=1/2/4/8 で取る (`cap = r`、出荷時の特殊化):

| F | 末尾 | r=1 | r=2 | r=4 | r=8 | **+µs/行 (r1→r2)** |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 512 | **0** | 106.0 | 115.1 | 298.5 | 660.3 | **+9.1** |
| 576 | 2 | 120.9 | 148.1 | 469.1 | 1069.6 | +27.2 |
| 640 | 4 | 141.1 | 185.4 | 642.2 | 1485.1 | +44.3 |
| **704** | **6** | 169.9 | 222.4 | 813.7 | 1902.4 | **+52.5** |
| 768 | **0** | 164.5 | 165.5 | 411.1 | 907.3 | **+1.0** |
| 832 | 2 | 173.9 | 204.5 | 576.9 | 1315.9 | +30.6 |

production (F=704) を末尾の無い F=768 と並べると:

| | r=1 | r=2 | r=4 | r=8 |
| --- | ---: | ---: | ---: | ---: |
| F=704 → F=768 | **−3.2%** | **−25.6%** | **−49.5%** | **−52.3%** |

⇒ **末尾は r=1 ではほとんどタダで、行を 1 本足すたびに丸ごともう一度払う。**
末尾の無い形状は 2 本目の行が **+1.0〜9.1 µs** しかかからない
(20-M4.8 §3 の「k=4 は k=1 と同じ時間」= 重み読みが行で償却される) のに、
**F=704 は +52.5 µs 取られる。**

理由はカーネルを読めば見える (`prefill.metal:1184-1198`)。全ブロックの経路は
重みを 4 バイト (`uint`) で読み、活性化を `half4` 2 本で読む。**末尾は 1 レーン
1 バイトの重み読みと、`x_row[r][g*32 + lane*2]` のスカラー half 2 本**である。
**前者は行で償却されるが、後者は行ごとに払う。**

**⇒ これは `F` (ブロック 1 回の固定費) ではなく `c` (検証位置 1 つの限界費用) である。**
41 §4 が「`c` の 89〜94% は routed MoE」、41 §6 が「`c` を動かせるのは `moe` だけ」と
書いた、その `c` の出どころが**カーネル 1 本の末尾ループ**まで降りた。

**ただし r≥3 では別の要因が乗る** — 31 §4 の cap 崖 (cap=2 と 3 の間) がここでも
再現しており (F=704 で r=2 の 222.4 が r=4 で 813.7)、上の r=4/r=8 の列は
末尾と崖の合算である。**分離していない。**

## 4. 判定 — 34 §2b-1 の二択は「**末尾繕い**」。simdgroup_matrix は要らない

- **34 §5 の閉じる条件は発火しない。**「実 DRAM トラフィックが帯域床に近ければ
  `moe` はこの形状の相場」— production は **89.2 GB/s で床の 66%** である。
  **果実 A は閉じない。**
- **`mul_mm_id` 型 simdgroup_matrix 化は要らない。**理由は 1 つで、
  **速い経路は既に床に届いている** (F=512/768 で 125〜131 GB/s、`gate/up` は
  全形状で 133〜137)。**床より速くは書けない。**28 §6 が指名して以来
  未使用だったこの札は、**ここで降りてよい。**
- **払う総和順序の価格は末尾繕いのぶんだけでよい** (34 §2b-1 の
  「一度だけ払う」がそのまま満たせる)。

### 4a. production のタイル形状で測り直す (**実測**)

上のスイープは **16 エキスパートに一様な r** である。production は違う —
32 §5 が `encodeStreamedRows` を計器して **5.7 エキスパート/タイル、行数
1:4036 2:1257 3:818 4:449 (平均 1.65)**、しかも **PSO はタイル内で最も広い
ブロックに合わせて 1 つ**選ばれる。**31 §6 の −17% が 32 で −7% になった原因は
3 つともこれだった。**だから**数字を言う前にこの分布を掛ける**。

同じ 2 形状を、その幅と混合で (1 ディスパッチ、cap = タイル最大。µs/タイル):

| 幅 | 行の混合 | F | `gate/up` | **`down`** | 両方 |
| ---: | --- | ---: | ---: | ---: | ---: |
| **6 (production)** | 1,1,1,1,2,3 | **704** | 127.5 | **145.0** | 272.5 |
| **6 (production)** | 1,1,1,1,2,3 | 768 | 139.4 | **81.6** | 221.0 |
| 16 (31 §5 のタイル) | 1×10,2×3,3×2,4 | **704** | 335.1 | **410.8** | 745.9 |
| 16 (31 §5 のタイル) | 1×10,2×3,3×2,4 | 768 | 365.2 | **237.3** | 602.5 |

⇒ **production の形状で `down` は 145.0 → 81.6 µs = −43.7%。**
一様 r=2 の −25.6% より**大きい** — 混合には cap 3〜4 のタイルが混ざり、
そこでは末尾の取り分がさらに大きいからである。

**`gate/up` の列は比較に使えない。**F は `gate/up` にとって**出力行数**なので、
F=768 では 9% 多く計算している (127.5 → 139.4 はその分)。
繕いは F を変えないので、**2 本合計の見積もりは `gate/up` を 704 の値に据え置いて
127.5 + 81.6 = 209.1 µs 対 272.5 µs = −23.3%** である (**導出**)。

**上限の見積もり (まとめ)。**`down` **−44%**、rows カーネル 2 本で **−23%**、
いずれも production のタイル幅と行数混合の上での実測ベースである。
F=768 はバイトが 9% 多いので、本来の繕いは**これより良いはず**。

## 5. **これが t/s に出るとは限らない** (先に書いておく)

32 §5 が同じ場所で 1 度外している — `down` の 2 分割で **`moe` −7.0% / GPU 全体 −4.1%
が出たのに t/s は −0.2% (ノイズ)** だった。理由は 3 つとも**タイルの実形状**で、
本書の測定は**その形状を持っていない**:

1. **タイルの形状は §4a で畳んだ** — 32 が外した 3 つの理由のうち 2 つ
   (幅 5.7、行数の混合と cap の選ばれ方) は、もう予測の中に入っている。
   **これが 31 §6 との違いである。**
2. **残っているのは 2 つで、どちらも測っていない**:
   - **rows カーネル 2 本がブロックの `moe` の何割か。**41 §4 は `moe` を
     11.16 ms/ブロック (bs=2) と測ったが、**その中を rows / router / gather に
     割ってはいない。**割り算の分子が分からない。
   - **GPU を削って壁時計が出るか。**32 スロット (採点条件) のブロックは
     **SSD で律速している** (27 §7、469 MB/ブロック)。36 §16 の α で割られる
     (39 §5 の decode 側は変換率 43%)。
3. **前例の目盛り。**32 は **GPU 全体 −4.1% で t/s −0.2% (ノイズ)** だった。
   仮に rows が `moe` の全部なら、本書の −23% は 41 §4 の内訳で
   **ブロック GPU busy の −8.6%** に当たる (**導出**、moe は busy の 37.5%)。
   **32 の 2 倍だが、桁は同じである。**

**⇒ 実装したら本番で測り直すこと。**カーネル単体の −44% を
ブロックや t/s に持ち込んではいけない (40 §4-11)。

## 6. 限界 (**未確認**)

1. **合成重み・常駐・I/O 無し。**タイルの形状は §4a で production に合わせたが、
   **重みは合成でキャッシュに常駐**しており、本番の I/O とは並んでいない。
2. **r≥3 は cap 崖と交絡している** (§3 末尾)。末尾だけの寄与は r=1→2 でしか読めていない。
3. **なぜ `gate/up` の末尾が無料なのかは説明していない。**末尾ループの形は
   `down` と同じ (`prefill.metal:1080` と `:1184` に同じ 16 レーンの走査がある) のに、
   D=2752 (6 群の末尾) でも 133.3 GB/s で床を割らない。
   **候補は「gate と up の 2 行列ぶんの算術が末尾の非効率を隠している」だが、測っていない。**
4. **r=1 の 1 セル目が暖機を踏むことがある** (最初の実装で `gate/up` D=2560 が
   391 µs と出た)。現在は形状ごとに 1 パス捨てているが、**捨てたパスの値は記録していない。**
5. **群サイズ 32 のみ。**64 でも走るが production は 32 である
   (`ArchConfig.gemma4_26B_A4B`)。64 では末尾の走査が 32 レーン全部を使うので、
   そもそも別の話になる。
6. **末尾繕いの実装コストと、それが壊すビット一致の本数は見積もっていない**
   (`PrefillRoutedMoERowsVsDecodeTests`。31 §3)。

## 7. 再現手順

```bash
swift build -c release --product TurboFieldfareKernelCheck
# 還元次元のスイープ (モデル不要 / I/O 無し / 1 分未満)
for R in 1 2 4 8; do
  .build/release/TurboFieldfareKernelCheck --moe-rows-shape-sweep \
    --group-size 32 --moe-rows-r $R > bench/logs/43_p2/sweep_g32_r$R.log
done
# production 形状の段別 (31 と同じもの、群 32 で)
.build/release/TurboFieldfareKernelCheck --moe-rows-bench --group-size 32 \
  > bench/logs/43_p2/rowsbench_g32.log
```

`--moe-rows-shape-sweep` は `--moe-rows-r <1..8>` と
`--moe-rows-bench-iterations <n>` (既定 50) を取る。
形状ごとに 1 パス捨ててから計時する。
