# 39. N1 — 48 スロットの台帳: c 曲線は伸び、最適 bs は伸びない

測定: 2026-08-20 06:54〜07:39、M3 Pro 18GB / macOS 15.7.5 / commit `e09032a`。
`Sources/` は無改変。一次資料は `bench/mtp39/`。
`sudo sysctl iogpu.wired_limit_mb=14336` 済み — **48 スロットは起動する**
(`peak=6.78GB`、32 スロットは 4.94GB)。36 §8f の唯一の穴が塞がった。

[37](37-M9-B-PROPOSAL.md) §3 の **N1**。36 の `c(slots)` (16/24/32) は消えた
`IMG_2113.JPG` で測られていたので足元ごと取り直した。画像は
`~/Pictures/sample_imgs` の写真 46 枚 (>1MB) を名前順にした **index 0 (A) と
index 23 (B)**。md5 は `bench/mtp39/driver.log` にある。

## 1. `c(slots)` は 48 まで伸びた。しかも別の画像で再現した (**実測**)

costProbe (画像 A / thinking on / 144 位置 / 幅 1〜8):

| slots | base ms/tok | c (k=4) | decode hit% |
| ---: | ---: | ---: | ---: |
| 16 | 61.20 | 0.633 | 56.0 |
| 24 | 52.60 | 0.563 | 66.3 |
| 32 | 48.80 | 0.440 | 73.9 |
| **48** | **45.30** | **0.287** | **84.2** |

**36 §8a の同じ量 (旧画像、消失) は 0.673 / 0.557 / 0.453。**
まったく別の画像で測り直した本書が **0.633 / 0.563 / 0.440** で、
**3 点とも 0.04 以内**。⇒ **`c(slots)` は画像に依らない。**
**48 は外挿ではなく実測になった** — 36 §7-10 が禁じていた外挿は不要である。

## 2. 48 スロットの最適 bs は 2 である。3〜4 には伸びない (**実測**)

本番スイープ、運用点 (temp 1.0 / 20 秒クールダウン)、3 反復。
**`accept` / `rounds` / `tok_per_round` はスロット数を変えても完全に同一**
(投機は可逆なので当然。健全性チェックとして合格)。動くのは時間だけである。

| 画像 | base t/s | bs=2 比 | bs=3 比 | bs=4 比 | 最適 |
| --- | ---: | ---: | ---: | ---: | :-: |
| A | 24.41±0.59 (n=3) | **1.311±0.032** | 1.276±0.012 | 1.246±0.031 | **bs=2** |
| B | 24.41±0.58 (n=2) | **1.376±0.007** | 1.373±0.026 | 1.292±0.004 | **bs=2** |

⇒ **36 §8d の「48 では最適 bs が 3〜4 に伸びるかもしれない」(未確認) は否定された。**
`c` が 0.440 → 0.287 に下がっても最適 bs は 2 のまま動かない。
**36 §0-(7) の「広い幅が負ける理由は費用側だけ」は 48 でも成り立つ。**

## 3. 外れ値 1 本と、それを捕まえた計器 (**実測**)

1 反復目の画像 B / 48 スロットだけが **bs=2 で 27.22 t/s (他の反復は 33.15 / 34.04)**
と 22% 遅く、bs=4 だけが遅くならなかった。**この run は同一スイープ内の
base が head と tail で 8.0% ずれている** (他の 5 本は 0.1〜1.7%)。

⇒ **`mtp_cd_sweep.py` の head/tail base は外れ値検出器として機能する。
|head/tail| > 5% の run は捨てる**、を手続きに足す (36 §9g の 3 規則に続く 4 つ目)。
原因は 48 スロット (6.78GB 常駐) の切り替え直後のページインと見られる
(**未確認** — 2 反復目以降は暖機を 1 本入れており、そちらでは再現しない)。

## 4. 35 §6(a) の入力が直った。**A は閉じられない** (**実測**)

35 §6(a) は「MoE decode は帯域律速だから実装の余地は無い」と読んで
**果実 A を閉じてよい**と書いた。その入力は 36 §3a で壊れていることが分かり、
37 §0-6 が「48 スロット・MTP off・register 明示の decode を 1 本」で直せると書いた。
取った:

| | 48 スロット / 日本語散文 / MTP off |
| --- | ---: |
| 画像 A | **40.98 ± 0.97 ms/tok** (うち expert io 8.90 = **22%**) |
| 画像 B | **40.96 ± 0.99 ms/tok** (うち expert io 8.48 = **21%**) |
| 2 画像 | **40.98 ± 0.85 ms/tok** |
| 参照実装 (35 §8) | llama.cpp **26.9 ms/tok** |

⇒ **turbo の decode は参照実装の 1.52 倍遅く、その時間の 8 割は expert I/O ではない。**
**「帯域律速だから実装の余地が無い」は成り立たない。⇒ 果実 A は閉じない。**

**ただし比較は片側が揃っていない** (**未確認**、37 §0-6 が挙げた通り)。
参照側の 26.9 ms/tok は `llama-bench -p 512 -n 64` の合成列で **register が未定義**、
かつ llama.cpp は mmap でスロットキャッシュを持たない。
**「1.52 倍」は turbo 側だけを揃えた数字である。**

## 5. スロットを増やしても壁時計はほとんど動かない (**実測**)

| 画像 A / bs=0 | 16 slots | 48 slots | 変化 |
| --- | ---: | ---: | ---: |
| decode hit | 85.2% | 96.6% | +11.4 pt |
| expert io | 13.44 ms/tok | 8.35 ms/tok | **−38%** |
| **ms/tok** | 42.10 | 39.89 | **−5.2%** |

**節約した I/O 5.09 ms のうち壁時計になったのは 2.21 ms (43%)。**
36 §16 の α (露出率) が verify ブロックだけでなく **decode 側にも出ている**。
⇒ **スロット数は「I/O を減らす」レバーとしては効くが、「速くする」レバーとしては
4 割しか通らない。**P5 (mmap) の期待値もこの係数で割る必要がある (**導出**)。
