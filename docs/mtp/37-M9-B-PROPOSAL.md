`bench/mtp36/36_trace/*.err`) の**四則による集計**だけから成る提案書である。
推論プロセスは 1 つも起動していない。`Sources/` も `bench/` も 1 行も変えていない。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

[34-M9-PROPOSAL](34-M9-PROPOSAL.md) は P1〜P7 を並べ、
[35-LLAMACPP-CALIBRATION](35-LLAMACPP-CALIBRATION.md) が P7 を、

書いた台帳は**出た** (36 §3b の 5 列)。だから本書は 34 を並べ直す。

**並べ直す理由は 2 つある。**(1) 台帳が出たので P1/P4 が閉じ、残りの優先順位が

> `TF_PREFILL_HOST_PROFILE=1` のブロック別台帳が 3 つの register で取れ、
> **34 §1-L1 (壁時計 ≈ Σ max(I/O 露出, GPU busy)) が破れた** — 実測は
> Σ max より **20〜29% 大きく**、240 ブロックのどれ 1 つとして max に張り付いていない。
> 当たるのは **Σ(busy + 0.66·io)** (誤差 −0.7〜−1.2%) で、**expert I/O の約 3 分の 2 は
> GPU 仕事の裏に隠れていない**。この 0.66 は io が 2.2 倍動いても変わらない。
> ⇒ 本書 §3 の N の順序は変わらないが、**N2 の位置づけが「P2 に払うかの前提検定」から
> 「隠れない I/O をどう隠すかの設計」に寄る**。また **busy > io のブロックの割合は
> 日本語散文 92.2% 対 英語箇条書き 39.0% 対 コード 32.9%** で、
> **§2 の「register がどの果実を摘むかを決める」は分布のレベルで裏が取れた。**

## 0. 結論 — 7 つ

1. **34 の P1 (台帳) と P4 (行列) は終わった。**台帳の形は
   **(c, d, ラウンド外) の 3 値**で、`step(k) = base + Σc_i + d·k` は turbo でも
   成り立つ (36 §3b/§4c)。ただし **c を定数と置く外挿は bs=6 以上で 10〜15% 破れ、
   prose bs=6 では予言の符号が逆になる** (36 §4d)。
   ⇒ **台帳は内挿には使えるが外挿には使えない。**34 §5 の
   「数字を言うのは台帳が出てから」は、**「測った bs の内側でなら数字を言ってよい」**
   に更新される。台帳の 3 値のうちスロット数が動かすのは **c だけ**で、
   d ≈ 0.06 base/本 と ラウンド外 1.277 ms/引いた行 は温度・thinking・スロット数の
   どれでも動かない (36 §4b/§4c/§8c/§10d)。
2. **34 が想定していなかった軸が 1 本増えた: 出力の register である。**
   同じ画像・同じスロット数・同じ温度で、**何語でどう書くかだけ**を変えると
   expert キャッシュ hit が **93.2% → 81.0%**、decode が **−21.9%** 動く
   (36 §11a)。機構も判明していて、**層あたりの実効エキスパート数 (2^H) が
   日本語散文 23.5 / 英語箇条書き 41.8 / コード 43.8** で、
   **32 スロットは日本語散文の側にだけ収まっている** (36 §12b)。
   ⇒ **34 の P1〜P7 はすべて「どの register で」という修飾を欠いている。**
   とくに P5 (mmap) と、33 §3 / 28 §4-3 のスロット数の議論は、
   register を決めないと優先度が立たない (36 §12f)。
3. **P2 (counters で `down` の 15.1 µs/行) の優先度が上がった。ただし
   34 が書いた理由とは別の理由である。**既存の footer 9 本を集計すると、
   **register を変えて動くのは `io` の項だけ**で、
   **有利な register (日本語散文 / 32 スロット) では io は decode の 26% にすぎない**
   (§1 の表、**導出**)。35 §6(a) が「MoE decode は帯域律速だから実装の問題ではない」と
   読んだ姿は、**苦手な register の姿である** (苦手側では io が 45%)。
   ただし **残り約 25 ms/tok が GPU busy なのか待ちなのかは、この footer では
   分解されていない** (**未確認**)。**だから P2 の前に前提検定が要る** (§3 の N2)。
4. **P3 (適応ドラフト打ち切り) の価値は下がった。**最適 bs は 2〜4 で
   (36 §4f/§8d/§10e)、**そもそも捨てる札が 1〜3 本しかない**。しかも
   位置別受理率 a_i は深さで落ちない (15 run で 0.450〜0.728、36 §4g) ので、
   **受理側から幅を絞る理由は無い**。受理が飽和する条件では **bs を下げるだけで足りる**
   (bs=6 と bs=8 が完全に同値、36 §4f)。残っているのは**位置ごとの τ ではなく
   タスク/register ごとの門番**のほうである (35 §6(c)、26 §2(c) の受理長 1.058)。
5. **既定 bs を 4 から動かす性能上の根拠は立たない。**bs=4 は本書が読んだ
   10 の (条件 × タスク) のどこでも単独最速にならないが、
   **採点条件 (36 §9f、差 +0.3〜1.4%、反復雑音 5.2% の内側) と
   コード register (36 §11c、差 0.24%) では引き分けている** (36 §10e)。
   `(slots, temperature, task, register)` のどれもまだ凍結されていない以上、
   **定数 1 個を動かす議論は register が決まるまで開けない。**
6. **35 §6(a)「A を閉じてよい」は復活を検討すべきである。**復活の手続きは
   **48 スロット・MTP off・register を明示した decode を 1 本測るだけ**である
   (36 §3d の脚注)。ただし**閉じ方は 35 が書いたものとは変わる** —
   §6(a) の結論は「実効帯域が参照実装と同水準だから実装の余地は無い」だったが、
   (i) 参照側の 26.9 ms/tok は `llama-bench -p 512 -n 64` の合成列で
   **register が定義されていない** (35 §8、**未確認**)、
   (ii) turbo 側は register で decode が 1.28 倍動く (36 §11a)、
   (iii) 有利な register では io は decode の 26% しかない (上の 3)。
   ⇒ **閉じるとしても「その register で閉じた」としか言えない。**
7. **34 §1 の L1〜L6 は 1 つも死んでいない。むしろ 36 が 2 つ増やした。**
   L2 (平均で割った導出は分布に負ける) は **36 §9g で自分自身に当たった**
   (2 反復の +3.48% が 3 反復で +1.42%、平均なら +0.28%、r1 を落とせば
   **符号が反転**する)。L3 (形状を仮定しない) は **出力側の版**を得た
   (§2)。L6 (衛生) は **36 §11 冒頭で 1 度破られ、その場で取り直された**。
   ⇒ 本書は 34 §5 と同じく **t/s の合算表を置かない**。置くのは判定条件だけである (§4)。

### 1a. P2 の根拠 — footer の `decode/tok` 行を register × スロット数で並べる (**導出**)

一次資料は `bench/mtp36/36_register/*.err` と `bench/mtp36/36_trace/*.err` の
`[decode/tok io= cb1= cb2= head=]` 行 (`Sources/TurboFieldfareCLI/Run.swift:302-305`)。
`ms/tok` は同じ footer の `tok/s` の逆数である。**四則のみ、フィットは無い。**
条件はすべて **bs=0 / temp 0 / thinking off / seed 1234 / 192 tok** (36 §11 と同一)。

| register / スロット | ms/tok | io | cb1 | cb2 | head | **4 項の外** | io の割合 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 日本語散文 / 32 | 39.79 | **10.42** | 0.66 | 0.24 | 3.61 | **24.86** | **26.2%** |
| 日本語箇条書き / 32 | 42.08 | 13.22 | 0.66 | 0.25 | 3.62 | 24.33 | 31.4% |
| 英語散文 / 32 | 43.81 | 15.57 | 0.65 | 0.25 | 3.61 | 23.73 | 35.5% |
| 英語箇条書き / 32 | 51.44 | **22.89** | 0.66 | 0.28 | 3.65 | 23.96 | **44.5%** |
| コード / 32 | 45.92 | 19.57 | 0.67 | 0.27 | 3.65 | 21.76 | 42.6% |
| 日本語散文 / 24 | 40.99 | 12.00 | 0.66 | 0.25 | 3.64 | 24.44 | 29.3% |
| 日本語散文 / 16 | 42.10 | 14.53 | 0.69 | 0.27 | 3.66 | 22.95 | 34.5% |
| コード / 24 | 47.61 | 21.57 | 0.68 | 0.30 | 3.66 | 21.40 | 45.3% |
| コード / 16 | 49.52 | 23.70 | 0.72 | 0.33 | 3.66 | 21.11 | 47.9% |

3 つ読める:

1. **register とスロット数が動かすのは `io` の項だけである** (**実測**)。
   io は **10.42 → 23.70 ms/tok (2.3 倍)** 動くのに、
   **cb1 は 0.65〜0.72、cb2 は 0.23〜0.33、head は 3.61〜3.66 ms/tok** で
   9 run すべてほぼ一定である。
2. **有利な register では io は decode の 26% にすぎない。**
   苦手な register (英語箇条書き) では 45%、コードでは 43〜48%。
   **35 §6(a) が入力に置いた「turbo の off 側 decode」は、どの register の姿かを
   書いていない。**
3. **4 項の外に約 21〜25 ms/tok が残る** (**導出**、`ms/tok − io − cb1 − cb2 − head`)。
   これは 9 run で **21.11〜24.86 ms/tok (幅 ±8%)** とほぼ定数である。

**ここで止めること** (**未確認**)。この 4 項は decode を分割し尽くしていない。
`cb1` は待ち時間を引いた値であり
(`Sources/TurboFieldfare/Runtime/Inference/RealForwardRunner.swift:2980` が
`- waitNanos` している)、**4 項はいずれもホスト側の時間であって GPU busy の内訳ではない**。
したがって **残り約 25 ms/tok が「カーネルの余地」だとは言えない** —
GPU busy なのか、30 層ぶんのホスト往復の待ちなのか (22 §7 が置いた 20 ms がこれに当たる)、
この footer では分解されていない。**分解するには `TF_PREFILL_GPU_PROFILE`
(`Sources/TurboFieldfare/Runtime/Prefill/PrefillGPUProfile.swift:57`) か
counters (34 P2) が要る。だから P2 の優先度が上がる、という論法である。**

**もう 1 つの限界。**投機オン (bs>0) の run ではこの 4 項が**全部 0.00 と出る**
(`bench/mtp36/36_register/code_s32_bs{3,4,6}.err`)。scalar decode 経路の計器なので、
**verify ブロック経路の内訳は今の計器では取れない。**運用点は投機オンなので、
この穴は N2 の中で塞ぐ必要がある。

## 2. 新しく増えた軸 — register

**34 は register という語を 1 度も使っていない。**26 §2 が「受理長はタスクで
2 倍動く」を出していたので、34 P6 は「プロンプトを {goal, story, pi} の 3 本に」と
書いた。**方向は正しかったが、軸として設計されていなかった。**36 §11/§12 が
実測で立てたのは次の 3 点である (再掲は最小限にする)。

1. **decode 速度そのものが register で 1.28 倍動く** (36 §11a、**実測**)。
   26 §2 が言ったのは**受理長**の話だった。register はそこに**分母の側**を足す。
   ⇒ **タスク軸は受理と速度の両方を動かす。**
2. **機構は分布である** (36 §12b、**実測**)。層あたりの実効エキスパート数は
   日本語散文 **23.5** / 英語箇条書き **41.8** / コード **43.8** で、
   **32 スロットは日本語散文の側にだけ収まっている**。しかも
   「各層の最頻 32 個を固定する静的オラクル」が実測 hit を 3 本とも 2 pp 以内で
   言い当てる — LFU の使用回数が減衰しないので、**稼働中のキャッシュは
   静的オラクルに退化している**。
3. **バースト仮説は棄却済み** (36 §12d)。「悪い位置」は存在せず、分布そのものが広い。
   ⇒ **機構 (先読み・行頭専用の扱い) で狙える的が無い。**

**提案として言うべきことは 2 つある。**

**(a) ベンチマークは register を固定しないと、実装を比較したことにならない。**
34 §1 の **L3「合成ベンチは production の形状ヒストグラムを先に測ってから」**の
**出力側の版**である。L3 が入力形状 (タイルの行数・エキスパート数) について
言ったことが、そのまま出力の register について成り立つ。
**2 つの実装を別々の register で測った比較は、実装ではなく register を測っている。**
これは外部校正 (P7) に直接効く — 35 §6(a) の両辺 (llama.cpp の 26.9 ms/tok と
turbo の 40.5 ms/tok) は**どちらも register が書かれていない**。

**(b) 採点基準 v1 は楽観側の register で凍結されている。**
22 §4 の v1 は **日本語散文キャプション 1 種類**であり、
36 §11a の 4 register のうち**最も速い**側である (36 §11e-1、§12f)。
さらに 36 §12f はそれを機構まで下ろした — **この機体の 32 スロットは、
日本語散文のワーキングセットがたまたま収まる数である** (W=32 の窓で
日本語散文 34.5 対 英語箇条書き 52.5)。誰かの判断ミスではない。
33 §3 のスロットスイープも 28 §4-3 の動的スロットも、**すべてこの 1 種類の上に
立っている**。

⇒ **34 P6 の「プロンプトを 3 本に」は、`(task × language × format)` の
明示的な軸に置き換える。**ただし **v1 を壊してはいけない** — 22 §5-5 が
「ベンチの条件を変えるときは **v2 を切って旧数字を測り直す**」と定めている。
これが §3 の **N3** である。

**順序は N1 → N2 → N3 → N4 → N5 → N6。理由を書く。**

- **N1 が最初なのは、`sysctl` 1 行で 3 つの宙吊りが同時に落ちるからである。**
  コード変更ゼロ・半日で、34 の P4 の唯一の穴と P7 の唯一の穴を同時に塞ぐ。
  34 が P1 を最初に置いたのと同じ理屈 (これ無しに立てた期待値が負けている) が、
  そのまま 48 スロットに移る。
- **N2 が 2 番目なのは、一次資料の大半がもう在るからである** (§1a はそれで書けた)。
  残りは 2 run で、しかも **P2 (34 の 2 番目) に進むか捨てるかがここで決まる**。
  34 は P2 を 1 日と見積もっていたが、**前提検定なしに 1 日を払う理由は無い** —
  L3 (形状を仮定して合成ベンチを回して外した) と同じ失敗を避ける。
- **N3 が 3 番目なのは、これが「判定条件を書けるようにする」作業だからである。**
  既定 bs (36 §10e)、既定スロット数 (36 §12f-3)、P5 の優先度 (36 §12f-2) の
  3 つが**すべて register 待ち**で止まっている。ただし **1 日かかり、
  製品判断 (どの register で採点するか) を上に戻す必要がある**ので、
  半日で終わる N1/N2 より後ろに置く。
- **N4 が N3 より後ろなのは、N3 が N4 の結果を待たなくても切れるからである** —
  v2 は「2×2 を測る」だけで成立する。N4 は**なぜ**の答えで、v2 の register を
  減らしたり増やしたりする根拠になる。順序が逆だと N3 が止まる。
- **N5 が後ろなのは、運用点の判断を 1 つも動かさないからである。**36 §4e が
  「運用点の側から答えが出た」(costProbe も §3b も高すぎて今夜の bs=4 の勝ちを
  説明できない) と書いた時点で、**運用点の c は本番 footer から取ればよい**。
  N5 は計器の資産価値の話であって、性能の話ではない。
- **N6 が最後なのは、唯一実装を伴い、しかも 1 度負けている手だからである。**
  34 L1 は「単独 A/B で負けたレバーは捨てられない — 相方の床が動いた後に再評価」と
  書いた。**register は「相方の床が動く」ことの新しい形**だが、
  それでも **N3 で「苦手な register で運用する」と決まらない限り、
  当たっても製品に入らない。**

**34 の P1〜P7 のうち、本書が N に載せなかったもの**: P3 (§0-4 のとおり降格、
残るのは門番だけで、それは N3 の register 設計の中で扱う)、
P5 (N3 の結果待ち — 36 §12f-2 のとおり「解こうとしている問題の大きさ」が
register で違う)、P6 (N3 に吸収した)。

## 4. 判定条件だけ置く (34 §5 の作法)

**34 §5 と同じ理由で、t/s の合算表は置かない。**28 §7 の積み上げは 2 回外れ、
36 §9g では**同じ測定を 2 反復から 3 反復に増やしただけで +3.48% が +1.42% になり、
反復の取り方によっては符号が反転した**。期待値は台帳の上で、
**測った bs の内側でだけ**積む (§0-1)。

各 N について「何が出たら進むか / 何が出たら捨てるか」だけを書く。

- **N1 (48 スロットの台帳)**
  - **進む**: 48 スロットの平均 c が 32 スロットの値 (temp 1.0 / bs=4 で 0.128〜0.187、
    36 §4a) より小さく出て、かつ最適 bs が **3 以上**に伸びたら —
    **既定 bs の議論はスロット軸を含めて設計し直す** (36 §8d の「c が下がるほど
    最適 bs は伸びる」が実測になる)。
  - **捨てる**: 48 スロットでも最適 bs が 2〜3 のままなら、**bs はスロット軸から
    切り離せる** — 以後 bs は `(temperature, register)` だけの関数として扱う。
  - **A を閉じる判定**: 同時に取る MTP-off decode 1 本は、**register を明記して
    記録する**こと。参照実装側 (llama-bench の合成列) と同じ register を用意できない
    以上、**35 §6(a) を「閉じた」と書いてよいのは「日本語散文で閉じた」と
    書ける場合だけ**である。それ以外は **未確認**のまま置く。
  - **数字を言うのは 48 スロットが起動してからである。**`sysctl` の値を
    ログに残さない測定は、35 と比較できない (36 §8f)。

- **N2 (`decode/tok` の内訳)**
  - **P2 に進む**: 残り約 25 ms/tok (§1a) の**半分以上が GPU busy** なら、
    34 P2 の二択 (末尾繕い vs `mul_mm_id` 型 simdgroup_matrix 化) を counters で
    1 回で決める。総和順序の価格は一度だけ払う (34 §2b-1)。
  - **P2 を捨てる**: 残りの主成分が**待ち (ホスト往復)** なら、counters は
    答えを出さない。行き先は 22 §7 の F (30 層のホスト往復 ≈ 20 ms) であって
    `down` のカーネルではない。**この場合 34 P2 は閉じる。**
  - **どちらとも言えない場合**: 投機オン経路で 4 項が 0.00 になる穴 (§1a) を
    先に塞ぐ。**運用点は投機オンなので、scalar decode の内訳だけで
    P2 を判断してはいけない。**
  - **数字を言うのは GPU プロファイルが 2 register ぶん出てからである。**
    §1a の「74% は io ではない」は**内訳ではなく残差**であり、
    これを「カーネルに余地がある」と読んではいけない。

- **N3 (採点基準 v2)**
  - **v2 を採用する**: 同じバイナリ・同じスロット数で、**register 間の decode 差が
    36 §11a の水準 (最良と最悪で 1.2 倍以上) で再現したら**、register を
    採点の軸に入れる。36 §11 は**各条件 1 回測り**なので (36 §7-17)、
    再現は 3 反復・隣接ペアで取る (36 §9g)。
  - **register 軸を捨てる**: 3 反復で register 差が反復雑音 (最大 5.2%、36 §9c) の
    内側に入るなら、36 §11 は 1 回測りの偽物だったということである。
    その場合 v1 を触る理由は無い。
  - **絶対にやらないこと**: **v1 の 8 枚を測り直して「基準が変わった」と書く**
    (22 §5-5 の禁止事項)。v1 は凍結したまま、v2 を別に切る。
  - **数字を言うのは 8 枚が揃ってからである** (36 §9a)。5 枚が消えたままの
    3 枚では、画像間のばらつき (2.9〜4.2%) が bs の効果と同じ桁である。

- **N4 (token id 1 列)**
  - **進む**: 同じトークンが層ごとに同じエキスパートを引く (ルータが文脈に
    ほとんど依らない) なら、**register の差はトークン集合の差に還元される** —
    v2 の register はトークン分布で設計でき、新しい register を測らずに
    hit を予測できる (36 §12a の再生器がそのまま使える)。
  - **捨てる**: 同じトークンが文脈でばらけるなら、還元は成り立たない。
    その場合 register は**プロンプト単位の経験則**として扱い、
    「なぜ」は追わない (36 §12f の 3 候補は未確認のまま閉じる)。
  - **数字を言うのは 5 本のトレース (2×2 + code) が揃ってからである。**
    36 §12 は対角 2 点 + code しか持っておらず、**言語と書式のどちらが
    分布を広げるのかを分けられていない** (36 §7-22)。

- **N5 (計器の食い違い)**
  - **costProbe を使う**: プロンプト長と文脈長を本番に揃えたとき、平均 c が
    本番の thinking on の値 (0.264〜0.283、36 §10d) に**±10% で寄ったら**、
    以後 c は costProbe で測る。
  - **costProbe を捨てる**: 寄らないなら、**c は本番 footer からしか取らない**と
    決める。36 §2 の c 曲線は「ブロック経路に固定費が乗っていない (k=1 が
    decode と同値)」という**定性的な事実の出典としてのみ**残す。
  - **数字を言うのは各幅を 3 回測ってからである** (36 §7-2: 現状は各幅 1 回測りで、
    decode 基準が 8.6% ドリフトしている)。

- **N6 (苦手 register でのプリフェッチ)**
  - **実装として復活させる**: 32 スロット × 英語箇条書きで、交互 ABBA の壁時計が
    **+2% を超えたら**。30 §7 の 2 つの副作用 (予測の router 1 本 = −1.0〜1.2%、
    追い出し 5.2 本/ブロック) を先に潰した上で測ること。
  - **永久に捨てる**: ±0 または負なら、**果実 B は register 非依存に死んでいる**と
    確定させ、二度と測らない。30 の結論を「32 スロット・日本語散文に限る」から
    「無条件」に格上げして閉じる。
  - **判定は壁時計だけである** (34 L5)。的中率は 30 §3 で既に 70% 出ていて、
    それでも遅かった。**hit 率も使えない** (29 §7)。
  - **数字を言うのは N3 で運用 register が決まってからである。**苦手な register で
    +2% 出ても、日本語散文で運用するなら製品には入らない。
