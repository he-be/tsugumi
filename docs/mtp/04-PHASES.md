## 1. M0 — 追加ダウンロード不要

参照ソースは `scratch/mtp-ref/` に取得済み (transformers `gemma4_assistant`、
mlx-vlm のドラフター実装と README)。追加取得は要らない。

1. Q1〜Q6 (`01-CHECKPOINT.md` §5) を参照ソースを読んで確定させ、01 の表を埋める。
2. **`decode/tok` の内訳を実測する。**footer は `io / cb1 / cb2 / head` しか出さず、
   32 tok/s = 31 ms/tok の大半が説明できていない (`02-RUNTIME-FIT.md` §1)。
   計装を足すか既存のプロファイル経路を使って、**残りが何かを特定する**。
3. 上の内訳から速度上限の式を書く。おおまかには (**導出**):

   ```
   MTP の 1 トークンあたり時間 ≈ ( 1 ラウンドの固定費 + 受理数 a に比例する費用 ) / (a + 1)
     1 ラウンドの固定費 = ドラフト (bs−1) × ドラフター 1 ステップ + verify 1 回 (head × bs 含む)
     verify の expert I/O = bs トークンのルーティング和集合ぶん
                            (1 トークンぶんより多く、bs 倍より少ない)
   ```

   **この式が「受理率 100% でも 1.2 倍未満」と言うなら、M1 以降に進まない。**

> **参照系 (mlx-vlm) での受理率測定はやらない。**26B の 4bit チェックポイント
> (約 15 GB) の追加ダウンロードが要り、`AGENTS.md` の「フルチェックポイントを落とすな」に
> 当たる。18 GB 機で resident 運用できるかも**未確認**。受理率は M3 でもっと安く、
> もっと本番条件に近い形で測れる。

## 2. M3 — 受理率の測り方 (本命)

M1 + M2 が済めば、**verify パスも KV 巻き戻しもループ改修もなし**で受理率が測れる:

- 通常の decode を回す。各ステップで、ターゲットの最終 hidden と直前のトークンを使って
  ドラフターを bs−1 ステップ回し、提案列を**記録するだけ**にする (KV には何も書かない)。
- 次の bs−1 ステップでターゲットが実際に出したトークンと突き合わせる。一致した接頭辞の
  長さがその位置の受理長そのもの (**導出**、D5 の受理規則の定義から)。
- temp>0 でも、D5 は「ターゲットを同じ seed で 1 回引く」規則なので、実際に引かれた
  トークンと比較すればよい。追加の抽選は要らない。

これは**診断モード** (`--draft-accept-probe` 相当、既定オフ) で、オフ時は 1 命令も増えない。
テキスト経路への回帰リスクがない状態で go/no-go の数字が取れる。

**判定は「上限に対する達成率」で見る** (上限は 10-M0 §3)。実ドラフターの受理率を
M0 の式に入れて **1.2 倍を切るなら報告して停止**。到達可能な水準は同系モデルの
参照実装で測れる (13-M3 §3)。

## 4. 中止条件

> **22-GOAL-RESET が中止条件と採点基準を分けた。**以下は**中止条件** — 下回ったら
> 止めるための片側の安全弁であって、**通過しても何も達成していない**。
> 20-M4.8 §0 が `verify(4) ≤ 1.9` を「達成」と書いたのがこの取り違えで、
> 21 §2 が測り方の穴を見つけた瞬間に消えた (22 §1-b)。
> **採点基準は 22 §5 に凍結した 1 本だけ**: ゴールタスク 8 枚の end-to-end 壁時計比の
> 中央値 (目標 1.33 倍 / 中止 1.10 倍)、**M5 のループ実測で測る**。
> `verify(k)` はどこに時間があるかを言う**診断**として測り続けるが、
> 「達成/未達」の欄には入れない (22 §6)。


- **M0 の式が、受理率 100% を仮定しても意味のある改善を示さない** → 進まない。
- **実ドラフターの受理率を M0 の式に入れて 1.2 倍を切る** → 報告して停止。
  「参照実装が同系モデルで出している水準」を上限側の目安に使う (13-M3 §3)。
- **M4 で verify の全位置 logits が 1 トークン decode と一致しない**、かつ近似
  (誤差許容) でしか通らない → 通さずに報告。出力一致ゲートが崩れるため。
  → **該当した。報告済み** (15-M4 §2-1)。差は verify が作ったものではなく
  「チャンク経路 対 decode 経路」の既存差で、argmax は 256/256 一致。
  ゲート 1 を上表のとおり読み替えて進む。
- **M4.5 のゲート** (16-M4.5 §6。15-M4 §5-1 を根拠にした旧条件
  「k=4 で 2.65 decode ステップ」は、その根拠が無効になったので差し替えた):
  - **`verify(1)` が decode の 1.15 倍を切れない → 停止。**k=1 の verify は decode と
    読むバイトが 1 バイトも違わない。切れないなら k 行カーネルの一般化が失敗している。
    → **21 §5 で読み替え**: 1 トークン先読みは運用点ではないので中止条件から外し、
    ブロック 1 回の固定費の**診断値**として読む (実測 `verify(k) ≈ 0.79 + 0.35k`)。
  - **`verify(4)` が 1.9 decode ステップを切れない → 報告して停止。**物理床は 1.55。
  - **ゴール条件 (vision + Reasoning ON) のループ実測で m / vis が 1.2 倍を切る
    → 報告して停止。**warm text のマイクロベンチでは判定しない。
- **M5 でテキストのみの回帰が ±4% を超える** → 設計を見直すまで停止。
- 12 GB 予算を守れない構成しかない → 報告して停止。
