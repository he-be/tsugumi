# 04. Phase 分解 M0〜M6

**go / no-go の判断は M3 (受理率の実測) で行う。M3 までは decode 経路に 1 行も触れない。**

| Phase | 内容 | 出口条件 |
| --- | --- | --- |
| **M0** | 参照実装の読解と期待値モデル | `01-CHECKPOINT.md` §5 の Q1〜Q6 に答えが付く。`decode/tok` の内訳を実測し、MTP の速度上限を式で書く (§1) |
| **M1** | フォーマット拡張 + repacker | `--include-draft` / `--add-draft`。ドラフターなしの `.gturbo` が現行と**バイト一致** (凍結フィクスチャ)。旧ランタイムが `flags.mtpDraft` を名指しで拒否し、対照 (フラグなし) は exit 0 |
| **M2** | ドラフター forward 単体 | 参照実装との突き合わせ (合成入力、閾値は測って決める)。検出力 3 件 (わざと壊した参照が閾値を**超える**こと) |
| **M3** | **受理率の実測 (go / no-go)** | 診断モードで `bench.sh ja` 3 本 + 実運用プロンプトの受理率を bs=2/3/4、temp 0 と 1.0 で記録。診断オフ時のテキスト速度は不変 (§2) |
| **M4** | verify パス + KV 巻き戻し | 全位置 logits が 1 トークンずつの `produce` と一致。巻き戻し後の続きが「巻き戻さなかった世界」と一致。**わざと壊して FAIL** を確認 |
| **M5** | ループ統合 | 同一 seed で MTP あり/なしの出力が**完全一致** (temp 0 と 1.0)。正解到達時間の改善。**テキストのみ (MTP 無効) の回帰 ±4% 以内** |
| **M6** | CLI / Server / 受入 | `RESULTS_MTP.md` (PLAN §6 準拠: commit / ハード / コマンド / exit code / footer 全文 / 逸脱すべて) |

## 1. M0 — 追加ダウンロード不要

参照ソースは `scratch/mtp-ref/` に取得済み (transformers `gemma4_assistant`、
mlx-vlm のドラフター実装と README)。追加取得は要らない。

1. Q1〜Q6 (`01-CHECKPOINT.md` §5) を参照ソースを読んで確定させ、01 の表を埋める。
2. **`decode/tok` の内訳を実測する。**footer は `io / cb1 / cb2 / head` しか出さず、
   32 tok/s = 31 ms/tok の大半が説明できていない (`02-RUNTIME-FIT.md` §1)。
   計装を足すか既存のプロファイル経路を使って、**残りが何かを特定する**。
3. 上の内訳から速度上限の式を書く。おおまかには (**導出**):

   ```
   MTP の 1 トークンあたり時間 ≈ ( 1 ラウンドの固定費 + 受理数 a に比例する費用 ) / (a + 1)
     1 ラウンドの固定費 = ドラフト (bs−1) × ドラフター 1 ステップ + verify 1 回 (head × bs 含む)
     verify の expert I/O = bs トークンのルーティング和集合ぶん
                            (1 トークンぶんより多く、bs 倍より少ない)
   ```

   **この式が「受理率 100% でも 1.2 倍未満」と言うなら、M1 以降に進まない。**

> **参照系 (mlx-vlm) での受理率測定はやらない。**26B の 4bit チェックポイント
> (約 15 GB) の追加ダウンロードが要り、`AGENTS.md` の「フルチェックポイントを落とすな」に
> 当たる。18 GB 機で resident 運用できるかも**未確認**。受理率は M3 でもっと安く、
> もっと本番条件に近い形で測れる。

## 2. M3 — 受理率の測り方 (本命)

M1 + M2 が済めば、**verify パスも KV 巻き戻しもループ改修もなし**で受理率が測れる:

- 通常の decode を回す。各ステップで、ターゲットの最終 hidden と直前のトークンを使って
  ドラフターを bs−1 ステップ回し、提案列を**記録するだけ**にする (KV には何も書かない)。
- 次の bs−1 ステップでターゲットが実際に出したトークンと突き合わせる。一致した接頭辞の
  長さがその位置の受理長そのもの (**導出**、D5 の受理規則の定義から)。
- temp>0 でも、D5 は「ターゲットを同じ seed で 1 回引く」規則なので、実際に引かれた
  トークンと比較すればよい。追加の抽選は要らない。

これは**診断モード** (`--draft-accept-probe` 相当、既定オフ) で、オフ時は 1 命令も増えない。
テキスト経路への回帰リスクがない状態で go/no-go の数字が取れる。

**最有力の中止点はここ:** bs=3 で平均受理長が伸びないなら、M0 の式に入れて利益が
出ないことを確認し、**報告して停止する**。

## 3. 受入ゲート (M5/M6)

`RESULTS_QAT.md` §2-3 の教訓 (「tok/s は受入指標として誤っていた。速いほうが答えに遅い
逆転が起きた」) を適用し、速度は**正解到達時間**で見る。

| # | ゲート | 判定基準 |
| --- | --- | --- |
| 1 | **出力一致** | 同一 seed・同一プロンプトで MTP あり/なしの生成テキストが**完全一致** (temp 0 と 1.0)。D5 が正しければ機械的に通るはずで、通らなければ実装が間違っている |
| 2 | 正解到達時間 | `bench.sh ja` の 3 本で、正解に達するまでの**実時間**が改善する |
| 3 | テキスト回帰 | MTP 無効時の `bench.sh ja` が現行比 **±4% 以内** (同一セッション A/B。セッションを跨いだ比較は分解能がない — `RESULTS_VISION.md` §3) |
| 4 | メモリ | peak が 12 GB 予算内。テキストのみ 6.64 GB / vision 同居 7.01 GB に **+0.24 GB** 程度で収まること |
| 5 | ロード時間 | MTP 無効時の `load=` が現行と変わらない (D1 の遅延ロード) |
| 6 | 旧ランタイム拒否 | MTP 付き `.gturbo` を MTP 以前のビルドに食わせて exit 1。対照 (フラグなし) は exit 0 |
| 7 | 追記 | `--add-draft` が 236 MB のみ取得。テキスト側 inode 不変、再検証 exit 0 |
| 8 | KV 巻き戻しの検出力 | わざと壊した rewind で検査が **FAIL する**こと |
| 9 | Server | プロンプトキャッシュが投機位置を publish しない。`cached_tokens` が MTP あり/なしで一致 |
| 10 | 退行なし | `Scripts/test.sh` の失敗が既知の陳腐化スイートのみ (新規失敗ゼロ) |

## 4. 中止条件

- **M0 の式が、受理率 100% を仮定しても意味のある改善を示さない** → 進まない。
- **M3 の受理率が低く、M0 の式で利益が出ない** → 報告して停止。
- **M4 で verify の全位置 logits が 1 トークン decode と一致しない**、かつ近似
  (誤差許容) でしか通らない → 通さずに報告。出力一致ゲートが崩れるため。
- **M5 でテキストのみの回帰が ±4% を超える** → 設計を見直すまで停止。
- 12 GB 予算を守れない構成しかない → 報告して停止。

## 5. ツールの置き場所

vision と同じ形にする:

- `Scripts/mtp/fetch_draft_weights.py` — ドラフター重みの取得 (236 MB)。
  `Scripts/vision/fetch_vision_weights.py` の写像。
- `Scripts/mtp/dump_draft_fixtures.py` — **合成入力**でドラフターだけを回して段階別

  `(トークン, last_hidden, 共有 KV)` なので、ここを乱数で与えれば参照と本ランタイムを
  同じ入力で比べられる。**ターゲット 26B を Python 側で回す必要はない** (**導出**)。
- fixture は `scratch/mtp-fixtures/` (作業ツリー外)。
- 突き合わせは `TurboFieldfareKernelCheck --draft` (`--vision-tower` の写像)。
