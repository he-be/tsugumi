# 47. D 提案 — expert blob を `mmap` して GPU に直接読ませる。プローブの設計と判定条件

> **実行済み: [48](48-D-P1-P4-MMAP-RESIDENCY.md) が P-1〜P-4 を測った。**
> P-1 PASS / P-2 PASS / P-3 FAIL / **P-4 はゲートの上**。
> **§3 の「clean file-backed」は `MAP_SHARED` でだけ成り立つ** (48 §2) ほか、
> §6 の冷たい条件の作り方も 48 §6 が差し替えている。**本書だけを読まないこと。**

提案: 2026-08-20、M3 Pro 18 GiB / macOS 15.7.5、[46](46-W3-CODE-ENTROPY.md) の続き。
**これは提案であって測定ではない。**本書に**実測**の新しい数字は 1 つも無く、
引いている数字はすべて 33 / 41 / 45 / 46 のものである。

[28](28-M8-PROPOSAL.md) §5 の末尾が唯一「却下しなかった転換」として置いたまま、
1 年ぶんの測定を挟んで手つかずだったもの — **スロットキャッシュを捨てて
`mmap` + `makeBuffer(bytesNoCopy:)` にする**。46 §5b がその期待値を大きく変えたので、
**判定条件を先に置いてプローブを設計する** (43 / 44 と同じ作法)。

**前提が 1 つ変わっている** (ユーザー確定 2026-08-20): **本プロジェクトはこの
MBP (M3 Pro 18 GiB) 専用**であり、他機への配布予定は無い。したがって
「8 GB 機で動くこと」は制約ではなくなり、**運用点は暖かい regime である**。

## 0. 何を決めるのか

**決めるのは 1 つ: 冷たいときに今の並列 `pread` に負けないか。**
暖かいときに勝つことは 46 §5b からほぼ確実なので、賭けは片側にしかない。

## 1. なぜ今か — 46 §5b が出した 2 つの事実 (**実測**)

1. **decode の `io` はディスクではなく大半がコピーである。**
   運用点の decode は 129.2 MB/tok を 14.21 ms で「読む」(9.09 GB/s、45 §4) が、
   そのうち**ディスクから来ているのは 4 分の 1** (pagein 0.66 GB/s 対 読むバイト
   2.49 GB/s、46 §5b)。**残り 4 分の 3 はページキャッシュから私有スロットへの memcpy。**
   裏付け: `affine` (143.0 MB/tok) と `sym` (129.2 MB/tok) で**バイトが 10% 違うのに
   実効帯域は 8.88 / 9.09 GB/s とほぼ同じ**。バイト数に依らず一定のレートが出るのは、
   律速がデバイスではなく**固定レートの転送**である signature である (**導出**)。
2. **同じバイトを RAM に 2 枚持っている。**私有スロットは
   30 層 × 32 スロット × 3.358720 MB = **3.22 GB**。同じ内容が OS のページキャッシュにも載る。

## 2. 形式はもう準備できている (**実測**、確認済み)

D は**フォーマットの変更を必要としない**。

| | 値 | 効く理由 |
| --- | ---: | --- |
| `hw.pagesize` | **16,384** | `mmap` / `bytesNoCopy` の粒度 |
| `MoEPackFormatV1.alignmentBytes` | **16,384** | **ページサイズと一致している** |
| `expertStride` (sym) | 3,358,720 | **= 205 ページちょうど**、余り 0 |
| blob の位置 | `physicalRank × expertStride` | ⇒ **全 blob がページ境界から始まり、ページ数が整数** |

`makeBuffer(bytesNoCopy:length:options:deallocator:)` はポインタのページ整列と
長さのページ倍数を要求する。**両方すでに満たしている。**再レイアウトは要らない。

## 3. 予算 — 18 GiB に何が載るか (**導出**)

`hw.memsize` = 19,327,352,832 B = **18.000 GiB**。

| | サイズ |
| --- | ---: |
| packed_experts (`sym`) | **12.011 GiB** |
| resident core (`model_weights.bin`) | 1.270 GiB |
| drafter | 0.220 GiB |
| KV @ 8192 ctx (SWA 25 層 × 1024 窓 + full 5 層、`attentionKEqV`) | **約 0.18 GiB** (K/V 別持ちなら 0.35) |
| **小計 (常時)** | **約 13.68 GiB** |
| vision tower (BF16、prefill のみ) | +1.02 GiB |

**pre-`sym` では 14.7 GiB でこの算数は成立しなかった。**45 (W2) が空けた 1.43 GiB が
そのままこのドアを開けている。

**ただし「全部 wire する」版は採らない。**現在の `iogpu.wired_limit_mb` は 14336
(= 14.0 GiB) で、13.68 GiB を全部 wire すると余白が 0.3 GiB しか無く、
弾力性も失う。**採るのは resident-but-not-all-wired である:**

- ページキャッシュが 12.011 GiB を **clean な file-backed ページ**として持つ
- Metal が wire するのは **1 ステップが触るぶんだけ** = 30 層 × 8 × 3.36 MB = **806 MB**
- 私有の硬い下限は resident core + KV + 在庫で **約 2.1 GiB** (今の 4.5 GB から縮む)

**degradation の質も上がる** (**導出**): 今の 3.22 GB は anonymous memory なので、
OS が回収するには圧縮か swap が要る。D 後はほぼ全部が clean file-backed になり、
**page-out もせず swap にも行かず、捨てて読み直すだけ**になる。
**モデルの重みが swap に落ちることは原理的に起きなくなる。**

## 4. 取り分 — 上限は計算できる (**導出**)

> **[50 §4](50-D-PRIZE-NOCACHE.md) がこの節の取り分を引き直している (2026-08-20)。**
> `mmap` が消せるのは「ページキャッシュ → 私有スロットの memcpy」だけで、
> **ディスク → ページキャッシュは消せない。**キャッシュ由来は運用点で `io` の
> **17〜19%** なので、**消せるのは 0.62〜1.08 ms/tok = 壁時計の約 2%** である。
> **ここの 36〜40 t/s は立たない。**48 §12 が指摘した穴 1 (根拠が 1 本) より
> 手前に、**そもそも消せる量の見積もりの誤り**があった。

2 つの独立な見積もりが一致する。

- **コピー側から**: 45 の 38.76 ms/tok から `io` 14.21 の 4 分の 3 (10.5 ms) が消えると
  **約 28.3 ms/tok = 35.4 t/s**。`io` が完全に消えれば 24.6 ms/tok = **40.7 t/s**
- **GPU 側から**: 41 §1 の scalar decode は `busy` **25.53 ms/tok** で、
  **スロット数にも register にも動かない**。`sym` で `head` が 9.2% 下がったぶんを引くと
  約 25.2 ms/tok ＝ **約 39.7 t/s** が I/O ゼロの天井

⇒ **36〜40 t/s。**22 §5 が凍結したゴール `tg ≥ 30` を、I/O 側から超える。
**そしてそこで頭打ちになる。**その先は `attn` 11.12 (うち 76% が dense 射影)、
`moe` 8.05、`shared` 4.27、`head` 3.39 しか残らない (41 §4/§5)。

## 5. 賭けは 1 点 — Metal の residency (**未確認**)

**GPU は CPU のようにページフォルトを取れない。**コマンドバッファが使うリソースは
実行前に resident (wired) になる必要がある。ここから 2 つの未確認が出る。

- **(a) 粒度。**層ファイル単位 (128 × 3.36 MB = 420 MB) の MTLBuffer を 1 個作ると、
  それを使うたび 420 MB が wire される。30 層で 12.6 GB ＝ 破綻。
  **エキスパート単位 (3.36 MB) のバッファを 3,840 個作れば 806 MB/ステップに収まる**
  はずだが、**確かめていない。**
- **(b) 深さ。**今は `concurrentPerform(iterations: plan.misses.count)`
  (`PreadExpertStreamer.swift:345`) でミスを並列発行しており、33 §2 が
  「発行深さ = 層のミス数」、33 §1 が「深さ 1 で 4.3〜4.6 GB/s、深さ 8 以上で
  6.0〜6.5」と測っている。**residency 起点のページインがエンコードスレッド上で
  直列化すると、冷たい側では今より遅くなりうる。**

(b) の緩和策は既にリポジトリにある — `RDAdvice.swift:34` の `F_RDADVISE`。
**エンコードの前にバックグラウンドで並列にページを温めておけば、
今の深さを保ったまま memcpy だけを消せる**という筋書きである。

## 6. プローブの設計 — カーネルではなく**バッファの出どころ**だけを振る

44 が「形状を固定して重みの形式だけを振った」のと同じ形にする。
**計器は `TsugumiKernelCheck --mmap-residency-probe` (新規フラグ 1 つ)、
推論経路 (`Sources/Tsugumi/`) は無改変。**

`packed_experts/layer_00.bin` を `mmap` し、`e × expertStride` の位置・長さ
`expertStride` で `bytesNoCopy` の MTLBuffer を 128 個作る。カーネルは
43 / 44 が使った `prefill_moe_rows_gate_up_act` / `prefill_moe_rows_down` を
**production の形状・`--group-size 32` で**そのまま回す (40 §4-15)。

| | 測るもの | 対照 |
| --- | --- | --- |
| **P-1** | 8 個を使うコマンドバッファを commit したときの **wired ページの増分** | 層ファイル 1 個の MTLBuffer で同じことをした場合 |
| **P-2** | **暖かい**とき、1 エキスパートを GPU に読ませるまでの費用 | 今の経路 (`pread` して私有バッファへ) の同じ費用 |
| **P-3** | **冷たい**とき (`purge` あるいは `madvise(MADV_DONTNEED)` 後) の同じ費用 | 同上 (今の並列 `pread`) |
| **P-4** | P-3 が落ちたときだけ: `F_RDADVISE` で先に温めた場合の P-3 | — |

計測の作法は 44 と同じ (50 反復 × 3 回、間に 20 秒のクールダウン、中央値)。
**`purge` は sudo が要る**ので、冷たい条件は `madvise` 側を第一手にする。

## 7. 判定条件 (先に置く)

- **P-1 PASS**: 1 コマンドバッファあたりの wired 増分が **8 × 3.36 = 約 27 MB**。
  **FAIL** (層ファイル 420 MB ぶん wire される) ⇒ この形は死ぬ。
  代替は「blob ごとに `mmap` を 1 本ずつ張る」(3,840 マップ) で、それも駄目なら**枝を閉じる**。
- **P-2 PASS**: 暖かい 1 エキスパートの費用が、今の `pread` 経路
  (3.359 MB / 9.09 GB/s = **0.37 ms**) の **3 分の 1 以下**。
  **FAIL** ⇒ コピーが消えていないので**閉じる**。
- **P-3 が本番のゲート**: 冷たい 1 エキスパートの費用が、今の冷たい `pread`
  (33 §1 の深さ 1 付近 4.3 GB/s ⇒ **0.78 ms**) の **1.2 倍以内**。
- 判定表:

| P-1 | P-2 | P-3 | P-4 | 次の行動 |
| --- | --- | --- | --- | --- |
| FAIL | — | — | — | 閉じる |
| PASS | FAIL | — | — | 閉じる |
| PASS | PASS | PASS | — | **実装する** |
| PASS | PASS | FAIL | PASS | **実装する** (先読みを併せて) |
| PASS | PASS | FAIL | FAIL | **保留。**単機・暖かい前提なら採る判断もありうるが、それは**ユーザーの決定** |

## 8. プローブが答えられないこと (**未確認**、先に書いておく)

- **end-to-end の噛み合い。**先読み (`ExpertPrefetch`) との相互作用、
  層をまたぐ発行の重なり、3,840 個の MTLBuffer をエンコード時に触る費用。
  **単体の µs からは出ない。**実装してからでないと分からない。
- **`--expert-cache-slots` の意味が変わる。**D にはスロットが無い。
  運用点 (32 スロット、`Scripts/demo/serve.py:62`) が何を指すかは**製品の決定**であり、
  **こちらで勝手に決めない** (40 §4-12)。
- **`iogpu.wired_limit_mb` は再起動で 8192 に戻る。**常駐前提の設計にすると、
  これが起動時の必須条件に格上げされる (今は「48 スロットを測るときだけ」の話)。

## 9. 実装する場合の受け入れ (45 と同じ)

**同じバイトを読むので、出力はビット一致するはずである。**
45 §3 と同じゲートを使う — temp 0 / 256 tok × 3 プロンプトで**バイト一致**、
`decode hit` (に相当する指標) とルーティングの一致。
**「差が無いこと」ではなく「差が存在しないこと」で通す。**

## 11. これが当たると、ロードマップが書き換わる

expert I/O が消えると、**M8 以降の調査の大半は対象ごと無くなる** —
スロットキャッシュ、先読み、LFU、`c(slots)`、`hit%`、`2^H`、`register`、
39 §4 の「果実 A」、41 §7-2 の 32 対 48 の食い違い、46 §5 のページキャッシュ。
**これらは全部「I/O 露出」の話で、露出が無ければ意味を失う。**

残るのは GPU 側の 2 枚だけになる:

- **43 の `down` の末尾繕い** (40-HANDOFF の「次の 1 手 (a)」)
- **41 §5 の dense 射影** (`attn` 11.0 ms/ブロックの 76%、見積もり未了)

**⇒ 47 は (a) より先に置く。**(a) は `moe` バケットの分子を取る計器で、
D が当たれば同じ計器がそのまま使える (対象が I/O から GPU に移るだけ) が、
順序を逆にすると (a) の判定条件 (「rows 2 本が `moe` の 7 割以上か」) を
I/O 律速の条件下で取ることになる。**2026-08-20 のユーザー確定で 47 を先にする。**
