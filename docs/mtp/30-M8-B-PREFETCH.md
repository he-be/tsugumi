# 30. M8 果実 B の実装 — 先読みを fetch に渡したら遅くなった

測定: 2026-08-19、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3。
対象モデル `scratch/gemma4-qat.moepack` (drafter 同梱)、32 / 48 スロット、8192 context。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

29-M8-B-PROBE §6 が置いた引き継ぎ (「まだ入っていないのは予測を実際に fetch に
渡す経路である」) を実装した。設計はそのまま入り、**予測は 29 §4 が測ったとおりに
当たる**。それでも**壁時計は速くならない** — 32 スロットで **−3.5%**、
48 スロットで **−1.5%** である。

## 0. 結論 — 5 つ

1. **入った。出力は 1 バイトも動かない** (**実測**)。先読み on/off で md5 一致
   (`3eefadf6…`、120 tok)。20 回以上の A/B すべてで一致し、受理列
   (`accepted=14,15,5,15`) とラウンド数も同じである (§2)。
2. **予測は設計どおり当たる** (**実測**)。N=1 で先読みした 28.2 本/ブロックのうち
   **19.8 本 (70%)** をその層が本当に要求した — 29 §4 の「1 位で 70%」と同じ値。
   `declined=0` (投機用プランは毎回置けた)、`wait.prefetch=0.06 ms/ブロック`
   (層が着いたときには読み終わっている)。**前倒しそのものは効いている。**
3. **それでも遅い** (**実測**、交互 A/B ×3)。32 スロット 20.80 → **20.07 t/s**、
   48 スロット 24.09 → **23.74 t/s**。
4. **内訳は 2 つで、どちらも 29 §5 の導出に入っていなかった** (**実測**、§4)。
   - **予測そのものの費用**: 層ごとに router をもう 1 本 GPU で回す分。
     単独で **−1.0% (32) / −1.2% (48)**。`TF_MTP_EXPERT_PREFETCH_N=0`
     (予測はするが 1 本も投げない) で切り分けた。
   - **投げる費用**: 32 スロットで **−2.6%**、48 スロットで **±0**。
5. **29 §5 の導出が外したのは「層あたり I/O 1.50 ms」**である (**実測**、§5)。
   32 スロットのブロックは fetch に 60.7 ms/94.2 ms を使っていて、
   **すでに I/O 帯域が床**である。前倒しは読むバイトを減らさないので、
   増えたバイト (+11%) がそのまま費用になる。48 スロットでは
   fetch が **42.6 → 40.2 ms** と本当に縮むが、`wait.front` の +3.7 ms が食う。

既定はオフ (`TF_MTP_EXPERT_PREFETCH`) のまま残す。**機構は正しく動いていて
符号だけが負**なので、§7 の 2 つを潰せば表に出る見込みがある。

## 1. 何を入れたか (**実測**、`TF_MTP_EXPERT_PREFETCH=1`)

29 §6 の設計をそのまま実装した。3 つある。

**1. 投機用のプラン** `PreadExpertStreamer.planSpeculativeExperts`。
既存の `makeExpertCachePlan` と 2 点だけ違う (29 §6-1 のとおり):

- **`expertUseCount` を増やさない。**LFU でスロットを守るのは使用回数なので、
  外れた先読みが回数を上げると**誰も使っていないエキスパートが守られる**。
- **`slotLastUse` が直近のプラン以上のスロットは犠牲にしない。**置けなければ
  `nil` を返して先読みを諦める。単体テスト 3 本 (§8) がこの 2 つを固定する。

**2. 予測の読み戻しと発行**。`RealForwardRunner` の `.route` 段で、
層 L+d の予測のうち非常駐のものを**予測重みの強い順に上から N 本**
(既定 1) だけ `startRoutedExpertFetch` に渡す。計器 (`RouterPreviewProbe`) と
同じ予測を使うので、router の追加 encode もバッファも共用である。

**3. 待ち位置**。層 L の `.route` 段の頭で、その層宛の先読みハンドルを
`wait()` する (`drain` の直後、プランを作る前)。完了した先読みは
`expertResidency` が上がっているのでプランには**ただのヒットとして見える**。
チャンクを抜けるときは `defer` で残りを全部待つ — 飛行中の読み出しを待たずに
捨てると、割り当て直されたスロットへ書き込みうる。

計器も 1 本足した: 先読みしたエキスパートのうちその層が本当に要求した数
(`useful`)。**telemetry の hit 率では判定できない** — 先読みの read は miss として
数えられるので、hit 率は必ず下がる (29 §7 のとおり 76.2% → 75.1%)。


出力 md5 は **on/off・32/48 スロット・N=0,1,2,4・d=1,2 のすべてで
`3eefadf60a5aa49540a4086706d6e5e4`** で一致した。29 §6 の「構造的に通る」
(どのスロットに置くかが変わるだけ) が実測でも成り立っている。

## 3. 速度 (**実測**、同一セッション交互 A/B ×3、120 tok)

`pred` は `TF_MTP_EXPERT_PREFETCH_N=0` = **予測はするが 1 本も投げない**。
予測の費用と先読みの費用を分けるための設定である。

| スロット | off | pred (N=0) | on (N=1) |
| --- | ---: | ---: | ---: |
| 32 | **20.80** t/s | 20.60 (−1.0%) | **20.07 (−3.5%)** |
| 48 | **24.09** t/s | 23.79 (−1.2%) | **23.74 (−1.5%)** |

> 単発の値は run 間で ±5% 振れる (熱・ページキャッシュ)。**交互に回した組の中でだけ
> 比べること** — 上の 6 つは off→pred→on を 3 周した平均で、3 周とも順序が同じである。

## 4. ブロックの内訳 (**実測**、`TF_PREFILL_HOST_PROFILE=1`、135 ブロック平均)

| | call | fetch | wait.front | wait.prefetch | 読むバイト |
| --- | ---: | ---: | ---: | ---: | ---: |
| 32 off | 94.2 ms | 60.7 | 24.8 | — | 466 MB (7.49 GB/s) |
| 32 pred | 95.2 | 60.3 | 25.9 | — | 466 MB |
| 32 **on** | **98.6** | 62.4 | 26.7 | 0.06 | **517 MB** (8.08 GB/s) |
| 48 off | 77.1 ms | 42.6 | 26.2 | — | 242 MB (5.54 GB/s) |
| 48 pred | 77.5 | 41.6 | 27.4 | — | 242 MB |
| 48 **on** | **79.1** | **40.2** | **29.9** | 0.19 | **291 MB** (7.08 GB/s) |

読むバイトの増分の内訳 (**実測**、ミス本数から。先読みが当たった分は
「同じ読み出しが早くなった」だけでバイトは増えない):

| | 層自身のミス | 先読みの発行 | うち当たり | 追い出しで増えたミス | 合計 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 32 | 125.3 → 105.5 | +28.2 | 19.8 (70%) | **+5.2** | 138.9 (+11%) |
| 48 | 65.0 → 50.8 | +25.6 | 14.2 (55%) | **+2.0** | 78.4 (+21%) |

**「追い出しで増えたミス」が 29 §7 の追い出し合戦**で、32 スロットで 5.2 本/ブロック。
29 §6-1 の「直近のラウンドを守る」規則は効いている (`declined=0` で置けており、
外れた先読み 8.4 本に対して追加ミスは 5.2 本) が、ゼロではない。

## 5. なぜ 29 §5 の導出とずれたか (**実測**)

29 §5 は「層あたり I/O 1.50 ms、GPU busy 1.63 ms」から出発して
「先読みが当たった分は前の層の GPU 仕事の陰に入る」と積んだ。実測は違う:

- **32 スロット**: fetch は 60.7 ms/ブロック = **層あたり 2.0 ms**。GPU busy
  (約 1.5 ms/層) より**大きい**。つまり I/O はすでに床で、GPU の陰に隠す余地が無い。
  466 MB を 60.7 ms = **7.5 GB/s** で、27 §7 のプローブの上限 (深さ 8 で 8.9 GB/s)
  に張り付いている。**先読みは読むバイトを減らさない**ので、
  増えた 11% がほぼそのまま fetch の +1.7 ms になる。
- **48 スロット**: fetch は 42.6 → **40.2 ms** と本当に縮む — バイトが 21% 増えても
  縮むので、**前倒しは機構として効いている** (帯域も 5.54 → 7.08 GB/s と深い
  キューぶん伸びている)。それでも call は +2.0 ms で、食っているのは
  `wait.front` の **+3.7 ms** である。

`wait.front` の増分のうち **1.2 ms は予測そのもの** (`pred` 行) — 層ごとに
層 L+d の router GEMV (720 KB の重み読み) を 1 本増やしているぶんで、
29 §1 が計器の費用として測った 23.6 → 22.0 t/s と同じものである。
残り 2.5 ms は**未確認**: 先読みの DMA (+49 MB/ブロック) が unified memory の
帯域を GPU と食い合っている疑いがある。

## 6. N と d のスイープ (**実測**、48 スロット、交互 A/B ×2)

| | t/s | off 比 | 先読みの的中 |
| --- | ---: | ---: | ---: |
| off | 23.72 | — | — |
| N=2 | 23.32 | −1.7% | 62% |
| N=4 | 22.63 | −4.6% | 57% |

| | t/s | off 比 | 先読みの的中 |
| --- | ---: | ---: | ---: |
| off | 24.23 | — | — |
| N=1, d=1 | 23.93 | −1.3% | 80% |
| N=1, d=2 | 23.60 | −2.6% | 68% |

**N を増やすほど単調に悪い。**的中率は 29 §4 の積み上げ表 (1 位 70% → 4 位 48%)
どおりに落ち、落ちたぶんがバイトになる。**d=2 も悪い** — リードタイムは長いが
的中が 12 ポイント低く、§5 のとおり床はバイトである。
**N=1 / d=1 が最良**という 29 §5 の推しは正しかった。符号が負なだけである。

> d=2 の測定中に 1 つ直した: 先読みだけを有効にしても d=1 と d=2 の router を
> **両方** encode していた。要る距離だけ回すようにして d=2 は 22.94 → 23.60 t/s。

## 7. 次に潰すもの (**未確認**)

48 スロットの内訳が示すのは「機構は効いていて、2 つの副作用が利益を上回っている」
である。どちらも潰せる見込みがある。

| | |
| --- | --- |
| **予測を安くする** | 層あたり router 1 本 (−1.0〜1.2%) が固定費。層 L 自身の router と**同じ dispatch** で 2 層ぶん出すか、行を 1 本に減らせば消える見込み。ただし重み 720 KB の読みが費用の主なら行数は効かない |
| **追い出しをゼロにする** | 32 スロットで 5.2 本/ブロック。守る範囲を直近 1 プランから K プランに広げる (`slotLastUse < useClock - (K-1)`)。置けなければ諦める規則はもう入っているので、K を足すだけで測れる |
| **`wait.front` の残り 2.5 ms** | §5 の未確認。先読みの DMA と GPU の帯域競合なら、そもそも 32 スロットでは打つ手が薄い |
| **48 スロットで先に黒字化するか** | 48 では投げる費用が ±0 で、fetch は −2.4 ms 出ている。予測が只になれば 48 スロットは +2〜3% になる**導出** |
| **A (`moe` 28 ms) は依然未測定** | 28 §7 の 1 本目。B がこの結果なので、次はこちらを先に測るのが筋である |
