# 21. ゴール条件で測る — 「MTP が最も得をしない領域」は逆だった

測定: 2026-08-18、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3、commit `4e767e1` + §1 の変更。
対象モデル `scratch/gemma4-qat.moepack`、画像は `sample_imgs/IMG_2112.JPG` (853×1280、
soft 260 tok — 10-M0 §4 と同じ 1 枚)。表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

---

## 0. 結論 — 4 つ

> **22-GOAL-RESET が本書の位置づけを直した。**本書の測定 (§2〜§5) は**診断として有効**だが、
> §6 の速度比は `verify(k) の実測 × a の実測` の**導出**であり、**採点ではない**。
> 15-M4 以降の速度比が 6 本にわたって互いを差し替え続けたのは、別条件で測った 2 つの
> proxy の積を成績表に載せたからで、本書もその形を踏襲している (22 §1-c)。
> **採点は M5 のループ実測だけ**で行う (22 §5)。§6 の表は予測として読み、M5 で
> 答え合わせすること。ズレたらモデルを直して機械的に引き直す — 読み替えない (22 §6)。


1. **測り方に穴があった。**15-M4 〜 20-M4.8 の k スイープは幅ごとに**ブロック数**が固定で、
   k=1 は k=8 の 1/8 の位置しか歩いていない。KV はスイープ中に伸びるので、
   **狭い k ほど浅い文脈で測られていた**。全幅を同じ 384 位置に揃えると、
   text warm 80 スロットの `verify(4)` は **1.78 → 2.1**。
   **20-M4.8 §0 の「ゲート 1.9 を初めて下回った」は、揃えた測り方では成り立たない** (§2)。
2. **ゴール条件は MTP に不利な側だった。**16-M4.5 §5-3 が「25 tok・warm・テキストのみは
   MTP が最も得をしない領域」と書いたのは**逆**で、そこが今のところ最も**得をする**領域である。
   画像 + Reasoning ON + 冷えたキャッシュ (= 単発タスクの実際) で `verify(4)` は **2.44** (§3)。
3. **「ブロックが SSD ミスを畳む」利益は実測でほぼゼロ。**冷えたキャッシュでは
   ミスが初回参照なので和集合では 1 件も減らず (decode 2036 に対し k=4 2014)、
   io の壁時計はむしろ k とともに増える。暖かい側でも、同じ温度で比べると
   ミスは k にほぼ横ばい (k=1 1223 → k=8 1169) である (§4)。
4. **速度比は 1.0 前後に戻る。**ゴール条件の受理長を初めて実測したところ
   (vis: a=0.739 / 1.243 / 1.596)、**vis は math より低く m と同水準**だった。
   これを §3 の費用に入れると **vis は bs=2/3/4 で 0.98 / 1.00 / 0.95** —
   ゴール条件では**損益分岐**である (§6)。20-M4.8 §5 の「math 1.42 倍」は
   §2 の測り方の穴の上に乗っていた。

k=1 についての整理も併せて置く: **1 トークン先読みは運用点ではない** (§5)。
`verify(1) ≤ 1.15` は 16-M4.5 §5-1 が置いた**診断**であって目標ではない。
`verify(k) ≈ 0.79 + 0.35k` (ゴール条件では `0.96 + 0.36k`) と分けると、
**残っている当たりはブロック 1 回の固定費 0.8〜1.0** のほうである。

## 2. 測り方の訂正 — 幅ごとに歩く位置を揃える (**実測**)

15-M4 〜 20-M4.8 のコスト probe は、幅ごとに**ブロック数**を固定していた
(warmup 2 + 計測 16〜18 ブロック)。ブロックは k 位置進むので、**歩く位置数が k に比例する**:
144 位置の stream なら k=1 は 18 位置、k=4 は 72 位置、k=8 は 144 位置しか見ない。
decode 基準線はその間ずっと 144 位置ぶん歩いている。KV はスイープ中に伸びるから、
**狭い k ほど浅い文脈で、decode より手前で測られていた**。

同一セッション・同一バイナリでの A/B (text warm、80 スロット、
`TF_VERIFY_COST_FIXED_BLOCKS=1` が旧、各幅の後ろ側の基準線で割った値):

| 測り方 | k=1 | k=2 | k=4 | k=8 |
| --- | ---: | ---: | ---: | ---: |
| 旧 (ブロック数固定、stream 144 位置) | 1.33 | 1.51 | **1.88** | 3.83 |
| 新 (全幅 144 位置) | 1.13 | 1.36 | **2.04** | 3.50 |
| 新 (全幅 384 位置) | 1.19 | 1.48 | **2.12** | 3.57 |

- **k=8 は両方とも同じ 144 位置を歩く**ので、旧 3.83 対 新 3.50 の差は run 間のばらつきである
  (この機械の振れ幅の範囲)。**系統的に動くのは k=4 と k=2** — そこだけ歩く位置が違う。
- 旧の `verify(4)` = 1.88 は 20-M4.8 §0 の 1.78 を再現している。
  **したがって 1.78 と 2.09 の差はセッション間のドリフトではなく、測り方である。**
- **`verify(4)` は文脈が深いほど上がる**: 72 位置 1.88 → 144 位置 2.04 → 384 位置 2.12。
  ブロックは k 行ぶんの attention を KV 全長に対して回すので、深いほど decode との差が開く。
  ゴール条件の生成長は 384 tok なので、**384 位置の値が判定に使うべき値**である。

## 3. ゴール条件の費用 (**実測**、80 / 48 スロット、384 位置、2 run の中央値)

`verify(k)` を decode ステップ換算で。decode 基準線は各 k の前後で測り直した値の平均。

| 条件 | decode ms/tok | k=2 | k=4 |
| --- | ---: | ---: | ---: |
| テキスト 25 tok・warm (従来のベンチ) | 34.6 | **1.39** | **2.09** |
| 画像 + Reasoning ON・warm | 38.3 | 1.52 | 2.24 |
| 画像 + Reasoning ON・**cold** | 45.1 | **1.65** | **2.44** |
| 画像 + Reasoning ON・warm (48 スロット) | 41.4 | 1.62 | 2.33 |
| 画像 + Reasoning ON・**cold** (48 スロット) | 43.0 | **1.70** | **2.45** |

> **22-GOAL-RESET §4 が生成長を訂正した。**ゴールタスクを上限なしで走らせると
> **868〜1272 tok** (8 枚、全部 `stop=endOfTurn`、中央値 1048) で、本書が採った
> 384 位置はその 4 割である。10-M0 §4 のベースラインが `stop=maxTokens` だったのは
> 思考の途中で切っていたからで、**384 は自然な区切りではなくツマミだった**。
> 本書 §2 が「`verify(4)` は文脈が深いほど上がる」を実測しているので、
> **上の費用は楽観側**である。v1 のベンチは長さに上限を置かない (22 §4)。

- **ゴール条件のほうが費用は高い。**text warm → vision cold で k=4 は 2.09 → 2.44 (+17%)。
  16-M4.5 §5-3 の「25 tok・warm・テキストのみ = MTP が最も得をしない領域」は
  **実測で否定された**。
- 内訳は 2 つ: **文脈が長い** (プロンプト 290 tok + 生成 384 tok に対し、テキスト側は
  25 + 384) ぶんブロックの attention が k 行ぶん効き、**キャッシュが冷たい**ぶん
  ブロックの io が増える (§4)。
- **48 スロットでも比は変わらない** (2.45 対 2.44)。分母の decode も同じだけ遅くなるからで、
  絶対時間では 80 スロットが両方で速い。ただし**ブロックのほうが狭いキャッシュに弱い**
  (§4 の hit 率)。
- probe がゴール条件を再現できているかの確認 (**実測**): 48 スロット・cold の decode は
  hit **91.1%** / io **12.2 ms/pos**。10-M0 §4 のゴール条件実測は hit 93% / io 20.06 ms/tok で、
  同じ領域にいる (probe のほうが少し良いのは、同じプロンプトを 2 回目以降も歩くため)。

> **注意 (**実測**)**: 各 run の最初の decode パスだけはキャッシュを埋めながら走るので
> 他より遅い (例: 38.3 → 32.8 → 32.5 ms/tok)。掃く順で最初に来る幅はその基準線に
> 挟まれるぶん**比が低めに出る**。上の表では k=2 がそれに当たる。§5 の当てはめでは
> 各幅の**後ろ側**の基準線だけを使っている。

## 4. 「ブロックが SSD ミスを畳む」利益の実測 (**実測**)

フェーズごとの expert I/O。384 位置あたりのミス件数と、位置あたりの io 壁時計。

| 条件 | decode | k=2 | k=4 |
| --- | --- | --- | --- |
| 画像・**cold** 80 スロット | 97.8% / 2036 / 8.9 ms | 97.2% / 2021 / 10.1 ms | 96.2% / 2014 / **10.1 ms** |
| 画像・warm 80 スロット | 97.8% / 2036 / 8.5 ms | 98.6% / 999 / 2.8 ms | 98.2% / 957 / 2.5 ms |
| 画像・**cold** 48 スロット | 91.1% / 8161 / 12.2 ms | 88.8% / 8049 / 15.5 ms | 84.9% / 8068 / **18.7 ms** |
| 画像・warm 48 スロット | 91.1% / 8161 / 13.4 ms | 90.3% / 6973 / 11.2 ms | 87.1% / 6901 / 13.0 ms |

読み方に 1 つ注意がいる: **decode の行は各プロセスの最初のパス**である
(記録パスを兼ねるため)。cold でも warm でもキャッシュは prefill 後の状態から始まるので
この行は両者で同一 (2036 / 8161) になり、**warm 側の「decode 2036 対 k=4 957」は
畳んだのではなく温度差である**。同じ温度どうしで比べるには、幅の間で比べる:

| text warm 80 スロット、384 位置あたりのミス | k=1 | k=2 | k=4 | k=8 |
| --- | ---: | ---: | ---: | ---: |
| ミス件数 | 1223 | 1140 | 1157 | 1169 |
| io ms/pos | 2.66 | 2.58 | 2.80 | 3.39 |

- **k を増やしてもミスは減らない。**80 スロットでは作業集合がほぼ入るので、
  k トークンの和集合が節約する fetch はほとんどない。
- **冷えたキャッシュでは畳めないことが原理的にはっきりする**: cold のミスは
  初回参照 (compulsory) であり、**和集合では 1 件も減らない** (2036 → 2014)。
  減らせるのは容量ミスだけで、それは暖かいキャッシュにしか存在しない。
- **io の壁時計はむしろ k とともに増える** (cold 48 スロットで 12.2 → 18.7 ms/pos)。
  ブロックは 1 層あたり最大 `k × topK` = k=4 で 32 本、k=8 で 64 本を*同時に*要求する
  (このモデルは 128 experts / layer、topK=8、30 層)。48 スロットでは k=4 の和集合が
  層キャッシュの 2/3 を占め、**ブロックが自分で前ブロックの中身を追い出す**。
  hit 率も decode 91.1% に対し k=4 84.9% と、**ブロックのほうが狭いキャッシュに弱い**。
  k=8 (最大 64 本) は 48 スロットには原理的に入らない。
- したがって **16-M4.5 §5-3 の「io 側にもう 1 つ利益がある」は取り下げる。**
  利益は測って**ゼロ〜負**だった。**MTP は非 MTP より広い expert cache を要求する**
  というのが、同じ測定の裏返しの結論である (19-M4.7 の 80 スロット採用は正しかった)。

## 5. k=1 は運用点ではない — 固定費と限界費用に分ける (**実測** + **導出**)

同じ位置数で k を掃くと (text warm 80 スロット、各幅の後ろ側の基準線で割った値):

| k | 1 | 2 | 4 | 8 |
| --- | ---: | ---: | ---: | ---: |
| verify(k) [decode ステップ] | 1.19 | 1.48 | 2.12 | 3.57 |

k=2 と k=8 で当てはめると (**導出**):

```
verify(k) ≈ 0.79 + 0.35 k      [decode ステップ]
```

k=4 の予測 2.18 (実測 2.12)、k=1 の予測 1.13 (実測 1.19) — 4 点が 1 本に乗る。

- **0.79 がブロック 1 回の固定費**で、19-M4.7 §4 の `wait.front` (k=1 で 31.5 ms、
  k=4 で 55 ms) がその実体である。**0.35 が 1 トークンぶんの限界費用。**
- **k=1 はこの固定費を 1 トークンにだけ払う形**であり、投機のための先読みが 1 なら
  そもそも投機ではない。**運用範囲は k=2〜4** で、そこでは固定費が 2〜4 トークンに
  割られる。`verify(1) ≤ 1.15` (16-M4.5 §6) はこの固定費を裸で見るための**診断値**として
  読むのが正しく、**中止条件としては k=2〜4 の比で書くべきである** (§7)。
- 固定費を削る仕事と限界費用を削る仕事は別物である。20-M4.8 が削ったのは限界費用側
  (k 行カーネルの活性化) で、**残っているのは固定費 0.79** — 18-M4.6 の系統である。

## 6. 速度比の引き直し — vision タスクの受理長を初めて実測した (**実測** + **導出**)

受理長は 14-M3.5 §4 が math / m / story しか持っていなかったので、
**ゴール条件そのもの (画像 + Reasoning ON、temp 0、384 tok) を `TF_DRAFT_PROBE` で測った**
(**実測**、379 ラウンド、80 スロット):

| プロンプト | a (bs=2) | a (bs=3) | a (bs=4) | 第1ドラフト |
| --- | ---: | ---: | ---: | ---: |
| **vis (本書)** | **0.739** | **1.243** | **1.596** | 0.739 |
| math (14-M3.5) | 0.794 | 1.430 | 1.947 | 0.794 |
| m (14-M3.5) | 0.715 | 1.222 | 1.562 | 0.715 |
| story (14-M3.5) | 0.547 | 0.813 | 0.937 | 0.547 |

**vis は m とほぼ同じで、math より低い。**受理側にゴール条件の割増はない —
費用が §3 で上がったぶんを取り返す材料は受理長にはなかった。
(README が「5 本 (cpp / haiku / math / story / vis) で測る」と書いていた vis がこれである。)
同じ run の実測で `draft_ms=2.84`、`decode io=12.12 ms/tok` (80 スロット)。

1 ラウンド = `verify(k) + (k−1) × 0.098`、産出 = `a + 1` (**導出**):

| プロンプト | text warm 80: bs=2 | bs=3 | bs=4 | ゴール条件 cold 80: bs=2 | bs=3 | bs=4 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| math | 1.14 | 1.19 | **1.22** | 1.01 | **1.09** | 1.08 |
| m | 1.09 | 1.09 | 1.06 | 0.96 | 0.99 | 0.94 |
| story | 0.98 | 0.89 | 0.80 | 0.87 | 0.81 | 0.71 |
| **vis** | 1.10 | 1.10 | 1.08 | **0.98** | **1.00** | **0.95** |

費用は §2/§5 の値 (`verify(2)`=1.48 / 2.12、ゴール条件 1.68 / 2.44)、k=3 は §5 の
当てはめから (1.84 / 2.04)。ドラフター 1 ステップをこの run の実測 (2.84 ms / decode 44.7 ms
= 0.064) に替えると vis は 1.00 / 1.03 / 0.99 で、結論は動かない。

> **22-GOAL-RESET §3 が §5 の当てはめを感度表にした。**`verify(k) ≈ 0.96 + 0.36k` の
> F と M を振ると、**F (固定費) が唯一の大きなレバー**で (半減で e2e 1.29)、
> **受理長 a はもう効かない** (vis を math 並みにしても 1.08) と着手前に言える。
> 4 タスクの幅 0.16〜0.20 に対しレバーは 0.6 なので、**タスクの選び方で結論は
> ひっくり返らない**。`./bench/mtp_budget.py --tasks`。

- **ゴール条件では vis も math も 1.0 前後**で、`tg 30` = **1.48 倍には届いていない**。
  20-M4.8 §5 の「math 1.42 倍、あと一歩」は、§2 の測り方の穴の上に乗っていた数字である。
- **どの条件でも最良の k は 3 前後**で、bs=4 と bs=2 の差は小さい。
  19-M4.7 §6 / 20-M4.8 §5 の「bs を固定しない」という結論は変わらない。
- story は全条件で赤字のままである。
