## 1. 1 トークンあたりの重み読み出し量 (**実測**)

decode はメモリ帯域律速なので、費用は「forward が読む重みのバイト数」で書ける。

| | バイト | 出所 |
| --- | ---: | --- |
| dense (`model_weights.bin` 全体) | 1.5129 GB | ファイルサイズ **実測** |
| routed expert | 240 個 × 3.719168 MB = **0.8926 GB** | 30 層 × top-8、`layer_NN.bin` ÷ 128 **実測** |
| **計** | **2.4055 GB/tok** | |

検算: 150 GB/s なら床は 16.0 ms/tok = 62.5 t/s。`RESULTS_VISION.md` §3 の
32.2 t/s (31.0 ms) は 77 GB/s = ピークの 52%。**帯域律速として整合する。**

240 個/tok は `--dump-expert-trace` の実測値そのもの (30 層 × top-8 = 240、重複なし)。

verify は k トークンを 1 forward で流すので、**dense を 1 回しか読まない**。

| 3 | 502.6 | 167.5 | 0.698 |
| 4 | 596.9 | 149.2 | 0.622 |
| 5 | 683.1 | 136.6 | 0.569 |
| 6 | 765.1 | 127.5 | 0.531 |
| 8 | 883.0 | 110.4 | 0.460 |

ドラフター 1 ステップは 0.236 GB (int4 チェックポイント全体) = **decode の 9.8%**。

## 3. 受理の上限 — タスク別 (**実測**)

D5 (same-seed sample-and-compare) では、位置 t の提案が受理される確率は
`P(ターゲットが引いた 1 個 == 提案)`。提案をどう作っても
**ターゲット自身の抽選分布の最大確率を超えられない**ので、
「ターゲットが argmax を引いた割合」が**任意のドラフターに対する上限**になる。
これはドラフターなしで測れる (§5 の診断)。

384 tok 生成、Reasoning ON、64 スロット、temp 1.0 / top-k 64 / top-p 0.95:

| task | p(argmax) | E[p_max] |
| --- | ---: | ---: |
| C++ 連結リスト | 0.898 | 0.893 |
| 寿司俳句 (PLAN 付録) | 0.917 | 0.918 |
| 三次方程式 (同) | **0.940** | 0.938 |
| デカ妹創作 (同) | **0.810** | 0.811 |
| Vision 1 枚 + 日本語説明 | 0.831 | 0.832 |

**日本語の創作 (story) が最も低く、数式が最も高い。**ユーザの見立てどおり
ライティング系が下限を作るが、その下限でも 0.81 で、事前に懸念した水準
(0.5 前後) ではない。理由は温度そのものではなく**切り落とし**にある:
top-k 64 + top-p 0.95 を通したあとの分布は temp 1.0 でも十分に尖っている。

平均受理長 a の上限 (実際の位置列でラウンドを回した **実測**、独立性の仮定なし):

| task | k=2 | k=3 | k=4 | k=5 | k=6 | k=8 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| cpp | 0.88 | 1.65 | 2.43 | 3.00 | 3.36 | 4.49 |
| haiku | 0.92 | 1.72 | 2.49 | 3.13 | 3.80 | 4.73 |
| math | 0.92 | 1.84 | 2.59 | 3.41 | 4.12 | 5.40 |
| story | 0.81 | 1.53 | 2.00 | 2.46 | 2.76 | 3.22 |
| vis | 0.81 | 1.58 | 2.12 | 2.69 | 3.00 | 3.63 |

速度比の上限 = `(a + 1) / cost(k)`:

| task | k=2 | k=3 | k=4 | k=5 | k=6 | k=8 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| cpp | 1.42 | 1.65 | 1.86 | **1.93** | 1.90 | 2.05 |
| haiku | 1.45 | 1.70 | 1.89 | 1.99 | 2.08 | **2.14** |
| math | 1.45 | 1.78 | 1.94 | 2.12 | 2.22 | **2.39** |
| story | 1.37 | 1.58 | 1.63 | **1.67** | 1.64 | 1.57 |
| vis | 1.37 | 1.61 | 1.69 | **1.78** | 1.74 | 1.73 |

**最適な k はタスクで動く (5〜8)。**創作と Vision は k=5 で頭打ち、
数式は k=8 でもまだ伸びる。**03 D7 の `0|2|3|4` は狭すぎる。**

> これは**完璧なドラフター**(常にターゲットの argmax を提案する) の上限であり、
> 実ドラフターの受理率はこれ以下になる (**導出**)。実値は M3 で測る。

## 4. ゴール条件のベースライン (**実測**)

Vision 1 枚 (853×1280、soft 260 tok) + 日本語説明 + Reasoning ON、384 tok 生成。
Server と同一ランタイムの CLI で測った (Server は Reasoning ON を持たないため、§6)。

```
[stop=maxTokens prefill=304tok new=384tok decode=18.96s tok/s=20.251]
[load=0.708s prefill=4.128s ttft=4.129s peak=6.23GB rss=3.90GB]
[vision images=1 soft=260 tower=1.761s towerLoad=0.003s]
```

| 指標 | 実測 | ゴール | 距離 |
| --- | ---: | ---: | --- |
| pp | 73.6 t/s (tower 込み) / 128 t/s (tower 除く) | 200 t/s | **構造的に未達** |
| tg | 20.3 t/s | 30 t/s | **1.48 倍**必要 (上限 1.78 倍 @ k=5) |
| wall | 25.3 s | ― | load 0.71 + tower 1.76 + prefill 2.37 + decode 18.96 |

スロット数を振ると (Vision タスク、256 tok 生成、**実測**):

| slots | tg | peak |
| ---: | ---: | ---: |
| 48 | 19.4 | 6.24 GB |
| 64 | 19.5 | 8.02 GB |
| 80 | 21.5 | 9.80 GB |

**MTP 以外に tg の伸びしろはほぼない。**80 スロットでも +11% で、
peak が 9.8 GB まで上がる。ゴールの 1.48 倍は MTP でしか届かない。

> 注意: このセッションのテキスト tg は 22〜25 t/s で、`RESULTS_VISION.md` §3 の
> 32.2 t/s より 30% 低い。同 §3 の警告どおり**セッションを跨いだ比較は分解能を持たない**。
> §3 と §4 の表はすべて同一セッション内の値なので、相対比較には使える。

## 5. 参照実装から確定した仕様 (01 §5 の Q1〜Q3)

`scratch/mtp-ref/` の transformers `gemma4_assistant` と mlx-vlm 実装を読んで確定。

| # | 質問 | 決着 |
| --- | --- | --- |
| Q1 | ドラフターに final logit softcap 30.0 を掛けるか | **掛けない (実測)。**HF は `self.lm_head(last_hidden_state)`、mlx-vlm は `embed_tokens.as_linear(h)` の素通し。ターゲット側の 30.0 とは非対称になる |
| Q2 | ドラフターに渡す hidden は `model.norm` 後か | **後で確定 (実測)。**HF は `post_projection(outputs.last_hidden_state)`、mlx-vlm は `post_projection(self.model.norm(h))`。02 §N3 のとおり rmsnorm 1 本の追加が要る |
| Q3 | ドラフト内部の sampling は greedy か | **greedy が最適 (導出)。**D5 が「ターゲットが引いた 1 個と比べる」規則である以上、`P(一致)` を最大化する提案は argmax。参照実装も `supports_greedy_draft_argmax = True` を持つ |

Q4〜Q6 は M2 のまま。

## 6. 途中で見つかった実装ギャップ

**Server に Reasoning ON が無い。**`ServerInference.swift:720` と `:764` が
`applyChatTemplate` を既定 (`enableThinking: false`) で呼ぶだけで、
リクエスト項目も起動フラグもない (`--help` にも無い)。
CLI は `--thinking on|off` を持つ (`Args.swift:319`)。
**ゴールの前提条件なので、MTP とは独立に足す必要がある。**

## 7. 入れた診断 (既定オフ)

`Sources/Tsugumi/Runtime/Generation/AcceptanceProbe.swift` (新規) と
`RawCompletion.swift:282` の 3 行。`TF_ACCEPT_PROBE=<path>` が立っているときだけ、
decode 1 step ごとに「抽選分布 (top-k 64 + top-p を `sample_topk64_final` と
同じ規約で適用し再正規化) の最大確率・引いたトークンの確率と順位」を TSV に出す。

環境変数が無ければ decode 経路のコストは `shared == nil` の判定 1 個。
M3 で実ドラフターの受理率を測るときも、この列と突き合わせれば
**「上限のうち何割を取れているか」**が直接出る。

## 8. 04-PHASES への反映

- **中止条件はクリア。**M1 に進んでよい。
- `03-DESIGN.md` D7 の `--draft-block-size <0|2|3|4>` を **`0|2..8`** に広げる。
  タスクによって最適 k が 5〜8 に動くため。

- M3 の判定は「上限に対する達成率」で見る。上限は §3 の表がすでに与えている。
