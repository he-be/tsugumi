# 24. M5.5 の結果 — ブロックは GPU 律速だった。`wait.front` は往復ではない

測定: 2026-08-18、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3。
対象モデル `scratch/gemma4-qat.gturbo` (drafter 同梱)。触ったファイルは §9。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

23-M5 §7 は「次の 1 段は `wait.front` を削る (30 層ぶんのホスト往復)」と書いた。
**その読みは間違っていた。**本書は計器を 1 つ足してそれを示し、
代わりに出てきた本当の 1 段 — **ブロックの attention カーネル** — を直す。

---

## 0. 結論 — 5 つ

1. **`wait.front` はホスト往復ではない** (§2)。GPU の占有率を測る計器を足すと、
   温まったブロックは **GPU busy 70 ms / wall 86 ms = 81%** である。
   ホストが 68 ms 待っていた相手はほぼ全部**本物の GPU 仕事**
   (前層の MoE + 自層の front) で、キューが空だったのは 15 ms しかない。
   23-M5 §7 の「F 半減 → e2e 1.33」は、この 15 ms から **28 ms** (F=1.33
   decode ステップ ≒ 56 ms の半分) を取り出せるという前提の上に立っていた。
   **ホスト往復を全部消しても届かない。**
2. **比べる相手は decode の占有率だった** (§2)。decode は **busy 25.7 ms / wall 約 38 ms**。
   つまり k=4 のブロックは **decode の 2.7 倍の GPU 仕事**をして 2.9 トークンを出す。
   `verify(4) = 2.53` は「ホストが遅い」ではなく「**GPU 仕事が 2.7 倍**」だった。
3. **差は全部 attention だった** (§3)。投機を止めた 1 行ブロック
   (`TF_MTP_DRAFTS=0`) は GPU busy **40 ms**、同じ 1 トークンを decode は
   **25.7 ms** で出す。内訳を割ると moe / shared / head は**同値**で、
   ブロックの `attn.swa` だけが **15 ms** — decode の attention (約 1.6 ms) の
   **9 倍**で、decode の層前半 30 本ぶん (11.6 ms) より大きい。
4. **原因はカーネルの形である** (§3)。`attention_prefill_causal_qblock_d256` は
   1 simdgroup が 4 クエリを持ち、キー範囲を分割しない。k≤8 では
   threadgroup 16 個・生きている simdgroup は各 1 個 = **512 スレッド**しか走らない
   (プロンプト prefill 用の形をそのまま使っていた)。decode 側は split-KV
   (flash-decoding) で並列度を確保している。
5. **ブロックの attention を decode のカーネルに 1 行ずつ渡した** (§4)。
   M4.5 が router でやったのと同じ手で、同じ副産物が付く — ブロックが
   decode の隣ではなく decode そのもののカーネルを通る。
   温まったブロックは **93 → 72 ms**、GPU busy **70 → 59 ms**、front **34 → 24 ms**。
   スコア (採点基準 v1) は §5。

## 1. 足した計器 — キューが空だった時間 (**実測**、コード)

`PrefillHostProfile` は「ホストがどこで止まっていたか」、`PrefillGPUProfile` は
「どの段が GPU で何秒か」を出していた。**どちらも「止まっている間、GPU は
働いていたのか」に答えない。**23-M5 §7 がそこを推測で埋めた
(「19-M4.7 §5 の k=1 の GPU スパン 11 ms との差はホスト往復のレイテンシ」) のが
本書の出発点である。

`GPUQueueOccupancy` (`Sources/TurboFieldfare/Runtime/Prefill/GPUQueueOccupancy.swift`) は
コマンドバッファ自身の `gpuStartTime`/`gpuEndTime` を集めて**区間の和集合**を取る:

```
busy = 和集合の長さ    idle = span − busy    span = 最初の開始から最後の終了まで
```

和にせず和集合にするのは、ドライバが隣り合うバッファを重ねても二重に数えないため。
`TF_PREFILL_HOST_PROFILE=1` で、ブロック 1 回につき 1 行:

```
[prefill gpuq busy=0.070s(81%) idle=0.015s(19%) span=0.086s buffers=180]
```

同じものを **decode 側にも付けた** (32 ステップに 1 行)。これが本書の要点で、
`verify(k)` は 2 つの壁時計の比でしかなく、**どちらの側が GPU 律速かを何も言わない**。
`TF_PREFILL_GPU_PROFILE=1` を足すと decode も段別に割れる
(`attn` = norm/QKV/RoPE/attention/o/router を積んだ 1 本、`moe`、`shared`、`head`)。

> **落とし穴 1 つ (実測)**: decode の routed バッファは**待たれない**
> (次の層の front を待った時点で完了しているので `waitIfNeeded: false` で
> エラーだけ見る)。素直に「待った所で記録」すると 29 層ぶんの MoE が
> 記録から落ち、その時間が **idle に化ける**。decode の busy が 15 ms に
> 見えていたのはこれで、正しくは 25.7 ms である。

## 2. 測ったこと — ブロックは 81% GPU 律速 (**実測**)

条件は 23-M5 §7 と同じ (`bench/mtp_goal_prompt.json` / IMG_2112 / Reasoning ON /
temp 0 / 200 tok / 80 スロット)。温まった 25 ブロックの中央値:

| | k=4 ブロック | 1 行ブロック (`TF_MTP_DRAFTS=0`) | decode 1 ステップ |
| --- | ---: | ---: | ---: |
| wall | 86 ms | 50 ms | 約 38 ms |
| **GPU busy** | **70 ms** | **40 ms** | **25.7 ms** |
| GPU idle | 15 ms (19%) | 8 ms (16%) | 10〜15 ms (32%) |
| `attn` (層前半 30 本) | 35 | 24 | 11.6 |
| `moe` | 27 | 8 | 7.6 |
| `shared` | 4 | 4 | 3.4 |
| `head` | 3 | 4 | 3.4 |

読み方は 3 つある (**実測** + **導出**):

- **ブロックは GPU 律速。**81% は「ホスト往復を消す」改修の上限が 19% (= 15 ms)
  だという意味で、23-M5 §7 が要求した F 半減 (= 28 ms) はここには無い。
- **decode は GPU 律速ではない** (68%)。expert I/O 待ちとホスト往復で 3 割空いている。
  **投機はその空きを埋める取引**であって、ブロックの GPU 仕事が decode の 2.7 倍
  (70 / 25.7) では埋め切れない。
- **1 行ブロックが決定的**。投機要素がゼロで、産出も 1 トークンで、decode と同じ
  重みを読むのに **40 ms 対 25.7 ms**。`moe` / `shared` / `head` は同値なので、
  差は層前半の **24 対 11.6** に集中している。

層前半をさらに割ると (`TF_PREFILL_GPU_PROFILE=2`、1 行ブロック):

| | qkv | rope | **attn.swa** | attn.full | oproj | post | 計 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 行ブロック | 4 | 1 | **15** | 1 | 2.5 | 2 | 25 |
| k=4 ブロック | 5 | 1 | **21** | 2 | 3 | 5 | 35 |

**`attn.swa` が 15 ms** — 25 層ぶんで、1 層あたり 0.6 ms。同じ KV を decode は
約 1.6 ms (= decode の層前半 11.6 から qkv/oproj/router/norm ぶんを引いた残り、**導出**)
で読んでいる。**帯域の床**は 25 層 × 16 head × 560 tok × 256 × 2 B × 2 (K,V)
= 229 MB ≒ 1.7 ms (**導出**) なので、ブロック側は床の **9 倍**である。

> **訂正 (25-M5.6 §2)**: この床は head 数を **Q head の 16** で数えている。
> SWA の **KV head は 8** なので、正しくは **115 MB ≒ 0.85 ms** である。
> 「ブロック側は床の 9 倍」は「**18 倍**」が正しい。以降の比較は 25-M5.6 の値を使う。

18-M4.6 §3 は「層前半の内訳は qkv 36% / oproj 20% / post 26% / attention 13% で、
ここを触っても GPU 時間はほとんど減らない」と書いていた。**これは短い文脈の
warm text で測った内訳で、ゴール条件では逆転している** (attention 58%)。
attention だけが文脈長に比例して伸びるからである (**導出**)。

## 3. なぜ遅いか — プロンプト用の形のまま k≤8 を通していた (**実測**、コード)

`attention_prefill_causal_qblock_d256` (`Sources/TurboFieldfare/Metal/Prefill/prefill.metal`)
の分割はこうである:

```
threadgroup = 256 スレッド = 8 simdgroup
1 simdgroup = 連続する 4 クエリを担当   → threadgroup は 32 クエリ
grid = ( ceil(queryCount / 32), numQHeads )
```

長いプロンプト (数百クエリ) ではこれが正しい: キー行を 1 回読んで 4 クエリで
使い回すので、K/V のトラフィックが 1/4 になる。**k=4 のブロックでは病的になる**:

- grid.width = 1、grid.height = 16 → **threadgroup は 16 個**
- そのうち生きている simdgroup は `q_first < queryCount` の **1 個だけ** (残り 7 個は即 return)
- 結果、GPU 全体で **16 simdgroup = 512 スレッド**が、それぞれ 560 行のキーを
  直列に舐める。**キー範囲の分割 (split-KV) が無い**ので、それ以上の並列度は出ない。

decode 側 (`Attention.encodeSplit`) は同じ問題を flash-decoding で解いてある:
キー範囲を chunk に割って `head × chunk` 個の threadgroup を立て、2 パス目で
partial を merge する。**ブロックが使っていないのはこれである。**

## 4. 直したこと — ブロックの attention を decode のカーネルに 1 行ずつ渡す

`RealForwardRunner` の chunk 経路で、**投機ブロックかつ span mask 無し**
(生成トークンなので画像スパンは無い) のときだけ、行ごとに decode の
attention を呼ぶ:

```
for row in 0..<t:
    seqLen = startPosition + row + 1          ← 行 row の可視範囲そのもの
    attention.encodeSWA/encodeFull(q: q + row, out: out + row, seqLen: seqLen, ...)
```

- **これは M4.5 が router でやったのと同じ手である** (16-M4.5-PLAN §4)。
  ブロックが decode の「隣のカーネル」ではなく **decode のカーネルそのもの**を通る。
- 行ごとに 2 パスぶんの encoder が増える (30 層 × k × 2)。同じ scratch を使うので
  Metal のハザード追跡で直列化されるが、**1 本 1 本の中の並列度が桁違い**なので勝つ。
- `TF_MTP_ROWS_ATTENTION=0` で旧経路に戻せる (M4.5 系の切り替えと同じ規約)。

A/B (**実測**、同一条件・連続実行、温まった 25 ブロックの中央値):

| | 旧 (`=0`) | **新** | 差 |
| --- | ---: | ---: | --- |
| ブロック 1 回 (wall) | 93 ms | **72 ms** | **−23%** |
| GPU busy | 70 ms | **59 ms** | −16% |
| GPU idle | 23 ms | 13 ms | |
| `attn` (層前半) | 34 ms | **24 ms** | **−10 ms** |
| `moe` / `shared` / `head` | 27 / 4 / 3 | 27 / 4 / 3 | 不変 |
| `wait.front` | 72 ms | 55 ms | |

> **wall の 2 つは同一セッションではない** (2 プロセスの連続実行) ので、
> マシンの温まりと expert I/O の振れが乗っている — 旧側の 93 ms は、
> 同じ設定の別の実行では 83〜86 ms も出ている。**振れないのは GPU 側の
> 70 → 59 ms のほう**で、スコアの判定は §5 の交互 A/B に任せる。

k=4 で attention は約 20 → 約 10 ms になった (行ごとに約 2.5 ms、**導出**)。
**まだ床 (1.7 ms) の 6 倍**である — 行をまたいで KV を共有していないので、
k に比例して伸びる。ここは §7 の宿題として残す。

## 6. 正しさ (**実測**、`TurboFieldfareKernelCheck --verify-block`)

12 cases のうち **11 PASS / 1 FAIL**。落ちたのは分布の比を見るガード 1 本で、
**出力一致のゲートは全部通っている**:

| | 旧 | 新 |
| --- | --- | --- |
| `verify/rows/argmax k=1` / `k=4` | PASS | **PASS** (全位置で decode と一致) |
| `verify/rows/greedy` | PASS | **PASS** (全位置一致) |
| `verify/rows/logits k=4` (tol 8e-2) | 8.3e-3 | **4.0e-2** PASS |
| `rewind/*` 4 本 | PASS | **PASS** |
| `verify/rows/wide-vs-width1` (k=4 の worst / k=1 の worst ≤ 3) | 1.4 PASS | **6.5 FAIL** |

- 中央値は動いていない (1.35e-3 → 1.40e-3)。動いたのは **32 位置中 1 行の worst**
  (pos=28 の i=3) で、値 4.0e-2 は 15-M4 §2 が測ったチャンク経路対 decode 経路の
  既知の帯 (最大 3.8e-2) と同じ桁である。top-1 マージン (3.9e-1) は超えていない。
- **未確認**: この 1 行がなぜ広がるか。split-KV の merge 順で丸めが変わるところまでは
  **導出**だが、行 i=3 だけに寄る理由は説明できていない。ガードの意図
  (「幅を広げたことで増える誤差を検出する」) はまさにここなので、**通ったことにしない**。

## 7. 残っているもの (**実測** + **導出**)

新しいブロックの GPU busy 59 ms の内訳と、それぞれの床:

| 段 | いま | 床 (**導出**) | 差 |
| --- | ---: | ---: | --- |
| `moe` | 27 ms | 約 16 ms (607 expert × 3.72 MB = 2.26 GB / 135 GB/s) | 11 |
| attention | 約 10 ms | 約 1.7 ms (KV 229 MB) | 8 |
| qkv + oproj | 8 ms | 20-M4.8 が帯域床と測った | 0 |
| `post` (norm + router 行ループ) | 5 ms | 約 1 ms (router 720 KB × 30) | 4 |
| `shared` / `head` / `tail` | 8 ms | decode と同値 | 0 |

順に:

1. **attention の行共有** — いまは decode のカーネルを k 回呼んでいるので KV を
   k 回読む。k 行を 1 回の split-KV で通すカーネルを書けば約 3 ms、**−7 ms**。
   → **やった ([25-M5.6-RESULTS.md](25-M5.6-RESULTS.md))。約 1.5 ms、−9 ms** で、
   予測より下に出た。スコアは **1.136 → 1.336** (目標 1.33 に到達)。
2. **`moe` の 11 ms** — 和集合の分だけ読むのは仕方ないが、床の 1.7 倍ある。
3. **`post` の 4 ms** — router の行ループ (30 層 × k dispatch)。

**ホスト往復 (idle 13 ms) は 4 番目である。**23-M5 §7 が 1 番に置いたものが、
計器を足すと 4 番目になった。

## 8. 測り直しの 1 行

採点基準 v1 (スコアはこれだけ):

```
./bench/mtp_goal_ab.py --block-size 4
```

GPU 占有率 (本書 §2 の busy/idle) と段別:

```
TF_PREFILL_HOST_PROFILE=1 TF_PREFILL_GPU_PROFILE=1 .build/release/TurboFieldfareCLI \
  --model scratch/gemma4-qat.gturbo --messages-file bench/mtp_goal_prompt.json \
  --image sample_imgs/IMG_2112.JPG --image-tokens 280 --thinking on --temperature 0 \
  --max-new 200 --expert-cache-slots 80 --verification trusted-install --draft-block-size 4
```

`--draft-block-size 0` で decode 側の同じ 2 行が出る (32 ステップに 1 行)。
`TF_MTP_DRAFTS=0` を足すと 1 行ブロック (§2 の中列)。
層前半の内訳は `TF_PREFILL_GPU_PROFILE=2`。

attention の A/B:

```
TF_MTP_ROWS_ATTENTION=0 …   # 旧 (prefill の query-block カーネル)
```

正しさ:

```
.build/release/TurboFieldfareKernelCheck --verify-block scratch/gemma4-qat.gturbo \
  --verify-block-size 4 --verify-rounds 8
```
