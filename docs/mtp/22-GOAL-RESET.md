# 22. 目標設定のやり直し — 倒れたのは水準だけで、差分は一度も倒れていない

測定: 2026-08-18、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3、commit `8f1aab5`。
対象モデル `scratch/gemma4-qat.moepack`、`sample_imgs/` の 8 枚。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

本書は新しい測定を 1 本 (§4) 足すが、主目的は**採点の仕組みを直すこと**である。
15-M4 から 21 までの 6 本が互いを差し替え続けた原因を特定し、止める。

---

## 0. 結論 — 4 つ

1. **目標は壊れていない。運用が壊れていた。**README「ゴール」は「主眼は wall time」、
   04-PHASES §4 は「ゴール条件の**ループ実測**で判定。warm text のマイクロベンチでは
   判定しない」と既に書いてある。M4.5〜21 の 6 本は、そのどちらも守らずに
   warm text のマイクロベンチと**導出**の速度比で採点していた (§1)。
2. **倒れたのは水準だけである。**21 が差し替えたものを 1 件ずつ見ると、
   同一セッション A/B で取った**差分**は 1 件も倒れていない。倒れたのは
   閾値と比べた**水準** (`verify(4)=1.78 ≤ 1.9` → 達成) と、**条件間の比較**
   (「text warm が最も得をしない領域」) だけである (§2)。
   → ルールは「マイクロを使わない」ではなく **「マイクロは差分として使い、
   閾値と比べない」**。これは principle ではなく、本リポジトリの 6 本で
   実証済みの経験則である。
3. **欠けていたのは感度表である。**「その改修に完全勝利したらスコアが何倍になるか」を
   着手前に出す固定の関数が無かったので、どのマイクロに投資するかが毎回議論になった。
   作った (`bench/mtp_budget.py`、§3)。表が言うのは 3 つ:
   **F (ブロック 1 回の固定費) が唯一の大きなレバー** (半減で e2e 1.29、床付近で 1.58)、
   **受理長 a はもう効かない** (vis を math 並みにしても 1.08)、
   **タスク依存は二次** (4 タスクの幅 0.16〜0.20 に対しレバーは 0.6)。
4. **M5 は存在しない。**`verifyBlock` を呼ぶのは `KernelCheck` の測定ハーネスだけで、
   `SpeculativeVerifier` は `RealForwardRunner` の protocol 適合が付いているだけである
   (**実測**、`grep`)。15-M4 以降の速度比は全部**導出**で、別条件で測った 2 つの proxy の
   積だった。片方が動くと全史が書き換わる — 6 本の巻き直しはこの 1 点に帰着する。

## 1. 何が迷走だったか (**実測**、文書の突合)

**(a) 自分で書いた禁止事項を 6 回破った。**

| 文書 | 書いてあること |
| --- | --- |
| `README.md`「ゴール (2026-08-17 に確定)」 | 「**主眼は wall time で、t/s は目安**」「受理率はタスク依存なので **5 本で測る**」 |
| `04-PHASES.md` §4 | 「ゴール条件 (vision + Reasoning ON) の**ループ実測**で m / vis が 1.2 倍を切る → 停止。**warm text のマイクロベンチでは判定しない**」 |

M4.5〜M4.8 の 4 本は warm text 25 tok のマイクロベンチで採点し、21 はゴール条件に
移したがやはりマイクロベンチ (コスト probe) で採点した。**ループ実測は一度も無い。**

**(b) 中止条件を採点基準に昇格させた。**
`verify(1) ≤ 1.15` / `verify(4) ≤ 1.9` は 04 §4 の**中止条件**、つまり
「下回ったら止める」ための片側の安全弁である。安全弁は通過しても何も意味しない。
20-M4.8 §0 はこれを「**達成**」と書き、21 §2 が測り方の穴を見つけた瞬間に消えた。
`verify(1) ≤ 1.15` は 16-M4.5 で中止条件になり、21 §5 で「診断だった」と読み替えられ、
これが 3 回目の読み替えである。

**(c) 導出を成績表に載せた。**
15-M4 以降の速度比はすべて `verify(k) の実測 × a の実測`。両者は別条件・別ハーネスで
測られており、**条件そのものが効くと後から分かるたびに**全部書き換わった。
21 は実際に両方動かした (位置数の揃え方 §2、ゴール条件 §3、vis の a §6)。

## 2. 21 が倒したものの内訳 — 差分は生き残っている (**実測**)

| 種類 | 例 | 21 のあと |
| --- | --- | --- |
| **差分** (同一セッション A/B) | 18-M4.6 の読み出し先行発行 / 19-M4.7 のスロット 48→80 / 20-M4.8 の `TF_MTP_ROWS_WIDE` 0→1 で k=4 が 2.02→1.78 | **全部生きている** |
| **水準** (閾値と比べた絶対値) | `verify(4)=1.78 ≤ ゲート 1.9 → 達成` (20 §0) | **倒れた** (21 §2 で 2.09) |
| **条件間比較** | 「25 tok・warm・テキストのみが MTP の最悪条件」(16-M4.5 §5-3) | **逆だった** (21 §0-2) |
| **導出の速度比** | 「math 1.42 倍、あと一歩」(20 §5) | **倒れた** (21 §6 で 1.0 前後) |

差分が生き残る理由は構造的である: 21 が見つけた「幅ごとに歩く位置数が違う」バグは
A/B の**両側に同じだけ乗る**ので、比を取ると相殺される。20 §0 の 2.02→1.78 (−12%) は
両側とも旧測り方なので、水準が 1.78→2.09 に動いても**改善幅は動かない**。

**したがって:**

> **マイクロは差分としてだけ使う。閾値と比べない。文書に「達成/未達」欄を作らない。**

## 3. 感度表 — マイクロの差分をスコアに翻訳する (**導出**、`bench/mtp_budget.py`)

差分だけでは「どの差分に投資するか」が決まらない。要るのは固定の翻訳関数と、
着手前に出す上限である。モデルは 21 §5-6 のもので、入力は全部実測:

```
verify(k) = F + M*k                     F=0.96 / M=0.36 (21 §5、ゴール条件 cold 80)
1 ラウンド = verify(k) + (k-1) * 0.098   (21 §6)
産出       = a(k) + 1                    (21 §6 vis、14-M3.5 §4 math/m/story)
e2e 倍率   = 1 / ((1-share) + share / decode 倍率)    share=0.888 (§4)
```

| シナリオ | k=2 | k=3 | k=4 |
| --- | ---: | ---: | ---: |
| **現状** F=0.96 M=0.36 | 0.98 | **1.00** | 0.97 |
| F 半減 (0.48) | **1.29** | 1.24 | 1.15 |
| F→0.20 (床付近) | **1.58** | 1.44 | 1.29 |
| M 半減 (0.18) | 1.20 | 1.28 | **1.27** |
| F 半減 + M 半減 | **1.69** | 1.69 | 1.61 |
| F→0.20 + M→0.18 | **2.23** | 2.07 | 1.90 |
| 現状費用のまま **a を math 並みに** | 1.01 | **1.08** | 1.08 |

(end-to-end 壁時計の倍率。目標 e2e 1.33 に必要な decode 倍率は **1.39**)

- **F が唯一の大きなレバー。**半減で 1.29、床付近で 1.58。**目標 1.33 は
  F 半減 + α でしか届かない。**
- **受理長 a はもう効かない。**vis を math 並み (a(4) 1.596 → 1.947) まで上げても
  1.08 止まりである。**ドラフター側の投資は打ち止め**と着手前に言える。
- **タスク依存は二次である** (`--tasks`):

| F | math | m | vis | story | 幅 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0.96 (現状) | 1.08 | 0.99 | 1.00 | 0.88 | 0.20 |
| 0.48 | 1.33 | 1.28 | 1.29 | 1.17 | 0.16 |
| 0.20 | 1.62 | 1.56 | 1.58 | 1.44 | 0.19 |

  (各タスクの最良 k での e2e 倍率)

  **タスク間の幅は 0.16〜0.20 で一定、対して F のレバーは 0.6。**レバーが幅の 3 倍
  あるので、**タスクの選び方で「その改修が効いたか」の結論はひっくり返らない** —
  k をタスクごとに選ぶ限り (19-M4.7 §6 の「bs を固定しない」のまま)。
  「MTP はタスクで結果がどうにでも変わる」は事実だが、**変わり幅が判定を左右しない**
  ことを表で示せる。
- おまけの予測 (**導出**): **F が下がると最良 k が 3 から 2 に動く。**
  機械的な帰結なので、M5 で答え合わせできる。

## 4. 採点基準 v1 — ゴールタスクの実測 (**実測**)

**8 枚 (`sample_imgs/`) × 固定プロンプト 1 本 (`bench/mtp_goal_prompt.json`、`sample_imgs/caption.py` と同文) / Reasoning ON / temp 0 / 80 スロット / 画像ごとに
プロセスを分ける (単発タスクの実際) / 生成長の上限を置かず `endOfTurn` まで走らせる。**

生成長に上限を置かないのが v1 の要点である。10-M0 §4 が置いた 384 tok は**ツマミ**で、
値を巡る議論が起きる余地を残していた。長さはタスクに決めさせれば議論が消える。
`--max-new 2048` は保険で、**到達したら FAIL** (データ点にしない)。

- **10-M0 §4 のゴール条件ベースライン (384 tok) は `stop=maxTokens` だった** — 思考の

- 参考: Reasoning **OFF** では 174〜289 tok (中央値 200)、decode 比 **61.4%**。
  **Reasoning ON のほうが MTP の効く面積が 1.4 倍広い。**ゴール条件に ON を
  選んだのは正しかった。

## 5. 目標値 — `tg 30 t/s` は変えない。単位を固定する

`tg 30 t/s` は 10-M0 §4 が 20.3 t/s (**48 スロット**) に対して置いた 1.48 倍である。
同 §4 のスロットスイープ (同一セッション) では 80 スロットが 21.5 t/s なので:

| | |
| --- | ---: |
| スロット変更が既に払った分 (MTP と無関係) | 1.11 倍 |
| **MTP に残っている分 (decode)** | **1.40 倍** |
| §4 の長さと固定費を入れた end-to-end (**導出**) | **1.33 倍** |

| | v1 の値 |
| --- | ---: |
| **目標** | ゴールタスク 8 枚の **end-to-end 壁時計比の中央値 1.33 倍** |
| **中止** | **1.10 倍**を切る → 報告して停止 |

- 絶対 t/s は今後**載せない**。比は必ず**同一セッションの MTP on/off 交互 A/B** で取る。
  各文書が「セッション跨ぎは分解能がない」(`RESULTS_VISION.md` §3) と警告しながら
  跨いで比べていた。
- `tg 30 t/s` は情報として残すが、判定には使わない。単位が machine state に依存する。
- **この値は以後変えない。**証拠が「目標が高すぎる」と言ったら、目標を書き直すのではなく
  **未達を報告して止める** (04 §4 の中止条件が本来やる仕事)。

## 6. 運用ルール — 勾配の入れ方

1. **着手前に感度表の行を引く** (`bench/mtp_budget.py`)。完全勝利したときの上限が
   中止条件 (e2e 1.10) を動かさないなら**やらない**。
2. **作業中は同一セッション A/B の差分だけで進捗を見る。**閾値と比べない。
   文書に「達成/未達」欄を作らない。
3. **マイルストーンで M5 のループ実測を取り、感度表の予測と突き合わせる。**
4. **ズレたらモデル (F / M / a / share) を直して、全部機械的に引き直す。**
   文章で読み替えない。← 6 本の巻き直しを止められるのはこの 1 点だけである。
   21 が 20 に対してやったのは 4 ではなく読み替えだった。
5. ベンチの条件を変えるときは **v2 を切って旧数字を測り直す。**

`verify(k)` / `a` / hit 率 / `wait.front` / GPU スパンは**どこに時間があるか**を言う
診断として測り続ける。**達成/未達の欄には二度と入れない。**

## 7. 次

**M4.x の最適化を止めて、M5 (ループ統合) を先に作る。**採点基準が存在しないまま
最適化を続けたことが迷走の原因なので、順番を逆にする。M5 があれば
「固定費 F を削る」も「スロットを広げる」も、**直したらスコアが動くか**で判定できて、
判定基準そのものを毎回発明せずに済む。

M5 のあと、感度表が指す唯一の経路は **F の内訳**である:
19-M4.7 §4 の `wait.front` は k=1・80 スロットで 31.5 ms、うち GPU は 11 ms (同 §5)。
**残り約 20 ms は 30 層ぶんのホスト往復レイテンシ** (**導出**)。F を半分にするとは
この 20 ms を半分にすることで、感度表ではそれが e2e 1.29 に相当する。
**他は触らない** — a も io もスロットも、表の上では中止条件を動かさない。
