# 17. M4.5 の結果 — verify から prefill カーネルを外した

測定: 2026-08-18、M3 Pro 18GB / macOS 15.7.5 / Swift 6.3.3。
対象モデル `scratch/gemma4-qat.moepack`。

表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

---

## 0. 結論 — 費用は 2.1〜2.2 倍下がった。ゲートには届いていない

16-M4.5 §4 の (a)〜(d) を全部入れた。verify の routed MoE・dense 射影・shared
expert・lm_head は **decode のカーネルを k 行に一般化したもの**になり、router は
decode のものそのものになった (§1)。カーネルの正しさは「decode と bit 一致」で
検査してある (§2) — 近似ではない。

費用 (**実測**、warm、decode ステップ換算):

| | k=1 | k=2 | k=4 | k=8 |
| --- | ---: | ---: | ---: | ---: |
| M4 の借り物カーネル | 3.48 | 4.65 | 6.02 | 8.53 |
| **M4.5** | **1.67** | **2.12** | **2.74** | **4.89** |
| 16-M4.5 §3 の予測 (バイトのみ) | 1.00 | 1.23 | 1.55 | 1.99 |

**16-M4.5 §6 の停止条件には届いていない** (`verify(1) ≤ 1.15`、`verify(4) ≤ 1.9`)。
届いていない分の内訳は §4 のとおりで、**GPU の演算ではない**:
k=4 で GPU が使っている時間は予測どおり床の近く (§4) で、
残りは**層ごとのホスト往復と、decode が fused カーネルで済ませている部分**である。

**規定どおり、ここで報告して止める** (§7)。ただし止まっている場所は
16-M4.5 が想定した場所ではない: 演算は予測どおりタダになり、GPU が使う時間は
帯域床の 1.19 倍まで来ている。残っているのは**層の前半がまだチャンク経路である**
ことで、そこは decode なら fused カーネル数本で済む区間である。
続けるかどうかの判断材料は §4 と §7 に置いた。

正しさは M4 と同じ 12 cases が PASS で、verify と decode の数値差は
M4 と同水準かわずかに小さい (§5, §6)。`produce` は 1 命令も変えていない。

## 1. 入れたもの

| # | 内容 | 置き換えた前の姿 |
| --- | --- | --- |
| **a** | `prefill_moe_rows_gate_up_act` / `prefill_moe_rows_down` — 1 SIMD グループが 1 expert の 1 出力行を持ち、その expert に routing された ≤8 行ぶんを一度に回す | 64×64 タイルの `prefill_moe_gemm_int4` (有効行 1〜4 に対して 64 行ぶん計算) |
| **c** | `dequant_int4_gemv_rows_simd` — 同じ重みで k 行ぶんの活性を回す。q/k/v/o 射影と shared expert と logits ヘッドが使う | 射影は 1 行 GEMV を k 回 (重みを k 回読む)、shared expert は 64 行タイルの QMM |
| **b** | `lm_head_greedy_int4_rows_chunk_block` と `PrefillFinalRowHeadInt4.encodeLogitsRows` — 461 MB の lm_head を 1 回だけ読んで k 行ぶんの argmax / logits を出す | 1 行ヘッドを k 回 (461 MB を k 回読む) |
| — | router を decode の `router_gemv_gemma4_bf16_r4` + `router_topk_select_k8` に (行ごとに 1 回) | prefill の router ブロックカーネル。**同じ内積を違う順で畳む**ので、僅差の expert が別に選ばれうる |
| **d** | 層あたりのコマンドバッファ: shared expert を routing 読み戻しの**前**に投げる / tile の完了待ちを次の層まで遅らせる / sorted-pair と argument buffer を使い回す / 常駐 expert の fetch を I/O キューに渡さない | 層ごとに 5〜6 回の commit + wait、tile ごとにバッファ 2 個を新規確保、常駐でもスレッドホップ 1 回 |

`produce` (decode 経路) は**引き続き無変更**。prompt prefill が出す数も無変更で、
新しい経路は `verifyBlock` から来た呼び出し (`speculativeBlock: true`) だけが通る。
唯一の例外は c の k 行 GEMV で、これは 8 トークン以下のチャンクなら prompt prefill も
通るが、**1 行 GEMV を k 回回したのと bit 一致**なので出る数は変わらない (§2)。
各段は環境変数で個別に切れる (`TF_MTP_ROWS_MOE` / `_DENSE` / `_HEAD` / `_ROUTER` /
`TF_MTP_ROWS_PIPELINE` に `0`) ので、A/B は再ビルドなしで取れる。

## 2. 正しさ — 「decode と bit 一致」で検査した (**実測**)

16-M4.5 §0 の主張は「verify は decode の k 行一般化であって別実装ではない」だった。
近似ではなく**同一**であることを、カーネル単位で検査する新しいテストで確かめてある:

| テスト | 主張 | 結果 |
| --- | --- | --- |
| `PrefillRoutedMoERowsVsDecodeTests` | rows 経路の phase1 (gate/up/gelu) と phase2 (down) が decode の `moe_phase1_gate_up_act_u16load` / `moe_phase2_down_reduce_k8` と**要素ごとに一致** | **一致** (F=384 行 × 8 expert、D=576 出力 × 8 expert とも差 0) |
| `DequantInt4GEMVRowsTests` | k 行 GEMV が 1 行 GEMV を k 回回したものと一致 (t=1/2/4/8、2 バイト整列オフセット、ストライド付き、スカラー尾) | **一致** |
| `BlockHeadRowsTests` | ブロックヘッド (greedy / logits) が 1 行ヘッドを k 回回したものと一致 | **一致** |
| `PrefillGroupedRoutedMoETests` (追加分) | 実寸 (D=2816, F=704) で rows 経路の対 CPU 参照誤差が**タイル経路以下**であること、tile を跨いだパイプライン実行でも壊れないこと、行数上限とスクラッチ超過は**計算せずに断ること** | 成立 |

前 2 つが言っているのは「k=1 の verify は、この 4 面については decode と同じ数を出す」
である。タイル経路は dequant した重みを FP16 で置くので、**rows 経路のほうが
参照に近い** (上表 4 行目) 。

## 3. 費用 — 段ごとの実測

`TsugumiKernelCheck --verify-block` の cost 行 (正しさ検査のあと、
expert キャッシュが温まった状態。ms/block、decode は ms/tok):

| 段 | decode | k=1 | k=2 | k=4 | k=8 |
| --- | ---: | ---: | ---: | ---: | ---: |
| M4 (借り物) | 40.2 | 140 | 187 | 242 | 343 |
| + a, c (MoE / dense / shared を k 行に) | 40.1 | 78 | 101 | 138 | 223 |
| + b (ヘッドを 1 回に) | 39.4 | 73 | 92 | 127 | 211 |
| + router を decode のものに | 39.9 | 78 | 87 | 126 | 212 |
| + d (往復を削る) | 40.7 | 54 | 72 | 107 | 207 |
| **最終 (新経路を verify ブロックだけに限定)** | **40.1** | **67** | **85** | **110** | **196** |

**中間の 4 行と最終行は同じ数列を測っていない。**途中の段では新しい経路が
prompt prefill の一部の tile にも入っており、25 tok のプロンプトから出る
生成トークン列が M4 と変わっていた (`verify/baseline/prefill-vs-decode` が
1.762e-03 → 1.637e-02 に動いたのがその指標)。最終形では新経路を
`verifyBlock` 由来の呼び出しだけに閉じたので、**列は M4 と同一に戻っている**。
段ごとの寄与は §3-1 の A/B (同じビルド・同じ列) で読むこと。

decode 側は run ごとに 39.4〜43.2 ms/tok の幅で動く (この機械の既知の drift、
15-M4 §4-4) ので、**比は同じ run の中でだけ読む**こと。

### 3-1. 段ごとの寄与 — 同じビルドで 1 段ずつ切った A/B (**実測**)

`TF_MTP_ROWS_*=0` で 1 段だけ元に戻し、`--verify-cost-only` を回した。
機械が run 内でも drift する (decode が 38〜48 ms/tok で動く) ので、
**それぞれの run の decode で割った比**で並べる:

| 切った段 | k=1 | k=2 | k=4 | k=8 |
| --- | ---: | ---: | ---: | ---: |
| **なし (M4.5 全部入り)** | **1.67** | **1.98** | **2.63** | **4.73** |
| `MOE`=0 (routed MoE をタイル経路に戻す) | 2.44 | 3.32 | 4.29 | 6.54 |
| `PIPELINE`=0 (層あたりの往復を戻す) | 2.07 | 2.41 | 3.00 | 4.95 |
| `DENSE`=0 (射影と shared expert を戻す) | 1.86 | 2.30 | 2.63 | 4.88 |
| `ROUTER`=0 (prefill の router に戻す) | 1.82 | 2.04 | 2.70 | 4.65 |
| `HEAD`=0 (ヘッドを 1 行ずつに戻す) | 1.65 | 2.04 | 2.77 | 4.99 |

読み取れること:

- **(a) routed MoE が圧倒的に大きい** — k=4 で 4.29 → 2.63 ステップ。
  16-M4.5 §2 が「64 行タイルで空回りしている演算」を主犯としたのは当たっていた。
- **(d) の往復削りが 2 番目** — k=4 で 3.00 → 2.63。k が大きいほど効きが薄れる
  (k=8 では 4.95 → 4.73) のは、expert 和集合が増えて 1 層の tile 数が増えるため。
- **(b) ヘッドは k とともに効く** — k=1 では出番がなく (行が 1 本なら
  ブロックヘッドは使わない) 、k=4 で 2.77 → 2.63、k=8 で 4.99 → 4.73。
  461 MB を k 回読む代わりに 1 回読む、という**バイトの効果**そのもの。
- **router を decode のものにする代償はほぼない。**k=1 では逆に速く
  (1.82 → 1.67): prefill の router は 1 行あたり 1 スレッドグループで 128 expert を
  直列に回すので、decode の「expert ごとに 1 SIMD グループ」より遅い。
  行ごとに 1 回呼ぶぶん k とともに不利になり、k=8 でようやく 0.08 ステップの負け
  (4.65 → 4.73)。**買っているのは速度ではなく、ブロックの expert 選択が
  decode の選択と同じであること**である (§5)。
- `DENSE`=0 の k=4 だけ差が出ていないが、この run は decode が
  48.0 → 43.4 ms/tok と run 内で 10% drift しており、**この 1 マスは信用しない**
  (**未確認**)。他の 3 つの幅 (k=1/2/8) では 0.15〜0.32 ステップの寄与がある。

1 ラウンドの費用 = `verify(k) + (k−1) × 0.098` (10-M0 §2) に 14-M3.5 §4 の
実測受理長を入れると、現時点の速度比は (**導出**):

| プロンプト | a (bs=4) | 産出 | 費用 (steps) | 速度比 |
| --- | ---: | ---: | ---: | ---: |
| math (temp 0) | 1.947 | 2.947 | 3.03 | **0.97** |
| m (temp 0) | 1.562 | 2.562 | 3.03 | **0.85** |
| story (temp 0) | 0.937 | 1.937 | 3.03 | **0.64** |

つまり **今の実装ではまだ黒字ではない** (math で損益分岐のわずかに下)。
16-M4.5 §3 の予測 (verify(4)=1.55 → math 1.60) に対して、費用側が 1.77 倍残っている。

## 4. 残っているのはどこか (**実測**)

`TF_PREFILL_GPU_PROFILE=1` で 1 ブロックぶんのコマンドバッファの GPU スパンを
足し上げ、同じ条件の壁時計と並べた:

| | k=1 | k=2 | k=4 | k=8 |
| --- | ---: | ---: | ---: | ---: |
| GPU スパン合計 (中央値/block) | 30 ms | 40 ms | 70 ms | 120 ms |
| 壁時計 | 66 ms | 82 ms | 108 ms | 191 ms |
| GPU が動いていない時間 | 36 ms | 42 ms | 38 ms | 71 ms |
| 16-M4.5 §3 の帯域床 | 38 ms | 47 ms | 59 ms | 76 ms |

(同じ run の `--verify-cost-only`、decode=40.6 ms/tok。GPU スパンは
コマンドバッファごとの `gpuEndTime − gpuStartTime` の和なので、
バッファ間の空白は入らない = 「GPU が動いていない時間」に落ちる)

GPU 側の内訳は k=1 で attn 35% / shared 11% / moe 40% / tail 3% / head 11%
(**実測**) で、バイトから引いた decode の内訳 (attn 10 ms / shared 5 / moe 14 /
head 7、**導出**) とほぼ同じ形である。**k 行に増やした演算は実際にタダだった**
(16-M4.5 §1 の主張は成立)。

残差は **GPU が動いていない時間**で、その正体は層ごとに 2 回残っている
ホスト同期 (routing の読み戻し待ちと、expert スロットを返すための drain) と、
その間に GPU を埋められていないことである。decode は同じ構造でありながら
1 層あたりのホスト時間がはるかに短い: fused カーネルで dispatch 数が少なく、
読み戻すのは 1 トークンぶんの top-8 だけで、tile も binding も argument buffer も
作らない。**この差が今の verify と decode の差のほとんどである** (**導出**)。

## 5. verify と decode の数値差 — M4 と同水準、わずかに小さい (**実測**)

15-M4 §2 が測った「チャンク経路 対 decode 経路」の差は、M4.5 でも**消えていない**。
消えていないこと自体は 16-M4.5 §4 の留保どおりで、attention・RoPE/QKV epilogue・
layer tail・埋め込みはまだチャンク経路のカーネルだからである。ただし
**悪化もしていない**:

(どちらも今日の同じハーネス・同じプロンプト・48 位置。15-M4 §2 の数字は
128 位置の別 run なので直接は比べない)

| | 中央値 (k=4 は i=0..3) | 最悪 | argmax |
| --- | --- | ---: | --- |
| M4 (借り物) k=1 | 1.2e-3 | 1.3e-2 | 128/128 一致 |
| **M4.5 k=1** | **1.2e-3** | **9.8e-3** | **128/128 一致** |
| M4 (借り物) k=4 | 1.2e-3 / 1.4e-3 / 1.3e-3 / 1.7e-3 | 2.4e-2 | 128/128 一致 |
| **M4.5 k=4** | **1.4e-3 / 1.3e-3 / 1.1e-3 / 1.3e-3** | **2.4e-2** | **128/128 一致** |

ブロック内の深さ i に対して平ら、という 15-M4 §2 の観察もそのまま残る。

> **途中の形では平らではなかった** (記録として)。新しい経路を
> 「expert あたりの行数が 8 以下の tile」全部に入れていた段では、prompt prefill も
> 新経路を通り、25 tok のプロンプトから出る**生成列そのものが変わっていた**。
> その列では k=4 の中央値が i=0 の 2.3e-3 から i=3 の 4.1e-2 まで伸び、
> 最悪は 1.3e-1 だった。新経路を `verifyBlock` に閉じて列を M4 と同一に戻すと、
> 上表のとおり平らに戻る。**深さに対する伸びは列の性質であって、
> k 行カーネルの性質ではない** (**導出** — 同じビルドで列だけが違う 2 つの run の差)。
> なお router を decode のものに替える変更は、その列でも中央値を
> 1.29e-2 → 8.1e-3 に下げている: 僅差の expert が両経路で別に選ばれる
> という離散的な差は、実際に効いていた。

**トークンの選択は全条件で一致している** (logits ヘッド 128/128、
fused greedy ヘッド 48/48)。ただし bit 一致ではないので、M5 のゲート 1 は
15-M4 §2-1 が言うとおり「完全一致」ではなく「分岐位置の実測」で書く。

M4 の 830 から +12 は今回足した分である。

## 7. 次 — 04-PHASES の中止条件に照らすと「報告して停止」

16-M4.5 §6 が置いた 2 本の線に対して、実測は

| 条件 | 線 | 実測 | |
| --- | ---: | ---: | --- |
| `verify(1)` | ≤ 1.15 | **1.67** | 未達 |
| `verify(4)` | ≤ 1.9 | **2.74** | 未達 |

**したがって規定どおり報告して止める。**そのうえで、止まっている場所は
16-M4.5 が想定した場所とは違うことを記録しておく:

- **物理 (演算) の側は主張どおりだった。**k 行に増やした演算はタダで、
  GPU が使っている時間は k=4 で 70 ms — 帯域床 59 ms の 1.19 倍まで来ている (§4)。
  15-M4 §5-1 の「実装の余裕がほとんどない」も、16-M4.5 §2 の再解釈のほうが
  正しかったことになる。
- **残っているのは経路の残り半分である。**層の前半 (embed / norm / QKV / RoPE /
  attention / o / post-attn) はまだチャンク経路のカーネルで、decode がそこを
  fused カーネル数本で済ませているのに対し verify は 10 本以上の dispatch と
  1 回のホスト往復を使う。k=1 で GPU が 30 ms しか動いていないのに壁時計が
  66 ms なのは、ほぼこれである (§4)。

続けるなら次の 1 段は「層前半を k 行の decode カーネルに寄せる」で、
見積もりの前に `TF_PREFILL_GPU_PROFILE=2` で層前半の内訳を取ること (**未確認**)。
止めるなら、M4.5 で入ったものは decode 経路を一切変えていないので、
そのまま残して害はない (`verifyBlock` を呼ばない実行のコストはゼロ)。

そのほか、順番が変わらないもの:

1. **k=8 は今のところ割に合わない** (4.89 ステップ)。expert 和集合が増えると
   1 層あたりの tile が増え、d 段の効きが薄れる。16-M4.5 §3-1 の
   「k を 5〜8 に上げる」は層前半を直した後にもう一度測る。
2. **ゴール条件 (vision + Reasoning ON) はまだ一度も測っていない**
   (16-M4.5 §5-3)。ブロックが SSD ミスを和集合に畳む利益が乗るのはそこだけで、
   text-only の warm ベンチは MTP が最も得をしない条件である。
3. ドラフターの group 32 repack (13-M3 §8) は引き続き後。

**測り直しの 1 行**:
`.build/release/TsugumiKernelCheck --verify-block scratch/gemma4-qat.moepack`
(正しさ 12 cases + warm の cost 行)、
`--verify-cost-only` に `TF_PREFILL_GPU_PROFILE=1` を足すと §4 の GPU/壁時計比。
段ごとの A/B は `TF_MTP_ROWS_*=0` (§3-1)。
