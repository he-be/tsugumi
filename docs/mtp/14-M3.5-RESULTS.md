測定: 2026-08-18、M3 Pro 18GB / macOS 15.7.5 / Swift 6.2。
対象モデル `scratch/gemma4-qat.gturbo`。
参照実装は llm-server (V100 32GB + RTX 3090、llama.cpp build 10427 / `650913862`)。

表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

## 0. 結論 — 実装のバグだった。参照実装と並んだ

13-M3 §3 が「こちらの受理率は参照実装のほぼ半分」と書いた差は、**ドラフターの
アテンション出力バッファが 8 倍小さく確保されていた**ことによるメモリ破壊だった
(§1)。壊されていたのは probe がキャプチャしたターゲットの hidden で、その結果
**ドラフターは h をゼロ同然の別ベクトルとして受け取り、トークン埋め込みと共有 K/V
だけで予測していた** (§2-5 の実測)。

直した後の第 1 ドラフト受理率 (**実測**、384 tok、seed 1):

| プロンプト | temp | 修正前 | 修正後 | 参照実装 (§3) |
| --- | ---: | ---: | ---: | ---: |
| math | 0 | 0.503 | **0.794** | 0.810 |
| math | 1.0 | — | **0.847** | 0.790 |
| story | 0 | 0.362 | **0.547** | 0.572 |
| story | 1.0 | 0.460 | **0.517** | 0.496 |
| m (技術説明) | 0 | 0.592 | **0.715** | — |
| m | 1.0 | 0.588 | **0.709** | — |

**参照実装と同水準。**13-M3 §3 の「ドラフターに渡す入力規約に未決着が残っている」
という読みは外れで、規約は最初から llama.cpp と同一だった (§6)。

**bs は 4 で進む** (§5)。

## 1. バグ — `attnOut` の確保サイズ

`Sources/TurboFieldfare/MTP/DraftForward.swift`:

```swift
self.attnOut = try buffer(c.hiddenSize)        // 1024 half = 2048 B
```

アテンションが書くのは `numHeads × headDim` — sliding 層で 16×256 = **4096**、
full 層で 16×512 = **8192** half。1024 に落とすのは後段の o_proj であって、
アテンション自身ではない。**full 層で 8 倍のオーバーラン** (16384 B を 2048 B の
確保に書く) が起き、後ろに並んだ別の確保領域を潰していた。

**ドラフター自身の出力は壊れない** (**導出**、§2-3 の実測が裏づけ)。o_proj は
`qDim` 個を `attnOut` から読むので、はみ出して書いた値をそのまま読み戻す。
辻褄が合ってしまうため、12-M2 の fixture 突合 (100 cases PASS) も、実入力での
参照実装との argmax 一致 94.2% (§2-3) も通っていた。**壊れるのは隣人だけ**で、
その隣人が probe の `hiddenCaptureBuffer` / `prevHidden` だった。

`DraftForward` は現状 probe と `KernelCheck --draft` からしか呼ばれないので
**本番 decode 経路への影響はない**。ただし M4 で decode ループに載せた時点で、
KV なり decode 側のスクラッチなりを踏んでいたはずである。

修正は確保サイズを `numHeads * fullHeadDim` に揃えるだけ (target 側の `attnOut`
は最初からこの規約: `RealForwardRunner.swift:208` の `[N_HEADS * head_dim]`)。

## 2. どう突き止めたか — 証拠の連鎖 (**実測**)

「受理率が低い」から「特定のバッファが特定の encode に踏まれている」まで、
仮説を 1 個ずつ落とした。順序に意味があるので全部残す。

1. **llama.cpp の `draft-mtp` を読んだ。**ペアは (直前行の `h`, `id_last`)、
   RoPE 位置 `n_past`、KV は `0..n_past-1`、ドラフト 2 本目以降は**全部同じ位置**
   (`common/speculative.cpp` の `is_mem_shared` 分岐)。`gemma4-assistant.cpp` に
   `wk`/`wv` は無く、共有先は SWA→`n_layer-2` / full→`n_layer-1`
   (`llama-model.cpp:2380`) — **こちらの 28/29 と一致**。受理規則も
   `common_sampler_sample_and_accept_n` = ターゲットから引いて一致判定で、
   D5 と同じ。13-M3 §3 の「未確認 (rejection sampling かも)」はこれで解消。
2. **参照実装を実測した** (§3)。`--spec-draft-n-max 1` にすると `mean len - 1` が
   そのまま第 1 ドラフト受理率になり、幾何分布の仮定なしに比較できる。
   math の生成テキストは両者ほぼ同一だったので、「タスクの性格が違うから」という
   説明は消えた。
3. **実入力を参照実装にリプレイした。**実機 190 ラウンドの (bonus トークンの埋め込み、
   ターゲットの post-norm hidden、層 28/29 の実キャッシュ、位置、kv 長) を
   そのまま `Gemma4AssistantForCausalLM` に float32 で流した (§9 の
   `TF_DRAFT_DUMP`)。**argmax 一致 179/190 = 94.2%**、受理率は参照 0.4895 /
   実機 0.4842。**カーネルの計算は正しい**、FP16 で失うのは 0.005。
   (修正後に同じ突合を回すと一致 181/190 = 95.3%、参照 0.7789 / 実機 0.7684 —
   関係は変わらず水準だけが上がる。**実測**)
4. **ドラフターの重みを 3 種入れ替えた。**我々の int4 group 64 / 同一チェックポイントの
   bf16 / 別ベンダの int4 group 32 — **全部 0.48〜0.51**。重みでも量子化でもない。
5. **入力をアブレーションした。**ここで決着した:

   | 入力 | 受理率 |
   | --- | ---: |
   | そのまま | 0.4842 |
   | **hidden をゼロに** | **0.4947** |
   | hidden を 1 ラウンド前のものに | 0.5158 |
   | embed をゼロに | 0.0421 |
   | KV を 1 行に | 0.0316 |

   **h はゼロにしても落ちない** = 効いていない。embed と KV は抜くと崩壊するので
   そちらは効いている。さらに、ドラフター自身の `h_next` を代わりに食わせると
   **0.6436** まで上がる — h は本来 +0.15 効く入力で、渡していた h はゼロより悪かった。
6. **pre-norm 側も吐かせて突合した。**同一コマンドバッファ内では
   `post = normalize(pre) ⊙ w` が per-dim 比の CV 0.0002 で一致する
   (= RMSNorm カーネルは正しい)。にもかかわらず、**同じバッファをドラフター実行時に
   読み直すと別物** (cos = −0.001、rms 4.21 → 0.68)。
7. **embed 後 / drafter 後で二分した。**embed の後は無傷 (cos = +1.0000)、
   drafter の後で壊れる (cos = +0.002)。→ `DraftForward.encode` が犯人。
   確保サイズを見て §1 に到達。

修正後、同じ計測で **cos = +1.0000** (ドラフターはターゲットの hidden を
そのまま受け取っている)。

## 5. 速度比と bs (**導出**)

10-M0 §2 の費用モデル (`cost(k)` = 1.32 / 1.60 / 1.85) に §4 を入れる:

| プロンプト | temp | bs=2 | bs=3 | bs=4 |
| --- | ---: | ---: | ---: | ---: |
| math | 0 | 1.36 | 1.52 | **1.59** |
| math | 1.0 | 1.40 | 1.61 | **1.73** |
| m | 0 | 1.30 | 1.39 | **1.39** |
| m | 1.0 | 1.29 | 1.37 | **1.36** |
| story | 0 | **1.17** | 1.13 | 1.05 |
| story | 1.0 | **1.15** | 1.10 | 1.00 |

**bs = 4 で進む。**math で 1.59〜1.73、m (ゴールに最も近い技術説明) で 1.36〜1.39。
story だけは bs=2 が最良 (1.17) で bs=4 は損益分岐 (1.00〜1.05) だが、
bs を落としても 1.17 にしかならず、他 2 本で失う分の方が大きい。
参照実装の実運用設定 (`--spec-draft-n-max 4`) とも揃う。

13-M3 §4 が「最適 k は 3 まで下がる」としていたのは、壊れた h の受理率
(p ≈ 0.66 を仮定した机上値ではなく、実測 0.36〜0.50) で引いた結論なので**無効**。

ゴール (10-M0 §4: tg 20.3 → 30 t/s = **1.48 倍**) との距離:
math は超え、m は 1.39 で **あと 6%**、story は届かない。13-M3 §4 が
「受理率をどれだけ上げても 1.48 倍には上限の 93〜95% が要る」と書いた壁は、
費用モデルはそのままでも**受理率側がそこまで戻った**ことで崩れている。

## 6. 入力規約 — 決着 (13-M3 §6 の撤回)

修正後に同じ 2 次元スイープを引き直した (192 tok、temp 0、bs=4 の第 1 ドラフト受理率、
**実測**):

| | rope −2 | rope −1 | rope 0 | rope +1 |
| --- | ---: | ---: | ---: | ---: |
| story (kv = p) | 0.495 | 0.516 | **0.516** | 0.505 |
| math (kv = p) | 0.770 | 0.781 | **0.770** | 0.738 |

**RoPE 位置はノイズの中**。13-M3 §6 の「`prev-last` が `prev-bonus` に一貫して勝つ」
「1 位置ぶんの回転で math が 21% 動く」は**壊れた h の産物**で、どこかの off-by-one を
打ち消しているという読みも含めて撤回する。§2-1 のとおり llama.cpp と同じ
`prev-bonus` (RoPE = bonus トークン自身、KV = `0..p-1`、ドラフト間は位置固定) が
そのまま正しい。

`TF_DRAFT_PROBE_MODE` の既定は `prev-bonus` のまま。`prev-last` は残すが、
選ぶ理由はもう無い。

## 7. まだ埋まらない差 — bonus トークン自身の K/V 行

同じスイープの `kv = p+1` (bonus トークン自身の行まで attend させる) は今も効く:
story 0.516 → **0.638**、math 0.770 → **0.824** (**実測**)。

**これは使えない** (**導出**)。ドラフトを作る時点で bonus トークンはまだターゲットを
通っていないので、層 28/29 のその行は存在しない。行を作るにはターゲットを 1 手
回す必要があり、それは投機で省こうとしている当のステップである。llama.cpp も
同じ制約下にあり (§2-1)、実際に同水準の受理率で止まっている。
**学習時 (自分の行を見る因果 attention) と推論時の構造的なギャップ**であって、
こちらの穴ではない。
