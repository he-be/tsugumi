# 50. D の賞金 — ページキャッシュの取り分は運用点で `io` の 17〜19%。47 §4 の 10.5 ms は無い

実測: 2026-08-20、M3 Pro 18 GiB / macOS 15.7.5。
[46 §6](46-W3-CODE-ENTROPY.md) が置いたまま未着手だった `F_NOCACHE` の 1 手を、
[49 §10](49-D-P5-RESIDENCY-SET.md) の「次に効くのは賞金側」を受けて実行した。
計器は `PreadExpertStreamer.swift:109` に **env var 1 個** (`TF_EXPERT_NOCACHE`)。
**推論経路のロジックは無改変** (fd フラグを 1 つ立てるだけで、既定は今のまま)。

一次ログは `bench/mtp49/`。**4 条件 × ABBA 3 ラウンド = 片側 n=6**。
ドライバは `bench/mtp49_nocache_ab.py`。

**結論から:**

- **D の賞金は `io` 全体ではない。**`mmap` が消せるのは
  「ページキャッシュ → 私有スロットの memcpy」だけで、**ディスク → ページキャッシュは
  消せない** (`MAP_SHARED` も同じキャッシュを読む)。
  運用点でキャッシュ由来なのは **`io` の 17〜19%** で、
  **D が消せるのは 0.62〜1.08 ms/tok** (**導出**、§4)。
  **47 §4 が置いた「`io` の 3/4 = 10.5 ms/tok」は無い**
- **⇒ D の速度の取り分は壁時計の約 2%** (24.58 → 約 25.1 t/s)。
  **49 §4 が置いたフォールト費用の上限 3.22 ms/tok のほうが大きい。**
  **D の根拠は速度から占有 (私有スロット 3.22 GB) に移る**
- **46 §5 の「この運用点の SSD ストリーミングは、実態としてかなりの割合が
  RAM → RAM の memcpy である」は成り立たない** (§3)。あれは
  「9.09 GB/s が 33 §2 の冷たい天井 6.0〜6.5 を超えている」を根拠にしていたが、
  **キャッシュを迂回させても 9.36 GB/s 出る**条件がある
- **`F_NOCACHE` 自体は製品の札にならない — 符号が条件で反転する** (§2)。
  短い生成では **tok/s +27.1%**、運用点では **−7.7%**。**既定にはしない**
- 迂回は本物である (§5、`vm_stat` で検定)

## 1. 計器 — env var 1 個、ABBA、出力を検定する

```swift
// PreadExpertStreamer.swift、fd を開いた直後
if ProcessInfo.processInfo.environment["TF_EXPERT_NOCACHE"] == "1" {
    _ = fcntl(openedFD, F_NOCACHE, 1)
}
```

腕は 2 つ、違いはこの fcntl だけである。
`temp 0` なのでミスは決定論 (46 §5a) で、ドライバは**毎 run 次の 2 つを検定する**:

| 検定 | 結果 (全 4 条件 × 12 run) |
| --- | --- |
| ミス数が両腕で同一か (= バイトが固定されているか) | **全条件で同一** (例: 9145/61200 が 12 run とも) |
| 生成文の sha256 が両腕で同一か | **全条件で同一** (条件ごとに 1 個の digest) |

⇒ **比べているのは純粋にバイトあたりの費用である。**

`--verification trusted-install` を使っている。既定の `full-sha256` は
**初回に 12 GB をハッシュしてページキャッシュを暖める** (46 §6 の交絡) ので、
測りたいものが先に壊れる。**両腕とも同じ条件なので内部の比較は成り立つ**が、
**既定で運用しているときの値ではない** (**未確認**、§6)。

## 2. 結果 — **符号が条件で反転する** (実測、各 n=6)

| 条件 | ミス/tok | MB/tok | cached `io` | GB/s | t/s | `F_NOCACHE` `io` | GB/s | t/s | **Δ t/s** |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| story / 48 tok / 32 slots | 21.9 | 73.6 | 16.99 ms | 4.33 | 23.23 | **9.05** | 8.14 | 29.52 | **+27.1%** |
| story / 256 tok / 32 slots | 15.0 | 50.4 | 8.57 | 5.88 | 28.72 | **7.42** | 6.80 | 29.87 | **+4.0%** |
| story / 256 tok / 16 slots | 36.0 | 121.1 | 12.88 | 9.39 | 26.70 | 12.94 | 9.36 | 26.64 | −0.3% |
| **math / 256 tok / 32 slots** | **35.9** | **120.5** | **15.51** | 7.77 | **24.58** | 17.84 | 6.75 | 22.70 | **−7.7%** |

**最後の行が運用点である** — 32 スロット (42 §1)、256 tok、35.9 ミス/tok。
45 §4 の運用点 (38.45 ミス/tok、129.2 MB/tok、`io` 14.21 ms、9.09 GB/s、25.80 t/s) と
**同じ regime に居る**。

**バイト率だけでは決まらない。**3 行目と 4 行目は MB/tok がほぼ同じ (121.1 対 120.5) なのに
`F_NOCACHE` の符号が逆である (+0.4% 対 +15.1%)。**何が分けているかは帰属していない**
(**未確認**、§6)。分かっているのは、**運用点ではキャッシュが効いている**ことだけである。

**短い生成では `F_NOCACHE` が 46 §5a の「生成の頭ほど遅い」を消す** (実測):
cached は 48 tok で 23.23 t/s / 256 tok で 28.72 t/s と**長さに従う**のに、
`F_NOCACHE` 側は **29.52 / 29.87 でほぼ動かない**。
46 §5b が「run 中は空きが 0.06 GiB に張り付き、ファイルバックが +3.4 GiB 増える」と
書いた**キャッシュを埋める費用**が、頭の遅さの正体だったと読める (**導出**)。

## 3. **46 §5 の導出は成り立たない** (実測)

46 §5 はこう書いた:

> §4 の 9.09 GB/s は、33 §2 が `F_NOCACHE` で測った冷たい天井 6.0〜6.5 GB/s を
> 超えている (…) ⇒ **この運用点の「SSD ストリーミング」は、実態としてかなりの
> 割合が RAM → RAM の memcpy である**

**3 行目が反例である** — `F_NOCACHE` を立てて**キャッシュを迂回させても 9.36 GB/s** 出る。
9 GB/s はこの機械の SSD が出せる速度であって、キャッシュの証拠ではない。
33 §2 の 6.0〜6.5 は **MTP の verify ブロック・画像プロンプト**の値で、
40 §4-11 が禁じている「条件の違う絶対値の持ち込み」に触れていた。

**キャッシュの取り分は、超過分から推定するのではなく、外して測る。**
外して測ると運用点で **17〜19%** である (§4)。

## 4. **D の賞金の引き直し** (**導出**)

バイトの一部 `f` がキャッシュから (コピー速度で)、残りがディスクから来るとすると

```
io_cached  = f * C + (1-f) * D        C = 全部コピーだった場合の費用
io_nocache = D                        D = 全部ディスクだった場合の費用
⇒ f = (io_nocache - io_cached) / (io_nocache - C)
```

`C` は 48 §3 の暖かい `pread` の対照 (8 エキスパート 26.87 MB を 0.84〜1.26 ms =
**21.3〜32.0 GB/s**) を 120.5 MB/tok に当てて **3.76〜5.66 ms/tok**。運用点の行から:

| | 値 |
| --- | ---: |
| `io` cached | 15.51 ms/tok |
| `io` `F_NOCACHE` | 17.84 ms/tok |
| **キャッシュ由来の割合 `f`** | **17〜19%** |
| **D が消せる量 = `f * C`** | **0.62〜1.08 ms/tok** |
| 今の `io` に対して | **4〜7%** |
| 壁時計 (40.7 ms/tok) に対して | **1.5〜2.7%** ⇒ 24.58 → **約 25.1 t/s** |

**47 §4 の「取り分 36〜40 t/s」は立たない。**48 §12 が既に穴 1 (根拠が 1 本しかない) を
指摘していたが、**穴はもっと手前にあった** — そもそも消せる量が 10.5 ms/tok ではない。

**しかも 49 §4 のフォールト費用の上限 (30 層 × 0.11 ms = 3.22 ms/tok) のほうが大きい。**
上限であって実測の見込み値ではない (production はマッピングを張りっぱなしにする) が、
**賞金 0.62〜1.08 と同じ桁かそれ以上である。**

⇒ **D の根拠は速度から占有に移る。**残っているのは 48 §8 が挙げたうちの:

- 私有スロット **3.22 GB** が消え、残るページは clean file-backed (48 §2)
- **`iogpu.wired_limit_mb` 依存が外れる** (48 §7)
- 暖かい側のコピーは**決定的に 0** (48 §3 の P-2)

**速度の札としては、47 §0 の「冷たい側で負けない」を辛うじて満たす代わりに
暖かい側で 2% 取る、という話になる。**

## 5. 迂回は本物である (実測、`vm_stat`、4 run 交互)

「速くなった」は迂回の証拠にならない (キャッシュに当たったまま別の理由で
速い可能性がある) ので、46 §5b と同じ読み方でファイルバックページの増分を見た。
16 スロット / 256 tok / math ではない story:

| | run 中のファイルバックの増分 | `io` |
| --- | ---: | ---: |
| `TF_EXPERT_NOCACHE=0` | **+506 MB** / +184 MB | 12.66 / 12.63 ms |
| `TF_EXPERT_NOCACHE=1` | **−163 MB** / −172 MB | 12.61 / 12.56 ms |

**立てると増えないどころか減る** (走行中に他が回収していく)。
⇒ **`F_NOCACHE` は UBC を実際に迂回している。**§2〜§4 の前提は成り立つ。

## 6. このプローブが答えていないこと (**未確認**)

- **何が符号を決めるかは帰属していない。**MB/tok がほぼ同じ 2 点で
  `F_NOCACHE` の符号が逆になる (§2 の 3 行目と 4 行目)。スロット数 (16 対 32)、
  プロンプト、作業集合の大きさが交絡している。**軸を 1 本ずつ振っていない。**
- **`--verification full-sha256` (既定) では測っていない。**既定は初回に 12 GB を
  ハッシュしてキャッシュを暖める。**既定で運用しているときのキャッシュ取り分は
  これより大きい可能性がある** ⇒ **§4 の 0.62〜1.08 は下限側に振れている**。
- **45 §4 のプロンプトを再現していない。**運用点の行は `bench/math.json` で
  35.9 ミス/tok、45 §4 は別プロンプトで 38.45。**近いが同じではない。**
- **`C` (全部コピーだった場合の費用) はプローブハーネスの値である** (48 §3)。
  production の並列度 (運用点で 1.2 ミス/層) はプローブの 8 並列と違う。
  **`C` が小さければ賞金はさらに小さくなる。**
- **D 側を直接測ってはいない。**§4 は「`mmap` はコピーを消すがディスクは消せない」
  という構造から引いた**導出**であって、`mmap` の実測ではない。決着は 49 §10 の P-6。
- **`F_NOCACHE` を運用点で立てると遅くなる理由**は測っていない。

## 7. 判断の材料

**D を進める側に残るもの**

- 占有 3.22 GB と `wired_limit` 依存 (§4)。**これは速度と独立に価値がある**
- 暖かい側のコピー 0 は決定的 (48 §3)
- P-5 が通っており、実装の差分は小さい (49 §9)

**D を止める / 後回しにする側**

- **速度の取り分が壁時計の約 2% しかない** (§4)。47 §4 の 36〜40 t/s は無い
- **フォールト費用の上限 (3.22 ms/tok) が賞金 (0.62〜1.08) より大きい** (49 §4)
- 48 §5 のゲートは分解能の内側 (48 §5b) のままで、**冷たい側の余白は無い**
- **フォーマットの探索空間が閉じる** (48 §8) — 承知の上でなら決定である

**`F_NOCACHE` を製品に入れるか**

**入れない。**運用点で **tok/s −7.7%** である (§2)。
ただし**短い生成では +27.1%** なので、**「生成長かキャッシュ充填状態で切り替える」
という枝は開いている** — ただし §6 のとおり**符号を決める軸を特定していない**ので、
**今は測定用の env var として置く以上のことをしない。**
