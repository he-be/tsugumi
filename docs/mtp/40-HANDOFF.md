### 次の 1 手 — **札を 1 枚選ぶ (実装を伴う)**

**N2 は 41 で、N3 は 42 で終わった。**37 §4 の判定条件 (「残り 25 ms/tok の半分以上が
GPU busy なら P2 に進む」) は満たされている (残差の 90〜107%)。
**採点の道具も揃った** — 42 の v2 で、条件・画像・共変量・目盛りが凍結されている。
**N4/N5/N6 は 37 §3 のまま。**

**先に 1 つユーザーに聞くこと (42 §7-3)**: **スコアの定義を e2e 壁時計比のまま行くか。**
42 §4 で、セル 1 個の壁時計比のばらつきの主犯が **on/off の答えの長さの違い**
(相関 −0.910) だと分かった。**16 セルの中央値は頑健だった** (長さの揃う 10 セルだけで
取っても 1.411 対 1.415) ので**基準としては使える**が、**t/s 比のほうが 3 倍きれい**
(sd 0.064 対 0.209) である。22 §5 は凍結されているので、**変えるなら基準を切り直す話**になる。
**42 は両方を必ず並べて報告する形で置いてある**ので、決めずに進むこともできる。

**札は 2 枚。どちらも 41 が開けた** (どちらも実装を伴う):

- **P2 (`moe`、1 日)。**的は `c` = 1 位置 6.4〜6.9 GPU ms の routed MoE。

  `attn` 11.0 で、その **76% が qkv/oproj/post の dense 行列積**である
  (attention 本体は 9.6%)。22 §3 の感度表は「F が唯一の大きなレバー」と言い続けてきたが、

## 4. 落とし穴 (実際に踏んだもの)

1. **n=1 のセルに解釈を書かない。**36 は 188 測定から 3,321 行を書き、
   看板の発見 (§11/§12) が n=1 だった。**反復 3 未満のセルは表に数字を置くだけにする。**
   38/39 はこの規則で書いて **115 / 116 行**に収まっている。
2. **`mtp_cd_sweep.py` の head/tail base は外れ値検出器である。**
   `|head/tail| > 5%` の run は捨てる (39 §3。実際に 1 本捕まえた)。
   36 §9g の 3 規則 (隣接ペア / 反復 3 以上 / 中央値・平均・分布を並べる) に続く 4 つ目。
3. **48 スロットは切り替え直後にページイン費用を払う** (6.78GB 常駐)。
   スイープの前に暖機を 1 本入れる (39 §3)。
4. **温度の既定 (temp 1.0 / top-k 64 / top-p 0.95) がそのまま運用点である。**
   `--temperature 0` を明示すると運用点から外れる。36 §11 はこれで n=1 のまま
   運用点でない条件を測っていた。
5. **macOS の `/bin/bash` は 3.2 で連想配列が無い** (`declare -A` が落ちる)。
6. **`sleep` を Bash ツールのコマンドに直接書くとタスクごと落ちる。**
   待つならスクリプト内に入れてバックグラウンドで投げる。
7. **生ログは必ずファイルにリダイレクトし、`bench/mtpNN/` にコピーしてコミットする**
   (`bench/logs/` は gitignore。`*.log` も gitignore なので `git add -f` が要る)。
8. **`[prefill gpu]` と `[prefill host]` は `tail` と `head` を両方持つ (意味は別物)。**
   同じ辞書に入れると先に読んだほうが上書きされる (41 §7-8 で実際に踏んだ)。
9. **計器は無料ではない。**`TF_PREFILL_HOST_PROFILE=1` + `TF_PREFILL_GPU_PROFILE=1` は
   decode を **1.9〜2.3% 遅くする** (41 §7-1)。速度比を取る run には立てない。
10. **カテゴリ軸を裏口から戻さない。**38 §3 が `register` を `2^H` に置き換え、
    41 §1a が「その `2^H` すら入力ではない」を出した。それでも「主軸となる register を
    決める」という形で 1 度戻しかけた。**選べるのはプロンプトであって、
    出てくるトークン列ではない。**
11. **条件を跨いで数字を突き合わせない。**41 の絶対 t/s は
    thinking off / CLI / 計器 ON。ゴールの `tg ≥ 30` は Reasoning ON / Server。
    **並べた瞬間に嘘になる。**22 §1 が「導出を成績表に載せた」と呼んだ失敗の別の形である。
    **2026-08-20 に 2 度目を踏みかけた** — 39 §2 の「最適 bs=2」(48 スロット / temp 1.0 /
    192 tok) を採点条件 (32 スロット / temp 0 / 生成長無制限) に持ち込もうとした (42 §2d)。
12. **「運用点」を勝手に決めない。**運用は **32 スロット**である
    (`Scripts/demo/serve.py:62`)。39/41 が 48 で測ったのはトレンドのためなのに、
    40 の初版はそれを「運用点」と呼び替えていた。**要件は serve.py とユーザーが持つ。**
13. **反復は画像 (セル) を増やす代わりにならない。**temp 0 では同一画像の run は
    決定論的で、反復が測るのは装置の再現幅だけである。**中央値の n を増やすのは
    セルを増やすこと。**反復は目盛りとドリフト検定に使う (42 §2e)。
14. **e2e 壁時計比は生成長の分岐に開いている** (42 §4)。temp 0 でも on/off が
    文字まで一致するのは 18 本中 4 本で、**セル 1 個の比は相関 −0.910 で長さに従う。**
    **中央値は頑健だが、セル 1 個の比を本文で引いてはいけない。**

## 5. 揃っていない実測どうしの食い違い (**未確認**、揃えるために数字を動かしていない)

1. **計器と本番の `c` が 2.2〜2.7 倍離れている** (costProbe 0.343 対 本番 0.128〜0.155)。
   thinking を外しても消えなかった。**N5 の主題。** (36 §13-2)
2. **32 スロットの投機比 (A 1.355 / B 1.424) が 48 の比 (1.311 / 1.376) より
   両画像とも高い**のに、`c` は 48 のほうが低い。32 側が n=1 で確定していない。 (39 §6-2)
3. **同じ計算の壁時計比が夜をまたぐと 8.6% 動く。**産出トークン・受理・hit は
   ビット単位で再現するのに採点量だけが動く。 (36 §9c(b))
4. **`code` bs=6 の α (0.509) が `ja_prose` bs=6 (0.399) より高い。**
   bs 以外に効く軸が残っている。 (36 §16 末尾)
5. **参照実装との比較は片側が未定義。**llama.cpp の 26.9 ms/tok は
   `llama-bench` の合成列で register が定義されていない。 (39 §4)
6. **48 スロットが 32 スロットより遅く出た** (ja_prose、42.26 対 41.00 ms/tok)。
   ただし 32 を後に回しており、ドリフト (+0.85%) と交絡している。**ABBA が要る。**
   39 §6-3 の符号の不一致と同じ場所である。 (41 §7-2)
7. **`busy` が register でわずかに動く** (+0.5〜0.9 ms/tok)。動くのは `shared` と
   `moe` だけで `attn`/`head` は動かない。並行 pread との競合か、タイル数か。 (41 §7-3)
