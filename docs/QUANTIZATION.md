# 量子化 — このランタイムが選んだ形

**対象読者:** このリポジトリの中身を知らない人。
**前提:** M3 Pro / 18 GB / macOS 15.7.5 **1 台**で速いことだけが目的で、
互換性・移植性・他アーキテクチャへの一般化は最初から狙っていない。

表記は他の文書と同じ **実測(手元)** / **実測(上流)** / **導出** / **未確認**。

---

## 1. 量子化を 3 つの軸に分ける

「4bit 量子化」と一口に言うが、実際には独立した 3 つの選択がある。混ぜると
議論が噛み合わなくなるので、先に分けておく。

### 軸 ① — ビットの配り方

| 方式 | 中身 | 代表 |
| --- | --- | --- |
| 一律 | 全層を同じビット幅にする | `mlx_lm.convert -q --q-bits 4` |
| ルールベース | 層の種類と深さで決め打ちのレシピ | mlx-lm の `--quant-predicate mixed_4_6` など (llama.cpp の Q4_K_M 相当を狙ったもの) |
| **感度計測** | 校正推論で層ごとの敏感さを測ってから配る | mlx-lm の `dynamic_quant`、**oQ**、mlx-optiq |
| 学習時に決める | **量子化後の格子に合うように訓練する** | **QAT** |

oQ の感度は `MSE(float 出力, 量子化出力) / mean(float 出力²)` で、出力の
大きさで正規化するので残差が積み上がる後段の層が不当に敏感に見えない。
最大感度比 50% 以上なら base+4 bit、20% 以上なら +2、それ未満は +1、という
ティア割り当てをして bpw 予算に収める。

### 軸 ② — 重みそのものをいじるか

| 方式 | 中身 |
| --- | --- |
| RTN | 丸めるだけ。上記の大半がこれ |
| AWQ | 量子化前にスケールとクリップを調整する |
| GPTQ | 層出力の二乗誤差が最小になるよう、列ごとに丸めて残りを補正する |
| DWQ | 非量子化パラメータをフル精度モデルからの蒸留で微調整する。時間はかかるが通常いちばん良い |

oQ+ は「感度で配る」の後ろに GPTQ を挟む版で、MoE 向けに**層内の全エキスパートで
Hessian を共有したバッチ GPTQ** を持つ (Qwen3.5-35B-A3B で 90 分 → 6 分)。

**軸 ① と ② は直交する。**「どの層に何ビット配るか」と「そのビットにどの値を
書くか」は別の話で、どちらも**書き出すバイトの値を変えるだけでフォーマットを
変えない。**

### 軸 ③ — 格納フォーマット

| 方式 | 中身 |
| --- | --- |
| **affine** | MLX の既定。`w ≈ scale × q + bias` をグループ単位で持つ |
| mxfp4 / mxfp8 / nvfp4 | 浮動小数点モード。M5 世代の Neural Accelerator 狙い |
| K-quant / IQ 系 | llama.cpp 系のコーデック。mlx-kquant が MLX ネイティブ実装を持つ |
| 独自形式 | JANG など。専用ローダが要る |

**ここだけが互換性を壊す。**①②をどれだけ凝っても出力が affine のままなら
既存のローダで読めるが、③を変えた瞬間に読み手を選ぶ。

## 2. このランタイムが読める形

方式を選ぶ前に、**読める形がそもそも狭い**。制約は 4 つ (実測 = ソース):

1. **affine のみ。**mxfp / K-quant / IQ のカーネルを持たない
2. **group size は 32 か 64 のみ、しかもシェーダライブラリ全体の
   コンパイル時定数**。**1 つのモデルの中で混在させることが原理的にできない**
3. **4-bit と 8-bit のみ。**5-bit / 6-bit のカーネルが無い
4. **routed expert は int4 GEMV しか無い**、かつ 16 KiB ページに揃っていること

さらに **repack は量子化しない。**`.gturbo` への変換はバイトを並べ替えて
ページに揃えるだけで、途中で値を作る余地が無い (ストリーミング install が
range copy + 指紋で成立しているため)。

**つまりこのプロジェクトの立場は「量子化器を書く側」ではなく「既に量子化された
ものを受け取る側」である。**だから軸 ③ は最初から `affine` に固定で、
選べるのは実質 ① と ②、それも**他人が済ませたものを選ぶ**という形になる。

## 3. Gemma 4 の時 — QAT を採った

採用したのは `qat-q4_0-mlx-aligned` (**実測(上流)**、pinned revision):

| | |
| --- | --- |
| ビット配分 | **全部 4-bit / group 32** (オーバーライド無し) |
| 例外 | router のみ BF16 非量子化 |
| 軸での位置 | ①「学習時に決める」+ ③ affine |

**効いたのは軸 ① でも ② でもない。**q4_0 の格子に合うように**訓練済み**という
性質そのもので、後付けの感度割り当てや GPTQ 補正がここに勝つのは難しい。

### 対価は group 32 だった

group 32 は 32 重みごとに scale と bias を 1 組持つので、**重量あたり約 5.0 bit**
(group 64 は約 4.5 bit)。数字にすると 4-bit なのに、実際は 5 bit 相当を運ぶ。

そして速度に出た (**実測(手元)**):

- expert GEMV が **−17〜−25%**
- **メモリを積んでも買い戻せない。**96 スロットまで積むと QAT のヒット率は
  ベースラインを上回る (97.7% 対 95.1%) のに **tok/s は動かない**
- スロットの knee もモデルで違った (ベースライン 64、QAT 48)

それでも採用した。理由は「ゲートを満たしたから」ではなく、**受入指標そのものが
誤っていたと判断したため**である。ここで得た教訓が 2 つあって、後の判断を
ずっと縛っている:

1. **ハーネスが何を暗黙に固定しているかを先に列挙する。**チャットテンプレートが
   `enable_thinking = false` をハードコードしていたせいで、1 回目の測定は
   品質ではなく**指示への追従**を測っており、直したら結論が反転した
2. **tok/s は指標ではない。**測るべきは正解に到達するまでの時間で、答えが
   出なければ再生成 = −100%。実際、同一予算で閉形式に到達したのは QAT が
   2/3、ベースラインが 0/3 で、**tok/s が速いほうが答えに遅かった**

## 4. Qwen3.5-MoE の時 — oQ を「拾って直す」

Ornith-1.5-35B-A3B には QAT が無い。そこで採ったのが
`oQ4e-mtp` を拾って手直しした `oQ4e-g64` である。

### oQ の立ち位置

**独自フォーマットではない。**軸 ① の「感度計測」+ 軸 ② の GPTQ (oQ+) を
やった上で、**出力は普通の MLX safetensors** として書く。手間だけ増えて
読み手は増えない、という設計で、**これがこのプロジェクトにとって唯一
重要な性質**だった。独自ローダが要る系 (JANG など) は、設計思想
(attention を保護し expert を圧縮する) は参考になっても**バイトは使えない**。

### そのままでは乗らなかった 248 本

oQ の割り当てには `num_experts >= 150` なら group 128 を返す規則があり、
Ornith は 256 なので **routed expert 以外が自動的に g128 側に倒れていた**
(**実測(上流)**)。5-bit や 6-bit も混ざる。§2 の制約 2 と 3 に正面から当たる。

やったこと: **非互換 248 本 (533 MB) だけを 8-bit group 64 で打ち直した。**
入力は逆量子化ではなく**上流 bf16 の原本を HTTP range で部分取得** (3.50 GB)。
71.9 GB の全体は引いていない。

| 打ち直した先 | 本数 |
| --- | ---: |
| `linear_attn` 系 (out_proj / in_proj_z / in_proj_a / in_proj_b / in_proj_qkv) | 121 |
| `mlp.shared_expert.*` | 120 |
| `self_attn.{q,k,v}_proj` | 7 |

結果、**routed expert (全体の 83.8%) は 4-bit g64 のまま、周辺だけが 8-bit** と
いう形になった。これは偶然ではなく、oQ の割り当て思想 (routed expert は
「バイトあたりの品質改善効率が悪い」から昇格させない) と一致している。

### 混在ビット幅をどう受けたか

同じモデルの中に 4-bit と 8-bit と BF16 が同居する。manifest は幅を
スロットで持っていたので、そこを**常駐索引からテンソルごとに導く**形に変えた。
**`.gturbo` の形式は 1 バイトも変えていない。**

## 5. ウェイトのダイエット — 何が軽くなったか

Gemma 4 26B-A4B から Ornith 35B-A3B へ移ると、パラメータは増えるのに
**運び方は 3 つの意味で軽くなった。**

### (a) group 32 → 64 で、重量あたり 5.0 → 4.5 bit

同じ「4-bit」でも scales / biases の本数が半分になる。Gemma で 20% を
奪っていた group 32 の重さが、そのまま消えた。

### (b) パディングがゼロになった (**実測(手元)**、3 回バイト一致)

| | エキスパート 1 個 | 16 KiB ページ | 捨て札 |
| --- | ---: | ---: | ---: |
| Gemma 4 | 3.203 MiB | 205 ページ | **13,312 B** |
| Ornith | 1.6875 MiB | **108 ページちょうど** | **0 B** |

ページ揃えのための余りが出ない。読みは 108 ページの連続で、無駄が無い。

### (c) 1 トークンあたりのバイトが 0.78 倍 (**導出**)

エキスパートが「小さく・多く」なったので、top-8 × 層数で運ぶバイトは
4K 文脈の全ヒット時で **2.41 GB → 1.89 GB**。

### そして、心配していた劣化は起きなかった (**実測(手元)**)

エキスパートの母集団は 3,840 → 10,240 と 2.67 倍になり、32 スロットが覆う
割合は 25% → 12.5% に半減する。ヒット率が落ちると予想していたが:

| | Gemma 32 スロット | Ornith 32 スロット |
| --- | ---: | ---: |
| decode hit | 71.0% | **74.9%** |

**ルーティングの偏りが母集団の増加を吸収した。**

### ダイエットと感度割り当ての関係

ここが Gemma → Qwen の本質的な違いである。

- Gemma は **group 32 という「太い格納」を、QAT という「訓練済みの格子」で
  正当化していた**
- Ornith は **group 64 に痩せたぶんの品質を、感度でビットを配ることで
  買い戻している** (embed / lm_head / shared expert / attention / SSM 系を 8-bit に)

つまり「一律に太らせる」から「**要る所だけ太らせる**」への移行であり、
痩せた総量がそのまま速度に出た、という話である。

## 6. ベンチマークの読み方 — 自分の測定にも同じ物差しを当てる

### 他人の数字

- **oQ の公式ベンチは話半分。**2bit で MMLU 14.0% → 64.0%、HumanEval
  0.0% → 78.0% は、比較相手の一律 2bit が単に崩壊しているだけである。
  しかも oQ2 の実効は約 2.9 bpw、oQ4 は約 4.6 bpw で **bpw が揃っていない**。
  意味のある比較は「oQ4 (4.6 bpw) 対 一律 5bit」であって、一律 4bit ではない
- **MLX 本家の検証**は「mixed quant は効くが、**収まるなら group_size を
  大きくして n+1 bit にしたほうがずっとマシ**」という結論を出している
- **壊れたハーネスの差分は何も証明しない。**JANG が 41 ポイント勝ったという
  記事は、同じ記事で bf16 の MMLU が 22.7% (4 択のランダム 25% 未満) と
  出ている時点で測定系が壊れている

### 自分の数字

本線を `oQ4e-g64` に決めた根拠は、同じ文章 4 本の平均 NLL である
(**実測(手元)**、CPU float32):

| 文章 | oQ4e-g64 | 公式 MLX-4bit | 差 |
| --- | ---: | ---: | ---: |
| 日本語散文 | **2.578** | 2.610 | −0.032 |
| 日本語技術文 | **2.520** | 2.634 | **−0.115** |
| 英語技術文 | **2.923** | 2.973 | −0.050 |
| コード (Swift) | **1.298** | 1.316 | −0.019 |

**この測定は上で批判したのと同じ弱点を持っている。**oQ4e-g64 は 21.86 GB、
公式 MLX-4bit は 19.51 GB で、**2.35 GB 多いほうが低い NLL を出したというだけ**
かもしれない。bpw は揃っていないし、標本は 4 本、位置ごとの対比較も取っていない。

したがって、この表から言えるのは:

- ✅ 「**2.35 GB という差額の対価は説明が付く**」— 品質がどの文章でも負けておらず、
  MTP と vision の実物も入っている
- ❌ 「**oQ の感度割り当てが一律配分より優れている**」— これは言えていない。
  言うには同じ bpw で並べる必要がある

## 7. この機械で回せるもの・回せないもの

**oQ を自分で回すのは現実的でない。**感度測定に一時的なモデルロードが要り、
ピークメモリがモデルサイズに近づく。18 GB は「メモリが足りないから量子化
したいのに、量子化にフルロードが要る」の一番苦しいところにある。入力として
上流 bf16 の全体 71.9 GB も要る。

だから実際の戦略はこうなった:

1. **他人が量子化した affine のものを拾う**
2. **§2 の制約に当たる部分だけを、bf16 原本から打ち直す** (248 本 / 533 MB)
3. **焼き込みと名前寄せをして repack する** (`q_norm × 1/16` など)

この 1 が成立するのは、**oQ の出力が普通の MLX safetensors だから**である。
ここが oQ の一番の実務的な価値で、公称のベンチマーク差ではない。

## 8. まとめ

| 論点 | Gemma 4 26B-A4B | Ornith 35B-A3B |
| --- | --- | --- |
| ビット配分 (軸 ①) | 全部 4-bit (QAT) | 感度で配る (oQ) + 打ち直し |
| 重みの補正 (軸 ②) | 訓練時に格子へ合わせる | RTN + imatrix (GPTQ は掛けていない) |
| 格納 (軸 ③) | affine / **group 32** | affine / **group 64** |
| 重量あたり | 約 5.0 bit | 約 4.5 bit |
| ページの捨て札 | 13,312 B / エキスパート | **0 B** |
| 例外 | router のみ BF16 | embed / lm_head / shared / attention / SSM が 8-bit、router が BF16 |
| 32 スロットの hit | 71.0% | **74.9%** |

**選ばなかったもの:** mxfp4 / mxfp8 (カーネルが無い)、oQ2〜3 の低ビット帯
(2/3-bit のカーネルが無い)、K-quant / IQ 系 (同上)、独自フォーマット
(読み手が自分だけになる)、per-expert のビット混在 (`expertStride` の
等間隔前提が壊れる。**原理的に不可能**)。

**残っている道:** 校正データを差し替えたい、あるいは GPTQ も掛けたいと
なったときに「oQ を自分で回す」案がある。**上流 bf16 の全体 71.9 GB を
要求する唯一の用途**なので、やると決めてから引けばよい。
