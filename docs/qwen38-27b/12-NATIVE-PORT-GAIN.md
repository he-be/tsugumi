# 12. Bonsai を自前ランナーに移した場合に縮められる量 — llama-server の子サーバとの比較

2026-09-21、M3 Pro 18 GB。新しい実行は無い。[11](11-GUI-WIRING.md) §6 の 2 セットの記録 (`scratch/bonsai27b/runs/s6-full-set{1,2}/turn-metrics.jsonl`) の
集計と、03〜11 の実測の読み直し。表記は [qwen38/01](../qwen38/01-Q2-FIRST-LIGHT.md) と同じ (実測 / 導出 / 未確認)。

言葉: **子サーバ経路** = 今の形 (アプリが prism フォークの `llama-server` を立てる、11)。**自前経路** = `Qwen38DenseRunner` に PQ2_0 と Hadamard を足して
Tsugumi の中で走らせる形 ([05](05-BONSAI-PQ2-0.md) §11-2)。**縮められる量** = 子サーバ経路の実測値のうち、自前経路に替えることでしか減らせない時間とメモリ。

## 0. 結論

> 追記 (2026-09-21): §6 の 1 と 2 を [13](13-KVQ8-AND-SLOT-SAVE.md) で流し、その結果で 3 と §3 の表と §6 を書き換えた。

1. **1 ターンの時間の 56% は prefill で、ここは自前経路にしても縮まらない。**prefill の 98% 以上は新規トークン (取得したページ) で、
   会話の中の読み直しは 1.8% / 1.1% しかない (§1、実測)。新規トークンの速さ 86.6 / 87.7 tok/s は、行列積の上限から出る 95 tok/s (08 §1、導出) の 9 割。
   自前経路の prefill (逆量子化 → MPS sgemm) の実測は、同じ 27B 構造の IQ3_S で最初の 512 トークンが 54.0 tok/s (GPU 時間だけなら 73 tok/s、04 §3-1、1 回)。
2. **decode (43%) で縮められるのは、1 ステップ 73.9 ms のうち行列積の外の約 15 ms が上限** (08 §5)。全部消えたとして 1 ターン −10% (§2、導出)。
   行列積そのものを自前のカーネルが 128.0 us (08 §3) より速く回せるかは測っていない。**ここが 1 本で測れる唯一の分かれ目。**
3. **メモリは子サーバの引数で取れた。「前の会話に戻る」は引数だけでは取れない** ([13](13-KVQ8-AND-SLOT-SAVE.md)、実測)。
   `-ctk q8_0 -ctv q8_0` は 14 ターン × 2 セットが通り、サーバの RSS の最大が 10.88 / 10.73 → 10.15 / 10.07 GB、decode が 16.3 / 16.4 → 15.8 / 15.9 tok/s (13 §1)。
   `manifest.json` の `server_args` に入れた。`--slot-save-path` の save / restore は動くが、続きの要求が保存した状態の末尾より手前で食い違うと全部読み直しになり、
   実ターンでは新しいターンの最初のラウンド 32 回のうち 6 回がその形だった (13 §2・§3・§3-1)。アプリには入れない (ユーザー決定)。
4. **自前経路で確実に得るのは速さではなく、依存と配布の単純さ** (§4)。失うのは上流追従と、未解決の wired の伸び (04 §3-1) を自分で解く工数 (§5)。
5. 提案: **移植は始めない。先に §3 の 2 つを子サーバで確かめ、decode を詰めたくなった時点で PQ2_0 の GEMV 1 本だけを自前で書いて 128.0 us と比べる** (§6)。

## 1. 1 ターンの時間はどこにあるか (実測、11 §6 の記録の集計)

| | セット 1 | セット 2 |
| --- | ---: | ---: |
| ラウンド数 | 85 | 80 |
| 合計の秒 (11 §6) | 1,551 | 1,317 |
| prefill の秒 (割合) | 870 (56%) | 692 (53%) |
| decode の秒 (割合) | 668 (43%) | 579 (44%) |
| prompt の延べトークン | 809,630 | 624,323 |
| うち cache から (`cachedPromptTokens`) | 734,292 | 563,617 |
| 実際に読んだトークン | 75,338 | 60,706 |
| うち同じ会話で既に読んでいた分 (読み直し、導出) | 1,342 (1.8%) | 650 (1.1%) |
| 読んだトークン ÷ prefill の秒 | 86.6 tok/s | 87.7 tok/s |

- 読み直しは「その会話で直前までに評価済みの長さ」と `cachedPromptTokens` の差。256 トークンを超えたのは各セット 1 ラウンドだけ (1,298 と 608、どちらもターンの最初のラウンド)。
- **会話の中の cache は既に当たっている。**自前経路のチェックポイント ([qwen38/18](../qwen38/18-PROMPT-CACHE-CHECKPOINTS.md)) を持ち込んでも、この 14 ターンの中では 1〜2% しか動かない。
- 測っていないのは **別の会話に移ってから戻ったとき** (11 §7-4)。`--cache-ram 0` なので全部読み直しになるはずで、16K なら約 185 秒 (16,000 ÷ 86.6、導出)。

## 2. decode で縮められる上限 (導出、元の数字は 08 §5)

| | 1 ステップ | decode の倍率 | 1 ターンの時間 (セット 1 の 1,551 s に当てた値) |
| --- | ---: | ---: | ---: |
| 今 (実測、B=1) | 73.9 ms (93 GB/s) | 1.00 | 1,551 s |
| 行列積の外が 0 になった場合 (カーネル単体の 123 GB/s) | 55.9 ms | 1.32 | 1,389 s (−10%) |

- 下の行は到達点ではなく上限。ノルム・GDN・注意・Hadamard (1 トークン 2.16M 要素、05 §3) は自前経路でも残る。
- 行列積の外 1,268 ノードのどれが何 ms かは取れていない (08 §6-2)。自前経路は層ごとに 1 本のコマンドバッファで op をまとめて書ける (04 §1) が、
  それで 15 ms のうち何 ms が消えるかの実測は無い。**別の型の自前経路の数字 (IQ3_S の 0.105 s、04 §3) からの換算はしない。**
- 上の倍率は B=1 のステップから出した。実際の decode は MTP の 2 列のステップ (07 §3) で、行列積の外の割合は測っていない。
- MTP の 2 列の行列積は 08 §4 で多列カーネルを書いて負けている (211.6 対 188.0 us)。ここは自前にしても同じ演算。
- prefill は §0-1 の通り。llama.cpp の行列積は型によらず 5.1〜5.2 TFLOPS (08 §1) で、自前経路の 27B の実測 (54.0 tok/s、1 回) はそれより遅い。

## 4. 自前経路でしか得られないもの

1. **外部のバイナリが要らない。**今は prism フォーク b10709 + 自前の 12 行のパッチ + 有志の MTP 同梱 GGUF の 3 つに依存し、`.app` に同梱していない (10 §5)。
   配布するなら `llama-server` と dylib の署名・公証が増える。自前経路は今の `.app` のまま。
2. **プロセスが 1 系統になる。**子サーバの起動 20 秒・pid ファイル・ポート・`/health`・decode service との切り替え (11 §7-1、未確認) が消える。
3. **速度計と Inspector のメモリ欄が出る。**遠隔クライアントは `runtimeOwnBytes` 0 (§1 の記録でも 0)。
4. **Stop が全経路で同じ形。**強制呼び出しの回 (ストリームなし) の途中の Stop は未確認のまま (11 §7-3)。
5. **op の粒度を自分で決められる** (§2 の 15 ms に手が届く唯一の道)。

## 5. 自前経路で失うもの・払うもの

1. **作るもの** (05 §11-2、04 §1 の「まだ無い」):
   Metal の FWHT (1024 ブロック、±1、`gdn_v_grouped` の並べ替え、`token_embd` の逆向き) / PQ2_0 の GEMV・2 列・prefill 用の逆量子化 /
   MTP ヘッド (Q8_0) と dense ランナーの投機・GDN 状態の巻き戻し / チェックポイント / server・アプリ結線 / Vision の塔。
   `Qwen38DenseRunner` は参照一致までで、MTP・チェックポイント・巻き戻しは無い。
2. **04 §3-1 の wired の伸びが未解決。**IQ3_S (12 GB) の 4K prefill で wired 17.05 GB まで伸びて見張りが止めた。原因は特定していない。
   Bonsai は 7.66 GB なので同じにはならないはずだが、未確認で、解くのは自分になる。
3. **Tsugumi の持ち味が効かないモデル。**全部常駐の dense で、SSD からの expert 読み・先読み・I/O を計算の裏に隠す構造を使う場所が無い。
   残るのは素の dense の行列積で、08 が示す通り llama.cpp が既にこの機体の上限近くで回している。
4. **上流に追従できなくなる。**Prism が次の型・次のモデルを出すたびに移植し直す。子サーバ経路ならバイナリの差し替えで済む (07 のパッチは 12 行)。
5. 12 行のパッチで 1.30 倍を拾えたのは、`test-backend-ops perf` と `batched-bench` があったから (07)。自前経路ではこの計測器も自前になる。
