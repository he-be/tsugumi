# M6 mini 256GB の SSD は 3.34 GB/s が天井 — M3 Pro 1TB の半分

測定: 2026-09-22（受領当日）。**M6 mini** Mac18,5 / M6 12 コア / 16GB / **APPLE SSD AP0256Z** / macOS 27.0 (26A428)、
**M3 Pro** Mac15,6 / 18GB / **APPLE SSD AP1024Z** / macOS 15.7.5。両機とも同じプローブ・同じ幾何・同じ 66 GB のデータセット。
表記は PLAN 系と同じ: **実測** / **導出** / **未確認**。

[M6_MAC_MINI_TARGETING.md](M6_MAC_MINI_TARGETING.md) §7 の「実機で最初に取る 5 つの数字」の **#2**（`F_NOCACHE` での SSD 帯域、
「512 GB を買うべきかの唯一の根拠」）に対する答えである。#1・#3・#4・#5 はまだ取っていない（Xcode が未インストール）。

## 0. 結論 — 5 つ

1. **M6 256GB の読みは 3.34 GB/s で頭打ち**（**実測**、§2）。M3 Pro 1TB は 6.68〜6.75 GB/s なので、**ちょうど半分**である。
2. **ランダム読みのせいではない**（**実測**、§2-3）。64 MB のシーケンシャルでも 3.34 GB/s。**これは device の天井**であって、アクセスパターンの問題ではない。
3. **キュー深さは 1 ミリも効かない**（**実測**、§2-1）。深さ 1 → 64 で 2.90 → 3.33 GB/s、QD20 のレイテンシは QD1 のきっかり 20 倍。
   M3 Pro は深さ 1 → 16 で 4.41 → 6.16 と伸びる（帯域に余裕がある）。
4. **コントローラは遅くない。NAND のダイ数である**（**実測** + **導出**、§4）。16 KB QD1 のレイテンシは **M6 のほうが速い**（0.074 vs 0.099 ms）。
   世代は新しく、レイテンシも良い。足りないのは並列度で、それは容量で買うもの。**512GB なら約 2 倍という推測は妥当だが未測定**（**未確認**）。
5. **外付けで逃げられない**（**実測**、§4）。この M6 mini の Thunderbolt は **40 Gb/s（TB5 ではない）** で、
   外付け NVMe の実効は 3 GB/s 前後 = 内蔵と同じ。容量を買う以外の手がない。

**試算への波及（§5）: `M6_QWEN38_FLASH_NEXT.md` §3 は SSD を 5〜8 GB/s と置いていた。実測 3.0〜3.36 で引き直すと、
16GB + 256GB の M6 は Flash-Next で約 8 tok/s（直列、導出）になり、手元の M3 Pro（9 tok/s）を下回る。**

## 1. 測り方 — データセットは RAM より十分大きくすること

プローブは 2 本。`bench/io_depth_probe.c` は [33 §1](../mtp/33-M8-IO-FLOOR.md) のものをそのまま使った（同時エキスパート数 × 分割数を振る）。
`bench/rec_probe.c` は新規で、[QWEN38_FLASH_NEXT_VERIFY_PLAN.md](QWEN38_FLASH_NEXT_VERIFY_PLAN.md) D3 の形（レコード長 × QD、p50 / p99）を測る。
`bench/gen_dataset.c` は xorshift ノイズでデータセットを作る（sparse でも clone でもない実体）。

```bash
clang -O2 -o gen_dataset gen_dataset.c
clang -O2 -o rec_probe rec_probe.c -lpthread
./gen_dataset data 31 2149580800        # 31 層 × 2.15 GB = 66.6 GB
NOCACHE=1 RDAHEAD=0 ./rec_probe data 3358720 10 25
NOCACHE=1 RDAHEAD=0 ./io_depth_probe data 30 640
```

> **最初 12 GB のデータセットで測って 2 倍速い値が出た。全部キャッシュだった。**
> 1.49 MB を QD1 で p50 **0.050 ms** = 30 GB/s は PCIe リンクより速く、RAM からしか出ない値である。
> **`F_NOCACHE` は新規キャッシュを止めるだけで、既に常駐しているページは使われる。**
> 12 GB のデータセットは 16 GB RAM の M6 に収まってしまう。**66 GB に増やしたら両プローブが一致した**
> （3.36 MB QD1 で rec_probe 1.104 ms / io_depth 1.159 ms）。以下の数字はすべて 66 GB 版である。
>
> 同じ疑いは [33 §1](../mtp/33-M8-IO-FLOOR.md) の M3 Pro 表（12 GB のデータセット / 18 GB RAM）にもかかるので再測した。
> **66 GB で 4.41 → 6.16 GB/s、33 §1 の 4.03 → 6.04 と一致する。あの表は正しかった**（**実測**、§2-1）。

## 3. §7 #2 への答え

**512GB を買う意味はある**（SSD ストリーミングを続ける場合）。根拠は §0-4 のとおり:

- 16 KB QD1 のレイテンシは M6 のほうが **速い**（0.074 vs 0.099 ms）ので、コントローラ・NVMe リンク・OS のせいではない。
- にもかかわらず帯域は半分で、**QD を上げても増えない**。これは同時に動かせる NAND ダイが少ない形である。
- 容量はダイ数で決まるので、512GB（ダイ 2 枚）なら **約 2 倍** が期待値。ただし**実機が無いので未確認**。

[M4 mini の 256GB は遅くない](https://softantenna.com/blog/m4-mac-mini-ssd/)（M6 文書の出典）という前例は **M6 では成立していない**。
Apple の「前世代比 2 倍」も 256GB 構成には当てはまらなかった（**実測**）。

**外付けは代替にならない**: `system_profiler SPThunderboltDataType` は **40 Gb/s**（TB5 ではない）。TB4 の実効上限は §6 の実測で 4.72 GB/s だが、
外付け NVMe ケースは TB4 プロトコルのオーバーヘッドで 3 GB/s 前後に落ちるのが通例で、内蔵（3.34）を上回らない（**導出**）。

## 4. 試算への波及（**導出**）

### 4-1. Flash-Next

[M6_QWEN38_FLASH_NEXT.md](M6_QWEN38_FLASH_NEXT.md) §3 は SSD 項を **5〜8 GB/s**（「M6 mini は前世代比 2 倍（公称）」）と置いていた。
実測 **3.0〜3.36** で引き直す。ついでに §3 の表は DRAM を 170 GB/s（= 24/32GB 構成）で計算していたが、
**16GB 構成は 153 GB/s** なので実効 115 GB/s で引き直した（hit 0.72 → DRAM 3.68 GB ÷ 115 = 32 ms）。

| 構成 | hit | SSD ミス/tok | DRAM | SSD | 直列合計 | **tok/s（直列）** | 重なった場合 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 文書の想定（16GB、5〜8 GB/s） | 0.72 | 0.27 GB | 28 ms | 34〜54 ms | 72〜92 ms | 11〜14 | 16〜23 |
| **16GB + 256GB（実測 3.3）** | 0.72 | 0.27 GB | 32 ms | **82 ms** | 124 ms | **約 8** | 11 |
| 16GB + 512GB（6.7 と仮定、**未確認**） | 0.72 | 0.27 GB | 32 ms | 40 ms | 82 ms | 12 | 20 |
| 32GB + 256GB（実測 3.3） | 0.87 | 0.13 GB | 29 ms | 39 ms | 78 ms | 13 | 20 |
| 32GB + 512GB（6.7 と仮定、**未確認**） | 0.87 | 0.13 GB | 29 ms | 19 ms | 58 ms | 17 | 25（全常駐の天井） |
| 参考: M3 Pro 18GB（§3-3） | 0.76 | 0.23 GB | 33 ms | 48 ms | 108 ms | 9 | — |

**受領した 16GB + 256GB は、Flash-Next に関しては手元の M3 Pro を下回る。**
128k 埋め切り平均で読むならここからさらに 3 割引き（§3-2）で **約 6 tok/s**。

hit 0.72 / 0.87 は D1（キャッシュシミュ）が未了なので**外挿のまま**である。実測 SSD を入れた今、
**ミス 1 回の値段が上がったので、RAM を足す取り分も以前の試算より大きい**（16 → 32GB で 8 → 13 tok/s、以前は 11〜14 → 15〜18）。

### 4-2. Tsugumi 本線（Gemma / Ornith）

[33](../mtp/33-M8-IO-FLOOR.md) の結論は「48 スロットでは I/O はもう床ではない、GPU が床」だった（M3 Pro、io 2.73 s / GPU 合計 13.44 s）。
M6 では **SSD が半分・GPU は M6-2 で速くする**ので、**I/O が再び床に戻る**可能性が高い（io 2.73 → 約 5.5 s、GPU 13.44 → 7 s 目標、いずれも**導出**）。
M6-2（expert GEMM の `matmul2d` 化）の A/B を取るときは、**io と GPU を分けて読むこと**。混ざると「tensor ops が効かなかった」と誤読する。

## 5. Thunderbolt 4 ブリッジ（母艦 ↔ M6、**実測**）

大容量転送用に TB4 ケーブルで直結した。`ifconfig` の `media` は Thunderbolt Bridge では `autoselect` としか出ないので実測した。

| 経路 | 実測 |
| --- | ---: |
| 生 TCP（M3 Pro → M6） | **4.72 GB/s = 37.8 Gb/s**（リンクの 94%） |
| 生 TCP（M6 → M3 Pro） | 4.67 GB/s = 37.4 Gb/s |
| ssh 既定（chacha20-poly1305） | 0.39 GB/s |
| **ssh + aes128-gcm** | **2.15 GB/s** |
| 有線 LAN（`m6-lan`、1000baseT） | 0.11 GB/s |

**ssh の既定暗号が TB4 の 8% しか使えていなかった。**AES-NI の効く `aes128-gcm` で 5.5 倍になる。
母艦の `~/.ssh/config` の `m6-tb`（169.254.24.129、リンクローカル自動割り当て）に `Ciphers aes128-gcm@openssh.com` を入れた。
scp / rsync もこれを継ぐ。MTU は 1500 のままで 37.8 Gb/s 出ているので、ジャンボフレーム化は不要。

実転送は **M6 の SSD 書き込み 1.41 GB/s が床**になるので、ssh 経由で既にディスク律速である。生 TCP を使う理由はない。

> 罠: macOS の `nc` は 80 KB で接続を切ってしまい、帯域測定に使えない。Python の素の TCP で測った（`bench/tbsink.py`）。

## 6. 未確認リスト

1. **512GB 構成の実速度。**「ダイ 2 枚で約 2 倍」は推測にすぎない。
2. **production の fd フラグ（`NOCACHE=0 RDAHEAD=1`）での 66 GB 版。**12 GB 版では深さ 32 で 9.93 GB/s まで伸びたが、
   これはキャッシュ込みの値で、33 §1 の第 2 表と同じ二重天井の形。66 GB で取り直していない。
3. 1.84 MB / QD1 の p99 外れ値（10.8 ms）の原因。
4. M6 の SSD が熱で落ちるかどうか。今回は最長 47 秒の連続書き込みと 25 秒 × 12 本の読みで、劣化は見えていない。
5. §7 の #1・#3・#4・#5（Xcode 未インストールのため未着手）。

## 7. 再現手順

プローブは M6 の `~/ssdprobe/` にも置いてある（ソース 3 本 + バイナリ 3 本）。**データセット（66 GB）は測定後に消した**ので、
`./gen_dataset data 31 2149580800` で作り直す（47 秒）。**12 GB のような RAM より小さいデータセットで測ってはいけない**（§1）。
