# 調査: コーディングエージェント (pi) から使ったときの TTFT とツールループ

作成: 2026-08-16
スコープ: 調査のみ。ソース・ランタイム既定・モデルファイルは一切変更していない。
表記は PLAN.md に合わせる: **実測** / **導出** / **未確認**

対象は `pi` v0.84.2 (`openai-completions` アダプタ) から
`TsugumiServer` を使ったときに観測された 3 つの症状。

---

## 1. 結論 (要約)

| # | 症状 | 原因 | 位置 |
| --- | --- | --- | --- |
| A | pi 起動後の 1 発目が 55-99 秒 | プロンプトキャッシュは**直前の会話をそのまま延長した場合しか**効かない。同じシステムプロンプトでも新しい質問で始まると再利用ゼロ (**実測**) | `ServerPromptCache.swift:101`, `:110` |
| B | 会話の途中で突然フル再プレフィルが再発する | 同一のツール呼び出しを 2 回すると、継続ブリッジの「一致はちょうど 1 個」ガードが例外を投げてキャッシュを捨てる (**実測**) | `Tokenizer.swift:428` |
| C | bash コマンドをテキストで提案するだけで実行しない | モデル挙動。ハーネス側のシステムプロンプトに明示規則を 1 文足すと 0/16 → 12/12 に直る (**実測**) | — |
| 付 | そもそも pp が 50-64 tok/s と遅い | GPU の計算律速ではない (ピークの約 6%、**導出**)。チャンクサイズにも無反応 (**実測**) | — |

A と B はどちらもサーバ側の挙動。C はサーバの問題ではない。

## 3. 症状 A: セッション開始のたびに全文プレフィル

### 3-1. 実測

同一のシステムプロンプト (2081 トークン) を共有し、最初の user だけを変えた:

| リクエスト | wall | prompt | cached |
| --- | ---: | ---: | ---: |
| session1 1 ターン目 | 42.91 s | 2084 | 0 |
| session1 2 ターン目 (同じ履歴 + 新しい user) | **1.45 s** | 2110 | **2090** |
| session2 1 ターン目 (**同じ system**・別の質問) | 41.11 s | 2081 | **0** |
| session3 1 ターン目 (**同じ system**・別の質問) | 41.51 s | 2081 | **0** |

pi のシステムプロンプトは 8134 文字 ≈ 2650 トークン (**実測**、プロキシ記録) なので、
**pi を起動するたびに必ず 55-99 秒**を払う。ユーザー報告の 75.8 秒 (prompt=2654)
はこれ。2 ターン目以降が速いのは KV が効いているため。

### 3-2. 原因

`ServerPromptCache.match` の再利用条件は 2 つしかない (`ServerPromptCache.swift:86-131`)。

1. `:101` — 新しいプロンプトが**保持中の KV 全体**を丸ごと前方一致で含む
2. `:110` — 保持中の会話に、その続き (user 追加 / tool 結果) だけが足されている

どちらも「保持中の KV 全体」が前提で、**共通接頭辞ぶんだけ再利用する経路がない**。
新しいセッションの 1 発目は、system が同一でも直前の会話の assistant 応答で
分岐するため、必ず `.miss` → `promptCache.invalidate()` → 全文プレフィルになる
(`ServerInference.swift:498-512`)。

`docs/OPENAI_SERVER.md` の「Prompt reuse」は仕様どおりの記述だが、
「保持している接頭辞をそのまま延長したときだけ」という条件は読み取りにくい。

### 3-3. 直すとしたら

最長共通接頭辞での部分再利用が要る。ただし KV を短い位置へ巻き戻す API がない:
`RealForwardRunner.prepareForContinuation` は `kv.position == expectedPosition` を
厳密に要求する (`RealForwardRunner.swift:411`)。また SWA 層は
`fp16RingEnabled` 時にリングバッファなので、巻き戻せる範囲に構造的な上限がある
(`KVCacheManager.swift`)。**未確認**: リング有効時に安全に巻き戻せる位置の下限。

## 4. 症状 B: 会話の途中で突然フル再プレフィルが再発する

### 4-1. 実測 (pi の実走)

pi に `proj` ディレクトリを調べさせた 1 セッション = 19 リクエスト。
履歴は最初から最後まで追記のみで、pi が送り直した assistant メッセージは
サーバがストリームした tool_call と**全ターン一致**していた (プロキシ記録で照合)。
それでも途中で 1 回だけ止まった:

```
08:45:01 completed in  1.693s prompt=3466 cached=3450 finish=tool_calls
08:46:41 completed in 99.317s prompt=3440 cached=0    finish=tool_calls   <-- 停止
08:46:44 completed in  2.859s prompt=3498 cached=3457 finish=tool_calls
```

停止した回の直前 2 ターンで、モデルは `read {"path":"notes.txt"}` を
**2 回続けて**呼んでいた。

### 4-2. 原因

チャットテンプレートはツール呼び出しを
`<|tool_call>call:` + 名前 + `{` 引数 `}` + `<tool_call|>` として描画し、
**呼び出し ID を含めない**
(モデル同梱の `scratch/gemma4-qat.moepack/tokenizer/chat_template.jinja:246`)。

継続ブリッジ `GFTokenizer.encodeToolResultContinuation`
(`Tokenizer.swift:408-438`) は、キャッシュ側の assistant のツール呼び出し
トークン列を会話全体から**部分列検索**し、

```swift
guard matches.count == 1 else {
    throw GFTokenizerError.invalidChatTemplate(
        "cached assistant tool-call boundary is ambiguous")
}
```

一致が 1 個でなければ例外を投げる (`Tokenizer.swift:428`)。
同じ名前・同じ引数の呼び出しが履歴に 2 回あると一致は 2 個になり、
`matchToolContinuation` が `.miss` を返して全文プレフィルに落ちる。

### 4-3. A/B で確定 (**実測**)

他の条件を完全に同一にし、履歴に仕込む先行呼び出しだけを変えた:

```
CONTROL 先行呼び出し = bash {"command":"pwd"}  -> 継続 cached=136  HIT
CASE    先行呼び出し = bash {"command":"ls"}   -> 継続 cached=0    MISS (フル再プレフィル)
```

生成された呼び出しはどちらも `bash {"command":"ls"}`。
`pwd` を `ls` に変えるだけで再利用が消える。

### 4-4. 毎回は起きない

pi のログでは同じ重複が 3 回発生したが、停止したのは 1 回だけ。
`:101` のトークン前方一致 (経路 1) が成立している間はそちらで救われ、
KV 列が正規描画からずれた後に初めて経路 2 に落ちて重複ガードに当たる、
と読める。停止した回だけ prompt が前ターンより 26 トークン**短い** (3466 → 3440)
のは、ブリッジで積み上げた KV 列が正規描画より長くドリフトしていた跡。
**未確認**: ドリフトの発生条件と 1 ターンあたりの増分。

### 4-5. 影響

コーディングエージェントは `ls` や同じファイルの再読み込みを日常的に繰り返す。
3.4k トークンの会話で 1 回当たると約 99 秒止まる。

直すとしたら、部分列検索ではなく呼び出し位置 (メッセージ index) で
境界を特定するか、描画にツール呼び出し ID を含めて一意にする。

### 4-6. 対照実験

同じ形の追記のみのツールループを 25 ターン、非ストリーミングとストリーミングの
両方で回したが、**重複呼び出しが無ければ 1 回も外れなかった**
(毎ターン cached > 0、1.0-1.8 s)。プロトコル自体は健全。

## 5. 症状 C: ツールを呼ばずコマンドをテキストで提案する

### 5-1. 再現 (**実測**)

報告と同じ判断点 (`ls` 成功の直後に「3tene とは何？」) を組んで試行:

| 条件 | tool_call | テキストでコマンド提案 |
| --- | ---: | ---: |
| pi 相当の system, temp 1.0 | **0/8** | 0/8 |
| pi 相当の system, temp 0.2 | **0/8** | 3/8 |
| system + ツール優先の明示規則, temp 0.2 | **6/6** | 0/6 |
| system + ツール優先の明示規則, temp 1.0 | **6/6** | 0/6 |

モデルは事前知識で答えてしまい、答えられないときは
「以下を実行してください」とコマンドを提示して止まる。

### 5-2. 温度は主因ではない

ただし付随事実として、**pi は `temperature` を送っていない** (プロキシ記録で確認)。
サーバの既定は `request.temperature ?? 1.0` (`OpenAIModels.swift:300`) なので、
pi 経由の実効温度は 1.0。Mac アプリの推奨既定 0.2 とは別物になっている。
上表のとおり温度を 0.2 にしてもツール呼び出し率は 0/8 のままなので、
これは症状 C の原因ではないが、設定として揃っていない点は記録しておく。

### 5-3. 対処 (サーバ変更不要)

```bash
pi --append-system-prompt "Questions about anything on this machine (files, directories, their purpose or contents) must be answered from the filesystem, not from prior knowledge. Never print a shell command in your reply and never ask the user to run one: call the bash or read tool yourself and act on the result."
```

## 6. 付: pp (プレフィル) の律速要因

`tsugumi-m3pro-status.md` §5「分かっていないこと」1 番目の
「prefill が I/O 律速か計算律速か」に対する測定。

### 6-1. 実測

| 条件 | wall | tok | tok/s |
| --- | ---: | ---: | ---: |
| 512 tok × 4 連続 (ウォーム) | 8.34-8.92 s | 527-540 | **60.3-63.2** |
| 512 tok (アイドル 10 分後の初回) | 42.40 s | 534 | 12.6 |
| 512 tok (プロセス再起動後の初回) | 15.72 s | 536 | 34.1 |
| 1363 tok | 23.93 s | 1363 | 57.0 |
| 2702-2755 tok | 55.0-59.1 s | — | 45.7-49.2 |
| 5386 tok | 138.94 s | 5386 | 38.8 |
| **chunk 32** (512 tok × 3) | 8.60-8.85 s | 518-529 | **59.8-60.4** |

同時サンプリング: GPU `Device Utilization %` 中央値 85-88、
disk0 読み出し 0.2-1.6 GB/s が継続。

### 6-2. 切り分け

- **計算律速ではない (導出)**: 有効 FLOPs は
  MoE `2 × 8 × 3 × 2816 × 704 × 30` = 2.86 GFLOP、
  共有エキスパート 1.07 GFLOP、attention 約 2.1 GFLOP で **約 6 GFLOP/token**。
  61 tok/s なら **約 0.37 TFLOP/s**。M3 Pro 18 コアのピーク (6 TFLOP/s 台) の
  **約 6%**。GPU 使用率 85% は「コマンドが載っている割合」であって演算効率ではない。
- **チャンク単位の費用ではない (実測)**: chunk 32 と 128 の差は 4%。
  チャンク数を 4 倍にしても総時間が変わらない = 費用がトークン単位で積み上がっている。
  `RESULTS.md` §3-3 の「スロット 16 → 96 でも prefill 秒は 9.4 → 9.2」も同じ方向。
- **重み移動量律速と読める (導出)**: 再利用ゼロなら 1 トークンあたり
  top-8 × 3.72 MB × 30 層 = **約 0.9 GB**。61 tok/s で約 55 GB/s 相当になる。
  pp が tg (30 tok/s) の 2 倍しか出ないのは、バッチしてもエキスパート重みを
  トークンごとに読み直していて償却が効いていないことを示す。

### 6-3. 冷えているときの追加ペナルティ

アイドル後の初回は 3-5 倍遅い (12.6-34.1 tok/s)。計測中 swap 使用 974 MB。
ユーザー報告の 75.8 秒 (2654 tok = 35 tok/s) は、この冷えた状態と
2.6k トークンの合わせ技。

**未確認**: 冷える閾値 (時間・メモリ圧) と、ページキャッシュ退避と
スロットバッファのページアウトのどちらが支配的か。

## 7. 手当ての優先順位 (実装は未実施)

1. **症状 C** — ハーネス側の 1 文追加だけ。サーバ変更不要、効果は実測済み。
2. **症状 B** — ツール呼び出し境界の特定を部分列検索から位置ベースに変える。
   影響範囲は `Tokenizer.swift` の 1 関数と `ServerPromptCache` のテスト。
   コーディングエージェント用途では体感が最も大きい。
3. **症状 A** — 最長共通接頭辞での部分再利用。KV 巻き戻し API が要るので
   3 件の中では最も重い。SWA リングの制約を先に確認すること。
