# 13. S3.6 — 画像セッションのプレフィックス再利用

実装・実測: 2026-08-19、M3 Pro 18GB / macOS 15.7.5 / `scratch/gemma4-qat.gturbo` /
16K / 32 スロット / `--draft-block-size 4` / temp 0。
表記は mtp 系と同じ: **実測** / **導出** / **未確認**。

pi の対話モードで画像キャプションを 2 連続で投げると、**毎ターン全再 prefill**
していた (3,700〜4,600 トークンで 1 ターン 18〜20 秒)。原因は 2 つあり、
順番に潰した — S1 で入れた思考の除外 (§0-1) と、Vision の既存仕様 (§0-2)。

---

## 0. 結論 — 3 つ

1. **思考 ON の除外は撤回した** ([10-S1 §5](10-S1-REASONING.md))。ただし
   **キャッシュ経由の思考 ON は素の描き直しと答えが変わる** (§3、**実測**)。
   速度と引き換えの選択であることを明示する。
2. **画像を含む要求もキャッシュに参加する** (§1)。画像スパンは prefill する
   スライス相対のオフセットなので、途中から prefill しても壊れない —
   `PLAN_VISION §4-6` が「壊れる」と書いていたのは、呼び出し側が
   リベースしない前提での話だった。
3. **思考 OFF の画像 2 連続は、キャッシュの有無で出力が md5 一致** (§2)。
   2 ターン目は 366 トークンが cached になり 7.12 s → 4.59 s。

## 1. 何を直したか

| 変更 | 場所 |
| --- | --- |
| 画像 1 枚ごとの SHA-256 をエントリに持つ | `ServerPromptCache`。テキストだけを鍵にしていると「同じ言葉・違う写真」を見分けられず、前の写真の soft token が入った KV から答えてしまう |
| 継続ブリッジが画像 part を描けるようにした | `GFTokenizer.encodeContinuation(parts:)`。`<|image|>` を残して返し、`VisionPromptAssembler` がブリッジの中で widen する |
| ヒット時に「これから prefill するぶんだけ」の `VisionPrefillInput` を返す | `ServerPromptCacheMatch.hit(_:_:vision:)`。スパンはブリッジ内オフセット = スライス相対 |
| 「キャッシュされた prefix と画像は併用不可」を解除 | `CompletionPrefill`。スライス外のスパンは `imageSpanRejection` が今までどおり弾く |
| 参加判定から画像を外した | `ServerModelSession.promptCacheParticipates` はモードだけを見る |

トークン列の先頭一致で当たる経路 (branch 1) だけは、**画像が全部キャッシュ側に
収まっている場合のみ**許す。こちらは描き直し済みプロンプトの絶対オフセットを
持っているので、境界をまたぐスパンはミスにする。

## 2. 思考 OFF での検証 (**実測**)

`sample_imgs/IMG_2113.JPG` → `IMG_2114.JPG` の 2 連続キャプション、tools 宣言あり、
`--prompt-cache-mode off` と `single-prefix` を別プロセスで:

| | cache off | cache on |
| --- | ---: | ---: |
| turn 1: prompt / cached / 壁時計 | 344 / 0 / 6.14 s | 344 / 0 / 5.94 s |
| turn 2: prompt / cached / 壁時計 | 657 / 0 / 7.12 s | 661 / **366** / **4.59 s** |
| 出力 md5 (turn 1 / turn 2) | 6ba0e8c8a4e8 / 2b6b0749314b | **同一** |

**出力は両ターンとも md5 一致。**turn 2 の prompt が 4 トークン多いのは、
キャッシュ側の履歴が生成プロンプトの空 thought channel を含むためで、
これは思考 OFF でも以前からある差である ([10-S1 §5](10-S1-REASONING.md))。

## 3. 思考 ON では答えが変わる (**実測**)

同じ 2 連続を思考 ON (`max_tokens` 1600) で:

| | cache off | cache on |
| --- | ---: | ---: |
| turn 1: prompt / cached / 壁時計 | 342 / 0 / 24.19 s | 342 / 0 / 23.68 s |
| turn 1: 出力 md5 | 7e0b3289c9df | **同一** |
| turn 2: prompt / cached / 壁時計 | 650 / 0 / 25.56 s | 1,085 / **794** / 27.23 s |
| turn 2: 出力 md5 | 71d2dd98f7a5 | **4e709fb3bffd (別)** |

turn 2 のプロンプトが 650 → 1,085 に増えているのが理由である。
**キャッシュ側は turn 1 の思考 (約 450 トークン) を文脈に残したまま**続きを書く。
素の描き直しはクライアントが送り返した答えだけを載せるので、思考は消える。
どちらも `finish=stop` で妥当な答えを返すが、**同じ答えにはならない**。

この 2 ターンでは壁時計も改善していない (25.56 → 27.23 s)。プロンプトが
600 トークン程度だと、再 prefill の節約より思考を持ち回るぶんの decode 増が
勝つためである。**pi の常用 (3,700〜4,600 トークン)** では prefill が支配的なので
逆転する — そちらの実測は §4。

pi は要求ごとに `preserve_thinking: true` を送っており、思考を残す方針自体は
クライアントの意図と一致する。**とはいえ「キャッシュの状態で答えが変わる」ことは
残る**ので、描き直しと一致させたい用途では `--prompt-cache-mode off` を使う。
